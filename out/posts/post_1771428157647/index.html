Retry and Backoff for APIs: What We Learned the Hard Way

We run a service that calls external LLM and agent APIs. When those APIs returned 429 or 503, we retried immediately. That made things worse: we hit rate limits harder and sometimes got temporary bans. Here’s how we fixed it with proper retry and backoff so our service stays within limits and fails in a predictable way.

Why retries are dangerous without backoff

Retrying on transient errors is good. Retrying with no delay is not. If the upstream is overloaded or rate-limiting you, firing the same request again right away increases load and can push the provider to throttle or block you. The goal is to give the system time to recover and to spread our retries so we don’t create a thundering herd.

What we did wrong at first

  • No delay between retries — We caught 429/503 and called the same endpoint again in a loop. A single flaky task could send dozens of requests in a few seconds.
  • Fixed number of retries — We always retried exactly 3 times regardless of error type. For “quota exceeded” we needed to back off longer; for a one-off 503, a short retry was enough.
  • No jitter — When we finally added exponential backoff, many workers restarted at the same time and retried at the same moment. That created spikes and triggered rate limits again.
  • Retrying non-retryable errors — We retried on 4xx (e.g. 400 bad request, 401 unauthorized). Those don’t succeed on retry and just waste time and quota.

    • We assumed “retry a few times” was enough. It wasn’t.

    What we changed

    1. Exponential backoff with cap

    We wait 1s, then 2s, then 4s, then 8s, up to a maximum of 60s. The delay doubles each attempt. That gives the upstream time to recover and keeps our retries from piling up.

    function delayMs(attempt: number): number {
  const base = 1000;
  const max = 60_000;
  const ms = Math.min(base  Math.pow(2, attempt), max);
  return ms;
}

    2. Jitter

    We add random jitter to the delay so not every client backs off in lockstep. We use full jitter: sleep a random value between 0 and the computed delay. That spreads retries over time.

    const delay = delayMs(attempt);
const jittered = Math.random()  delay;
await new Promise((r) => setTimeout(r, jittered));

    3. Retry only on retryable status and errors

    We retry on 429 (rate limit), 503 (unavailable), 502 (bad gateway), and on network/timeout errors. We do not retry on 4xx (except 429) or 5xx like 500 when the provider’s docs say “do not retry.” We also respect Retry-After when present and use it instead of our computed delay when it’s larger.

    4. Per-client and global limits

    We limit retries per request (e.g. 5 attempts) and also track a simple “concurrent outbound” cap so we don’t open hundreds of connections during a burst. If we’re at the cap, we wait or fail fast instead of queuing unbounded retries.

    Observability

    We log each retry with attempt number, status code, and delay. That made it obvious when we were still retrying too aggressively and helped us tune the base delay and cap. Metrics for “retries per minute” and “final failure after N retries” let us see if backoff is working and when we need to escalate (e.g. quota increase or circuit breaker).

    Lessons learned

  • Retry without backoff can make outages and rate limits worse. Exponential backoff plus jitter is a small change with a big impact.
  • Only retry when the error is transient and the operation is idempotent (or at least safe to retry). Document which status codes and errors you retry.
  • Respect Retry-After when the server sends it; it often reflects real capacity.
  • Cap retries and concurrency so one bad upstream doesn’t tie up all your workers. When in doubt, fail fast and let a higher-level process (e.g. task queue) retry later.
