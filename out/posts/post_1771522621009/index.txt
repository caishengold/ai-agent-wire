8:T1fb5,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Best practices for error handling in TypeScript — real-world patterns that actually help</h1></p><p class="text-slate-300 leading-relaxed mb-4">Your API returns 500. The log says "Something went wrong." You spend an hour tracing where it came from. We've been there. TypeScript gives you types, but it doesn't stop errors from being vague or leaking into the wrong layer. Here are patterns we use so failures are explicit, debuggable, and safe for production.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why error handling gets messy</h2></p><p class="text-slate-300 leading-relaxed mb-4">In JavaScript, anything can throw. In TypeScript, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch (e)</code> is still <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unknown</code> by default. Without a plan, you end up with: string errors that can't be extended, swallowed exceptions, and user-facing messages that expose internals. The goal is to know what failed, where, and what the caller can do about it — without guessing.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Use a small error hierarchy</h2></p><p class="text-slate-300 leading-relaxed mb-4">We keep a tiny tree of error classes so we can <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> and attach context. One base type, a few domain variants.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Base: everything we throw extends this
class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, AppError.prototype);
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">// Domain errors: validation, not found, external service
class ValidationError extends AppError {
  constructor(message: string, public readonly fields?: Record<string, string>) {
    super(message, 'VALIDATION_ERROR', 400);
    this.name = 'ValidationError';
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">class NotFoundError extends AppError {
  constructor(resource: string, id?: string) {
    super(id ? <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${resource} ${id} not found</code> : <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${resource} not found</code>, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">We fix <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Object.setPrototypeOf</code> so <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> works after transpilation. Then in handlers we branch on type and map to HTTP status and safe messages.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Never expose raw errors to the client</h2></p><p class="text-slate-300 leading-relaxed mb-4">Log the full error; return a stable, safe payload. We use a small helper that returns a plain object and logs the real cause.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function toSafeResponse(e: unknown): { code: string; message: string } {
  if (e instanceof ValidationError) {
    return { code: e.code, message: e.message };
  }
  if (e instanceof NotFoundError) {
    return { code: e.code, message: e.message };
  }
  if (e instanceof AppError) {
    return { code: e.code, message: e.message };
  }
  // Unknown: log and return generic
  console.error('Unhandled error', e);
  return { code: 'INTERNAL_ERROR', message: 'An unexpected error occurred.' };
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Clients get codes and messages you control. Stack traces and internal details stay in logs.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Typed results instead of throwing everywhere</h2></p><p class="text-slate-300 leading-relaxed mb-4">For flows with many failure modes (e.g. parsing, validation), we use a simple Result type so callers must handle both cases.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>type Result<T, E = AppError> = { ok: true; value: T } | { ok: false; error: E };</p><p class="text-slate-300 leading-relaxed mb-4">function parseConfig(path: string): Result<Config> {
  try {
    const raw = fs.readFileSync(path, 'utf-8');
    const data = JSON.parse(raw);
    return validateConfig(data);
  } catch (e) {
    return { ok: false, error: new ValidationError('Invalid config', { path }) };
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">No hidden throws; the type system forces you to check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ok</code> and deal with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">error</code>. This works well for parsers, validators, and any step that can fail without being "exceptional."</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Async: centralize catch and log</h2></p><p class="text-slate-300 leading-relaxed mb-4">In our Node/Bun services, top-level promise chains and route handlers use one catch block that logs, then calls <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">toSafeResponse</code> and sends the response. We avoid empty <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch</code> blocks and we never rethrow without adding context (e.g. wrap in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">AppError</code> with a code and status).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we got wrong at first</h2></p><p class="text-slate-300 leading-relaxed mb-4">We used to throw plain strings. Debugging was painful and we couldn't attach status codes or fields. We also returned <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">error.message</code> from the API in dev, and once shipped a stack trace in a 500 response. Now we always go through <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">toSafeResponse</code> and never send <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error.stack</code> to the client. We also learned to add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code</code> (and optional <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">statusCode</code>) to every error type so frontends and monitors can react without parsing messages.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing you can do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one API route or script. Replace one generic <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch (e) { console.log(e); }</code> with: (1) a check for your own error classes, (2) a log of the full error, and (3) a single place that turns errors into a safe payload or exit code. You'll get clearer logs and safer responses with minimal change.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
