Best practices for error handling in TypeScript — real-world patterns that actually help

Your API returns 500. The log says "Something went wrong." You spend an hour tracing where it came from. We've been there. TypeScript gives you types, but it doesn't stop errors from being vague or leaking into the wrong layer. Here are patterns we use so failures are explicit, debuggable, and safe for production.

Why error handling gets messy

In JavaScript, anything can throw. In TypeScript, catch (e) is still unknown by default. Without a plan, you end up with: string errors that can't be extended, swallowed exceptions, and user-facing messages that expose internals. The goal is to know what failed, where, and what the caller can do about it — without guessing.

Use a small error hierarchy

We keep a tiny tree of error classes so we can instanceof and attach context. One base type, a few domain variants.

// Base: everything we throw extends this
class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, AppError.prototype);
  }
}
// Domain errors: validation, not found, external service
class ValidationError extends AppError {
  constructor(message: string, public readonly fields?: Record) {
    super(message, 'VALIDATION_ERROR', 400);
    this.name = 'ValidationError';
  }
}
class NotFoundError extends AppError {
  constructor(resource: string, id?: string) {
    super(id ? ${resource} ${id} not found : ${resource} not found, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}

We fix Object.setPrototypeOf so instanceof works after transpilation. Then in handlers we branch on type and map to HTTP status and safe messages.

Never expose raw errors to the client

Log the full error; return a stable, safe payload. We use a small helper that returns a plain object and logs the real cause.

function toSafeResponse(e: unknown): { code: string; message: string } {
  if (e instanceof ValidationError) {
    return { code: e.code, message: e.message };
  }
  if (e instanceof NotFoundError) {
    return { code: e.code, message: e.message };
  }
  if (e instanceof AppError) {
    return { code: e.code, message: e.message };
  }
  // Unknown: log and return generic
  console.error('Unhandled error', e);
  return { code: 'INTERNAL_ERROR', message: 'An unexpected error occurred.' };
}

Clients get codes and messages you control. Stack traces and internal details stay in logs.

Typed results instead of throwing everywhere

For flows with many failure modes (e.g. parsing, validation), we use a simple Result type so callers must handle both cases.

type Result = { ok: true; value: T } | { ok: false; error: E };
function parseConfig(path: string): Result {
  try {
    const raw = fs.readFileSync(path, 'utf-8');
    const data = JSON.parse(raw);
    return validateConfig(data);
  } catch (e) {
    return { ok: false, error: new ValidationError('Invalid config', { path }) };
  }
}

No hidden throws; the type system forces you to check ok and deal with error. This works well for parsers, validators, and any step that can fail without being "exceptional."

Async: centralize catch and log

In our Node/Bun services, top-level promise chains and route handlers use one catch block that logs, then calls toSafeResponse and sends the response. We avoid empty catch blocks and we never rethrow without adding context (e.g. wrap in AppError with a code and status).

What we got wrong at first

We used to throw plain strings. Debugging was painful and we couldn't attach status codes or fields. We also returned error.message from the API in dev, and once shipped a stack trace in a 500 response. Now we always go through toSafeResponse and never send Error.stack to the client. We also learned to add a code (and optional statusCode) to every error type so frontends and monitors can react without parsing messages.

One thing you can do right now

Pick one API route or script. Replace one generic catch (e) { console.log(e); } with: (1) a check for your own error classes, (2) a log of the full error, and (3) a single place that turns errors into a safe payload or exit code. You'll get clearer logs and safer responses with minimal change.
