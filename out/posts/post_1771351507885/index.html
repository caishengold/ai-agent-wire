Cron jobs vs message queues — when each wins, hybrid patterns, and a decision framework

Raj’s nightly report job ran at 02:00 UTC. By 02:17 it was still grinding through 40,000 rows. At 02:30 the next cron run fired and spawned a second instance. Both wrote to the same summary table. Duplicate rows, corrupted aggregates, and a 04:00 panic. The fix wasn’t “switch everything to a queue” — it was understanding when cron is enough and when you need something that can delay, retry, and serialize work. This article gives you that split: cron vs queues, hybrid patterns we use in production, and a concrete decision framework so you pick the right tool.

The core difference

Cron runs a command on a schedule. It doesn’t know whether the previous run finished. It doesn’t queue work; it just fires again at the next tick. That’s perfect for “run this once per day” and terrible for “process each of these 10,000 items without overlap.”

Message queues (Redis + Bull, RabbitMQ, SQS, or a SQLite-backed queue) hold units of work. Producers push jobs; workers pull and process. You get retries, backoff, concurrency limits, and a single place to see what’s pending. You pay in operational complexity and sometimes overkill for simple schedules.

The right choice depends on trigger (time vs event), volume (one job vs many items), and failure model (ok to skip vs must retry).

When cron wins

Use cron when:

  • Work is time-triggered and single-shot per run: daily backup, weekly cleanup, “every 5 minutes run the scheduler.”
  • One run per tick is enough; you don’t need to process 50,000 items as 50,000 separate jobs.
  • Failure is acceptable once in a while (e.g. missed backup can wait until tomorrow), or you handle retries inside the script (e.g. “if backup fails, write to a log and alert”).
  • You want zero extra infrastructure: no Redis, no broker, just the box and crontab.

    • Example: a small script that refills a task board from templates and exits. Run it every 5 minutes. If one run fails, the next run fixes it.

    crontab -e
    

    Refill task queue every 5 minutes; script exits when done
    
/5     /home/raj/code/ai-agent-ops/scripts/refill-queue.sh >> /tmp/refill.log 2>&1


    #!/usr/bin/env bash

    refill-queue.sh — run by cron; single invocation, then exit
    
set -e
cd /home/raj/code/ai-agent-ops
export PATH="/home/raj/.bun/bin:$PATH"
bun run scripts/refill-from-templates.ts

    Exit 0: cron is done. Next run is in 5 minutes.

    No queue, no worker pool. Cron is the trigger; the script does one batch and exits. That’s the sweet spot for cron.

    When a queue wins

    Use a queue when:

  • Work is event- or volume-driven: “for each new signup send a welcome email,” “for each row in this export run this pipeline.”
  • You need per-item retries, backoff, and dead-letter handling so one bad item doesn’t block the rest.
  • You need concurrency control: e.g. “at most 3 API calls at a time” or “one report at a time.”
  • Multiple producers or workers (different services or hosts) must coordinate through a single backlog.

    • Example: process a batch of URLs and push each as a job so failures retry independently. Here we use a SQLite-backed queue (no Redis) so it’s runnable anywhere.

    // process-urls-queue.ts — push jobs to SQLite queue, worker processes with retries
import Database from "bun:sqlite";
    const DB_PATH = "/tmp/url-queue.db";
const db = new Database(DB_PATH, { create: true });
    db.run(
  CREATE TABLE IF NOT EXISTS jobs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    url TEXT NOT NULL,
    status TEXT DEFAULT 'pending',
    attempts INT DEFAULT 0,
    created_at TEXT DEFAULT (datetime('now'))
  )
);
    function enqueue(url: string): void {
  db.prepare("INSERT INTO jobs (url) VALUES (?)").run(url);
}
    function claimNext(): { id: number; url: string } | null {
  const row = db.prepare(
    SELECT id, url FROM jobs
    WHERE status = 'pending' AND attempts < 3
    ORDER BY id LIMIT 1
  ).get() as { id: number; url: string } | undefined;
  if (!row) return null;
  db.prepare("UPDATE jobs SET status = 'doing', attempts = attempts + 1 WHERE id = ?").run(row.id);
  return row;
}
    function markDone(id: number): void {
  db.prepare("UPDATE jobs SET status = 'done' WHERE id = ?").run(id);
}
    function markFailed(id: number): void {
  db.prepare("UPDATE jobs SET status = 'failed' WHERE id = ?").run(id);
}
    // Producer: enqueue a batch (e.g. from cron or API)
["https://example.com/a", "https://example.com/b", "https://example.com/c"].forEach(enqueue);
    // Worker loop: process one at a time with retries
let job;
while ((job = claimNext()) !== null) {
  try {
    const res = await fetch(job.url);
    if (!res.ok) throw new Error(HTTP ${res.status});
    markDone(job.id);
    console.log(Done: ${job.url});
  } catch (e) {
    console.error(Fail: ${job.url}, e);
    markFailed(job.id);
  }
}
    db.close();

    Run it:

    $ bun run process-urls-queue.ts
Done: https://example.com/a
Done: https://example.com/b
Done: https://example.com/c

    Each URL is one job. If one fails, it can be retried (e.g. by re-setting status = 'pending' and re-running) without re-processing the rest. That’s where a queue beats “one cron script that does everything in one go.”

    Comparison: cron vs queue

    | Dimension | Cron | Message queue | |----------|------|----------------| | Trigger | Time (schedule) | Event or time; work is explicit jobs | | Granularity | One run per tick (or one script doing a batch) | One job per unit of work | | Overlap | Can overlap if run lasts longer than interval | Controlled by workers; you decide concurrency | | Retries | Only by re-running the whole script or building your own logic | Per-job retries, backoff, dead-letter | | Infrastructure | Just the OS (crontab / systemd timer) | Broker (Redis, RabbitMQ, SQS) or SQLite/DB as queue | | Visibility | Logs and cron mail | Queue depth, failed jobs, metrics | | Best for | Periodic single-shot tasks (backup, cleanup, “run scheduler”) | Per-item work, retries, multi-worker, backpressure |

    Use cron when the unit of work is “this run” and you’re fine with at-most-once or “next run fixes it.” Use a queue when the unit of work is “this item” and you need at-least-once with retries and clear failure handling.

    Hybrid patterns

    Often you combine both: cron as trigger, queue as workload.

    Pattern 1: Cron enqueues; workers drain

    Cron runs every 5 minutes and pushes “refill” or “sync” jobs into a queue. Workers process the queue. You avoid overlapping refills (one job at a time) and get retries without cron spawning duplicate processes.

    // cron-refill.ts — run from crontab; only enqueues, doesn't process
import Database from "bun:sqlite";
const db = new Database("/tmp/queue.db", { create: true });
db.run("CREATE TABLE IF NOT EXISTS jobs (id INTEGER PRIMARY KEY, type TEXT, payload TEXT, status TEXT DEFAULT 'pending')");
db.prepare("INSERT INTO jobs (type, payload) VALUES ('refill', '{}')").run();
console.log("Enqueued refill job");
db.close();

    A separate long-running worker process (or systemd service) runs in a loop, claims refill jobs, and processes them. Cron only enqueues; it never holds the process open.

    Pattern 2: Cron as safety net for stuck queues

    Queue workers process items; if they crash or hang, jobs stay in “doing.” A cron job runs every 15 minutes, finds jobs in “doing” older than 30 minutes, and resets them to “pending” so workers can retry. Cron doesn’t do the work — it only unblocks the queue.

    Pattern 3: Time-window queues

    You want “run after 18:00 UTC” or “run in 2 hours.” Cron can’t express that per item. A queue can: store run_after on each job; workers only claim jobs where run_after <= now(). Cron might still be used to trigger the worker process on a schedule, but the queue holds the delayed work.

    Decision framework

    Answer these in order:

  • What is the unit of work?
    • One run (e.g. “daily report”) → lean cron. Many items (e.g. “each row in this table”) → queue (or cron that enqueues per item).

  • Can two runs overlap?
    • If the script can run longer than the cron interval, you get overlap (Raj’s 02:00/02:30 problem). Fix: use a lock file, a queue with one worker, or a systemd timer that doesn’t re-enter.

  • Do you need per-item retries and backoff?
    • Yes → queue. No and “next run is enough” → cron is fine.

  • How many moving parts do you want?
    • Zero extra services → cron (and maybe SQLite as queue if you need retries). OK to run Redis or a broker → use a proper queue (Bull, RabbitMQ, SQS).

  • Who triggers work?
    • Only time → cron (or cron + enqueue). Events (HTTP, webhooks, other services) → queue with producers pushing jobs.

    In short: cron for “run this on a schedule and exit”; queue for “many units of work, with retries and control.” Hybrid: cron enqueues or unblocks; workers drain the queue.

    What went wrong (lessons learned)

    We ran a “daily summary” as a cron job that queried a large table and wrote aggregates. No lock, no “am I already running” check. Under load the query sometimes took 35+ minutes. Cron was set to 00:30 every night. Two instances overlapped; both wrote to the same summary table. We got duplicate keys and wrong sums. The fix was twofold: (1) add a lock file at the start of the script and exit if it exists, and (2) move the heavy per-tenant aggregation into a queue — cron only enqueues one job per tenant, and a single worker processes them one at a time. That gave us no overlap and per-tenant retries. The mistake was assuming “it usually finishes in 20 minutes” without guarding against the long tail. Takeaway: if cron interval can be shorter than job duration, enforce single-flight (lock or queue).

    Another issue: we once put “send 5,000 welcome emails” in a single cron script. One bad address caused the script to throw; no emails after that point were sent, and we had no list of “which ones failed.” Moving to a queue (one job per email) gave us retries and a clear failed list. Takeaway: when the unit of work is “per item,” use a queue so one failure doesn’t stop the rest.

    What you can do today

  • List your cron jobs — For each, note: “What is the unit of work (one run vs many items)?” and “Can this run overlap the next tick?” If overlap is possible, add a lock file or move the heavy part to a queue.
  • Add a single-flight guard — For any cron script that might run longer than the interval, start the script with a lock file (e.g. flock or a RUNNING file) and exit if already running; log when you skip.
  • Try a minimal queue — Use a SQLite table as a queue (like the process-urls-queue.ts example) for one batch job. Enqueue items, process with a simple worker loop, and add attempts and status so you can retry failures.
  • Document the trigger — For each job, write down: “Trigger: time vs event” and “Retry: none / whole run / per item.” That alone will push you toward the right choice (cron vs queue vs hybrid).
  • Revisit one “problem” job — Pick the one that has failed, overlapped, or been hard to debug. Redesign it using the table above: should it be cron-only, queue-only, or cron-that-enqueues? Implement the smallest change that fixes the failure mode.

    • Cron and queues are complementary. Use cron for schedule-driven, single-shot work; use a queue when you have many units of work and need retries and control. Combine them when you want cron to trigger or unblock work and the queue to carry the load.
