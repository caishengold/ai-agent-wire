8:T4bda,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Cron jobs vs message queues — when each wins, hybrid patterns, and a decision framework</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s nightly report job ran at 02:00 UTC. By 02:17 it was still grinding through 40,000 rows. At 02:30 the next cron run fired and spawned a second instance. Both wrote to the same summary table. Duplicate rows, corrupted aggregates, and a 04:00 panic. The fix wasn’t “switch everything to a queue” — it was understanding <strong>when</strong> cron is enough and when you need something that can delay, retry, and serialize work. This article gives you that split: cron vs queues, hybrid patterns we use in production, and a concrete decision framework so you pick the right tool.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The core difference</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cron</strong> runs a command on a schedule. It doesn’t know whether the previous run finished. It doesn’t queue work; it just fires again at the next tick. That’s perfect for “run this once per day” and terrible for “process each of these 10,000 items without overlap.”</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Message queues</strong> (Redis + Bull, RabbitMQ, SQS, or a SQLite-backed queue) hold units of work. Producers push jobs; workers pull and process. You get retries, backoff, concurrency limits, and a single place to see what’s pending. You pay in operational complexity and sometimes overkill for simple schedules.</p><p class="text-slate-300 leading-relaxed mb-4">The right choice depends on <strong>trigger</strong> (time vs event), <strong>volume</strong> (one job vs many items), and <strong>failure model</strong> (ok to skip vs must retry).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When cron wins</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use cron when:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Work is <strong>time-triggered</strong> and <strong>single-shot</strong> per run: daily backup, weekly cleanup, “every 5 minutes run the scheduler.”</li>
<li class="ml-4 list-disc text-slate-300">One run per tick is enough; you don’t need to process 50,000 items as 50,000 separate jobs.</li>
<li class="ml-4 list-disc text-slate-300">Failure is acceptable once in a while (e.g. missed backup can wait until tomorrow), or you handle retries inside the script (e.g. “if backup fails, write to a log and alert”).</li>
<li class="ml-4 list-disc text-slate-300">You want <strong>zero extra infrastructure</strong>: no Redis, no broker, just the box and crontab.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: a small script that refills a task board from templates and exits. Run it every 5 minutes. If one run fails, the next run fixes it.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">crontab -e</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Refill task queue every 5 minutes; script exits when done</h1>
<em>/5 </em> <em> </em> <em> /home/raj/code/ai-agent-ops/scripts/refill-queue.sh >> /tmp/refill.log 2>&1
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>#!/usr/bin/env bash
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">refill-queue.sh — run by cron; single invocation, then exit</h1>
set -e
cd /home/raj/code/ai-agent-ops
export PATH="/home/raj/.bun/bin:$PATH"
bun run scripts/refill-from-templates.ts
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Exit 0: cron is done. Next run is in 5 minutes.</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">No queue, no worker pool. Cron is the trigger; the script does one batch and exits. That’s the sweet spot for cron.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When a queue wins</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use a queue when:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Work is <strong>event- or volume-driven</strong>: “for each new signup send a welcome email,” “for each row in this export run this pipeline.”</li>
<li class="ml-4 list-disc text-slate-300">You need <strong>per-item retries</strong>, backoff, and dead-letter handling so one bad item doesn’t block the rest.</li>
<li class="ml-4 list-disc text-slate-300">You need <strong>concurrency control</strong>: e.g. “at most 3 API calls at a time” or “one report at a time.”</li>
<li class="ml-4 list-disc text-slate-300">Multiple producers or workers (different services or hosts) must coordinate through a single backlog.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: process a batch of URLs and push each as a job so failures retry independently. Here we use a SQLite-backed queue (no Redis) so it’s runnable anywhere.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// process-urls-queue.ts — push jobs to SQLite queue, worker processes with retries
import Database from "bun:sqlite";</p><p class="text-slate-300 leading-relaxed mb-4">const DB_PATH = "/tmp/url-queue.db";
const db = new Database(DB_PATH, { create: true });</p><p class="text-slate-300 leading-relaxed mb-4">db.run(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  CREATE TABLE IF NOT EXISTS jobs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    url TEXT NOT NULL,
    status TEXT DEFAULT 'pending',
    attempts INT DEFAULT 0,
    created_at TEXT DEFAULT (datetime('now'))
  )
</code>);</p><p class="text-slate-300 leading-relaxed mb-4">function enqueue(url: string): void {
  db.prepare("INSERT INTO jobs (url) VALUES (?)").run(url);
}</p><p class="text-slate-300 leading-relaxed mb-4">function claimNext(): { id: number; url: string } | null {
  const row = db.prepare(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
    SELECT id, url FROM jobs
    WHERE status = 'pending' AND attempts < 3
    ORDER BY id LIMIT 1
  </code>).get() as { id: number; url: string } | undefined;
  if (!row) return null;
  db.prepare("UPDATE jobs SET status = 'doing', attempts = attempts + 1 WHERE id = ?").run(row.id);
  return row;
}</p><p class="text-slate-300 leading-relaxed mb-4">function markDone(id: number): void {
  db.prepare("UPDATE jobs SET status = 'done' WHERE id = ?").run(id);
}</p><p class="text-slate-300 leading-relaxed mb-4">function markFailed(id: number): void {
  db.prepare("UPDATE jobs SET status = 'failed' WHERE id = ?").run(id);
}</p><p class="text-slate-300 leading-relaxed mb-4">// Producer: enqueue a batch (e.g. from cron or API)
["https://example.com/a", "https://example.com/b", "https://example.com/c"].forEach(enqueue);</p><p class="text-slate-300 leading-relaxed mb-4">// Worker loop: process one at a time with retries
let job;
while ((job = claimNext()) !== null) {
  try {
    const res = await fetch(job.url);
    if (!res.ok) throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HTTP ${res.status}</code>);
    markDone(job.id);
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Done: ${job.url}</code>);
  } catch (e) {
    console.error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Fail: ${job.url}</code>, e);
    markFailed(job.id);
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run it:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run process-urls-queue.ts
Done: https://example.com/a
Done: https://example.com/b
Done: https://example.com/c
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Each URL is one job. If one fails, it can be retried (e.g. by re-setting <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status = 'pending'</code> and re-running) without re-processing the rest. That’s where a queue beats “one cron script that does everything in one go.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: cron vs queue</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Dimension | Cron | Message queue |
|----------|------|----------------|
| <strong>Trigger</strong> | Time (schedule) | Event or time; work is explicit jobs |
| <strong>Granularity</strong> | One run per tick (or one script doing a batch) | One job per unit of work |
| <strong>Overlap</strong> | Can overlap if run lasts longer than interval | Controlled by workers; you decide concurrency |
| <strong>Retries</strong> | Only by re-running the whole script or building your own logic | Per-job retries, backoff, dead-letter |
| <strong>Infrastructure</strong> | Just the OS (crontab / systemd timer) | Broker (Redis, RabbitMQ, SQS) or SQLite/DB as queue |
| <strong>Visibility</strong> | Logs and cron mail | Queue depth, failed jobs, metrics |
| <strong>Best for</strong> | Periodic single-shot tasks (backup, cleanup, “run scheduler”) | Per-item work, retries, multi-worker, backpressure |</p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>cron</strong> when the unit of work is “this run” and you’re fine with at-most-once or “next run fixes it.” Use a <strong>queue</strong> when the unit of work is “this item” and you need at-least-once with retries and clear failure handling.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Hybrid patterns</h2></p><p class="text-slate-300 leading-relaxed mb-4">Often you combine both: <strong>cron as trigger</strong>, <strong>queue as workload</strong>.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 1: Cron enqueues; workers drain</h3></p><p class="text-slate-300 leading-relaxed mb-4">Cron runs every 5 minutes and pushes “refill” or “sync” jobs into a queue. Workers process the queue. You avoid overlapping refills (one job at a time) and get retries without cron spawning duplicate processes.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// cron-refill.ts — run from crontab; only enqueues, doesn't process
import Database from "bun:sqlite";
const db = new Database("/tmp/queue.db", { create: true });
db.run("CREATE TABLE IF NOT EXISTS jobs (id INTEGER PRIMARY KEY, type TEXT, payload TEXT, status TEXT DEFAULT 'pending')");
db.prepare("INSERT INTO jobs (type, payload) VALUES ('refill', '{}')").run();
console.log("Enqueued refill job");
db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">A separate long-running worker process (or systemd service) runs in a loop, claims <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">refill</code> jobs, and processes them. Cron only enqueues; it never holds the process open.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 2: Cron as safety net for stuck queues</h3></p><p class="text-slate-300 leading-relaxed mb-4">Queue workers process items; if they crash or hang, jobs stay in “doing.” A cron job runs every 15 minutes, finds jobs in “doing” older than 30 minutes, and resets them to “pending” so workers can retry. Cron doesn’t do the work — it only unblocks the queue.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 3: Time-window queues</h3></p><p class="text-slate-300 leading-relaxed mb-4">You want “run after 18:00 UTC” or “run in 2 hours.” Cron can’t express that per item. A queue can: store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run_after</code> on each job; workers only claim jobs where <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run_after <= now()</code>. Cron might still be used to trigger the worker process on a schedule, but the queue holds the delayed work.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Decision framework</h2></p><p class="text-slate-300 leading-relaxed mb-4">Answer these in order:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>What is the unit of work?</strong>  </li>
   One run (e.g. “daily report”) → lean cron. Many items (e.g. “each row in this table”) → queue (or cron that enqueues per item).</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Can two runs overlap?</strong>  </li>
   If the script can run longer than the cron interval, you get overlap (Raj’s 02:00/02:30 problem). Fix: use a lock file, a queue with one worker, or a systemd timer that doesn’t re-enter.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Do you need per-item retries and backoff?</strong>  </li>
   Yes → queue. No and “next run is enough” → cron is fine.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>How many moving parts do you want?</strong>  </li>
   Zero extra services → cron (and maybe SQLite as queue if you need retries). OK to run Redis or a broker → use a proper queue (Bull, RabbitMQ, SQS).</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Who triggers work?</strong>  </li>
   Only time → cron (or cron + enqueue). Events (HTTP, webhooks, other services) → queue with producers pushing jobs.</p><p class="text-slate-300 leading-relaxed mb-4">In short: <strong>cron for “run this on a schedule and exit”; queue for “many units of work, with retries and control.”</strong> Hybrid: cron enqueues or unblocks; workers drain the queue.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">We ran a “daily summary” as a cron job that queried a large table and wrote aggregates. No lock, no “am I already running” check. Under load the query sometimes took 35+ minutes. Cron was set to 00:30 every night. Two instances overlapped; both wrote to the same summary table. We got duplicate keys and wrong sums. The fix was twofold: (1) add a lock file at the start of the script and exit if it exists, and (2) move the heavy per-tenant aggregation into a queue — cron only enqueues one job per tenant, and a single worker processes them one at a time. That gave us no overlap and per-tenant retries. The mistake was assuming “it usually finishes in 20 minutes” without guarding against the long tail. <strong>Takeaway:</strong> if cron interval can be shorter than job duration, enforce single-flight (lock or queue).</p><p class="text-slate-300 leading-relaxed mb-4">Another issue: we once put “send 5,000 welcome emails” in a single cron script. One bad address caused the script to throw; no emails after that point were sent, and we had no list of “which ones failed.” Moving to a queue (one job per email) gave us retries and a clear failed list. <strong>Takeaway:</strong> when the unit of work is “per item,” use a queue so one failure doesn’t stop the rest.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>List your cron jobs</strong> — For each, note: “What is the unit of work (one run vs many items)?” and “Can this run overlap the next tick?” If overlap is possible, add a lock file or move the heavy part to a queue.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a single-flight guard</strong> — For any cron script that might run longer than the interval, start the script with a lock file (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flock</code> or a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RUNNING</code> file) and exit if already running; log when you skip.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Try a minimal queue</strong> — Use a SQLite table as a queue (like the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process-urls-queue.ts</code> example) for one batch job. Enqueue items, process with a simple worker loop, and add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">attempts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code> so you can retry failures.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document the trigger</strong> — For each job, write down: “Trigger: time vs event” and “Retry: none / whole run / per item.” That alone will push you toward the right choice (cron vs queue vs hybrid).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Revisit one “problem” job</strong> — Pick the one that has failed, overlapped, or been hard to debug. Redesign it using the table above: should it be cron-only, queue-only, or cron-that-enqueues? Implement the smallest change that fixes the failure mode.</li></p><p class="text-slate-300 leading-relaxed mb-4">Cron and queues are complementary. Use cron for schedule-driven, single-shot work; use a queue when you have many units of work and need retries and control. Combine them when you want cron to trigger or unblock work and the queue to carry the load.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
