8:T4b69,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Automating Git workflows — hooks, CI triggers, auto-changelog, branch protection</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a feature on 2026-01-15. The merge went to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> without a required review because someone had pushed with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--no-verify</code> and the only gate was a local hook. By the time CI ran, the branch was already merged. A week later, someone asked what changed in that release — no changelog, no consistent tags. They fixed it by layering <strong>Git hooks</strong> (local, fast), <strong>CI triggers</strong> (shared truth), <strong>auto-changelog</strong> (release docs), and <strong>branch protection</strong> (no bypass). Here’s what they did and what broke.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What each layer does</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Layer | Runs where | Purpose |
|-------|------------|---------|
| <strong>Git hooks</strong> | Developer machine, on commit/push | Catch mistakes before they leave the laptop: lint, format, fast checks. |
| <strong>CI</strong> | Server (GitHub Actions, GitLab CI, etc.) | Same checks for everyone; integration tests, builds; required before merge. |
| <strong>Auto-changelog</strong> | CI or release script | Generate CHANGELOG from commits or tags so humans don’t forget. |
| <strong>Branch protection</strong> | Host (GitHub, GitLab, etc.) | Enforce rules: no direct push to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code>, require PR, require status checks. |</p><p class="text-slate-300 leading-relaxed mb-4">Hooks are fast and local; CI is the source of truth. Branch protection makes CI mandatory before merge. Changelog automation keeps release notes in sync with commits.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Git hooks — fast local checks</h2></p><p class="text-slate-300 leading-relaxed mb-4">Hooks live in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.git/hooks/</code>. Common ones: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pre-commit</code> (before the commit is created) and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pre-push</code> (before data is sent to the remote). They don’t run on the server and aren’t versioned by default, so teams usually install them via a script or a hook manager (e.g. pre-commit, Husky).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example 1: pre-commit that runs format and lint.</strong> Put this in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.git/hooks/pre-commit</code> and run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">chmod +x .git/hooks/pre-commit</code>. The script runs only on staged files so it stays fast.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>#!/bin/sh
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.git/hooks/pre-commit — format and lint staged files only</h1>
set -e
REPO_ROOT="$(git rev-parse --show-toplevel)"
cd "$REPO_ROOT"</p><p class="text-slate-300 leading-relaxed mb-4">echo "Running pre-commit checks..."</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Staged files (added or modified)</h1>
STAGED=$(git diff --cached --name-only --diff-filter=ACM)</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Format check: if Prettier is present, run on staged JS/TS/JSON</h1>
if [ -n "$STAGED" ] && command -v npx >/dev/null 2>&1 && [ -f "$REPO_ROOT/package.json" ]; then
  echo "$STAGED" | grep -E '\.(js|ts|tsx|json)$' | xargs -r npx prettier --check 2>/dev/null || {
    echo "Pre-commit failed: run 'npx prettier --write' on staged files."
    exit 1
  }
  # Lint only staged JS/TS (avoid linting whole tree)
  FILES=$(echo "$STAGED" | grep -E '\.(js|ts|tsx)$' || true)
  if [ -n "$FILES" ]; then
    echo "$FILES" | xargs npx eslint --max-warnings 0 || {
      echo "Pre-commit failed: fix ESLint errors above."
      exit 1
    }
  fi
fi</p><p class="text-slate-300 leading-relaxed mb-4">echo "Pre-commit passed."
exit 0
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">To share the hook, keep a canonical copy in the repo and install it from a script. Example install script:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>#!/bin/bash
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">scripts/install-hooks.sh — run once after clone (e.g. npm postinstall or README step)</h1>
REPO_ROOT="$(git rev-parse --show-toplevel)"
for hook in pre-commit pre-push; do
  SRC="$REPO_ROOT/scripts/hooks/$hook"
  DST="$REPO_ROOT/.git/hooks/$hook"
  if [ -f "$SRC" ]; then
    cp "$SRC" "$DST"
    chmod +x "$DST"
    echo "Installed $hook hook."
  fi
done
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Terminal output when the hook runs and passes:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ git add src/parser.ts && git commit -m "fix: null check in parser"
Running pre-commit checks...
Pre-commit passed.
[main a1b2c3d] fix: null check in parser
 1 file changed, 2 insertions(+), 1 deletion(-)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If ESLint finds issues, the hook exits non-zero and Git aborts the commit. Keep pre-commit under about 10 seconds; put the full test suite in CI.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">CI triggers — one source of truth</h2></p><p class="text-slate-300 leading-relaxed mb-4">CI runs on push or pull request (configurable). It’s the place for tests, builds, and later changelog generation. Hooks can be bypassed; branch protection plus CI cannot (for protected branches).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example 2: GitHub Actions workflow</strong> that runs on push and pull request to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code>, and fails if lint or tests fail. This is the same “source of truth” you’ll require in branch protection.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.github/workflows/ci.yml</h1>
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npx prettier --check "src/*<em>/</em>.{js,ts,tsx,json}"
      - run: npx eslint src/ --max-warnings 0
      - run: npm test -- --run
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">When Aiko (or anyone) opens a PR to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code>, this workflow runs. Branch protection can then require the “lint-and-test” job to pass before merge, so no one can merge failing code even if they bypass local hooks.</p><p class="text-slate-300 leading-relaxed mb-4">Example CI run (conceptually):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Run npx eslint src/ --max-warnings 0
...
Run npm test -- --run
  ✓ 12 tests passed (3.2s)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Auto-changelog — release notes from commits</h2></p><p class="text-slate-300 leading-relaxed mb-4">Manual changelogs get out of date. Auto-changelog tools (e.g. conventional-changelog, standard-version, release-please) generate entries from commit messages, often using Conventional Commits (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">feat:</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">fix:</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">BREAKING CHANGE:</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: generating CHANGELOG with conventional-changelog (CLI).</strong> Install and run in CI or a release script:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">One-time: npm install -D conventional-changelog-cli conventional-changelog-conventionalcommits</h1>
npx conventional-changelog -p conventionalcommits -i CHANGELOG.md -s
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This appends a new section to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CHANGELOG.md</code> from the last tag to HEAD. Run it when cutting a release (e.g. before or after <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm version</code>), not on every merge. Example output after running:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ npx conventional-changelog -p conventionalcommits -i CHANGELOG.md -s</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">CHANGELOG.md now has a new section at the top, e.g.:</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">## [1.2.0] - 2026-02-12</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">### Features</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4"><em> add null check in parser (a1b2c3d)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">### Bug Fixes</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4"></em> fix login redirect loop (b2c3d4e)</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Branch protection strategies</h2></p><p class="text-slate-300 leading-relaxed mb-4">Branch protection is configured on the host (GitHub, GitLab, Bitbucket). It doesn’t run scripts; it enforces rules. Typical settings for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Require a pull request</strong> before merging (optionally require one or more approvals).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Require status checks</strong> to pass (e.g. the “lint-and-test” job from CI).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Disallow direct push</strong> to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> so all changes go through a branch and PR.</li>
<li class="ml-4 list-disc text-slate-300">Optionally: require linear history, restrict who can push, or require signed commits.</li></p><p class="text-slate-300 leading-relaxed mb-4">That way, even if someone uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--no-verify</code>, the push goes to a branch; CI runs; and merge to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> is blocked until CI is green.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: when to use what</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Hooks only</strong> | Instant feedback, no server. | Can be skipped; not shared; must be installed. | Solo or small team; catch lint/format before push. |
| <strong>CI only</strong> | Shared, auditable; can’t be bypassed for merge. | Slower (every push/PR); needs host config. | Any team; “everyone runs the same checks.” |
| <strong>Hooks + CI</strong> | Fast local path + shared gate. | Two places to keep in sync (same lint in both). | Default for most teams. |
| <strong>Branch protection</strong> | Enforces PR + status checks; prevents direct push to main. | Host-specific; overkill for single-maintainer repos. | Shared repo where <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> must stay deployable. |
| <strong>Auto-changelog</strong> | Consistent release notes; less human error. | Needs conventional commits or tags. | When you ship versions and need a CHANGELOG. |</p><p class="text-slate-300 leading-relaxed mb-4">We use <strong>hooks + CI + branch protection</strong> on every shared repo; we add <strong>auto-changelog</strong> when we tag releases and maintain a CHANGELOG.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team rolled out hooks and branch protection together. Three things bit them.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. Hook and CI disagreed.</strong> The pre-commit hook ran <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">eslint .</code> (whole tree); CI ran <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">eslint src/</code>. Omar had an uncommitted file in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scripts/</code> that passed in CI but failed locally. Result: “CI passes but I can’t commit.” They aligned both to the same command and scope (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npx eslint src/ --max-warnings 0</code>) and documented it in the README. Lesson: <strong>run the same lint command (and scope) in the hook and in CI.</strong></p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. Changelog only on release.</strong> They ran the changelog generator only when cutting a release. The first time they ran it, they pointed it at the whole history instead of “since last tag” and got one giant block (200+ commits in a single section). Fix: generate changelog from the <strong>previous tag</strong> to HEAD only; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">conventional-changelog</code> does this by default when tags exist. They now run it at release time from last tag so the CHANGELOG stays one section per version.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. Heavy work in pre-commit.</strong> Another team put the full test suite in pre-commit. Commits took 2–3 minutes and people started using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--no-verify</code> regularly. Fix: keep pre-commit to format + lint + very fast unit tests (e.g. under 10 seconds); run the full suite in CI.</p><p class="text-slate-300 leading-relaxed mb-4">A smaller surprise: branch protection “require status checks” needed the exact job name as it appears in the GitHub UI. They had named the job <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">build</code> but added a second job later and had to list both. <strong>Use stable, clear job names</strong> and confirm they match what the host shows in “Required status checks.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaways — what you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add a pre-commit hook</strong> that runs your linter (and optionally formatter) on staged files. Store the script in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scripts/hooks/pre-commit</code> and add a one-line install step to your README or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm postinstall</code> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">./scripts/install-hooks.sh</code>).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Turn on a minimal CI workflow</strong> (lint + test) on push and PR to your main branch. Use the same lint command and scope as in the hook so behaviour is consistent.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Enable branch protection on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code></strong>: require a pull request and require the CI status check to pass. Disallow direct pushes so every change is reviewed and tested.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Adopt Conventional Commits</strong> (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">feat:</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">fix:</code>, etc.) and add an auto-changelog step to your release process (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">conventional-changelog -p conventionalcommits -i CHANGELOG.md -s</code> before tagging).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document the pipeline</strong> in the README: how to install hooks, what CI runs, and how to cut a release (including changelog). New joiners (and future you) will thank you.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once hooks, CI, auto-changelog, and branch protection are in place, “it worked on my machine” and “we forgot to document that” become much rarer — because the process enforces checks and keeps release notes tied to commits.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
