Creating effective TypeScript API documentation with Swagger

> Aiko’s team added three new routes to their proxy. The OpenAPI spec was still the old one. A partner integrated against the spec, got 400s on the new fields, and support spent two days tracing the mismatch. We learned the hard way: docs that drift from code are worse than no docs. Here’s how we keep TypeScript APIs and Swagger (OpenAPI) in sync, with one source of truth and minimal manual upkeep.

Why documentation drifts (and why it hurts)

TypeScript gives you types at compile time; it doesn’t publish them. If you write an OpenAPI spec by hand, every new route or changed request body is a chance to forget to update the spec. Downstream clients and QA then rely on stale docs, and failures show up as "your API doesn’t match the docs" — which is true, but the fix is process, not more typing.

We run a small proxy (cursor-proxy.ts) that exposes health, stats, dashboard, and a SQL query endpoint. We had a hand-maintained spec until a client broke on a field we’d renamed. We switched to generating the OpenAPI spec from the same TypeScript server that handles requests. The spec is now an artifact of the code, not a parallel document.

One source of truth: code or spec?

You have two realistic options:

| Approach | Pros | Cons | |----------|------|------| | Code-first — generate OpenAPI from routes/types | Spec always matches server. No duplicate typing. | Schema richness depends on what you export (e.g. JSDoc, Zod, or explicit schema objects). | | Spec-first — write OpenAPI, generate types/code | Single contract; clients and server align to it. | You must regenerate server types or keep code in sync manually; easy to drift if discipline slips. |

We chose code-first because our team is small and we change the proxy often. Our script (tool-api-doc-gen-2026-02-12-08-54.ts) scans the route table, extracts method, path, and request/response shapes we define in TypeScript, and writes docs/openapi/cursor-proxy.json. Anyone adding a route knows they need to expose a shape the generator can see — and we run the generator in CI so PRs fail if someone forgets to regenerate.

What to put in the spec (and what to skip)

Not every internal type belongs in the API docs. We only document public request and response shapes: the JSON bodies and query/path params that a client must send or can rely on. Internal helpers, DB row types, and pipeline intermediates stay out of the OpenAPI schemas. That keeps the spec short and stable.

For each route we document:

  • Method and path — e.g. GET /health, POST /query
  • Auth — which routes need Authorization: Bearer (we use a single token for server-to-server)
  • Request body — JSON schema for POST/PUT (e.g. query, limit for the SQL endpoint)
  • Response — success shape and, where useful, one or two error shapes (e.g. 400, 401)

    • We avoid over-documenting internal error codes or every possible 4xx unless they’re part of the contract (e.g. "retry after 429").

    Practical setup: TypeScript types → OpenAPI

    You don’t need to hand-write JSON Schema for every DTO. If your routes already use typed request/response objects, you can map them to OpenAPI schema objects once and reuse.

    Example: a minimal route type and how we might describe it in the generator:

    // Example: route handler shape we use in cursor-proxy
interface QueryBody {
  query: string;
  limit?: number;
}
    // In the OpenAPI generator we build a schema object like:
const queryBodySchema = {
  type: "object",
  required: ["query"],
  properties: {
    query: { type: "string", description: "SQL query (read-only, no DROP/ALTER)" },
    limit: { type: "integer", minimum: 1, maximum: 1000, default: 100 },
  },
};

    The generator then attaches this to the POST /query path. We keep our route table in TypeScript; the script reads it and emits the spec. So the "source of truth" for paths and methods is the code; the "source of truth" for request/response shape is either the same types (if we export schema-like objects) or a small set of schema definitions we maintain next to the routes.

    If you use Zod, you can derive OpenAPI from your schemas with libraries like zod-openapi or @asteasolutions/zod-to-openapi, so one schema gives you runtime validation and docs. We haven’t adopted that yet; our current script uses explicit schema objects that mirror the types we use in the proxy.

    Keeping the spec fresh

  • Regenerate after route changes — Run the generator (e.g. bun run scripts/tool-api-doc-gen-2026-02-12-08-54.ts) after any change to routes or public request/response shapes. We document this in the script header and in the README.
  • CI check — Run the generator and diff the output (or commit the generated file and fail if it’s modified without a committed change). That way "forgot to regenerate" is caught before merge.
  • Validate the spec — Use npx @redocly/cli lint docs/openapi/cursor-proxy.json (or any OpenAPI 3.x linter) so invalid refs or wrong types are caught early.

    • Gotchas we ran into

  • RegExp reuse — Our first generator used a global RegExp with the g flag and reused it across routes. The regex’s lastIndex wasn’t reset, so some paths were mis-parsed. We now create a new regex per route or reset lastIndex. If you scan routes with regex, avoid shared state.
  • Auth in the spec — We document that /stats and /dashboard require the bearer token. If the spec says nothing, a client might assume everything is public and then get 401s; if the spec is wrong, they send the token to the wrong place. One sentence per route or a single security block at the top helps.
  • Optional vs required* — Mark optional query params and body fields correctly. We had limit as required in the spec while the server treated it as optional with a default; clients started sending limit: 100 everywhere. Harmless but noisy. Align spec and server defaults.

    • Takeaway

    Pick one source of truth (code or spec) and automate the other. We generate OpenAPI from our TypeScript proxy so the spec can’t drift without CI catching it. Document only public request/response shapes, run the generator after every route or contract change, and validate the spec with a linter. Next step: run your generator once, open the output in Swagger UI or Redoc, and fix the first route that doesn’t match what clients actually need.
