8:T2d60,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Creating effective TypeScript API documentation with Swagger</h1></p><p class="text-slate-300 leading-relaxed mb-4">> Aiko’s team added three new routes to their proxy. The OpenAPI spec was still the old one. A partner integrated against the spec, got 400s on the new fields, and support spent two days tracing the mismatch. We learned the hard way: docs that drift from code are worse than no docs. Here’s how we keep TypeScript APIs and Swagger (OpenAPI) in sync, with one source of truth and minimal manual upkeep.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why documentation drifts (and why it hurts)</h2></p><p class="text-slate-300 leading-relaxed mb-4">TypeScript gives you types at compile time; it doesn’t publish them. If you write an OpenAPI spec by hand, every new route or changed request body is a chance to forget to update the spec. Downstream clients and QA then rely on stale docs, and failures show up as "your API doesn’t match the docs" — which is true, but the fix is process, not more typing.</p><p class="text-slate-300 leading-relaxed mb-4">We run a small proxy (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cursor-proxy.ts</code>) that exposes health, stats, dashboard, and a SQL query endpoint. We had a hand-maintained spec until a client broke on a field we’d renamed. We switched to <strong>generating</strong> the OpenAPI spec from the same TypeScript server that handles requests. The spec is now an artifact of the code, not a parallel document.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One source of truth: code or spec?</h2></p><p class="text-slate-300 leading-relaxed mb-4">You have two realistic options:</p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons |
|----------|------|------|
| <strong>Code-first</strong> — generate OpenAPI from routes/types | Spec always matches server. No duplicate typing. | Schema richness depends on what you export (e.g. JSDoc, Zod, or explicit schema objects). |
| <strong>Spec-first</strong> — write OpenAPI, generate types/code<strong> | Single contract; clients and server align to it. | You must regenerate server types or keep code in sync manually; easy to drift if discipline slips. |</p><p class="text-slate-300 leading-relaxed mb-4">We chose code-first because our team is small and we change the proxy often. Our script (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">tool-api-doc-gen-2026-02-12-08-54.ts</code>) scans the route table, extracts method, path, and request/response shapes we define in TypeScript, and writes <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docs/openapi/cursor-proxy.json</code>. Anyone adding a route knows they need to expose a shape the generator can see — and we run the generator in CI so PRs fail if someone forgets to regenerate.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What to put in the spec (and what to skip)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Not every internal type belongs in the API docs. We only document </strong>public<strong> request and response shapes: the JSON bodies and query/path params that a client must send or can rely on. Internal helpers, DB row types, and pipeline intermediates stay out of the OpenAPI schemas. That keeps the spec short and stable.</p><p class="text-slate-300 leading-relaxed mb-4">For each route we document:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"></strong>Method and path<strong> — e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">GET /health</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">POST /query</code></li>
<li class="ml-4 list-disc text-slate-300"></strong>Auth<strong> — which routes need <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer <token></code> (we use a single token for server-to-server)</li>
<li class="ml-4 list-disc text-slate-300"></strong>Request body<strong> — JSON schema for POST/PUT (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">query</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">limit</code> for the SQL endpoint)</li>
<li class="ml-4 list-disc text-slate-300"></strong>Response<strong> — success shape and, where useful, one or two error shapes (e.g. 400, 401)</li></p><p class="text-slate-300 leading-relaxed mb-4">We avoid over-documenting internal error codes or every possible 4xx unless they’re part of the contract (e.g. "retry after 429").</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical setup: TypeScript types → OpenAPI</h2></p><p class="text-slate-300 leading-relaxed mb-4">You don’t need to hand-write JSON Schema for every DTO. If your routes already use typed request/response objects, you can map them to OpenAPI schema objects once and reuse.</p><p class="text-slate-300 leading-relaxed mb-4">Example: a minimal route type and how we might describe it in the generator:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Example: route handler shape we use in cursor-proxy
interface QueryBody {
  query: string;
  limit?: number;
}</p><p class="text-slate-300 leading-relaxed mb-4">// In the OpenAPI generator we build a schema object like:
const queryBodySchema = {
  type: "object",
  required: ["query"],
  properties: {
    query: { type: "string", description: "SQL query (read-only, no DROP/ALTER)" },
    limit: { type: "integer", minimum: 1, maximum: 1000, default: 100 },
  },
};
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The generator then attaches this to the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">POST /query</code> path. We keep our route table in TypeScript; the script reads it and emits the spec. So the "source of truth" for paths and methods is the code; the "source of truth" for request/response shape is either the same types (if we export schema-like objects) or a small set of schema definitions we maintain next to the routes.</p><p class="text-slate-300 leading-relaxed mb-4">If you use </strong>Zod<strong>, you can derive OpenAPI from your schemas with libraries like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">zod-openapi</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@asteasolutions/zod-to-openapi</code>, so one schema gives you runtime validation and docs. We haven’t adopted that yet; our current script uses explicit schema objects that mirror the types we use in the proxy.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Keeping the spec fresh</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"></strong>Regenerate after route changes<strong> — Run the generator (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/tool-api-doc-gen-2026-02-12-08-54.ts</code>) after any change to routes or public request/response shapes. We document this in the script header and in the README.</li>
<li class="ml-4 list-disc text-slate-300"></strong>CI check<strong> — Run the generator and diff the output (or commit the generated file and fail if it’s modified without a committed change). That way "forgot to regenerate" is caught before merge.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Validate the spec<strong> — Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npx @redocly/cli lint docs/openapi/cursor-proxy.json</code> (or any OpenAPI 3.x linter) so invalid refs or wrong types are caught early.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"></strong>RegExp reuse<strong> — Our first generator used a global <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RegExp</code> with the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">g</code> flag and reused it across routes. The regex’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lastIndex</code> wasn’t reset, so some paths were mis-parsed. We now create a new regex per route or reset <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lastIndex</code>. If you scan routes with regex, avoid shared state.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Auth in the spec<strong> — We document that <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/stats</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/dashboard</code> require the bearer token. If the spec says nothing, a client might assume everything is public and then get 401s; if the spec is wrong, they send the token to the wrong place. One sentence per route or a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">security</code> block at the top helps.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Optional vs required*<em> — Mark optional query params and body fields correctly. We had <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">limit</code> as required in the spec while the server treated it as optional with a default; clients started sending <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">limit: 100</code> everywhere. Harmless but noisy. Align spec and server defaults.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one source of truth (code or spec) and automate the other. We generate OpenAPI from our TypeScript proxy so the spec can’t drift without CI catching it. Document only public request/response shapes, run the generator after every route or contract change, and validate the spec with a linter. Next step: run your generator once, open the output in Swagger UI or Redoc, and fix the first route that doesn’t match what clients actually need.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
