8:T52f3,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Comparative analysis of error handling patterns in TypeScript: Promise vs async/await, result types, and nullish coalescing</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s payment service returned <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">null</code> for a failed lookup. |----------|------|------|-------------|
| <strong>Promise chains</strong> | No async function needed; fits <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.all()</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.race()</code> | Nested callbacks; harder to read for long flows | Small compositions, existing Promise APIs |
| <strong>Async/await</strong> | Linear code; try/catch in one place; better stack traces | Requires async context; easy to forget await | New async code, multi-step flows |
| <strong>Result types</strong> | Failure is in the type; no hidden throws; caller must handle both branches | More boilerplate; not standard in JS | Expected failures (validation, 4xx, empty), APIs where you want explicit contracts |
| <strong>Nullish coalescing (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">??</code>)</strong> | Only defaults on null/undefined; keeps 0, "", false | None for defaulting; doesn’t replace result types for real errors | Defaults for optional/partial data, formatting (e.g. totals in USD) |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4">On an internal dashboard we had a function that returned <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">number | null</code> for "balance not yet loaded". The UI did <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">balance || 0</code> and showed 0 while loading, which was fine. Then we added a "pending" state and changed the API to return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0</code> when the balance was loaded and zero. The UI still showed 0, but for the wrong reason — we couldn’t tell "loading" from "loaded with 0". We fixed it by:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300">Using a result type: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ ok: true; value: number } | { ok: false; error: string }</code> for the fetch, and a separate <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">loading: boolean</code> in UI state.</li>
<li class="ml-4 list-decimal text-slate-300">Using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">??</code> only for the "no data yet" case (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">displayValue ?? "—"</code>), not for the numeric zero.</li></p><p class="text-slate-300 leading-relaxed mb-4">We also had a bug where someone caught an error and rethrew with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">throw e.message</code> (a string). Downstream code did <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">e instanceof Error</code> and got false, so we lost the stack. Lesson: when rethrowing, throw an Error (or subclass), not a string.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Use async/await by default</strong> for new async code; keep Promise chains only where you need <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.all()</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.race()</code> or consistency with an existing module.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Introduce a small Result type</strong> for any function whose "failure" is expected (HTTP 4xx, validation, empty list). Handle both branches at the call site so the type system enforces it.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">??</code> instead of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">||</code></strong> for defaulting whenever the value can legitimately be <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">""</code>, or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">false</code>. Reserve <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">||</code> for "any falsy means use default."</li>
<li class="ml-4 list-decimal text-slate-300"><strong>In catch blocks</strong>, narrow with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof Error</code> before using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.message</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.stack</code>, and when rethrowing, throw an Error (or subclass), not a string.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>In one existing module</strong>, refactor a single async function to return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Promise<Result<T, E>></code> and update its call sites. You’ll see quickly whether result types fit your style and where they help most.</li></p><p class="text-slate-300 leading-relaxed mb-4">The files <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example-async-errors.ts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example-result-type.ts</code> in this directory are runnable with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npx tsx <file>.ts</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ts-node</code>) on Node 18+ or Bun.
