Comparative analysis of error handling patterns in TypeScript: Promise vs async/await, result types, and nullish coalescing

Sofia’s payment service returned null for a failed lookup. Her UI showed "Total: null USD" because the code used || for fallbacks — and 0 (a valid total) was also replaced. She switched to nullish coalescing and explicit result types. A month later, support tickets for "weird numbers" dropped. TypeScript gives you types; how you model failure decides whether bugs hide in production or get caught at compile time.

This post compares three patterns we use in real backends and CLIs: Promise vs async/await for async errors, result types for explicit success/failure, and nullish coalescing for defaulting without swallowing valid values. Each has a place; the table and examples below show when to use which.

Promise vs async/await: same semantics, different style

Both represent asynchronous work and propagate rejections. The difference is syntax and stack readability. With raw Promises you chain .then() and .catch(); with async/await you write linear code and use try/catch for errors.

Where people get tripped up: mixing styles in one file (some functions return Promises and are never awaited, others are async). Pick one style per module and stick to it. In our codebase we use async/await for all new code; Promises stay where we need .all() or .race() and don’t need a full async function.

Example 1: Promise chain vs async/await

Both snippets do the same thing: fetch a user, then fetch their orders, and surface any failure. The first uses a Promise chain; the second uses async/await with try/catch.

// promise-chain.ts
function fetchUserOrdersPromise(userId: string): Promise<{ user: string; orders: number[] }> {
  return fetch(https://api.example.com/users/${userId})
    .then((res) => {
      if (!res.ok) throw new Error(HTTP ${res.status});
      return res.json();
    })
    .then((user: { id: string; name: string }) =>
      fetch(https://api.example.com/orders?userId=${user.id})
        .then((res) => {
          if (!res.ok) throw new Error(HTTP ${res.status});
          return res.json();
        })
        .then((orders: { id: number }[]) => ({ user: user.name, orders: orders.map((o) => o.id) }))
    );
}
// async-await.ts
async function fetchUserOrdersAsync(userId: string): Promise<{ user: string; orders: number[] }> {
  const userRes = await fetch(https://api.example.com/users/${userId});
  if (!userRes.ok) throw new Error(HTTP ${userRes.status});
  const user: { id: string; name: string } = await userRes.json();
  const ordersRes = await fetch(https://api.example.com/orders?userId=${user.id});
  if (!ordersRes.ok) throw new Error(HTTP ${ordersRes.status});
  const orders: { id: number }[] = await ordersRes.json();
  return { user: user.name, orders: orders.map((o) => o.id) };
}

Runnable example that doesn’t hit the network — we simulate success and failure so you can run it locally:

npx tsx example-async-errors.ts

Expected output:

Caught: HTTP 404

So: Promise vs async/await is mostly a style choice for async error flow; semantics are the same. Use async/await when you want linear code and try/catch; use Promise chains when you’re composing with .all()/.race() or existing Promise APIs.

Result types: when failure is a value, not an exception

Throwing is good for "this should never happen" or when you want errors to bubble. When failure is expected (validation, 4xx, empty result), a result type keeps success and failure in the type and forces the caller to handle both. No hidden control flow.

We use a small Result discriminated union. No library required.

Example 2: Result type and call site

// result-type.ts
type Result =
  | { ok: true; value: T }
  | { ok: false; error: E };
async function getBalance(accountId: string): Promise> {
  const res = await fetch(/api/accounts/${accountId}/balance);
  if (!res.ok) {
    return { ok: false, error: await res.text() };
  }
  const data = await res.json();
  if (typeof data.balance !== "number") {
    return { ok: false, error: "Invalid balance in response" };
  }
  return { ok: true, value: data.balance };
}
async function main() {
  const result = await getBalance("acc-123");
  if (result.ok) {
    console.log("Balance:", result.value);
  } else {
    console.error("Error:", result.error);
  }
}

Runnable version with a mock (no HTTP):

// example-result-type.ts
type Result =
  | { ok: true; value: T }
  | { ok: false; error: E };
function getBalanceSync(accountId: string): Result {
  if (accountId === "bad") return { ok: false, error: "Account not found" };
  if (accountId === "zero") return { ok: true, value: 0 };
  return { ok: true, value: 100 };
}
function main() {
  const a = getBalanceSync("acc-1");
  const b = getBalanceSync("zero");
  const c = getBalanceSync("bad");
  console.log("a:", a.ok ? a.value : a.error);
  console.log("b:", b.ok ? b.value : b.error);
  console.log("c:", c.ok ? c.value : c.error);
}
main();

Run:

npx tsx example-result-type.ts

Output:

a: 100
b: 0
c: Account not found

Notice b is 0 — a valid value. With result types you don’t confuse "failed" with "zero"; the type makes both cases explicit.

Nullish coalescing: default only for null/undefined

|| treats any falsy value as "use default" (including 0, "", false). Nullish coalescing (??) uses the default only when the left side is null or undefined. That’s what fixed Sofia’s "Total: null USD" bug: totals can be 0; they shouldn’t be replaced by a fallback.

// nullish-coalescing.ts
function formatTotal(value: number | null | undefined): string {
  const n = value ?? 0;       // default only if null/undefined
  return ${n} USD;
}
console.log(formatTotal(0));      // "0 USD"  — correct
console.log(formatTotal(null));   // "0 USD"
console.log(formatTotal(undefined)); // "0 USD"
// Wrong: using || would turn 0 into the default
function formatTotalWrong(value: number | null | undefined): string {
  const n = value || 0;       // 0 is falsy, so you get 0 anyway here, but...
  return ${n} USD;
}
// If you had value ?? "N/A" vs value || "N/A", the difference shows:
console.log((0 ?? "N/A").toString());   // "0"
console.log((0 || "N/A").toString());   // "N/A"

So: use ?? whenever you mean "use this default only when the value is missing (null/undefined)". Use || only when you want to replace all falsy values.

Comparison: when to use which

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Promise chains | No async function needed; fits .all()/.race() | Nested callbacks; harder to read for long flows | Small compositions, existing Promise APIs | | Async/await | Linear code; try/catch in one place; better stack traces | Requires async context; easy to forget await | New async code, multi-step flows | | Result types | Failure is in the type; no hidden throws; caller must handle both branches | More boilerplate; not standard in JS | Expected failures (validation, 4xx, empty), APIs where you want explicit contracts | | Nullish coalescing (??) | Only defaults on null/undefined; keeps 0, "", false | None for defaulting; doesn’t replace result types for real errors | Defaults for optional/partial data, formatting (e.g. totals in USD) |

What went wrong

On an internal dashboard we had a function that returned number | null for "balance not yet loaded". The UI did balance || 0 and showed 0 while loading, which was fine. Then we added a "pending" state and changed the API to return 0 when the balance was loaded and zero. The UI still showed 0, but for the wrong reason — we couldn’t tell "loading" from "loaded with 0". We fixed it by:

  • Using a result type: { ok: true; value: number } | { ok: false; error: string } for the fetch, and a separate loading: boolean in UI state.
  • Using ?? only for the "no data yet" case (e.g. displayValue ?? "—"), not for the numeric zero.

    • We also had a bug where someone caught an error and rethrew with throw e.message (a string). Downstream code did e instanceof Error and got false, so we lost the stack. Lesson: when rethrowing, throw an Error (or subclass), not a string.

    Takeaways

  • Use async/await by default for new async code; keep Promise chains only where you need .all()/.race() or consistency with an existing module.
  • Introduce a small Result type for any function whose "failure" is expected (HTTP 4xx, validation, empty list). Handle both branches at the call site so the type system enforces it.
  • Use ?? instead of || for defaulting whenever the value can legitimately be 0, "", or false. Reserve || for "any falsy means use default."
  • In catch blocks, narrow with instanceof Error before using .message or .stack, and when rethrowing, throw an Error (or subclass), not a string.
  • In one existing module, refactor a single async function to return Promise> and update its call sites. You’ll see quickly whether result types fit your style and where they help most.

    • The files example-async-errors.ts and example-result-type.ts in this directory are runnable with npx tsx .ts (or ts-node) on Node 18+ or Bun. No extra dependencies.
