Best practices for creating reusable DevOps CI/CD templates

Sofia’s team maintained 12 microservices. Each repo had its own pipeline: same lint, test, and build steps, copied and tweaked. When they upgraded their Node.js version and adjusted the test command, they had to change 12 files. They missed two. Those two services kept running old tests and broke in staging. The fix was a single reusable template; updating it once updated every pipeline. This post is about doing that without painting yourself into a corner — reusable CI/CD templates that stay maintainable and predictable.

Who this is for: DevOps and platform engineers (and devs who own pipelines) who want one place to define build, test, and deploy logic so many repos can reuse it. We focus on patterns that work in GitHub Actions and GitLab CI, with runnable examples and a comparison of approaches.

Why reuse beats copy-paste

Copy-pasted pipelines drift. One repo gets a new security scan; another doesn’t. Fixes and improvements require editing N files and hoping nothing was “special” in one of them. Reusable templates give you:

  • Single source of truth — change the template once, all consumers get the update (after they opt in or you version it).
  • Consistent behaviour — same Node/Bun/Go version, same lint rules, same test command across services.
  • Easier auditing — one place to check for secrets handling, caching, and compliance.

    • The trade-off: templates need clear inputs (e.g. node version, test script name), versioning so you don’t break everyone at once, and docs so Raj in Bangalore and Aiko in Tokyo know how to use them.

    Approach comparison: when to use which

    | Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Copy-paste per repo | No shared dependency; each repo is independent. | Drift, N-fold maintenance, inconsistent behaviour. | One-off or legacy repos you rarely touch. | | Reusable workflow / template (single file) | One definition; consumers call it with inputs. | All consumers share the same behaviour; changing it affects everyone. | Standard pipelines (lint, test, build) where you want consistency. | | Parameterized template + version pin | Reuse plus controlled rollout; pin to a tag or commit. | Slightly more setup (versioning, release of the template repo). | When you have many teams and need to roll out changes gradually. | | Monorepo with shared job definitions | One repo, one pipeline; no cross-repo sync. | Only works if all code lives in one repo. | Monorepos (e.g. Nx, Turborepo). |

    For most teams, reusable workflow (GitHub) or included template (GitLab) with a few inputs is the sweet spot. Add version pinning once you have more than a handful of consumers or multiple teams.

    Example 1: GitHub Actions reusable workflow

    A reusable workflow lives in one repo and is triggered by other repos (or the same repo). You define inputs and pass them from the caller.

    Template repo: .github/workflows/build-and-test.yml (e.g. in your-org/ci-templates).

    .github/workflows/build-and-test.yml
    
name: Build and test (reusable)
    on:
  workflow_call:
    inputs:
      node_version:
        required: true
        type: string
        default: '20'
      install_cmd:
        required: false
        type: string
        default: 'npm ci'
      test_cmd:
        required: false
        type: string
        default: 'npm test'
    secrets:
      NPM_TOKEN:
        required: false
    jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
          - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node_version }}
          cache: 'npm'
          - name: Install
        run: ${{ inputs.install_cmd }}
          - name: Lint
        run: npm run lint
          - name: Test
        run: ${{ inputs.test_cmd }}

    Consumer repo: .github/workflows/ci.yml (in a service repo).

    .github/workflows/ci.yml
    
name: CI
    on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
    jobs:
  build-and-test:
    uses: your-org/ci-templates/.github/workflows/build-and-test.yml@main
    with:
      node_version: '20'
      install_cmd: 'npm ci'
      test_cmd: 'npm test'
    secrets: inherit

    Run it: Push to the consumer repo; the workflow runs and uses the template from ci-templates. To pin a version, use a tag: @v1.0.0 instead of @main.

    Typical terminal output (summary):

    Run your-org/ci-templates/.github/workflows/build-and-test.yml@main
  with:
    node_version: 20
    install_cmd: npm ci
    test_cmd: npm test
...

  node-version: 20
  cache: npm
...

    Example 2: GitLab CI template with include and variables

    In GitLab you can put a template in a separate project and include it. Each project overrides variables as needed.

    Template project: your-group/ci-templates — file templates/build-test.gitlab-ci.yml.

    templates/build-test.gitlab-ci.yml
    

    Reusable: lint, install, test. Override NODE_VERSION, INSTALL_CMD, TEST_CMD.
    variables:
  NODE_VERSION: "20"
  INSTALL_CMD: "npm ci"
  TEST_CMD: "npm test"
    .lint-and-test:
  image: node:${NODE_VERSION}-alpine
  before_script:
    - $INSTALL_CMD
  script:
    - npm run lint
    - $TEST_CMD

    Consumer project: .gitlab-ci.yml in a service repo.

    .gitlab-ci.yml
    
include:
  - project: your-group/ci-templates
    ref: main
    file: templates/build-test.gitlab-ci.yml
    variables:
  NODE_VERSION: "20"
  TEST_CMD: "npm run test:unit"
    jobs:
  lint-and-test:
    extends: .lint-and-test

    Run it: Push to the consumer project; GitLab loads the included file and runs the job. Pin by setting ref: v1.0.0 when you tag the template repo.

    Design practices that keep templates usable

  • Expose only what callers need — e.g. node_version, install_cmd, test_cmd. Don’t pass 20 options; add them when a real use case appears.
  • Sensible defaults — so a consumer can call the template with no (or few) inputs and get a working run.
  • Document inputs and any secrets — a short README in the template repo with a table of inputs, default values, and which repos use which version.
  • Version the template — use tags (v1.0.0) so consumers can pin. Rolling out a change? Bump the tag and update consumers in batches.
  • Fail clearly — if a required input is missing or invalid, fail the job with a message that says which input and which value (e.g. “NODE_VERSION must be 18, 20, or 22”).

    • Lessons learned

    What went wrong: We introduced a reusable “build and test” workflow and pointed seven repos at @main. A colleague changed the default test_cmd from npm test to npm run test:ci (which added coverage and different env). Two services didn’t have a test:ci script. Their pipelines started failing with:

    npm ERR! Missing script: "test:ci"

    We had to fix the template (keep npm test as default and make test:ci opt-in via input) and add the missing script to those two repos. Takeaway: avoid changing default behaviour in a shared template in a way that assumes new scripts exist in every consumer. Prefer additive changes or new optional inputs; if you change defaults, communicate and migrate callers first.

    Another mistake: We didn’t pin the template ref. Every consumer used @main. A bad merge broke all seven pipelines for about an hour. We now use tags (@v1.0.0) and only move v1 (or “current”) after testing in one repo.

    Actionable next steps

  • Audit one pipeline — Pick your most common pattern (e.g. “Node lint + test”). List how many repos duplicate it and what differs (node version, test command, install command). That list is your initial set of template inputs.
  • Extract one reusable workflow or include — In GitHub, add a workflow_call workflow with 2–3 inputs and point one consumer at it. In GitLab, add one .gitlab-ci.yml include and extends in one project. Confirm the run matches the previous behaviour.
  • Document inputs and pin ref — In the template repo, add a short README (inputs, defaults, example). Tag the repo (e.g. v1.0.0) and switch the consumer to @v1.0.0 (or your tag name) instead of @main.
  • Migrate one more repo — Move a second service to the same template. If something is missing (e.g. a special env var or script), add one optional input or variable instead of forking the template.
  • Decide who can change the template — Use branch protection or MR rules so template changes are reviewed and, if possible, tested against at least one consumer before merge.

    • Once this is in place, you get a single place to add security scans, dependency bumps, or new steps — and every consumer can adopt the change by updating the ref or the inputs they pass.
