8:T216c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Graceful Shutdown in TypeScript Services: What We Got Wrong First</h1></p><p class="text-slate-300 leading-relaxed mb-4">We had a task runner that accepted work over HTTP and wrote results to SQLite. Restarts during a long run left rows stuck in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> and no clear way to tell whether the process had finished or been killed. Our first fix was "just don't restart during a run." That didn't scale. Here's how we added proper graceful shutdown so in-flight work completes and the process exits cleanly.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why it matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Processes stop for deploys, OOM kills, scaling down, or manual restarts. If you exit immediately, you drop active requests, leave DB rows in an inconsistent state, and force clients to retry blindly. Graceful shutdown means: stop accepting new work, finish or hand off in-flight work, close connections, then exit. The goal is predictable, observable behavior so operators and callers know what to expect.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we did wrong at first</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Exiting on first SIGTERM</strong> — We called <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit(1)</code> inside the signal handler. Anything in progress was aborted; no drain, no cleanup.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Ignoring in-flight HTTP</strong> — The server closed the listen socket but we didn't track or wait for open requests. Some responses never made it; clients saw connection resets.</li>
<li class="ml-4 list-disc text-slate-300"><strong>No DB checkpoint</strong> — SQLite WAL was in use. We didn't run a checkpoint or close the DB handle before exit, so we sometimes left the DB in a mess after a hard kill during a write.</li></p><p class="text-slate-300 leading-relaxed mb-4">We assumed "exit when we get SIGTERM" was enough. It wasn't.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we changed</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. Signal handling without immediate exit</strong></p><p class="text-slate-300 leading-relaxed mb-4">We listen for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code> (and optionally <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGINT</code> in dev). On signal we set a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">shuttingDown</code> flag and call a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">gracefulShutdown()</code> function. We do not call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit()</code> in the handler. The event loop keeps running until we explicitly exit after cleanup.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>let shuttingDown = false;</p><p class="text-slate-300 leading-relaxed mb-4">function gracefulShutdown() {
  if (shuttingDown) return;
  shuttingDown = true;
  server.close(() => {
    // All HTTP connections drained
    db.checkpoint();
    db.close();
    process.exit(0);
  });
  // Optional: timeout to force exit if drain takes too long
  setTimeout(() => process.exit(1), 30_000);
}</p><p class="text-slate-300 leading-relaxed mb-4">process.on('SIGTERM', gracefulShutdown);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. Stop accepting new work</strong></p><p class="text-slate-300 leading-relaxed mb-4">We call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code>. That stops the HTTP server from accepting new connections. Existing connections keep running until they finish. The callback to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code> runs when every connection is closed. Only then do we checkpoint and close the DB.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. In-flight task semantics</strong></p><p class="text-slate-300 leading-relaxed mb-4">Our runner has a single "worker" that pulls one task at a time. When we set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">shuttingDown</code>, the worker loop checks the flag after each task. If it's set, it stops pulling new tasks, waits for the current task to finish (or a short timeout), then returns so that <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">gracefulShutdown</code> can run DB cleanup. Tasks already in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> either complete and get marked <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">done</code> or, if we hit the timeout, stay in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> for a recovery job to reassign later. We document that behavior so operators know what "stuck in doing" means after a restart.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>4. SQLite checkpoint and close</strong></p><p class="text-slate-300 leading-relaxed mb-4">Before exit we run a WAL checkpoint (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PRAGMA wal_checkpoint(TRUNCATE)</code> or your runtime's equivalent) and then close the database handle. That reduces the chance of leaving the DB in a bad state if the process is killed later during the 30s timeout.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Timeout and trade-offs</h2></p><p class="text-slate-300 leading-relaxed mb-4">We use a 30-second cap. If the server hasn't drained by then, we exit with code 1. That avoids hanging forever on a stuck client. The trade-off: some requests may still be in progress and get cut off. We log "graceful shutdown timeout" so we can tune the value or fix slow handlers. For our workload 30s was enough; yours may differ.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Graceful shutdown is a small amount of code but requires a clear contract: what "in progress" means and who is responsible for retries or reassignment.</li>
<li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code> plus a single "no new work" flag in the worker loop was enough for our case; we didn't need a request counter.</li>
<li class="ml-4 list-disc text-slate-300">Checkpointing and closing the DB before exit avoided several "database locked" and inconsistent WAL issues after restarts.</li>
<li class="ml-4 list-disc text-slate-300">Document the timeout and the meaning of tasks left in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> so the next person (or a runbook) knows what to do after a deploy.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing you can do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">If your service uses HTTP and a DB, add a SIGTERM handler that (1) stops accepting new connections with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code>, (2) waits for the close callback or a timeout, (3) checkpoints and closes the DB, then (4) exits. Don't call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit()</code> inside the signal handler before cleanup. Test by sending SIGTERM during a request and confirming the response is returned and the process exits with 0.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
