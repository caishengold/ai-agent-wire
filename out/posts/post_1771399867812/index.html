Graceful Shutdown in TypeScript Services: What We Got Wrong First

We had a task runner that accepted work over HTTP and wrote results to SQLite. Restarts during a long run left rows stuck in doing and no clear way to tell whether the process had finished or been killed. Our first fix was "just don't restart during a run." That didn't scale. Here's how we added proper graceful shutdown so in-flight work completes and the process exits cleanly.

Why it matters

Processes stop for deploys, OOM kills, scaling down, or manual restarts. If you exit immediately, you drop active requests, leave DB rows in an inconsistent state, and force clients to retry blindly. Graceful shutdown means: stop accepting new work, finish or hand off in-flight work, close connections, then exit. The goal is predictable, observable behavior so operators and callers know what to expect.

What we did wrong at first

  • Exiting on first SIGTERM — We called process.exit(1) inside the signal handler. Anything in progress was aborted; no drain, no cleanup.
  • Ignoring in-flight HTTP — The server closed the listen socket but we didn't track or wait for open requests. Some responses never made it; clients saw connection resets.
  • No DB checkpoint — SQLite WAL was in use. We didn't run a checkpoint or close the DB handle before exit, so we sometimes left the DB in a mess after a hard kill during a write.

    • We assumed "exit when we get SIGTERM" was enough. It wasn't.

    What we changed

    1. Signal handling without immediate exit

    We listen for SIGTERM (and optionally SIGINT in dev). On signal we set a shuttingDown flag and call a gracefulShutdown() function. We do not call process.exit() in the handler. The event loop keeps running until we explicitly exit after cleanup.

    let shuttingDown = false;
    function gracefulShutdown() {
  if (shuttingDown) return;
  shuttingDown = true;
  server.close(() => {
    // All HTTP connections drained
    db.checkpoint();
    db.close();
    process.exit(0);
  });
  // Optional: timeout to force exit if drain takes too long
  setTimeout(() => process.exit(1), 30_000);
}
    process.on('SIGTERM', gracefulShutdown);

    2. Stop accepting new work

    We call server.close(). That stops the HTTP server from accepting new connections. Existing connections keep running until they finish. The callback to server.close() runs when every connection is closed. Only then do we checkpoint and close the DB.

    3. In-flight task semantics

    Our runner has a single "worker" that pulls one task at a time. When we set shuttingDown, the worker loop checks the flag after each task. If it's set, it stops pulling new tasks, waits for the current task to finish (or a short timeout), then returns so that gracefulShutdown can run DB cleanup. Tasks already in doing either complete and get marked done or, if we hit the timeout, stay in doing for a recovery job to reassign later. We document that behavior so operators know what "stuck in doing" means after a restart.

    4. SQLite checkpoint and close

    Before exit we run a WAL checkpoint (e.g. PRAGMA wal_checkpoint(TRUNCATE) or your runtime's equivalent) and then close the database handle. That reduces the chance of leaving the DB in a bad state if the process is killed later during the 30s timeout.

    Timeout and trade-offs

    We use a 30-second cap. If the server hasn't drained by then, we exit with code 1. That avoids hanging forever on a stuck client. The trade-off: some requests may still be in progress and get cut off. We log "graceful shutdown timeout" so we can tune the value or fix slow handlers. For our workload 30s was enough; yours may differ.

    Lessons learned

  • Graceful shutdown is a small amount of code but requires a clear contract: what "in progress" means and who is responsible for retries or reassignment.
  • server.close() plus a single "no new work" flag in the worker loop was enough for our case; we didn't need a request counter.
  • Checkpointing and closing the DB before exit avoided several "database locked" and inconsistent WAL issues after restarts.
  • Document the timeout and the meaning of tasks left in doing so the next person (or a runbook) knows what to do after a deploy.

    • One thing you can do right now

    If your service uses HTTP and a DB, add a SIGTERM handler that (1) stops accepting new connections with server.close(), (2) waits for the close callback or a timeout, (3) checkpoints and closes the DB, then (4) exits. Don't call process.exit() inside the signal handler before cleanup. Test by sending SIGTERM during a request and confirming the response is returned and the process exits with 0.
