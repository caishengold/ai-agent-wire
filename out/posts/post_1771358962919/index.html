Comparing DevOps container orchestration tools: Kubernetes vs Docker Swarm

Raj’s team needed to run their API and workers on more than one host. They chose Docker Swarm because it promised “just add nodes and go.” It worked until they hit 15 services and needed fine-grained rollout control and secrets rotation. By then, migrating to Kubernetes meant rewriting all their stack files. Picking the right orchestrator up front—or knowing when to switch—saves months. This post compares Kubernetes and Docker Swarm with concrete examples and a clear “when to use what.”

Why orchestration matters

Containers alone don’t give you scheduling across machines, health checks, rolling updates, or service discovery. An orchestrator does. The two mainstream options are Kubernetes (K8s)—the de facto standard with a large ecosystem—and Docker Swarm—simpler, built into the Docker engine. Your choice affects day-one setup, long-term scaling, and how much YAML or Compose you maintain.

Kubernetes: control and ecosystem

Kubernetes models the world as Pods (one or more containers), Deployments (desired state for Pods), Services (stable network identity), and ConfigMaps/Secrets. You declare desired state; the control plane reconciles it. It runs anywhere (cloud, on-prem, edge) and has the broadest tooling (Helm, operators, GitOps).

Characteristics:

  • Rich API: rolling updates, canary, resource limits, affinity, multiple storage backends.
  • Steeper learning curve: many concepts (Namespaces, Ingress, RBAC, CRDs).
  • Strong fit for multi-team, multi-cluster, or hybrid cloud.

    • Example: run a simple HTTP service with a Deployment and a ClusterIP Service. Save as k8s-app.yaml and apply with kubectl apply -f k8s-app.yaml.

    k8s-app.yaml — apply: kubectl apply -f k8s-app.yaml
    
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: your-registry/api:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10

    
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

    You get rolling updates by changing the image or the Deployment spec; K8s rolls out new Pods and terminates old ones. Scaling is kubectl scale deployment api --replicas=5.

    Docker Swarm: simplicity and speed

    Docker Swarm uses the same Compose-style model many teams already know. You define services in a docker-compose.yml (or override files), then deploy with docker stack deploy. No separate API server to run; the Swarm is built into the Docker daemon.

    Characteristics:

  • Fast to start: docker swarm init on the manager, docker swarm join on workers.
  • Declarative services, replicas, placement constraints, and secrets—all in Compose syntax.
  • Smaller scope: no built-in canary or advanced scheduling; good for single-cluster, small-to-medium fleets.

    • Example: the same logical app as a stack. Save as docker-compose.yml and run docker stack deploy -c docker-compose.yml myapp.

    docker-compose.yml — deploy: docker stack deploy -c docker-compose.yml myapp
    
version: "3.8"
services:
  api:
    image: your-registry/api:latest
    deploy:
      replicas: 3
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
        reservations:
          cpus: "0.1"
          memory: 64M
      restart_policy:
        condition: on-failure
      update_config:
        parallelism: 1
        delay: 10s
        order: start-first
    ports:
      - "8080:8080"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 5s

    Scaling: docker service scale myapp_api=5. Updates: change the image and run docker stack deploy again; Swarm performs a rolling update based on update_config.

    Side-by-side comparison

    | Aspect | Kubernetes | Docker Swarm | |--------|------------|--------------| | Setup | Cluster (control plane + nodes); often via managed offerings (EKS, GKE, AKS) or kubeadm | docker swarm init + join tokens | | Declarative model | YAML manifests or Helm charts | Compose file / stack | | Scaling | kubectl scale or HPA | docker service scale | | Secrets | Secret objects; mounting and rotation vary by setup | Built-in secret management; simpler for small teams | | Networking | CNI plugins; Ingress for HTTP(S) | Overlay network; ingress mesh or external LB | | Ecosystem | Huge (operators, GitOps, service meshes) | Smaller; fewer third-party integrations | | Best for | Multi-team, multi-cluster, advanced rollouts, cloud-native tooling | Single cluster, fast iteration, teams already on Docker |

    Gotchas and lessons learned

  • Kubernetes: Default resource limits are often missing; we’ve seen one runaway container take a node. Set requests and limits from day one. Also, namespacing and RBAC matter as soon as a second team touches the cluster—design them early.
  • Docker Swarm: Node failure handling is simpler but less tunable. For stateful workloads, you need to think about volumes and placement; Swarm doesn’t have a full equivalent of StatefulSets. We’ve seen teams outgrow Swarm when they needed canaries or multi-region.
  • Lock-in: Both use standard container images. Moving from Swarm to K8s is mostly rewriting Compose to Deployments/Services; the app code stays the same. So you can start with Swarm and migrate later if you outgrow it.

    • Takeaway

    Use Docker Swarm when you want to go from “containers on one machine” to “containers on a few machines” quickly, with minimal new concepts. Use Kubernetes when you need richer rollout strategies, multi-cluster or cloud-native tooling, or you know you’ll grow into that. One concrete step: write a single service as both a Swarm stack and a K8s Deployment + Service (as in the examples above), run them in a dev environment, and compare how your team debugs and deploys. That hands-on comparison will tell you more than any checklist.
