Deploying Bun apps in production — Docker, systemd, health checks, zero-downtime updates

Omar’s internal API was a small Bun server that returned task stats. On his laptop it was fine. He deployed it to a single VM with nohup bun run server.ts & and went home. At 03:00 the process died (OOM kill). Nothing restarted it. The next deploy was a straight systemctl restart — users saw 503s for about 12 seconds while the new binary came up. No health endpoint, so the load balancer kept sending traffic to the old port until the process was gone. That week he added a proper Dockerfile, systemd with a watchdog, /health/live and /health/ready, and a graceful shutdown so restarts don’t drop in-flight requests. This post is the setup that actually works: runnable examples, a comparison of deployment options, and what went wrong along the way.

Why production Bun needs more than bun run

Bun is fast and simple for local dev. In production you still need: a repeatable image (Docker or similar), a process manager that restarts on failure (systemd, k8s, or a PaaS), health signals so the orchestrator knows when to send traffic and when to restart, and graceful shutdown so deploys don’t cut active connections. The sections below cover each of these with real configs and code.

1. Docker: small image, non-root, and .dockerignore

Use the official Bun image so you don’t maintain a custom runtime. A multi-stage build keeps the final image small: install deps in one stage, copy only what’s needed into the run stage. Run as a non-root user so a container escape doesn’t give host root.

Example: minimal Bun HTTP server with health and graceful shutdown

Save as server.ts in a new directory (e.g. bun-app-demo/):

// server.ts — minimal Bun server with health endpoints and SIGTERM handling
const server = Bun.serve({
  port: Number(process.env.PORT) || 3000,
  async fetch(req) {
    const url = new URL(req.url);
    if (url.pathname === "/health/live") {
      return Response.json({ ok: true, ts: new Date().toISOString() });
    }
    if (url.pathname === "/health/ready") {
      // Add dependency checks here (e.g. DB ping). For demo we're always ready.
      return Response.json({ ok: true, ready: true });
    }
    return new Response("OK", { status: 200 });
  },
});
// Graceful shutdown: stop accepting new connections, then exit
process.on("SIGTERM", () => {
  server.stop();
  process.exit(0);
});
console.log(Listening on ${server.hostname}:${server.port});

Run it locally:

cd bun-app-demo
bun run server.ts

Listening on 0.0.0.0:3000

In another terminal:

curl -s http://127.0.0.1:3000/health/live

{"ok":true,"ts":"2026-02-12T03:31:00.000Z"}

curl -s http://127.0.0.1:3000/health/ready

{"ok":true,"ready":true}

Dockerfile — multi-stage, non-root:

Dockerfile

FROM oven/bun:1.1-alpine AS deps
WORKDIR /app
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile
FROM oven/bun:1.1-alpine
WORKDIR /app
RUN adduser -D appuser
COPY --from=deps /app/node_modules ./node_modules
COPY package.json bun.lockb ./
COPY server.ts ./
RUN chown -R appuser:appuser /app
USER appuser
EXPOSE 3000
ENV PORT=3000
CMD ["bun", "run", "server.ts"]

Create a minimal package.json and optional bun.lockb (or run bun install once to generate it). Add a .dockerignore so you don’t send the whole repo into the build context:

.dockerignore

node_modules
.git
.md
.env
.env.

Build and run:

docker build -t bun-app:demo .
docker run --rm -p 3000:3000 bun-app:demo

Terminal output (example):

$ docker run --rm -p 3000:3000 bun-app:demo
Listening on 0.0.0.0:3000

Then curl -s http://127.0.0.1:3000/health/live returns 200. The image uses Alpine and only your app + deps, so it stays small (often under 150 MB).

2. systemd: unit file, watchdog, and env file for secrets

On a single VM or bare metal, systemd keeps the process running and restarts it on failure. Use an EnvironmentFile for secrets (tokens, DB URLs) with chmod 600 so they’re not in the unit file. For long-running servers, WatchdogSec plus a periodic “I’m alive” signal (e.g. touching a file or calling sd_notify) lets systemd restart the process if it hangs.

Example: systemd unit for the Bun app

Assume the app is at /home/aiko/apps/bun-api. Create ~/.config/systemd/user/bun-api.service (or /etc/systemd/system/bun-api.service for system-wide):

[Unit]
Description=Bun API server
After=network.target
[Service]
Type=simple
WorkingDirectory=/home/aiko/apps/bun-api
EnvironmentFile=%h/.config/systemd/user/bun-api.env
ExecStart=/home/aiko/.bun/bin/bun run server.ts
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal

Optional: restart if no watchdog ping within 60s (requires app to sd_notify or touch a file)


WatchdogSec=60
[Install]
WantedBy=default.target

Put PORT=3000 (and any secrets) in ~/.config/systemd/user/bun-api.env, then:

chmod 600 ~/.config/systemd/user/bun-api.env
systemctl --user daemon-reload
systemctl --user enable --now bun-api.service
systemctl --user status bun-api.service

Health checks from the host:

curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/health/live

200

If you use WatchdogSec, your app must notify systemd periodically (e.g. every 30s when WatchdogSec=60). In Bun you can use the sd-notify package or a simple file-based heartbeat that a separate timer checks. Without that, don’t set WatchdogSec or systemd will kill the process when it doesn’t receive the ping.

3. Health checks: liveness vs readiness

Liveness means “is the process alive and willing to keep running?” — e.g. a simple /health/live that returns 200. If it fails, the orchestrator restarts the process.

Readiness means “is this instance ready to accept traffic?” — e.g. DB connected, caches warm. If readiness fails, the orchestrator stops sending traffic but does not restart. Use readiness for “still starting” or “dependency temporarily down.”

| Endpoint | Returns 200 when | Failure action | |----------------|------------------------|-----------------------------| | /health/live | Process is running | Restart (Docker, systemd, k8s) | | /health/ready| Ready for traffic (DB, etc.) | Stop sending traffic only |

Keep checks fast (timeout after 1–2 seconds). Don’t put secrets or internal details in the response. The runnable server.ts above already exposes both; in a real app you’d add a DB ping or similar to /health/ready.

Docker — use HEALTHCHECK so Docker marks the container unhealthy and can restart it:

HEALTHCHECK --interval=15s --timeout=2s --start-period=5s --retries=3 \
  CMD wget -q -O - http://127.0.0.1:3000/health/live || exit 1

systemd — you can run a timer that hits /health/live and restarts the service on failure, or rely on Restart=on-failure when the process exits. WatchdogSec is for “process is hung but not dead.”

4. Zero-downtime updates: graceful shutdown and replace strategy

If you just kill the process on deploy, in-flight HTTP requests get connection resets. Graceful shutdown: on SIGTERM, stop accepting new connections, finish existing requests (or after a short timeout), then exit. The server.ts example does server.stop() on SIGTERM; Bun closes the listener and drains active connections.

Ways to reduce or avoid downtime:

| Approach | How it works | Downtime / complexity | |--------------------|---------------------------------------|----------------------------| | Graceful restart | systemd sends SIGTERM, waits TimeoutStopSec, then SIGKILL | Short gap (seconds) while new process starts | | Rolling replace | New container/process starts; LB shifts traffic when ready | Near zero if you have 2+ instances | | Blue-green | New version deployed alongside old; switch traffic in one go | Zero if you have spare capacity | | Reload (symlink) | New binary; send SIGHUP or replace symlink and restart | Same as graceful restart on single node |

On a single VM with systemd, the practical approach is: build the new version (or pull new image), then systemctl restart bun-api.service. With graceful shutdown, in-flight requests complete; new ones may see a short delay until the new process is up. To avoid that delay you need a second instance (e.g. two containers behind a reverse proxy that checks /health/ready and only sends traffic to ready instances).

systemd timeout — give the process time to shut down before SIGKILL:

TimeoutStopSec=30

So: systemctl restart sends SIGTERM, waits up to 30s, then SIGKILL. Your app must handle SIGTERM and exit within that window.

5. Deployment options at a glance

| Option | Pros | Cons | When to use | |---------------------|-------------------------------------------|-------------------------------------------|--------------------------------| | Bare systemd | No container runtime, simple, low overhead | No image portability, host-coupled | Single VM, same OS everywhere | | Docker + systemd| Portable image, systemd restarts container | Two layers to configure | VM or bare metal, want images | | Docker only | Same image dev/prod, easy to move to k8s | You still need restarts (Docker restart policy or orchestrator) | CI, staging, or k8s later | | Kubernetes | Rolling updates, health probes, scaling | Heavier, more moving parts | Multi-node, many services |

For a single Bun app on one VM, systemd only or Docker with systemd managing the container both work. Use Docker when you want the same image in CI and production or plan to move to k8s later.

Lessons learned

SIGTERM not handled. The first version of the server didn’t listen for SIGTERM. On systemctl restart, systemd sent SIGTERM; the process ignored it. After TimeoutStopSec (default 90s on some distros), systemd sent SIGKILL. Restarts took 90 seconds and looked like hangs. Fix: add process.on("SIGTERM", () => { server.stop(); process.exit(0); }); and set TimeoutStopSec=30 so shutdown is bounded.

Health check too slow. Readiness was doing a full DB schema check (dozens of queries) and sometimes took 4 seconds. The load balancer timed out at 3s and marked the instance unhealthy, which caused unnecessary restarts. We changed readiness to a single SELECT 1 (or SQLite PRAGMA quick_check) and kept it under 100 ms.

Docker image size. The first Dockerfile used FROM node:20 and then installed Bun on top; the image was over 1 GB. Switching to FROM oven/bun:1.1-alpine and a multi-stage build brought it down to about 140 MB. Always use a .dockerignore so COPY . . doesn’t pull in .git and local .env files.

Wrong working directory in systemd. The unit had WorkingDirectory=/home/aiko/bun-api but the app lived in /home/aiko/apps/bun-api. bun run server.ts failed with “file not found” and the service never stayed up. Double-check paths when you copy unit files from docs.

What you can do today

  • Add /health/live and /health/ready to your Bun server (and optionally a DB ping in ready). Return JSON like { "ok": true } with a 1–2s timeout.
  • Handle SIGTERM in the app: call server.stop() (or your framework’s shutdown), then process.exit(0). Set systemd TimeoutStopSec=30 (or similar) so restarts don’t hang.
  • Switch to the official Bun Alpine image in Docker (oven/bun:1.1-alpine), use a multi-stage build, and add a .dockerignore so the build context stays small.
  • Run the container or process as non-root (Docker USER appuser, or a dedicated system user for systemd).
  • Add a HEALTHCHECK to your Dockerfile using wget or curl against /health/live, and in systemd optionally use WatchdogSec only if your app can send a periodic watchdog ping.

    • Once these are in place, restarts and redeploys become predictable: health checks tell the orchestrator when to send traffic, and graceful shutdown avoids dropping requests during updates.
