8:T5dcd,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Deploying Bun apps in production — Docker, systemd, health checks, zero-downtime updates</h1></p><p class="text-slate-300 leading-relaxed mb-4">Omar’s internal API was a small Bun server that returned task stats. On his laptop it was fine. He deployed it to a single VM with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">nohup bun run server.ts &</code> and went home. At 03:00 the process died (OOM kill). Nothing restarted it. The next deploy was a straight <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart</code> — users saw 503s for about 12 seconds while the new binary came up. No health endpoint, so the load balancer kept sending traffic to the old port until the process was gone. That week he added a proper Dockerfile, systemd with a watchdog, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code>, and a graceful shutdown so restarts don’t drop in-flight requests. This post is the setup that actually works: runnable examples, a comparison of deployment options, and what went wrong along the way.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why production Bun needs more than <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run</code></h2></p><p class="text-slate-300 leading-relaxed mb-4">Bun is fast and simple for local dev. In production you still need: a <strong>repeatable image</strong> (Docker or similar), a <strong>process manager</strong> that restarts on failure (systemd, k8s, or a PaaS), <strong>health signals</strong> so the orchestrator knows when to send traffic and when to restart, and <strong>graceful shutdown</strong> so deploys don’t cut active connections. The sections below cover each of these with real configs and code.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Docker: small image, non-root, and .dockerignore</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use the official Bun image so you don’t maintain a custom runtime. A multi-stage build keeps the final image small: install deps in one stage, copy only what’s needed into the run stage. Run as a non-root user so a container escape doesn’t give host root.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: minimal Bun HTTP server with health and graceful shutdown</strong></p><p class="text-slate-300 leading-relaxed mb-4">Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.ts</code> in a new directory (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun-app-demo/</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// server.ts — minimal Bun server with health endpoints and SIGTERM handling

    }
    if (url.pathname === "/health/ready") {
      // Add dependency checks here (e.g. DB ping). For demo we're always ready.
      return Response.json({ ok: true, ready: true });
    }
    return new Response("OK", { status: 200 });
  },
});</p><p class="text-slate-300 leading-relaxed mb-4">// Graceful shutdown: stop accepting new connections, then exit

  process.exit(0);

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run it locally:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>cd bun-app-demo

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In another terminal:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>curl -s http://127.0.0.1:3000/health/live

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Terminal output (example):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ docker run --rm -p 3000:3000 bun-app:demo

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">curl -s http://127.0.0.1:3000/health/live</code> returns 200. The image uses Alpine and only your app + deps, so it stays small (often under 150 MB).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. systemd: unit file, watchdog, and env file for secrets</h2></p><p class="text-slate-300 leading-relaxed mb-4">On a single VM or bare metal, systemd keeps the process running and restarts it on failure. Use an <strong>EnvironmentFile</strong> for secrets (tokens, DB URLs) with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">chmod 600</code> so they’re not in the unit file. For long-running servers, <strong>WatchdogSec</strong> plus a periodic “I’m alive” signal (e.g. touching a file or calling <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sd_notify</code>) lets systemd restart the process if it hangs.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: systemd unit for the Bun app</strong></p><p class="text-slate-300 leading-relaxed mb-4">Assume the app is at <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/home/aiko/apps/bun-api</code>. Create <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/bun-api.service</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/etc/systemd/system/bun-api.service</code> for system-wide):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Bun API server
After=network.target</p><p class="text-slate-300 leading-relaxed mb-4">[Service]

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Put <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PORT=3000</code> (and any secrets) in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/bun-api.env</code>, then:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>chmod 600 ~/.config/systemd/user/bun-api.env

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Health checks from the host:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/health/live
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">200</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If you use <strong>WatchdogSec</strong>, your app must notify systemd periodically (e.g. every 30s when WatchdogSec=60). In Bun you can use the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sd-notify</code> package or a simple file-based heartbeat that a separate timer checks. Without that, don’t set WatchdogSec or systemd will kill the process when it doesn’t receive the ping.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Health checks: liveness vs readiness</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Liveness</strong> means “is the process alive and willing to keep running?” — e.g. a simple <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> that returns 200. If it fails, the orchestrator restarts the process.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Readiness</strong> means “is this instance ready to accept traffic?” — e.g. DB connected, caches warm. If readiness fails, the orchestrator stops sending traffic but does not restart. Use readiness for “still starting” or “dependency temporarily down.”</p><p class="text-slate-300 leading-relaxed mb-4">| Endpoint        | Returns 200 when       | Failure action              |
|----------------|------------------------|-----------------------------|
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> | Process is running     | Restart (Docker, systemd, k8s) |
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code>| Ready for traffic (DB, etc.) | Stop sending traffic only   |</p><p class="text-slate-300 leading-relaxed mb-4">Keep checks fast (timeout after 1–2 seconds). Don’t put secrets or internal details in the response. The runnable <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.ts</code> above already exposes both; in a real app you’d add a DB ping or similar to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Docker</strong> — use HEALTHCHECK so Docker marks the container unhealthy and can restart it:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>HEALTHCHECK --interval=15s --timeout=2s --start-period=5s --retries=3 \
  CMD wget -q -O - http://127.0.0.1:3000/health/live || exit 1
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>systemd</strong> — you can run a timer that hits <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> and restarts the service on failure, or rely on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=on-failure</code> when the process exits. WatchdogSec is for “process is hung but not dead.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">4. Zero-downtime updates: graceful shutdown and replace strategy</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you just kill the process on deploy, in-flight HTTP requests get connection resets. <strong>Graceful shutdown</strong>: on SIGTERM, stop accepting new connections, finish existing requests (or after a short timeout), then exit. The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.ts</code> example does <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.stop()</code> on SIGTERM; Bun closes the listener and drains active connections.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Ways to reduce or avoid downtime:</strong></p><p class="text-slate-300 leading-relaxed mb-4">| Approach           | How it works                          | Downtime / complexity      |
|--------------------|---------------------------------------|----------------------------|
| <strong>Graceful restart</strong> | systemd sends SIGTERM, waits TimeoutStopSec, then SIGKILL | Short gap (seconds) while new process starts |
| <strong>Rolling replace</strong>  | New container/process starts; LB shifts traffic when ready | Near zero if you have 2+ instances |
| <strong>Blue-green</strong>       | New version deployed alongside old; switch traffic in one go | Zero if you have spare capacity |
| <strong>Reload (symlink)</strong> | New binary; send SIGHUP or replace symlink and restart | Same as graceful restart on single node |</p><p class="text-slate-300 leading-relaxed mb-4">On a <strong>single VM</strong> with systemd, the practical approach is: build the new version (or pull new image), then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart bun-api.service</code>. With graceful shutdown, in-flight requests complete; new ones may see a short delay until the new process is up. To avoid that delay you need a second instance (e.g. two containers behind a reverse proxy that checks <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code> and only sends traffic to ready instances).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>systemd timeout</strong> — give the process time to shut down before SIGKILL:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>TimeoutStopSec=30
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart</code> sends SIGTERM, waits up to 30s, then SIGKILL. Your app must handle SIGTERM and exit within that window.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">5. Deployment options at a glance</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Option              | Pros                                      | Cons                                      | When to use                    |
|---------------------|-------------------------------------------|-------------------------------------------|--------------------------------|
| <strong>Bare systemd</strong>    | No container runtime, simple, low overhead | No image portability, host-coupled        | Single VM, same OS everywhere |
| <strong>Docker + systemd</strong>| Portable image, systemd restarts container | Two layers to configure                   | VM or bare metal, want images |
| <strong>Docker only</strong>     | Same image dev/prod, easy to move to k8s   | You still need restarts (Docker restart policy or orchestrator) | CI, staging, or k8s later      |
| <strong>Kubernetes</strong>      | Rolling updates, health probes, scaling    | Heavier, more moving parts                | Multi-node, many services      |</p><p class="text-slate-300 leading-relaxed mb-4">For a single Bun app on one VM, <strong>systemd only</strong> or <strong>Docker with systemd managing the container</strong> both work. Use Docker when you want the same image in CI and production or plan to move to k8s later.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>SIGTERM not handled.</strong> The first version of the server didn’t listen for SIGTERM. On <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart</code>, systemd sent SIGTERM; the process ignored it. After TimeoutStopSec (default 90s on some distros), systemd sent SIGKILL. Restarts took 90 seconds and looked like hangs. Fix: add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on("SIGTERM", () => { server.stop(); process.exit(0); });</code> and set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">TimeoutStopSec=30</code> so shutdown is bounded.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Health check too slow.</strong> Readiness was doing a full DB schema check (dozens of queries) and sometimes took 4 seconds. The load balancer timed out at 3s and marked the instance unhealthy, which caused unnecessary restarts. We changed readiness to a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT 1</code> (or SQLite <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PRAGMA quick_check</code>) and kept it under 100 ms.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Docker image size.</strong> The first Dockerfile used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FROM node:20</code> and then installed Bun on top; the image was over 1 GB. Switching to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FROM oven/bun:1.1-alpine</code> and a multi-stage build brought it down to about 140 MB. Always use a .dockerignore so <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">COPY . .</code> doesn’t pull in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.git</code> and local <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> files.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Wrong working directory in systemd.</strong> The unit had <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WorkingDirectory=/home/aiko/bun-api</code> but the app lived in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/home/aiko/apps/bun-api</code>. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run server.ts</code> failed with “file not found” and the service never stayed up. Double-check paths when you copy unit files from docs.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code></strong> to your Bun server (and optionally a DB ping in ready). Return JSON like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ "ok": true }</code> with a 1–2s timeout.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Handle SIGTERM</strong> in the app: call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.stop()</code> (or your framework’s shutdown), then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit(0)</code>. Set systemd <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">TimeoutStopSec=30</code> (or similar) so restarts don’t hang.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Switch to the official Bun Alpine image</strong> in Docker (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">oven/bun:1.1-alpine</code>), use a multi-stage build, and add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.dockerignore</code> so the build context stays small.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Run the container or process as non-root</strong> (Docker <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">USER appuser</code>, or a dedicated system user for systemd).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a HEALTHCHECK to your Dockerfile</strong> using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">wget</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">curl</code> against <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code>, and in systemd optionally use WatchdogSec only if your app can send a periodic watchdog ping.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once these are in place, restarts and redeploys become predictable: health checks tell the orchestrator when to send traffic, and graceful shutdown avoids dropping requests during updates.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
