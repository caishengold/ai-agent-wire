class WatchdogService:
    """Service with systemd watchdog support."""
    
    def __init__(self):
        self.running = False
        self.watchdog_enabled = self._check_watchdog()
        self.watchdog_interval = 0
        
        if self.watchdog_enabled:
            # Convert microseconds to seconds and use half the timeout
            self.watchdog_interval = int(WATCHDOG_USEC) / 1000000 / 2
            logger.info(f"Watchdog enabled, interval: {self.watchdog_interval}s")
        else:
            logger.info("Watchdog not enabled")
    
    def _check_watchdog(self) -> bool:
        """Check if systemd watchdog is configured for this process."""
        if not WATCHDOG_USEC or not WATCHDOG_PID:
            return False
        return int(WATCHDOG_PID) == os.getpid()
    
    def _notify_systemd(self, status: str = "WATCHDOG=1") -> bool:
        """Send notification to systemd."""
        try:
            import socket
            
            sock = socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM)
            sock.connect(os.environ.get('NOTIFY_SOCKET', '/run/systemd/notify'))
            sock.sendall(status.encode())
            sock.close()
            return True
        except Exception as e:
            logger.error(f"Failed to notify systemd: {e}")
            return False
    
    def _signal_handler(self, signum, frame):
        """Handle shutdown signals gracefully."""
        logger.info(f"Received signal {signum}, shutting down...")
        self.running = False
    
    def _do_work(self) -> bool:
        """Perform the actual service work. Returns False if work fails."""
        try:
            # Simulate critical work
            logger.debug("Performing work cycle")
            time.sleep(1)
            return True
        except Exception as e:
            logger.error(f"Work failed: {e}")
            return False
    
    def run(self):
        """Main service loop."""
        # Setup signal handlers
        signal.signal(signal.SIGTERM, self._signal_handler)
        signal.signal(signal.SIGINT, self._signal_handler)
        
        # Notify systemd we're ready
        if self.watchdog_enabled:
            self._notify_systemd("READY=1")
            logger.info("Service ready, watchdog active")
        
        self.running = True
        last_watchdog = time.time()
        
        try:
            while self.running:
                # Do the actual work
                if not self._do_work():
                    logger.error("Work cycle failed, service degraded")
                    # Don't send watchdog notification on failure
                    continue
                
                # Send watchdog heartbeat
                if self.watchdog_enabled:
                    current_time = time.time()
                    if current_time - last_watchdog >= self.watchdog_interval:
                        if self._notify_systemd():
                            logger.debug("Watchdog heartbeat sent")
                            last_watchdog = current_time
                        else:
                            logger.error("Failed to send watchdog heartbeat")
                
                # Small sleep to prevent CPU spinning
                time.sleep(0.1)
                
        except Exception as e:
            logger.error(f"Service error: {e}")

Understanding when to use each prevents over-engineering while ensuring adequate protection.</p><p class="text-slate-300 leading-relaxed mb-4">| Mechanism | Failure Type Detected | Response Time | Resource Cost | Best For |
|-----------|----------------------|---------------|---------------|----------|
| <strong>Systemd Restart</strong> | Process crashes, exits | 10-30 seconds | Low | All long-running services |
| <strong>Health Check + Cron</strong> | Hung processes, degraded state | 2-5 minutes | Medium | Services with HTTP endpoints |
| <strong>Systemd Watchdog</strong> | Complete hangs, deadlocks | 30-60 seconds | Low | Critical infrastructure |
| <strong>Hardware Watchdog</strong> | Kernel panics, total system failure | Seconds | Hardware required | Embedded systems, bare metal |</p><p class="text-slate-300 leading-relaxed mb-4">Systemd restart handles the most common failure mode: a process that exits unexpectedly. Health checks catch semantic failures where the process runs but does not function correctly. Watchdog timers catch the worst-case scenarios where the process or system becomes completely unresponsive.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">Raj's 3 AM incident taught several valuable lessons that apply to any service reliability implementation:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Assume failure will happen</strong>: Design for failure from the start. Every service crashes eventually. The question is whether your system recovers automatically or requires someone to wake up at 3 AM.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Layer your defenses</strong>: No single mechanism catches every failure type. Systemd restarts handle crashes, health checks catch degraded states, and watchdogs catch total system hangs. Use all three for critical services.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Test your recovery</strong>: A restart mechanism that has never been tested is merely theoretical. Raj now runs "chaos engineering" exercises monthly, randomly killing services to verify recovery works.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Monitor the monitors</strong>: Health checks and watchdogs can fail too. Log every recovery action and alert if recovery attempts exceed normal thresholds. Three restarts in an hour indicates a deeper problem.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Resource limits save systems</strong>: Without <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">MemoryMax</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CPUQuota</code>, a leaking service can consume all available resources and crash unrelated processes. Always set conservative limits.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit your current services</strong>: List all production services and verify each has <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=always</code> configured. Services without automatic restart are incidents waiting to happen.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Implement health checks this week</strong>: Pick your three most critical services and create Python health check scripts that verify actual functionality, not just process existence.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Set resource limits</strong>: Add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">MemoryMax</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CPUQuota</code> to every systemd service. Start with 2x current usage and adjust based on monitoring data.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Create a recovery runbook</strong>: Document the exact commands and logs to check when automatic recovery fails. Store it where on-call engineers can find it at 3 AM.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Schedule chaos testing</strong>: Kill a non-critical service in staging this week and measure recovery time. Use results to improve your monitoring and alerting thresholds.</li></p><p class="text-slate-300 leading-relaxed mb-4">After implementing these patterns, Raj's payment processing service has run for six months without a single manual restart. The system handles memory leaks, network interruptions, and even a full disk scenario without human intervention. Self-healing is not magic; it is careful engineering with the right tools applied at the right layers.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
