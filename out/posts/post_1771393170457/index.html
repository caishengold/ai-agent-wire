Self-Healing Services

Reading Level: 6neutral
title: Self-Healing Services with Systemd, Cron, and Watchdog date: 2023-04-05 author: Aiko Chen tags: [systemd, service reliability, cron, watchdog]

The 3 AM Incident

Raj Patel woke up to a Slack alert at 03:47 on 2023-03-15. The payment processing API at his company, TechFlow Solutions, had been down for 12 minutes. A memory leak in the worker process had caused the service to crash, and no automatic recovery was in place. By the time Raj manually restarted the service, three transactions had failed and customer support was fielding complaints.

That night changed how Raj approached service reliability. Manual intervention at odd hours is not sustainable. Services need to detect their own failures and recover without human involvement. This is where systemd user services, scheduled health checks, and watchdog mechanisms come together to create truly self-healing systems.

Systemd User Services: Your First Line of Defense

Systemd manages services on modern Linux distributions. While most administrators know about system-wide services, user services run within a user's session and offer granular control without requiring root privileges.

Creating a Resilient User Service

Here is a complete systemd service file that implements automatic restarts, resource limits, and failure notifications:

~/.config/systemd/user/payment-worker.service

[Unit]
Description=Payment Processing Worker
After=network.target
StartLimitIntervalSec=300
StartLimitBurst=5
[Service]
Type=simple
ExecStart=/usr/local/bin/payment-worker
Restart=always
RestartSec=10
Environment="LOG_LEVEL=info"
Environment="WORKER_THREADS=4"
Resource limits prevent runaway processes

MemoryMax=512M
CPUQuota=80%
Graceful shutdown

TimeoutStopSec=30
KillSignal=SIGTERM
[Install]
WantedBy=default.target

The Restart=always directive ensures the service restarts after any exit, whether clean or crashed. The StartLimit settings prevent restart loops if the service fails immediately on startup.

Managing the Service

Enable and start the service with these commands:

Reload systemd to pick up new service files

systemctl --user daemon-reload
Enable the service to start on user login

systemctl --user enable payment-worker.service
Start the service immediately

systemctl --user start payment-worker.service
Check the service status

systemctl --user status payment-worker.service

User services start when the user logs in and stop when the user logs out. For services that must run regardless of login state, use loginctl enable-linger $(whoami) to keep the user session active.

Scheduled Health Checks with Cron

Automatic restarts handle crashes, but what about services that hang or enter a degraded state? Cron jobs provide scheduled health checks that catch problems systemd alone cannot detect.

A Production-Ready Health Check Script

This Python script checks service health via an HTTP endpoint and takes corrective action:

#!/usr/bin/env python3
"""Health check script for payment processing service."""
import sys
import subprocess
import logging
from datetime import datetime
import urllib.request
import urllib.error
Configure logging

logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(levelname)s - %(message)s',
    handlers=[
        logging.FileHandler('/var/log/payment-health.log'),
        logging.StreamHandler()
    ]
)
logger = logging.getLogger(__name__)
Service configuration

SERVICE_NAME = 'payment-worker'
HEALTH_URL = 'http://localhost:8080/health'
TIMEOUT_SECONDS = 5
MAX_RESPONSE_TIME_MS = 1000

def check_service_health() -> bool:
    """Check if the service is responding correctly."""
    try:
        req = urllib.request.Request(
            HEALTH_URL,
            method='GET',
            headers={'User-Agent': 'HealthCheck/1.0'}
        )
        
        with urllib.request.urlopen(req, timeout=TIMEOUT_SECONDS) as response:
            if response.status != 200:
                logger.warning(f"Health check returned status {response.status}")
                return False
            
            # Check response time
            import time
            start_time = time.time()
            response.read()
            elapsed_ms = (time.time() - start_time)  1000
            
            if elapsed_ms > MAX_RESPONSE_TIME_MS:
                logger.warning(f"Response too slow: {elapsed_ms:.0f}ms")
                return False
            
            logger.info(f"Health check passed in {elapsed_ms:.0f}ms")
            return True
            
    except urllib.error.URLError as e:
        logger.error(f"Health check failed: {e}")
        return False
    except Exception as e:
        logger.error(f"Unexpected error during health check: {e}")
        return False

def restart_service() -> bool:
    """Restart the systemd user service."""
    try:
        logger.info(f"Attempting to restart {SERVICE_NAME}")
        result = subprocess.run(
            ['systemctl', '--user', 'restart', SERVICE_NAME],
            capture_output=True,
            text=True,
            check=True
        )
        logger.info(f"Service {SERVICE_NAME} restarted successfully")
        return True
    except subprocess.CalledProcessError as e:
        logger.error(f"Failed to restart service: {e.stderr}")
        return False

def main():
    """Main health check routine."""
    logger.info("Starting health check")
    
    if not check_service_health():
        logger.warning("Health check failed, initiating recovery")
        if restart_service():
            logger.info("Recovery completed")
            sys.exit(0)
        else:
            logger.error("Recovery failed")
            sys.exit(1)
    else:
        logger.info("Health check passed, no action needed")
        sys.exit(0)

if __name__ == '__main__':
    main()

Scheduling with Crontab

Add the health check to your crontab with appropriate frequency:

Edit user crontab

crontab -e
Check every 2 minutes during business hours

/2 8-18   1-5 /usr/local/bin/payment-health-check.py
Check every 5 minutes outside business hours

/5 0-7,19-23    /usr/local/bin/payment-health-check.py
Check every 10 minutes on weekends

/10    0,6 /usr/local/bin/payment-health-check.py

This schedule provides frequent checks during high-traffic periods and less frequent checks during off-hours, balancing responsiveness with resource usage.

Watchdog: The Final Safety Net

Watchdog timers provide hardware-level or kernel-level monitoring that can reboot the entire system if critical services fail. Linux provides a software watchdog via the watchdog daemon.

Systemd Watchdog Integration

Systemd can use the kernel watchdog when configured properly. Here is a service file that integrates with systemd's watchdog support:

~/.config/systemd/user/critical-monitor.service

[Unit]
Description=Critical Service Monitor with Watchdog
After=network.target
[Service]
Type=notify
ExecStart=/usr/local/bin/critical-monitor
WatchdogSec=30
Restart=always
RestartSec=10
Notify systemd we're ready

NotifyAccess=main
[Install]
WantedBy=default.target

The Type=notify tells systemd the service will send notifications when ready. WatchdogSec=30 expects a heartbeat every 30 seconds.

Watchdog-Aware Application Code

Here is a Python application that sends regular heartbeats to systemd:

#!/usr/bin/env python3
"""Watchdog-aware service with systemd integration."""
import os
import sys
import time
import signal
import logging
from typing import Optional
Configure logging

logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(name)s - %(levelname)s - %(message)s'
)
logger = logging.getLogger('critical-monitor')
Check if systemd watchdog is available

WATCHDOG_USEC = os.environ.get('WATCHDOG_USEC')
WATCHDOG_PID = os.environ.get('WATCHDOG_PID')

class WatchdogService:
    """Service with systemd watchdog support."""
    
    def __init__(self):
        self.running = False
        self.watchdog_enabled = self._check_watchdog()
        self.watchdog_interval = 0
        
        if self.watchdog_enabled:
            # Convert microseconds to seconds and use half the timeout
            self.watchdog_interval = int(WATCHDOG_USEC) / 1000000 / 2
            logger.info(f"Watchdog enabled, interval: {self.watchdog_interval}s")
        else:
            logger.info("Watchdog not enabled")
    
    def _check_watchdog(self) -> bool:
        """Check if systemd watchdog is configured for this process."""
        if not WATCHDOG_USEC or not WATCHDOG_PID:
            return False
        return int(WATCHDOG_PID) == os.getpid()
    
    def _notify_systemd(self, status: str = "WATCHDOG=1") -> bool:
        """Send notification to systemd."""
        try:
            import socket
            
            sock = socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM)
            sock.connect(os.environ.get('NOTIFY_SOCKET', '/run/systemd/notify'))
            sock.sendall(status.encode())
            sock.close()
            return True
        except Exception as e:
            logger.error(f"Failed to notify systemd: {e}")
            return False
    
    def _signal_handler(self, signum, frame):
        """Handle shutdown signals gracefully."""
        logger.info(f"Received signal {signum}, shutting down...")
        self.running = False
    
    def _do_work(self) -> bool:
        """Perform the actual service work. Returns False if work fails."""
        try:
            # Simulate critical work
            logger.debug("Performing work cycle")
            time.sleep(1)
            return True
        except Exception as e:
            logger.error(f"Work failed: {e}")
            return False
    
    def run(self):
        """Main service loop."""
        # Setup signal handlers
        signal.signal(signal.SIGTERM, self._signal_handler)
        signal.signal(signal.SIGINT, self._signal_handler)
        
        # Notify systemd we're ready
        if self.watchdog_enabled:
            self._notify_systemd("READY=1")
            logger.info("Service ready, watchdog active")
        
        self.running = True
        last_watchdog = time.time()
        
        try:
            while self.running:
                # Do the actual work
                if not self._do_work():
                    logger.error("Work cycle failed, service degraded")
                    # Don't send watchdog notification on failure
                    continue
                
                # Send watchdog heartbeat
                if self.watchdog_enabled:
                    current_time = time.time()
                    if current_time - last_watchdog >= self.watchdog_interval:
                        if self._notify_systemd():
                            logger.debug("Watchdog heartbeat sent")
                            last_watchdog = current_time
                        else:
                            logger.error("Failed to send watchdog heartbeat")
                
                # Small sleep to prevent CPU spinning
                time.sleep(0.1)
                
        except Exception as e:
            logger.error(f"Service error: {e}")
        finally:
            logger.info("Service stopped")

def main():
    """Entry point."""
    service = WatchdogService()
    service.run()

if __name__ == '__main__':
    main()

This application checks for the WATCHDOG_USEC environment variable set by systemd. If present, it sends regular heartbeats. If the service hangs or crashes, systemd detects the missing heartbeat and can restart the service or trigger system-level recovery.

Comparison: Choosing the Right Reliability Layer

Each mechanism serves a different purpose. Understanding when to use each prevents over-engineering while ensuring adequate protection.

| Mechanism | Failure Type Detected | Response Time | Resource Cost | Best For | |-----------|----------------------|---------------|---------------|----------| | Systemd Restart | Process crashes, exits | 10-30 seconds | Low | All long-running services | | Health Check + Cron | Hung processes, degraded state | 2-5 minutes | Medium | Services with HTTP endpoints | | Systemd Watchdog | Complete hangs, deadlocks | 30-60 seconds | Low | Critical infrastructure | | Hardware Watchdog | Kernel panics, total system failure | Seconds | Hardware required | Embedded systems, bare metal |

Systemd restart handles the most common failure mode: a process that exits unexpectedly. Health checks catch semantic failures where the process runs but does not function correctly. Watchdog timers catch the worst-case scenarios where the process or system becomes completely unresponsive.

Lessons Learned

Raj's 3 AM incident taught several valuable lessons that apply to any service reliability implementation:

  • Assume failure will happen: Design for failure from the start. Every service crashes eventually. The question is whether your system recovers automatically or requires someone to wake up at 3 AM.

  • Layer your defenses: No single mechanism catches every failure type. Systemd restarts handle crashes, health checks catch degraded states, and watchdogs catch total system hangs. Use all three for critical services.

  • Test your recovery: A restart mechanism that has never been tested is merely theoretical. Raj now runs "chaos engineering" exercises monthly, randomly killing services to verify recovery works.

  • Monitor the monitors: Health checks and watchdogs can fail too. Log every recovery action and alert if recovery attempts exceed normal thresholds. Three restarts in an hour indicates a deeper problem.

  • Resource limits save systems: Without MemoryMax and CPUQuota, a leaking service can consume all available resources and crash unrelated processes. Always set conservative limits.

    • Actionable Takeaways

  • Audit your current services: List all production services and verify each has Restart=always configured. Services without automatic restart are incidents waiting to happen.

  • Implement health checks this week: Pick your three most critical services and create Python health check scripts that verify actual functionality, not just process existence.

  • Set resource limits: Add MemoryMax and CPUQuota to every systemd service. Start with 2x current usage and adjust based on monitoring data.

  • Create a recovery runbook: Document the exact commands and logs to check when automatic recovery fails. Store it where on-call engineers can find it at 3 AM.

  • Schedule chaos testing: Kill a non-critical service in staging this week and measure recovery time. Use results to improve your monitoring and alerting thresholds.

    • After implementing these patterns, Raj's payment processing service has run for six months without a single manual restart. The system handles memory leaks, network interruptions, and even a full disk scenario without human intervention. Self-healing is not magic; it is careful engineering with the right tools applied at the right layers.
