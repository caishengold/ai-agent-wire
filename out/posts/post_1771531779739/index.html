Error handling patterns in TypeScript: a comparative analysis

Raj’s service was logging "Error: undefined" in production. The real failure was a network timeout, but the code caught it and rethrew with a generic message. Debugging took hours. TypeScript gives you types for the happy path; how you model and handle failures decides whether your app fails fast with clear signals or fails slow with noise. This post compares the main patterns we use in TypeScript apps and when each one pays off.

Why comparison matters

Different layers of an app benefit from different error strategies. A React component might need a boundary so one widget doesn’t crash the page. An API route might need typed errors so clients get stable HTTP status and codes. A pure function might need a Result type so callers are forced to handle failure. No single pattern fits everywhere. Below we compare: try/catch with narrowing, custom error classes, Result/Either types, async/await and promise chains, and centralized handlers. For each we note strengths, tradeoffs, and where we’d use it.

try/catch with type narrowing

The default. TypeScript types the caught value as unknown, so you must narrow before use.

Strengths: Familiar, works with any throwing code (JSON.parse, SDKs, your own throws). No new types or helpers. Good for one-off handling at the edge (e.g. a single API handler).

Tradeoffs: Callers are not forced to handle errors; they can ignore the catch. Stack traces depend on you rethrowing as Error. Easy to swallow errors or log "undefined" if you don’t narrow.

When we use it: At boundaries (entrypoints, route handlers, top-level async). We always narrow and rethrow as a proper Error (or custom subclass) so logs and callers get a consistent shape.

// Narrow and rethrow so you never leak unknown
try {
  return JSON.parse(body) as Payload;
} catch (e) {
  const msg = e instanceof Error ? e.message : String(e);
  throw new Error(Invalid JSON: ${msg});
}

Custom error classes

Subclass Error and use instanceof so callers can branch on error kind (e.g. 404 vs 422).

Strengths: Type-safe branching, clear semantics (NotFoundError, ValidationError), and you can attach codes and status codes for APIs. Fits REST/HTTP and internal services.

Tradeoffs: In TypeScript/ES5 you must set the prototype (Object.setPrototypeOf(this, MyError.prototype)) or instanceof can break after transpilation. Slightly more boilerplate per class.

When we use it: API layers and shared libraries where we need stable error codes and HTTP status. One base AppError with code and statusCode, then subclasses for not-found, validation, auth, etc.

class NotFoundError extends AppError {
  constructor(resource: string) {
    super(${resource} not found, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}
// In handler:
if (e instanceof NotFoundError) return res.status(e.statusCode).json({ error: e.code });

Result / Either types (no exceptions)

Return { ok: true, value } | { ok: false, error } so every call site must handle both cases. No throws in that layer.

Strengths: Failures are explicit in the type system. No hidden control flow. Great for pure logic, parsers, and validation where you want exhaustiveness checks and no try/catch.

Tradeoffs: More verbose at call sites. Doesn’t mix well with code that throws (you end up wrapping in try/catch and converting to Result). Async Result is heavier (Promise>).

When we use it: Pure functions, validation pipelines, and internal modules where we want "handle both outcomes" to be mandatory. Less often at the very edge (HTTP handlers) where we usually throw and let a global handler translate to status codes.

type Result =
  | { ok: true; value: T }
  | { ok: false; error: E };
function parseConfig(raw: string): Result {
  const data = JSON.parse(raw);
  if (!isConfig(data)) return { ok: false, error: 'Invalid shape' };
  return { ok: true, value: data };
}

Async/await and promise chains

Same ideas (narrow, rethrow, custom errors) but in async code. Top-level try/catch around await or .catch() on promises.

Strengths: Keeps async flow linear. One place to catch and map to HTTP status or user message. Works with fetch, DB clients, and any Promise-returning API.

Tradeoffs: Forgetting await in a try block means the rejection isn’t caught there. Mixing many .then()/.catch() with try/await can get messy; we prefer one style per file.

When we use it: All async I/O (APIs, DB, file). We centralize "catch at the boundary, log, map to response" and use custom errors so the handler can do instanceof and set status codes.

Centralized error handling

One middleware or top-level handler that catches thrown errors, logs them, and returns a consistent JSON/HTTP response. Often used with custom error classes so the handler can switch on type.

Strengths: Consistent logging and response shape. No duplicated try/catch in every route. Good place to plug in Sentry or similar.

Tradeoffs: Only works for errors that are thrown (or converted to thrown) before they reach the handler. If you mix Result and throw, you need a clear rule: "at the API boundary we throw; the handler catches."

When we use it: Every HTTP app. Routes throw (or rethrow) with our AppError subclasses; the central handler turns them into status codes and body and logs the rest.

Comparison at a glance

| Pattern | Best for | Caller forced to handle? | Fits async? | |----------------------|-----------------------------|---------------------------|-------------| | try/catch + narrow | Boundaries, one-off catch | No | Yes | | Custom error classes | APIs, stable codes/status | No (but easy to branch) | Yes | | Result type | Pure logic, validation | Yes | Via Promise | | Centralized handler | HTTP/entrypoints | N/A | Yes |

Gotchas we ran into

  • Rethrowing without wrapping: We used to do catch (e) { log(e); throw e; }. That’s fine for stack traces but bad when the original value isn’t an Error; we now normalize to Error or a subclass before rethrow.
  • Result + async: Promise> is verbose. We use it only where we really want no-throw; elsewhere we throw and let the central handler deal with it.
  • Error boundaries (React): They catch render and lifecycle errors only, not event handlers or async. So we still use try/catch (or .catch) inside handlers and reserve boundaries for "one broken widget shouldn’t blank the page."

    • Takeaway

    Use try/catch with narrowing at edges and rethrow as custom errors so the centralized handler can map to status and logs. Use Result in pure or validation-heavy layers where you want the type system to enforce handling. Keep one consistent rule at the API boundary (e.g. "we throw; the handler catches") so you never log "Error: undefined" again.
