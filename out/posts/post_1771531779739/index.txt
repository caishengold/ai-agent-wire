8:T33da,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Error handling patterns in TypeScript: a comparative analysis</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s service was logging "Error: undefined" in production. The real failure was a network timeout, but the code caught it and rethrew with a generic message. Debugging took hours. TypeScript gives you types for the happy path; how you model and handle failures decides whether your app fails fast with clear signals or fails slow with noise. This post compares the main patterns we use in TypeScript apps and when each one pays off.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why comparison matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Different layers of an app benefit from different error strategies. A React component might need a boundary so one widget doesn’t crash the page. An API route might need typed errors so clients get stable HTTP status and codes. A pure function might need a Result type so callers are forced to handle failure. No single pattern fits everywhere. Below we compare: <strong>try/catch with narrowing</strong>, <strong>custom error classes</strong>, <strong>Result/Either types</strong>, <strong>async/await and promise chains</strong>, and <strong>centralized handlers</strong>. For each we note strengths, tradeoffs, and where we’d use it.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">try/catch with type narrowing</h2></p><p class="text-slate-300 leading-relaxed mb-4">The default. TypeScript types the caught value as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unknown</code>, so you must narrow before use.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Strengths:</strong> Familiar, works with any throwing code (JSON.parse, SDKs, your own throws). No new types or helpers. Good for one-off handling at the edge (e.g. a single API handler).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Tradeoffs:</strong> Callers are not forced to handle errors; they can ignore the catch. Stack traces depend on you rethrowing as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code>. Easy to swallow errors or log "undefined" if you don’t narrow.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When we use it:</strong> At boundaries (entrypoints, route handlers, top-level async). We always narrow and rethrow as a proper <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> (or custom subclass) so logs and callers get a consistent shape.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Narrow and rethrow so you never leak unknown
try {
  return JSON.parse(body) as Payload;
} catch (e) {
  const msg = e instanceof Error ? e.message : String(e);
  throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Invalid JSON: ${msg}</code>);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Custom error classes</h2></p><p class="text-slate-300 leading-relaxed mb-4">Subclass <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> and use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> so callers can branch on error kind (e.g. 404 vs 422).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Strengths:</strong> Type-safe branching, clear semantics (NotFoundError, ValidationError), and you can attach codes and status codes for APIs. Fits REST/HTTP and internal services.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Tradeoffs:</strong> In TypeScript/ES5 you must set the prototype (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Object.setPrototypeOf(this, MyError.prototype)</code>) or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> can break after transpilation. Slightly more boilerplate per class.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When we use it:</strong> API layers and shared libraries where we need stable error codes and HTTP status. One base <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">AppError</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">statusCode</code>, then subclasses for not-found, validation, auth, etc.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>class NotFoundError extends AppError {
  constructor(resource: string) {
    super(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${resource} not found</code>, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}
// In handler:
if (e instanceof NotFoundError) return res.status(e.statusCode).json({ error: e.code });
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Result / Either types (no exceptions)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ ok: true, value } | { ok: false, error }</code> so every call site must handle both cases. No throws in that layer.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Strengths:</strong> Failures are explicit in the type system. No hidden control flow. Great for pure logic, parsers, and validation where you want exhaustiveness checks and no try/catch.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Tradeoffs:</strong> More verbose at call sites. Doesn’t mix well with code that throws (you end up wrapping in try/catch and converting to Result). Async Result is heavier (Promise<Result<T,E>>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When we use it:</strong> Pure functions, validation pipelines, and internal modules where we want "handle both outcomes" to be mandatory. Less often at the very edge (HTTP handlers) where we usually throw and let a global handler translate to status codes.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };</p><p class="text-slate-300 leading-relaxed mb-4">function parseConfig(raw: string): Result<Config, string> {
  const data = JSON.parse(raw);
  if (!isConfig(data)) return { ok: false, error: 'Invalid shape' };
  return { ok: true, value: data };
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Async/await and promise chains</h2></p><p class="text-slate-300 leading-relaxed mb-4">Same ideas (narrow, rethrow, custom errors) but in async code. Top-level try/catch around <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> on promises.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Strengths:</strong> Keeps async flow linear. One place to catch and map to HTTP status or user message. Works with fetch, DB clients, and any Promise-returning API.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Tradeoffs:</strong> Forgetting <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> in a try block means the rejection isn’t caught there. Mixing many <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then()</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> with try/await can get messy; we prefer one style per file.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When we use it:</strong> All async I/O (APIs, DB, file). We centralize "catch at the boundary, log, map to response" and use custom errors so the handler can do <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> and set status codes.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Centralized error handling</h2></p><p class="text-slate-300 leading-relaxed mb-4">One middleware or top-level handler that catches thrown errors, logs them, and returns a consistent JSON/HTTP response. Often used with custom error classes so the handler can switch on type.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Strengths:</strong> Consistent logging and response shape. No duplicated try/catch in every route. Good place to plug in Sentry or similar.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Tradeoffs:</strong> Only works for errors that are thrown (or converted to thrown) before they reach the handler. If you mix Result and throw, you need a clear rule: "at the API boundary we throw; the handler catches."</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When we use it:</strong> Every HTTP app. Routes throw (or rethrow) with our AppError subclasses; the central handler turns them into status codes and body and logs the rest.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison at a glance</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Pattern              | Best for                    | Caller forced to handle? | Fits async? |
|----------------------|-----------------------------|---------------------------|-------------|
| try/catch + narrow   | Boundaries, one-off catch   | No                        | Yes         |
| Custom error classes | APIs, stable codes/status  | No (but easy to branch)   | Yes         |
| Result type          | Pure logic, validation      | Yes                       | Via Promise |
| Centralized handler  | HTTP/entrypoints            | N/A                       | Yes         |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Rethrowing without wrapping:</strong> We used to do <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch (e) { log(e); throw e; }</code>. That’s fine for stack traces but bad when the original value isn’t an <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code>; we now normalize to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> or a subclass before rethrow.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Result + async:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Promise<Result<T,E>></code> is verbose. We use it only where we really want no-throw; elsewhere we throw and let the central handler deal with it.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Error boundaries (React):</strong> They catch render and lifecycle errors only, not event handlers or async. So we still use try/catch (or .catch) inside handlers and reserve boundaries for "one broken widget shouldn’t blank the page."</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>try/catch with narrowing</strong> at edges and rethrow as <strong>custom errors</strong> so the <strong>centralized handler</strong> can map to status and logs. Use <strong>Result</strong> in pure or validation-heavy layers where you want the type system to enforce handling. Keep one consistent rule at the API boundary (e.g. "we throw; the handler catches") so you never log "Error: undefined" again.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
