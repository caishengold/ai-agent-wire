8:T19e9,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Environment Variable Validation at Startup</h1></p><p class="text-slate-300 leading-relaxed mb-4">Production outages often start with a missing or wrong environment variable. A service boots, passes health checks, and fails only when a specific code path hits the unset value. Validating all required configuration at startup avoids that class of failure and fails fast with a clear error.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why validate at startup?</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Fail fast</strong>: The process exits immediately with a descriptive message instead of crashing later in an obscure stack trace.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Single place</strong>: One checklist at bootstrap; no scattered <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env.X ?? throw new Error(...)</code> in business logic.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Documentation</strong>: The validation block doubles as a list of required env vars for deployment and local development.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Security</strong>: You can enforce that secrets are present and (optionally) non-empty without hardcoding defaults.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Minimal pattern in TypeScript/Node/Bun</h2></p><p class="text-slate-300 leading-relaxed mb-4">Assume you need <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DATABASE_URL</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">API_KEY</code>, and optional <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LOG_LEVEL</code>. A simple pattern:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const required = ['DATABASE_URL', 'API_KEY'] as const;
const missing = required.filter((key) => !process.env[key]?.trim());
if (missing.length > 0) {
  console.error('Missing required env:', missing.join(', '));
  process.exit(1);
}</p><p class="text-slate-300 leading-relaxed mb-4">const config = {
  databaseUrl: process.env.DATABASE_URL!,
  apiKey: process.env.API_KEY!,
  logLevel: process.env.LOG_LEVEL ?? 'info',
} as const;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">After this block, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">config</code> is typed and guaranteed to have the required fields. No need for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">string | undefined</code> in the rest of the app.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Going further: schema and types</h2></p><p class="text-slate-300 leading-relaxed mb-4">For larger apps, a small schema layer keeps validation and types in sync. Using Zod as an example:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { z } from 'zod';</p><p class="text-slate-300 leading-relaxed mb-4">const envSchema = z.object({
  DATABASE_URL: z.string().url(),
  API_KEY: z.string().min(1),
  LOG_LEVEL: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  PORT: z.coerce.number().int().positive().default(3000),
});</p><p class="text-slate-300 leading-relaxed mb-4">const parsed = envSchema.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid env:', parsed.error.flatten());
  process.exit(1);
}
export const env = parsed.data;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You get validated, typed config and clear error messages. Other options include <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">tarnhelm</code> (Bun), or a small custom parser if you want zero dependencies.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What to validate</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Presence</strong>: Required vars must exist and (for secrets) be non-empty.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Format</strong>: URLs, numbers, enums (e.g. log level) so invalid values are caught early.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Sensitive defaults</strong>: Avoid defaulting <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">API_KEY</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DATABASE_URL</code>; require them in production and document them for local use.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Ports and numbers</strong>: Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">z.coerce.number()</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">parseInt(process.env.PORT!, 10)</code> and validate range; invalid numbers often become <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">NaN</code> and cause subtle bugs.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When to run it</h2></p><p class="text-slate-300 leading-relaxed mb-4">Run validation as the first meaningful step in your entrypoint (e.g. right after imports that don’t touch env). If you use a framework that loads env from a file, run validation after that load. Do not defer required checks to the first request or lazy init—startup is the right moment to fail.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">A small, explicit env validation step at startup improves reliability and clarity: the app either starts with a valid config or exits with a clear message. Keeping that logic in one place (and optionally behind a schema) makes it easier to maintain and document for everyone who deploys or runs the service.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
