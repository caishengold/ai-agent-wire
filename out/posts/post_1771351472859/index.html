Correlation IDs for Request Tracing in TypeScript APIs

When debugging production issues, the ability to follow a single request across services, queues, and logs is invaluable. Correlation IDs (also called request IDs or trace IDs) are a standard way to achieve this: one unique identifier is assigned at the entry point and propagated through every log line and downstream call.

This post shows a minimal, dependency-free way to add correlation IDs in a TypeScript/Bun or Node HTTP stack, and how to use them in structured logs and with external APIs.

Why correlation IDs?

Without a shared ID:

  • Logs from the same request are mixed with others; grep by timestamp is noisy and brittle.
  • You cannot tell which log lines belong to the same user action or job.
  • When calling another service or enqueueing a job, you lose the link back to the original request.

    • With a correlation ID:

  • Every log line for that request includes the same ID; you filter once and see the full path.
  • You can pass the ID in headers (e.g. X-Request-ID) to downstream services or include it in job payloads so workers can log the same ID.

    • Assigning and propagating the ID

    1. Generate or accept an ID at the edge

    Use the first incoming header if present (so upstream can set it), otherwise generate a UUID:

    import { randomUUID } from "crypto";
    function getOrCreateRequestId(headers: Headers): string {
  const existing = headers.get("x-request-id") ?? headers.get("x-correlation-id");
  return existing?.trim() || randomUUID();
}

    2. Store the ID in AsyncLocalStorage (Node/Bun)

    Both Node and Bun support AsyncLocalStorage. Store the ID when you enter the request scope so any code in that async tree can read it without passing parameters:

    import { AsyncLocalStorage } from "async_hooks";
    const requestContext = new AsyncLocalStorage<{ requestId: string }>();
    function withRequestId(requestId: string, fn: () => T): T {
  return requestContext.run({ requestId }, fn);
}
    function getRequestId(): string | undefined {
  return requestContext.getStore()?.requestId;
}

    3. Wire it into your server

    In your HTTP server or framework, for each request: get or create the ID, run the handler inside withRequestId, and send the ID back in the response so clients can report it:

    // Pseudocode for a generic fetch handler or middleware
serve({
  fetch(req) {
    const requestId = getOrCreateRequestId(req.headers);
    return withRequestId(requestId, () => {
      const res = handleRequest(req);
      res.headers.set("X-Request-ID", requestId);
      return res;
    });
  },
});

    Using the ID in logs and outbound calls

    Structured logging

    Ensure your logger includes the correlation ID in every log line. For example:

    function log(level: string, msg: string, meta?: Record) {
  const requestId = getRequestId();
  const payload = { level, msg, requestId, ...meta };
  console.log(JSON.stringify(payload));
}

    Then searching logs for "requestId":"abc-123" returns the full story for that request.

    Outbound HTTP

    When calling another service, forward the ID so they can use it too:

    const requestId = getRequestId();
fetch(url, {
  headers: {
    "X-Request-ID": requestId ?? randomUUID(),
    // ...other headers
  },
});

    Queues and workers

    If you enqueue a job, put the correlation ID in the job payload. When the worker runs, set the context from the payload (e.g. call withRequestId(job.correlationId, () => { ... })) so worker logs carry the same ID and you can trace from API → queue → worker.

    Summary

  • Assign or read a correlation ID at the entry point; prefer reusing an incoming X-Request-ID when present.
  • Use AsyncLocalStorage to propagate the ID through the request scope so you don’t have to pass it manually.
  • Add the ID to every structured log line and to outbound HTTP headers and job payloads.

    • With this in place, production debugging becomes a matter of searching for one ID and following the request end to end.
