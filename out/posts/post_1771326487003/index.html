Best practices for API security headers in 2026

A single missing or misconfigured header can expose your API to clickjacking, MIME sniffing, or information leakage. This post covers the headers that matter in 2026 and how to set them from a TypeScript API.

Why security headers matter

Headers tell browsers and clients how to treat your responses. Without them, defaults can be unsafe: browsers may guess content types, embed your pages in iframes, or leak details in error responses. Security headers are cheap to add and often required for compliance (e.g. OWASP, SOC 2).

Headers to set on every API response

Strict-Transport-Security (HSTS)

Forces clients to use HTTPS. After the first visit, the browser will not send requests over plain HTTP to your origin.

// Only on HTTPS. max-age in seconds; includeSubDomains and preload are common.
res.setHeader(
  "Strict-Transport-Security",
  "max-age=31536000; includeSubDomains; preload"
);

Gotcha: Do not enable HSTS on HTTP-only endpoints. You will lock clients into HTTPS before your cert is valid. Use a short max-age when testing.

X-Content-Type-Options

Stops the browser from MIME-sniffing. Without this, a response labeled text/plain that contains HTML could be executed as HTML.

res.setHeader("X-Content-Type-Options", "nosniff");

Set this on all responses. There is no downside for APIs.

X-Frame-Options

Controls whether your response can be embedded in an iframe. Use this to prevent clickjacking.

// Deny any framing
res.setHeader("X-Frame-Options", "DENY");
// Or allow only same-origin
res.setHeader("X-Frame-Options", "SAMEORIGIN");

For JSON APIs, DENY or SAMEORIGIN are both reasonable. If you serve HTML that must be framed by a partner, use Content-Security-Policy (see below) with frame-ancestors instead — it is more flexible and overrides X-Frame-Options when both are present.

Content-Security-Policy (CSP)

CSP restricts where resources can be loaded from and whether inline script/style is allowed. For API responses that are JSON, a minimal CSP still helps if the response is ever rendered in a browser context:

// For API JSON: strict default, no inline execution
res.setHeader(
  "Content-Security-Policy",
  "default-src 'none'; frame-ancestors 'none'"
);

For HTML-serving endpoints, you would tune default-src, script-src, style-src, etc. Start strict and relax only what you need; report-only mode can help you test without breaking the app.

Referrer-Policy

Controls how much of the URL is sent in the Referer header on outbound links or redirects. For APIs you often want to avoid leaking path or query data.

res.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");

Options: no-referrer (send nothing), strict-origin-when-cross-origin (full URL same-origin, only origin when cross-origin and downgrade to HTTPS), or same-origin (only for same-origin requests). Pick based on how much you want third-party sites to see.

Permissions-Policy (formerly Feature-Policy)

Disables browser features (camera, geolocation, etc.) for the page. For API responses that drive a front end, the front end’s HTML response should set this; for pure API endpoints it has limited effect but does not hurt.

res.setHeader(
  "Permissions-Policy",
  "camera=(), microphone=(), geolocation=()"
);

Hiding server identity

Reducing server fingerprinting and information leakage:

res.removeHeader("X-Powered-By"); // If your framework adds it
res.setHeader("X-DNS-Prefetch-Control", "off");

Avoid sending stack traces or framework names in error payloads to clients. Log them server-side instead.

Centralizing headers in a TypeScript API

Apply security headers in one place so every response gets them:

import type { IncomingMessage, ServerResponse } from "http";
function applySecurityHeaders(res: ServerResponse): void {
  res.setHeader("X-Content-Type-Options", "nosniff");
  res.setHeader("X-Frame-Options", "DENY");
  res.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
  res.setHeader(
    "Content-Security-Policy",
    "default-src 'none'; frame-ancestors 'none'"
  );
  res.setHeader(
    "Permissions-Policy",
    "camera=(), microphone=(), geolocation=()"
  );
  // Only if serving over HTTPS
  // res.setHeader("Strict-Transport-Security", "max-age=31536000; includeSubDomains; preload");
}
createServer((req: IncomingMessage, res: ServerResponse) => {
  applySecurityHeaders(res);
  // ... handle request
}).listen(3000);

In Express, use a middleware that calls applySecurityHeaders(res) before next(). In Hono or Elysia, use a similar middleware or a wrapper that runs on every response.

Gotchas and lessons learned

  • HSTS on HTTP: Enabling HSTS while still serving HTTP can make your site unreachable until max-age expires. Enable it only after HTTPS is stable.
  • CSP and APIs: A strict CSP on HTML is valuable; on JSON-only APIs the main benefit is frame-ancestors and avoiding accidental execution. Keep default-src 'none' for API routes that return only data.
  • Order and overrides: Browsers respect the first value for some headers and the strictest for others (e.g. CSP). Set security headers in middleware before route handlers so they are not overwritten by accident.
  • CORS: Security headers do not replace CORS. Use Access-Control-Allow-Origin (and related headers) explicitly; do not use for credentials or sensitive APIs.

    • Takeaway

    Add at least X-Content-Type-Options: nosniff and X-Frame-Options: DENY (or a CSP with frame-ancestors 'none') to every response. Put them in a single middleware or helper so new routes get them by default. Enable HSTS only over HTTPS. Run a scan (e.g. securityheaders.com or your own auditor) to confirm headers are present and correct.
