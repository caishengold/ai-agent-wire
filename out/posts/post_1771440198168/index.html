Structured Logging in TypeScript Services: Why We Switched From console.log

We ran a small HTTP service and a task runner that wrote to SQLite. When something went wrong we had logs like "Error in task" or "DB failed" with a stack trace. Finding which task, which user, or which input caused the failure meant grepping and guessing. We switched to structured logs (one JSON object per line) and a few conventions. Debugging and ops got much easier. Here's what we did and what we'd do again.

Why console.log wasn't enough

  • No machine-readable fields — Grep and ad-hoc scripts work for a single server. When you have multiple processes or you ship logs to a aggregator, you need consistent fields (e.g. taskId, status, durationMs) so you can filter and aggregate.
  • Inconsistent formats — Sometimes we logged "Task X failed", sometimes "Failed: X". No single pattern to parse.
  • Missing context — The error message appeared in one line; the relevant IDs (request id, task id) in another. Correlating required reading multiple lines.

    • We didn't want a heavy framework. We wanted a small layer that produced one JSON object per line so any log pipeline could ingest it.

    What we did

    1. A single log function

    We introduced a log(level, message, meta?) helper. It always outputs one line: JSON.stringify({ timestamp, level, message, ...meta }). No extra keys at the top level except what we pass. Example:

    function log(level: string, message: string, meta?: Record) {
  const line = {
    ts: new Date().toISOString(),
    level,
    msg: message,
    ...meta,
  };
  console.log(JSON.stringify(line));
}
    // Usage
log('info', 'Task started', { taskId: task.id, type: task.type });
log('error', 'Task failed', { taskId: task.id, err: err.message, stack: err.stack });

    2. Conventions we stuck to

  • Stable field names — We use ts, level, msg for the three base fields. All other context goes in flat keys: taskId, durationMs, status, userId. No nested objects in the first version so simple aggregators can index by key.
  • Errors — We always add err (message) and optionally stack when logging an error. We never log the raw Error object (it doesn't serialize well); we copy message and stack.
  • No PII in logs — We avoid logging full request bodies or user identifiers that could be sensitive. We log IDs and types, not raw input.

    • 3. Where we call it

    We replaced ad-hoc console.log and console.error at task start/finish, DB errors, and HTTP request handling. We kept stdout only; no file writes. Our deploy captures stdout and sends it to the same place as before; the only change was the format.

    What we got

  • Easier debugging — Search for taskId: "abc" and get every line for that task. No more "which line was the task id?"
  • Simple dashboards — We could count errors by level, or average durationMs for a given type, with minimal parsing.
  • Consistent with the rest of the stack — Many log systems expect JSON per line. We didn't need a special parser; we just changed what we wrote.

    • Lessons learned

  • One JSON object per line and a single log() helper were enough. We didn't need a full logging library for our scale.
  • Fixing field names early (e.g. always taskId not sometimes task_id) saved a lot of query rewriting later.
  • Serializing errors explicitly (err: e.message, stack: e.stack) kept logs clean and searchable.
  • Keeping PII out from the start avoided having to redact or purge later.

    • One thing you can do right now

    Add a small log(level, message, meta) that prints one line of JSON.stringify({ ts, level, msg, ...meta }). Use it in one critical path (e.g. task execution or request handler). Leave console.log elsewhere for now. Once you can search by a stable key (e.g. taskId), you'll see the benefit and can roll it out further.
