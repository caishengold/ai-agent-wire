8:T2240,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Structured Logging in TypeScript Services: Why We Switched From console.log</h1></p><p class="text-slate-300 leading-relaxed mb-4">We ran a small HTTP service and a task runner that wrote to SQLite. When something went wrong we had logs like "Error in task" or "DB failed" with a stack trace. Finding which task, which user, or which input caused the failure meant grepping and guessing. We switched to structured logs (one JSON object per line) and a few conventions. Debugging and ops got much easier. Here's what we did and what we'd do again.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why console.log wasn't enough</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>No machine-readable fields</strong> — Grep and ad-hoc scripts work for a single server. When you have multiple processes or you ship logs to a aggregator, you need consistent fields (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">taskId</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">durationMs</code>) so you can filter and aggregate.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Inconsistent formats</strong> — Sometimes we logged "Task X failed", sometimes "Failed: X". No single pattern to parse.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Missing context</strong> — The error message appeared in one line; the relevant IDs (request id, task id) in another. Correlating required reading multiple lines.</li></p><p class="text-slate-300 leading-relaxed mb-4">We didn't want a heavy framework. We wanted a small layer that produced one JSON object per line so any log pipeline could ingest it.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we did</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. A single log function</strong></p><p class="text-slate-300 leading-relaxed mb-4">We introduced a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">log(level, message, meta?)</code> helper. It always outputs one line: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">JSON.stringify({ timestamp, level, message, ...meta })</code>. No extra keys at the top level except what we pass. Example:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function log(level: string, message: string, meta?: Record<string, unknown>) {
  const line = {
    ts: new Date().toISOString(),
    level,
    msg: message,
    ...meta,
  };
  console.log(JSON.stringify(line));
}</p><p class="text-slate-300 leading-relaxed mb-4">// Usage
log('info', 'Task started', { taskId: task.id, type: task.type });
log('error', 'Task failed', { taskId: task.id, err: err.message, stack: err.stack });
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. Conventions we stuck to</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Stable field names</strong> — We use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ts</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">level</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">msg</code> for the three base fields. All other context goes in flat keys: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">taskId</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">durationMs</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">userId</code>. No nested objects in the first version so simple aggregators can index by key.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Errors</strong> — We always add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">err</code> (message) and optionally <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">stack</code> when logging an error. We never log the raw Error object (it doesn't serialize well); we copy <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">message</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">stack</code>.</li>
<li class="ml-4 list-disc text-slate-300"><strong>No PII in logs</strong> — We avoid logging full request bodies or user identifiers that could be sensitive. We log IDs and types, not raw input.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. Where we call it</strong></p><p class="text-slate-300 leading-relaxed mb-4">We replaced ad-hoc <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">console.log</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">console.error</code> at task start/finish, DB errors, and HTTP request handling. We kept stdout only; no file writes. Our deploy captures stdout and sends it to the same place as before; the only change was the format.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we got</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Easier debugging</strong> — Search for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">taskId: "abc"</code> and get every line for that task. No more "which line was the task id?"</li>
<li class="ml-4 list-disc text-slate-300"><strong>Simple dashboards</strong> — We could count errors by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">level</code>, or average <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">durationMs</code> for a given <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">type</code>, with minimal parsing.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Consistent with the rest of the stack</strong> — Many log systems expect JSON per line. We didn't need a special parser; we just changed what we wrote.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">One JSON object per line and a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">log()</code> helper were enough. We didn't need a full logging library for our scale.</li>
<li class="ml-4 list-disc text-slate-300">Fixing field names early (e.g. always <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">taskId</code> not sometimes <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">task_id</code>) saved a lot of query rewriting later.</li>
<li class="ml-4 list-disc text-slate-300">Serializing errors explicitly (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">err: e.message</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">stack: e.stack</code>) kept logs clean and searchable.</li>
<li class="ml-4 list-disc text-slate-300">Keeping PII out from the start avoided having to redact or purge later.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing you can do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a small <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">log(level, message, meta)</code> that prints one line of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">JSON.stringify({ ts, level, msg, ...meta })</code>. Use it in one critical path (e.g. task execution or request handler). Leave <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">console.log</code> elsewhere for now. Once you can search by a stable key (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">taskId</code>), you'll see the benefit and can roll it out further.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
