title: Bun CLI performance optimization — tips and tricks for high-performance web applications date: 2026-02-14

Your Bun app starts fast in development, but in production the CLI pipeline — installs, builds, and script runs — can still eat time and CPU. A few targeted tweaks turn that pipeline into something you can rely on at scale.

This post is for teams already using Bun and wanting to squeeze more out of it: faster cold starts, leaner builds, and scripts that don't surprise you under load. We focus on the CLI and toolchain, not application-level JS optimization.

Why the CLI pipeline matters

In high-performance web apps, the runtime is only part of the story. CI/CD, local dev loops, and deployment all run through the same CLI: bun install, bun run build, bun test. Slow or memory-heavy commands there add up across every developer and every pipeline run. Optimizing them pays off in wall-clock time and cost.

Install speed: lockfile and cache

Bun's install is already quick; you can make it more predictable.

  • Use a lockfile. Commit bun.lockb so every environment resolves the same dependency tree. No lockfile means re-resolving on every install and slower, inconsistent runs.
  • Reuse the global cache. Bun uses a single cache directory. In CI, persist it (e.g. ~/.bun/install/cache) between jobs so most installs are cache hits.

    • CI example: restore cache keyed by lockfile hash
    

    ... restore step for ~/.bun/install/cache ...
    
bun install --frozen-lockfile

  • Trim optional deps when safe. If you don't need optional native addons in a given environment, bun install with a clean env can skip some work. Profile first; the gain is environment-specific.

    • Build performance: scripts and tooling

    Use Bun's native bundler

    For builds, prefer bun build over spawning Node-based bundlers when you can. Fewer processes and less JS-on-JS overhead often mean faster and more stable builds.

    Single entry, ESM output — minimal config
    
bun build ./src/index.ts --outdir=./dist --target=bun

  • Splitting: Use --splitting for larger apps to get chunked output and better caching.
  • Minify only in production: Skip --minify in dev to speed up incremental builds.

    • Script orchestration

    Keep package.json scripts thin. Heavy logic belongs in small TypeScript/JavaScript modules that you run with bun run; that way Bun executes one process and you can profile a single entrypoint.

    {
  "scripts": {
    "build": "bun run scripts/build.ts",
    "test": "bun run scripts/test.ts"
  }
}

    We moved our build and test orchestration into typed scripts and saw more consistent timings and easier debugging than with long shell one-liners.

    Environment and runtime knobs

    Bun respects a few env vars that can help in constrained or noisy environments:

  • BUN_INSTALL_CACHE_DIR — Override cache location (e.g. to a fast volume or CI cache dir).
  • GOMAXPROCS — Bun's runtime uses Go; on big machines, limiting parallelism can sometimes reduce contention. Only tune if you've measured.

    • Avoid setting NODE_OPTIONS for Bun; it's a Node convention and can confuse or conflict with Bun's own flags.

    Monitoring and profiling

    Before optimizing, measure. We added a small performance monitoring script that runs key CLI commands (install, build, test) and logs duration and memory; that baseline made it obvious which step to improve first.

    // scripts/bench-cli.ts — measure install/build/test
const start = performance.now();
await $bun install --frozen-lockfile;
const installMs = performance.now() - start;
console.log({ installMs });

    Run this in CI or locally when you change tooling. If install jumps from 5s to 20s after a dependency change, you'll see it immediately.

    Lessons we ran into

  • Frontend checklist overlap: Our frontend performance checklist (bundle size, lazy loading, etc.) is separate from CLI performance. Don't confuse the two: CLI optimization speeds up how you build and ship; the checklist governs what you ship. Both matter for "high-performance" apps.
  • Docker and multi-stage builds: In containers, we use multi-stage builds: one stage for bun install and build, another for the runtime image. Only copy in node_modules and built assets, not the full repo or dev tooling. That keeps images smaller and builds faster. See Docker multi-stage build optimization for patterns.
  • Cold vs warm: The first bun invocation after a reboot or in a fresh container is slower. Our benchmarks always record both cold and warm runs so we don't over-optimize for the warm path only.

    • One thing to do next

    Pick one: add a single timing log around your main CI build (e.g. bun install + bun run build). Run it for a week. If the p95 drifts up, you'll have data to justify fixing the pipeline instead of guessing.

    Bun's official docs and CLI reference are the source for flags and env vars; this post reflects what worked for us in production-style web apps.
