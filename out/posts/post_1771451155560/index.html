10 systemd tricks every developer should know

Raj’s backup script ran via cron at 02:00. After a kernel update, the server rebooted at 01:58. Cron didn’t run the 02:00 job — the box was down. The next night it ran at 02:00 and again when someone manually triggered a restart at 14:00. No audit trail, no "last run" state in the journal, and no way to say "run this 5 minutes after boot, but only once." That mess pushed him to learn systemd timers, socket activation, and journald filters. What follows are 10 tricks that actually ship: timers instead of cron, on-demand services via sockets, and making the journal do the work when you debug.

Why systemd timers beat cron for many jobs

Cron is fine for "run this at 3 AM." It’s weak for: run after boot with a delay, run only if the previous run finished, or see unified logs next to your service. systemd timers give you calendar and monotonic schedules, same logging as the rest of the stack, and no duplicate runs from reboots.

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | cron | Simple, universal, no daemon config | No "after boot", no dependency ordering, logs scattered | One-off daily/weekly scripts, legacy boxes | | systemd timers | Calendar + monotonic, journal integration, OnActiveSec after boot | One unit pair per job (.service + .timer) | Scheduled jobs on systemd hosts, especially after-boot tasks | | External scheduler (e.g. CI) | Centralized, cross-host | Extra dependency, network | Multi-host or when you already have a scheduler |

Trick 1: Replace a cron job with a timer

Two files: a service (what runs) and a timer (when it runs). The service is a normal unit; the timer activates it on a schedule.

Example: Aiko runs a cleanup script every day at 04:30 and wants it in the journal.

Service — ~/.config/systemd/user/cleanup-cache.service:

[Unit]
Description=Daily cache cleanup
[Service]
Type=oneshot
ExecStart=/home/aiko/scripts/cleanup-cache.sh
StandardOutput=journal
StandardError=journal

Timer — ~/.config/systemd/user/cleanup-cache.timer:

[Unit]
Description=Run cleanup daily at 04:30
[Timer]
OnCalendar=-- 04:30:00
Persistent=yes
[Install]
WantedBy=timers.target

Persistent=yes means: if the machine was off at 04:30, run once when it’s next up. Enable and start the timer (not the service):

systemctl --user daemon-reload
systemctl --user enable --now cleanup-cache.timer
systemctl --user list-timers --all

Example output:

NEXT                        LEFT        LAST                        PASSED  UNIT
Thu 2026-02-13 04:30:00 CET 23h left    Wed 2026-02-12 04:30:01 CET 2h ago   cleanup-cache.timer

You never start cleanup-cache.service by hand for the schedule; the timer does. To run the job once manually: systemctl --user start cleanup-cache.service.

Trick 2: Run once after boot with a delay

Omar needed a "wait for the network and DB, then run the migration" job. Cron has no clean "once after boot." A timer with OnBootSec does.

Timer — migrate-after-boot.timer:

[Unit]
Description=Run migration 2 minutes after boot
[Timer]
OnBootSec=2min
AccuracySec=1min
[Install]
WantedBy=timers.target

OnBootSec=2min is monotonic (counted from boot). AccuracySec=1min allows systemd to coalesce with other timers within that window. The matching .service is a normal Type=oneshot unit. After enabling the timer, it runs once per boot, 2 minutes after boot — no duplicate runs from cron’s "every minute" hacks.

Trick 3: Calendar syntax that bites (and how to fix it)

Calendar expressions are easy to get wrong. OnCalendar=-- ::00 means "every second" (every minute, every second of that minute). For "every 5 minutes" you want :0/5 (minute 0, 5, 10, …).

Runnable check without installing a timer:

systemd-analyze calendar '-- 04:30:00'
systemd-analyze calendar ':0/5'
systemd-analyze calendar 'Mon -- 00:00:00'

Example output:

  Original form: -- 04:30:00
  Normalized form: -- 04:30:00
  Next elapse: Thu 2026-02-13 04:30:00 CET
  ...
  Original form: :0/5
  Normalized form: :0/5:0
  Next elapse: Wed 2026-02-12 15:35:00 CET

Always run systemd-analyze calendar '...' before wiring a timer. It shows the next run and confirms the expression.

Trick 4: Socket activation — start the service only when someone connects

Sofia had a small internal tool that ran rarely. Keeping the process always up wasted memory. Socket activation starts the service on first connection and can stop it when idle.

Socket — internal-api.socket:

[Unit]
Description=Internal API socket
[Socket]
ListenStream=9999
Accept=yes
[Install]
WantedBy=sockets.target

Service — internal-api@.service (template; %i is the instance):

[Unit]
Description=Internal API per-connection
[Service]
ExecStart=/home/sofia/tools/internal-api
StandardInput=socket
StandardOutput=journal
StandardError=journal

With Accept=yes, systemd accepts the connection and spawns one service instance per connection, passing the socket as stdin. Enable the socket (not the service):

systemctl --user enable --now internal-api.socket

Service is not running yet; no process.

ss -tlnp | grep 9999

After first connection (e.g. curl localhost:9999), the service starts.

The service appears in the journal only when it’s actually used. Good for low-traffic or on-demand helpers.

Trick 5: Socket activation with a single long-lived service

If you want one process to serve all connections (e.g. a daemon that listens on a port), use Accept=no and pass the socket via FileDescriptorName:

Socket — my-daemon.socket:

[Socket]
ListenStream=8888
Accept=no

Service — my-daemon.service:

[Service]
ExecStart=/usr/bin/my-daemon
Socket=my-daemon.socket

systemd creates the listening socket and passes it to the daemon (e.g. via sd_listen_fds()). The daemon starts only when the first connection arrives (if you use Accept=no and the daemon supports socket activation). One process, one socket.

Trick 6: journald — filter by unit, priority, and time

Everything from your units goes to the journal. The win is filtering without grep.

Only your service

journalctl --user -u cleanup-cache.service
Last 2 hours, errors and above

journalctl --user -p err -S "2 hours ago"
Today, one unit, follow

journalctl --user -u cursor-proxy.service --since today -f
Boot to boot: show only this boot

journalctl -b

Previous boot

journalctl -b -1

Example (truncated) output for a service:

Feb 12 04:30:01 host cleanup-cache.sh[12345]: Starting cleanup...
Feb 12 04:30:03 host cleanup-cache.sh[12345]: Removed 1.2G in /tmp/cache

Combine filters: -u, -p, -S, -U, -b, -f. No need to ship logs to a separate file for these queries.

Trick 7: Export and search the journal

For scripts or external tools, export as JSON or short format:

journalctl --user -u cleanup-cache.service -o json
journalctl --user -u cleanup-cache.service -o short-iso

Search by MESSAGE content (e.g. "error" or "timeout"):

journalctl --user -u cursor-proxy.service MESSAGE="timeout"

You can pipe journalctl ... -o json into jq for structured parsing in automation.

Trick 8: User vs system units — and linger

User units (systemctl --user) run in your session. If you log out, they stop unless linger is enabled:

loginctl enable-linger "$USER"

Then user units run under the user’s systemd instance and survive logout. No root needed. Paths:

  • User: ~/.config/systemd/user/
  • System: /etc/systemd/system/

    • Reload after editing: systemctl --user daemon-reload or sudo systemctl daemon-reload.

    Trick 9: Restart limits so a bad unit doesn’t spin forever

    Restart=always is useful until the process crashes in a loop. Cap restarts:

    [Service]
Restart=on-failure
RestartSec=10
StartLimitIntervalSec=300
StartLimitBurst=5

    After 5 restarts within 300 seconds, systemd stops trying and marks the unit as failed. You fix the bug and run systemctl --user reset-failed (or sudo systemctl reset-failed for system units) before starting again.

    Trick 10: systemd-analyze and why your unit didn’t start

    When a unit fails to start:

    systemctl --user status cleanup-cache.service
journalctl --user -u cleanup-cache.service -n 30 --no-pager

    Check syntax of unit files:

    systemd-analyze verify ~/.config/systemd/user/cleanup-cache.service

    And dependency / startup time:

    systemd-analyze critical-chain cleanup-cache.service

    That shows what delayed the unit. Often the cause is a wrong path in ExecStart or WorkingDirectory — the unit "starts" then exits with code 1 and shows up in status as failed.

    What went wrong

    We used OnCalendar=:0/1 intending "every minute." That’s correct. Earlier we had used ::0 thinking "every minute at second 0" and got runs every second (every minute:second). systemd-analyze calendar would have caught it. Another time, a timer was enabled but the service had ExecStart=/home/raj/scripts/old-path.sh; the script had moved. The timer "fired" but the service exited immediately with "No such file". journalctl -u cleanup-cache.service showed the exec error in one line. So: validate calendar expressions and verify ExecStart/WorkingDirectory paths; the journal is the first place to look for "why didn’t it run."

    Takeaway: what to do today

  • Pick one cron job — Replace it with a .service + .timer pair under ~/.config/systemd/user/. Use systemd-analyze calendar '...' for the OnCalendar value, then enable --now the timer.
  • Turn on linger — Run loginctl enable-linger "$USER" so your user units survive logout.
  • Add restart limits — For any unit with Restart=always or Restart=on-failure, add StartLimitIntervalSec and StartLimitBurst so a broken service doesn’t burn CPU.
  • Use journal filters — Next time you debug a service, use journalctl --user -u UNIT -p err -S "1 hour ago" instead of hunting in log files.
  • Try socket activation — For one low-traffic or internal tool, add a .socket unit and Accept=yes (or Accept=no with a socket-aware daemon); start only the socket and confirm the service appears only after the first connection.

    • Once these are in place, you get one place for schedules (timers), one place for logs (journal), and the option to start services only when needed (sockets). No need to remember which cron tab or log file to open.
