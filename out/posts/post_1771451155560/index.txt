8:T6356,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">10 systemd tricks every developer should know</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s backup script ran via cron at 02:00. After a kernel update, the server rebooted at 01:58. Cron didn’t run the 02:00 job — the box was down. The next night it ran at 02:00 and again when someone manually triggered a restart at 14:00. No audit trail, no "last run" state in the journal, and no way to say "run this 5 minutes after boot, but only once." That mess pushed him to learn systemd timers, socket activation, and journald filters. What follows are 10 tricks that actually ship: timers instead of cron, on-demand services via sockets, and making the journal do the work when you debug.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why systemd timers beat cron for many jobs</h2></p><p class="text-slate-300 leading-relaxed mb-4">Cron is fine for "run this at 3 AM." It’s weak for: run after boot with a delay, run only if the previous run finished, or see unified logs next to your service. systemd timers give you calendar and monotonic schedules, same logging as the rest of the stack, and no duplicate runs from reboots.</p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>cron</strong> | Simple, universal, no daemon config | No "after boot", no dependency ordering, logs scattered | One-off daily/weekly scripts, legacy boxes |
| <strong>systemd timers</strong> | Calendar + monotonic, journal integration, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnActiveSec</code> after boot | One unit pair per job (.service + .timer) | Scheduled jobs on systemd hosts, especially after-boot tasks |
| <strong>External scheduler (e.g. CI)</strong> | Centralized, cross-host | Extra dependency, network | Multi-host or when you already have a scheduler |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 1: Replace a cron job with a timer</h2></p><p class="text-slate-300 leading-relaxed mb-4">Two files: a <strong>service</strong> (what runs) and a <strong>timer</strong> (when it runs). The service is a normal unit; the timer activates it on a schedule.</p><p class="text-slate-300 leading-relaxed mb-4">Example: Aiko runs a cleanup script every day at 04:30 and wants it in the journal.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Service</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/cleanup-cache.service</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Daily cache cleanup</p><p class="text-slate-300 leading-relaxed mb-4">[Service]
Type=oneshot
ExecStart=/home/aiko/scripts/cleanup-cache.sh
StandardOutput=journal
StandardError=journal
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Timer</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/cleanup-cache.timer</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Run cleanup daily at 04:30</p><p class="text-slate-300 leading-relaxed mb-4">[Timer]
OnCalendar=<em>-</em>-<em> 04:30:00
Persistent=yes</p><p class="text-slate-300 leading-relaxed mb-4">[Install]
WantedBy=timers.target
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Persistent=yes</code> means: if the machine was off at 04:30, run once when it’s next up. Enable and start the timer (not the service):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemctl --user daemon-reload
systemctl --user enable --now cleanup-cache.timer
systemctl --user list-timers --all
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>NEXT                        LEFT        LAST                        PASSED  UNIT
Thu 2026-02-13 04:30:00 CET 23h left    Wed 2026-02-12 04:30:01 CET 2h ago   cleanup-cache.timer
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You never start <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cleanup-cache.service</code> by hand for the schedule; the timer does. To run the job once manually: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl --user start cleanup-cache.service</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 2: Run once after boot with a delay</h2></p><p class="text-slate-300 leading-relaxed mb-4">Omar needed a "wait for the network and DB, then run the migration" job. Cron has no clean "once after boot." A timer with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnBootSec</code> does.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Timer</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">migrate-after-boot.timer</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Run migration 2 minutes after boot</p><p class="text-slate-300 leading-relaxed mb-4">[Timer]
OnBootSec=2min
AccuracySec=1min</p><p class="text-slate-300 leading-relaxed mb-4">[Install]
WantedBy=timers.target
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnBootSec=2min</code> is monotonic (counted from boot). <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">AccuracySec=1min</code> allows systemd to coalesce with other timers within that window. The matching <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.service</code> is a normal <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Type=oneshot</code> unit. After enabling the timer, it runs once per boot, 2 minutes after boot — no duplicate runs from cron’s "every minute" hacks.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 3: Calendar syntax that bites (and how to fix it)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Calendar expressions are easy to get wrong. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnCalendar=</em>-<em>-</em> <em>:</em>:00</code> means "every second" (every minute, every second of that minute). For "every 5 minutes" you want <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm"><em>:0/5</code> (minute 0, 5, 10, …).</p><p class="text-slate-300 leading-relaxed mb-4">Runnable check without installing a timer:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemd-analyze calendar '</em>-<em>-</em> 04:30:00'
systemd-analyze calendar '<em>:0/5'
systemd-analyze calendar 'Mon </em>-<em>-</em> 00:00:00'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>  Original form: <em>-</em>-<em> 04:30:00
  Normalized form: </em>-<em>-</em> 04:30:00
  Next elapse: Thu 2026-02-13 04:30:00 CET
  ...</p><p class="text-slate-300 leading-relaxed mb-4">  Original form: <em>:0/5
  Normalized form: </em>:0/5:0
  Next elapse: Wed 2026-02-12 15:35:00 CET
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Always run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemd-analyze calendar '...'</code> before wiring a timer. It shows the next run and confirms the expression.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 4: Socket activation — start the service only when someone connects</h2></p><p class="text-slate-300 leading-relaxed mb-4">Sofia had a small internal tool that ran rarely. Keeping the process always up wasted memory. Socket activation starts the service on first connection and can stop it when idle.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Socket</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">internal-api.socket</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Internal API socket</p><p class="text-slate-300 leading-relaxed mb-4">[Socket]
ListenStream=9999
Accept=yes</p><p class="text-slate-300 leading-relaxed mb-4">[Install]
WantedBy=sockets.target
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Service</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">internal-api@.service</code> (template; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">%i</code> is the instance):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Internal API per-connection</p><p class="text-slate-300 leading-relaxed mb-4">[Service]
ExecStart=/home/sofia/tools/internal-api
StandardInput=socket
StandardOutput=journal
StandardError=journal
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">With <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Accept=yes</code>, systemd accepts the connection and spawns one service instance per connection, passing the socket as stdin. Enable the socket (not the service):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemctl --user enable --now internal-api.socket
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Service is not running yet; no process.</h1>
ss -tlnp | grep 9999
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">After first connection (e.g. curl localhost:9999), the service starts.</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The service appears in the journal only when it’s actually used. Good for low-traffic or on-demand helpers.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 5: Socket activation with a single long-lived service</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you want one process to serve all connections (e.g. a daemon that listens on a port), use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Accept=no</code> and pass the socket via <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FileDescriptorName</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Socket</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">my-daemon.socket</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Socket]
ListenStream=8888
Accept=no
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Service</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">my-daemon.service</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Service]
ExecStart=/usr/bin/my-daemon
Socket=my-daemon.socket
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">systemd creates the listening socket and passes it to the daemon (e.g. via sd_listen_fds()). The daemon starts only when the first connection arrives (if you use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Accept=no</code> and the daemon supports socket activation). One process, one socket.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 6: journald — filter by unit, priority, and time</h2></p><p class="text-slate-300 leading-relaxed mb-4">Everything from your units goes to the journal. The win is filtering without grep.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Only your service</h1>
journalctl --user -u cleanup-cache.service</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Last 2 hours, errors and above</h1>
journalctl --user -p err -S "2 hours ago"</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Today, one unit, follow</h1>
journalctl --user -u cursor-proxy.service --since today -f</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Boot to boot: show only this boot</h1>
journalctl -b
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Previous boot</h1>
journalctl -b -1
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example (truncated) output for a service:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Feb 12 04:30:01 host cleanup-cache.sh[12345]: Starting cleanup...
Feb 12 04:30:03 host cleanup-cache.sh[12345]: Removed 1.2G in /tmp/cache
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Combine filters: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-u</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-p</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-S</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-U</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-b</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-f</code>. No need to ship logs to a separate file for these queries.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 7: Export and search the journal</h2></p><p class="text-slate-300 leading-relaxed mb-4">For scripts or external tools, export as JSON or short format:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>journalctl --user -u cleanup-cache.service -o json
journalctl --user -u cleanup-cache.service -o short-iso
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Search by MESSAGE content (e.g. "error" or "timeout"):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>journalctl --user -u cursor-proxy.service MESSAGE="<em>timeout</em>"
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You can pipe <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">journalctl ... -o json</code> into <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">jq</code> for structured parsing in automation.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 8: User vs system units — and linger</h2></p><p class="text-slate-300 leading-relaxed mb-4">User units (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl --user</code>) run in your session. If you log out, they stop unless <strong>linger</strong> is enabled:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>loginctl enable-linger "$USER"
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Then user units run under the user’s systemd instance and survive logout. No root needed. Paths:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">User: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/</code></li>
<li class="ml-4 list-disc text-slate-300">System: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/etc/systemd/system/</code></li></p><p class="text-slate-300 leading-relaxed mb-4">Reload after editing: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl --user daemon-reload</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo systemctl daemon-reload</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 9: Restart limits so a bad unit doesn’t spin forever</h2></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=always</code> is useful until the process crashes in a loop. Cap restarts:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Service]
Restart=on-failure
RestartSec=10
StartLimitIntervalSec=300
StartLimitBurst=5
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">After 5 restarts within 300 seconds, systemd stops trying and marks the unit as failed. You fix the bug and run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl --user reset-failed</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo systemctl reset-failed</code> for system units) before starting again.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Trick 10: systemd-analyze and why your unit didn’t start</h2></p><p class="text-slate-300 leading-relaxed mb-4">When a unit fails to start:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemctl --user status cleanup-cache.service
journalctl --user -u cleanup-cache.service -n 30 --no-pager
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Check syntax of unit files:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemd-analyze verify ~/.config/systemd/user/cleanup-cache.service
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">And dependency / startup time:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>systemd-analyze critical-chain cleanup-cache.service
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">That shows what delayed the unit. Often the cause is a wrong path in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ExecStart</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WorkingDirectory</code> — the unit "starts" then exits with code 1 and shows up in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code> as failed.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4">We used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnCalendar=<em>:0/1</code> intending "every minute." That’s correct. Earlier we had used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm"></em>:<em>:0</code> thinking "every minute at second 0" and got runs every second (every minute:second). systemd-analyze calendar would have caught it. Another time, a timer was enabled but the service had <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ExecStart=/home/raj/scripts/old-path.sh</code>; the script had moved. The timer "fired" but the service exited immediately with "No such file". journalctl -u cleanup-cache.service showed the exec error in one line. So: validate calendar expressions and verify ExecStart/WorkingDirectory paths; the journal is the first place to look for "why didn’t it run."</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway: what to do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Pick one cron job</strong> — Replace it with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.service</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.timer</code> pair under <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.config/systemd/user/</code>. Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemd-analyze calendar '...'</code> for the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OnCalendar</code> value, then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">enable --now</code> the timer.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Turn on linger</strong> — Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">loginctl enable-linger "$USER"</code> so your user units survive logout.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add restart limits</strong> — For any unit with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=always</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=on-failure</code>, add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">StartLimitIntervalSec</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">StartLimitBurst</code> so a broken service doesn’t burn CPU.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use journal filters</strong> — Next time you debug a service, use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">journalctl --user -u UNIT -p err -S "1 hour ago"</code> instead of hunting in log files.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Try socket activation</strong> — For one low-traffic or internal tool, add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.socket</code> unit and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Accept=yes</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Accept=no</code> with a socket-aware daemon); start only the socket and confirm the service appears only after the first connection.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once these are in place, you get one place for schedules (timers), one place for logs (journal), and the option to start services only when needed (sockets). No need to remember which cron tab or log file to open.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
