8:T2042,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Backpressure in Node.js and Bun Streams</h1></p><p class="text-slate-300 leading-relaxed mb-4">When you pipe high-throughput data through streams—file I/O, HTTP bodies, or event logs—fast producers can overwhelm slow consumers. <strong>Backpressure</strong> is the mechanism that slows the producer so the consumer is not flooded and memory stays bounded.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why It Matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Without backpressure, a readable stream may push chunks faster than the writable stream can process them. The writable’s buffer grows until you hit high memory usage or crashes. Backpressure propagates a “pause” signal from the consumer back to the producer so the producer stops (or slows) until the consumer is ready again.</p><p class="text-slate-300 leading-relaxed mb-4">In Node.js and Bun, streams implement the same conceptual model: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Readable</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Writable</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Transform</code> use an internal buffer and expose <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">highWaterMark</code>. When the consumer’s buffer exceeds <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">highWaterMark</code>, the stream can signal that it is not ready for more data, and the producer should back off.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">How Node.js and Bun Handle It</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipe()</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipeline()</code></strong>: When you <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipe()</code> a Readable to a Writable, backpressure is automatic. The writable stream’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">write()</code> returns <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">false</code> when its buffer is full; the readable stream then pauses until the writable emits <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">'drain'</code>. So using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">source.pipe(dest)</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipeline(source, dest)</code> is the easiest way to get correct backpressure.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Manual <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read()</code> / <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">write()</code></strong>: If you call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read()</code> in a loop or push to a writable without checking the return value of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">write()</code>, you can bypass backpressure. Always respect <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">write() === false</code> and wait for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">'drain'</code> before writing again, or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipeline()</code> so the runtime handles it.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Bun</strong>: Bun’s stream API is designed to be compatible with Node’s. The same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipe()</code> and backpressure semantics apply when you use Bun’s built-in streams. So the practices below apply to both runtimes.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical Rules</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Prefer <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipeline()</code> over multiple <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipe()</code> calls</strong>  </li>
   <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">stream.pipeline(A, B, C, callback)</code> handles errors and cleanup and ensures backpressure flows through the whole chain. Use it for multi-stage pipelines.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Avoid swallowing backpressure in custom streams</strong>  </li>
   If you implement a custom <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Transform</code>, call the callback only when you are done processing the chunk (and when you are ready for more). Do not push synchronously in a tight loop without giving the consumer a chance to drain.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Tune <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">highWaterMark</code> only when you have a reason</strong>  </li>
   The default is often enough. Increasing it can improve throughput when both ends are fast, but it also raises memory usage. Decrease it if you want to limit memory and are okay with more backpressure.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Use async iteration with care</strong>  </li>
   <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">for await (const chunk of readable)</code> consumes the stream at the pace of your loop. If your loop is slow (e.g. doing I/O or heavy work per chunk), backpressure naturally applies because you only pull the next chunk when you advance the loop. If your loop is very fast and the next stage is slow, prefer piping to a Writable or Transform that applies backpressure.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Example: Pipe with Automatic Backpressure</h2></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { createReadStream, createWriteStream } from "fs";
import { pipeline } from "stream/promises";</p><p class="text-slate-300 leading-relaxed mb-4">await pipeline(
  createReadStream("large.log"),
  transformStream(), // your Transform
  createWriteStream("out.log")
);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Here, the file read stream will be paused whenever the transform or the file write stream is slow, and resumed when they drain. No extra code is needed.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">Backpressure in Node.js and Bun is about keeping producer and consumer in balance so buffers do not grow without bound. Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipe()</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pipeline()</code>, respect <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">write()</code> return values when writing by hand, and implement custom streams so they do not ignore backpressure. That keeps your stream-based code efficient and safe under load.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
