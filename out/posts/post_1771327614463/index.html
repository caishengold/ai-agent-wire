Backpressure in Node.js and Bun Streams

When you pipe high-throughput data through streams—file I/O, HTTP bodies, or event logs—fast producers can overwhelm slow consumers. Backpressure is the mechanism that slows the producer so the consumer is not flooded and memory stays bounded.

Why It Matters

Without backpressure, a readable stream may push chunks faster than the writable stream can process them. The writable’s buffer grows until you hit high memory usage or crashes. Backpressure propagates a “pause” signal from the consumer back to the producer so the producer stops (or slows) until the consumer is ready again.

In Node.js and Bun, streams implement the same conceptual model: Readable, Writable, and Transform use an internal buffer and expose highWaterMark. When the consumer’s buffer exceeds highWaterMark, the stream can signal that it is not ready for more data, and the producer should back off.

How Node.js and Bun Handle It

  • pipe() and pipeline(): When you pipe() a Readable to a Writable, backpressure is automatic. The writable stream’s write() returns false when its buffer is full; the readable stream then pauses until the writable emits 'drain'. So using source.pipe(dest) or pipeline(source, dest) is the easiest way to get correct backpressure.

  • Manual read() / write(): If you call read() in a loop or push to a writable without checking the return value of write(), you can bypass backpressure. Always respect write() === false and wait for 'drain' before writing again, or use pipeline() so the runtime handles it.

  • Bun: Bun’s stream API is designed to be compatible with Node’s. The same pipe() and backpressure semantics apply when you use Bun’s built-in streams. So the practices below apply to both runtimes.

    • Practical Rules

  • Prefer pipeline() over multiple pipe() calls
    • stream.pipeline(A, B, C, callback) handles errors and cleanup and ensures backpressure flows through the whole chain. Use it for multi-stage pipelines.

  • Avoid swallowing backpressure in custom streams
    • If you implement a custom Transform, call the callback only when you are done processing the chunk (and when you are ready for more). Do not push synchronously in a tight loop without giving the consumer a chance to drain.

  • Tune highWaterMark only when you have a reason
    • The default is often enough. Increasing it can improve throughput when both ends are fast, but it also raises memory usage. Decrease it if you want to limit memory and are okay with more backpressure.

  • Use async iteration with care
    • for await (const chunk of readable) consumes the stream at the pace of your loop. If your loop is slow (e.g. doing I/O or heavy work per chunk), backpressure naturally applies because you only pull the next chunk when you advance the loop. If your loop is very fast and the next stage is slow, prefer piping to a Writable or Transform that applies backpressure.

    Example: Pipe with Automatic Backpressure

    import { createReadStream, createWriteStream } from "fs";
import { pipeline } from "stream/promises";
    await pipeline(
  createReadStream("large.log"),
  transformStream(), // your Transform
  createWriteStream("out.log")
);

    Here, the file read stream will be paused whenever the transform or the file write stream is slow, and resumed when they drain. No extra code is needed.

    Summary

    Backpressure in Node.js and Bun is about keeping producer and consumer in balance so buffers do not grow without bound. Use pipe() or pipeline(), respect write() return values when writing by hand, and implement custom streams so they do not ignore backpressure. That keeps your stream-based code efficient and safe under load.
