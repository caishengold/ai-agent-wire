8:T4209,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Best practices for creating reusable DevOps CI/CD templates</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team maintained 12 microservices. Each repo had its own pipeline: same lint, test, and build steps, copied and tweaked. When they upgraded their Node.js version and adjusted the test command, they had to change 12 files. They missed two. Those two services kept running old tests and broke in staging. The fix was a single reusable template; updating it once updated every pipeline. This post is about doing that without painting yourself into a corner — <strong>reusable CI/CD templates</strong> that stay maintainable and predictable.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> DevOps and platform engineers (and devs who own pipelines) who want one place to define build, test, and deploy logic so many repos can reuse it. We focus on patterns that work in GitHub Actions and GitLab CI, with runnable examples and a comparison of approaches.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why reuse beats copy-paste</h2></p><p class="text-slate-300 leading-relaxed mb-4">Copy-pasted pipelines drift. One repo gets a new security scan; another doesn’t. Fixes and improvements require editing N files and hoping nothing was “special” in one of them. Reusable templates give you:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Single source of truth</strong> — change the template once, all consumers get the update (after they opt in or you version it).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Consistent behaviour</strong> — same Node/Bun/Go version, same lint rules, same test command across services.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Easier auditing</strong> — one place to check for secrets handling, caching, and compliance.</li></p><p class="text-slate-300 leading-relaxed mb-4">The trade-off: templates need clear inputs (e.g. node version, test script name), versioning so you don’t break everyone at once, and docs so Raj in Bangalore and Aiko in Tokyo know how to use them.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Approach comparison: when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Copy-paste per repo</strong> | No shared dependency; each repo is independent. | Drift, N-fold maintenance, inconsistent behaviour. | One-off or legacy repos you rarely touch. |
| <strong>Reusable workflow / template (single file)</strong> | One definition; consumers call it with inputs. | All consumers share the same behaviour; changing it affects everyone. | Standard pipelines (lint, test, build) where you want consistency. |
| <strong>Parameterized template + version pin</strong> | Reuse plus controlled rollout; pin to a tag or commit. | Slightly more setup (versioning, release of the template repo). | When you have many teams and need to roll out changes gradually. |
| <strong>Monorepo with shared job definitions</strong> | One repo, one pipeline; no cross-repo sync. | Only works if all code lives in one repo. | Monorepos (e.g. Nx, Turborepo). |</p><p class="text-slate-300 leading-relaxed mb-4">For most teams, <strong>reusable workflow (GitHub) or included template (GitLab)</strong> with a few inputs is the sweet spot. Add version pinning once you have more than a handful of consumers or multiple teams.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Example 1: GitHub Actions reusable workflow</h2></p><p class="text-slate-300 leading-relaxed mb-4">A reusable workflow lives in one repo and is triggered by other repos (or the same repo). You define inputs and pass them from the caller.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Template repo:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.github/workflows/build-and-test.yml</code> (e.g. in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">your-org/ci-templates</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.github/workflows/build-and-test.yml</h1>
name: Build and test (reusable)</p><p class="text-slate-300 leading-relaxed mb-4">on:
  workflow_call:
    inputs:
      node_version:
        required: true
        type: string
        default: '20'
      install_cmd:
        required: false
        type: string
        default: 'npm ci'
      test_cmd:
        required: false
        type: string
        default: 'npm test'
    secrets:
      NPM_TOKEN:
        required: false</p><p class="text-slate-300 leading-relaxed mb-4">jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4</p><p class="text-slate-300 leading-relaxed mb-4">      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node_version }}
          cache: 'npm'</p><p class="text-slate-300 leading-relaxed mb-4">      - name: Install
        run: ${{ inputs.install_cmd }}</p><p class="text-slate-300 leading-relaxed mb-4">      - name: Lint
        run: npm run lint</p><p class="text-slate-300 leading-relaxed mb-4">      - name: Test
        run: ${{ inputs.test_cmd }}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Consumer repo:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.github/workflows/ci.yml</code> (in a service repo).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.github/workflows/ci.yml</h1>
name: CI</p><p class="text-slate-300 leading-relaxed mb-4">on:
  push:
    branches: [main]
  pull_request:
    branches: [main]</p><p class="text-slate-300 leading-relaxed mb-4">jobs:
  build-and-test:
    uses: your-org/ci-templates/.github/workflows/build-and-test.yml@main
    with:
      node_version: '20'
      install_cmd: 'npm ci'
      test_cmd: 'npm test'
    secrets: inherit
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run it:</strong> Push to the consumer repo; the workflow runs and uses the template from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ci-templates</code>. To pin a version, use a tag: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@v1.0.0</code> instead of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@main</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Typical terminal output (summary):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Run your-org/ci-templates/.github/workflows/build-and-test.yml@main
  with:
    node_version: 20
    install_cmd: npm ci
    test_cmd: npm test
...
Setup Node
  node-version: 20
  cache: npm
...
Install
  npm ci
...
Lint
  npm run lint
...
Test
  npm test
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Example 2: GitLab CI template with include and variables</h2></p><p class="text-slate-300 leading-relaxed mb-4">In GitLab you can put a template in a separate project and include it. Each project overrides variables as needed.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Template project:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">your-group/ci-templates</code> — file <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">templates/build-test.gitlab-ci.yml</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">templates/build-test.gitlab-ci.yml</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Reusable: lint, install, test. Override NODE_VERSION, INSTALL_CMD, TEST_CMD.</h1></p><p class="text-slate-300 leading-relaxed mb-4">variables:
  NODE_VERSION: "20"
  INSTALL_CMD: "npm ci"
  TEST_CMD: "npm test"</p><p class="text-slate-300 leading-relaxed mb-4">.lint-and-test:
  image: node:${NODE_VERSION}-alpine
  before_script:
    - $INSTALL_CMD
  script:
    - npm run lint
    - $TEST_CMD
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Consumer project:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.gitlab-ci.yml</code> in a service repo.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.gitlab-ci.yml</h1>
include:
  - project: your-group/ci-templates
    ref: main
    file: templates/build-test.gitlab-ci.yml</p><p class="text-slate-300 leading-relaxed mb-4">variables:
  NODE_VERSION: "20"
  TEST_CMD: "npm run test:unit"</p><p class="text-slate-300 leading-relaxed mb-4">jobs:
  lint-and-test:
    extends: .lint-and-test
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run it:</strong> Push to the consumer project; GitLab loads the included file and runs the job. Pin by setting <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ref: v1.0.0</code> when you tag the template repo.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Design practices that keep templates usable</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Expose only what callers need</strong> — e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node_version</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">install_cmd</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">test_cmd</code>. Don’t pass 20 options; add them when a real use case appears.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Sensible defaults</strong> — so a consumer can call the template with no (or few) inputs and get a working run.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document inputs and any secrets</strong> — a short README in the template repo with a table of inputs, default values, and which repos use which version.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Version the template</strong> — use tags (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">v1.0.0</code>) so consumers can pin. Rolling out a change? Bump the tag and update consumers in batches.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Fail clearly</strong> — if a required input is missing or invalid, fail the job with a message that says which input and which value (e.g. “NODE_VERSION must be 18, 20, or 22”).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What went wrong:</strong> We introduced a reusable “build and test” workflow and pointed seven repos at <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@main</code>. A colleague changed the default <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">test_cmd</code> from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm test</code> to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm run test:ci</code> (which added coverage and different env). Two services didn’t have a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">test:ci</code> script. Their pipelines started failing with:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>npm ERR! Missing script: "test:ci"
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">We had to fix the template (keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm test</code> as default and make <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">test:ci</code> opt-in via input) and add the missing script to those two repos. <strong>Takeaway:</strong> avoid changing default behaviour in a shared template in a way that assumes new scripts exist in every consumer. Prefer additive changes or new optional inputs; if you change defaults, communicate and migrate callers first.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Another mistake:</strong> We didn’t pin the template ref. Every consumer used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@main</code>. A bad merge broke all seven pipelines for about an hour. We now use tags (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@v1.0.0</code>) and only move <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">v1</code> (or “current”) after testing in one repo.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable next steps</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit one pipeline</strong> — Pick your most common pattern (e.g. “Node lint + test”). List how many repos duplicate it and what differs (node version, test command, install command). That list is your initial set of template inputs.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Extract one reusable workflow or include</strong> — In GitHub, add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">workflow_call</code> workflow with 2–3 inputs and point one consumer at it. In GitLab, add one <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.gitlab-ci.yml</code> include and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">extends</code> in one project. Confirm the run matches the previous behaviour.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document inputs and pin ref</strong> — In the template repo, add a short README (inputs, defaults, example). Tag the repo (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">v1.0.0</code>) and switch the consumer to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@v1.0.0</code> (or your tag name) instead of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@main</code>.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Migrate one more repo</strong> — Move a second service to the same template. If something is missing (e.g. a special env var or script), add one optional input or variable instead of forking the template.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Decide who can change the template</strong> — Use branch protection or MR rules so template changes are reviewed and, if possible, tested against at least one consumer before merge.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once this is in place, you get a single place to add security scans, dependency bumps, or new steps — and every consumer can adopt the change by updating the ref or the inputs they pass.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
