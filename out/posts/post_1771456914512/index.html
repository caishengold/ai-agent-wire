Comparative Analysis of Authentication Strategies in TypeScript APIs

Authentication remains one of the most critical decisions when designing a TypeScript API. The strategy you choose impacts security, developer experience, performance, and long-term maintenance. This analysis compares the three most prevalent approaches: JWT tokens, session-based authentication, and API keys. By examining real-world trade-offs, you can make an informed decision for your project.

The Scenario

Raj Patel, engineering lead at a Series B health-tech company, faced a difficult choice in early 2025. His team was building a patient data API that needed to serve three distinct client types: a web application, a mobile app, and third-party integrations from partner hospitals. Each client had different requirements around security, session duration, and token management.

The web application needed seamless re-authentication when tokens expired. The mobile app required offline capabilities with secure token storage. Third-party integrations demanded simple, machine-to-machine authentication without user interaction. Raj evaluated each authentication strategy to find a solution that could handle all three use cases without compromising security or user experience.

JWT Tokens

JWT (JSON Web Token) authentication has become the default choice for modern API design. The server issues a signed token containing claims about the user, and the client includes this token in subsequent requests.

How JWT Works

The server generates a token with an expiration time and signs it using a secret key or private key. Each request includes the token in the Authorization header. The server validates the signature and expiration without querying a database, making JWT extremely fast.

Here is a complete implementation using TypeScript and the jsonwebtoken library:

import jwt from 'jsonwebtoken';
import { Request, Response, NextFunction } from 'express';
const JWT_SECRET = process.env.JWT_SECRET || 'your-secret-key';
const TOKEN_EXPIRY = '15m';
const REFRESH_TOKEN_EXPIRY = '7d';
interface TokenPayload {
  userId: string;
  role: string;
  permissions: string[];
}
function generateAccessToken(payload: TokenPayload): string {
  return jwt.sign(payload, JWT_SECRET, { expiresIn: TOKEN_EXPIRY });
}
function generateRefreshToken(payload: TokenPayload): string {
  return jwt.sign(payload, JWT_SECRET, { expiresIn: REFRESH_TOKEN_EXPIRY });
}
function authenticateToken(req: Request, res: Response, next: NextFunction): void {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];
  if (!token) {
    res.status(401).json({ error: 'Access token required' });
    return;
  }
  jwt.verify(token, JWT_SECRET, (err, decoded) => {
    if (err) {
      res.status(403).json({ error: 'Invalid or expired token' });
      return;
    }
    (req as any).user = decoded;
    next();
  });
}
function refreshAccessToken(refreshToken: string): string | null {
  try {
    const decoded = jwt.verify(refreshToken, JWT_SECRET) as TokenPayload;
    return generateAccessToken(decoded);
  } catch {
    return null;
  }
}
export { 
  generateAccessToken, 
  generateRefreshToken, 
  authenticateToken, 
  refreshAccessToken,
  TokenPayload 
};

The refresh token mechanism allows short-lived access tokens without forcing users to log in repeatedly. When the access token expires, the client presents the refresh token to obtain a new one.

When JWT Makes Sense

JWT excels in distributed systems where the authentication server is separate from resource servers. The stateless nature means any server can validate a token without database lookups. Mobile applications benefit from JWT because tokens can be stored securely in the device keychain.

However, JWT has limitations. If you need to revoke tokens immediately (for security incidents or user logout), you must implement a token blacklist or use short expiration times. The tokens grow with each added claim, increasing header size on every request.

Session-Based Authentication

Traditional session authentication stores user state on the server. A unique session identifier links the client to stored session data, typically in memory, a database, or a Redis cache.

Implementing Sessions in TypeScript

Here is a complete session implementation using Express and Redis:

import express from 'express';
import session from 'express-session';
import RedisStore from 'connect-redis';
import { createClient } from 'redis';
import crypto from 'crypto';
const app = express();
async function setupSession() {
  const redisClient = createClient({
    socket: {
      host: process.env.REDIS_HOST || 'localhost',
      port: parseInt(process.env.REDIS_PORT || '6379')
    }
  });
  await redisClient.connect();
  const redisStore = new RedisStore({
    client: redisClient,
    prefix: 'session:'
  });
  const sessionMiddleware = session({
    store: redisStore,
    secret: process.env.SESSION_SECRET || 'your-session-secret',
    resave: false,
    saveUninitialized: false,
    cookie: {
      secure: process.env.NODE_ENV === 'production',
      httpOnly: true,
      maxAge: 24  60  60  1000,
      sameSite: 'strict'
    }
  });
  app.use(sessionMiddleware);
  return sessionMiddleware;
}
interface SessionData {
  userId: string;
  role: string;
  lastActivity: number;
}
declare module 'express-session' {
  interface SessionData {
    user: SessionData;
  }
}
function requireAuth(req: express.Request, res: express.Response, next: express.NextFunction): void {
  if (!req.session.user) {
    res.status(401).json({ error: 'Authentication required' });
    return;
  }
  req.session.user.lastActivity = Date.now();
  next();
}
export { app, setupSession, requireAuth };

Sessions work exceptionally well when you need instant token revocation. Deleting the session from storage immediately invalidates the user's access. This matters for applications requiring strict access control or compliance with data protection regulations.

Session Trade-offs

The primary disadvantage is horizontal scaling complexity. In a multi-server deployment, you need a shared session store like Redis. Database queries on each request add latency compared to stateless JWT validation. Sessions also require CSRF protection, adding another layer of complexity to your implementation.

API Keys for Machine-to-Machine Communication

API keys provide simple authentication for server-to-server communication. Each key identifies the calling service and typically maps to specific permissions and rate limits.

TypeScript API Key Implementation

import { Request, Response, NextFunction } from 'express';
import crypto from 'crypto';
import { createHash } from 'crypto';
interface ApiKeyData {
  keyId: string;
  serviceName: string;
  permissions: string[];
  rateLimit: number;
  createdAt: Date;
  expiresAt?: Date;
}
const apiKeyStore = new Map();
function generateApiKey(serviceName: string, permissions: string[]): { key: string; keyId: string } {
  const keyId = crypto.randomUUID();
  const key = sk_${crypto.randomBytes(32).toString('hex')};
  
  const hashedKey = createHash('sha256').update(key).digest('hex');
  apiKeyStore.set(hashedKey, {
    keyId,
    serviceName,
    permissions,
    rateLimit: 1000,
    createdAt: new Date()
  });
  return { key, keyId };
}
function validateApiKey(req: Request, res: Response, next: NextFunction): void {
  const apiKey = req.headers['x-api-key'] as string;
  if (!apiKey) {
    res.status(401).json({ error: 'API key required' });
    return;
  }
  const hashedKey = createHash('sha256').update(apiKey).digest('hex');
  const keyData = apiKeyStore.get(hashedKey);
  if (!keyData) {
    res.status(403).json({ error: 'Invalid API key' });
    return;
  }
  if (keyData.expiresAt && keyData.expiresAt < new Date()) {
    res.status(403).json({ error: 'API key expired' });
    return;
  }
  (req as any).apiKey = keyData;
  next();
}
function revokeApiKey(keyId: string): boolean {
  for (const [hashedKey, data] of apiKeyStore.entries()) {
    if (data.keyId === keyId) {
      apiKeyStore.delete(hashedKey);
      return true;
    }
  }
  return false;
}
export { generateApiKey, validateApiKey, revokeApiKey };

API keys excel for third-party integrations. Partners can authenticate without implementing OAuth flows. You can issue keys with limited permissions and revoke them instantly if suspicious activity occurs.

Comparing Authentication Strategies

| Aspect | JWT Tokens | Session-Based | API Keys | |--------|-----------|---------------|----------| | Stateless validation | Yes | No | Yes | | Instant revocation | No (requires blacklist) | Yes | Yes | | Storage overhead | Token size | Session store | Key lookup | | Horizontal scaling | Easy | Requires shared store | Easy | | Client complexity | Medium | Low | Low | | Best for | Microservices, mobile | Web apps with user sessions | M2M, third-party |

Each strategy serves different use cases. JWT provides the best developer experience for modern applications requiring stateless authentication. Sessions offer immediate revocation for security-sensitive applications. API keys remain the simplest solution for machine-to-machine integration.

Lessons Learned

  • Raj's team ultimately implemented a hybrid approach: JWT for their web and mobile clients, API keys for partner integrations, with session-style revocation via a Redis blacklist for security incidents
  • Short access token lifetimes (15 minutes) with refresh tokens reduced the window of exposure if tokens were compromised
  • API key rotation schedules prevented long-term key compromise without disrupting services
  • Logging authentication failures helped detect attacks early, with automated alerting for unusual patterns

    • Actionable Takeaways

  • Implement token rotation for sensitive applications — Use short-lived access tokens with refresh token rotation to limit exposure if credentials are stolen
  • Choose your primary store based on scaling needs — JWT works well for stateless services, while sessions require Redis or database-backed storage
  • Add authentication logging immediately — Track failed attempts, token revocations, and unusual access patterns from day one
  • Design for multiple client types from the start — Supporting both user authentication and API keys prevents costly refactoring later
  • Test your revocation mechanisms — Verify that blacklisted tokens and deleted sessions actually prevent access before deploying to production
