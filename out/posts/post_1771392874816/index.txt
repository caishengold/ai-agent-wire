8:T46d8,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Feature flags done right: implementation patterns, gradual rollout, kill switches, and open-source tools</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj shipped a new recommendation engine to production on 2026-01-15. Within 20 minutes, error rates spiked and support was flooded. The fix was a one-line code change, but the deploy pipeline took 12 minutes and required a full staging run. By the time the rollback landed, they had lost roughly 2,400 failed requests and one angry enterprise customer. The missing piece was a <strong>kill switch</strong>: a way to turn off the feature without redeploying. Feature flags are that mechanism — and when done right, they give you gradual rollout, instant off-ramps, and fewer 2 AM pages.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Developers and platform teams who want to ship features safely, run experiments, or need to disable functionality without a full release.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The problem in one sentence</h2></p><p class="text-slate-300 leading-relaxed mb-4">You need to enable or disable behaviour at runtime (by user, percentage, or environment) without redeploying. That implies a source of truth for "is this on?", evaluation at runtime, and a path to change the answer quickly when things go wrong.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Implementation patterns that actually work</h2></p><p class="text-slate-300 leading-relaxed mb-4">Three patterns show up repeatedly: environment variables for the simplest cases, a small in-process evaluator backed by config or a remote service, and a full SDK from a feature-flag provider. Each has trade-offs.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 1: Environment variable flags</h3></p><p class="text-slate-300 leading-relaxed mb-4">Best when you have a handful of flags and no need for per-user or percentage rollout. Your app reads <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env.FEATURE_NEW_CHECKOUT === "true"</code> and branches. No SDK, no network call.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Runnable example: Node with env-based flags.</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>mkdir -p /tmp/feature-flag-demo && cd /tmp/feature-flag-demo

No per-request or percentage logic — but zero dependencies and trivial to reason about.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 2: Config file + in-process evaluator</h3></p><p class="text-slate-300 leading-relaxed mb-4">When you want percentage rollout or simple targeting (e.g. by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">env</code> or tenant), a small module that reads a config (file or remote) and evaluates rules keeps the app logic clean. The app never holds business logic for </em>when<em> a feature is on — only the evaluator does.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gradual rollout and kill switches</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gradual rollout</strong> means exposing a feature to a subset of traffic (by percentage, user segment, or region) and increasing exposure only when metrics look good. The percentage rule in the example above does that: same user always gets the same bucket (deterministic hash), so you can ramp from 5% to 50% without users flipping on and off.</p><p class="text-slate-300 leading-relaxed mb-4">A <strong>kill switch</strong> is a rule that overrides everything and turns the feature off. In the env pattern, you set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FEATURE_NEW_CHECKOUT=false</code> and restart (or update the process env). In the config pattern, you change the rule to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ type: "off", value: false }</code> and push config. The critical part: <strong>the decision must be read at request time</strong> (or at least on a short TTL cache). If your app only reads flags at startup, changing the env or config does nothing until you redeploy or restart.</p><p class="text-slate-300 leading-relaxed mb-4">So "done right" means:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Flags are evaluated per request (or with a short-lived cache, e.g. 60 seconds).</li>
<li class="ml-4 list-disc text-slate-300">There is a single place (env, file, or feature-flag service) that you can change without a code deploy.</li>
<li class="ml-4 list-disc text-slate-300">You have one or more "kill" rules (e.g. global off, or off when error rate &gt; threshold) so that turning off is a config change, not a release.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">How the main approaches compare</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Env vars</strong> | No deps, easy to reason about, works everywhere. | No per-user or percentage; change requires env update/restart. | Few flags, on/off per environment only. |
| <strong>Config file + evaluator</strong> | Percentage and env/tenant rules, no vendor lock-in, runnable in-process. | You own config storage, refresh, and (if needed) UI. | Small to mid teams, need rollout + kill switch without a SaaS. |
| <strong>Unleash (open source)</strong> | Host yourself, SDKs, UI, targeting and percentage, active community. | You run and maintain the server and DB. | Teams that want a dashboard and multiple apps. |
| <strong>Flagsmith (open source)</strong> | Cloud or self-hosted, segments and experiments. | Extra moving part; self-host has operational cost. | When you want experiments and a polished UI. |
| <strong>Commercial (LaunchDarkly, etc.)</strong> | Mature UI, experiments, integrations, SLA. | Cost, vendor dependency, data leaves your infra. | Enterprise needs, compliance, or "we don’t want to run it". |</p><p class="text-slate-300 leading-relaxed mb-4">For many teams, <strong>config file + evaluator</strong> or <strong>Unleash self-hosted</strong> hits the sweet spot: real gradual rollout and a kill switch, without a big bill or a closed-source dependency.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Open-source tools worth a look</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong><a href="https://www.getunleash.io/" class="text-cyan-400 hover:underline">Unleash</a></strong> (Apache 2.0) is the one we’ve seen most often in production. You run the Unleash server (and a DB — Postgres or SQLite), add feature toggles in the UI or API, and use the Node (or other) SDK in your app. The SDK fetches toggles and evaluates strategies (e.g. "gradualRollout" by percentage). Flipping a toggle off in the UI takes effect on the next SDK poll (or when you use the real-time option). That’s your kill switch.</p><p class="text-slate-300 leading-relaxed mb-4"><strong><a href="https://www.flagsmith.com/" class="text-cyan-400 hover:underline">Flagsmith</a></strong> is open source (MIT) and can be self-hosted or used as a hosted service. You define flags and segments (e.g. "beta users"), and the SDK evaluates them per request. Good if you care about segment-based targeting and a ready-made UI.</p><p class="text-slate-300 leading-relaxed mb-4"><strong><a href="https://openfeature.dev/" class="text-cyan-400 hover:underline">OpenFeature</a></strong> is a standard (CNCF) for feature-flag </em>evaluation<em>: your code calls a provider-agnostic API, and you plug in a provider (Unleash, LaunchDarkly, or your own). Use it when you want to avoid locking the codebase to one vendor while still using a provider for rules and UI.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">We once treated feature flags as "env vars that we set at deploy time." That meant every change required a new deploy. When a partner API started returning 5xx for 30% of requests, we had to roll back the entire release and wait for CI. Downtime was about 18 minutes. The fix was to move that integration behind a flag whose value was read from a small config service updated every 60 seconds. We could turn the integration off by changing one key in the config — no deploy. After that we made it a rule: <strong>any code path that talks to an external system we don’t control must be behind a flag we can turn off without a release.</strong></p><p class="text-slate-300 leading-relaxed mb-4">Another mistake: we had a "beta_dashboard" flag evaluated only at login. The config was updated to turn it off, but existing sessions kept seeing the dashboard until they logged out. So we learned to <strong>evaluate flags at the boundary of the feature</strong> (e.g. per request or per page load), not only at session creation. That way a kill switch takes effect on the next request.</p><p class="text-slate-300 leading-relaxed mb-4">We also saw a 40% latency spike on one endpoint when we added a flag SDK that did a synchronous HTTP call on every request. We switched to a background poll (or real-time subscription) and in-memory evaluation; latency went back to baseline. So: <strong>avoid blocking the request path on network calls</strong>; prefer cached or pushed flag state and evaluate in-process.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add one kill switch this week.</strong> Pick a single feature or integration (e.g. "new payment provider" or "recommendation engine") and put it behind a flag. Ensure the flag is read at request time and can be turned off via env or a config change without redeploy. Verify you can flip it and see the old behaviour within a minute.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Decide where the source of truth lives.</strong> If you have fewer than ~5 flags and only need on/off per environment, env vars are enough. If you need percentage or user-based rollout, implement a small evaluator (like the TypeScript example) or adopt Unleash/Flagsmith and keep the app code provider-agnostic where possible.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Never block the request on a remote flag call.</strong> Use in-process evaluation with config loaded in the background (file, polling, or push). If you use a vendor SDK, enable local caching and ensure time-to-live is short enough for kill switches (e.g. 60 seconds).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document how to turn each high-risk feature off.</strong> In runbooks or README, list flags that act as kill switches and the exact env key or UI toggle. When something breaks at 2 AM, the person on call should not have to grep the codebase to find the flag name.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Review flags quarterly.</strong> Remove flags for features that have been fully rolled out for months. Stale flags accumulate and make "what’s actually on?" harder to answer; a small cleanup keeps the system understandable.</li></p><p class="text-slate-300 leading-relaxed mb-4">Feature flags are not just "if (feature_on)". They are the lever that lets you ship faster and roll back in seconds. Start with one kill switch and one gradual rollout; then grow from there.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
