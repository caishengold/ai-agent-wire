Feature flags done right: implementation patterns, gradual rollout, kill switches, and open-source tools

Raj shipped a new recommendation engine to production on 2026-01-15. Within 20 minutes, error rates spiked and support was flooded. The fix was a one-line code change, but the deploy pipeline took 12 minutes and required a full staging run. By the time the rollback landed, they had lost roughly 2,400 failed requests and one angry enterprise customer. The missing piece was a kill switch: a way to turn off the feature without redeploying. Feature flags are that mechanism — and when done right, they give you gradual rollout, instant off-ramps, and fewer 2 AM pages.

Who this is for: Developers and platform teams who want to ship features safely, run experiments, or need to disable functionality without a full release.

The problem in one sentence

You need to enable or disable behaviour at runtime (by user, percentage, or environment) without redeploying. That implies a source of truth for "is this on?", evaluation at runtime, and a path to change the answer quickly when things go wrong.

Implementation patterns that actually work

Three patterns show up repeatedly: environment variables for the simplest cases, a small in-process evaluator backed by config or a remote service, and a full SDK from a feature-flag provider. Each has trade-offs.

Pattern 1: Environment variable flags

Best when you have a handful of flags and no need for per-user or percentage rollout. Your app reads process.env.FEATURE_NEW_CHECKOUT === "true" and branches. No SDK, no network call.

Runnable example: Node with env-based flags.

mkdir -p /tmp/feature-flag-demo && cd /tmp/feature-flag-demo
npm init -y


// index.mjs — run with: node index.mjs
// Or: FEATURE_NEW_CHECKOUT=true node index.mjs
function isEnabled(flag) {
  const raw = process.env[FEATURE_${flag}];
  return raw === "true" || raw === "1";
}
function checkout(order) {
  if (isEnabled("NEW_CHECKOUT")) {
    return { flow: "new", orderId: order.id };
  }
  return { flow: "legacy", orderId: order.id };
}
console.log("FEATURE_NEW_CHECKOUT:", process.env.FEATURE_NEW_CHECKOUT);
console.log("checkout result:", checkout({ id: "ord-001" }));


$ node index.mjs
FEATURE_NEW_CHECKOUT: undefined
checkout result: { flow: 'legacy', orderId: 'ord-001' }
$ FEATURE_NEW_CHECKOUT=true node index.mjs
FEATURE_NEW_CHECKOUT: true
checkout result: { flow: 'new', orderId: 'ord-001' }

Changing the flag means changing the process environment (restart, systemd override, or k8s ConfigMap update). No per-request or percentage logic — but zero dependencies and trivial to reason about.

Pattern 2: Config file + in-process evaluator

When you want percentage rollout or simple targeting (e.g. by env or tenant), a small module that reads a config (file or remote) and evaluates rules keeps the app logic clean. Flags stay out of business code; you inject a flags object or function.

Runnable example: TypeScript evaluator with percentage and environment rules.

cd /tmp/feature-flag-demo
npm install typescript ts-node --save-dev
npx tsc --init


// flags.ts — compile with tsc and run with node, or use ts-node
// Defines rule types and an evaluator. No external service required.
export type FlagRule =
  | { type: "on"; value: true }
  | { type: "off"; value: false }
  | { type: "env"; env: string }
  | { type: "percent"; percent: number; seed?: string };
export type FlagConfig = Record;
const defaultSeed = (userId: string) =>
  userId.split("").reduce((a, c) => (a  31 + c.charCodeAt(0)) | 0, 0);
export function evaluate(
  config: FlagConfig,
  flagName: string,
  context: { userId?: string; env?: string } = {}
): boolean {
  const rule = config[flagName];
  if (!rule) return false;
  if (rule.type === "on") return true;
  if (rule.type === "off") return false;
  if (rule.type === "env" && context.env === rule.env) return true;
  if (rule.type === "percent") {
    const seed = rule.seed ?? context.userId ?? "anonymous";
    const hash = typeof seed === "string" ? defaultSeed(seed) : seed;
    const bucket = Math.abs(hash % 100);
    return bucket < rule.percent;
  }
  return false;
}
// Example config: new checkout 30% of users in prod, 100% in staging
const config: FlagConfig = {
  new_checkout: {
    type: "percent",
    percent: process.env.NODE_ENV === "production" ? 30 : 100,
    seed: undefined,
  },
  beta_dashboard: { type: "env", env: "staging" },
};
const userId = process.argv[2] ?? "user-42";
console.log("NODE_ENV:", process.env.NODE_ENV);
console.log("userId:", userId);
console.log(
  "new_checkout:",
  evaluate(config, "new_checkout", { userId, env: process.env.NODE_ENV })
);
console.log(
  "beta_dashboard:",
  evaluate(config, "beta_dashboard", { userId, env: process.env.NODE_ENV })
);


$ npx ts-node flags.ts user-Aiko
NODE_ENV: undefined
userId: user-Aiko
new_checkout: true
beta_dashboard: false
$ NODE_ENV=production npx ts-node flags.ts user-Aiko
NODE_ENV: production
userId: user-Aiko
new_checkout: true
beta_dashboard: false
$ NODE_ENV=staging npx ts-node flags.ts user-Raj
NODE_ENV: staging
userId: user-Raj
new_checkout: true
beta_dashboard: true

Here the "source of truth" is the config object; in production you could load it from a JSON file, S3, or a small internal API and refresh it periodically. The app never holds business logic for when a feature is on — only the evaluator does.

Gradual rollout and kill switches

Gradual rollout means exposing a feature to a subset of traffic (by percentage, user segment, or region) and increasing exposure only when metrics look good. The percentage rule in the example above does that: same user always gets the same bucket (deterministic hash), so you can ramp from 5% to 50% without users flipping on and off.

A kill switch is a rule that overrides everything and turns the feature off. In the env pattern, you set FEATURE_NEW_CHECKOUT=false and restart (or update the process env). In the config pattern, you change the rule to { type: "off", value: false } and push config. The critical part: the decision must be read at request time (or at least on a short TTL cache). If your app only reads flags at startup, changing the env or config does nothing until you redeploy or restart.

So "done right" means:

  • Flags are evaluated per request (or with a short-lived cache, e.g. 60 seconds).
  • There is a single place (env, file, or feature-flag service) that you can change without a code deploy.
  • You have one or more "kill" rules (e.g. global off, or off when error rate > threshold) so that turning off is a config change, not a release.

    • How the main approaches compare

    | Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Env vars | No deps, easy to reason about, works everywhere. | No per-user or percentage; change requires env update/restart. | Few flags, on/off per environment only. | | Config file + evaluator | Percentage and env/tenant rules, no vendor lock-in, runnable in-process. | You own config storage, refresh, and (if needed) UI. | Small to mid teams, need rollout + kill switch without a SaaS. | | Unleash (open source) | Host yourself, SDKs, UI, targeting and percentage, active community. | You run and maintain the server and DB. | Teams that want a dashboard and multiple apps. | | Flagsmith (open source) | Cloud or self-hosted, segments and experiments. | Extra moving part; self-host has operational cost. | When you want experiments and a polished UI. | | Commercial (LaunchDarkly, etc.) | Mature UI, experiments, integrations, SLA. | Cost, vendor dependency, data leaves your infra. | Enterprise needs, compliance, or "we don’t want to run it". |

    For many teams, config file + evaluator or Unleash self-hosted hits the sweet spot: real gradual rollout and a kill switch, without a big bill or a closed-source dependency.

    Open-source tools worth a look

    Unleash (Apache 2.0) is the one we’ve seen most often in production. You run the Unleash server (and a DB — Postgres or SQLite), add feature toggles in the UI or API, and use the Node (or other) SDK in your app. The SDK fetches toggles and evaluates strategies (e.g. "gradualRollout" by percentage). Flipping a toggle off in the UI takes effect on the next SDK poll (or when you use the real-time option). That’s your kill switch.

    Flagsmith is open source (MIT) and can be self-hosted or used as a hosted service. You define flags and segments (e.g. "beta users"), and the SDK evaluates them per request. Good if you care about segment-based targeting and a ready-made UI.

    OpenFeature is a standard (CNCF) for feature-flag evaluation: your code calls a provider-agnostic API, and you plug in a provider (Unleash, LaunchDarkly, or your own). Use it when you want to avoid locking the codebase to one vendor while still using a provider for rules and UI.

    What went wrong (lessons learned)

    We once treated feature flags as "env vars that we set at deploy time." That meant every change required a new deploy. When a partner API started returning 5xx for 30% of requests, we had to roll back the entire release and wait for CI. Downtime was about 18 minutes. The fix was to move that integration behind a flag whose value was read from a small config service updated every 60 seconds. We could turn the integration off by changing one key in the config — no deploy. After that we made it a rule: any code path that talks to an external system we don’t control must be behind a flag we can turn off without a release.

    Another mistake: we had a "beta_dashboard" flag evaluated only at login. The config was updated to turn it off, but existing sessions kept seeing the dashboard until they logged out. So we learned to evaluate flags at the boundary of the feature (e.g. per request or per page load), not only at session creation. That way a kill switch takes effect on the next request.

    We also saw a 40% latency spike on one endpoint when we added a flag SDK that did a synchronous HTTP call on every request. We switched to a background poll (or real-time subscription) and in-memory evaluation; latency went back to baseline. So: avoid blocking the request path on network calls; prefer cached or pushed flag state and evaluate in-process.

    Actionable takeaways

  • Add one kill switch this week. Pick a single feature or integration (e.g. "new payment provider" or "recommendation engine") and put it behind a flag. Ensure the flag is read at request time and can be turned off via env or a config change without redeploy. Verify you can flip it and see the old behaviour within a minute.
  • Decide where the source of truth lives. If you have fewer than ~5 flags and only need on/off per environment, env vars are enough. If you need percentage or user-based rollout, implement a small evaluator (like the TypeScript example) or adopt Unleash/Flagsmith and keep the app code provider-agnostic where possible.
  • Never block the request on a remote flag call. Use in-process evaluation with config loaded in the background (file, polling, or push). If you use a vendor SDK, enable local caching and ensure time-to-live is short enough for kill switches (e.g. 60 seconds).
  • Document how to turn each high-risk feature off. In runbooks or README, list flags that act as kill switches and the exact env key or UI toggle. When something breaks at 2 AM, the person on call should not have to grep the codebase to find the flag name.
  • Review flags quarterly. Remove flags for features that have been fully rolled out for months. Stale flags accumulate and make "what’s actually on?" harder to answer; a small cleanup keeps the system understandable.

    • Feature flags are not just "if (feature_on)". They are the lever that lets you ship faster and roll back in seconds. Start with one kill switch and one gradual rollout; then grow from there.
