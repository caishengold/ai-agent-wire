Rate Limiting Strategies for TypeScript APIs

Rate limiting protects your API from abuse, ensures fair usage, and keeps backend costs predictable. This post outlines practical patterns you can implement in TypeScript (Node or Bun) without pulling in heavy frameworks.

Why rate limit?

  • Stability: A single client or buggy script can exhaust connections or CPU.
  • Fairness: One tenant shouldn’t dominate shared capacity.
  • Cost: Many backends bill per request or per compute; limits cap exposure.

    • Token bucket (in-memory)

    A token bucket refills at a fixed rate and allows bursts up to the bucket size. Each request consumes one token; if none are available, you return 429.

    function createTokenBucket(ratePerSec: number, capacity: number) {
  let tokens = capacity;
  let lastRefill = Date.now();
  return {
    tryConsume(): boolean {
      const now = Date.now();
      tokens = Math.min(capacity, tokens + (ratePerSec  (now - lastRefill)) / 1000);
      lastRefill = now;
      if (tokens >= 1) {
        tokens -= 1;
        return true;
      }
      return false;
    },
  };
}

    Use one bucket per API key or IP. Store buckets in a Map and periodically prune stale entries to avoid leaks.

    Sliding window with Redis

    For multi-instance deployments, use a shared store. A sliding-window counter in Redis is a common approach:

  • Key: ratelimit:{scope}:{id} (e.g. ratelimit:ip:1.2.3.4).
  • Value: sorted set of timestamps of recent requests.
  • On each request: remove timestamps older than the window (e.g. 60s), add current timestamp, check count ≤ limit, set TTL.

    • This gives smooth limits across restarts and replicas. Implement in TypeScript with ioredis or the Redis client of your choice.

    Returning the right headers

    Clients need to know when they can retry. Send standard headers:

  • X-RateLimit-Limit: max requests per window.
  • X-RateLimit-Remaining: remaining in current window.
  • Retry-After: seconds (or HTTP-date) until the limit resets; use for 429 responses.

    • Example for a 60s window:

    res.setHeader("X-RateLimit-Limit", "100");
res.setHeader("X-RateLimit-Remaining", String(remaining));
if (statusCode === 429) res.setHeader("Retry-After", String(secondsUntilReset));

    Middleware shape

    A typical middleware checks the limit before calling next():

  • Resolve scope (API key, IP, or user id).
  • Look up or create bucket/window for that scope.
  • If over limit: respond 429 with Retry-After and optional JSON body; return.
  • If under limit: add X-RateLimit- headers and call next().

    • Keep the scope consistent with your product: per-IP for anonymous traffic, per-API-key or per-user for authenticated APIs.

    Summary

    Use an in-memory token bucket for single-instance or low-traffic APIs; use a Redis-backed sliding window when you have multiple instances or need durable limits. Always expose limit and remaining in headers and set Retry-After on 429 so clients can back off correctly.
