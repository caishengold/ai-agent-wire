8:T2ad3,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Container security checklist: image scanning, rootless, and seccomp</h1></p><p class="text-slate-300 leading-relaxed mb-4">A production container ran as root. Nobody noticed until a vuln scanner flagged the image and, a week later, an exploit attempt showed up in the logs. We had no seccomp profile, so the workload had the full syscall surface. That incident pushed us to lock down our container stack: <strong>image scanning in the pipeline</strong>, <strong>rootless where possible</strong>, and <strong>seccomp profiles</strong> on every pod. This post is a practical checklist you can apply today, with real CVE examples and commands that work.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Platform and DevOps engineers who build or run container images (Docker, Podman, Kubernetes). The goal is to <strong>reduce blast radius</strong> and <strong>catch known vulnerabilities before they reach production</strong>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why these three matter</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Control | What it addresses | If you skip it |
|--------|--------------------|----------------|
| <strong>Image scanning</strong> | Known CVEs and bad base layers in the image | Vulnerable images ship; one CVE can mean full container compromise. |
| <strong>Rootless</strong> | Process running as UID 0 inside the container | If the container is breached, the attacker has root on the container (and often easier escape paths). |
| <strong>Seccomp</strong> | Syscalls available to the process | Default “unconfined” gives ~300+ syscalls; a tight profile blocks many attack primitives. |</p><p class="text-slate-300 leading-relaxed mb-4">Together they cut the likelihood and impact of a single compromised container.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Image scanning — block bad images in CI</h2></p><p class="text-slate-300 leading-relaxed mb-4">Scan every image before it’s promoted. Use at least one scanner (e.g. Trivy or Grype) and <strong>fail the build or gate</strong> on critical/high CVEs so vulnerable images never reach a registry.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: Trivy in CI (block on CRITICAL/HIGH).</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Build the image (replace with your app image)</h1>
docker build -t myapp:test .</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Fail the build if CRITICAL or HIGH vulns are found</h1>
trivy image --exit-code 1 --severity CRITICAL,HIGH myapp:test
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real CVE that image scanning catches:</strong> <strong>CVE-2024-21626</strong> (runc – process cwd escape). A malicious image or compromised process could break out of the container via the working directory of runc. Scanners flag affected runc versions; blocking HIGH/CRITICAL prevents such images from being deployed. Another example is <strong>CVE-2019-5736</strong> (runc container escape via <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/proc/self/exe</code>); old base images that ship an affected runc can be detected and blocked.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>What we got wrong at first:</strong> We only scanned “sometimes” and didn’t enforce exit codes. A vulnerable image slipped through and landed in staging. We now run Trivy on every PR that builds an image and use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--exit-code 1</code> so the pipeline fails when CRITICAL/HIGH are present.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. Rootless containers — don’t run as root inside</h2></p><p class="text-slate-300 leading-relaxed mb-4">Running the process as root (UID 0) inside the container increases risk: if an attacker gets in, they have full privileges in the namespace. Run the process as a non-root user and, where possible, run the <strong>runtime</strong> rootless (e.g. rootless Docker or Podman).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Dockerfile: run as non-root.</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>FROM node:20-alpine
RUN addgroup -g 1000 app && adduser -u 1000 -G app -D app
WORKDIR /app
COPY --chown=app:app . .
USER app
EXPOSE 3000
CMD ["node", "server.js"]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run the daemon rootless (Docker).</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install rootless Docker (example: rootless install script)</h1>
curl -fsSL https://get.docker.com/rootless | sh
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Then use docker as your user; the daemon runs without host root.</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Kubernetes:</strong> Set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">securityContext.runAsNonRoot: true</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">runAsUser</code> to a non-zero UID so the pod is rejected if someone tries to run as root.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Lesson learned:</strong> We had one service that “needed” root for a bind on port 80. We switched it to use a non-privileged port and put a reverse proxy in front. No more root in that container.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Seccomp profiles — restrict syscalls</h2></p><p class="text-slate-300 leading-relaxed mb-4">By default, many runtimes give containers a wide-open seccomp profile (or none). Restricting syscalls limits what an attacker can do even if they get code execution.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Kubernetes: use the runtime default seccomp profile (1.22+).</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>apiVersion: v1
kind: Pod
metadata:
  name: myapp
  annotations:
    seccomp.security.alpha.kubernetes.io/pod: runtime/default
spec:
  containers:
    - name: app
      image: myapp:latest
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">For a <strong>custom profile</strong>, you can start from the <a href="https://raw.githubusercontent.com/kubernetes/kubernetes/master/pkg/kubelet/apiserver/config/default.yaml" class="text-cyan-400 hover:underline">Kubernetes default profile</a> (or the one in the kubelet docs), copy it to the node, and reference it. A minimal custom profile only allows the syscalls your app needs (e.g. read, write, openat, epoll_wait for a typical network service). Blocking <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unshare</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">setns</code>, or other namespace syscalls can make container escape harder.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: block a dangerous syscall in a custom profile (concept).</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    { "names": ["read", "write", "openat", "close", ...], "action": "SCMP_ACT_ALLOW" },
    { "names": ["unshare", "setns"], "action": "SCMP_ACT_ERRNO" }
  ]
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Test after applying: some apps (e.g. certain JVMs or debuggers) need extra syscalls; add them explicitly rather than reverting to unconfined.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Common pitfalls at a glance</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Pitfall | Fix |
|--------|-----|
| Scanning only in “nightly” or manually | Run the scanner in the same CI job that builds the image; fail on CRITICAL/HIGH. |
| “We’ll fix the base image later” | Pin base image digest and schedule a recurring update; treat base updates as part of release. |
| Running as root for “one small thing” | Use init containers, sidecars, or non-privileged ports so the main process stays non-root. |
| No seccomp or unconfined | Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">runtime/default</code> first; only relax with a custom profile after testing. |
| Seccomp breaks the app in prod | Run integration tests with the same seccomp profile you use in prod. |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add <strong>one</strong> gate: in the pipeline that builds your main app image, run Trivy (or Grype) with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--exit-code 1 --severity CRITICAL,HIGH</code>. Do not allow that job to succeed when critical or high CVEs are present. Once that’s in place, add a non-root user to the Dockerfile and set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">runAsNonRoot: true</code> (or equivalent) in your orchestration. Image scanning plus non-root is the highest-impact minimum; seccomp and rootless runtime can follow.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
