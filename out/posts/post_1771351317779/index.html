Container security checklist: image scanning, rootless, and seccomp

A production container ran as root. Nobody noticed until a vuln scanner flagged the image and, a week later, an exploit attempt showed up in the logs. We had no seccomp profile, so the workload had the full syscall surface. That incident pushed us to lock down our container stack: image scanning in the pipeline, rootless where possible, and seccomp profiles on every pod. This post is a practical checklist you can apply today, with real CVE examples and commands that work.

Who this is for: Platform and DevOps engineers who build or run container images (Docker, Podman, Kubernetes). The goal is to reduce blast radius and catch known vulnerabilities before they reach production.

Why these three matter

| Control | What it addresses | If you skip it | |--------|--------------------|----------------| | Image scanning | Known CVEs and bad base layers in the image | Vulnerable images ship; one CVE can mean full container compromise. | | Rootless | Process running as UID 0 inside the container | If the container is breached, the attacker has root on the container (and often easier escape paths). | | Seccomp | Syscalls available to the process | Default “unconfined” gives ~300+ syscalls; a tight profile blocks many attack primitives. |

Together they cut the likelihood and impact of a single compromised container.

1. Image scanning — block bad images in CI

Scan every image before it’s promoted. Use at least one scanner (e.g. Trivy or Grype) and fail the build or gate on critical/high CVEs so vulnerable images never reach a registry.

Example: Trivy in CI (block on CRITICAL/HIGH).

Build the image (replace with your app image)

docker build -t myapp:test .
Fail the build if CRITICAL or HIGH vulns are found

trivy image --exit-code 1 --severity CRITICAL,HIGH myapp:test

Real CVE that image scanning catches: CVE-2024-21626 (runc – process cwd escape). A malicious image or compromised process could break out of the container via the working directory of runc. Scanners flag affected runc versions; blocking HIGH/CRITICAL prevents such images from being deployed. Another example is CVE-2019-5736 (runc container escape via /proc/self/exe); old base images that ship an affected runc can be detected and blocked.

What we got wrong at first: We only scanned “sometimes” and didn’t enforce exit codes. A vulnerable image slipped through and landed in staging. We now run Trivy on every PR that builds an image and use --exit-code 1 so the pipeline fails when CRITICAL/HIGH are present.

2. Rootless containers — don’t run as root inside

Running the process as root (UID 0) inside the container increases risk: if an attacker gets in, they have full privileges in the namespace. Run the process as a non-root user and, where possible, run the runtime rootless (e.g. rootless Docker or Podman).

Dockerfile: run as non-root.

FROM node:20-alpine
RUN addgroup -g 1000 app && adduser -u 1000 -G app -D app
WORKDIR /app
COPY --chown=app:app . .
USER app
EXPOSE 3000
CMD ["node", "server.js"]

Run the daemon rootless (Docker).

Install rootless Docker (example: rootless install script)

curl -fsSL https://get.docker.com/rootless | sh

Then use docker as your user; the daemon runs without host root.

Kubernetes: Set securityContext.runAsNonRoot: true and runAsUser to a non-zero UID so the pod is rejected if someone tries to run as root.

Lesson learned: We had one service that “needed” root for a bind on port 80. We switched it to use a non-privileged port and put a reverse proxy in front. No more root in that container.

3. Seccomp profiles — restrict syscalls

By default, many runtimes give containers a wide-open seccomp profile (or none). Restricting syscalls limits what an attacker can do even if they get code execution.

Kubernetes: use the runtime default seccomp profile (1.22+).

apiVersion: v1
kind: Pod
metadata:
  name: myapp
  annotations:
    seccomp.security.alpha.kubernetes.io/pod: runtime/default
spec:
  containers:
    - name: app
      image: myapp:latest

For a custom profile, you can start from the Kubernetes default profile (or the one in the kubelet docs), copy it to the node, and reference it. A minimal custom profile only allows the syscalls your app needs (e.g. read, write, openat, epoll_wait for a typical network service). Blocking unshare, setns, or other namespace syscalls can make container escape harder.

Example: block a dangerous syscall in a custom profile (concept).

{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    { "names": ["read", "write", "openat", "close", ...], "action": "SCMP_ACT_ALLOW" },
    { "names": ["unshare", "setns"], "action": "SCMP_ACT_ERRNO" }
  ]
}

Test after applying: some apps (e.g. certain JVMs or debuggers) need extra syscalls; add them explicitly rather than reverting to unconfined.

Common pitfalls at a glance

| Pitfall | Fix | |--------|-----| | Scanning only in “nightly” or manually | Run the scanner in the same CI job that builds the image; fail on CRITICAL/HIGH. | | “We’ll fix the base image later” | Pin base image digest and schedule a recurring update; treat base updates as part of release. | | Running as root for “one small thing” | Use init containers, sidecars, or non-privileged ports so the main process stays non-root. | | No seccomp or unconfined | Use runtime/default first; only relax with a custom profile after testing. | | Seccomp breaks the app in prod | Run integration tests with the same seccomp profile you use in prod. |

One thing to do right now

Add one gate: in the pipeline that builds your main app image, run Trivy (or Grype) with --exit-code 1 --severity CRITICAL,HIGH. Do not allow that job to succeed when critical or high CVEs are present. Once that’s in place, add a non-root user to the Dockerfile and set runAsNonRoot: true (or equivalent) in your orchestration. Image scanning plus non-root is the highest-impact minimum; seccomp and rootless runtime can follow.
