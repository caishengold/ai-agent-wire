Linux performance debugging toolkit: htop, perf, strace, bpftrace

The dashboard said p99 latency had tripled. Logs showed no errors. We had no idea whether it was CPU, disk, locks, or something in the kernel. That’s when a small set of CLI tools turned “something is slow” into “this syscall is the bottleneck” in under ten minutes.

This post is a practical toolkit: htop for a quick picture of who is busy, perf for CPU and call stacks, strace for syscall-level visibility, and bpftrace for custom, low-overhead probes. Each section includes real diagnosis stories and copy-paste commands.

Why these four?

| Tool | Answers | When to use it | |----------|----------------------------------|-----------------------------------------| | htop | Who is using CPU and memory? | First step: identify the busy process | | perf | Which functions burn CPU? | After you know the PID, find the code | | strace | What syscalls is this process making? | I/O, network, locks, or “mystery” stalls | | bpftrace | What’s slow or frequent at kernel level? | Custom probes without changing code |

Use them in order: htop → perf → strace or bpftrace when you need syscall or kernel detail.

htop: who is using CPU and memory?

Install (Debian/Ubuntu): sudo apt install htop. Run htop.

  • Sort by CPU: F6 → PERCENT_CPU.
  • Tree view: F5 — parent/child relationship.
  • Filter: F4, type e.g. node or bun.

    • Real case: A Bun API was slow under load. htop showed one worker at 99% CPU while others were idle. Tree view showed it was a single child of the main process. We attached perf to that PID and found the hot function in a JSON parsing path; we switched to a streaming parser and latency dropped.

    perf: where is CPU time spent?

    Install: sudo apt install linux-tools-common linux-tools-$(uname -r) (or distro equivalent).

    Record 10 seconds system-wide (needs root)
    
sudo perf record -g -a -- sleep 10
    Report with call graph
    
sudo perf report -g 'graph,0.5,caller'

    Focus on the Overhead column and the call stack. Hot functions (e.g. regex, parsing, hashing) show up at the top.

    Single process:

    sudo perf record -g -p $(pgrep -f "bun run server") -- sleep 10
sudo perf report -g 'graph,0.5,caller'

    Real case: After htop pointed to one process, perf showed ~50% of samples in a single function that did repeated small allocations in a loop. We replaced it with a preallocated buffer; CPU dropped and p99 improved.

    strace: what syscalls is this process making?

    Attach to a running process or run a command under strace:

    Attach to PID (-f to follow forks)
    
sudo strace -p  -f -tt -T 2>&1 | tee strace.log
    Run and trace
    
strace -tt -T -f -o trace.log -- your-command

    -tt adds timestamps; -T prints time per syscall. Look for syscalls with large time (e.g. read, poll, futex, epoll_wait).

    Real case: A service looked CPU-bound in htop, but perf showed little userspace CPU. strace revealed a huge number of futex calls with high T — lock contention. We reduced lock scope and added a small per-shard cache; load dropped.

    Gotcha: strace is slow and can change timing. Use short captures or on already-slow operations. In production, prefer perf or bpftrace when you can.

    bpftrace: custom probes and one-liners

    bpftrace answers questions like “which syscalls are slow?” or “which process is doing disk I/O?” without code changes. Install: sudo apt install bpftrace (or see bpftrace).

    Count syscalls by name (run a few seconds, then Ctrl+C):

    sudo bpftrace -e 'tracepoint:syscalls:sys_enter_ { @[probe] = count(); }'

    Slow syscalls (e.g. > 10 ms):

    sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_ { @start[probe] = nsecs; }
  tracepoint:syscalls:sys_exit_ /@start[probe]/ {
    $d = (nsecs - @start[probe])/1000000;
    if ($d > 10) { @slow[probe] = hist($d); }
  }
  END { clear(@start); }'

    Real case: We suspected a library was doing many small reads. A short bpftrace script counted read/readv by process; one helper process had orders of magnitude more than others. We swapped that component and I/O dropped.

    Gotcha: bpftrace needs kernel headers and a supported kernel. On minimal or locked-down hosts, use strace or perf instead.

    Common pitfalls at a glance

    | Pitfall | Symptom | Fix | |---------|---------|-----| | Profiling too short | perf report shows noise | Record at least 10–30 s under load | | strace on high-throughput process | Process slows down a lot | Prefer perf or bpftrace; if strace, use short capture | | Ignoring kernel time in perf | “No hot function” but process is busy | Check kernel frames; may be syscall or I/O wait | | Missing symbols in perf | Only hex addresses | Install debug symbols or use -f and build with debug info | | bpftrace not available | Script fails on minimal image | Use strace + perf and document for runbook |

    Lessons learned

  • Start with htop so you know which process to profile; tree view is often enough to pick the right PID.
  • perf is the workhorse for CPU: record under real load, then inspect the call graph.
  • When CPU looks high but perf shows little userspace time, think locks or I/O — that’s when strace (or bpftrace) pays off.
  • Keep a small runbook of one-liners (perf record/report, strace attach, one bpftrace script) so the next incident is a copy-paste, not a scramble.

    • Takeaway

    Next time something is “slow” and logs are silent: run htop, sort by CPU, pick the PID, then run sudo perf record -g -p -- sleep 10 and perf report. You’ll often go from “slow” to “this function or this syscall” in under five minutes.
