8:T2e31,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Linux performance debugging toolkit: htop, perf, strace, bpftrace</h1></p><p class="text-slate-300 leading-relaxed mb-4">The dashboard said p99 latency had tripled. Logs showed no errors. We had no idea whether it was CPU, disk, locks, or something in the kernel. That’s when a small set of CLI tools turned “something is slow” into “this syscall is the bottleneck” in under ten minutes.</p><p class="text-slate-300 leading-relaxed mb-4">This post is a practical toolkit: <strong>htop</strong> for a quick picture of who is busy, <strong>perf</strong> for CPU and call stacks, <strong>strace</strong> for syscall-level visibility, and <strong>bpftrace</strong> for custom, low-overhead probes. Each section includes real diagnosis stories and copy-paste commands.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why these four?</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Tool     | Answers                         | When to use it                          |
|----------|----------------------------------|-----------------------------------------|
| <strong>htop</strong> | Who is using CPU and memory?     | First step: identify the busy process   |
| <strong>perf</strong> | Which functions burn CPU?        | After you know the PID, find the code   |
| <strong>strace</strong> | What syscalls is this process making? | I/O, network, locks, or “mystery” stalls |
| <strong>bpftrace</strong> | What’s slow or frequent at kernel level? | Custom probes without changing code     |</p><p class="text-slate-300 leading-relaxed mb-4">Use them in order: htop → perf → strace or bpftrace when you need syscall or kernel detail.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">htop: who is using CPU and memory?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Install (Debian/Ubuntu): <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install htop</code>. Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">htop</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Sort by CPU: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F6</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PERCENT_CPU</code>.</li>
<li class="ml-4 list-disc text-slate-300">Tree view: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F5</code> — parent/child relationship.</li>
<li class="ml-4 list-disc text-slate-300">Filter: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F4</code>, type e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> A Bun API was slow under load. htop showed one worker at 99% CPU while others were idle. Tree view showed it was a single child of the main process. We attached perf to that PID and found the hot function in a JSON parsing path; we switched to a streaming parser and latency dropped.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">perf: where is CPU time spent?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Install: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install linux-tools-common linux-tools-$(uname -r)</code> (or distro equivalent).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Record 10 seconds system-wide (needs root)</h1>
sudo perf record -g -a -- sleep 10</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Report with call graph</h1>
sudo perf report -g 'graph,0.5,caller'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Focus on the Overhead column and the call stack. Hot functions (e.g. regex, parsing, hashing) show up at the top.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Single process:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo perf record -g -p $(pgrep -f "bun run server") -- sleep 10
sudo perf report -g 'graph,0.5,caller'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> After htop pointed to one process, perf showed ~50% of samples in a single function that did repeated small allocations in a loop. We replaced it with a preallocated buffer; CPU dropped and p99 improved.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">strace: what syscalls is this process making?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Attach to a running process or run a command under strace:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Attach to PID (-f to follow forks)</h1>
sudo strace -p <PID> -f -tt -T 2>&1 | tee strace.log</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Run and trace</h1>
strace -tt -T -f -o trace.log -- your-command
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-tt</code> adds timestamps; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-T</code> prints time per syscall. Look for syscalls with large time (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">poll</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">futex</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">epoll_wait</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> A service looked CPU-bound in htop, but perf showed little userspace CPU. strace revealed a huge number of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">futex</code> calls with high <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">T</code> — lock contention. We reduced lock scope and added a small per-shard cache; load dropped.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> strace is slow and can change timing. Use short captures or on already-slow operations. In production, prefer perf or bpftrace when you can.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">bpftrace: custom probes and one-liners</h2></p><p class="text-slate-300 leading-relaxed mb-4">bpftrace answers questions like “which syscalls are slow?” or “which process is doing disk I/O?” without code changes. Install: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install bpftrace</code> (or see <a href="https://github.com/iovisor/bpftrace" class="text-cyan-400 hover:underline">bpftrace</a>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Count syscalls by name (run a few seconds, then Ctrl+C):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo bpftrace -e 'tracepoint:syscalls:sys_enter_<em> { @[probe] = count(); }'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Slow syscalls (e.g. > 10 ms):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_</em> { @start[probe] = nsecs; }
  tracepoint:syscalls:sys_exit_<em> /@start[probe]/ {
    $d = (nsecs - @start[probe])/1000000;
    if ($d > 10) { @slow[probe] = hist($d); }
  }
  END { clear(@start); }'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> We suspected a library was doing many small reads. A short bpftrace script counted <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">readv</code> by process; one helper process had orders of magnitude more than others. We swapped that component and I/O dropped.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> bpftrace needs kernel headers and a supported kernel. On minimal or locked-down hosts, use strace or perf instead.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Common pitfalls at a glance</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Pitfall | Symptom | Fix |
|---------|---------|-----|
| Profiling too short | perf report shows noise | Record at least 10–30 s under load |
| strace on high-throughput process | Process slows down a lot | Prefer perf or bpftrace; if strace, use short capture |
| Ignoring kernel time in perf | “No hot function” but process is busy | Check kernel frames; may be syscall or I/O wait |
| Missing symbols in perf | Only hex addresses | Install debug symbols or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-f</code> and build with debug info |
| bpftrace not available | Script fails on minimal image | Use strace + perf and document for runbook |</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Start with <strong>htop</strong> so you know which process to profile; tree view is often enough to pick the right PID.</li>
<li class="ml-4 list-disc text-slate-300"><strong>perf</strong> is the workhorse for CPU: record under real load, then inspect the call graph.</li>
<li class="ml-4 list-disc text-slate-300">When CPU looks high but perf shows little userspace time, think <strong>locks or I/O</strong> — that’s when <strong>strace</strong> (or bpftrace) pays off.</li>
<li class="ml-4 list-disc text-slate-300">Keep a small runbook of one-liners (perf record/report, strace attach, one bpftrace script) so the next incident is a copy-paste, not a scramble.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Next time something is “slow” and logs are silent: run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">htop</code>, sort by CPU, pick the PID, then run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo perf record -g -p <PID> -- sleep 10</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">perf report</code>. You’ll often go from “slow” to “this function or this syscall” in under five minutes.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
