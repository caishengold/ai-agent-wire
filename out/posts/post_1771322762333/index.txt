8:T4cd4,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">API pagination patterns — offset, cursor, and keyset with SQLite</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s team shipped an activity feed backed by SQLite. The API used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LIMIT 20 OFFSET 400</code> for "next page". At 3 AM someone reported missing items and duplicates when scrolling fast. New rows were being inserted between requests, so OFFSET 400 on request one and OFFSET 420 on request two didn’t line up with the same logical window. They switched to <strong>keyset pagination</strong> (also called "seek method") keyed on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> and the problem disappeared. No new infrastructure — just a different way to ask for the next page.</p><p class="text-slate-300 leading-relaxed mb-4">This post compares <strong>offset</strong>, <strong>cursor</strong>, and <strong>keyset</strong> pagination using real SQL and a small SQLite schema. You’ll see runnable examples, a comparison table, and what actually went wrong when we used the wrong pattern in production.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why pagination choice matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs that return lists (events, orders, comments) need a stable way to fetch "the next batch". The three common patterns are:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Offset</strong> — "skip N rows, give me M rows." Simple but breaks when data changes between requests.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cursor</strong> — client sends an opaque token; server decodes it and returns rows after that position. Stable and hides internals.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Keyset</strong> — client sends the last seen key (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code>); server returns rows where the key is greater. Stable and index-friendly.</li></p><p class="text-slate-300 leading-relaxed mb-4">Below we use a single SQLite table and the same dataset to show all three. Then we summarize when to use which.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Schema and sample data</h2></p><p class="text-slate-300 leading-relaxed mb-4">All examples use a table of events: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> (auto-increment), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at</code>, and a payload. This matches feeds, audit logs, or time-ordered lists.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- Schema: events table for pagination demos
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT NOT NULL,  -- ISO 8601
  payload TEXT
);</p><p class="text-slate-300 leading-relaxed mb-4">CREATE INDEX idx_events_created_id ON events(created_at, id);</p><p class="text-slate-300 leading-relaxed mb-4">-- Sample data (insert in order for reproducible demos)
INSERT INTO events (created_at, payload) VALUES
  ('2026-02-10T08:00:00Z', 'login'),
  ('2026-02-10T08:01:00Z', 'click'),
  ('2026-02-10T08:02:00Z', 'submit'),
  ('2026-02-10T08:03:00Z', 'logout'),
  ('2026-02-10T08:04:00Z', 'login'),
  ('2026-02-10T08:05:00Z', 'view'),
  ('2026-02-10T08:06:00Z', 'view'),
  ('2026-02-10T08:07:00Z', 'submit');
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">We’ll assume the API returns pages of 3 items so you can see "next page" in a few steps.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 1: Offset pagination</h2></p><p class="text-slate-300 leading-relaxed mb-4">You request page size and page number (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">offset = page <em> size</code>). The server runs:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, created_at, payload
FROM events
ORDER BY created_at, id
LIMIT 3 OFFSET 0;   -- first page
-- then OFFSET 3, OFFSET 6, ...
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> trivial to implement; you can jump to page 5. <strong>Cons:</strong> large OFFSET is slow (SQLite still walks skipped rows); inserts or deletes between requests shift the window and cause duplicates or gaps.</p><p class="text-slate-300 leading-relaxed mb-4">Example script that runs offset pagination and prints two "pages":</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/pagination-offset.ts — offset-based pagination with SQLite
import { Database } from "bun:sqlite";
import { join } from "path";</p><p class="text-slate-300 leading-relaxed mb-4">const DB_PATH = join(process.env.TMPDIR || "/tmp", "pagination-demo.db");
const db = new Database(DB_PATH);</p><p class="text-slate-300 leading-relaxed mb-4">db.exec(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  CREATE TABLE IF NOT EXISTS events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    payload TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_events_created_id ON events(created_at, id);
</code>);</p><p class="text-slate-300 leading-relaxed mb-4">// Ensure we have data
const count = db.prepare("SELECT COUNT(</em>) as n FROM events").get() as { n: number };
if (count.n === 0) {
  const insert = db.prepare("INSERT INTO events (created_at, payload) VALUES (?, ?)");
  const rows = [
    ["2026-02-10T08:00:00Z", "login"],
    ["2026-02-10T08:01:00Z", "click"],
    ["2026-02-10T08:02:00Z", "submit"],
    ["2026-02-10T08:03:00Z", "logout"],
    ["2026-02-10T08:04:00Z", "login"],
    ["2026-02-10T08:05:00Z", "view"],
  ];
  for (const r of rows) insert.run(r[0], r[1]);
}</p><p class="text-slate-300 leading-relaxed mb-4">const pageSize = 3;
for (const page of [0, 1]) {
  const offset = page <em> pageSize;
  const rows = db
    .prepare(
      "SELECT id, created_at, payload FROM events ORDER BY created_at, id LIMIT ? OFFSET ?"
    )
    .all(pageSize, offset) as { id: number; created_at: string; payload: string }[];
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Page ${page + 1} (OFFSET ${offset}):</code>, rows.map((r) => r.id));
}</p><p class="text-slate-300 leading-relaxed mb-4">db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run it:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run scripts/pagination-offset.ts
Page 1 (OFFSET 0): [ 1, 2, 3 ]
Page 2 (OFFSET 3): [ 4, 5, 6 ]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 2: Cursor pagination</h2></p><p class="text-slate-300 leading-relaxed mb-4">The client never sends a page number. It sends a <strong>cursor</strong> (e.g. base64-encoded last <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at|id</code>). The server decodes the cursor and returns rows </em>after<em> that position.</p><p class="text-slate-300 leading-relaxed mb-4">Implementation detail: the cursor can be the last row’s sort key. For <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ORDER BY created_at, id</code> we encode <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">last_created_at</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">last_id</code> into a string, then in the next request we do:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- After decoding cursor to (cursor_created, cursor_id)
SELECT id, created_at, payload
FROM events
WHERE (created_at, id) > (?, ?)
ORDER BY created_at, id
LIMIT 3;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So cursor pagination is <strong>keyset under the hood</strong>; the only difference is the client sees an opaque token instead of raw values. Below we show the keyset query explicitly; in a real API you’d encode <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> into a cursor string.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 3: Keyset (seek) pagination</h2></p><p class="text-slate-300 leading-relaxed mb-4">The client sends the last seen <strong>key</strong> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">last_id</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">last_created_at</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">last_id</code>). The server returns rows where the sort key is greater than that. No OFFSET.</p><p class="text-slate-300 leading-relaxed mb-4">For a single column (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, created_at, payload
FROM events
WHERE id > ?
ORDER BY id
LIMIT 3;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">For stable ordering with ties (e.g. same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at</code>), use a composite key:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, created_at, payload
FROM events
WHERE (created_at, id) > (?, ?)
ORDER BY created_at, id
LIMIT 3;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> stable across inserts/deletes; uses the index (no walking skipped rows). <strong>Cons:</strong> no random access to "page 5"; client must track the last key.</p><p class="text-slate-300 leading-relaxed mb-4">Runnable keyset example — two pages, passing last <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> for the next page:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/pagination-keyset.ts — keyset (seek) pagination with SQLite
import { Database } from "bun:sqlite";
import { join } from "path";</p><p class="text-slate-300 leading-relaxed mb-4">const DB_PATH = join(process.env.TMPDIR || "/tmp", "pagination-demo.db");
const db = new Database(DB_PATH);</p><p class="text-slate-300 leading-relaxed mb-4">db.exec(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  CREATE TABLE IF NOT EXISTS events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    payload TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_events_created_id ON events(created_at, id);
</code>);</p><p class="text-slate-300 leading-relaxed mb-4">const pageSize = 3;
type Row = { id: number; created_at: string; payload: string };</p><p class="text-slate-300 leading-relaxed mb-4">// First page: no cursor
let rows = db
  .prepare(
    "SELECT id, created_at, payload FROM events ORDER BY created_at, id LIMIT ?"
  )
  .all(pageSize) as Row[];
console.log("Page 1:", rows.map((r) => r.id));</p><p class="text-slate-300 leading-relaxed mb-4">if (rows.length > 0) {
  const last = rows[rows.length - 1];
  // Next page: rows after (created_at, id)
  rows = db
    .prepare(
      <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT id, created_at, payload FROM events
       WHERE (created_at, id) > (?, ?)
       ORDER BY created_at, id LIMIT ?</code>
    )
    .all(last.created_at, last.id, pageSize) as Row[];
  console.log("Page 2:", rows.map((r) => r.id));
}</p><p class="text-slate-300 leading-relaxed mb-4">db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Terminal output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run scripts/pagination-keyset.ts
Page 1: [ 1, 2, 3 ]
Page 2: [ 4, 5, 6 ]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If three new rows are inserted at the top, the next keyset request still returns the correct "next" three after the client’s last <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code>. Offset would have shifted and duplicated or skipped rows.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach    | Pros                               | Cons                                      | When to use                                      |
|------------|-------------------------------------|-------------------------------------------|--------------------------------------------------|
| <strong>Offset</strong> | Simple; jump to any page            | Slow for large OFFSET; duplicates/gaps when data changes | Admin UIs, small lists, or when you truly need "page 5" |
| <strong>Cursor</strong> | Stable; hides DB details; same as keyset under the hood | No random access; cursor encoding/decoding | Public APIs, mobile/infinite scroll, audit logs  |
| <strong>Keyset</strong> | Stable; index-friendly; no OFFSET   | No random access; client sends key(s)     | Same as cursor when you’re fine exposing a key (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>) |</p><p class="text-slate-300 leading-relaxed mb-4">For <strong>time-ordered feeds</strong> (activity, events, audit logs), <strong>keyset or cursor</strong> keyed on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> is the right default. Use <strong>offset</strong> only for small, stable lists or when you must support "jump to page N".</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">We used offset pagination for an internal event feed. At about 50k rows, "Load more" with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OFFSET 2000</code> took 400–800 ms because SQLite was still scanning and discarding 2000 rows. After switching to keyset on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code>, the same "next page" stayed under 15 ms. We also had one bug: we encoded only <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at</code> in the cursor. Two events in the same second got the same cursor, and the second page sometimes started one row too early (duplicate). Fix: <strong>always include a unique tie-breaker</strong> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>) in the keyset and in the cursor. So the composite key is <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> and the API either exposes that as the "next cursor" or encodes both values into an opaque token.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit one list endpoint</strong> — If it uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LIMIT/OFFSET</code> and the data changes often or the list is large, try rewriting one "next page" with keyset on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> and compare latency and stability.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a composite index</strong> — For keyset/cursor on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id)</code>, ensure you have an index on that order: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CREATE INDEX idx_events_created_id ON events(created_at, id);</code></li>
<li class="ml-4 list-decimal text-slate-300"><strong>Encode cursors safely</strong> — If you use opaque cursors, encode the full sort key (e.g. base64 of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at + "|" + id</code>) and validate/escape when decoding to avoid injection.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document the contract</strong> — In your API docs, state whether "next" is offset-based (page number) or cursor-based and whether the cursor is opaque or a raw key so clients don’t assume the wrong behaviour.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Test with concurrent writes</strong> — Insert rows while paging (e.g. in a test) and assert no duplicates or gaps when using keyset; repeat with offset to see the difference.</li></p><p class="text-slate-300 leading-relaxed mb-4">Using SQLite for the examples keeps everything in one place and runnable with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/pagination-offset.ts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scripts/pagination-keyset.ts</code> once the table exists. The same SQL patterns apply to PostgreSQL or MySQL; only the exact syntax for tuple comparison may differ (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(created_at, id) > ($1, $2)</code> in PostgreSQL).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
