API pagination patterns — offset, cursor, and keyset with SQLite

Raj’s team shipped an activity feed backed by SQLite. The API used LIMIT 20 OFFSET 400 for "next page". At 3 AM someone reported missing items and duplicates when scrolling fast. New rows were being inserted between requests, so OFFSET 400 on request one and OFFSET 420 on request two didn’t line up with the same logical window. They switched to keyset pagination (also called "seek method") keyed on (created_at, id) and the problem disappeared. No new infrastructure — just a different way to ask for the next page.

This post compares offset, cursor, and keyset pagination using real SQL and a small SQLite schema. You’ll see runnable examples, a comparison table, and what actually went wrong when we used the wrong pattern in production.

Why pagination choice matters

APIs that return lists (events, orders, comments) need a stable way to fetch "the next batch". The three common patterns are:

  • Offset — "skip N rows, give me M rows." Simple but breaks when data changes between requests.
  • Cursor — client sends an opaque token; server decodes it and returns rows after that position. Stable and hides internals.
  • Keyset — client sends the last seen key (e.g. id or (created_at, id)); server returns rows where the key is greater. Stable and index-friendly.

    • Below we use a single SQLite table and the same dataset to show all three. Then we summarize when to use which.

    Schema and sample data

    All examples use a table of events: id (auto-increment), created_at, and a payload. This matches feeds, audit logs, or time-ordered lists.

    -- Schema: events table for pagination demos
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT NOT NULL,  -- ISO 8601
  payload TEXT
);
    CREATE INDEX idx_events_created_id ON events(created_at, id);
    -- Sample data (insert in order for reproducible demos)
INSERT INTO events (created_at, payload) VALUES
  ('2026-02-10T08:00:00Z', 'login'),
  ('2026-02-10T08:01:00Z', 'click'),
  ('2026-02-10T08:02:00Z', 'submit'),
  ('2026-02-10T08:03:00Z', 'logout'),
  ('2026-02-10T08:04:00Z', 'login'),
  ('2026-02-10T08:05:00Z', 'view'),
  ('2026-02-10T08:06:00Z', 'view'),
  ('2026-02-10T08:07:00Z', 'submit');

    We’ll assume the API returns pages of 3 items so you can see "next page" in a few steps.

    Pattern 1: Offset pagination

    You request page size and page number (or offset = page size). The server runs:

    SELECT id, created_at, payload
FROM events
ORDER BY created_at, id
LIMIT 3 OFFSET 0;   -- first page
-- then OFFSET 3, OFFSET 6, ...

    Pros: trivial to implement; you can jump to page 5. Cons: large OFFSET is slow (SQLite still walks skipped rows); inserts or deletes between requests shift the window and cause duplicates or gaps.

    Example script that runs offset pagination and prints two "pages":

    // scripts/pagination-offset.ts — offset-based pagination with SQLite
import { Database } from "bun:sqlite";
import { join } from "path";
    const DB_PATH = join(process.env.TMPDIR || "/tmp", "pagination-demo.db");
const db = new Database(DB_PATH);
    db.exec(
  CREATE TABLE IF NOT EXISTS events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    payload TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_events_created_id ON events(created_at, id);
);
    // Ensure we have data
const count = db.prepare("SELECT COUNT() as n FROM events").get() as { n: number };
if (count.n === 0) {
  const insert = db.prepare("INSERT INTO events (created_at, payload) VALUES (?, ?)");
  const rows = [
    ["2026-02-10T08:00:00Z", "login"],
    ["2026-02-10T08:01:00Z", "click"],
    ["2026-02-10T08:02:00Z", "submit"],
    ["2026-02-10T08:03:00Z", "logout"],
    ["2026-02-10T08:04:00Z", "login"],
    ["2026-02-10T08:05:00Z", "view"],
  ];
  for (const r of rows) insert.run(r[0], r[1]);
}
    const pageSize = 3;
for (const page of [0, 1]) {
  const offset = page  pageSize;
  const rows = db
    .prepare(
      "SELECT id, created_at, payload FROM events ORDER BY created_at, id LIMIT ? OFFSET ?"
    )
    .all(pageSize, offset) as { id: number; created_at: string; payload: string }[];
  console.log(Page ${page + 1} (OFFSET ${offset}):, rows.map((r) => r.id));
}
    db.close();

    Run it:

    $ bun run scripts/pagination-offset.ts
Page 1 (OFFSET 0): [ 1, 2, 3 ]
Page 2 (OFFSET 3): [ 4, 5, 6 ]

    Pattern 2: Cursor pagination

    The client never sends a page number. It sends a cursor (e.g. base64-encoded last id or created_at|id). The server decodes the cursor and returns rows after that position.

    Implementation detail: the cursor can be the last row’s sort key. For ORDER BY created_at, id we encode last_created_at and last_id into a string, then in the next request we do:

    -- After decoding cursor to (cursor_created, cursor_id)
SELECT id, created_at, payload
FROM events
WHERE (created_at, id) > (?, ?)
ORDER BY created_at, id
LIMIT 3;

    So cursor pagination is keyset under the hood; the only difference is the client sees an opaque token instead of raw values. Below we show the keyset query explicitly; in a real API you’d encode (created_at, id) into a cursor string.

    Pattern 3: Keyset (seek) pagination

    The client sends the last seen key (e.g. last_id or last_created_at + last_id). The server returns rows where the sort key is greater than that. No OFFSET.

    For a single column (e.g. id):

    SELECT id, created_at, payload
FROM events
WHERE id > ?
ORDER BY id
LIMIT 3;

    For stable ordering with ties (e.g. same created_at), use a composite key:

    SELECT id, created_at, payload
FROM events
WHERE (created_at, id) > (?, ?)
ORDER BY created_at, id
LIMIT 3;

    Pros: stable across inserts/deletes; uses the index (no walking skipped rows). Cons: no random access to "page 5"; client must track the last key.

    Runnable keyset example — two pages, passing last (created_at, id) for the next page:

    // scripts/pagination-keyset.ts — keyset (seek) pagination with SQLite
import { Database } from "bun:sqlite";
import { join } from "path";
    const DB_PATH = join(process.env.TMPDIR || "/tmp", "pagination-demo.db");
const db = new Database(DB_PATH);
    db.exec(
  CREATE TABLE IF NOT EXISTS events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    payload TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_events_created_id ON events(created_at, id);
);
    const pageSize = 3;
type Row = { id: number; created_at: string; payload: string };
    // First page: no cursor
let rows = db
  .prepare(
    "SELECT id, created_at, payload FROM events ORDER BY created_at, id LIMIT ?"
  )
  .all(pageSize) as Row[];
console.log("Page 1:", rows.map((r) => r.id));
    if (rows.length > 0) {
  const last = rows[rows.length - 1];
  // Next page: rows after (created_at, id)
  rows = db
    .prepare(
      SELECT id, created_at, payload FROM events
       WHERE (created_at, id) > (?, ?)
       ORDER BY created_at, id LIMIT ?
    )
    .all(last.created_at, last.id, pageSize) as Row[];
  console.log("Page 2:", rows.map((r) => r.id));
}
    db.close();

    Terminal output:

    $ bun run scripts/pagination-keyset.ts
Page 1: [ 1, 2, 3 ]
Page 2: [ 4, 5, 6 ]

    If three new rows are inserted at the top, the next keyset request still returns the correct "next" three after the client’s last (created_at, id). Offset would have shifted and duplicated or skipped rows.

    Comparison: when to use which

    | Approach | Pros | Cons | When to use | |------------|-------------------------------------|-------------------------------------------|--------------------------------------------------| | Offset | Simple; jump to any page | Slow for large OFFSET; duplicates/gaps when data changes | Admin UIs, small lists, or when you truly need "page 5" | | Cursor | Stable; hides DB details; same as keyset under the hood | No random access; cursor encoding/decoding | Public APIs, mobile/infinite scroll, audit logs | | Keyset | Stable; index-friendly; no OFFSET | No random access; client sends key(s) | Same as cursor when you’re fine exposing a key (e.g. id) |

    For time-ordered feeds (activity, events, audit logs), keyset or cursor keyed on (created_at, id) is the right default. Use offset only for small, stable lists or when you must support "jump to page N".

    Lessons learned

    We used offset pagination for an internal event feed. At about 50k rows, "Load more" with OFFSET 2000 took 400–800 ms because SQLite was still scanning and discarding 2000 rows. After switching to keyset on (created_at, id), the same "next page" stayed under 15 ms. We also had one bug: we encoded only created_at in the cursor. Two events in the same second got the same cursor, and the second page sometimes started one row too early (duplicate). Fix: always include a unique tie-breaker (e.g. id) in the keyset and in the cursor. So the composite key is (created_at, id) and the API either exposes that as the "next cursor" or encodes both values into an opaque token.

    What you can do today

  • Audit one list endpoint — If it uses LIMIT/OFFSET and the data changes often or the list is large, try rewriting one "next page" with keyset on (created_at, id) or id and compare latency and stability.
  • Add a composite index — For keyset/cursor on (created_at, id), ensure you have an index on that order: CREATE INDEX idx_events_created_id ON events(created_at, id);
  • Encode cursors safely — If you use opaque cursors, encode the full sort key (e.g. base64 of created_at + "|" + id) and validate/escape when decoding to avoid injection.
  • Document the contract — In your API docs, state whether "next" is offset-based (page number) or cursor-based and whether the cursor is opaque or a raw key so clients don’t assume the wrong behaviour.
  • Test with concurrent writes — Insert rows while paging (e.g. in a test) and assert no duplicates or gaps when using keyset; repeat with offset to see the difference.

    • Using SQLite for the examples keeps everything in one place and runnable with bun run scripts/pagination-offset.ts and scripts/pagination-keyset.ts once the table exists. The same SQL patterns apply to PostgreSQL or MySQL; only the exact syntax for tuple comparison may differ (e.g. (created_at, id) > ($1, $2) in PostgreSQL).
