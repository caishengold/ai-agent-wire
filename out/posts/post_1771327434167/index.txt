8:T596c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Authentication patterns for APIs — JWT, session tokens, API keys, OAuth2 PKCE</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a React dashboard that called their internal API using JWTs stored in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">localStorage</code>. A few months later, a third-party script on the marketing site was compromised. Attackers read the tokens from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">localStorage</code> and hit the API as authenticated users for about 47 minutes before someone noticed the spike in requests. The fix wasn’t just removing the script — it was admitting they had chosen the wrong auth pattern for a browser client. They had treated “we need a token” as one problem. In reality, <em>who</em> holds the token (server, browser, mobile app) and <em>what</em> you need (revocation, no secrets in the client) dictate which pattern you should use. This post walks through the four patterns we use most — API keys, session tokens, JWTs (JSON Web Tokens), and OAuth2 PKCE (Proof Key for Code Exchange) — with runnable code, a comparison matrix, and the mistakes we’d avoid next time.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the mechanism matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs need to answer two questions: who is calling, and what are they allowed to do? The way you pass and verify identity affects whether you can revoke access quickly, whether secrets can leak from the client, and how well the design fits servers, browsers, and mobile apps. No single pattern fits every scenario. Pick by client type and by how much you care about instant revocation, statelessness, and keeping secrets out of untrusted environments.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">API keys</h2></p><p class="text-slate-300 leading-relaxed mb-4">An <strong>API key</strong> is a long secret string the client sends on every request. It’s usually in a header (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-API-Key</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer <key></code>) or, less ideally, in a query parameter. The server looks it up in a store (database or cache) and maps it to an identity and permissions.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> Simple to implement and to hand to partners or scripts. No cryptography in the client.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> If leaked, anyone with the key has the same access until you revoke it. Keys in query params end up in logs and referrers; even headers can be logged by proxies. Rotation forces every client to update.</li></p><p class="text-slate-300 leading-relaxed mb-4">Use API keys for server-to-server calls, cron jobs, internal tools, and partner integrations where you control or document how keys are stored. Never put them in frontend code or URLs.</p><p class="text-slate-300 leading-relaxed mb-4">Example: validate an API key and attach identity. Store only a hash of the key (e.g. SHA-256), never plaintext.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Middleware: validate API key and attach identity (concept)

The client sends that id on each request (cookie or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization</code> header). The server looks up the session and gets the identity.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> Revocable immediately (delete or invalidate the session). No sensitive data in the token itself. Works well for “log out everywhere.”</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> Every request may hit the store unless you add a cache. You need a shared or sticky store for multi-node deployments. Cookie configuration (SameSite, Secure, HTTPOnly) matters for browsers.</li></p><p class="text-slate-300 leading-relaxed mb-4">Use sessions for web apps with a login page and for any case where you need to invalidate access quickly.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">JWT (JSON Web Token)</h2></p><p class="text-slate-300 leading-relaxed mb-4">A <strong>JWT</strong> is a signed payload: claims like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sub</code> (subject), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code> (expiry), and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scope</code>. The server signs it with a secret or private key. The client sends the token (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer <jwt></code>). The server verifies the signature and optionally the expiry; no database lookup is required for verification.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> Stateless verification; horizontal scaling is straightforward. One service can issue tokens, others verify with a shared secret or public key. Good for microservices and mobile backends.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> Revoking before <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code> is hard unless you add a blocklist or keep expiry short and use refresh tokens. Large payloads bloat the token. Algorithm confusion (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">alg: none</code>) and key leakage are real risks.</li></p><p class="text-slate-300 leading-relaxed mb-4">Use JWTs for service-to-service, mobile apps with a backend that issues tokens, or when you want stateless auth and can accept limited revocation.</p><p class="text-slate-300 leading-relaxed mb-4">Runnable example — sign and verify with HMAC-SHA256 (no external dependencies). <li class="ml-4 list-disc text-slate-300"><strong>Server or script calling your API:</strong> API key (hashed, scoped) or JWT issued by you.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Third-party app (“Login with X”):</strong> OAuth2 with PKCE on the client; issuer returns JWTs or opaque tokens.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Service-to-service inside your system:</strong> JWT or short-lived API key; verification can avoid a DB hit if you design for it.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">We made three mistakes that are worth avoiding.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>JWTs in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">localStorage</code> for an SPA.</strong> We treated “we need a token” the same for backend and frontend. For Sofia’s dashboard we issued JWTs and stored them in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">localStorage</code>. When a third-party script was compromised, the tokens were readable by any script on the page. We had no way to revoke them before expiry (we used 24-hour access tokens). We moved the dashboard to an OAuth2 PKCE flow with an authorization server, so tokens are obtained in a redirect flow and we could use httpOnly cookies or shorter-lived tokens with refresh in a controlled way. For browser clients we now avoid putting long-lived tokens in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">localStorage</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>API key in query params.</strong> We documented <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">?api_key=xxx</code> for convenience. One partner committed it to a public repo; another sent it in a support email. We moved to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer</code> only and started hashing keys in the database. Later we found two keys in proxy logs that had logged query strings. We now recommend headers only and never log the key or the full <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization</code> header.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>PKCE with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">plain</code> code_challenge.</strong> A legacy flow sent <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_challenge</code> as plain text (method <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">plain</code>) instead of S256. That gives no protection if the authorization code is intercepted. We switched to S256 only and deprecated <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">plain</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit where API keys appear</strong> — Search code and docs for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api_key</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apikey</code>, and query params. Move to header-only; ensure keys are hashed in storage and never logged.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Run the JWT and PKCE demos</strong> — In this repo: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/auth-jwt-demo.ts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/auth-pkce-demo.ts</code>. Use them as a reference for signing/verifying JWTs and generating PKCE parameters.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Map client types to one pattern each</strong> — Decide per use case: browser user, partner API, mobile app, internal service. Document it and enforce it (e.g. API key only for server clients, PKCE for the SPA).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add expiry to every token</strong> — JWTs and session tokens should have a short <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code>. Use refresh tokens or re-login for longer sessions; keep access tokens under an hour where possible.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Plan rotation</strong> — For API keys, support multiple keys per client and a grace period so you can rotate without downtime. For JWTs, use short expiry and a refresh flow so you can rotate signing keys on a schedule.</li></p><p class="text-slate-300 leading-relaxed mb-4">The scripts in this repo run with Bun and no extra dependencies. For production, consider a library like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">jose</code> for JWTs and a well-audited OAuth2/PKCE client for the full flow.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
