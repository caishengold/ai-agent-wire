Authentication patterns for APIs — JWT, session tokens, API keys, OAuth2 PKCE

Reading Level: 6neutral

Authentication patterns for APIs — JWT, session tokens, API keys, OAuth2 PKCE

Sofia’s team shipped a React dashboard that called their internal API using JWTs stored in localStorage. A few months later, a third-party script on the marketing site was compromised. Attackers read the tokens from localStorage and hit the API as authenticated users for about 47 minutes before someone noticed the spike in requests. The fix wasn’t just removing the script — it was admitting they had chosen the wrong auth pattern for a browser client. They had treated “we need a token” as one problem. In reality, who holds the token (server, browser, mobile app) and what you need (revocation, no secrets in the client) dictate which pattern you should use. This post walks through the four patterns we use most — API keys, session tokens, JWTs (JSON Web Tokens), and OAuth2 PKCE (Proof Key for Code Exchange) — with runnable code, a comparison matrix, and the mistakes we’d avoid next time.

Why the mechanism matters

APIs need to answer two questions: who is calling, and what are they allowed to do? The way you pass and verify identity affects whether you can revoke access quickly, whether secrets can leak from the client, and how well the design fits servers, browsers, and mobile apps. No single pattern fits every scenario. Pick by client type and by how much you care about instant revocation, statelessness, and keeping secrets out of untrusted environments.

API keys

An API key is a long secret string the client sends on every request. It’s usually in a header (X-API-Key or Authorization: Bearer ) or, less ideally, in a query parameter. The server looks it up in a store (database or cache) and maps it to an identity and permissions.

  • Pros: Simple to implement and to hand to partners or scripts. No cryptography in the client.
  • Cons: If leaked, anyone with the key has the same access until you revoke it. Keys in query params end up in logs and referrers; even headers can be logged by proxies. Rotation forces every client to update.

    • Use API keys for server-to-server calls, cron jobs, internal tools, and partner integrations where you control or document how keys are stored. Never put them in frontend code or URLs.

    Example: validate an API key and attach identity. Store only a hash of the key (e.g. SHA-256), never plaintext.

    // Middleware: validate API key and attach identity (concept)
// In production, use a proper hash (e.g. SHA-256) and compare with stored hash.
    import { createHash } from "node:crypto";
    async function requireApiKey(
  key: string | null
): Promise<{ userId: string; scope: string[] } | null> {
  if (!key) return null;
  const keyHash = createHash("sha256").update(key).digest("hex");
  // In real code: const record = await db.get("SELECT user_id, scope FROM api_keys WHERE key_hash = ?", [keyHash]);
  // Demo: pretend we found a record for this hash
  if (keyHash.length < 64) return null;
  return { userId: "raj@partner.co", scope: ["read:reports", "write:exports"] };
}
    // Usage: key from header or query (prefer header only)
const fromHeader = await requireApiKey("sk_live_abc123...");
console.log("Auth result:", fromHeader);
// Auth result: { userId: "raj@partner.co", scope: ["read:reports", "write:exports"] }

    Rate limit and audit by key so you can spot abuse and rotate when needed.

    Session tokens

    A session is created at login: the server stores session data (user id, roles, expiry) in a store (database or Redis) and returns a session id to the client. The client sends that id on each request (cookie or Authorization header). The server looks up the session and gets the identity.

  • Pros: Revocable immediately (delete or invalidate the session). No sensitive data in the token itself. Works well for “log out everywhere.”
  • Cons: Every request may hit the store unless you add a cache. You need a shared or sticky store for multi-node deployments. Cookie configuration (SameSite, Secure, HTTPOnly) matters for browsers.

    • Use sessions for web apps with a login page and for any case where you need to invalidate access quickly.

    JWT (JSON Web Token)

    A JWT is a signed payload: claims like sub (subject), exp (expiry), and scope. The server signs it with a secret or private key. The client sends the token (e.g. Authorization: Bearer ). The server verifies the signature and optionally the expiry; no database lookup is required for verification.

  • Pros: Stateless verification; horizontal scaling is straightforward. One service can issue tokens, others verify with a shared secret or public key. Good for microservices and mobile backends.
  • Cons: Revoking before exp is hard unless you add a blocklist or keep expiry short and use refresh tokens. Large payloads bloat the token. Algorithm confusion (e.g. alg: none) and key leakage are real risks.

    • Use JWTs for service-to-service, mobile apps with a backend that issues tokens, or when you want stateless auth and can accept limited revocation.

    Runnable example — sign and verify with HMAC-SHA256 (no external dependencies). From this repo: bun run scripts/auth-jwt-demo.ts.

    // scripts/auth-jwt-demo.ts — sign and verify JWT with HMAC-SHA256 (no deps)
// Run: bun run scripts/auth-jwt-demo.ts
    import { createHmac } from "node:crypto";
    const base64url = (buf: Buffer): string =>
  buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
    function signJwt(
  payload: Record,
  secret: string,
  expiresInSeconds: number = 3600
): string {
  const header = { alg: "HS256", typ: "JWT" };
  const now = Math.floor(Date.now() / 1000);
  const claims = { ...payload, iat: now, exp: now + expiresInSeconds };
  const headerB64 = base64url(Buffer.from(JSON.stringify(header)));
  const payloadB64 = base64url(Buffer.from(JSON.stringify(claims)));
  const signingInput = ${headerB64}.${payloadB64};
  const sig = createHmac("sha256", secret).update(signingInput).digest();
  return ${signingInput}.${base64url(sig)};
}
    function verifyJwt(token: string, secret: string): Record | null {
  const parts = token.split(".");
  if (parts.length !== 3) return null;
  const [headerB64, payloadB64, sigB64] = parts;
  const signingInput = ${headerB64}.${payloadB64};
  const expectedSig = createHmac("sha256", secret).update(signingInput).digest();
  const expectedB64 = base64url(expectedSig);
  if (expectedB64 !== sigB64) return null;
  const raw = Buffer.from(payloadB64.replace(/-/g, "+").replace(/_/g, "/"), "base64").toString("utf8");
  const parsed = JSON.parse(raw) as Record;
  if (typeof parsed.exp === "number" && parsed.exp < Math.floor(Date.now() / 1000)) return null;
  return parsed;
}
    const secret = "your-256-bit-secret-change-in-production";
const token = signJwt({ sub: "aiko@example.com", scope: "read:api" }, secret, 60);
const decoded = verifyJwt(token, secret);
const bad = verifyJwt(token, "wrong-secret");

    OAuth2 PKCE (Proof Key for Code Exchange)

    PKCE is an OAuth2 extension for clients that cannot keep a client secret: single-page apps (SPAs), mobile apps, and other “public” clients. The client generates a random code_verifier, computes code_challenge = base64url(sha256(code_verifier)), and sends the challenge when requesting the authorization code. When exchanging the code for tokens, it sends the code_verifier. The server hashes the verifier and checks it against the stored challenge, so a stolen authorization code alone cannot be used to get tokens.

  • Pros: No client secret in the browser or app. Mitigates authorization-code interception.
  • Cons: You need an authorization server (or identity provider) that supports PKCE. The flow has more steps than “send API key.”

    • Use PKCE for browser SPAs (e.g. “Login with X” and then call your API), native mobile apps, and any OAuth2 flow where the client is not trusted with a secret.

    Runnable example — generate code_verifier and code_challenge (S256). From this repo: bun run scripts/auth-pkce-demo.ts.

    // scripts/auth-pkce-demo.ts — generate PKCE code_verifier and code_challenge (no deps)
// Run: bun run scripts/auth-pkce-demo.ts
    import { randomBytes, createHash } from "node:crypto";
    const base64url = (buf: Buffer): string =>
  buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
    function generateCodeVerifier(): string {
  return base64url(randomBytes(32));
}
    function generateCodeChallenge(verifier: string): string {
  return base64url(createHash("sha256").update(verifier).digest());
}
    const codeVerifier = generateCodeVerifier();
const codeChallenge = generateCodeChallenge(codeVerifier);
// Client keeps code_verifier; sends code_challenge with the auth request.
// On token exchange, client sends code + code_verifier; server verifies hash(verifier) === stored code_challenge.

    Comparison matrix

    | Pattern | Pros | Cons | When to use | |----------------|------------------------------------|------------------------------------------------|--------------------------------------------------| | API key | Simple; no crypto in client | Leaks in logs/URLs; rotation breaks clients | Server-to-server, scripts, partners, internal | | Session | Revocable; no secrets in token | Needs server/store; cookie and state design | Web login; need to invalidate sessions fast | | JWT | Stateless; scales horizontally | Revocation before exp is awkward | Services, mobile backends, stateless APIs | | OAuth2 PKCE| No client secret; safe for SPAs | Needs auth server; more flow steps | Browser/mobile OAuth; public clients |

    Rough mapping:

  • Human in a browser (your app): Session or OAuth2 with PKCE if your app is the client.
  • Server or script calling your API: API key (hashed, scoped) or JWT issued by you.
  • Third-party app (“Login with X”): OAuth2 with PKCE on the client; issuer returns JWTs or opaque tokens.
  • Service-to-service inside your system: JWT or short-lived API key; verification can avoid a DB hit if you design for it.

    • Lessons learned

    We made three mistakes that are worth avoiding.

  • JWTs in localStorage for an SPA. We treated “we need a token” the same for backend and frontend. For Sofia’s dashboard we issued JWTs and stored them in localStorage. When a third-party script was compromised, the tokens were readable by any script on the page. We had no way to revoke them before expiry (we used 24-hour access tokens). We moved the dashboard to an OAuth2 PKCE flow with an authorization server, so tokens are obtained in a redirect flow and we could use httpOnly cookies or shorter-lived tokens with refresh in a controlled way. For browser clients we now avoid putting long-lived tokens in localStorage.

  • API key in query params. We documented ?api_key=xxx for convenience. One partner committed it to a public repo; another sent it in a support email. We moved to Authorization: Bearer only and started hashing keys in the database. Later we found two keys in proxy logs that had logged query strings. We now recommend headers only and never log the key or the full Authorization header.

  • PKCE with plain code_challenge. A legacy flow sent code_challenge as plain text (method plain) instead of S256. That gives no protection if the authorization code is intercepted. We switched to S256 only and deprecated plain.

    • What you can do today

  • Audit where API keys appear — Search code and docs for api_key, apikey, and query params. Move to header-only; ensure keys are hashed in storage and never logged.

  • Run the JWT and PKCE demos — In this repo: bun run scripts/auth-jwt-demo.ts and bun run scripts/auth-pkce-demo.ts. Use them as a reference for signing/verifying JWTs and generating PKCE parameters.

  • Map client types to one pattern each — Decide per use case: browser user, partner API, mobile app, internal service. Document it and enforce it (e.g. API key only for server clients, PKCE for the SPA).

  • Add expiry to every token — JWTs and session tokens should have a short exp. Use refresh tokens or re-login for longer sessions; keep access tokens under an hour where possible.

  • Plan rotation — For API keys, support multiple keys per client and a grace period so you can rotate without downtime. For JWTs, use short expiry and a refresh flow so you can rotate signing keys on a schedule.

    • The scripts in this repo run with Bun and no extra dependencies. For production, consider a library like jose for JWTs and a well-audited OAuth2/PKCE client for the full flow.
