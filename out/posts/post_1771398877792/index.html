Feature Flags for TypeScript Backends (2026)

Feature flags let you ship code behind a switch: turn features on or off without redeploying. For TypeScript backends, they improve safety (gradual rollouts, kill switches) and flexibility (A/B tests, per-tenant toggles). This post outlines a minimal, type-safe approach you can run in-process or back with a store.

Why Use Feature Flags?

  • Gradual rollout: Enable a new API or behavior for a percentage of traffic or a allowlist of tenant IDs.
  • Kill switch: If a deployment causes issues, disable the feature and redeploy later instead of rolling back.
  • Experimentation: Run A/B tests by branching on a flag and measuring outcomes.
  • Operational control: Turn off non-critical features under load without touching code.

    • In-Process Flags (Env or Config)

    The simplest form is reading flags from environment or config at startup:

    const flags = {
  useNewBilling: process.env.FEATURE_NEW_BILLING === 'true',
  enableBetaApi: process.env.FEATURE_BETA_API === 'true',
} as const;
    export function isEnabled(name: keyof typeof flags): boolean {
  return Boolean(flags[name]);
}

    Use at call sites:

    if (isEnabled('useNewBilling')) {
  return await newBillingService.charge(req);
}
return await legacyBilling.charge(req);

    Pros: no extra infra, type-safe keys. Cons: changing a flag requires restart or env change.

    Type-Safe Flag Keys

    Define a single source of truth and derive types:

    const FLAG_DEFS = {
  newSearch: { default: false },
  highTrafficMode: { default: false },
} as const;
    export type FlagName = keyof typeof FLAG_DEFS;
    export function getFlag(name: FlagName): boolean {
  const envKey = FEATURE_${name.toUpperCase().replace(/([A-Z])/g, '_$1').replace(/^_/, '')};
  const raw = process.env[envKey];
  if (raw === 'true') return true;
  if (raw === 'false') return false;
  return FLAG_DEFS[name].default;
}

    This keeps flag names and defaults in one place and avoids typos.

    Optional: Remote or DB-Backed Flags

    For runtime changes without restart, back flags with a DB or remote config:

    const flagCache = new Map();
const TTL_MS = 60_000;
    async function fetchFlag(name: FlagName): Promise {
  const cached = flagCache.get(name);
  if (cached && cached.until > Date.now()) return cached.value;
  const row = await db.prepare('SELECT enabled FROM feature_flags WHERE name = ?').get(name);
  const value = Boolean(row?.enabled);
  flagCache.set(name, { value, until: Date.now() + TTL_MS });
  return value;
}

    Use short TTLs so changes propagate quickly; for critical kill switches you can bypass cache.

    Best Practices

  • Default off: New features should default to false so a misconfiguration doesn’t enable them everywhere.
  • Scoped checks: Prefer checking the flag at the boundary (handler or service entry) rather than deep inside libraries.
  • Remove old code: Once a feature is fully rolled out, delete the legacy path and the flag to avoid permanent branching.
  • Audit: Log when flags are evaluated in production if you need to debug rollout or experiments.
  • Naming: Use a consistent prefix (e.g. FEATURE_ or flag.) and clear names like newBilling or betaApi.

    • Summary

    Feature flags in TypeScript backends can start as env-driven, type-safe in-process toggles and grow to DB- or remote-backed flags with caching. Keep a single definition for names and defaults, use them at boundaries, and plan to remove flags once the feature is the only path.
