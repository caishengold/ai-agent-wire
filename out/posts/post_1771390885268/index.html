Edge computing patterns for AI inference: a comparative analysis

Aiko’s team runs object detection on video from 200 retail stores. Sending every frame to the cloud cost too much and missed the 150 ms window for triggering alerts. They tried three approaches: full cloud, edge gateways with small models, and on-camera inference. Each pattern changed their latency, cost, and operational load in different ways. This post compares the main edge patterns for AI inference so you can pick the right one for your constraints.

Why compare patterns at all?

AI inference can run in the cloud, at a gateway (e.g. store or factory), or on the device (camera, phone, sensor). Where you run it drives latency, bandwidth, privacy, and cost. No single pattern wins everywhere—you choose by latency target, data sensitivity, and how much you can operate at the edge.

We’ll walk through four patterns, when each fits, and what we’d do again (or avoid).

Pattern 1: Cloud-only inference

All input is sent to a central region; models run in a data centre or managed ML service.

  • Pros: One place to update models, scale, and monitor. Easiest to start.
  • Cons: Round-trip latency (often 100–500 ms+), bandwidth cost for video or high-frequency sensors, and all data leaves the site.

    • When it fits: Batch jobs, non-real-time analytics, or when regulatory or policy requires central processing. Not a good fit when you need sub-100 ms response or must keep data on-premises.

    Pattern 2: Edge gateway with a small model

    A server or appliance at the site (store, factory, branch) runs a compressed or distilled model. Raw data stays on the LAN; only summaries, alerts, or samples go to the cloud.

  • Pros: Lower latency (often 20–80 ms on LAN), less bandwidth, data can stay on-site. One gateway can serve many cameras or sensors.
  • Cons: You operate and patch gateways, manage model updates per site, and need enough CPU/GPU at each location.

    • When it fits: Real-time decisions (alerts, quality checks, occupancy) with multiple streams per site. Aiko’s team landed here: one gateway per store, small YOLO-style model, alerts and daily aggregates to the cloud.

    Example: a minimal gateway config that loads a model and runs inference on a local queue.

    // gateway-inference.ts — pattern: load model once, infer on queue
import { createInferenceQueue } from "./inference-queue";
    const model = await loadModelFromPath("/opt/models/detector-v1.onnx");
const queue = createInferenceQueue(model, { concurrency: 2, batchSize: 4 });
    // Frames from cameras pushed to queue; results trigger alerts or forward to cloud
queue.on("result", (result) => {
  if (result.confidence > 0.9) sendAlert(result);
  else maybeSampleForCloud(result);
});

    Pattern 3: On-device inference

    The camera, phone, or sensor runs a tiny model (e.g. TensorFlow Lite, ONNX Runtime, or vendor SDK). No frame leaves the device unless the model flags an event.

  • Pros: Lowest latency (single-digit ms), no bandwidth for raw data, works offline, strong privacy.
  • Cons: Tight CPU/memory limits, small model only, and updating models across many devices is hard.

    • When it fits: Strict latency or privacy, or very high device count where gateway cost doesn’t scale. Good for “run locally, sync only when something interesting happens.”

    Pattern 4: Hybrid — device or gateway plus cloud fallback

    Edge runs a small, fast model for real-time decisions; a larger cloud model handles hard cases or periodic refinement.

  • Pros: You get low latency for most requests and higher accuracy when you can afford a round-trip.
  • Cons: Two model pipelines, routing logic, and you must define “hard case” (e.g. confidence threshold, or human-in-the-loop).

    • When it fits: When the edge model is good enough for 80% of cases and you want the cloud to handle the rest (e.g. fraud, rare objects, or audit).

    | Pattern | Typical latency | Bandwidth | Ops complexity | Best for | |------------------|-----------------|----------------|----------------|-----------------------------| | Cloud-only | 100–500 ms+ | High | Low | Batch, non-real-time | | Edge gateway | 20–80 ms | Medium (summaries) | Medium | Multi-stream, one site | | On-device | <20 ms | Very low | High (fleet) | Privacy, offline, scale-out | | Hybrid | Edge + cloud | Low–medium | High | Accuracy + latency trade-off|

    Practical comparison: same workload, different patterns

    Assume 10 cameras per site, 1 FPS analysis, 5 sites.

  • Cloud-only: 10 × 5 × 60 × 60 ≈ 180k images/hour to the cloud. Bandwidth and egress cost dominate; latency depends on region (often 200–400 ms).
  • Edge gateway: Each site runs inference locally; only metadata or thumbnails go up. Latency on the order of 30–60 ms; you pay for 5 gateways and model updates.
  • On-device: Each camera runs a small model; only events (e.g. “motion + class X”) are sent. Minimal bandwidth; you manage 50 devices and model rollouts.

    • For Aiko’s 200 stores, gateways per store beat cloud-only on cost and latency; on-device wasn’t needed because one gateway could handle the store’s streams.

    Gotchas we ran into

  • Model format and runtime mismatch — Gateways often use ONNX or TensorRT; devices use TFLite or vendor SDKs. Exporting from one framework to another can lose accuracy or require requantization. Test the exact target runtime early.
  • Cold start at the edge — Gateways that scale to zero or sleep between batches can add 1–3 s on first request. If you need consistent sub-100 ms, keep a warm process or a small always-on pool.
  • Updates at scale — Pushing a new model to hundreds of gateways or thousands of devices needs a clear strategy: staged rollout, rollback, and version checks. We’ve seen a bad model push spike false positives; having a quick rollback saved us.
  • Metrics and drift — Edge models see different data than the cloud (lighting, angles). Plan for monitoring accuracy and drift per site or cohort; otherwise you won’t notice when a model degrades in the field.

    • One thing to do next

    Map your current (or planned) inference flow to one of the four patterns. Then pick a single metric: latency p99, bandwidth per site, or cost per 1k inferences. Measure that for your current setup and estimate it for one alternative pattern. One concrete comparison (e.g. “gateway vs cloud for our 20 stores”) is more useful than a generic “edge is better.”
