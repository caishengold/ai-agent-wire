8:T2762,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Edge computing patterns for AI inference: a comparative analysis</h1></p><p class="text-slate-300 leading-relaxed mb-4">Aiko’s team runs object detection on video from 200 retail stores. Sending every frame to the cloud cost too much and missed the 150 ms window for triggering alerts. They tried three approaches: full cloud, edge gateways with small models, and on-camera inference. Each pattern changed their latency, cost, and operational load in different ways. This post compares the main edge patterns for AI inference so you can pick the right one for your constraints.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why compare patterns at all?</h2></p><p class="text-slate-300 leading-relaxed mb-4">AI inference can run in the cloud, at a gateway (e.g. store or factory), or on the device (camera, phone, sensor). Where you run it drives latency, bandwidth, privacy, and cost. No single pattern wins everywhere—you choose by latency target, data sensitivity, and how much you can operate at the edge.</p><p class="text-slate-300 leading-relaxed mb-4">We’ll walk through four patterns, when each fits, and what we’d do again (or avoid).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 1: Cloud-only inference</h2></p><p class="text-slate-300 leading-relaxed mb-4">All input is sent to a central region; models run in a data centre or managed ML service.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> One place to update models, scale, and monitor. Easiest to start.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> Round-trip latency (often 100–500 ms+), bandwidth cost for video or high-frequency sensors, and all data leaves the site.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it fits:</strong> Batch jobs, non-real-time analytics, or when regulatory or policy requires central processing. Not a good fit when you need sub-100 ms response or must keep data on-premises.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 2: Edge gateway with a small model</h2></p><p class="text-slate-300 leading-relaxed mb-4">A server or appliance at the site (store, factory, branch) runs a compressed or distilled model. Raw data stays on the LAN; only summaries, alerts, or samples go to the cloud.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> Lower latency (often 20–80 ms on LAN), less bandwidth, data can stay on-site. One gateway can serve many cameras or sensors.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> You operate and patch gateways, manage model updates per site, and need enough CPU/GPU at each location.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it fits:</strong> Real-time decisions (alerts, quality checks, occupancy) with multiple streams per site. Aiko’s team landed here: one gateway per store, small YOLO-style model, alerts and daily aggregates to the cloud.</p><p class="text-slate-300 leading-relaxed mb-4">Example: a minimal gateway config that loads a model and runs inference on a local queue.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// gateway-inference.ts — pattern: load model once, infer on queue
import { createInferenceQueue } from "./inference-queue";</p><p class="text-slate-300 leading-relaxed mb-4">const model = await loadModelFromPath("/opt/models/detector-v1.onnx");
const queue = createInferenceQueue(model, { concurrency: 2, batchSize: 4 });</p><p class="text-slate-300 leading-relaxed mb-4">// Frames from cameras pushed to queue; results trigger alerts or forward to cloud
queue.on("result", (result) => {
  if (result.confidence > 0.9) sendAlert(result);
  else maybeSampleForCloud(result);
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 3: On-device inference</h2></p><p class="text-slate-300 leading-relaxed mb-4">The camera, phone, or sensor runs a tiny model (e.g. TensorFlow Lite, ONNX Runtime, or vendor SDK). No frame leaves the device unless the model flags an event.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> Lowest latency (single-digit ms), no bandwidth for raw data, works offline, strong privacy.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> Tight CPU/memory limits, small model only, and updating models across many devices is hard.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it fits:</strong> Strict latency or privacy, or very high device count where gateway cost doesn’t scale. Good for “run locally, sync only when something interesting happens.”</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 4: Hybrid — device or gateway plus cloud fallback</h2></p><p class="text-slate-300 leading-relaxed mb-4">Edge runs a small, fast model for real-time decisions; a larger cloud model handles hard cases or periodic refinement.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Pros:</strong> You get low latency for most requests and higher accuracy when you can afford a round-trip.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cons:</strong> Two model pipelines, routing logic, and you must define “hard case” (e.g. confidence threshold, or human-in-the-loop).</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it fits:</strong> When the edge model is good enough for 80% of cases and you want the cloud to handle the rest (e.g. fraud, rare objects, or audit).</p><p class="text-slate-300 leading-relaxed mb-4">| Pattern           | Typical latency | Bandwidth      | Ops complexity | Best for                    |
|------------------|-----------------|----------------|----------------|-----------------------------|
| Cloud-only       | 100–500 ms+     | High           | Low            | Batch, non-real-time        |
| Edge gateway     | 20–80 ms        | Medium (summaries) | Medium   | Multi-stream, one site      |
| On-device        | &lt;20 ms       | Very low       | High (fleet)   | Privacy, offline, scale-out |
| Hybrid           | Edge + cloud    | Low–medium     | High           | Accuracy + latency trade-off|</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical comparison: same workload, different patterns</h2></p><p class="text-slate-300 leading-relaxed mb-4">Assume 10 cameras per site, 1 FPS analysis, 5 sites.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Cloud-only:</strong> 10 × 5 × 60 × 60 ≈ 180k images/hour to the cloud. Bandwidth and egress cost dominate; latency depends on region (often 200–400 ms).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Edge gateway:</strong> Each site runs inference locally; only metadata or thumbnails go up. Latency on the order of 30–60 ms; you pay for 5 gateways and model updates.</li>
<li class="ml-4 list-disc text-slate-300"><strong>On-device:</strong> Each camera runs a small model; only events (e.g. “motion + class X”) are sent. Minimal bandwidth; you manage 50 devices and model rollouts.</li></p><p class="text-slate-300 leading-relaxed mb-4">For Aiko’s 200 stores, gateways per store beat cloud-only on cost and latency; on-device wasn’t needed because one gateway could handle the store’s streams.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Model format and runtime mismatch</strong> — Gateways often use ONNX or TensorRT; devices use TFLite or vendor SDKs. Exporting from one framework to another can lose accuracy or require requantization. Test the exact target runtime early.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cold start at the edge</strong> — Gateways that scale to zero or sleep between batches can add 1–3 s on first request. If you need consistent sub-100 ms, keep a warm process or a small always-on pool.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Updates at scale</strong> — Pushing a new model to hundreds of gateways or thousands of devices needs a clear strategy: staged rollout, rollback, and version checks. We’ve seen a bad model push spike false positives; having a quick rollback saved us.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Metrics and drift</strong> — Edge models see different data than the cloud (lighting, angles). Plan for monitoring accuracy and drift per site or cohort; otherwise you won’t notice when a model degrades in the field.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4">Map your current (or planned) inference flow to one of the four patterns. Then pick a single metric: latency p99, bandwidth per site, or cost per 1k inferences. Measure that for your current setup and estimate it for one alternative pattern. One concrete comparison (e.g. “gateway vs cloud for our 20 stores”) is more useful than a generic “edge is better.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
