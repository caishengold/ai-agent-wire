8:T207f,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">TypeScript decorators in 2026: TC39 stage, patterns, and leaving experimental behind</h1></p><p class="text-slate-300 leading-relaxed mb-4">You added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators: true</code> years ago. Your Angular or Nest app runs. Then you see "stage 3 decorators" in the news and wonder: do I need to change anything, and what actually improved?</p><p class="text-slate-300 leading-relaxed mb-4">The short answer: the TC39 decorators proposal reached stage 3, and TypeScript 5+ supports it with a new <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators: false</code> (or omitted) world. The semantics are different from the old "experimental" decorators. Here’s where things stand in 2026 and how to use decorators without the legacy flag.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why decorators changed</h2></p><p class="text-slate-300 leading-relaxed mb-4">Legacy decorators were TypeScript-only and never aligned with a real JavaScript standard. The TC39 committee designed a new decorator model that works on classes, methods, accessors, and fields, with a clear contract: decorators receive a <em>value</em> and <em>context</em> (metadata about what’s being decorated) and return a new value or the same value. That’s the model TypeScript 5+ implements when you don’t enable <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>.</p><p class="text-slate-300 leading-relaxed mb-4">Stage 3 decorators are <strong>standard JavaScript</strong>. TypeScript’s job is to type them and emit code that matches the spec. So the "experimental" path is the one that’s going away; the new path is the one that will stick.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What the new decorators look like</h2></p><p class="text-slate-300 leading-relaxed mb-4">A stage 3 class method decorator receives two arguments: the current value (the function) and a context object that includes <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kind</code> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"method"</code>), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">name</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">addInitializer</code>. You return a new function (or the original) to replace the method.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function logged<This, Args extends unknown[], R>(
  value: (this: This, ...args: Args) => R,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => R>
) {
  const methodName = String(context.name);
  return function (this: This, ...args: Args): R {
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">entering ${methodName}</code>);
    const result = value.call(this, ...args);
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exiting ${methodName}</code>);
    return result;
  };
}</p><p class="text-slate-300 leading-relaxed mb-4">class Service {
  @logged
  handleRequest(id: number) {
    return { id, ok: true };
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">No <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> needed. The signature is explicit: you’re wrapping a function with a function. TypeScript and the runtime (e.g. a modern engine or a transpiler that targets the decorators spec) do the rest.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical patterns that work today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Method logging / tracing</strong> — As above: wrap the method, log on entry and exit, and return the original result. Same idea works for timing or error boundaries.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Validation</strong> — A decorator can return a new method that validates arguments (e.g. with Zod or a small validator) before calling the original. The context object tells you the method name for error messages.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Memoization</strong> — A decorator can replace a getter or method with one that caches the first result keyed by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">this</code> (and optionally arguments). Works well for expensive computations or accessors.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Dependency injection / registration</strong> — Some frameworks use class and method decorators to register handlers or inject dependencies. With stage 3, you use the same value/context contract; the main change is that you no longer rely on the old parameter property and metadata layout.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Migrating from experimental decorators</h2></p><p class="text-slate-300 leading-relaxed mb-4">The biggest gotcha: <strong>parameter decorators don’t exist in the stage 3 proposal.</strong> If you used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Param()</code> or similar to attach metadata to constructor or method parameters, you need another strategy. Common options: explicit config objects, a small DI container that reads types or a registry, or moving validation to the method body (e.g. with a single validated-args object).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Property decorators</strong> in the legacy world often mutated the descriptor or patched the prototype in ad hoc ways. In stage 3, field decorators receive the initial value and context and return a new initializer (or a getter/setter). The mental model is "replace the field’s definition" rather than "patch a descriptor."</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Execution order</strong> can differ. Run your test suite and any integration tests when switching; edge cases around inheritance and decorator order do exist.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Build setup:</strong> target a runtime that supports decorators (e.g. recent Node with the right flags, or a bundler/transpiler that implements the proposal). TypeScript’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">target</code> and the decorators proposal are independent: TS emits the decorator calls; the runtime or downstream tool must understand them.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do this week</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one class that still uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> (e.g. a single service or controller). Rewrite its decorators to the stage 3 style: function that takes <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(value, context)</code> and returns a replacement. Remove <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> for that file if your config allows per-file overrides, or do it in a branch. You’ll see exactly where you depended on parameter or property metadata and can then decide how to replace that with explicit config or validation.</p><p class="text-slate-300 leading-relaxed mb-4">Stage 3 decorators are the future; the experimental kind are legacy. Moving one small surface area now will make the rest of the migration predictable.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
