TypeScript decorators in 2026: TC39 stage, patterns, and leaving experimental behind

You added experimentalDecorators: true years ago. Your Angular or Nest app runs. Then you see "stage 3 decorators" in the news and wonder: do I need to change anything, and what actually improved?

The short answer: the TC39 decorators proposal reached stage 3, and TypeScript 5+ supports it with a new experimentalDecorators: false (or omitted) world. The semantics are different from the old "experimental" decorators. Here’s where things stand in 2026 and how to use decorators without the legacy flag.

Why decorators changed

Legacy decorators were TypeScript-only and never aligned with a real JavaScript standard. The TC39 committee designed a new decorator model that works on classes, methods, accessors, and fields, with a clear contract: decorators receive a value and context (metadata about what’s being decorated) and return a new value or the same value. That’s the model TypeScript 5+ implements when you don’t enable experimentalDecorators.

Stage 3 decorators are standard JavaScript. TypeScript’s job is to type them and emit code that matches the spec. So the "experimental" path is the one that’s going away; the new path is the one that will stick.

What the new decorators look like

A stage 3 class method decorator receives two arguments: the current value (the function) and a context object that includes kind (e.g. "method"), name, and addInitializer. You return a new function (or the original) to replace the method.

function logged(
  value: (this: This, ...args: Args) => R,
  context: ClassMethodDecoratorContext R>
) {
  const methodName = String(context.name);
  return function (this: This, ...args: Args): R {
    console.log(entering ${methodName});
    const result = value.call(this, ...args);
    console.log(exiting ${methodName});
    return result;
  };
}
class Service {
  @logged
  handleRequest(id: number) {
    return { id, ok: true };
  }
}

No experimentalDecorators needed. The signature is explicit: you’re wrapping a function with a function. TypeScript and the runtime (e.g. a modern engine or a transpiler that targets the decorators spec) do the rest.

Practical patterns that work today

Method logging / tracing — As above: wrap the method, log on entry and exit, and return the original result. Same idea works for timing or error boundaries.

Validation — A decorator can return a new method that validates arguments (e.g. with Zod or a small validator) before calling the original. The context object tells you the method name for error messages.

Memoization — A decorator can replace a getter or method with one that caches the first result keyed by this (and optionally arguments). Works well for expensive computations or accessors.

Dependency injection / registration — Some frameworks use class and method decorators to register handlers or inject dependencies. With stage 3, you use the same value/context contract; the main change is that you no longer rely on the old parameter property and metadata layout.

Migrating from experimental decorators

The biggest gotcha: parameter decorators don’t exist in the stage 3 proposal. If you used @Param() or similar to attach metadata to constructor or method parameters, you need another strategy. Common options: explicit config objects, a small DI container that reads types or a registry, or moving validation to the method body (e.g. with a single validated-args object).

Property decorators in the legacy world often mutated the descriptor or patched the prototype in ad hoc ways. In stage 3, field decorators receive the initial value and context and return a new initializer (or a getter/setter). The mental model is "replace the field’s definition" rather than "patch a descriptor."

Execution order can differ. Run your test suite and any integration tests when switching; edge cases around inheritance and decorator order do exist.

Build setup: target a runtime that supports decorators (e.g. recent Node with the right flags, or a bundler/transpiler that implements the proposal). TypeScript’s target and the decorators proposal are independent: TS emits the decorator calls; the runtime or downstream tool must understand them.

One thing to do this week

Pick one class that still uses experimentalDecorators (e.g. a single service or controller). Rewrite its decorators to the stage 3 style: function that takes (value, context) and returns a replacement. Remove experimentalDecorators for that file if your config allows per-file overrides, or do it in a branch. You’ll see exactly where you depended on parameter or property metadata and can then decide how to replace that with explicit config or validation.

Stage 3 decorators are the future; the experimental kind are legacy. Moving one small surface area now will make the rest of the migration predictable.
