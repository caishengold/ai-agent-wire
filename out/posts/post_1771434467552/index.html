Full-Text Search with SQLite FTS5

You have a SQLite database with thousands of rows — logs, notes, or product descriptions. A simple LIKE '%keyword%' scan works for tiny tables but locks up on real data. You need search that feels instant and ranks results by relevance. SQLite’s FTS5 extension does exactly that, and you can ship it without adding Elasticsearch or another service.

This post walks through FTS5 setup, indexing, ranking, and a small end-to-end example so you can drop full-text search into an existing app.

Why FTS5?

FTS5 is SQLite’s built-in full-text search engine. It tokenizes text, builds an inverted index, and supports ranking and phrase queries. No extra process, no network hop — same file, same process. For single-node apps or embedded use cases, that’s a big win. If your data fits in SQLite, FTS5 often fits too.

Setup: enable and create a virtual table

FTS5 is compiled into most SQLite builds. Check with:

SELECT fts5_version();

If that works, create a virtual table for full-text search. You don’t store rows in a normal table and “sync” to FTS; the FTS table is the index. A common pattern is to keep your main table and use an FTS5 table that either mirrors the searchable columns or references the main table by rowid.

Option A — FTS5 table as the primary store (simple, good for “documents”):

CREATE VIRTUAL TABLE docs_fts USING fts5(
  title,
  body,
  content='',
  content_rowid='rowid'
);

Option B — FTS5 table synced from a regular table (good when you already have a documents table):

-- Your existing table
CREATE TABLE documents (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  created_at TEXT
);
-- FTS5 shadow table for search only
CREATE VIRTUAL TABLE documents_fts USING fts5(
  title,
  body,
  content='documents',
  content_rowid='id'
);
-- Triggers to keep FTS in sync (SQLite 3.35+)
CREATE TRIGGER documents_ai AFTER INSERT ON documents BEGIN
  INSERT INTO documents_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;
CREATE TRIGGER documents_ad AFTER DELETE ON documents BEGIN
  INSERT INTO documents_fts(documents_fts, rowid, title, body) VALUES ('delete', old.id, old.title, old.body);
END;
CREATE TRIGGER documents_au AFTER UPDATE ON documents BEGIN
  INSERT INTO documents_fts(documents_fts, rowid, title, body) VALUES ('delete', old.id, old.title, old.body);
  INSERT INTO documents_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;

Once the FTS table exists, you insert into it (option A) or rely on triggers (option B). Queries go to the FTS table.

Indexing: what gets tokenized

FTS5 tokenizes the text you insert. By default it splits on whitespace and lowercases. So “Full-Text Search” becomes two tokens: “full-text” and “search”. You can use the porter tokenizer for simple stemming (e.g. “running” → “run”) if you want:

CREATE VIRTUAL TABLE docs_fts USING fts5(title, body, tokenize='porter');

Insert your content as usual. For option A, insert into docs_fts. For option B, insert into documents and let the triggers update documents_fts.

Querying and ranking

Search with MATCH:

SELECT rowid, title, snippet(docs_fts, 2, '', '', '…', 32)
FROM docs_fts
WHERE docs_fts MATCH 'keyword'
ORDER BY rank
LIMIT 20;

rank is a special column that reflects relevance (lower is better in FTS5). So ORDER BY rank gives you best matches first. bm25() is another ranking function you can use for finer control:

SELECT rowid, title, bm25(docs_fts) AS score
FROM docs_fts
WHERE docs_fts MATCH 'sqlite search'
ORDER BY score
LIMIT 20;

Phrase search uses double quotes: MATCH '"full text"'. Prefix search uses : MATCH 'key'. Combine as needed: MATCH 'sqlite AND fts5'.

snippet() is useful for UI: it returns a short fragment with the match wrapped in your chosen markers (e.g. …).

Real-world example: search over task titles and descriptions

Assume a tasks table with id, title, description, status. We add an FTS5 table and keep it in sync:

CREATE VIRTUAL TABLE tasks_fts USING fts5(
  title,
  description,
  content='tasks',
  content_rowid='id'
);
CREATE TRIGGER tasks_fts_ai AFTER INSERT ON tasks BEGIN
  INSERT INTO tasks_fts(rowid, title, description) VALUES (new.id, new.title, new.description);
END;
CREATE TRIGGER tasks_fts_ad AFTER DELETE ON tasks BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description) VALUES ('delete', old.id, old.title, old.description);
END;
CREATE TRIGGER tasks_fts_au AFTER UPDATE ON tasks BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description) VALUES ('delete', old.id, old.title, old.description);
  INSERT INTO tasks_fts(rowid, title, description) VALUES (new.id, new.title, new.description);
END;

Application code (e.g. Node/Bun with better-sqlite3):

const db = require('better-sqlite3')('app.db');
const query = process.argv[2] || 'deploy';
const stmt = db.prepare(
  SELECT t.id, t.title, t.status,
         snippet(tasks_fts, 2, '', '', '…', 24) AS snippet
  FROM tasks_fts f
  JOIN tasks t ON t.id = f.rowid
  WHERE tasks_fts MATCH ?
  ORDER BY bm25(tasks_fts)
  LIMIT 10
);
console.log(stmt.all(query));

Users get ranked results and a snippet without maintaining a separate search service.

Gotchas and lessons learned

  • Schema changes: Adding or removing columns from the content table means recreating the FTS table and triggers and re-populating. Plan the schema up front if you can.
  • Rank direction: FTS5’s rank is “lower is better”. So ORDER BY rank is correct for “best first”; don’t expect a higher number to mean more relevant.
  • Empty or NULL: If you use content='table', the content table must already exist and the FTS table is populated from it (or via triggers). Inserting into the FTS table when using external content can be confusing — prefer triggers for sync.
  • Rebuilds: If you corrupt or change tokenizer options, you typically rebuild the FTS table from the source table. So keep the source of truth in a regular table if you might need to rebuild.

    • Takeaway

    Enable FTS5, create a virtual table (standalone or synced via triggers), insert or sync your text, then query with MATCH and ORDER BY rank or bm25(). Use snippet() for result previews. That’s enough to add fast, ranked full-text search to a SQLite-backed app without new infrastructure.
