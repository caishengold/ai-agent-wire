DNS for developers — record types, TTL strategies, debugging with dig, common pitfalls

DNS for developers — record types, TTL strategies, debugging with dig, common pitfalls

Aiko’s deployment pipeline updated the A record for api.shop.example.com to a new Kubernetes ingress IP. Staging and her local machine picked it up within a minute. Customers in Berlin and Sydney kept getting connection refused for another 11 hours. The cause: a 43200-second (12-hour) TTL on that record. Their resolvers had cached the old IP. One config change — lowering TTL before the cutover — would have made the switch invisible. DNS is one of those layers that works until it doesn’t; when it breaks, it’s often in a region where you don’t have a terminal open. This post covers the record types you’ll actually use, how to choose TTLs, how to debug with dig, and the mistakes that bite back.

Who this is for: Developers who own domains, deploy services, or chase “it works here but not there” — and want to verify instead of guess.

Record types you’ll use in practice

The Domain Name System (DNS) maps names to data. Each record type answers a different question. You don’t need every type; these are the ones that show up in app and infra work.

| Type | Purpose | Example use | |--------|----------------------------------|--------------------------------------------------| | A | Hostname → IPv4 address | api.example.com → 203.0.113.42 | | AAAA | Hostname → IPv6 address | api.example.com → 2001:db8::1 | | CNAME | Alias: name → another name | www.example.com → example.com | | MX | Mail server for the domain | example.com → mail.provider.com (with priority) | | TXT | Arbitrary text (verification, SPF, DKIM) | Domain ownership, email auth | | NS | Which servers are authoritative | Delegation to your DNS provider | | SRV | Service discovery (host, port, priority) | _http._tcp.api.example.com → host + port |

Rule that trips people up: A CNAME makes a name an alias of exactly one other name. You cannot have both a CNAME and another record type (A, MX, TXT, etc.) for the same label. Either the label is an alias (CNAME only) or it has “real” records. At the zone apex (e.g. example.com with nothing in front), a bare CNAME is also problematic; many providers offer “ALIAS” or “CNAME flattening” so the apex can point at another hostname without breaking MX or other records.

Runnable example 1: inspecting records with dig

dig is the standard CLI tool for querying DNS. You give it a name and optionally a record type; it returns the answer, TTLs, and which server replied.

A record (IPv4) — replace with your own domain to experiment

dig +short api.github.com A

Example output:

20.248.137.48

Without +short you get the full response: TTL, flags, and authority info.

dig api.github.com A

Example output (abbreviated):

; <<>> DiG 9.18.24 <<>> api.github.com A
;; QUESTION SECTION:
;api.github.com.			IN	A
;; ANSWER SECTION:
api.github.com.		43	IN	A	20.248.137.48
;; Query time: 8 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)

The 43 in the answer is the TTL in seconds — resolvers may cache this for up to 43 seconds. Checking several types:

A and AAAA for dual-stack

dig +short api.github.com A
dig +short api.github.com AAAA
MX for mail

dig +short gmail.com MX
TXT (e.g. domain verification)

dig +short github.com TXT

Example MX output:

5 gmail-smtp-in.l.google.com.
10 alt1.gmail-smtp-in.l.google.com.
20 alt2.gmail-smtp-in.l.google.com.

TTL strategies: when to use what

TTL (time-to-live) is how long resolvers and clients may cache the answer. No single number fits every case.

| Situation | Typical TTL (seconds) | Why | |----------------------------------|-------------------------|-----| | Stable production endpoint | 300–3600 (5 min–1 h) | Balance cache hits with ability to change IPs with notice | | Pre-migration or failover | 60–300 (1–5 min) | After you flip the record, most clients see it within minutes | | CDN or load-balanced pool | 300–600 | Some caching; provider may suggest or override | | Static marketing site | 3600–86400 (1–24 h) | Rarely changes; long TTL cuts DNS load and speeds lookups | | Staging or ephemeral envs | 60–300 | IPs change or tear down; low TTL so fixes stick |

Cutover drill: Lower TTL to 60–300 at least one full TTL period before you change the record. If current TTL is 3600, set it to 300, wait an hour so old caches expire, then change the A/AAAA target. That avoids the “half the world still has the old IP” situation Aiko hit.

Runnable example 2: tracing resolution and querying authority

When “my domain doesn’t resolve” or “I updated DNS but nothing changed”, you need: (1) what your machine gets, (2) what the authoritative server says, (3) whether something in between is caching.

1. What your default resolver returns

dig +short docs.github.com A
2. Get the nameservers for the zone

dig +short github.com NS

Example NS output:

dns1.p08.nsone.net.
dns2.p08.nsone.net.
dns3.p08.nsone.net.
dns4.p08.nsone.net.


3. Ask one of those NS directly (bypass local/cache)

dig @dns1.p08.nsone.net docs.github.com A +short

If the authority answer matches what you expect but your default resolver does not, the issue is caching (wait for TTL or flush). If the authority answer is wrong, the bug is in your DNS config at the provider.

Check from another view: Your laptop may use a different resolver than production. Use a public resolver:

dig @8.8.8.8 docs.github.com A +short
dig @1.1.1.1 docs.github.com A +short

Full resolution path (optional): dig +trace docs.github.com A walks the chain from root → TLD → authoritative and shows each hop. Useful when delegation or glue records are wrong.

Low TTL vs high TTL: comparison

| | Low TTL (e.g. 60–300 s) | High TTL (e.g. 3600–86400 s) | |--|--------------------------|-------------------------------| | Pros | Changes propagate quickly; fewer “stale IP” incidents after migrations | Fewer DNS queries, less load on auth servers, faster repeat lookups from cache | | Cons | More queries to your DNS provider; slightly higher latency on cache miss | After a change, some users keep the old IP until TTL expires | | When to use | Before/after migrations, failover, or when the target IP changes often | Stable endpoints, static assets, when you rarely change the mapping |

We use 300 s for most production APIs and drop to 60 s the day before a planned cutover.

Common pitfalls

  • CNAME at the zone apex. The apex is the domain itself (e.g. example.com). A CNAME at the apex can conflict with MX and other records and is not allowed by the standard. Use A/AAAA or a provider-specific “ALIAS” / “flattened” target that resolves to an IP on the provider’s side.

  • Not lowering TTL before a change. You change the A record; part of the world keeps the old IP for hours. Lower TTL first, wait at least one full old TTL, then switch.

  • Assuming your change is live everywhere. Browsers, OS, and recursive resolvers all cache. dig from your machine shows what your resolver returned; production may use another resolver or region. Check from another network or use dig @8.8.8.8 / dig @1.1.1.1.

  • TXT record formatting. TXT can have multiple strings; providers may show them concatenated or separate. For SPF/DKIM, a single string is usual; watch for line breaks or extra quotes that break validation.

  • CNAME and another record on the same label. You cannot have both a CNAME and an A record for www.example.com. Pick one: either CNAME to another hostname or A/AAAA to IP(s).

  • SRV and CNAME confusion. SRV gives host + port; the host in the SRV target must resolve (usually A/AAAA). If that target is a CNAME, the chain must resolve end-to-end; a broken CNAME breaks the SRV lookup.

    • What went wrong (lessons learned)

    On a migration in 2025 we moved an API from one cloud region to another. We updated the A record to the new load balancer IP and ran smoke tests from our office — all green. Within an hour we got reports of timeouts from users in South America and Southeast Asia. Our office resolver had picked up the new IP quickly; resolvers in those regions were still serving the old one (TTL had been 7200). We had to lower TTL to 60, wait 2 hours, then change the record again. Downtime for those users was about 90 minutes. We now keep TTL at 300 for that record and have a runbook: “Before any IP or host change: set TTL to 60, wait 2× previous TTL, then apply change.”

    Another incident: Omar added a CNAME for api.example.com pointing at a third-party API gateway. The provider required a TXT record on the same name for verification. As soon as he added the TXT, DNS broke — their provider did not allow CNAME + TXT on the same label (strict RFC behaviour). The fix was to use a subdomain like gateway.api.example.com for the CNAME and keep api.example.com as an A record, or use the provider’s “CNAME flattening” so the apex-like name wasn’t a real CNAME in the zone. Lesson: check whether your DNS host allows CNAME plus other types; many do not.

    Actionable takeaway

  • Audit TTLs for any hostname that might change (APIs, load balancer targets). If they’re above 600, document why; if you have a migration plan, include “lower TTL 1–2× current TTL before cutover”.
  • Run dig from your machine and from a public resolver when debugging: dig +short A and dig @1.1.1.1 +short A. If they differ, it’s cache or resolver-specific.
  • Avoid CNAME at the zone apex. Use A/AAAA or your provider’s ALIAS/flattening for the root domain; use CNAME for subdomains (e.g. www, api) when you want to point at another hostname.
  • Before adding a CNAME, check whether that label already has (or will need) MX, TXT, or A. If it does, use a different subdomain or an A record.
  • Keep a one-line runbook for DNS changes: “TTL ≤ 300 for mutable targets; before cutover: set TTL to 60, wait 2× old TTL, then change record; verify with dig @8.8.8.8 A.”

    • Once you’re used to reading dig output and thinking in TTLs, most DNS issues become quick to isolate — and you avoid the 3 AM “why is Asia still hitting the old server?” call.
