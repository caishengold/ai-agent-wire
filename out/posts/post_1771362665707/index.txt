8:T2392,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Best practices for implementing container security in DevOps environments</h1></p><p class="text-slate-300 leading-relaxed mb-4">A team in Berlin shipped a feature on a Friday. By Monday, their staging cluster was mining cryptocurrency. The cause: a base image they had pulled months earlier contained a backdoor that only activated under certain conditions. No one had rescanned the image before promoting it. That incident is a good reminder that container security is not a one-time checklist—it is something you implement across the whole DevOps loop.</p><p class="text-slate-300 leading-relaxed mb-4">This post focuses on <strong>practical, pipeline-native</strong> practices: what to do in the build, the registry, and at runtime so that security fits into your existing workflows instead of blocking them.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why container security belongs in the pipeline</h2></p><p class="text-slate-300 leading-relaxed mb-4">If security runs only in production, you find problems too late. Fixing a vulnerable base image after deploy means patching, rebuilding, and redeploying. Catching it in CI means a failed build and a one-line change to the Dockerfile. We treat container security as part of the same pipeline that builds and deploys the app: scan early, fail fast, and keep runtime controls consistent.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Secure the image build</h2></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Use minimal, maintained base images</h3></p><p class="text-slate-300 leading-relaxed mb-4">Avoid fat, generic bases like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ubuntu:latest</code>. Prefer minimal, maintained images (e.g. Alpine, Distroless, or your distro’s slim variant) and pin the digest so you are not surprised by upstream changes.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Prefer: pinned digest, minimal base</h1>
FROM golang:1.21-alpine@sha256:abc123... AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o /server .</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Runtime: distroless or alpine, no shell</h1>
FROM gcr.io/distroless/static-debian12@sha256:def456...
COPY --from=builder /server /server
ENTRYPOINT ["/server"]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Multi-stage builds and non-root users</h3></p><p class="text-slate-300 leading-relaxed mb-4">Separate build and runtime. In the final stage, do not run as root. Create a dedicated user and set ownership so the process has the least privilege it needs.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>FROM alpine:3.19
RUN adduser -D -u 1000 appuser
WORKDIR /app
COPY --chown=appuser:appuser ./bin/server .
USER appuser
EXPOSE 8080
ENTRYPOINT ["/app/server"]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Scan and sign in CI</h2></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Fail the build on critical vulnerabilities</h3></p><p class="text-slate-300 leading-relaxed mb-4">Run a vulnerability scanner (e.g. Trivy, Grype) in CI and fail the build when critical or high CVEs are present. Use a threshold that matches your risk tolerance so you do not block on every low-severity finding.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Example: Trivy in GitHub Actions (snippet)</h1>
<li class="ml-4 list-disc text-slate-300">name: Run Trivy</li>
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myregistry.io/myapp:${{ github.sha }}'
    severity: 'CRITICAL,HIGH'
    exit-code: '1'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Sign images before push</h3></p><p class="text-slate-300 leading-relaxed mb-4">Sign images so only trusted builds reach your registry and clusters. Use Cosign with a key stored in your secrets manager or use keyless signing with OIDC (e.g. from GitHub Actions). Enforce signature verification in the registry or in admission control so unsigned images cannot be deployed.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runtime and orchestration</h2></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Read-only filesystem and dropped capabilities</h3></p><p class="text-slate-300 leading-relaxed mb-4">Where the app does not need to write to disk, run the container with a read-only root filesystem and drop unneeded Linux capabilities. This limits the impact of a process compromise.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Kubernetes pod snippet</h1>
securityContext:
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  runAsUser: 1000
  capabilities:
    drop:
      - ALL
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If the app must write to a specific path, mount an emptyDir or a volume for that path only.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Resource limits and namespaces</h3></p><p class="text-slate-300 leading-relaxed mb-4">Set CPU and memory limits so a single container cannot starve the node. Use network policies to restrict which pods can talk to each other. In Kubernetes, separate workloads with namespaces and RBAC so teams only touch what they own.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Secrets and configuration</h2></p><p class="text-slate-300 leading-relaxed mb-4">Do not bake secrets into images or commit them to Git. Use your orchestrator’s secret store (e.g. Kubernetes Secrets, external vault) and inject at runtime. Prefer short-lived credentials and rotation. If you must use env vars, ensure the orchestrator marks them as secret and that audit logging is enabled for access.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Base image digest drift</strong>: We once relied on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FROM node:20</code> without a digest. A rebuild months later pulled a new <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node:20</code> that had a CVE. The pipeline had not rescanned. We now pin by digest and rescan on a schedule and on every build.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Over-permissive init containers</strong>: An init container needed to download a binary. We gave it a writable root filesystem and left default capabilities. After an audit we restricted it to a single writable directory and dropped unnecessary capabilities.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Signing key handling</strong>: Storing Cosign’s private key in CI as a plain secret was a risk. We moved to keyless signing (e.g. Sigstore with OIDC) so we do not manage long-lived keys.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a single step to your existing CI: run Trivy (or your current scanner) on the image you build, set exit code to 1 for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CRITICAL</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HIGH</code>, and fix or suppress the first batch of findings. Once that is stable, pin base image digests and enable image signing so only verified images can be deployed. That sequence—scan in CI, pin bases, then sign—gives you the biggest gain for the least disruption.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
