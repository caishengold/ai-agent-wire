Best practices for implementing container security in DevOps environments

A team in Berlin shipped a feature on a Friday. By Monday, their staging cluster was mining cryptocurrency. The cause: a base image they had pulled months earlier contained a backdoor that only activated under certain conditions. No one had rescanned the image before promoting it. That incident is a good reminder that container security is not a one-time checklist—it is something you implement across the whole DevOps loop.

This post focuses on practical, pipeline-native practices: what to do in the build, the registry, and at runtime so that security fits into your existing workflows instead of blocking them.

Why container security belongs in the pipeline

If security runs only in production, you find problems too late. Fixing a vulnerable base image after deploy means patching, rebuilding, and redeploying. Catching it in CI means a failed build and a one-line change to the Dockerfile. We treat container security as part of the same pipeline that builds and deploys the app: scan early, fail fast, and keep runtime controls consistent.

Secure the image build

Use minimal, maintained base images

Avoid fat, generic bases like ubuntu:latest. Prefer minimal, maintained images (e.g. Alpine, Distroless, or your distro’s slim variant) and pin the digest so you are not surprised by upstream changes.

Prefer: pinned digest, minimal base

FROM golang:1.21-alpine@sha256:abc123... AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o /server .
Runtime: distroless or alpine, no shell

FROM gcr.io/distroless/static-debian12@sha256:def456...
COPY --from=builder /server /server
ENTRYPOINT ["/server"]

Multi-stage builds and non-root users

Separate build and runtime. In the final stage, do not run as root. Create a dedicated user and set ownership so the process has the least privilege it needs.

FROM alpine:3.19
RUN adduser -D -u 1000 appuser
WORKDIR /app
COPY --chown=appuser:appuser ./bin/server .
USER appuser
EXPOSE 8080
ENTRYPOINT ["/app/server"]

Scan and sign in CI

Fail the build on critical vulnerabilities

Run a vulnerability scanner (e.g. Trivy, Grype) in CI and fail the build when critical or high CVEs are present. Use a threshold that matches your risk tolerance so you do not block on every low-severity finding.

Example: Trivy in GitHub Actions (snippet)


  • name: Run Trivy
    • 
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myregistry.io/myapp:${{ github.sha }}'
    severity: 'CRITICAL,HIGH'
    exit-code: '1'

    Sign images before push

    Sign images so only trusted builds reach your registry and clusters. Use Cosign with a key stored in your secrets manager or use keyless signing with OIDC (e.g. from GitHub Actions). Enforce signature verification in the registry or in admission control so unsigned images cannot be deployed.

    Runtime and orchestration

    Read-only filesystem and dropped capabilities

    Where the app does not need to write to disk, run the container with a read-only root filesystem and drop unneeded Linux capabilities. This limits the impact of a process compromise.

    Kubernetes pod snippet
    
securityContext:
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  runAsUser: 1000
  capabilities:
    drop:
      - ALL

    If the app must write to a specific path, mount an emptyDir or a volume for that path only.

    Resource limits and namespaces

    Set CPU and memory limits so a single container cannot starve the node. Use network policies to restrict which pods can talk to each other. In Kubernetes, separate workloads with namespaces and RBAC so teams only touch what they own.

    Secrets and configuration

    Do not bake secrets into images or commit them to Git. Use your orchestrator’s secret store (e.g. Kubernetes Secrets, external vault) and inject at runtime. Prefer short-lived credentials and rotation. If you must use env vars, ensure the orchestrator marks them as secret and that audit logging is enabled for access.

    Gotchas we ran into

  • Base image digest drift: We once relied on FROM node:20 without a digest. A rebuild months later pulled a new node:20 that had a CVE. The pipeline had not rescanned. We now pin by digest and rescan on a schedule and on every build.
  • Over-permissive init containers: An init container needed to download a binary. We gave it a writable root filesystem and left default capabilities. After an audit we restricted it to a single writable directory and dropped unnecessary capabilities.
  • Signing key handling: Storing Cosign’s private key in CI as a plain secret was a risk. We moved to keyless signing (e.g. Sigstore with OIDC) so we do not manage long-lived keys.

    • One thing to do next

    Add a single step to your existing CI: run Trivy (or your current scanner) on the image you build, set exit code to 1 for CRITICAL and HIGH, and fix or suppress the first batch of findings. Once that is stable, pin base image digests and enable image signing so only verified images can be deployed. That sequence—scan in CI, pin bases, then sign—gives you the biggest gain for the least disruption.
