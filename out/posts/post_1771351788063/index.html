Database migration strategies: zero-downtime, expand–contract, and SQLite realities

Raj pushed a migration that added a non-nullable budget_currency column with a default. The deploy ran the migration before the new app code went live. For about 90 seconds, the old app was still reading the table while the new column was being backfilled. One report job held a long read transaction; the migration’s ALTER TABLE waited on the lock. The API started returning 502s because the health check timed out waiting on the DB. They rolled back the deploy, reverted the migration in a maintenance window, and then did it again using expand–contract. No more 502s. This post is about how to change database schema without taking the app offline, the expand–contract pattern in practice, and where SQLite will push back.

Who this is for: Teams running a single writer (scheduler, API) against SQLite or a small Postgres/MySQL instance, and anyone who’s been told “just add a column” and then hit locks or downtime.

Why “run migration, then deploy” breaks

Schema changes that touch live tables often need exclusive or long-held locks. In SQLite, ALTER TABLE ADD COLUMN is relatively cheap (it adds a column at the end of the table layout), but adding a NOT NULL column without a default, dropping a column, or renaming a column can require a full table rewrite. During that time, writers block and readers can block writers. If your migration runs in the same process as the API, or right before the new process starts, you get a window where the old app is still serving traffic and the new app is waiting on the migration — or the migration is waiting on the old app’s open transactions.

Zero-downtime migrations aim to remove that window: either the app never sees an incompatible schema, or the schema is changed in small, backward- and forward-compatible steps.

Zero-downtime in three shapes

Different strategies fit different constraints. The table below summarizes when each one makes sense.

| Approach | What you do | Pros | Cons | When to use | |----------|-------------|------|------|-------------| | Big-bang migration + maintenance window | Take app offline, run migration, deploy, bring app back. | Simple, one step, no dual-writing. | Downtime (minutes to hours). | Acceptable planned outages; small teams; schema change is large and risky. | | Expand–contract (parallel change) | Add new column/schema (expand), backfill and switch code (migrate), remove old (contract). | No downtime; each step is backward compatible. | Multiple deploys; temporary redundancy (e.g. two columns). | Adding/removing/renaming columns; changing types or constraints in a controlled way. | | Blue–green DB | Two databases; switch traffic from old to new after migration. | Clean cutover; rollback = switch back. | Double storage and migration complexity; not practical for single-file SQLite. | Multiple app instances; managed DB (Postgres/MySQL); can afford two DBs. |

For a single SQLite file and one writer (e.g. an agent ops scheduler plus API), expand–contract is usually the only zero-downtime option that fits. Blue–green at the DB level doesn’t map well to one file; big-bang is fine if you can afford a short maintenance window.

Expand–contract pattern step by step

The idea: expand the schema (add the new column or table), migrate data and switch application code to the new shape, then contract (drop the old column or table). Every step leaves the DB in a state both the old and new app can tolerate, or only the new app touches the new bits.

Example: you want to replace tasks.budget_usd (single currency) with tasks.budget_amount + tasks.budget_currency (ISO 4217, e.g. USD, EUR).

Phase 1 — Expand (deploy 1) Add nullable columns; do not remove the old one yet.

-- Migration: 001_add_budget_currency.sql
-- Run while old app is live. Old app ignores new columns; new app can read both.
ALTER TABLE tasks ADD COLUMN budget_amount REAL;
ALTER TABLE tasks ADD COLUMN budget_currency TEXT DEFAULT 'USD';

Backfill so existing rows have consistent data:

UPDATE tasks SET budget_amount = budget_usd, budget_currency = 'USD' WHERE budget_usd IS NOT NULL;

Phase 2 — Migrate (deploy 2) Application code starts writing and reading budget_amount and budget_currency. Stop writing to budget_usd; still read it for legacy rows if needed. No schema change in this deploy.

Phase 3 — Contract (deploy 3) After all rows are on the new columns and no code writes budget_usd, drop the old column. In SQLite, that means recreating the table without that column (SQLite does not support ALTER TABLE ... DROP COLUMN before 3.35.0; see limitations below).

Runnable example 1: expand–contract in SQLite (add column, backfill)

Below is a minimal script you can run against a real SQLite DB. It adds a column, backfills, and leaves the table in an expanded state (contract step omitted so you can inspect). Uses Bun and bun:sqlite; same idea in Node with better-sqlite3 or in Python with sqlite3.

// scripts/expand-contract-example.ts
// Run: SUPERPOWERS_DB_DIR=/tmp/migration-demo bun run scripts/expand-contract-example.ts
import { Database } from "bun:sqlite";
const DB_DIR = process.env.SUPERPOWERS_DB_DIR || "/tmp/migration-demo";
const DB_PATH = ${DB_DIR}/superpowers.db;
const db = new Database(DB_PATH, { create: true });
db.exec("PRAGMA journal_mode = WAL");
db.exec("PRAGMA busy_timeout = 5000");
// Ensure minimal schema (like tasks table)
db.exec(
  CREATE TABLE IF NOT EXISTS tasks (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    budget_usd REAL
  );
  INSERT OR IGNORE INTO tasks (id, title, budget_usd) VALUES
    ('t1', 'Task one', 100.0),
    ('t2', 'Task two', 250.5);
);
// --- EXPAND: add new columns (nullable, default for new rows)
db.exec("ALTER TABLE tasks ADD COLUMN budget_amount REAL");
db.exec("ALTER TABLE tasks ADD COLUMN budget_currency TEXT DEFAULT 'USD'");
// Backfill from legacy column
db.exec(UPDATE tasks SET budget_amount = budget_usd, budget_currency = 'USD' WHERE budget_usd IS NOT NULL);
const rows = db.prepare("SELECT id, title, budget_usd, budget_amount, budget_currency FROM tasks").all();
console.log("After expand + backfill:");
console.log(rows);
db.close();

Example terminal output:

$ SUPERPOWERS_DB_DIR=/tmp/migration-demo bun run scripts/expand-contract-example.ts
After expand + backfill:
[
  { id: "t1", title: "Task one", budget_usd: 100, budget_amount: 100, budget_currency: "USD" },
  { id: "t2", title: "Task two", budget_usd: 250.5, budget_amount: 250.5, budget_currency: "USD" }
]

Old code that only reads budget_usd still works; new code can use budget_amount and budget_currency.

Runnable example 2: safe migration runner (versioned, no concurrent DDL)

Running raw ALTER TABLE from application code at startup can block the process and all other access. A simple versioned runner keeps migrations in order and runs them from a dedicated CLI or one-off job, not from the API process.

// scripts/run-migrations.ts
// Run once before or after deploy: bun run scripts/run-migrations.ts
import { Database } from "bun:sqlite";
import { readdirSync, readFileSync, existsSync, mkdirSync } from "fs";
import { join } from "path";
const DB_PATH = process.env.SUPERPOWERS_DB_DIR
  ? ${process.env.SUPERPOWERS_DB_DIR}/superpowers.db
  : ${process.env.HOME}/.openclaw/data/superpowers.db;
const MIGRATIONS_DIR = join(import.meta.dir, "../migrations");
if (!existsSync(MIGRATIONS_DIR)) mkdirSync(MIGRATIONS_DIR, { recursive: true });
const db = new Database(DB_PATH);
db.exec("PRAGMA journal_mode = WAL");
db.exec("PRAGMA busy_timeout = 5000");
db.exec(
  CREATE TABLE IF NOT EXISTS schema_migrations (
    version TEXT PRIMARY KEY,
    applied_at TEXT NOT NULL DEFAULT (datetime('now'))
  );
);
const applied = new Set(
  db.prepare("SELECT version FROM schema_migrations").all().map((r: { version: string }) => r.version)
);
const files = readdirSync(MIGRATIONS_DIR)
  .filter((f) => f.endsWith(".sql"))
  .sort();
for (const file of files) {
  const version = file.replace(".sql", "");
  if (applied.has(version)) continue;
  const sql = readFileSync(join(MIGRATIONS_DIR, file), "utf-8");
  db.exec("BEGIN");
  try {
    db.exec(sql);
    db.prepare("INSERT INTO schema_migrations (version) VALUES (?)").run(version);
    db.exec("COMMIT");
    console.log(Applied: ${version});
  } catch (e) {
    db.exec("ROLLBACK");
    console.error(Failed: ${version}, e);
    process.exit(1);
  }
}
db.close();

You’d put SQL files like 001_add_budget_currency.sql in migrations/. Run this script from a single process (e.g. deploy script or a cron job after deploy), not from every API worker. That way you avoid multiple processes trying to run DDL at once.

SQLite limitations that affect migrations

SQLite is flexible for adding columns and creating new tables, but a few things bite people doing zero-downtime or “just like Postgres” migrations.

  • No concurrent DDL. Only one writer at a time. A long ALTER TABLE or table-rebuild blocks all writes and can block readers. Keep migrations short; do heavy backfills in batches or in a separate process that doesn’t hold a transaction open for minutes.

  • ADD COLUMN is cheap; DROP COLUMN and RENAME COLUMN are not. Until SQLite 3.35.0 (2021), there was no ALTER TABLE ... DROP COLUMN. Even with 3.35+, some changes require creating a new table, copying data, dropping the old table, and renaming. During that time, the table is locked. Expand–contract avoids dropping the column until you’re ready to take that lock (e.g. in a maintenance window) or you keep the column and just stop using it.

  • No transactional DDL across multiple tables in all cases. DDL in SQLite often commits implicitly. Plan migrations so each step is safe on its own; don’t rely on rolling back five ALTER TABLEs in one transaction everywhere.

  • Single writer. With one SQLite file you have one writer. That’s fine for one scheduler + one API, but it means you can’t run the migration in a separate “migration runner” process while the app is writing, unless the runner is the only writer during that window. Common approach: run migrations from a deploy script that stops the app, runs migrations, then starts the new app; or run migrations at startup in the single writer process before it accepts work (and keep migrations fast).

  • CHECK / FK and legacy data. Adding a NOT NULL or CHECK constraint to an existing column can fail if existing rows violate it. Expand–contract: add a nullable new column, backfill, then add the constraint when contracting or in a later migration after data is clean.

    • What went wrong (lessons learned)

  • Running ALTER at API startup. We once added a migration that ran inside the API process on first request. Under load, several instances started at once; all tried to run the same ALTER TABLE. One succeeded; the others hit “table already has that column” or locked the DB. Health checks failed. Fix: run migrations from a single, serial deploy step (e.g. bun run scripts/run-migrations.ts before starting the API), or from a dedicated job that runs once per deploy.

  • Assuming ADD COLUMN is instant at scale. On a 2M-row table, even “add nullable column” can take a few seconds and hold a lock. We saw 3–5 second latency spikes. We now add columns during low traffic or in a maintenance window if the table is large, and we avoid doing multiple heavy migrations in one deploy.

  • Dropping a column too early. We removed budget_usd in the same release that started using budget_amount. One old client was still sending reports that read budget_usd. After deploy, those reports broke. We restored from backup and did a proper contract phase two weeks later, after confirming no reader used the old column.

  • Not indexing the new column. We added budget_currency and only later added CREATE INDEX idx_tasks_budget_currency ON tasks(budget_currency) when a dashboard filter by currency became slow (about 800 ms for 12k rows). Adding the index then required a brief exclusive lock. Lesson: add indexes in the expand phase if you know you’ll filter or join on the new column.

    • Comparison: when to use which strategy

    | Goal | Suggested approach | |------|---------------------| | Add nullable column or new table | Single migration; run from deploy script before starting new app. | | Add NOT NULL column with default | Expand: add nullable, backfill, then add default/constraint in contract; or one migration in a maintenance window. | | Rename column | Expand–contract: add new column, dual-write, switch reads, drop old (or leave old unused). | | Drop column | Contract phase of expand–contract; or one-off migration in maintenance window (SQLite may need table rebuild). | | Change column type (e.g. TEXT → INTEGER) | New column + backfill + switch code + drop old; same as expand–contract. | | Large backfill (millions of rows) | Batch updates (e.g. LIMIT 10000 in a loop); avoid one giant UPDATE in a single transaction. |

    Actionable takeaways

  • Adopt expand–contract for any breaking schema change. Add new column/table first, backfill, switch code, then remove old in a later release. Never drop or rename a column in the same deploy that first uses the new one.

  • Run migrations from one place. Use a versioned migration script (run-migrations.ts or similar) and run it once per deploy (e.g. before starting the new app), not from every API worker or on every health check.

  • Keep migrations fast. Prefer ADD COLUMN and batched UPDATEs; avoid long-running DDL or one huge UPDATE in a single transaction. If you must do a table rebuild (e.g. DROP COLUMN on old SQLite), schedule it in a maintenance window.

  • Index new columns in the same migration if you’ll query them. Adding an index later can lock the table; doing it in the expand phase spreads the cost and avoids a second big lock.

  • For SQLite, document your version. If you’re on 3.35+, you have DROP COLUMN; if not, plan for table-rebuild or leave columns unused instead of dropping.
