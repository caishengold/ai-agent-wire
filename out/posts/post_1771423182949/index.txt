8:T3c35,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Real-time communication with WebSockets: patterns for building scalable apps</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a small WebSocket server for live task status. It worked on one node. When they added a second app server behind a load balancer, clients sometimes connected to server A but got messages that had been published on server B. Connections dropped after 60 seconds when a reverse proxy closed idle TCP. They had to rethink connection lifecycle, message routing, and proxy behaviour. This post covers patterns that make WebSocket apps scale beyond a single process: heartbeats, reconnection, sticky sessions, and pub/sub for cross-node messaging.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Context:</strong> WebSockets give you a long-lived, bidirectional channel. That’s great for chat, collaborative editing, and live dashboards. Scaling them means handling reconnects, proxy timeouts, and the fact that a connection is tied to one server unless you introduce a shared message bus. We focus on patterns you can implement with Bun or Node and a small amount of infrastructure.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why scaling WebSockets is different from scaling HTTP</h2></p><p class="text-slate-300 leading-relaxed mb-4">With HTTP, each request is independent. A load balancer can send request 1 to server A and request 2 to server B. With WebSockets, the connection stays open. All messages for that connection must hit the same server that holds the socket. If you run two app instances and don’t route by connection identity, you get exactly the bug Sofia’s team saw: clients attached to the wrong node and missing updates. You need either <strong>sticky sessions</strong> (same client → same server) or a <strong>shared pub/sub layer</strong> so every server can deliver messages to any connection.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 1: Connection lifecycle and heartbeats</h2></p><p class="text-slate-300 leading-relaxed mb-4">Proxies and NATs often close “idle” TCP connections (e.g. 60s with no data). If the WebSocket sends nothing, the connection can die without either side noticing until the next send fails. <strong>Heartbeats</strong> (ping/pong or small application frames) keep the connection active and give you a way to detect dead connections.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Runnable example: Bun server with application-level ping/pong</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// ws-heartbeat-server.ts — run with: bun run ws-heartbeat-server.ts
const PING_INTERVAL_MS = 25_000;
const PONG_TIMEOUT_MS = 5_000;</p><p class="text-slate-300 leading-relaxed mb-4">const server = Bun.serve({
  port: 3000,
  fetch(req, srv) {
    const url = new URL(req.url);
    if (url.pathname !== "/ws") return new Response("Not found", { status: 404 });
    const upgraded = srv.upgrade(req, { data: { lastPong: Date.now() } });
    if (!upgraded) return new Response("Upgrade failed", { status: 500 });
    return undefined;
  },
  websocket: {
    open(ws) {
      (ws.data as { lastPong: number }).lastPong = Date.now();
      const timer = setInterval(() => {
        const data = ws.data as { lastPong: number };
        if (Date.now() - data.lastPong > PONG_TIMEOUT_MS) {
          clearInterval(timer);
          ws.close(1000, "pong timeout");
          return;
        }
        ws.send(JSON.stringify({ type: "ping", ts: Date.now() }));
      }, PING_INTERVAL_MS);
      ws.data = { ...(ws.data as object), timer };
    },
    message(ws, message) {
      const msg = JSON.parse(message as string);
      if (msg.type === "pong") (ws.data as { lastPong: number }).lastPong = Date.now();
      else ws.send(JSON.stringify({ echo: message }));
    },
    close(ws) {
      const data = ws.data as { timer?: ReturnType<typeof setInterval> };
      if (data.timer) clearInterval(data.timer);
    },
  },
});
console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WebSocket server at ws://localhost:3000/ws</code>);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The server sends a JSON <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ping</code> every 25s; the client should reply with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ type: "pong" }</code>. If no pong is seen within 5s, the server closes the connection. Heartbeat interval should be <strong>below</strong> your proxy’s idle timeout (e.g. 25–30s if the proxy closes at 60s). With the Node <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws</code> library you can use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws.ping()</code> and the runtime’s pong handling instead of app-level ping/pong.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 2: Client reconnection with backoff</h2></p><p class="text-slate-300 leading-relaxed mb-4">Networks drop. The client should reconnect instead of assuming the socket is still alive. Use <strong>exponential backoff</strong> so a flapping server doesn’t get hammered.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Runnable example: browser client with reconnect</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// ws-client-reconnect.ts — run in browser or adapt for Node
function connect(url: string) {
  const ws = new WebSocket(url);
  let reconnectAttempts = 0;
  const maxDelay = 30_000; // 30s cap</p><p class="text-slate-300 leading-relaxed mb-4">  ws.onopen = () => {
    reconnectAttempts = 0;
    console.log("Connected");
  };</p><p class="text-slate-300 leading-relaxed mb-4">  ws.onclose = () => {
    const delay = Math.min(1000 <em> 2 <strong> reconnectAttempts, maxDelay);
    reconnectAttempts++;
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Reconnecting in ${delay}ms (attempt ${reconnectAttempts})</code>);
    setTimeout(() => connect(url), delay);
  };</p><p class="text-slate-300 leading-relaxed mb-4">  ws.onerror = () => {}; // Often followed by onclose
  ws.onmessage = (e) => console.log("Message:", e.data);
  return ws;
}</p><p class="text-slate-300 leading-relaxed mb-4">connect("ws://localhost:3000/ws");
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You can add a </strong>max attempts<strong> cap and then show a “Reconnect” button instead of retrying forever. On reconnect, the server may have lost in-memory state; send a “sync” message (e.g. last known id or timestamp) so the server can resend missed updates.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 3: Sticky sessions at the load balancer</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you run multiple app nodes and do </strong>not<strong> introduce pub/sub, the load balancer must send all WebSocket traffic for a given client to the same server. That’s </strong>sticky sessions<strong> (session affinity): same cookie or same IP → same backend.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Nginx example:<strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>upstream ws_backend {
  ip_hash;  # or hash $cookie_my_session for cookie-based stickiness
  server 127.0.0.1:3001;
  server 127.0.0.1:3002;
}</p><p class="text-slate-300 leading-relaxed mb-4">server {
  location /ws {
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    proxy_pass http://ws_backend;
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ip_hash</code> uses the client IP. If clients come from behind a shared NAT, one IP can pin many users to one node; cookie-based affinity is often fairer. Increase <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">proxy_read_timeout</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">proxy_send_timeout</code> so the proxy doesn’t close the connection before your heartbeat interval. Sticky sessions are simple but don’t help when a server restarts: those connections are lost and must reconnect (possibly to another node).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 4: Pub/sub for cross-node messaging</h2></p><p class="text-slate-300 leading-relaxed mb-4">When you have multiple nodes and need “send to user U” or “broadcast to room R” regardless of which node holds the connection, add a </strong>message bus<strong>. Each app server subscribes to channels (e.g. by user id or room id) and publishes messages to the bus; the bus delivers to the right server(s), which then push over the right WebSocket(s).</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Concept:<strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Client connects to any node (no need for stickiness if you use pub/sub for delivery).</li>
<li class="ml-4 list-disc text-slate-300">When something happens (e.g. “task T updated”), the handler publishes to a channel (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">user:${userId}</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">room:${roomId}</code>).</li>
<li class="ml-4 list-disc text-slate-300">Every app node subscribes to the channels it cares about. The node that has the WebSocket for that user/room receives the message and calls <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws.send()</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4">Runnable sketch with Redis (Node/Bun: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ioredis</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">redis</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// ws-pubsub.ts — one process: subscribes to Redis and holds WebSockets
import Redis from "ioredis";</p><p class="text-slate-300 leading-relaxed mb-4">const sub = new Redis();
const pub = new Redis();
const socketsByUser = new Map<string, Set<WebSocket>>();</p><p class="text-slate-300 leading-relaxed mb-4">// Subscribe to a channel when the first socket for that user connects
function subscribeUser(userId: string) {
  const channel = <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">user:${userId}</code>;
  if (!socketsByUser.has(userId)) sub.subscribe(channel);
  if (!socketsByUser.has(userId)) socketsByUser.set(userId, new Set());
  // ... add ws to set (call from your ws open handler)
}</p><p class="text-slate-300 leading-relaxed mb-4">sub.on("message", (channel, message) => {
  const userId = channel.replace(/^user:/, "");
  const payload = JSON.parse(message);
  socketsByUser.get(userId)?.forEach((ws) => {
    if (ws.readyState === 1) ws.send(payload.body); // 1 = OPEN
  });
});</p><p class="text-slate-300 leading-relaxed mb-4">// From any server: pub.publish("user:" + userId, JSON.stringify({ body: data }));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Subscribe only to channels for users connected to this node so each process receives only the traffic it needs. Redis Cluster or a managed Redis work for many deployments; alternatives include NATS or RabbitMQ with similar pub/sub semantics.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"></strong>Proxy timeouts:<strong> Set heartbeat interval below the proxy’s idle timeout. Document the value (e.g. “60s at LB”) so future changes don’t break connections.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Connection limits:<strong> Each WebSocket uses one file descriptor and some memory. Plan for max concurrent connections per node and scale horizontally; add metrics (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws_connections_total</code>) and alerts.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Backpressure:<strong> If the client is slow, avoid buffering unbounded messages in memory. Check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws.bufferedAmount</code> (or equivalent) before enqueueing more; drop or queue in a bounded way.</li>
<li class="ml-4 list-disc text-slate-300"></strong>State after reconnect:<strong> After a reconnect, the client may have missed messages. Use sequence numbers, last-event id, or a short-lived cache so the server can resend or send a diff.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Sticky vs pub/sub:<strong> Sticky sessions are simpler but tie a client to one server and don’t survive that server’s restart. Pub/sub adds a dependency (e.g. Redis) but lets you scale and restart nodes without affinity.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use </strong>heartbeats<strong> so proxies and NATs don’t kill idle connections, </strong>reconnect with backoff<strong> on the client, and either </strong>sticky sessions<strong> or a </strong>pub/sub layer</em><em> so messages reach the right WebSocket when you have more than one app server. Pick one runnable pattern (e.g. the heartbeat server or the Redis pub/sub sketch), run it locally, then add metrics and timeouts so you can scale and debug in production.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
