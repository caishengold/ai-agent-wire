8:T446c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Comparative analysis of API design patterns for modern web services</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a REST API for their order service. Three months later, the mobile app needed “just order id, status, and line count” per order. Every REST response was sending full line items and customer data. They added query params (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">?fields=id,status,lineCount</code>), then a second endpoint, then a third. By the time they looked at GraphQL, they had four ways to fetch “an order” and no clear rule for when to use which. Picking an API design pattern early—and sticking to it—saves that kind of mess. This post compares REST, GraphQL, and RPC-style APIs with runnable examples and a clear “when to use what.”</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the pattern matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs are contracts. The pattern you choose affects how clients request data, how you evolve the contract, and how much complexity you take on. Get it wrong and you either over-fetch (mobile pays for bytes it never uses) or under-serve (too many round-trips, or endpoints that don’t match how the client thinks). We’ll compare three patterns used in modern web services: <strong>REST</strong> (resource-oriented HTTP), <strong>GraphQL</strong> (query language over a single endpoint), and <strong>RPC</strong> (procedure calls: JSON-RPC or gRPC).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 1: REST (resource-oriented)</h2></p><p class="text-slate-300 leading-relaxed mb-4">REST models the system as resources identified by URLs. Clients use HTTP verbs (GET, POST, PUT, PATCH, DELETE) and get full representations. It’s the default for public and internal HTTP APIs.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Characteristics:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">One URL per resource or collection (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/orders</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/orders/123</code>).</li>
<li class="ml-4 list-disc text-slate-300">Responses are typically full documents; sparse fields need query params or separate endpoints.</li>
<li class="ml-4 list-disc text-slate-300">Cacheable by URL; status codes and headers drive client behavior.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: small REST API with Node’s built-in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">http</code> module. No extra dependencies. Two routes—list orders and get one order—return JSON. Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">rest-orders.mjs</code> and run with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node rest-orders.mjs</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// rest-orders.mjs — run: node rest-orders.mjs
const http = require("http");</p><p class="text-slate-300 leading-relaxed mb-4">const orders = [
  {
    id: "ord-1",
    status: "shipped",
    lineCount: 2,
    customerId: "cust-1",
    lines: [
      { sku: "WIDGET-A", qty: 3 },
      { sku: "WIDGET-B", qty: 1 },
    ],
  },
];</p><p class="text-slate-300 leading-relaxed mb-4">const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");
  const path = req.url || "/";
  const idMatch = path.match(/^\/orders\/([^/]+)$/);</p><p class="text-slate-300 leading-relaxed mb-4">  if (req.method === "GET" && path === "/orders") {
    res.end(JSON.stringify(orders));
    return;
  }

      res.end(JSON.stringify({ error: "Not found" }));
      return;
    }
    res.end(JSON.stringify(order));
    return;

  res.statusCode = 404;
  res.end(JSON.stringify({ error: "Not found" }));

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ node rest-orders.mjs
REST server on http://localhost:3000</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">In another terminal:</h1>
$ curl -s http://localhost:3000/orders/ord-1
{"id":"ord-1","status":"shipped","lineCount":2,"customerId":"cust-1","lines":[{"sku":"WIDGET-A","qty":3},{"sku":"WIDGET-B","qty":1}]}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">REST is simple to implement and to cache. The downside: if the client only needs <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lineCount</code>, it still gets the whole payload unless you add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">?fields=...</code> or more endpoints.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 2: GraphQL (query-defined response)</h2></p><p class="text-slate-300 leading-relaxed mb-4">GraphQL exposes a schema and a single endpoint. The client sends a query that describes exactly the fields it wants; the server returns a JSON object that mirrors that shape. Good fit when many clients need different slices of the same data.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Characteristics:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">One endpoint (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">POST /graphql</code>); operation type and selection set define the response.</li>
<li class="ml-4 list-disc text-slate-300">No over-fetching by design; new fields can be added without new URLs.</li>
<li class="ml-4 list-disc text-slate-300">Requires schema design, resolvers, and attention to N+1 and auth.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: same “orders” data exposed via GraphQL. The client asks only for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lineCount</code>; the server returns only those. Install the GraphQL library once: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm init -y && npm install graphql</code>, then run with Node. Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">graphql-orders.mjs</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// graphql-orders.mjs — run: node graphql-orders.mjs (after: npm install graphql)
const http = require("http");
const { graphql, buildSchema } = require("graphql");</p><p class="text-slate-300 leading-relaxed mb-4">const orderData = [
  {
    id: "ord-1",
    status: "shipped",
    lineCount: 2,
    customerId: "cust-1",
    lines: [
      { sku: "WIDGET-A", qty: 3 },
      { sku: "WIDGET-B", qty: 1 },
    ],
  },
];</p><p class="text-slate-300 leading-relaxed mb-4">const schema = buildSchema(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  type Order {
    id: String!
    status: String!
    lineCount: Int!
  }
  type Query {
    orders: [Order!]!
    order(id: String!): Order
  }
</code>);</p><p class="text-slate-300 leading-relaxed mb-4">const root = {
  orders: () =>
    orderData.map((o) => ({ id: o.id, status: o.status, lineCount: o.lineCount })),
  order: ({ id }) => {
    const o = orderData.find((x) => x.id === id);
    return o ? { id: o.id, status: o.status, lineCount: o.lineCount } : null;
  },
};</p><p class="text-slate-300 leading-relaxed mb-4">const server = http.createServer(async (req, res) => {
  if (req.method !== "POST" || req.url !== "/graphql") {
    res.statusCode = 404;
    res.end(JSON.stringify({ error: "Not found" }));
    return;
  }
  const chunks = [];
  for await (const chunk of req) chunks.push(chunk);
  const body = JSON.parse(Buffer.concat(chunks).toString());
  const result = await graphql({
    schema,
    source: body.query,
    rootValue: root,
    variableValues: body.variables,
  });
  res.setHeader("Content-Type", "application/json");
  res.end(JSON.stringify(result));
});</p><p class="text-slate-300 leading-relaxed mb-4">server.listen(4000, () => console.log("GraphQL server on http://localhost:4000"));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ npm init -y && npm install graphql
$ node graphql-orders.mjs
GraphQL server on http://localhost:4000</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">In another terminal — request only 3 fields:</h1>
$ curl -s -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ order(id: \"ord-1\") { id status lineCount } }"}'
{"data":{"order":{"id":"ord-1","status":"shipped","lineCount":2}}}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The response contains only <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lineCount</code>; no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">customerId</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">lines</code>. The mobile app gets exactly three fields with one request and no extra endpoints.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pattern 3: RPC (procedure calls)</h2></p><p class="text-slate-300 leading-relaxed mb-4">RPC-style APIs expose actions or procedures instead of resources. Call names and parameters are fixed; the “shape” of the system is “methods” rather than “nouns.” JSON-RPC and gRPC are the common options; we’ll keep the comparison at the idea level and use a minimal JSON-RPC-style example.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Characteristics:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">One endpoint; method name + params identify the operation.</li>
<li class="ml-4 list-disc text-slate-300">No inherent notion of “resource” or HTTP caching; often used for internal or performance-critical backends.</li>
<li class="ml-4 list-disc text-slate-300">gRPC adds binary encoding, streaming, and strong typing via protobuf; JSON-RPC is simpler and text-based.</li></p><p class="text-slate-300 leading-relaxed mb-4">Conceptually, the same “get order” operation looks like:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>POST /rpc
{"jsonrpc":"2.0","id":1,"method":"order.get","params":{"id":"ord-1"}}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">RPC fits when the team thinks in “operations” (e.g. “placeOrder”, “cancelOrder”) and when you want a single transport (e.g. gRPC) for speed and code generation across services.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison table</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | REST | GraphQL | RPC (e.g. JSON-RPC / gRPC) |
|--------|------|--------|----------------------------|
| <strong>Data shape</strong> | Server-defined; one or few representations per URL | Client-defined per request | Server-defined per method |
| <strong>Over-fetching</strong> | Common unless you add fields/params or many endpoints | Avoided by design | Depends on method return type |
| <strong>Caching</strong> | HTTP cache by URL; straightforward | Harder; often not cacheable by default | Not HTTP-cacheable; app-level only |
| <strong>Learning curve</strong> | Low; familiar to most devs | Medium; schema + resolvers + tooling | Medium (JSON-RPC) to high (gRPC, protobuf) |
| <strong>Best for</strong> | Public APIs, CRUD, cache-friendly reads | Many clients with different data needs, mobile/frontend-heavy | Internal services, performance, streaming |
| <strong>Evolution</strong> | New URLs or new fields; versioning common | Add fields/deprecate; avoid breaking query shape | New methods or params; versioning by method/contract |</p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>REST</strong> when you want broad compatibility, simple caching, and straightforward documentation. Use <strong>GraphQL</strong> when multiple clients need different views of the same data and you’re willing to invest in schema and resolvers. Use <strong>RPC</strong> (especially gRPC) when you care about throughput, streaming, and strong contracts between your own services.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">We shipped REST first and added “light” endpoints (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">GET /orders/:id/summary</code>) when the mobile team complained about payload size. That gave us two ways to get an order: full and summary. Then analytics wanted “order id + total amount,” so we added a third. We had no single rule for “which endpoint for which client,” and our OpenAPI spec became a long list of similar-looking routes. We also didn’t document response sizes; the “summary” endpoint still returned ~2 KB per order because we kept adding fields. After 6 months we introduced a small GraphQL layer for internal and partner clients; migration took two sprints and we had to fix N+1 in resolvers (orders → lines) with a DataLoader. <strong>Takeaway:</strong> choose one primary pattern per surface (e.g. REST for public, GraphQL for a BFF). If you add a second style, do it deliberately and document when each is used. Measure response sizes and query complexity so “light” stays light.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Decide per surface:</strong> Use one dominant pattern per API surface (e.g. REST for public HTTP, GraphQL for a BFF (backend-for-frontend) or partner API, gRPC for service-to-service). Avoid mixing REST and GraphQL for the same “product” API without a clear boundary.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Prototype the main client:</strong> Build a minimal version of your most important client (e.g. mobile list + detail) against each candidate pattern. Compare number of requests, payload size, and code clarity.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Lock in caching and versioning early:</strong> For REST, define cache headers and a versioning strategy (e.g. path or header) before v1. For GraphQL, define deprecation rules and consider persisted queries or allowlists to limit abuse.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document “which endpoint for what”:</strong> If you have both “full” and “summary” or multiple ways to get the same entity, add a short doc or table: which client uses which path and why. It prevents the “four ways to get an order” situation.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Measure:</strong> Log response sizes and, for GraphQL, query depth/field count. Set simple alerts so “light” endpoints don’t grow to full-document size over time.</li></p><p class="text-slate-300 leading-relaxed mb-4">If you’re starting a new service today, default to REST for simplicity and cacheability; add GraphQL or RPC only when you have a concrete need (e.g. many different client shapes or high-throughput internal calls) and the team capacity to maintain the extra stack.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
