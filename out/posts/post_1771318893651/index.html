Comparative analysis of API design patterns for modern web services

Sofia’s team shipped a REST API for their order service. Three months later, the mobile app needed “just order id, status, and line count” per order. Every REST response was sending full line items and customer data. They added query params (?fields=id,status,lineCount), then a second endpoint, then a third. By the time they looked at GraphQL, they had four ways to fetch “an order” and no clear rule for when to use which. Picking an API design pattern early—and sticking to it—saves that kind of mess. This post compares REST, GraphQL, and RPC-style APIs with runnable examples and a clear “when to use what.”

Why the pattern matters

APIs are contracts. The pattern you choose affects how clients request data, how you evolve the contract, and how much complexity you take on. Get it wrong and you either over-fetch (mobile pays for bytes it never uses) or under-serve (too many round-trips, or endpoints that don’t match how the client thinks). We’ll compare three patterns used in modern web services: REST (resource-oriented HTTP), GraphQL (query language over a single endpoint), and RPC (procedure calls: JSON-RPC or gRPC).

Pattern 1: REST (resource-oriented)

REST models the system as resources identified by URLs. Clients use HTTP verbs (GET, POST, PUT, PATCH, DELETE) and get full representations. It’s the default for public and internal HTTP APIs.

Characteristics:

  • One URL per resource or collection (e.g. /orders, /orders/123).
  • Responses are typically full documents; sparse fields need query params or separate endpoints.
  • Cacheable by URL; status codes and headers drive client behavior.

    • Example: small REST API with Node’s built-in http module. No extra dependencies. Two routes—list orders and get one order—return JSON. Save as rest-orders.mjs and run with node rest-orders.mjs.

    // rest-orders.mjs — run: node rest-orders.mjs
const http = require("http");
    const orders = [
  {
    id: "ord-1",
    status: "shipped",
    lineCount: 2,
    customerId: "cust-1",
    lines: [
      { sku: "WIDGET-A", qty: 3 },
      { sku: "WIDGET-B", qty: 1 },
    ],
  },
];
    const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");
  const path = req.url || "/";
  const idMatch = path.match(/^\/orders\/([^/]+)$/);
      if (req.method === "GET" && path === "/orders") {
    res.end(JSON.stringify(orders));
    return;
  }
  if (req.method === "GET" && idMatch) {
    const order = orders.find((o) => o.id === idMatch[1]);
    if (!order) {
      res.statusCode = 404;
      res.end(JSON.stringify({ error: "Not found" }));
      return;
    }
    res.end(JSON.stringify(order));
    return;
  }
  res.statusCode = 404;
  res.end(JSON.stringify({ error: "Not found" }));
});
    server.listen(3000, () => console.log("REST server on http://localhost:3000"));

    Terminal:

    $ node rest-orders.mjs
REST server on http://localhost:3000
    In another terminal:
    
$ curl -s http://localhost:3000/orders/ord-1
{"id":"ord-1","status":"shipped","lineCount":2,"customerId":"cust-1","lines":[{"sku":"WIDGET-A","qty":3},{"sku":"WIDGET-B","qty":1}]}

    REST is simple to implement and to cache. The downside: if the client only needs id, status, and lineCount, it still gets the whole payload unless you add ?fields=... or more endpoints.

    Pattern 2: GraphQL (query-defined response)

    GraphQL exposes a schema and a single endpoint. The client sends a query that describes exactly the fields it wants; the server returns a JSON object that mirrors that shape. Good fit when many clients need different slices of the same data.

    Characteristics:

  • One endpoint (e.g. POST /graphql); operation type and selection set define the response.
  • No over-fetching by design; new fields can be added without new URLs.
  • Requires schema design, resolvers, and attention to N+1 and auth.

    • Example: same “orders” data exposed via GraphQL. The client asks only for id, status, and lineCount; the server returns only those. Install the GraphQL library once: npm init -y && npm install graphql, then run with Node. Save as graphql-orders.mjs.

    // graphql-orders.mjs — run: node graphql-orders.mjs (after: npm install graphql)
const http = require("http");
const { graphql, buildSchema } = require("graphql");
    const orderData = [
  {
    id: "ord-1",
    status: "shipped",
    lineCount: 2,
    customerId: "cust-1",
    lines: [
      { sku: "WIDGET-A", qty: 3 },
      { sku: "WIDGET-B", qty: 1 },
    ],
  },
];
    const schema = buildSchema(
  type Order {
    id: String!
    status: String!
    lineCount: Int!
  }
  type Query {
    orders: [Order!]!
    order(id: String!): Order
  }
);
    const root = {
  orders: () =>
    orderData.map((o) => ({ id: o.id, status: o.status, lineCount: o.lineCount })),
  order: ({ id }) => {
    const o = orderData.find((x) => x.id === id);
    return o ? { id: o.id, status: o.status, lineCount: o.lineCount } : null;
  },
};
    const server = http.createServer(async (req, res) => {
  if (req.method !== "POST" || req.url !== "/graphql") {
    res.statusCode = 404;
    res.end(JSON.stringify({ error: "Not found" }));
    return;
  }
  const chunks = [];
  for await (const chunk of req) chunks.push(chunk);
  const body = JSON.parse(Buffer.concat(chunks).toString());
  const result = await graphql({
    schema,
    source: body.query,
    rootValue: root,
    variableValues: body.variables,
  });
  res.setHeader("Content-Type", "application/json");
  res.end(JSON.stringify(result));
});
    server.listen(4000, () => console.log("GraphQL server on http://localhost:4000"));

    Terminal:

    $ npm init -y && npm install graphql
$ node graphql-orders.mjs
GraphQL server on http://localhost:4000
    In another terminal — request only 3 fields:
    
$ curl -s -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ order(id: \"ord-1\") { id status lineCount } }"}'
{"data":{"order":{"id":"ord-1","status":"shipped","lineCount":2}}}

    The response contains only id, status, and lineCount; no customerId or lines. The mobile app gets exactly three fields with one request and no extra endpoints.

    Pattern 3: RPC (procedure calls)

    RPC-style APIs expose actions or procedures instead of resources. Call names and parameters are fixed; the “shape” of the system is “methods” rather than “nouns.” JSON-RPC and gRPC are the common options; we’ll keep the comparison at the idea level and use a minimal JSON-RPC-style example.

    Characteristics:

  • One endpoint; method name + params identify the operation.
  • No inherent notion of “resource” or HTTP caching; often used for internal or performance-critical backends.
  • gRPC adds binary encoding, streaming, and strong typing via protobuf; JSON-RPC is simpler and text-based.

    • Conceptually, the same “get order” operation looks like:

    POST /rpc
{"jsonrpc":"2.0","id":1,"method":"order.get","params":{"id":"ord-1"}}

    RPC fits when the team thinks in “operations” (e.g. “placeOrder”, “cancelOrder”) and when you want a single transport (e.g. gRPC) for speed and code generation across services.

    Comparison table

    | Aspect | REST | GraphQL | RPC (e.g. JSON-RPC / gRPC) | |--------|------|--------|----------------------------| | Data shape | Server-defined; one or few representations per URL | Client-defined per request | Server-defined per method | | Over-fetching | Common unless you add fields/params or many endpoints | Avoided by design | Depends on method return type | | Caching | HTTP cache by URL; straightforward | Harder; often not cacheable by default | Not HTTP-cacheable; app-level only | | Learning curve | Low; familiar to most devs | Medium; schema + resolvers + tooling | Medium (JSON-RPC) to high (gRPC, protobuf) | | Best for | Public APIs, CRUD, cache-friendly reads | Many clients with different data needs, mobile/frontend-heavy | Internal services, performance, streaming | | Evolution | New URLs or new fields; versioning common | Add fields/deprecate; avoid breaking query shape | New methods or params; versioning by method/contract |

    Use REST when you want broad compatibility, simple caching, and straightforward documentation. Use GraphQL when multiple clients need different views of the same data and you’re willing to invest in schema and resolvers. Use RPC (especially gRPC) when you care about throughput, streaming, and strong contracts between your own services.

    What went wrong (lessons learned)

    We shipped REST first and added “light” endpoints (GET /orders/:id/summary) when the mobile team complained about payload size. That gave us two ways to get an order: full and summary. Then analytics wanted “order id + total amount,” so we added a third. We had no single rule for “which endpoint for which client,” and our OpenAPI spec became a long list of similar-looking routes. We also didn’t document response sizes; the “summary” endpoint still returned ~2 KB per order because we kept adding fields. After 6 months we introduced a small GraphQL layer for internal and partner clients; migration took two sprints and we had to fix N+1 in resolvers (orders → lines) with a DataLoader. Takeaway: choose one primary pattern per surface (e.g. REST for public, GraphQL for a BFF). If you add a second style, do it deliberately and document when each is used. Measure response sizes and query complexity so “light” stays light.

    Actionable takeaways

  • Decide per surface: Use one dominant pattern per API surface (e.g. REST for public HTTP, GraphQL for a BFF (backend-for-frontend) or partner API, gRPC for service-to-service). Avoid mixing REST and GraphQL for the same “product” API without a clear boundary.
  • Prototype the main client: Build a minimal version of your most important client (e.g. mobile list + detail) against each candidate pattern. Compare number of requests, payload size, and code clarity.
  • Lock in caching and versioning early: For REST, define cache headers and a versioning strategy (e.g. path or header) before v1. For GraphQL, define deprecation rules and consider persisted queries or allowlists to limit abuse.
  • Document “which endpoint for what”: If you have both “full” and “summary” or multiple ways to get the same entity, add a short doc or table: which client uses which path and why. It prevents the “four ways to get an order” situation.
  • Measure: Log response sizes and, for GraphQL, query depth/field count. Set simple alerts so “light” endpoints don’t grow to full-document size over time.

    • If you’re starting a new service today, default to REST for simplicity and cacheability; add GraphQL or RPC only when you have a concrete need (e.g. many different client shapes or high-throughput internal calls) and the team capacity to maintain the extra stack.
