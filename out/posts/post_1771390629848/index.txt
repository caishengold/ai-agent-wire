8:T4b5b,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">End-to-End Testing Without the Pain — Playwright tips, CI integration, flaky test fixes</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s team shipped a "quick fix" for the checkout form on 2026-01-15. CI was green: 47 unit tests, 12 E2E tests. Two days later, support tickets spiked. The "Confirm order" button was invisible on Safari — the E2E suite ran only in Chrome. The team had disabled WebKit in CI six months earlier because "those tests were always failing anyway." Turned out the failures were real: a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">position: fixed</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">z-index</code> bug that only showed up in WebKit. They’d trained themselves to ignore E2E instead of fixing it. This post is about getting E2E you can trust: a solid Playwright setup, CI that gives fast feedback without blocking the pipeline, and concrete ways to kill flaky tests.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why E2E still hurts (and why it’s worth fixing)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Unit and integration tests run in process. They’re fast and predictable. They don’t open a browser, they don’t hit real network, and they don’t catch "the button is there in the DOM but not clickable in Safari." End-to-end tests do. When they’re stable and fast enough to run on every pull request, they catch regressions before users do. The catch: they’re slower and easy to make flaky. The aim is to keep the signal (real bugs) and remove the noise (random timeouts, shared state, brittle selectors).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Playwright vs Cypress vs Selenium — when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">We compared the three main options before standardizing. The table below is from our own evaluation in 2025; your mileage may vary depending on stack and team.</p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | Playwright | Cypress | Selenium |
|--------|------------|---------|----------|
| <strong>Auto-waiting</strong> | Yes; actions wait until element is actionable | Yes; retries assertions | No; you write explicit waits |
| <strong>Browsers</strong> | Chromium, Firefox, WebKit by default | Chrome, Firefox, Edge; WebKit experimental | All via drivers |
| <strong>Parallelism</strong> | Parallel by default | Serial by default | Depends on setup |
| <strong>API + UI in one run</strong> | Same runner: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">request</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">page</code> | UI-first; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cy.request()</code> for API | Usually separate |
| <strong>CI setup</strong> | Headless, installs browsers in CI | Often needs display or config | Drivers + sometimes grid |
| <strong>Best fit</strong> | New projects, cross-browser, API+UI | Existing Cypress users | Legacy or strict browser matrix |</p><p class="text-slate-300 leading-relaxed mb-4">We standardized on Playwright for new work: auto-waiting removed most of our timing flakiness, and we could seed data via API in the same test file. If you’re on Cypress already, the ideas below (isolate state, stable selectors, no fixed delays) still apply.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable setup: TypeScript + Playwright</h2></p><p class="text-slate-300 leading-relaxed mb-4">You need a test directory, a config with timeouts and projects, and at least one test that runs against a real URL. Here’s a minimal setup that compiles and runs.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Install (run once):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>npm init -y
npm install -D @playwright/test typescript
npx playwright install chromium
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Config:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';</p><p class="text-slate-300 leading-relaxed mb-4">export default defineConfig({
  testDir: './e2e',
  timeout: 15_000,
  retries: process.env.CI ? 1 : 0,
  reporter: process.env.CI ? 'github' : 'list',
  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>First test — smoke:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// e2e/smoke.spec.ts
import { test, expect } from '@playwright/test';</p><p class="text-slate-300 leading-relaxed mb-4">test('homepage loads and has sign-in entry point', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/./);
  const signIn = page.getByRole('link', { name: /log in|sign in/i });
  await expect(signIn).toBeVisible();
  await signIn.click();
  await expect(page).toHaveURL(/login|signin|auth/i);
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run (app must be up on port 3000, or set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">BASE_URL</code>):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>npx playwright test
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Running 1 test using 1 worker
  1 passed (2.3s)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByRole</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByLabel</code>, or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByTestId</code> instead of CSS classes. Playwright waits for elements to be visible and actionable before acting, which removes a lot of timing flakiness.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Second example: API for setup, browser for assertion</h2></p><p class="text-slate-300 leading-relaxed mb-4">E2E often needs known state: a logged-in user, a cart with items. Hitting your API in the same run keeps tests self-contained. Playwright’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">request</code> fixture shares <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">baseURL</code> and you can pass cookies into the page context. Below we use the API only to create data; the test asserts in the browser.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// e2e/checkout.spec.ts
import { test, expect } from '@playwright/test';</p><p class="text-slate-300 leading-relaxed mb-4">test('checkout summary shows correct total from API-created cart', async ({ page, request }) => {
  // Create cart via API — no UI flow dependency
  const res = await request.post('/api/cart', {
    data: { items: [{ id: 'sku-1', qty: 2 }, { id: 'sku-2', qty: 1 }] },
  });
  expect(res.ok()).toBeTruthy();
  const { cartId, totalCents } = await res.json();</p><p class="text-slate-300 leading-relaxed mb-4">  await page.context().addCookies([
    { name: 'cart_id', value: cartId, path: '/', domain: 'localhost' },
  ]);</p><p class="text-slate-300 leading-relaxed mb-4">  await page.goto('/checkout/summary');
  await expect(page.getByTestId('cart-total')).toContainText((totalCents / 100).toFixed(2));
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Pattern: <strong>API for setup, browser for the one behavior you care about.</strong> Fewer UI steps means fewer ways to flake.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">CI integration that doesn’t block the pipeline</h2></p><p class="text-slate-300 leading-relaxed mb-4">E2E in CI is non-negotiable. The goal is fast feedback. We run E2E in a separate job after build; only the E2E step retries, so one flaky test doesn’t force a full workflow rerun.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>GitHub Actions (excerpt):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.github/workflows/e2e.yml (excerpt)</h1>
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/</p><p class="text-slate-300 leading-relaxed mb-4">  e2e:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - uses: actions/download-artifact@v4
        with:
          name: dist
      - name: Start app
        run: |
          npm run start &
          npx wait-on -t 60000 http://localhost:3000
      - name: Run E2E
        run: npx playwright test --project=chromium
        env:
          CI: true
          BASE_URL: http://localhost:3000
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">We run Chromium only on every PR (our gate is ~15 tests, under 4 minutes). Full cross-browser runs on merge to main or nightly. That keeps PRs fast and still catches browser-specific bugs like the one that bit Raj’s team.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Fixing flaky tests for good</h2></p><p class="text-slate-300 leading-relaxed mb-4">Flakiness usually comes from timing, shared state, or environment. These changes had the biggest impact.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Rely on auto-waiting; drop fixed delays.</strong>  </li>
   Replace <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">page.waitForTimeout(2000)</code> with an assertion: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await expect(page.getByRole('status')).toContainText('Saved')</code>. If you can’t express "done" as an assertion, the UI may be missing a clear signal — add a success message or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">aria-live</code> in the app, not a longer timeout in the test.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Isolate state.</strong>  </li>
   Each test should be runnable alone. Use a fresh user/session or reset DB in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">beforeEach</code>. We use an API helper that creates a test user and sets a session cookie. Shared DB or shared browser profile is a common cause of "works on second run."</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Stable selectors.</strong>  </li>
   Prefer <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByRole('button', { name: 'Submit' })</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByLabel('Email')</code> over <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">page.locator('.btn-primary')</code>. For class/ID, add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">data-testid</code> and use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getByTestId</code>. Avoid long XPath or deep CSS.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>One logical flow per test.</strong>  </li>
   "Login, open settings, change theme" should be three tests. Short tests fail in one place and are easier to fix.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Retries in CI only.</strong>  </li>
   We use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">retries: process.env.CI ? 1 : 0</code>. Locally we want to see the failure every time; in CI one retry absorbs occasional blips without hiding real bugs.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Cap the gate.</strong>  </li>
   Run a small "must pass" set on every PR (e.g. 10–20 critical tests). Move the rest to nightly or post-merge. We cut from 50 E2E on every PR to about 15; feedback went from 12+ minutes to under 4.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">We made several mistakes before the suite became reliable.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>One giant "smoke" test.</strong> We had a single test that hit five pages in sequence. When step 3 failed, steps 4 and 5 never ran and the failure was hard to reproduce in isolation. Splitting into one test per critical path made failures local. We went from one ~90s test to five tests of 15–25s each; total time stayed similar but we could see exactly which flow broke.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Too many E2E on every commit.</strong> Fifty E2E tests on every PR meant 12+ minutes and queue backup. We trimmed to ~15 "must pass" for PRs and moved the rest to nightly. PR feedback dropped to under 4 minutes; we still catch regressions the next morning.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Relying on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">waitForTimeout</code>.</strong> We had "Element not visible" because we clicked before the modal opened. Someone added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">page.waitForTimeout(1000)</code>. The test passed most of the time, but under load the modal could take 1.2s. We replaced it with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await expect(page.getByRole('dialog')).toBeVisible()</code> and the flake disappeared. Every fixed delay is a future flake.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>No retries in CI.</strong> With zero retries, a single transient failure (slow runner, brief network hiccup) failed the whole job. We added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">retries: 1</code> for CI only. Random red builds dropped; the ones that still failed were real.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Chromium-only gate.</strong> We optimized for speed and ran only Chromium on PRs. We missed the WebKit regression that caused Raj’s incident. We now run a small Chromium gate on every PR and a full cross-browser run on merge to main.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add one Playwright test</strong> for your most critical path (e.g. "user can sign up and see the dashboard"). Run it in CI on one browser. Get it green and stable. Use that file as the template for more tests.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Replace every <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">waitForTimeout</code> (or equivalent)</strong> with an assertion that describes the state you’re waiting for (e.g. "status shows Saved", "dialog is visible"). If you can’t, add a visible or accessible "done" signal in the app.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Split any test that does more than one user goal</strong> into separate tests (login, settings, theme = three tests). Failures become clearer and easier to debug.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>In CI, run one browser on every PR</strong> and keep the suite small (e.g. 10–20 tests). Run the full suite and other browsers on merge or nightly so PRs stay fast.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Use the API for test data</strong> where you can (create user, cart, feature flag) and use the browser only for the behavior you’re asserting. Fewer UI steps mean fewer ways for the test to flake.</li></p><p class="text-slate-300 leading-relaxed mb-4">E2E doesn’t have to hurt. A small set of well-chosen tests and a CI setup that runs them without slowing the team down gives you the safety net without the pain.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
