8:T1ca5,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Graceful Shutdown for TypeScript HTTP Servers</h1></p><p class="text-slate-300 leading-relaxed mb-4">Handling process signals and draining connections before exit keeps deployments safe and avoids dropped requests. This post outlines how to implement graceful shutdown for HTTP servers in TypeScript (Node.js or Bun).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why Graceful Shutdown Matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">When you deploy or scale down, the process receives <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGINT</code> on Ctrl+C). If the server exits immediately, in-flight requests are cut off and clients see errors. Graceful shutdown means:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Stop accepting new connections</strong> so load balancers can route traffic elsewhere.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Finish existing requests</strong> within a timeout.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Close the server</strong> and exit cleanly.</li></p><p class="text-slate-300 leading-relaxed mb-4">Without this, rolling deployments and autoscaling can cause user-facing 502s or connection resets.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Basic Pattern</h2></p><p class="text-slate-300 leading-relaxed mb-4">The idea is the same in Node and Bun:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Create your HTTP server as usual.</li>
<li class="ml-4 list-disc text-slate-300">Listen for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGINT</code>.</li>
<li class="ml-4 list-disc text-slate-300">On signal: call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code> to stop accepting new connections, then give in-flight requests time to complete, then exit (or run any other cleanup).</li></p><p class="text-slate-300 leading-relaxed mb-4">Example skeleton:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const server = createServer(requestHandler);</p><p class="text-slate-300 leading-relaxed mb-4">server.listen(port, () => {
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Listening on ${port}</code>);
});</p><p class="text-slate-300 leading-relaxed mb-4">function shutdown(signal: string) {
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${signal} received, draining...</code>);
  server.close(() => {
    console.log("Server closed");
    process.exit(0);
  });
  setTimeout(() => {
    console.error("Drain timeout, forcing exit");
    process.exit(1);
  }, 30_000);
}</p><p class="text-slate-300 leading-relaxed mb-4">process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code> only stops new connections; it does not abort active requests. The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">setTimeout</code> is a safety net: if the server does not close within 30 seconds (e.g. a stuck request), you force exit.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Tracking In-Flight Requests</h2></p><p class="text-slate-300 leading-relaxed mb-4">For more control, track open requests and wait for them to finish (or hit a timeout):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>let inFlight = 0;
const server = createServer((req, res) => {
  inFlight++;
  res.on("finish", () => inFlight--);
  requestHandler(req, res);
});</p><p class="text-slate-300 leading-relaxed mb-4">function drain(): Promise<void> {
  return new Promise((resolve) => {
    const check = () => (inFlight === 0 ? resolve() : setTimeout(check, 50));
    check();
  });
}</p><p class="text-slate-300 leading-relaxed mb-4">async function shutdown(signal: string) {
  server.close();
  await Promise.race([drain(), sleep(25_000)]);
  process.exit(0);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This way you can log "waiting for N requests" and tune the timeout to your SLA.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Bun and Node Compatibility</h2></p><p class="text-slate-300 leading-relaxed mb-4">In Bun, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Bun.serve()</code> returns a server object with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.stop()</code> method. You still listen for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGINT</code>, then call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.stop(true)</code> (the boolean can control whether to wait for connections). The same idea applies: stop accepting new work, wait for a bounded time, then exit.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Health Checks During Shutdown</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you expose a readiness probe (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/ready</code>), flip it to "not ready" as soon as you receive the signal. That way the orchestrator stops sending new traffic before you call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.close()</code>. Combined with a short drain window, you get minimal dropped requests during rolling updates.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">Implement graceful shutdown by: (1) handling <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGINT</code>, (2) stopping the server from accepting new connections, (3) optionally waiting for in-flight requests with a timeout, and (4) exiting. Use a drain timeout to avoid hanging on stuck requests. Doing this in TypeScript (Node or Bun) keeps deployments and scaling events safe for users.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
