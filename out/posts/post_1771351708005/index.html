Database Connection Pooling in TypeScript (2026)

Connection pooling is a standard way to reuse database connections instead of opening a new one per request. In TypeScript backends (Node.js, Bun, Deno), doing it right improves throughput and avoids "too many connections" errors.

Why pool?

  • Opening a connection is slow: TCP handshake, auth, session setup.
  • DBs limit connections: PostgreSQL and MySQL have a max (often hundreds). Exceeding it causes failures.
  • Per-request open/close under load quickly hits that limit and adds latency.

    • A pool keeps a fixed number of connections open, hands one to each logical "operation," and returns it when done so the next operation can reuse it.

    Pool size

    Rule of thumb: pool size ≈ number of worker threads/processes that can run DB work concurrently, not "one per HTTP request."

  • Single process: start with min = 2, max = 10–20 and tune from there.
  • Multiple workers: max total = (workers × pool max per worker) must stay below the DB’s max_connections.
  • Leave headroom for admin tools, migrations, and other services.

    • Too small: queuing and latency under load. Too large: memory and DB connection pressure.

    Example: pg (PostgreSQL)

    import { Pool } from 'pg';
    const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});
    async function getUserId(email: string): Promise {
  const client = await pool.connect();
  try {
    const r = await client.query('SELECT id FROM users WHERE email = $1', [email]);
    return r.rows[0]?.id ?? null;
  } finally {
    client.release();
  }
}

    Always release() (or use a wrapper) so the connection goes back to the pool. Never hold a client across async boundaries without releasing.

    Example: mysql2 (MySQL / MariaDB)

    import mysql from 'mysql2/promise';
    const pool = mysql.createPool({
  uri: process.env.DATABASE_URL,
  connectionLimit: 20,
  waitForConnections: true,
  queueLimit: 0,
});
    async function getUserId(email: string): Promise {
  const [rows] = await pool.execute(
    'SELECT id FROM users WHERE email = ?',
    [email]
  );
  const row = (rows as { id: string }[])[0];
  return row?.id ?? null;
}

    Here the driver returns the connection to the pool when the promise resolves, so you don’t manually release.

    SQLite (Bun / better-sqlite3)

    SQLite is process-local; "pooling" usually means a single connection (or one per worker) and serialized access, not a classic TCP pool. Use one connection per process and share it safely (e.g. with a mutex or a single-threaded worker). WAL mode allows one writer and multiple readers.

    Health checks

    Expose a readiness check that acquires a connection from the pool and releases it (e.g. SELECT 1). If the pool is exhausted or the DB is down, this fails and your orchestrator can stop sending traffic.

    Takeaways

  • Use a pool for PostgreSQL and MySQL; size it to concurrency and DB limits.
  • Always release or scope usage so connections don’t leak.
  • For SQLite, prefer one connection per process and WAL; avoid opening many file connections.
  • Monitor pool usage (checked-out vs idle) and tune max and timeouts from real load.

    • Proper connection pooling keeps your TypeScript API fast and reliable under load.
