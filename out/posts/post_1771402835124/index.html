Linux Performance Debugging Toolkit: htop, perf, strace, bpftrace

When your Linux system starts misbehaving, knowing which tools to reach for can mean the difference between finding the root cause in minutes or spending hours guessing. This guide walks through the essential performance debugging tools that every Linux engineer should have in their toolkit, illustrated with real diagnosis stories from production environments.

The Scenario

Aiko Tanaka, a site reliability engineer at a growing e-commerce platform, faced an escalating problem in late January 2026. The customer-facing API was experiencing intermittent slowdowns during peak hours. Response times that normally hovered around 150ms would spike to 2-3 seconds, causing timeouts and lost checkout sessions. The on-call team could see CPU usage on the app servers climbing, but traditional monitoring only showed the symptom, not the cause.

This is exactly the kind of situation where Linux performance debugging tools shine. Let me walk you through how Aiko and her team systematically tracked down the problem using four essential tools: htop, perf, strace, and bpftrace.

htop: Your First Line of Sight

The first tool Aiko reached for was htop. It's the friendly face of system monitoring, showing you what's consuming resources in real time with a colour-coded interface that makes spotting anomalies easy.

Install htop if needed

sudo apt-get install htop   # Debian/Ubuntu
sudo yum install htop      # RHEL/CentOS
Run htop

htop

Key shortcuts in htop make investigation faster:

  • Press t to show the process tree
  • Press P to sort by CPU usage
  • Press M to sort by memory usage
  • Press F3 to search for a specific process
  • Press u to filter by user

    • When Aiko opened htop on the affected servers, she immediately noticed something odd. The application process wasn't at the top of the CPU list—instead, several garbage collection threads were spinning at 100% CPU. The Java service was spending far too much time in garbage collection, which pointed to a memory issue rather than a CPU-bound problem.

    htop showed the symptom clearly: excessive CPU time in GC threads. But it couldn't explain why memory usage had suddenly increased. That's when perf entered the picture.

    perf: Deep CPU Analysis

    perf is the Linux profiler that lives in the kernel. It can sample CPU performance counters, track hardware events, and give you a flame graph of where your CPU cycles are going.

    Install perf
    
sudo apt-get install linux-tools-common linux-tools-generic   # Ubuntu
sudo yum install perf                                          # RHEL
    Quick CPU sampling for 10 seconds
    
perf record -g -a -- sleep 10
    View the report
    
perf report

    Aiko ran a quick perf session during a traffic spike:

    Record for 30 seconds during peak load
    
perf record -g -p $(pgrep -f java) -- sleep 30

    The perf report revealed that 60% of CPU time was being spent in memory allocation functions. The application was allocating objects faster than the garbage collector could clean them up. This pointed to a code change that had introduced a memory leak or was creating far more objects than before.

    But perf couldn't show what was creating those objects or which code paths were triggering the allocations. That's where strace provided the next piece of the puzzle.

    strace: System Call Tracing

    strace attaches to a running process and logs every system call it makes. This is invaluable for understanding what a program is doing at the operating system level—opening files, reading network packets, allocating memory.

    Install strace
    
sudo apt-get install strace   # Debian/Ubuntu
sudo yum install strace       # RHEL/CentOS
    Trace system calls for a specific process
    
strace -p 12345
    Trace with timing information
    
strace -T -p 12345
    Trace specific system calls (network in this case)
    
strace -e trace=network -p 12345

    Aiko attached strace to one of the affected processes to see what the application was actually doing:

    Watch network calls with timing, output to file
    
strace -T -e trace=network -p $(pgrep -f java) 2>&1 | head -100

    The strace output showed an alarming pattern. The application was making thousands of DNS resolution calls per second—each one a getaddrinfo system call. Aiko checked the application logs and discovered that a recent deployment had introduced a new feature that resolved hostnames for every API request, rather than caching them.

    The DNS calls were causing both the memory spike (each resolution created new network buffers) and the CPU spike (the garbage collector was overwhelmed with the object churn). strace had revealed the symptom, but now they needed bpftrace to understand the full picture of what was happening across the system.

    bpftrace: The Power of BPF

    bpftrace is the modern tool for dynamic tracing. It uses eBPF (extended Berkeley Packet Filter) to instrument the kernel without requiring custom kernel modules. You can trace arbitrary kernel functions, measure latencies, and build custom tools in a domain-specific language.

    Install bpftrace
    
sudo apt-get install bpftrace   # Ubuntu 20.04+
sudo yum install bpftrace       # RHEL 8+
    Quick system overview
    
bpftrace -e 'profile:hz:99 { @[comm] = count(); }'
    Trace file opens across the system
    
bpftrace -e 'tracepoint:syscalls:sys_enter_open { @[comm] = count(); }'

    Aiko used bpftrace to get visibility into what's normally invisible:

    Count DNS resolution calls by process
    
bpftrace -e 'tracepoint:syscalls:sys_enter_getaddrinfo { @[comm] = count(); }'
    Measure memory allocations
    
bpftrace -e 'kr:mm_page_alloc { @ = count(); }'

    The bpftrace output confirmed what strace hinted at: the application was making over 5,000 DNS resolutions per second per server. This was completely unnecessary—the DNS results should have been cached.

    Tool Comparison

    Each tool serves a different purpose and operates at a different level of the stack:

    | Tool | Primary Use | Kernel Level | Overhead | Learning Curve | |------|-------------|--------------|----------|----------------| | htop | Real-time resource monitoring | User-space | Very low | Easy | | perf | CPU profiling, hardware events | Kernel | Low | Moderate | | strace | System call tracing | Kernel | High | Easy | | bpftrace | Dynamic kernel tracing | Kernel (eBPF) | Very low | Steep |

    The key insight is that these tools complement each other. htop showed the symptom (high CPU), perf identified the function category (memory allocation), strace revealed the system calls (DNS resolution), and bpftrace quantified the scope across the entire system.

    The Fix

    Armed with this diagnosis, Aiko's team implemented a DNS cache with a 60-second TTL. They also added connection pooling for external services to avoid repeated lookups. Within an hour of deploying the fix, CPU usage dropped back to normal levels, and API response times returned to their baseline of 150ms.

    The root cause was a configuration error: the DNS client library had been initialized with a zero-second cache timeout, which meant every hostname had to be resolved fresh every time.

    Lessons Learned

  • htop is great for spotting anomalies, but it rarely reveals root cause—use it to guide where to look next
  • perf shows you where CPU time goes, but for I/O-bound issues, you need system call tracing
  • strace has high overhead but invaluable for understanding application behavior at the OS level
  • bpftrace scales from single-process to whole-system analysis without adding significant load
  • Combining multiple tools in sequence prevents going down the wrong rabbit hole

    • Actionable Takeaways

  • Install the full toolkit now — Ensure htop, perf, strace, and bpftrace are available on your systems before you need them; install kernel debug symbols too
  • Start with htop to narrow the scope — Before diving into complex tracing, use htop to identify whether the issue is CPU, memory, or I/O bound
  • Use strace judiciously — Its overhead makes it unsuitable for long-term production use; capture short windows during issues instead
  • Learn one bpftrace one-liner — Even simple commands like bpftrace -e 'profile:hz:99 { @ = count(); }' provide system-wide visibility
  • Document your baselines — Capture normal perf and bpftrace output during healthy periods so you have something to compare against when things go wrong

    • The next time your system starts misbehaving, remember Aiko's story. A systematic approach with the right tools turned a potential hours-long outage into a one-hour fix.
