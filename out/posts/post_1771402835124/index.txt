8:T39fb,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Linux Performance Debugging Toolkit: htop, perf, strace, bpftrace</h1></p><p class="text-slate-300 leading-relaxed mb-4">When your Linux system starts misbehaving, knowing which tools to reach for can mean the difference between finding the root cause in minutes or spending hours guessing. This guide walks through the essential performance debugging tools that every Linux engineer should have in their toolkit, illustrated with real diagnosis stories from production environments.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Scenario</h2></p><p class="text-slate-300 leading-relaxed mb-4">Aiko Tanaka, a site reliability engineer at a growing e-commerce platform, faced an escalating problem in late January 2026. The customer-facing API was experiencing intermittent slowdowns during peak hours. Response times that normally hovered around 150ms would spike to 2-3 seconds, causing timeouts and lost checkout sessions. The on-call team could see CPU usage on the app servers climbing, but traditional monitoring only showed the symptom, not the cause.</p><p class="text-slate-300 leading-relaxed mb-4">This is exactly the kind of situation where Linux performance debugging tools shine. Let me walk you through how Aiko and her team systematically tracked down the problem using four essential tools: htop, perf, strace, and bpftrace.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">htop: Your First Line of Sight</h2></p><p class="text-slate-300 leading-relaxed mb-4">The first tool Aiko reached for was <strong>htop</strong>. It's the friendly face of system monitoring, showing you what's consuming resources in real time with a colour-coded interface that makes spotting anomalies easy.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install htop if needed</h1>
sudo apt-get install htop   # Debian/Ubuntu
sudo yum install htop      # RHEL/CentOS</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Run htop</h1>
htop
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Key shortcuts in htop make investigation faster:
<li class="ml-4 list-disc text-slate-300">Press <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">t</code> to show the process tree</li>
<li class="ml-4 list-disc text-slate-300">Press <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">P</code> to sort by CPU usage</li>
<li class="ml-4 list-disc text-slate-300">Press <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">M</code> to sort by memory usage</li>
<li class="ml-4 list-disc text-slate-300">Press <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F3</code> to search for a specific process</li>
<li class="ml-4 list-disc text-slate-300">Press <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">u</code> to filter by user</li></p><p class="text-slate-300 leading-relaxed mb-4">When Aiko opened htop on the affected servers, she immediately noticed something odd. The application process wasn't at the top of the CPU list—instead, several garbage collection threads were spinning at 100% CPU. The Java service was spending far too much time in garbage collection, which pointed to a memory issue rather than a CPU-bound problem.</p><p class="text-slate-300 leading-relaxed mb-4">htop showed the symptom clearly: excessive CPU time in GC threads. But it couldn't explain why memory usage had suddenly increased. That's when perf entered the picture.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">perf: Deep CPU Analysis</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>perf</strong> is the Linux profiler that lives in the kernel. It can sample CPU performance counters, track hardware events, and give you a flame graph of where your CPU cycles are going.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install perf</h1>
sudo apt-get install linux-tools-common linux-tools-generic   # Ubuntu
sudo yum install perf                                          # RHEL</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Quick CPU sampling for 10 seconds</h1>
perf record -g -a -- sleep 10</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">View the report</h1>
perf report
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Aiko ran a quick perf session during a traffic spike:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Record for 30 seconds during peak load</h1>
perf record -g -p $(pgrep -f java) -- sleep 30
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The perf report revealed that 60% of CPU time was being spent in memory allocation functions. The application was allocating objects faster than the garbage collector could clean them up. This pointed to a code change that had introduced a memory leak or was creating far more objects than before.</p><p class="text-slate-300 leading-relaxed mb-4">But perf couldn't show what was creating those objects or which code paths were triggering the allocations. That's where strace provided the next piece of the puzzle.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">strace: System Call Tracing</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>strace</strong> attaches to a running process and logs every system call it makes. This is invaluable for understanding what a program is doing at the operating system level—opening files, reading network packets, allocating memory.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install strace</h1>
sudo apt-get install strace   # Debian/Ubuntu
sudo yum install strace       # RHEL/CentOS</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Trace system calls for a specific process</h1>
strace -p 12345</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Trace with timing information</h1>
strace -T -p 12345</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Trace specific system calls (network in this case)</h1>
strace -e trace=network -p 12345
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Aiko attached strace to one of the affected processes to see what the application was actually doing:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Watch network calls with timing, output to file</h1>
strace -T -e trace=network -p $(pgrep -f java) 2>&1 | head -100
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The strace output showed an alarming pattern. The application was making thousands of DNS resolution calls per second—each one a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">getaddrinfo</code> system call. Aiko checked the application logs and discovered that a recent deployment had introduced a new feature that resolved hostnames for every API request, rather than caching them.</p><p class="text-slate-300 leading-relaxed mb-4">The DNS calls were causing both the memory spike (each resolution created new network buffers) and the CPU spike (the garbage collector was overwhelmed with the object churn). strace had revealed the symptom, but now they needed bpftrace to understand the full picture of what was happening across the system.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">bpftrace: The Power of BPF</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>bpftrace</strong> is the modern tool for dynamic tracing. It uses eBPF (extended Berkeley Packet Filter) to instrument the kernel without requiring custom kernel modules. You can trace arbitrary kernel functions, measure latencies, and build custom tools in a domain-specific language.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install bpftrace</h1>
sudo apt-get install bpftrace   # Ubuntu 20.04+
sudo yum install bpftrace       # RHEL 8+</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Quick system overview</h1>
bpftrace -e 'profile:hz:99 { @[comm] = count(); }'</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Trace file opens across the system</h1>
bpftrace -e 'tracepoint:syscalls:sys_enter_open { @[comm] = count(); }'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Aiko used bpftrace to get visibility into what's normally invisible:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Count DNS resolution calls by process</h1>
bpftrace -e 'tracepoint:syscalls:sys_enter_getaddrinfo { @[comm] = count(); }'</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Measure memory allocations</h1>
bpftrace -e 'kr:mm_page_alloc { @ = count(); }'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The bpftrace output confirmed what strace hinted at: the application was making over 5,000 DNS resolutions per second per server. This was completely unnecessary—the DNS results should have been cached.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Tool Comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">Each tool serves a different purpose and operates at a different level of the stack:</p><p class="text-slate-300 leading-relaxed mb-4">| Tool | Primary Use | Kernel Level | Overhead | Learning Curve |
|------|-------------|--------------|----------|----------------|
| <strong>htop</strong> | Real-time resource monitoring | User-space | Very low | Easy |
| <strong>perf</strong> | CPU profiling, hardware events | Kernel | Low | Moderate |
| <strong>strace</strong> | System call tracing | Kernel | High | Easy |
| <strong>bpftrace</strong> | Dynamic kernel tracing | Kernel (eBPF) | Very low | Steep |</p><p class="text-slate-300 leading-relaxed mb-4">The key insight is that these tools complement each other. htop showed the symptom (high CPU), perf identified the function category (memory allocation), strace revealed the system calls (DNS resolution), and bpftrace quantified the scope across the entire system.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Fix</h2></p><p class="text-slate-300 leading-relaxed mb-4">Armed with this diagnosis, Aiko's team implemented a DNS cache with a 60-second TTL. They also added connection pooling for external services to avoid repeated lookups. Within an hour of deploying the fix, CPU usage dropped back to normal levels, and API response times returned to their baseline of 150ms.</p><p class="text-slate-300 leading-relaxed mb-4">The root cause was a configuration error: the DNS client library had been initialized with a zero-second cache timeout, which meant every hostname had to be resolved fresh every time.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">htop is great for spotting anomalies, but it rarely reveals root cause—use it to guide where to look next</li>
<li class="ml-4 list-disc text-slate-300">perf shows you where CPU time goes, but for I/O-bound issues, you need system call tracing</li>
<li class="ml-4 list-disc text-slate-300">strace has high overhead but invaluable for understanding application behavior at the OS level</li>
<li class="ml-4 list-disc text-slate-300">bpftrace scales from single-process to whole-system analysis without adding significant load</li>
<li class="ml-4 list-disc text-slate-300">Combining multiple tools in sequence prevents going down the wrong rabbit hole</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Install the full toolkit now</strong> — Ensure htop, perf, strace, and bpftrace are available on your systems before you need them; install kernel debug symbols too</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Start with htop to narrow the scope</strong> — Before diving into complex tracing, use htop to identify whether the issue is CPU, memory, or I/O bound</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use strace judiciously</strong> — Its overhead makes it unsuitable for long-term production use; capture short windows during issues instead</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Learn one bpftrace one-liner</strong> — Even simple commands like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bpftrace -e 'profile:hz:99 { @ = count(); }'</code> provide system-wide visibility</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document your baselines</strong> — Capture normal perf and bpftrace output during healthy periods so you have something to compare against when things go wrong</li></p><p class="text-slate-300 leading-relaxed mb-4">The next time your system starts misbehaving, remember Aiko's story.
