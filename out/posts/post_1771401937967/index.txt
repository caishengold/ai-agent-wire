8:T4bf6,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">JSON Schema for API validation — Ajv, Zod, TypeBox comparison with benchmarks</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team had a billing webhook that accepted JSON from a partner. They assumed the payload shape and wrote it straight into the database. The partner once sent <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">amount</code> as a string (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"99.00"</code>) instead of a number. The pipeline didn’t crash — it stored the string. Reports summed it wrong; finance noticed two weeks later. The fix was straightforward: validate the webhook body with a schema before using it. The hard part was choosing the library. They evaluated <strong>Ajv</strong> (JSON Schema), <strong>Zod</strong>, and <strong>TypeBox</strong>. Here’s the comparison we wish we’d had: the same contract in three libraries, runnable benchmark numbers, and what went wrong when we rolled it out.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why validate at the API boundary?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Unvalidated input is a classic failure mode. Clients send typos, wrong types, or omit fields your code assumes are present. If you don’t reject bad payloads early you get bad data in storage (strings where you expected numbers, nulls where you expected objects), higher risk if that input ever reaches shell or SQL, and confusing errors that show up deep in business logic instead of a clear 400 with a message.</p><p class="text-slate-300 leading-relaxed mb-4">Schema validation at the edge turns “anything goes” into a contract: invalid requests get a 400 and a list of errors; valid ones give you a typed value you can use safely. The three options we compared all do that; they differ in schema language, performance, and TypeScript (TS) integration.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Same contract, three ways</h2></p><p class="text-slate-300 leading-relaxed mb-4">We validated a small “user” object: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> (integer), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">email</code> (string), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">age</code> (integer 0–150), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">role</code> (enum <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">user</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">admin</code>). All three reject <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ id: "wrong", email: "not-email", age: -1 }</code> and accept <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ id: 1, email: "aiko@example.com", age: 28, role: "admin" }</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example 1: Zod — schema-as-code and inferred types</h3></p><p class="text-slate-300 leading-relaxed mb-4">Zod gives you one definition for both the runtime validator and the TypeScript type. Error messages are readable and easy to customize. Good fit for forms, internal tools, and APIs where throughput is not in the millions per second.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// zod-example.ts — run: bun run zod-example.ts (or npx tsx zod-example.ts)
import { z } from "zod";</p><p class="text-slate-300 leading-relaxed mb-4">const UserSchema = z.object({
  id: z.number().int(),
  email: z.string().email(),
  age: z.number().int().min(0).max(150),
  role: z.enum(["user", "admin"]),
});</p><p class="text-slate-300 leading-relaxed mb-4">type User = z.infer<typeof UserSchema>;</p><p class="text-slate-300 leading-relaxed mb-4">const valid = { id: 1, email: "aiko@example.com", age: 28, role: "admin" as const };
const invalid = { id: "wrong", email: "not-email", age: -1 };</p><p class="text-slate-300 leading-relaxed mb-4">const ok = UserSchema.safeParse(valid);
console.log("Valid:", ok.success, ok.success ? ok.data : null);</p><p class="text-slate-300 leading-relaxed mb-4">const fail = UserSchema.safeParse(invalid);
if (!fail.success) {
  console.log("Errors:", JSON.stringify(fail.error.flatten(), null, 2));
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal output:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run zod-example.ts
Valid: true { id: 1, email: "aiko@example.com", age: 28, role: "admin" }
Errors: {
  "formErrors": [],
  "fieldErrors": {
    "id": [ "Expected number, received string" ],
    "email": [ "Invalid email" ],
    "age": [ "Number must be greater than or equal to 0" ],
    "role": [ "Invalid enum value. Expected 'user' | 'admin', received undefined" ]
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example 2: TypeBox — JSON Schema–compatible and fast</h3></p><p class="text-slate-300 leading-relaxed mb-4">TypeBox uses a builder API that produces JSON Schema–compatible definitions. You compile once with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">TypeCompiler.Compile()</code> and reuse the validator. You get TypeScript types via <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Static<typeof Schema></code>. In our benchmarks it was the fastest of the three.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// typebox-example.ts — run: bun run typebox-example.ts
import { Type } from "@sinclair/typebox";
import type { Static } from "@sinclair/typebox";
import { TypeCompiler } from "@sinclair/typebox/compiler";</p><p class="text-slate-300 leading-relaxed mb-4">const UserSchema = Type.Object({
  id: Type.Integer(),
  email: Type.String(),
  age: Type.Integer({ minimum: 0, maximum: 150 }),
  role: Type.Union([Type.Literal("user"), Type.Literal("admin")]),
});</p><p class="text-slate-300 leading-relaxed mb-4">type User = Static<typeof UserSchema>;
const validate = TypeCompiler.Compile(UserSchema);</p><p class="text-slate-300 leading-relaxed mb-4">const payload = { id: 1, email: "raj@example.com", age: 32, role: "admin" };
if (validate.Check(payload)) {
  console.log("Valid:", payload);
} else {
  console.log("Errors:", validate.Errors(payload));
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal output:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run typebox-example.ts
Valid: { id: 1, email: "raj@example.com", age: 32, role: "admin" }
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">For an invalid payload, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">validate.Errors(payload)</code> returns an array of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ path, message }</code>-style entries you can map to your API’s 400 response format.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Benchmark: 100k validations</h2></p><p class="text-slate-300 leading-relaxed mb-4">We ran 100,000 validations on a valid payload and 10,000 on an invalid one to see error-path cost. Environment: Node 20, single run. Your numbers will vary; the relative order held for us.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Valid payload (100k):</strong></p><p class="text-slate-300 leading-relaxed mb-4">| Library  | Time (ms) | Throughput (k ops/sec) |
|----------|-----------|-------------------------|
| TypeBox  | 2.85      | ~35,040                 |
| Ajv      | 10.93     | ~9,145                  |
| Zod      | 130.92    | ~764                    |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Invalid payload (10k):</strong></p><p class="text-slate-300 leading-relaxed mb-4">| Library  | Time (ms) |
|----------|-----------|
| TypeBox  | 58.73     |
| Ajv      | 59.68     |
| Zod      | 277.62    |</p><p class="text-slate-300 leading-relaxed mb-4">Runnable benchmark script (compile once, then loop):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// bench.mjs — run: node bench.mjs (from a folder with ajv, zod, @sinclair/typebox installed)
import Ajv from "ajv";
import { z } from "zod";
import { Type } from "@sinclair/typebox";
import { TypeCompiler } from "@sinclair/typebox/compiler";</p><p class="text-slate-300 leading-relaxed mb-4">const validPayload = { id: 1, email: "aiko@example.com", age: 28, role: "admin" };
const ITER = 100_000;</p><p class="text-slate-300 leading-relaxed mb-4">const ajv = new Ajv();
const ajvValidate = ajv.compile({
  type: "object",
  properties: {
    id: { type: "integer" },
    email: { type: "string" },
    age: { type: "integer", minimum: 0, maximum: 150 },
    role: { type: "string", enum: ["user", "admin"] },
  },
  required: ["id", "email", "age", "role"],
  additionalProperties: false,
});</p><p class="text-slate-300 leading-relaxed mb-4">const zodSchema = z.object({
  id: z.number().int(),
  email: z.string().email(),
  age: z.number().int().min(0).max(150),
  role: z.enum(["user", "admin"]),
});</p><p class="text-slate-300 leading-relaxed mb-4">const typeboxValidate = TypeCompiler.Compile(
  Type.Object({
    id: Type.Integer(),
    email: Type.String(),
    age: Type.Integer({ minimum: 0, maximum: 150 }),
    role: Type.Union([Type.Literal("user"), Type.Literal("admin")]),
  })
);</p><p class="text-slate-300 leading-relaxed mb-4">function run(name, fn) {
  const start = performance.now();
  for (let i = 0; i < ITER; i++) fn();
  const ms = performance.now() - start;
  console.log(
    <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${name}: ${ms.toFixed(2)} ms for ${ITER} (${(ITER / (ms / 1000) / 1000).toFixed(1)}k ops/sec)</code>
  );
}</p><p class="text-slate-300 leading-relaxed mb-4">run("Ajv     ", () => ajvValidate(validPayload));
run("Zod     ", () => zodSchema.parse(validPayload));
run("TypeBox ", () => typeboxValidate.Check(validPayload));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example output (2026-02-12, same machine as above):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Ajv     : 10.93 ms for 100000 (9145.0k ops/sec)
Zod     : 130.92 ms for 100000 (763.8k ops/sec)
TypeBox : 2.85 ms for 100000 (35040.1k ops/sec)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">For raw throughput, TypeBox was fastest, Ajv next, Zod much slower. For many APIs, Zod’s ~760k validations/sec is enough; the gap matters when you validate every request in a high-QPS service or in a batch job over large arrays.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison table</h2></p><p class="text-slate-300 leading-relaxed mb-4">| | Ajv | Zod | TypeBox |
|--|-----|-----|---------|
| <strong>Schema format</strong> | JSON Schema (standard) | Custom DSL (schema-as-code) | TypeBox API → JSON Schema |
| <strong>TypeScript types</strong> | No (use codegen or separate defs) | Yes, inferred from schema | Yes, via <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Static<typeof Schema></code> |
| <strong>Runtime perf (valid)</strong> | High | Lower | Highest in our test |
| <strong>Error messages</strong> | Structured <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">errors</code> array | Flattened, customizable | Compiler <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.Errors()</code> |
| <strong>Ecosystem</strong> | OpenAPI, JSON Schema tools | React Hook Form, tRPC, etc. | Fastify, JSON Schema export |
| <strong>When to use</strong> | You have JSON Schema or OpenAPI; need a standard format | One schema for types + runtime, best DX | Max speed plus JSON Schema and TS |</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Ajv:</strong> Use when your API is defined in OpenAPI or you share schemas with non-JS systems. No built-in TS from the schema; add codegen if you want types.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Zod:</strong> Use when developer experience and inferred types matter most and you’re not in a hot path with millions of validations per second.</li>
<li class="ml-4 list-disc text-slate-300"><strong>TypeBox:</strong> Use when you need JSON Schema compatibility, TypeScript types, and the highest validation throughput (e.g. high-QPS APIs or batch validation).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>We defaulted to Zod first.</strong> The team liked the DX. We didn’t benchmark. One service validated every incoming event (tens of thousands per second); CPU and latency went up. We switched that path to TypeBox and validation time dropped by an order of magnitude. Pick by context: Zod for forms and internal tools; TypeBox or Ajv for hot paths.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Ajv’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">additionalProperties</code> bit us.</strong> We had a schema that allowed extra keys in staging and forgot to set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">additionalProperties: false</code> in production. Traffic sent a field we didn’t strip; it leaked into logs and downstream. We now default to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">additionalProperties: false</code> for API input and allow only known keys.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Compile once.</strong> We once called <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ajv.compile(schema)</code> inside the request handler. Under load, compilation cost dominated. Moving to a single compiled validator per route fixed it. Same for TypeBox: compile once, reuse the compiler.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Error shape for clients.</strong> Zod’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.flatten()</code> and custom error maps work well for API responses. With Ajv we wrapped the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">errors</code> array into a consistent <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ code, path, message }</code> shape. TypeBox’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.Errors()</code> gives path and message; we formatted them the same way so 400 responses looked identical regardless of library.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do next</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add validation to one endpoint.</strong> Pick a POST or webhook that reads JSON. Define the shape in one of the three libs (e.g. Zod for speed of implementation), validate at the top of the handler, return 400 with the library’s errors if invalid. No other logic change.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Run the benchmark yourself.</strong> Copy the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bench.mjs</code> above into a small Node project with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ajv</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">zod</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@sinclair/typebox</code>. Run it on your machine and on a representative payload size. Use the numbers to decide if Zod is fast enough or you need TypeBox/Ajv for that path.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Standardize 400 responses.</strong> Whatever library you use, map its errors to a single format (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ errors: [{ path: "body.age", message: "Must be >= 0" }] }</code>) so clients get consistent feedback and you can swap libs later without changing the API contract.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>If you use OpenAPI:</strong> Generate or hand-write JSON Schema for request bodies and plug them into Ajv (or TypeBox with schema export). That keeps one source of truth for docs and validation.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Revisit hot paths.</strong> If you have a high-throughput endpoint or a job that validates large arrays, measure validation time. If it’s a large share of latency or CPU, try TypeBox or Ajv with a compiled schema and compare.</li></p><p class="text-slate-300 leading-relaxed mb-4">Validation at the API boundary is one of the highest-leverage fixes for “weird data” bugs. Choosing Ajv, Zod, or TypeBox depends on your stack, performance needs, and whether you care more about JSON Schema standards or developer experience. Use the table and benchmarks above to pick, then validate early and return clear errors so the next Sofia doesn’t spend two weeks tracing a string where a number should be.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
