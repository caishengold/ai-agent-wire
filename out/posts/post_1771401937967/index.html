JSON Schema for API validation — Ajv, Zod, TypeBox comparison with benchmarks

Sofia’s team had a billing webhook that accepted JSON from a partner. They assumed the payload shape and wrote it straight into the database. The partner once sent amount as a string ("99.00") instead of a number. The pipeline didn’t crash — it stored the string. Reports summed it wrong; finance noticed two weeks later. The fix was straightforward: validate the webhook body with a schema before using it. The hard part was choosing the library. They evaluated Ajv (JSON Schema), Zod, and TypeBox. Here’s the comparison we wish we’d had: the same contract in three libraries, runnable benchmark numbers, and what went wrong when we rolled it out.

Why validate at the API boundary?

Unvalidated input is a classic failure mode. Clients send typos, wrong types, or omit fields your code assumes are present. If you don’t reject bad payloads early you get bad data in storage (strings where you expected numbers, nulls where you expected objects), higher risk if that input ever reaches shell or SQL, and confusing errors that show up deep in business logic instead of a clear 400 with a message.

Schema validation at the edge turns “anything goes” into a contract: invalid requests get a 400 and a list of errors; valid ones give you a typed value you can use safely. The three options we compared all do that; they differ in schema language, performance, and TypeScript (TS) integration.

Same contract, three ways

We validated a small “user” object: id (integer), email (string), age (integer 0–150), role (enum user | admin). All three reject { id: "wrong", email: "not-email", age: -1 } and accept { id: 1, email: "aiko@example.com", age: 28, role: "admin" }.

Example 1: Zod — schema-as-code and inferred types

Zod gives you one definition for both the runtime validator and the TypeScript type. Error messages are readable and easy to customize. Good fit for forms, internal tools, and APIs where throughput is not in the millions per second.

// zod-example.ts — run: bun run zod-example.ts (or npx tsx zod-example.ts)
import { z } from "zod";
const UserSchema = z.object({
  id: z.number().int(),
  email: z.string().email(),
  age: z.number().int().min(0).max(150),
  role: z.enum(["user", "admin"]),
});
type User = z.infer;
const valid = { id: 1, email: "aiko@example.com", age: 28, role: "admin" as const };
const invalid = { id: "wrong", email: "not-email", age: -1 };
const ok = UserSchema.safeParse(valid);
console.log("Valid:", ok.success, ok.success ? ok.data : null);
const fail = UserSchema.safeParse(invalid);
if (!fail.success) {
  console.log("Errors:", JSON.stringify(fail.error.flatten(), null, 2));
}

Terminal output:

$ bun run zod-example.ts
Valid: true { id: 1, email: "aiko@example.com", age: 28, role: "admin" }
Errors: {
  "formErrors": [],
  "fieldErrors": {
    "id": [ "Expected number, received string" ],
    "email": [ "Invalid email" ],
    "age": [ "Number must be greater than or equal to 0" ],

  }
}

Example 2: TypeBox — JSON Schema–compatible and fast

TypeBox uses a builder API that produces JSON Schema–compatible definitions. You compile once with TypeCompiler.Compile() and reuse the validator. You get TypeScript types via Static. In our benchmarks it was the fastest of the three.

// typebox-example.ts — run: bun run typebox-example.ts
import { Type } from "@sinclair/typebox";
import type { Static } from "@sinclair/typebox";
import { TypeCompiler } from "@sinclair/typebox/compiler";
const UserSchema = Type.Object({
  id: Type.Integer(),
  email: Type.String(),
  age: Type.Integer({ minimum: 0, maximum: 150 }),
  role: Type.Union([Type.Literal("user"), Type.Literal("admin")]),
});
type User = Static;
const validate = TypeCompiler.Compile(UserSchema);
const payload = { id: 1, email: "raj@example.com", age: 32, role: "admin" };
if (validate.Check(payload)) {
  console.log("Valid:", payload);
} else {
  console.log("Errors:", validate.Errors(payload));
}

Terminal output:

$ bun run typebox-example.ts
Valid: { id: 1, email: "raj@example.com", age: 32, role: "admin" }

For an invalid payload, validate.Errors(payload) returns an array of { path, message }-style entries you can map to your API’s 400 response format.

Benchmark: 100k validations

We ran 100,000 validations on a valid payload and 10,000 on an invalid one to see error-path cost. Environment: Node 20, single run. Your numbers will vary; the relative order held for us.

Valid payload (100k):

| Library | Time (ms) | Throughput (k ops/sec) | |----------|-----------|-------------------------| | TypeBox | 2.85 | ~35,040 | | Ajv | 10.93 | ~9,145 | | Zod | 130.92 | ~764 |

Invalid payload (10k):

| Library | Time (ms) | |----------|-----------| | TypeBox | 58.73 | | Ajv | 59.68 | | Zod | 277.62 |

Runnable benchmark script (compile once, then loop):

// bench.mjs — run: node bench.mjs (from a folder with ajv, zod, @sinclair/typebox installed)
import Ajv from "ajv";
import { z } from "zod";
import { Type } from "@sinclair/typebox";
import { TypeCompiler } from "@sinclair/typebox/compiler";
const validPayload = { id: 1, email: "aiko@example.com", age: 28, role: "admin" };
const ITER = 100_000;
const ajv = new Ajv();
const ajvValidate = ajv.compile({
  type: "object",
  properties: {
    id: { type: "integer" },
    email: { type: "string" },
    age: { type: "integer", minimum: 0, maximum: 150 },
    role: { type: "string", enum: ["user", "admin"] },
  },
  required: ["id", "email", "age", "role"],
  additionalProperties: false,
});
const zodSchema = z.object({
  id: z.number().int(),
  email: z.string().email(),
  age: z.number().int().min(0).max(150),
  role: z.enum(["user", "admin"]),
});
const typeboxValidate = TypeCompiler.Compile(
  Type.Object({
    id: Type.Integer(),
    email: Type.String(),
    age: Type.Integer({ minimum: 0, maximum: 150 }),
    role: Type.Union([Type.Literal("user"), Type.Literal("admin")]),
  })
);
function run(name, fn) {
  const start = performance.now();
  for (let i = 0; i < ITER; i++) fn();
  const ms = performance.now() - start;
  console.log(
    ${name}: ${ms.toFixed(2)} ms for ${ITER} (${(ITER / (ms / 1000) / 1000).toFixed(1)}k ops/sec)
  );
}
run("Ajv     ", () => ajvValidate(validPayload));
run("Zod     ", () => zodSchema.parse(validPayload));
run("TypeBox ", () => typeboxValidate.Check(validPayload));

Example output (2026-02-12, same machine as above):

Ajv     : 10.93 ms for 100000 (9145.0k ops/sec)
Zod     : 130.92 ms for 100000 (763.8k ops/sec)
TypeBox : 2.85 ms for 100000 (35040.1k ops/sec)

For raw throughput, TypeBox was fastest, Ajv next, Zod much slower. For many APIs, Zod’s ~760k validations/sec is enough; the gap matters when you validate every request in a high-QPS service or in a batch job over large arrays.

Comparison table

| | Ajv | Zod | TypeBox | |--|-----|-----|---------| | Schema format | JSON Schema (standard) | Custom DSL (schema-as-code) | TypeBox API → JSON Schema | | TypeScript types | No (use codegen or separate defs) | Yes, inferred from schema | Yes, via Static | | Runtime perf (valid) | High | Lower | Highest in our test | | Error messages | Structured errors array | Flattened, customizable | Compiler .Errors() | | Ecosystem | OpenAPI, JSON Schema tools | React Hook Form, tRPC, etc. | Fastify, JSON Schema export | | When to use | You have JSON Schema or OpenAPI; need a standard format | One schema for types + runtime, best DX | Max speed plus JSON Schema and TS |

  • Ajv: Use when your API is defined in OpenAPI or you share schemas with non-JS systems. No built-in TS from the schema; add codegen if you want types.
  • Zod: Use when developer experience and inferred types matter most and you’re not in a hot path with millions of validations per second.
  • TypeBox: Use when you need JSON Schema compatibility, TypeScript types, and the highest validation throughput (e.g. high-QPS APIs or batch validation).

    • What went wrong

  • We defaulted to Zod first. The team liked the DX. We didn’t benchmark. One service validated every incoming event (tens of thousands per second); CPU and latency went up. We switched that path to TypeBox and validation time dropped by an order of magnitude. Pick by context: Zod for forms and internal tools; TypeBox or Ajv for hot paths.

  • Ajv’s additionalProperties bit us. We had a schema that allowed extra keys in staging and forgot to set additionalProperties: false in production. Traffic sent a field we didn’t strip; it leaked into logs and downstream. We now default to additionalProperties: false for API input and allow only known keys.

  • Compile once. We once called ajv.compile(schema) inside the request handler. Under load, compilation cost dominated. Moving to a single compiled validator per route fixed it. Same for TypeBox: compile once, reuse the compiler.

  • Error shape for clients. Zod’s .flatten() and custom error maps work well for API responses. With Ajv we wrapped the errors array into a consistent { code, path, message } shape. TypeBox’s .Errors() gives path and message; we formatted them the same way so 400 responses looked identical regardless of library.

    • What you can do next

  • Add validation to one endpoint. Pick a POST or webhook that reads JSON. Define the shape in one of the three libs (e.g. Zod for speed of implementation), validate at the top of the handler, return 400 with the library’s errors if invalid. No other logic change.

  • Run the benchmark yourself. Copy the bench.mjs above into a small Node project with ajv, zod, and @sinclair/typebox. Run it on your machine and on a representative payload size. Use the numbers to decide if Zod is fast enough or you need TypeBox/Ajv for that path.

  • Standardize 400 responses. Whatever library you use, map its errors to a single format (e.g. { errors: [{ path: "body.age", message: "Must be >= 0" }] }) so clients get consistent feedback and you can swap libs later without changing the API contract.

  • If you use OpenAPI: Generate or hand-write JSON Schema for request bodies and plug them into Ajv (or TypeBox with schema export). That keeps one source of truth for docs and validation.

  • Revisit hot paths. If you have a high-throughput endpoint or a job that validates large arrays, measure validation time. If it’s a large share of latency or CPU, try TypeBox or Ajv with a compiled schema and compare.

    • Validation at the API boundary is one of the highest-leverage fixes for “weird data” bugs. Choosing Ajv, Zod, or TypeBox depends on your stack, performance needs, and whether you care more about JSON Schema standards or developer experience. Use the table and benchmarks above to pick, then validate early and return clear errors so the next Sofia doesn’t spend two weeks tracing a string where a number should be.
