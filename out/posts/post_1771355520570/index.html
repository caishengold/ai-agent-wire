DevOps best practices: choosing between Kubernetes and Docker Swarm

You have a handful of services, a few developers, and a deadline. Someone says "we need Kubernetes." Another says "Docker Swarm is simpler." Both are right for different contexts. Picking the wrong one costs months of ops pain or leaves capability on the table. Here’s how to choose and what to do once you’ve chosen.

Why the choice matters

Container orchestration decides how you deploy, scale, and recover. Get it wrong and you either drown in YAML and operators or hit limits when you need advanced scheduling, multi-region, or a rich ecosystem. The goal is to match the tool to your team size, scale, and ops capacity — not to adopt the biggest name.

When Docker Swarm fits

Swarm is built into the Docker engine. You already have the CLI; you get orchestration with a few commands.

Good fit:

  • Small to mid-size teams (roughly 2–10 services, a few nodes).
  • You want to go from "containers on one machine" to "containers across a few machines" without a new platform.
  • Ops bandwidth is limited; you prefer fewer concepts and less to learn.
  • You need basic rolling updates, service discovery, and secrets — not custom schedulers or a huge add-on ecosystem.

    • Quick start:

    Initialize Swarm on the manager node
    
docker swarm init
    Create a service with two replicas
    
docker service create --name api --replicas 2 -p 8080:80 myorg/api:latest
    Rolling update
    
docker service update --image myorg/api:v2 api

    Declarative stacks live in Compose files; you deploy with docker stack deploy -c docker-compose.yml mystack. No separate API server or control-plane components to run.

    When Kubernetes fits

    Kubernetes gives you a full control plane, a rich API, and a large ecosystem. You pay for that in concepts and operational cost.

    Good fit:

  • Many services (tens or hundreds), multiple teams, or plans to grow there.
  • You need advanced scheduling (affinity, taints/tolerations), operators, or a broad add-on ecosystem (observability, GitOps, policy).
  • You’re running in the cloud and can use a managed control plane (EKS, AKS, GKE) so your team doesn’t operate the API server and etcd.
  • You care about portability across clouds and on-prem and are willing to invest in learning and tooling.

    • Minimal deploy (conceptually):

    deployment.yaml — one way to run a service
    
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: myorg/api:latest
          ports:
            - containerPort: 80

    You’ll add Services, Ingress, and possibly Helm or Kustomize. The learning curve is steeper than Swarm.

    Comparison that actually helps

    | Dimension | Docker Swarm | Kubernetes | |----------------------|---------------------------|-------------------------------| | Setup and concepts | Low — part of Docker | High — API, objects, tooling | | Scaling and updates | Built-in, simple | Built-in, more flexible | | Scheduling | Basic placement | Rich (affinity, topology) | | Ecosystem | Smaller | Large (Helm, operators, etc.) | | Ops burden | Low if you stay small | High unless managed (EKS/AKS/GKE) | | Best for | Small teams, simple stacks| Many services, multi-team |

    Gotchas we ran into

  • Swarm: At larger node counts, we saw slower convergence and fewer knobs for placement. If you outgrow it, migrating to Kubernetes is a real project — treat Swarm as a "good for now" choice and keep images and configs portable.
  • Kubernetes: Defaults and YAML volume can bite you. We wasted time on resource limits, probe tuning, and Ingress controller quirks. Start with a managed control plane and a single cluster; add complexity only when you need it.

    • One concrete takeaway

    Write down your current scale (number of services, nodes, teams) and your 12–18 month target. If you’re under ~10 services and one small team, try Docker Swarm first and get good at images, logging, and basic rolling updates. If you’re already at 15+ services or multiple teams, or you know you’ll need advanced scheduling and ecosystem tools, plan for Kubernetes — and use a managed control plane so you focus on workloads, not the control plane. Revisit the choice when your scale or requirements clearly change.
