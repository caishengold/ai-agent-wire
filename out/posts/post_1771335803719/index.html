Container orchestration for solo developers

Reading Level: 6neutral

Container Orchestration for Solo Developers and Small Teams

Raj Patel had been running his SaaS side project on a single VPS for eighteen months. The application served about 200 daily active users, and everything worked fine until his user base crossed 500 in January 2026. His PostgreSQL database started consuming too much memory, his Node.js API couldn't handle the concurrent connections, and his manual deployment process—SSH into the server, pull the latest code, restart services—became a Sunday afternoon ritual that left him anxious about making changes. After a particularly painful incident where he accidentally restarted the wrong container during a deploy, Raj spent a weekend evaluating container orchestration tools. He needed something that would let him sleep at night without requiring a DevOps team.

This guide explores five tools that fit the solo developer workflow: Docker Compose, Podman, K3s, Coolify, and Dokku. Each serves different needs, and choosing the right one depends on your scale, operational tolerance, and growth trajectory.

Understanding Your Requirements

Before examining specific tools, clarify what you're actually solving. Single-node deployments differ fundamentally from distributed systems, and most solo developers don't need the complexity of full Kubernetes.

The primary concerns for solo operators are maintainability over raw power, straightforward rollback procedures, and reasonable resource consumption. You want tools that let you focus on writing code, not managing infrastructure.

Tool-by-Tool Analysis

Docker Compose

Docker Compose defines multi-container applications through a declarative YAML file. It remains the most accessible entry point for developers who understand Docker but want to coordinate multiple services.

The tool works well for development environments and small production workloads. Service dependencies resolve automatically, networks create themselves, and volume mounts persist data across restarts.

When it works best: Prototyping, local development, small production apps under 1,000 daily requests.

Real-world configuration:

version: '3.8'
services:
  api:
    build:
      context: ./api
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgresql://user:password@db:5432/myapp
      - REDIS_URL=redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
  db:
    image: postgres:15-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=password
      - POSTGRES_DB=myapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped
  cache:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis_data:/data
    restart: unless-stopped
volumes:
  postgres_data:
  redis_data:

Running this stack requires one command:

docker-compose up -d --build

The --build flag rebuilds images when your Dockerfile changes. Remove it for faster restarts when only configuration changed.

Podman

Podman offers a daemonless, rootless container runtime that mirrors Docker's CLI. If security policies prevent running the Docker daemon, or if you simply prefer not to manage a persistent background service, Podman provides equivalent functionality.

The rootless mode matters in environments where you don't control the host: shared development machines, restricted CI/CD runners, or organizational environments with strict security policies.

When it works best: Security-conscious environments, development on shared machines, minimal footprint requirements.

Running a multi-container application:

Create a pod to group related containers

podman pod create --name myapp-pod -p 3000:3000
Start the database

podman run -d \
  --pod myapp-pod \
  --name myapp-db \
  -e POSTGRES_PASSWORD=secret \
  postgres:15
Start the API

podman run -d \
  --pod myapp-pod \
  --name myapp-api \
  -e DATABASE_URL=postgresql://postgres:secret@localhost/myapp \
  myapp/api:latest
Check pod status

podman pod ps
podman pod logs myapp-pod

Podman generates Kubernetes-compatible YAML, which becomes valuable if you eventually migrate to a fuller orchestration platform:

podman generate kube myapp-pod > deployment.yaml

K3s

K3s packages full Kubernetes into a binary under 100MB. It strips non-essential features while retaining the critical functionality: pod management, services, ingress, and the Kubernetes API. Single-node K3s clusters run comfortably on a $10 VPS with 2GB RAM.

The tradeoff is operational complexity. Kubernetes manifests require more structure than Docker Compose files, and debugging in a K3s environment demands familiarity with kubectl, pod logs, and container networking.

When it works best: Production workloads requiring horizontal scaling, learning Kubernetes without enterprise overhead, eventually needing multi-node clusters.

Deploying an application:

Save as deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
  labels:
    app: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: myapp/api:latest
        ports:
        - containerPort: 3000
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: app-secrets
              key: database-url
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5


apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector:
    app: api
  ports:
  - port: 80
    targetPort: 3000
  type: ClusterIP

Apply the manifest:

kubectl apply -f deployment.yaml
kubectl get pods -w

Coolify

Coolify provides a web-based interface that abstracts Kubernetes complexity. You connect your Git repository, configure build settings through a GUI, and Coolify handles container building, deployment, and health monitoring.

The platform targets teams that want Kubernetes capabilities without writing YAML. It's particularly useful if you're comfortable with web interfaces and prefer visual feedback over command-line configuration.

When it works best: Teams preferring GUI management, rapid deployments without YAML expertise, integrating multiple data sources through a unified interface.

Note that Coolify requires its own hosting infrastructure. The management interface consumes resources, so allocate at least 4GB RAM for a self-hosted instance.

Dokku

Dokku treats your server like a mini Heroku. You push code via Git, and Dokku detects your language, builds the container, and deploys it. The workflow feels natural for developers accustomed to Heroku or similar Platform-as-a-Service offerings.

Dokku works exceptionally well for single-application deployments where you want zero configuration after initial setup.

When it works best: Single application per server, preferring Git-push deployments, wanting Heroku-like experience on own infrastructure.

Basic deployment:

Server-side: create the application

dokku apps:create api
Add a PostgreSQL database

dokku postgres:create api-db
dokku postgres:link api-db api
Client-side: add Dokku as a remote

git remote add dokku dokku@your-server:api
Deploy

git push dokku main

Dokku automatically builds from your pushed code, creates environment variables, and manages database links.

Comparison Matrix

The following table evaluates each tool across dimensions critical for solo developers:

| Tool | Complexity | Scalability | Learning Curve | Resource Usage | Best For | |------|------------|-------------|----------------|----------------|----------| | Docker Compose | Low | Single node | Minimal | Low (minimal overhead) | Prototypes, small production | | Podman | Low | Single node | Minimal | Very low (daemonless) | Security-sensitive environments | | K3s | Medium | Multi-node | Moderate | Low (~1GB RAM) | Production with scaling potential | | Coolify | Medium | Multi-node | Low (GUI-based) | Medium (web interface) | Teams avoiding CLI | | Dokku | Low | Single node | Low | Low | Single-app deployments |

For solo developers with modest traffic, Docker Compose covers most needs. If you eventually require horizontal scaling, K3s provides a migration path without discarding everything. Podman serves specific security constraints, while Coolify and Dokku suit teams that prioritize deployment simplicity over flexibility.

Deployment Recipes

Recipe 1: Docker Compose with Production-Ready Setup

This recipe extends the basic Docker Compose setup with production concerns: health checks, restart policies, and resource limits.

docker-compose.prod.yml

version: '3.8'
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    env_file:
      - .env.production
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 512M
        reservations:
          cpus: '0.25'
          memory: 256M
    healthcheck:
      test: ["CMD", "wget", "--quiet", "--tries=1", "--spider", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
  db:
    image: postgres:15-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
    env_file:
      - .env.production
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 1G
        reservations:
          cpus: '0.5'
          memory: 512M
  cache:
    image: redis:7-alpine
    volumes:
      - redis_data:/data
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: '0.25'
          memory: 320M
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./ssl:/etc/nginx/ssl:ro
    depends_on:
      - api
    restart: unless-stopped
volumes:
  postgres_data:
  redis_data:

Deploy with:

docker-compose -f docker-compose.prod.yml up -d
docker-compose -f docker-compose.prod.yml logs -f

Recipe 2: K3s Single-Node Production Deployment

A complete K3s deployment with ingress and persistent storage.

Install K3s

curl -sfL https://get.k3s.io | K3S_KUBECONFIG_MODE="644" sh -
Save the kubeconfig for local access

sudo cat /etc/rancher/k3s/k3s.yaml > ~/k3s.yaml
export KUBECONFIG=~/k3s.yaml
Create namespace

kubectl create namespace production
Apply deployment

kubectl apply -f - <
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: myapp/api:v1.2.0
        ports:
        - containerPort: 3000
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: api-secrets
              key: database-url
        volumeMounts:
        - name: data
          mountPath: /app/data
        resources:
          requests:
            memory: "128Mi"
            cpu: "100m"
          limits:
            memory: "256Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: postgres-pvc


apiVersion: v1
kind: Service
metadata:
  name: api-service
  namespace: production
spec:
  selector:
    app: api
  ports:
  - port: 80
    targetPort: 3000
  type: ClusterIP


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
spec:
  rules:
  - host: api.yourdomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
EOF

Recipe 3: Dokku Zero-Config Deployment

A streamlined path from code to running application.

On the server, install Dokku (Ubuntu 22.04)

wget https://dokku.com/install/v0.32.4/bootstrap.sh
sudo DOKKU_VHOST=yourdomain.com DOKKU_HOST_IP=203.0.113.10 bootstrap.sh
Initialize the app

dokku apps:create myapp
Add PostgreSQL plugin and create database

dokku plugin:install https://github.com/dokku/dokku-postgres.git
dokku postgres:create myapp-db
Link database to app

dokku postgres:link myapp-db myapp
Set environment variables

dokku config:set myapp NODE_ENV=production PORT=3000
Configure SSL (using Let's Encrypt)

dokku letsencrypt:enable myapp
Add domain

dokku domains:add myapp api.yourdomain.com
On local machine, add remote and deploy

git remote add dokku dokku@yourdomain.com:myapp
git push dokku main

Monitoring Your Containers

Regardless of which tool you choose, observability matters. At 2 AM, you want to know why your site is down before users report it.

Basic Container Stats

Docker and Podman stats:

docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.NetIO}}"

This single command reveals CPU percentage, memory usage, and network I/O for every running container.

Monitoring Stack with Prometheus and Grafana

A lightweight monitoring stack suitable for single-node deployments:

monitoring/docker-compose.yml

version: '3.8'
services:
  prometheus:
    image: prom/prometheus:latest
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'
      - '--storage.tsdb.path=/prometheus'
      - '--web.console.libraries=/etc/prometheus/console_libraries'
      - '--web.console.templates=/etc/prometheus/consoles'
    ports:
      - "9090:9090"
    restart: unless-stopped
    networks:
      - monitoring
  node-exporter:
    image: prom/node-exporter:latest
    command:
      - '--path.procfs=/host/proc'
      - '--path.sysfs=/host/sys'
      - '--collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($$|/)'
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro
    ports:
      - "9100:9100"
    restart: unless-stopped
    networks:
      - monitoring
  grafana:
    image: grafana/grafana:latest
    volumes:
      - grafana_data:/var/lib/grafana
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=admin
      - GF_USERS_ALLOW_SIGN_UP=false
    ports:
      - "3001:3000"
    restart: unless-stopped
    networks:
      - monitoring
volumes:
  prometheus_data:
  grafana_data:
networks:
  monitoring:

The accompanying prometheus.yml:

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']
  - job_name: 'containers'
    static_configs:
      - targets: ['cadvisor:8080']

Start monitoring with:

docker-compose -f monitoring/docker-compose.yml up -d

Access Grafana at http://your-server:3001 (default credentials: admin/admin).

Simple Logging with Cron

For small deployments, a simple cron job that logs container stats periodically may suffice:

/5    * docker stats --no-stream >> /var/log/container_stats.log

Common Pitfalls

Avoiding these mistakes will save hours of troubleshooting:

Over-engineering the initial setup catches many developers. Starting with Kubernetes when Docker Compose would work creates unnecessary complexity. Raj, from our opening scenario, spent two weeks configuring K3s before realizing his 500-user application didn't need it. He switched to Docker Compose and deployed the same stack in an afternoon.

Aiko, a freelance developer in Tokyo, made a similar mistake with her client project. She set up a full Kubernetes cluster for a simple Laravel application serving 50 concurrent users. The client ended up paying for infrastructure they never used. After switching to Docker Compose, their monthly bill dropped from $120 to $35.

Sofia, a startup founder in Berlin, learned about health checks the hard way. Her container appeared to be running, but the application inside had crashed. Users saw random 502 errors for three days before she noticed. Now she defines liveness and readiness probes for every service.

Ignoring health checks leads to silent failures. Containers that appear running but aren't serving traffic waste resources and confuse debugging. Always define liveness and readiness probes.

Failing to automate backups ranks among the most expensive mistakes. Database volumes disappear when you least expect it. Schedule regular backups regardless of which orchestration tool you use.

Not documenting your deployment process creates bus factor problems. Even for solo projects, write down the steps to recreate your infrastructure. Future you will thank present you.

Lessons Learned

  • Docker Compose handles most solo developer workloads — only move to Kubernetes when you genuinely need horizontal scaling
  • Health checks are non-negotiable; they distinguish running containers from healthy services
  • Choose tools that match your operational tolerance, not your aspirational scale
  • Resource limits prevent one misbehaving service from consuming your entire server
  • Automate backups before you need them

    • Actionable Takeaways

  • Audit your current deployment — Write down every manual step you perform, then evaluate which orchestration tool eliminates the most steps

  • Add health checks to existing containers — Start with a simple HTTP endpoint that confirms your service responds, then refine from there

  • Set resource limits — Even for small deployments, limit each container to 50-75% of available memory to prevent one service from crashing everything

  • Schedule daily backups — Use cron with a simple script that copies volumes to object storage; test restoration quarterly

  • Document your stack — Create a single README that lists every service, its purpose, and the command to restart it
