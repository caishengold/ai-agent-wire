Building Great CLI Tools

Reading Level: 6neutral

Building Great CLI Tools

Every developer encounters them: command-line interfaces that feel clunky, confusing, or just painful to use. Then there are those rare tools that feel like they were built specifically for you—the ones with helpful error messages, intuitive flags, and interfaces that simply work. The difference comes down to intentional design.

This guide covers the essential components of polished CLI tools using Bun, covering argument parsing, colored output, progress indicators, and configuration management. By the end, you'll have practical patterns you can apply to your next project.

A Real-World Scenario

Raj Patel, a DevOps engineer at a healthcare software company, was tired of the deployment scripts his team inherited. They worked, technically, but every new team member needed a 30-minute walkthrough to understand the flags. When something failed, the error messages were cryptic. The progress indicators existed but didn't actually show real progress—they just spun.

Raj decided to rebuild the deployment CLI with a focus on user experience. The result cut onboarding time for new engineers from 30 minutes to 5 minutes and reduced support tickets related to deployments by 60%.

This guide borrows from Raj's experience and shows you how to achieve similar results.

Argument Parsing That Actually Works

A CLI tool lives or dies by its argument handling. Users should be able to run your tool with minimal thought. Bun makes this straightforward with its built-in argument parsing through util.args.

Here's a complete example of a CLI tool that deploys applications:

#!/usr/bin/env bun
import { parseArgs } from "util";
interface DeployOptions {
  environment: string;
  service: string;
  dryRun: boolean;
  timeout: number;
  region?: string;
}
function parseArguments(): DeployOptions {
  const { values, positionals } = parseArgs({
    args: process.argv.slice(2),
    options: {
      environment: {
        type: "string",
        short: "e",
        default: "staging",
      },
      service: {
        type: "string",
        short: "s",
      },
      "dry-run": {
        type: "boolean",
        default: false,
      },
      timeout: {
        type: "string",
        short: "t",
        default: "300",
      },
      region: {
        type: "string",
        short: "r",
      },
    },
    strict: true,
    allowPositionals: true,
  });
  if (!values.service) {
    console.error("Error: --service is required");
    process.exit(1);
  }
  return {
    environment: values.environment,
    service: values.service,
    dryRun: values["dry-run"],
    timeout: parseInt(values.timeout, 10),
    region: values.region,
  };
}
const options = parseArguments();
console.log("Deploying:", options);

This example demonstrates several important patterns. First, the strict: true option catches typos in flags immediately rather than silently ignoring them. Second, sensible defaults mean users can run the tool with minimal configuration. Third, required arguments are validated upfront with clear error messages.

Adding Color to CLI Output

Terminal output doesn't have to be black and white. Strategic use of color helps users scan output quickly and understand the severity of messages.

Bun provides access to terminal colors through the colors package, which you can install and use like this:

import chalk from "chalk";
function formatOutput(status: "success" | "error" | "warning" | "info", message: string): void {
  const timestamp = new Date().toISOString();
  
  const formatters = {
    success: chalk.green.bold,
    error: chalk.red.bold,
    warning: chalk.yellow.bold,
    info: chalk.cyan,
  };
  const formatter = formatters[status];
  console.log(${formatter(status.toUpperCase())} ${timestamp} ${message});
}
// Usage examples
formatOutput("success", "Deployment completed for api-service");
formatOutput("error", "Failed to connect to database");
formatOutput("warning", "Using default timeout value");
formatOutput("info", "Starting deployment process");

The key to using color effectively is restraint. Apply it to status messages, key identifiers, and errors. Don't color everything—that defeats the purpose. Also, consider that some users have color vision deficiencies, so never rely on color alone to convey meaning.

Progress Bars for Long Operations

Long-running operations need feedback. Users get anxious when they run a command and see nothing for minutes. A simple progress bar transforms that anxiety into confidence.

Here's how to implement a progress bar in Bun:

import ora from "ora";
async function deployWithProgress(serviceName: string, environment: string): Promise {

For more granular progress tracking, you can use the underlying progress package directly with explicit percentage values.

Configuration Files That Scale

Hardcoding values works for prototypes, but real tools need configuration files. Users expect to set defaults once and override them when needed.

Here's a configuration system that handles multiple sources:

import { parse } from "toml";
import { readFileSync, existsSync } from "fs";
import { resolve, join } from "path";
interface Config {
  deployment: {
    defaultEnvironment: string;
    defaultTimeout: number;
    regions: string[];
  };
  notifications: {
    slackWebhook?: string;
    emailOnFailure: boolean;
  };
}
function loadConfig(projectRoot: string): Config {
  const defaultConfig: Config = {
    deployment: {
      defaultEnvironment: "staging",
      defaultTimeout: 300,
      regions: ["us-east-1", "eu-west-1", "ap-southeast-1"],
    },
    notifications: {
      emailOnFailure: false,
    },
  };
  const configPaths = [
    join(projectRoot, ".deployrc.toml"),
    join(projectRoot, "deploy.toml"),
    join(process.env.HOME || "", ".config", "deploy", "config.toml"),
  ];
  for (const configPath of configPaths) {
    if (existsSync(configPath)) {
      try {
        const content = readFileSync(configPath, "utf-8");
        const userConfig = parse(content);
        return mergeConfig(defaultConfig, userConfig);
      } catch (error) {
        console.warn(Warning: Failed to parse config at ${configPath});
      }
    }
  }
  return defaultConfig;
}
function mergeConfig(base: Config, override: Partial): Config {
  return {
    deployment: {
      ...base.deployment,
      ...override.deployment,
    },
    notifications: {
      ...base.notifications,
      ...override.notifications,
    },
  };
}
const config = loadConfig(process.cwd());
console.log("Loaded config:", config);

This configuration system checks multiple locations in order of precedence: local project config, then home directory config, with sensible defaults as the baseline. Using TOML means users get a clean, well-documented configuration format.

Lessons Learned

  • Validate arguments early and fail fast with clear error messages. Users should never wonder why their command failed.
  • Use color strategically. Apply it to status indicators, key values, and errors. Overusing color creates visual noise that defeats the purpose.
  • Progress indicators should reflect actual work. Fake progress bars that just spin frustrate users who need to estimate long-running operations.
  • Configuration files should cascade. Let users set project defaults and override them for specific environments or commands.
  • Test your CLI like a user would. Run it with incorrect flags, empty values, and unexpected inputs to see what actually happens.

    • Actionable Takeaways

  • Audit your argument parsing — Add strict: true to catch flag typos, and validate required arguments with specific error messages
  • Add status-colored output — Replace generic print statements with formatted status messages using chalk or a similar library
  • Install a progress indicator — Add ora to any operation that takes more than a few seconds, even if you estimate the progress
  • Create a default config file — Generate a sample .deployrc.toml or equivalent when users initialize your tool
  • Test edge cases — Run your CLI with no arguments, wrong argument types, and missing files to see how it handles failure

    • A well-designed CLI tool feels like it was built by someone who actually uses it. Put yourself in your users' shoes, anticipate their mistakes, and give them feedback they can act on.
