Running OpenClaw + Cursor Agent as a 24/7 Unattended System

Enterprise AI agents need to operate continuously without human intervention. When Raj Patel, lead automation engineer at a mid-size logistics company in Hamburg, Germany, needed to deploy an AI-powered document processing system that ran around the clock, he faced a challenge common to many teams: how to keep AI agents running reliably without constant supervision.

This post walks through the architecture and implementation strategies for running OpenClaw and Cursor Agent as an unattended 24/7 system. You'll learn how to implement heartbeat monitoring, task scheduling, and error recovery mechanisms that keep your AI agents productive while you focus on other work.

The techniques covered here apply broadly to any AI agent deployment, but they're particularly relevant for OpenClaw users given its rich configuration options for unattended operation. Whether you're processing documents like Raj, monitoring systems, or handling customer inquiries across time zones, the principles remain the same.

The Real-World Challenge

Raj's team processes over 2,000 shipping documents daily. Their AI agent needed to monitor email inboxes, extract data from attachments, validate information against their ERP system, and flag exceptions for human review. The system had to work continuously because their customers spanned multiple time zones, from Tokyo to San Francisco.

Initial attempts with simple daemon processes failed within hours. Memory leaks caused gradual degradation. Network blips triggered unhandled exceptions. Weekend maintenance windows created data bottlenecks. Raj needed a robust architecture that could handle these challenges gracefully.

Heartbeat Implementation

The heartbeat mechanism serves as the vital sign monitor for your AI agent. It confirms the agent remains alive, responsive, and capable of processing work. Without proper heartbeat implementation, a failed agent can run undetected for hours, accumulating backlog and missing critical deadlines.

OpenClaw supports configurable heartbeat intervals through the agent configuration. Setting the heartbeat to "0" enables continuous monitoring mode, where the agent reports status after every operation completes.

interface HeartbeatConfig {
  every: number;
  capabilities: {
    inlineButtons: 'all' | 'limited' | 'none';
  };
}
const agentHeartbeat: HeartbeatConfig = {
  every: 0,
  capabilities: {
    inlineButtons: 'all'
  }
};

For external monitoring integration, implement a separate heartbeat exporter that reports to your observability infrastructure:

class AgentHeartbeatExporter {
  private lastHeartbeat: Date = new Date();
  private readonly endpoint: string;
  private readonly intervalMs: number = 30000;
  constructor(endpoint: string) {
    this.endpoint = endpoint;
  }
  async report(): Promise {
    const payload = {
      agentId: process.env.OPENCLAW_AGENT_ID,
      timestamp: new Date().toISOString(),
      uptime: process.uptime(),
      memoryUsage: process.memoryUsage(),
      status: 'healthy'
    };
    try {
      await fetch(this.endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(payload)
      });
      this.lastHeartbeat = new Date();
    } catch (error) {
      console.error('Heartbeat export failed:', error);
    }
  }
  start(): void {
    setInterval(() => this.report(), this.intervalMs);
  }
}
const exporter = new AgentHeartbeatExporter('https://monitoring.example.com/heartbeat');
exporter.start();

The key insight here is separating the agent's internal heartbeat from external monitoring. OpenClaw's built-in heartbeat manages agent-to-coordinator communication, while the exporter handles alerting and dashboards for your operations team.

Task Scheduling Architecture

Effective task scheduling for 24/7 agents requires a three-tier approach: immediate processing for urgent work, scheduled batches for predictable loads, and queue-based handling for background tasks. OpenClaw's cron system provides the foundation, while custom queue management handles the nuanced prioritization.

interface ScheduledTask {
  id: string;
  cronExpression: string;
  handler: () => Promise;
  retryPolicy: RetryPolicy;
  timeoutMs: number;
}
interface RetryPolicy {
  maxAttempts: number;
  backoffMs: number;
  backoffMultiplier: number;
}
class TaskScheduler {
  private tasks: Map = new Map();
  register(task: ScheduledTask): void {
    this.tasks.set(task.id, task);
    this.scheduleCron(task);
  }
  private scheduleCron(task: ScheduledTask): void {
    const cron = require('node-cron');
    cron.schedule(task.cronExpression, async () => {
      try {
        await this.executeWithTimeout(task);
      } catch (error) {
        await this.handleFailure(task, error);
      }
    });
  }
  private async executeWithTimeout(task: ScheduledTask): Promise {
    await Promise.race([
      task.handler(),
      new Promise((_, reject) => 
        setTimeout(() => reject(new Error('Timeout')), task.timeoutMs)
      )
    ]);
  }
  private async handleFailure(task: ScheduledTask, error: Error): Promise {
    const retryPolicy = task.retryPolicy;
    for (let attempt = 1; attempt <= retryPolicy.maxAttempts; attempt++) {
      const delay = retryPolicy.backoffMs  Math.pow(retryPolicy.backoffMultiplier, attempt - 1);
      await new Promise(resolve => setTimeout(resolve, delay));
      
      try {
        await task.handler();
        return;
      } catch (attemptError) {
        console.error(Attempt ${attempt} failed:, attemptError);
      }
    }
    await this.notifyFailure(task, error);
  }
  private async notifyFailure(task: ScheduledTask, error: Error): Promise {
    console.error(Task ${task.id} failed permanently:, error);
  }
}

This scheduler handles three critical scenarios. First, it respects timeout boundaries to prevent runaway tasks from consuming resources indefinitely. Second, it implements exponential backoff to give transient failures a chance to resolve. Third, it escalates to notification after exhausting retries, ensuring your team knows about persistent problems.

For Raj's document processing system, the scheduling looked like this:

const scheduler = new TaskScheduler();
scheduler.register({
  id: 'email-scan',
  cronExpression: '/5    ',
  handler: async () => {
    const emails = await fetchUnreadEmails();
    for (const email of emails) {
      await processEmailWithOpenClaw(email);
    }
  },
  retryPolicy: {
    maxAttempts: 3,
    backoffMs: 5000,
    backoffMultiplier: 2
  },
  timeoutMs: 120000
});
scheduler.register({
  id: 'document-validation',
  cronExpression: '0 /2   ',
  handler: async () => {
    const pendingDocs = await fetchPendingDocuments();
    for (const doc of pendingDocs) {
      await validateDocument(doc);
    }
  },
  retryPolicy: {
    maxAttempts: 5,
    backoffMs: 10000,
    backoffMultiplier: 1.5
  },
  timeoutMs: 300000
});

The email scanning runs every five minutes to catch new submissions quickly, while the validation batch runs every two hours to process accumulated work without overwhelming the ERP system.

Error Recovery Strategies

Error recovery transforms a fragile automation system into a resilient one. The core principle is assuming failures will happen and designing for graceful recovery rather than hoping everything works perfectly.

Circuit Breaker Implementation

When external services fail, your agent should stop hammering them and wait for recovery. The circuit breaker pattern manages this automatically:

class CircuitBreaker {
  private failures = 0;
  private lastFailureTime: Date | null = null;
  private state: 'closed' | 'open' | 'half-open' = 'closed';
  
  private readonly failureThreshold: number;
  private readonly resetTimeoutMs: number;
  constructor(failureThreshold: number = 5, resetTimeoutMs: number = 60000) {
    this.failureThreshold = failureThreshold;
    this.resetTimeoutMs = resetTimeoutMs;
  }
  async execute(operation: () => Promise): Promise {
    if (this.state === 'open') {
      if (this.shouldAttemptReset()) {
        this.state = 'half-open';
      } else {
        throw new Error('Circuit breaker is open');
      }
    }
    try {
      const result = await operation();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }
  private shouldAttemptReset(): boolean {
    if (!this.lastFailureTime) return false;
    return Date.now() - this.lastFailureTime.getTime() > this.resetTimeoutMs;
  }
  private onSuccess(): void {
    this.failures = 0;
    this.state = 'closed';
  }
  private onFailure(): void {
    this.failures++;
    this.lastFailureTime = new Date();
    if (this.failures >= this.failureThreshold) {
      this.state = 'open';
    }
  }
}

Integrate the circuit breaker with your external service calls:

const erpCircuitBreaker = new CircuitBreaker(5, 60000);
async function queryERP(orderId: string): Promise {
  return erpCircuitBreaker.execute(async () => {
    const response = await fetch(${ERP_BASE_URL}/orders/${orderId}, {
      headers: { 'Authorization': Bearer ${ERP_TOKEN} }
    });
    if (!response.ok) {
      throw new Error(ERP request failed: ${response.status});
    }
    return response.json();
  });
}

When the ERP system experiences issues, the circuit breaker prevents cascade failures. Your agent continues processing other work and automatically resumes ERP integration once the external system recovers.

Checkpointing for Long-Running Operations

For operations that span multiple steps or significant time, checkpointing ensures progress isn't lost when failures occur:

interface Checkpoint {
  operationId: string;
  step: number;
  completedSteps: string[];
  context: Record;
  timestamp: Date;
}
class CheckpointManager {
  private readonly storagePath: string;
  constructor(storagePath: string) {
    this.storagePath = storagePath;
  }
  async save(checkpoint: Checkpoint): Promise {
    const filename = ${this.storagePath}/${checkpoint.operationId}.json;
    await fs.writeFile(filename, JSON.stringify(checkpoint));
  }
  async load(operationId: string): Promise {
    const filename = ${this.storagePath}/${operationId}.json;
    try {
      const data = await fs.readFile(filename, 'utf-8');
      return JSON.parse(data);
    } catch {
      return null;
    }
  }
  async clear(operationId: string): Promise {
    const filename = ${this.storagePath}/${operationId}.json;
    try {
      await fs.unlink(filename);
    } catch {
      // File didn't exist, which is fine
    }
  }
}

For Raj's document processing, each document moved through validation stages with checkpoints between each step:

const checkpointManager = new CheckpointManager('/tmp/checkpoints');
async function processDocument(documentId: string, content: Buffer): Promise {
  let checkpoint = await checkpointManager.load(documentId);
  
  if (!checkpoint) {
    checkpoint = {
      operationId: documentId,
      step: 0,
      completedSteps: [],
      context: { content: content.toString('base64') },
      timestamp: new Date()
    };
  }
  try {
    if (checkpoint.step < 1) {
      await validateFormat(checkpoint.context.content);
      checkpoint.completedSteps.push('format-validation');
      checkpoint.step = 1;
      await checkpointManager.save(checkpoint);
    }
    if (checkpoint.step < 2) {
      const extracted = await extractData(checkpoint.context.content);
      checkpoint.context.extractedData = extracted;
      checkpoint.step = 2;
      await checkpointManager.save(checkpoint);
    }
    if (checkpoint.step < 3) {
      await enrichWithERPData(checkpoint.context.extractedData);
      checkpoint.completedSteps.push('erp-enrichment');
      checkpoint.step = 3;
      await checkpointManager.save(checkpoint);
    }
    await checkpointManager.clear(documentId);
    console.log(Document ${documentId} processed successfully);
  } catch (error) {
    console.error(Processing failed at step ${checkpoint.step}:, error);
    throw error;
  }
}

If the process crashed midway through enrichment, restarting picks up exactly where it left off rather than reprocessing from the beginning.

Lessons Learned

After running the system for six months, Raj's team gathered these insights:

  • Heartbeat separation proved essential. OpenClaw's internal heartbeat handles agent coordination, but external monitoring needs its own reporting channel to integrate with enterprise alerting systems.

  • Exponential backoff with jitter prevents the "thundering herd" problem. When the ERP system recovered, all waiting agents would immediately retry, potentially causing another outage. Adding random jitter spread the load naturally.

  • Checkpoint granularity matters. They initially checkpointed only at major phases, but mid-phase failures still caused significant rework. Finer-grained checkpoints reduced maximum reprocessing time from 30 minutes to 5 minutes.

  • Model fallbacks require testing. Their configured fallback model initially failed on their specific document formats. Regular testing of fallback paths revealed the incompatibility before it caused a production incident.

  • Alert fatigue is real. They started with alerts for every failure and quickly learned to distinguish recoverable failures (which get retried automatically) from permanent failures (which need human attention). The alerting system only triggers after retries are exhausted.

    • Actionable Takeaways

  • Separate monitoring layers — Implement both internal heartbeat (for OpenClaw coordination) and external heartbeat (for your observability stack). This provides clear separation between agent health and system health.

  • Configure exponential backoff with jitter — Set initial delays around 5-10 seconds with a multiplier of 1.5-2 and maximum attempts of 3-5 for most external service calls. Add random jitter between 0-30% of the delay to prevent synchronized retries.

  • Implement checkpointing for any operation exceeding 60 seconds — Save progress after each significant step to persistent storage. On restart, check for existing checkpoints before starting fresh.

  • Test fallback paths regularly — Schedule monthly tests of model fallback and service fallback configurations. Untested fallbacks often fail when you need them most.

  • Alert only after retry exhaustion — Configure your alerting to notify after all automatic retries fail. This reduces alert noise while ensuring persistent problems reach your team.
