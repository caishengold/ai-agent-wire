SSE vs WebSocket vs Long Polling — when to use each, scalability, code examples in Bun

SSE vs WebSocket vs Long Polling — when to use each, scalability, code examples in Bun

Real-time communication is essential for modern web applications. Whether you're building a live dashboard, a chat application, or a collaborative editing tool, choosing the right transport mechanism directly impacts user experience, server scalability, and development complexity.

Three technologies dominate this space: Server-Sent Events (SSE), WebSockets, and Long Polling. Each solves the same problem—server-to-client push communication—but with different trade-offs. This guide walks through when to use each, with practical code examples in Bun.

The scenario

Raj Mehta, backend lead at a Series B logistics startup, faced a familiar dilemma. His team was building a real-time fleet tracking dashboard that needed to display vehicle locations, driver status updates, and delivery notifications. Initial implementation used polling every 5 seconds, which worked but felt clunky.

"We had three options on the table," Raj explained. "SSE for its simplicity, WebSockets for full duplex, or Long Polling as a fallback for legacy systems. We chose wrong initially—our WebSocket server collapsed during a marketing event when 10,000 concurrent users connected simultaneously."

His team eventually landed on SSE for status updates (one-way server push) and WebSockets for location tracking (bidirectional). The solution handled 50,000 concurrent connections without breaking a sweat.

This article breaks down when each technology shines.

Server-Sent Events (SSE)

SSE provides a one-way channel from server to client over a single HTTP connection. The server pushes updates; the client receives them. It's remarkably simple to implement and works over standard HTTP/1.1 connections.

Best for: Live feeds, notifications, dashboards, scenarios where the server needs to push data but the client doesn't need to send messages back frequently.

Strengths: Automatic reconnection, works through proxies and firewalls, minimal client-side code, HTTP/2 compatible.

Weaknesses: One-way only, connection limits (6 per domain in HTTP/1.1), no binary support.

Here is a complete Bun server that streams server-sent events to connected clients:

// sse-server.ts
import { serve } from "bun";
const clients = new Set();
const server = serve({
  port: 3000,
  fetch(req, server) {
    const url = new URL(req.url);
    
    if (url.pathname === "/events") {
      const success = server.upgrade(req);
      if (success) return;
    }
    
    if (url.pathname === "/sse") {
      const stream = new ReadableStream({
        start(controller) {
          const encoder = new TextEncoder();
          
          const send = (data: string) => {
            controller.enqueue(encoder.encode(data: ${data}\n\n));
          };
          
          // Send initial connection message
          send(JSON.stringify({ type: "connected", timestamp: Date.now() }));
          
          // Simulate periodic updates every 2 seconds
          const interval = setInterval(() => {
            const update = {
              type: "position",
              vehicleId: TRUCK-${Math.floor(Math.random()  100)},
              lat: 40.7128 + (Math.random() - 0.5)  0.1,
              lng: -74.0060 + (Math.random() - 0.5)  0.1,
              timestamp: Date.now()
            };
            send(JSON.stringify(update));
          }, 2000);
          
          req.signal.addEventListener("abort", () => {
            clearInterval(interval);
            controller.close();
          });
        }
      });
      
      return new Response(stream, {
        headers: {
          "Content-Type": "text/event-stream",
          "Cache-Control": "no-cache",
          "Connection": "keep-alive"
        }
      });
    }
    
    return new Response("SSE Demo Server", { status: 200 });
  }
});
console.log(SSE server running at http://localhost:${server.port});

Run the server with bun run sse-server.ts and open the client in a browser console or use a simple HTML file.

WebSockets

WebSockets provide full-duplex communication over a single TCP connection. Once established, both client and server can send messages at any time without the overhead of HTTP headers. This makes it ideal for chat applications, real-time gaming, and collaborative editing.

Best for: Chat, gaming, collaborative tools, any scenario requiring bidirectional communication with low latency.

Strengths: True bidirectional communication, binary support, single connection after handshake, extremely low overhead per message.

Weaknesses: More complex to scale (requires sticky sessions or external state), proxy/load balancer configuration, connection drops need manual reconnection handling.

Here is a Bun WebSocket server with client connection handling:

// websocket-server.ts
import { serve } from "bun";
interface Client {
  id: string;
  role: "driver" | "dispatcher" | "admin";
  ws: WebSocket;
}
const clients = new Map();
const server = serve({
  port: 3001,
  fetch(req, server) {
    const url = new URL(req.url);
    
    if (url.pathname === "/ws") {
      const success = server.upgrade(req, {
        data: { 
          id: crypto.randomUUID(),
          role: url.searchParams.get("role") as "driver" | "dispatcher" || "driver"
        }
      });
      
      if (success) return;
    }
    
    return new Response("WebSocket Server", { status: 200 });
  },
  websocket: {
    open(ws) {
      const data = ws.data as { id: string; role: string };
      clients.set(data.id, { 
        id: data.id, 
        role: data.role as "driver" | "dispatcher" | "admin",
        ws 
      });
      
      console.log(Client connected: ${data.id} (${data.role}));
      
      // Broadcast to all dispatchers
      broadcastToRole("dispatcher", {
        type: "client_joined",
        clientId: data.id,
        role: data.role,
        timestamp: Date.now()
      });
    },
    
    message(ws, message) {
      const data = ws.data as { id: string; role: string };
      
      try {
        const payload = JSON.parse(message.toString());
        
        // Route messages based on type
        switch (payload.type) {
          case "location_update":
            // Broadcast location to dispatchers
            broadcastToRole("dispatcher", {
              type: "location_update",
              clientId: data.id,
              lat: payload.lat,
              lng: payload.lng,
              timestamp: Date.now()
            });
            break;
            
          case "dispatch_request":
            // Send to specific driver
            sendToClient(payload.targetId, {
              type: "new_dispatch",
              pickup: payload.pickup,
              destination: payload.destination
            });
            break;
        }
      } catch (e) {
        console.error("Failed to parse message:", e);
      }
    },
    
    close(ws) {
      const data = ws.data as { id: string };
      const client = clients.get(data.id);
      
      if (client) {
        broadcastToRole("dispatcher", {
          type: "client_left",
          clientId: data.id,
          timestamp: Date.now()
        });
        clients.delete(data.id);
      }
    }
  }
});
function broadcastToRole(role: string, message: object) {
  for (const client of clients.values()) {
    if (client.role === role) {
      client.ws.send(JSON.stringify(message));
    }
  }
}
function sendToClient(clientId: string, message: object) {
  const client = clients.get(clientId);
  if (client) {
    client.ws.send(JSON.stringify(message));
  }
}
console.log(WebSocket server running at ws://localhost:${server.port}/ws);

Client implementation with auto-reconnection:

// websocket-client.ts
class WebSocketClient {
  private ws: WebSocket | null = null;
  private reconnectAttempts = 0;
  private maxReconnectAttempts = 5;
  private reconnectDelay = 1000;
  private url: string;
  private role: string;
  
  constructor(url: string, role: string) {
    this.url = url;
    this.role = role;
  }
  
  connect() {
    const wsUrl = ${this.url}?role=${this.role};
    this.ws = new WebSocket(wsUrl);
    
    this.ws.onopen = () => {
      console.log("WebSocket connected");
      this.reconnectAttempts = 0;
    };
    
    this.ws.onmessage = (event) => {
      const data = JSON.parse(event.data);
      this.handleMessage(data);
    };
    
    this.ws.onclose = () => {
      console.log("WebSocket disconnected");
      this.attemptReconnect();
    };
    
    this.ws.onerror = (error) => {
      console.error("WebSocket error:", error);
    };
  }
  
  private handleMessage(data: any) {
    switch (data.type) {
      case "location_update":
        console.log(Vehicle ${data.clientId} moved to, ${data.lat}, ${data.lng});
        break;
      case "new_dispatch":
        console.log("New dispatch received:", data);
        break;
    }
  }
  
  private attemptReconnect() {
    if (this.reconnectAttempts >= this.maxReconnectAttempts) {
      console.error("Max reconnect attempts reached");
      return;
    }
    
    this.reconnectAttempts++;
    const delay = this.reconnectDelay  Math.pow(2, this.reconnectAttempts - 1);
    
    console.log(Reconnecting in ${delay}ms (attempt ${this.reconnectAttempts}));
    setTimeout(() => this.connect(), delay);
  }
  
  send(message: object) {
    if (this.ws?.readyState === WebSocket.OPEN) {
      this.ws.send(JSON.stringify(message));
    }
  }
  
  close() {
    this.ws?.close();
  }
}
// Usage
const client = new WebSocketClient("ws://localhost:3001/ws", "driver");
client.connect();
// Send location update
client.send({
  type: "location_update",
  lat: 40.7128,
  lng: -74.0060
});

Long Polling

Long Polling works by having the client make a request, the server holds that request open until new data is available, then responds. The client immediately makes another request after receiving the response. It's essentially a workaround for environments where WebSockets aren't available.

Best for: Legacy system compatibility, environments with strict proxy restrictions, simple implementations where other methods aren't available.

Strengths: Works everywhere (no special protocol), straightforward to implement, handles temporary disconnections gracefully.

Weaknesses: Higher latency than WebSockets, more server resources (one connection per client), no real-time guarantee.

Here is a simple Long Polling implementation in Bun:

// long-polling-server.ts
import { serve } from "bun";
interface PendingRequest {
  resolve: (response: Response) => void;
  timestamp: number;
}
const pendingRequests: PendingRequest[] = [];
const messageQueue: any[] = [];
const server = serve({
  port: 3002,
  fetch(req, server) {
    const url = new URL(req.url);
    
    if (url.pathname === "/poll") {
      // Long polling endpoint - holds connection until data available
      return new Promise((resolve) => {
        const timeout = setTimeout(() => {
          // Remove from pending
          const index = pendingRequests.findIndex(r => r.resolve === resolve);
          if (index > -1) pendingRequests.splice(index, 1);
          
          resolve(new Response(JSON.stringify({ 
            messages: [],
            timestamp: Date.now() 
          }), { headers: { "Content-Type": "application/json" } }));
        }, 30000); // 30 second timeout
        
        pendingRequests.push({
          resolve: (response) => {
            clearTimeout(timeout);
            resolve(response);
          },
          timestamp: Date.now()
        });
      });
    }
    
    if (url.pathname === "/publish") {
      // Endpoint to publish messages to all waiting clients
      const newMessage = {
        id: crypto.randomUUID(),
        data: { text: "New update from server", timestamp: Date.now() }
      };
      
      messageQueue.push(newMessage);
      
      // Respond to all pending requests with the message
      for (const pending of pendingRequests) {
        pending.resolve(new Response(JSON.stringify({ 
          messages: [newMessage],
          timestamp: Date.now()
        }), { headers: { "Content-Type": "application/json" } }));
      }
      pendingRequests.length = 0;
      
      return new Response(JSON.stringify({ success: true, queued: 1 }));
    }
    
    return new Response("Long Polling Server", { status: 200 });
  }
});
console.log(Long polling server running at http://localhost:${server.port});

Client-side long polling implementation:

// long-polling-client.ts
class LongPollingClient {
  private baseUrl: string;
  private isPolling = false;
  private pollInterval = 1000;
  
  constructor(baseUrl: string) {
    this.baseUrl = baseUrl;
  }
  
  async startPolling() {
    this.isPolling = true;
    
    while (this.isPolling) {
      try {
        const response = await fetch(${this.baseUrl}/poll, {
          method: "GET",
          headers: { "Content-Type": "application/json" }
        });
        
        if (!response.ok) {
          console.error("Poll failed:", response.status);
          await this.sleep(this.pollInterval);
          continue;
        }
        
        const data = await response.json();
        
        if (data.messages && data.messages.length > 0) {
          for (const message of data.messages) {
            console.log("Received:", message);
          }
        }
      } catch (error) {
        console.error("Polling error:", error);
        await this.sleep(this.pollInterval);
      }
    }
  }
  
  stopPolling() {
    this.isPolling = false;
  }
  
  private sleep(ms: number) {
    return new Promise(resolve => setTimeout(resolve, ms));
  }
  
  async publish(message: any) {
    await fetch(${this.baseUrl}/publish, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(message)
    });
  }
}
// Usage
const client = new LongPollingClient("http://localhost:3002");
client.startPolling();
// Simulate server push after 3 seconds
setTimeout(async () => {
  await client.publish({ text: "Hello from server!" });
}, 3000);
// Cleanup when done
window.addEventListener("beforeunload", () => {
  client.stopPolling();
});

Comparison

Each technology has distinct characteristics that make it suitable for different scenarios:

| Feature | SSE | WebSocket | Long Polling | |---------|-----|-----------|--------------| | Direction | Server → Client | Bidirectional | Bidirectional | | Protocol | HTTP/1.1 | WebSocket | HTTP | | Connection overhead | Low (after initial) | Very low | High (per request) | | Binary support | No | Yes | No | | Auto-reconnect | Built-in | Manual | Automatic on next poll | | Browser support | Modern browsers | Universal | Universal | | Proxy/firewall | Usually works | May fail | Works everywhere | | Scalability | Good | Requires sticky sessions | Poor | | Latency | Low | Lowest | Variable |

Lessons learned

  • Choose SSE for one-way server pushes. It handles reconnection automatically and integrates easily with existing HTTP infrastructure.
  • Reserve WebSockets for true bidirectional use cases. The complexity pays off when you need frequent, low-latency communication in both directions.
  • Long polling should be a fallback option. It works everywhere but consumes significantly more server resources than the alternatives.
  • Consider connection limits. HTTP/1.1 limits SSE to 6 connections per domain—HTTP/2 helps, or use multiple subdomains for large-scale deployments.
  • Plan for scaling from day one. WebSocket deployments need sticky sessions or external state management; SSE scales more naturally with standard load balancers.

    • Actionable takeaways

  • Audit your real-time requirements — If you only need server-to-client updates, SSE is simpler and more reliable than WebSockets.

  • Test through proxies early — Deploy your chosen technology behind your actual infrastructure (load balancers, CDNs) before committing to it.

  • Monitor connection counts — Set up metrics for active connections, reconnection frequency, and message delivery latency.

  • Start with SSE for dashboards — Implement vehicle tracking or monitoring dashboards using SSE first; upgrade to WebSockets only if bidirectional features become necessary.

  • Implement graceful degradation — Build connection fallbacks (WebSocket → SSE → Long Polling) for enterprise environments with strict network policies.
