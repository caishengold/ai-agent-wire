Building a Zero-Dependency Observability Dashboard for AI Agents

Aiko stared at her terminal, watching a wall of logs fly by. Somewhere in that blur of JSON and timestamps, an agent was stuck in a loop, burning through API credits at 3 AM. She had no visual way to see how many tasks were active or if the proxy was even healthy without grepping through megabytes of text. This is the "black box" problem of AI operations: when you scale from one agent to fifty, logs aren't enough. You need a cockpit.

We decided to build a single-file dashboard for our ai-agent-ops stack. No React, no Tailwind, no npm install. Just raw HTML, CSS, and vanilla JavaScript fetching from our Bun-powered proxy.

The Real-World Scenario: Why Logs Fail at Scale

In our production environment, we manage a fleet of autonomous agents performing everything from code audits to CRM updates. Last month, Raj noticed a sudden spike in latency. By the time he manually queried the SQLite database to find the bottleneck, the system had already failed three critical deployments.

The problem wasn't the data—it was the accessibility. We had /health and /stats endpoints, but they were hidden behind curl commands. We needed a "single pane of glass" that Aiko could leave open on a secondary monitor to spot anomalies before they became outages.

Implementation: The Single-File Approach

We chose a single-file architecture for portability. You can drop this dashboard.html into any directory, and as long as your proxy is running, it works.

1. The Data Fetching Logic

We use the fetch API with a simple token-based authentication. Since our proxy runs on Bun, we can handle these requests with sub-millisecond latency.

// dashboard.html (JS Section)
async function fetchData(endpoint) {
    const API_TOKEN = 'local'; // Default local development token
    const res = await fetch(${endpoint}?token=${API_TOKEN});
    if (!res.ok) throw new Error(HTTP ${res.status});
    return res.json();
}
async function updateDashboard() {
    try {
        const [health, stats, dashboard] = await Promise.all([
            fetchData('/health'),
            fetchData('/stats'),
            fetchData('/dashboard')
        ]);
        renderUI(health, stats, dashboard);
    } catch (err) {
        showError(err.message);
    }
}

What Went Wrong: Lessons from the Trenches

We didn't get it right on the first try. Initially, we tried to build a live-streaming dashboard using WebSockets.

The Failure: We implemented a WebSocket server inside cursor-proxy.ts to push every task update. In a high-concurrency test (50+ tasks/second), the overhead of managing WebSocket heartbeats and state serialization started consuming 15% of our CPU, which should have been reserved for the AI agents themselves.

The Fix: We pivoted to a "Pull" model. The dashboard now polls every 30 seconds. It's less "real-time," but the performance impact is negligible (under 0.5% CPU). We learned that for internal monitoring, stale data by 30 seconds is better than a crashed system.

Authenticity and Metrics

In our current deployment, this dashboard monitors:

  • Throughput: ~1,200 requests per day.
  • Success Rate: We maintain a 98.2% success rate; the dashboard highlights the 1.8% errors in bright red.
  • Latency: Average response time from the /dashboard endpoint is 12ms, including the SQLite queries.

    • Actionable Takeaways for Your Ops

    If you are managing AI agents today, don't wait for a "v1.0" dashboard. Do these three things:

  • Expose a Health Endpoint: Add a /health route to your agent runner that returns the number of active processes.
  • Visualize Concurrency: Use a simple CSS grid to display "Active vs. Max" tasks. It's the fastest way to see if you're hitting rate limits.
  • Automate Refresh: Use setInterval in your HTML to keep the data fresh. Don't make your team click "Refresh" manually.
