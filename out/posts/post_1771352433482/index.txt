  return { _tag: 'Left', left: error };
}</p><p class="text-slate-300 leading-relaxed mb-4">function right<E, T>(data: T): Either<E, T> {
  return { _tag: 'Right', right: data };
}</p><p class="text-slate-300 leading-relaxed mb-4">function isLeft<E, T>(either: Either<E, T>): either is Left<E> {
  return either._tag === 'Left';

  return either._tag === 'Right';
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The real power of Either comes from the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">map</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flatMap</code> (also called <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bind</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">andThen</code>) functions. Choose one approach per function and stick with it.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Conclusion</h2></p><p class="text-slate-300 leading-relaxed mb-4">Aiko eventually refactored that tangled payment function into a clean Either-based pipeline. Her team found bugs in production that had been silently swallowed for months.</p><p class="text-slate-300 leading-relaxed mb-4">The best pattern depends on your context. Use exceptions for truly exceptional situations. Use result types when callers need to make decisions based on failure type. Use Either when you want composable pipelines with automatic error propagation. All three have a place in a mature TypeScript codebase.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons-Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">TypeScript's type system is only as strong as its error handling. When exceptions escape unchecked, they bypass the safety the type system provides. Result types and Either make errors explicit in function signatures, forcing callers to acknowledge and handle failure cases.</p><p class="text-slate-300 leading-relaxed mb-4">The functional chaining patterns in Either require some upfront learning but pay dividends in code readability for complex validation and transformation pipelines. Result types achieve similar goals with simpler mental models, making them more accessible to teams new to functional programming.</p><p class="text-slate-300 leading-relaxed mb-4">Regardless of which pattern you choose, consistency matters most. Mixed approaches in the same codebase create confusion and increase the likelihood of bugs.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4">Audit your codebase for functions that throw exceptions but do not document this in their type signatures. If callers typically cannot recover from failures, exceptions may be appropriate.
