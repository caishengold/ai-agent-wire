Error Handling Patterns in TypeScript: Result Types, Exceptions, Either

Error handling is one of those topics that every developer talks about but few master. When Aiko Tanaka joined a fintech startup in Tokyo as a senior TypeScript developer, she inherited a codebase where a single payment processing function had seventeen try-catch blocks nested inside each other. The function technically worked, but debugging it was a nightmare. "I would spend hours tracing through the call stack just to find out why a legitimate transaction was failing," Aiko recalled in a later team retrospective.

This article walks through three fundamental patterns for handling errors in TypeScript: traditional exceptions, result types, and the Either monad. By the end, you will understand when to use each approach and how to implement them effectively in real projects.

Understanding the Problem Space

Before diving into patterns, it is worth understanding why error handling matters so much in TypeScript specifically. TypeScript's type system gives us compile-time guarantees about our code's behavior, but traditional JavaScript exceptions can silently break those guarantees. When a function throws an exception, TypeScript's type checker has no way to know that something went wrong. The return type says "string" but sometimes you get nothing because an exception bubbled up instead.

This disconnect between the type system and error handling is the core problem these patterns solve. Each approach represents a different philosophy for making errors visible to the type system and manageable in code.

The Exception Pattern

The most familiar approach uses try-catch blocks to handle errors that functions throw. This pattern works exactly like it does in JavaScript, with TypeScript adding type information to caught errors.

class InsufficientFundsError extends Error {
  constructor(accountId: string, available: number, requested: number) {
    super(Account ${accountId} has ${available} but requested ${requested});
    this.name = 'InsufficientFundsError';
  }
}
class InvalidAccountError extends Error {
  constructor(accountId: string) {
    super(Account ${accountId} does not exist);
    this.name = 'InvalidAccountError';
  }
}
function transferFunds(
  fromAccount: string,
  toAccount: string,
  amount: number
): number {
  if (amount <= 0) {
    throw new Error('Transfer amount must be positive');
  }
  const sourceBalance = getAccountBalance(fromAccount);
  
  if (sourceBalance < amount) {
    throw new InsufficientFundsError(fromAccount, sourceBalance, amount);
  }
  if (!accountExists(toAccount)) {
    throw new InvalidAccountError(toAccount);
  }
  const newBalance = sourceBalance - amount;
  updateAccountBalance(fromAccount, newBalance);
  return newBalance;
}
try {
  const result = transferFunds('ACC-001', 'ACC-002', 500);
  console.log(Transfer successful. New balance: ${result});
} catch (error) {
  if (error instanceof InsufficientFundsError) {
    console.error(Payment failed: ${error.message});
  } else if (error instanceof InvalidAccountError) {
    console.error(Invalid recipient: ${error.message});
  } else {
    console.error(Unexpected error: ${error});
  }
}

The exception pattern works well when errors are truly exceptional and should terminate the current operation. The key advantage is that calling code can choose to handle the error or let it propagate. However, this flexibility becomes a liability in large codebases where different callers might want different error handling strategies.

One common criticism is that exceptions do not appear in function signatures. When you look at transferFunds, there is no indication in the type system that it can fail. Callers might forget to wrap it in a try-catch, leading to unhandled exceptions in production.

Result Types: Making Errors Explicit

Result types solve the signature problem by encoding both success and failure in the return type. Instead of throwing, functions return an object that explicitly contains either the successful result or the error information.

type Result =
  | { success: true; data: T }
  | { success: false; error: E };
function transferFundsResult(
  fromAccount: string,
  toAccount: string,
  amount: number
): Result {
  if (amount <= 0) {
    return {
      success: false,
      error: new Error('Transfer amount must be positive'),
    };
  }
  const sourceBalance = getAccountBalance(fromAccount);
  if (sourceBalance < amount) {
    return {
      success: false,
      error: new Error(
        Insufficient funds: account has ${sourceBalance}, requested ${amount}
      ),
    };
  }
  if (!accountExists(toAccount)) {
    return {
      success: false,
      error: new Error(Destination account ${toAccount} does not exist),
    };
  }
  const newBalance = sourceBalance - amount;
  updateAccountBalance(fromAccount, newBalance);
  return { success: true, data: newBalance };
}
const result = transferFundsResult('ACC-001', 'ACC-002', 500);
if (result.success) {
  console.log(Transfer complete. New balance: ${result.data});
} else {
  console.error(Transfer failed: ${result.error.message});
}

The function signature now communicates its failure mode. Any caller can see at a glance that this function might fail and must handle both cases. This makes the code more self-documenting and harder to misuse accidentally.

Result types shine when you need to handle multiple potential failures in a single operation. Consider a registration function that validates email, checks password strength, and verifies username availability:

type ValidationError = {
  field: string;
  message: string;
};
type RegistrationResult = Result<{ userId: string }, ValidationError>;
function validateEmail(email: string): Result {
  const emailRegex = /^[^@\s]+@[^@\s]+\.[^@\s]+$/;
  if (!emailRegex.test(email)) {
    return {
      success: false,
      error: { field: 'email', message: 'Invalid email format' },
    };
  }
  return { success: true, data: email };
}
function registerUser(
  email: string,
  password: string,
  username: string
): RegistrationResult {
  const emailResult = validateEmail(email);
  if (!emailResult.success) return emailResult;
  if (password.length < 8) {
    return {
      success: false,
      error: { field: 'password', message: 'Password too short' },
    };
  }
  if (usernameExists(username)) {
    return {
      success: false,
      error: { field: 'username', message: 'Username already taken' },
    };
  }
  const userId = createUser(email, username, password);
  return { success: true, data: { userId } };
}

Each validation step returns early with a specific error. The calling code gets a clear picture of exactly what went wrong, including which field caused the failure.

The Either Monad: A Functional Approach

Either builds on the result type concept with additional helper methods that make chaining operations cleaner. The naming convention comes from functional programming: "Left" traditionally holds the error (the "wrong" path), while "Right" holds the success value.

type Left = { _tag: 'Left'; left: E };
type Right = { _tag: 'Right'; right: T };
type Either = Left | Right;
function left(error: E): Either {
  return { _tag: 'Left', left: error };
}
function right(data: T): Either {
  return { _tag: 'Right', right: data };
}
function isLeft(either: Either): either is Left {
  return either._tag === 'Left';
}
function isRight(either: Either): either is Right {
  return either._tag === 'Right';
}

The real power of Either comes from the map and flatMap (also called bind or andThen) functions. These allow you to chain operations without explicit branching:

function map(
  either: Either,
  fn: (value: T) => U
): Either {
  if (isLeft(either)) return either;
  return right(fn(either.right));
}
function flatMap(
  either: Either,
  fn: (value: T) => Either
): Either {
  if (isLeft(either)) return either;
  return fn(either.right);
}
type Account = { id: string; balance: number };
type TransferError = string;
function getAccount(id: string): Either {
  const account = findAccountById(id);
  if (!account) {
    return left(Account ${id} not found);
  }
  return right(account);
}
function processTransfer(
  fromId: string,
  toId: string,
  amount: number
): Either {
  return flatMap(getAccount(fromId), (from) =>
    flatMap(getAccount(toId), (to) => {
      if (from.balance < amount) {
        return left('Insufficient funds');
      }
      if (amount <= 0) {
        return left('Amount must be positive');
      }
      const newBalance = from.balance - amount;
      updateAccountBalance(fromId, newBalance);
      return right(newBalance);
    })
  );
}

This chaining pattern makes the code read like a sequence of steps, with errors automatically short-circuiting the chain. If either account lookup fails, the error propagates without any explicit if statements.

Comparison of the Three Approaches

Each pattern has distinct characteristics that make it suitable for different situations. The following table summarizes the key differences:

| Aspect | Exceptions | Result Types | Either | |--------|-----------|--------------|--------| | Type Safety | Errors not in signature | Explicit in return type | Explicit in return type | | Error Context | Stack trace, message | Custom error objects | Custom error objects | | Chaining | Manual try-catch | Explicit branching | map/flatMap chains | | Performance | Stack unwinding overhead | No overhead | No overhead | | Composability | Poor | Moderate | Excellent | | Learning Curve | Low | Low | Moderate |

Exceptions work best when errors represent truly exceptional circumstances that should almost never happen. Network timeouts, out-of-memory conditions, and programming bugs all fit this category. The calling code typically does not have a meaningful recovery strategy anyway, so propagating the exception upward is appropriate.

Result types excel in business logic where failures are expected and callers need to respond differently based on what went wrong. A payment processing system might return different result types for "insufficient funds" versus "card expired" versus "payment gateway timeout." Each error requires different handling.

Either shines in functional codebases that already embrace concepts like immapdata and function composition. The chaining methods integrate naturally with map-reduce patterns and make complex validation pipelines readable.

Best Practices and Common Pitfalls

Working with these patterns day-to-day reveals some important lessons. Raj Patel, a colleague of Aiko's, learned one of these lessons the hard way during a 2024Q3 system audit.

They had implemented a comprehensive result type system across their payment module. Everything worked beautifully in testing. Then production traffic revealed that developers downstream were ignoring the error cases entirely. They would check result.success and then blindly proceed as if the operation had succeeded.

const result = processPayment(card, amount);
console.log(result.data); // This crashes when success is false!

The fix was adding a type guard that narrowed the type properly:

function assertSuccess(result: Result): T {
  if (!result.success) {
    throw new Error(Assertion failed: ${result.error.message});
  }
  return result.data;
}
const result = processPayment(card, amount);
const amount = assertSuccess(result);

This pattern forces developers to acknowledge that they are bypassing the error handling. It is a trade-off between safety and convenience, and the right choice depends on your team's culture and code review practices.

Another common mistake is mixing patterns inconsistently. A function that sometimes throws and sometimes returns a result type creates confusion. Choose one approach per function and stick with it.

Conclusion

Aiko eventually refactored that tangled payment function into a clean Either-based pipeline. The new code was shorter, easier to test, and most importantly, made error handling explicit throughout the call stack. Her team found bugs in production that had been silently swallowed for months.

The best pattern depends on your context. Use exceptions for truly exceptional situations. Use result types when callers need to make decisions based on failure type. Use Either when you want composable pipelines with automatic error propagation. All three have a place in a mature TypeScript codebase.

Lessons-Learned

TypeScript's type system is only as strong as its error handling. When exceptions escape unchecked, they bypass the safety the type system provides. Result types and Either make errors explicit in function signatures, forcing callers to acknowledge and handle failure cases.

The functional chaining patterns in Either require some upfront learning but pay dividends in code readability for complex validation and transformation pipelines. Result types achieve similar goals with simpler mental models, making them more accessible to teams new to functional programming.

Regardless of which pattern you choose, consistency matters most. Mixed approaches in the same codebase create confusion and increase the likelihood of bugs.

Actionable Takeaways

Audit your codebase for functions that throw exceptions but do not document this in their type signatures. Consider converting these to result types or Either to make failure modes explicit.

Start small if you are introducing Either to a team. Use it first in a validation or transformation pipeline where the chaining pattern provides clear benefits, then expand to other areas.

Add type guards or assertion functions for result types to prevent downstream code from accidentally ignoring error cases. The initial inconvenience saves debugging time later.

Document which error handling pattern each module uses. When exceptions, results, and Either all appear in the same codebase without clear guidelines, developers will inevitably mix them incorrectly.

Consider the recovery strategies available to callers when choosing between patterns. If callers typically cannot recover from failures, exceptions may be appropriate. If callers need to make different decisions based on failure type, result types or Either provide the necessary granularity.
