Idempotency and Safe Retries for Agent Task Runners

> When a task runner (cron, scheduler, or agent loop) picks up the same task twice—e.g. after a crash or duplicate claim—you want the second run to be safe. This post outlines how to design agent tasks to be idempotent and how to combine that with retry and backoff so your ops stay predictable.

1. Why Idempotency Matters

In agent-ops systems, tasks move from todo → doing → done. A runner claims a task by setting status = 'doing' and started_at = now(). If the process dies before marking done, the next cycle may see the same task still in doing and either skip it or re-claim it. If two runners claim the same row (e.g. race), both may execute the same work. Idempotency means: running the same logical operation more than once produces the same outcome as running it once. No duplicate side effects, no double charges, no duplicate emails.

Design tasks so that:

  • Reads are fine to repeat.
  • Writes (API calls, file writes, DB updates) use idempotency keys, “create or update” semantics, or append-only logs so that a second run does not create a second artifact.

    • 2. Patterns for Idempotent Tasks

    Idempotency key per task run

    Store a unique key per task execution (e.g. task_id + started_at or a UUID written when the task is claimed). When calling an external API or writing to a store, send this key. The recipient can deduplicate: same key → return existing result or no-op.

    Natural keys and upserts

    For DB writes, use INSERT OR REPLACE (SQLite) or ON CONFLICT DO UPDATE so that re-running the task updates the same row instead of inserting a duplicate. The “natural key” (e.g. (task_id, date)) defines uniqueness.

    Append-only and “last write wins”

    For logs or events, appending is naturally idempotent if the event content is deterministic from the task input. For config or state, “last write wins” is acceptable if re-running the task simply overwrites with the same or newer value.

    Guard clauses

    At the start of the task body, check whether the work was already done (e.g. “if target file exists and checksum matches, skip”). Then do the real work only when the guard fails. This makes the whole task idempotent from the outside.

    3. Retry and Backoff

    Even with idempotency, you need a retry policy for transient failures (network, rate limits, locks).

  • Limit retries: e.g. max 3 attempts so a bad task does not spin forever.
  • Backoff: wait 1s, then 2s, then 4s (exponential) before retry to avoid hammering the failing dependency.
  • Mark outcome: on final failure, set status to failed and optionally write an error message or event so operators can fix and re-queue.

    • In code, wrap the task body in a loop: try → on failure, sleep(backoff), retry; after max retries, mark failed and exit. Use the same task id and idempotency key for all attempts so downstream can deduplicate.

    4. Putting It Together

  • Claim: update status = 'doing', set started_at, generate an idempotency key (e.g. store in task row or event).
  • Run: guard clause if work already done; then execute with retries and backoff; all external calls use the idempotency key.
  • Complete: set status = 'done', completed_at = now(), and optionally append an event.
  • On permanent failure: set status = 'failed', record reason; do not leave the task in doing forever.

    • With this, duplicate claims or retries after crashes do not cause duplicate side effects, and transient errors are handled in a controlled way.
