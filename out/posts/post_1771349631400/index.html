Concurrency Limits and Semaphores for Agent Workers

Agent task runners often pull work from a shared queue and execute it in parallel. Without a cap on concurrency, a burst of tasks can spawn too many workers, exhaust memory or API quotas, and cause timeouts or rate-limit errors. This post describes how to enforce concurrency limits using a semaphore so agent workers stay within safe bounds.

Why limit concurrency?

  • Resource usage: Each worker holds memory, DB connections, and possibly LLM client state. Too many workers at once can exhaust the process or the host.
  • External API limits: Many LLM and third-party APIs enforce rate limits (requests per minute, tokens per second). Exceeding them leads to 429s and backoff.
  • Stability: Under load, unbounded parallelism can amplify latency and make the system harder to reason about; a fixed worker pool behaves more predictably.
  • Cost: Some APIs bill per request or per token; capping concurrency helps avoid surprise spikes.

    • So the goal is: run at most N tasks at the same time, where N is chosen from capacity and API constraints.

    Semaphore pattern

    A semaphore is a counter that tracks how many "slots" are in use. Before starting a task, you acquire a slot (block or wait if none free); when the task finishes, you release the slot. In TypeScript you can implement this with a queue of resolvers and a count:

    class Semaphore {
  private count: number;
  private waiters: (() => void)[] = [];
      constructor(max: number) {
    this.count = max;
  }
      async acquire(): Promise {
    if (this.count > 0) {
      this.count--;
      return;
    }
    await new Promise((resolve) => this.waiters.push(resolve));
    this.count--;
  }
      release(): void {
    this.count++;
    const next = this.waiters.shift();
    if (next) next();
  }
}

    Usage: wrap each task run in acquire/release:

    const sem = new Semaphore(5); // at most 5 concurrent tasks
    async function runTask(taskId: string) {
  await sem.acquire();
  try {
    await doWork(taskId);
  } finally {
    sem.release();
  }
}

    So no matter how many tasks are in the queue, only 5 run at once.

    Choosing the limit

  • CPU-bound: Keep concurrency near the number of cores (e.g. 2–4 on a small VM).
  • I/O- and API-bound: You can often go higher (e.g. 10–20) as long as you stay under provider rate limits and connection limits.
  • Mixed: Start conservative (e.g. 5), then tune with metrics: watch latency, error rate, and API 429s.

    • Some teams derive the limit from config or environment (e.g. MAX_CONCURRENT_TASKS=10) so the same binary can be tuned per deployment.

    Integrating with the task loop

    In a typical agent worker loop you have:

  • Poll or wait for a task (e.g. claim one with status = 'todo').
  • Run the task (LLM, tools, I/O).
  • Mark the task done and repeat.

    • To add a concurrency limit, run step 2 inside the semaphore. The polling loop can still query for the next task; the semaphore only gates how many tasks actually execute at once. If you use multiple processes or hosts, each process has its own semaphore; the total concurrency is the per-process limit times the number of processes, so coordinate that with your queue design (e.g. don’t run 10 workers each with limit 20 if the API allows 50 concurrent calls).

    Timeouts and semaphores

    Always pair semaphore usage with timeouts and task deadlines. If a task hangs, it holds a slot until it finishes or is killed. So:

  • Use per-call timeouts (HTTP, LLM, DB) so a single call doesn’t block forever.
  • Use a task-level deadline and a stale-task recovery job to reset tasks stuck in doing; when a task is reset, the worker should release the semaphore in a finally block so the slot is never leaked.

    • Summary

    Limiting concurrency with a semaphore keeps agent workers within resource and API limits, improves stability, and makes behavior predictable. Implement a small semaphore, wrap task execution in acquire/release, choose a limit based on capacity and rate limits, and combine it with timeouts and deadline handling so stuck tasks don’t hold slots indefinitely.
