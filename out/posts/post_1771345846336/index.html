Comparing Bun and Node.js performance for microservices

You spin up dozens of small services—health checks, webhooks, workers—and every extra millisecond of cold start or CPU-bound work adds up. We ran a focused benchmark to see where Bun and Node.js actually differ for typical microservice workloads.

Why this comparison matters

Microservices often do a mix of: starting fast (serverless or frequent restarts), parsing JSON (APIs, config), doing light CPU work, and reading files. Picking a runtime based on marketing claims is risky; real numbers on your own machine help. We measured cold start, JSON round-trip, a tight loop, and repeated file reads so you can map results to your own patterns.

What we measured

We used a small runner script that spawns the same worker under Bun and Node and reports median times over five runs. Workloads:

  • Cold start — time to spawn a process that runs console.log(1) and exits (no heavy bootstrap).
  • JSON parse/stringify — 50,000 rounds of JSON.parse(JSON.stringify(obj)) on a small object.
  • Tight loop — 5 million iterations of a trivial loop (sum of indices).
  • File read — 100 synchronous reads of package.json (same file path for both runtimes).

    • The worker is plain JavaScript (CommonJS) so both runtimes execute the same code. The runner lives at scripts/bun-nodejs-benchmark-2026-02-13-00-50.ts; you can re-run it with:

    bun run scripts/bun-nodejs-benchmark-2026-02-13-00-50.ts

    Results (median of 5 runs)

    | Workload | Bun | Node | Winner | |-----------------------|--------|--------|-------------| | Cold start (spawn) | 86.6 ms | 135.3 ms | Bun 1.6× faster | | JSON (50k rounds) | 147.5 ms | 145.1 ms | ~tie (Node 1.0×) | | Tight loop (5M iter) | 68.6 ms | 21.5 ms | Node 3.2× faster | | File read (100×) | 4.7 ms | 5.7 ms | Bun 1.2× faster |

    So: Bun wins on cold start and file I/O in this setup; Node wins clearly on the tight numeric loop. JSON is effectively a tie.

    What this means for microservices

  • Serverless or frequent restarts — Bun’s faster cold start (1.6× here) can shave tens of milliseconds per invocation. That matters when you have many short-lived processes.
  • JSON-heavy APIs — Neither runtime has a strong advantage in this test; choose based on ecosystem and tooling.
  • CPU-bound helpers — Our tight-loop result is one data point: Node was 3.2× faster. If you have hot numeric or algorithmic code, benchmark it yourself; V8’s optimisations can dominate.
  • File-heavy or I/O-bound — Bun was a bit faster on repeated sync file reads. For async I/O and real network or DB work, both are capable; again, measure your own workload.

    • Gotchas and lessons learned

  • One machine, one point in time. Results were from a single run (2026-02-13); your OS, CPU, and Node/Bun versions will differ. The script writes results to scripts/bun-nodejs-benchmark-2026-02-13-00-50.result.txt so you can compare.
  • Tight loops are not “typical” microservice code. Most services spend time in I/O and JSON. The loop test is there to show that Bun is not always faster—Node’s V8 can win on pure CPU. So avoid extrapolating “Bun is faster” to every workload.
  • Cold start is process spawn only. We did not measure full framework bootstrap (e.g. Fastify or Hono). For real cold start, run your actual app under both runtimes.

    • Takeaway

    For microservices, Bun gives you quicker cold start and slightly faster sync file reads in our test; Node can be much faster on tight numeric loops. Run the benchmark script on your own box and, if possible, add a workload that matches your hottest path (e.g. a real handler or a DB round-trip). Use those numbers, not generic claims, to decide.
