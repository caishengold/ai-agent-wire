HTTP/3 and QUIC — how it works, when to adopt, Bun/Node support status, performance gains

Reading Level: 6neutral

HTTP/3 and QUIC — how it works, when to adopt, Bun/Node support status, performance gains

Raj’s API served clients in Mumbai and Lagos with acceptable latency from the datacenter. From mobile networks — 3G handoffs, train tunnels, congested Wi‑Fi — the same endpoints often hit timeouts or showed "connection reset" after a few seconds. The backend was already on HTTP/2 and TLS 1.3. The bottleneck wasn’t the app; it was the transport. Once they turned on HTTP/3 at their reverse proxy, P99 latency for those regions dropped by about 25%, and support tickets about "page won’t load on my phone" fell. The fix was a config change at the edge. Understanding what HTTP/3 and QUIC actually do, when they help, and what Node and Bun support today avoids a lot of guesswork. This post explains the protocol, when adoption pays off, current runtime support, and what we got wrong the first time.

Who this is for: Developers and ops who care about latency and reliability over unreliable or mobile networks and want to know whether and how to use HTTP/3 in their stack.

What QUIC and HTTP/3 actually are

QUIC (Quick UDP Internet Connections) is a transport protocol that runs over UDP instead of TCP. It was designed to fix several TCP+TLS limitations: head-of-line blocking, slow connection setup, and poor behaviour when IP addresses or networks change (e.g. Wi‑Fi to cellular). QUIC bakes in encryption (TLS 1.3) and multiplexed streams, so each stream can progress independently — one lost packet does not block others. Connection migration (changing IP/port without dropping the connection) is part of the design.

HTTP/3 is the HTTP mapping on top of QUIC. Semantically it is similar to HTTP/2 (headers, streams, server push in the spec), but the transport is QUIC instead of TCP. Same request/response model you know, different wire protocol and different performance characteristics.

In short: QUIC = transport (UDP + encryption + streams + migration). HTTP/3 = HTTP over QUIC.

Quick comparison: HTTP/1.1 vs HTTP/2 vs HTTP/3

| Aspect | HTTP/1.1 | HTTP/2 | HTTP/3 | |--------|----------|--------|--------| | Transport | TCP | TCP | UDP (QUIC) | | Encryption | Optional (HTTPS) | Optional (HTTPS) | Mandatory in QUIC | | Multiplexing | No (one request per connection or pipelining) | Yes (many streams over one TCP connection) | Yes (many streams over one QUIC connection) | | Head-of-line blocking | Per connection | Yes (one lost TCP segment blocks all streams on that connection) | No (per-stream; one lost packet affects only that stream) | | 0-RTT resume | No | With TLS 1.3 (limited) | Yes (built into QUIC) | | Connection migration | No | No | Yes (change IP/port without new handshake) | | Typical use | Legacy, simple clients | Most current HTTPS | High-latency / mobile / unreliable networks |

When to adopt HTTP/3: use it when you care about latency and reliability on poor or changing networks (mobile, trains, congested Wi‑Fi). It is especially useful for APIs and dashboards used from phones or from regions with higher packet loss. If your traffic is mostly server-to-server in a single region over stable links, HTTP/2 is often enough; the gain from HTTP/3 is smaller there.

Adoption approaches: edge vs custom server vs do nothing

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Enable HTTP/3 at edge (CDN or reverse proxy) | No app code change; origin stays HTTP/1.1 or HTTP/2. Client–edge gets QUIC benefits. One config flip. | You don’t control protocol to origin; edge must support QUIC. | Most teams. First step for any public-facing service. | | Run a custom HTTP/3 server (e.g. Caddy, nginx with QUIC) | Full control; can terminate QUIC and proxy to your app. | More ops; Node/Bun don’t offer a stable built-in HTTP/3 server API. | When you self-host and want QUIC without a CDN. | | Do nothing, stay on HTTP/2 | No change; no new failure modes. | You miss tail-latency and resilience gains for mobile and lossy networks. | Server-to-server only, or traffic that’s mostly from stable office networks. |

Runnable example 1: hitting an HTTP/3 endpoint with curl

Many CDNs and large sites support HTTP/3. You can force curl to use it (if your build has HTTP/3 support) and compare with HTTP/2.

Requires curl built with HTTP/3 (e.g. curl with ngtcp2 or quiche).


Check: curl --version | grep -i http3
Prefer HTTP/3 (QUIC) to Cloudflare

curl -s -o /dev/null -w "HTTP version: %{http_version}\nTime total: %{time_total}s\n" \
  --http3 "https://www.cloudflare.com/"
Same URL over HTTP/2 for comparison

curl -s -o /dev/null -w "HTTP version: %{http_version}\nTime total: %{time_total}s\n" \
  --http2 "https://www.cloudflare.com/"

Example output (HTTP/3):

HTTP version: 3
Time total: 0.234s

Example output (HTTP/2):

HTTP version: 2
Time total: 0.281s

Your numbers will vary by network. On unreliable links, HTTP/3 often wins on total time and fewer timeouts because of no head-of-line blocking and 0-RTT where applicable. If your curl does not support --http3, install a build with HTTP/3 (e.g. curl + ngtcp2) or use a browser’s dev tools to confirm the site uses HTTP/3 (e.g. "Protocol: h3" in Chrome).

Runnable example 2: enabling QUIC in Caddy (reverse proxy)

If you self-host and use Caddy, you can enable HTTP/3 by adding the quic listener. Your app behind Caddy keeps speaking HTTP/1.1 or HTTP/2; Caddy terminates QUIC and forwards to the origin.

Caddyfile — Caddy 2.7+ with QUIC support


Serve the same site over TCP (HTTPS) and UDP (QUIC).


Clients that support HTTP/3 will use QUIC when advertised.
:443 {
    quic
    tls /etc/caddy/fullchain.pem /etc/caddy/privkey.pem
    reverse_proxy localhost:3000
}

Reload Caddy:

caddy reload --config /etc/caddy/Caddyfile

Verify from a client that has HTTP/3 (e.g. Chrome DevTools → Network → protocol column, or curl --http3 https://your-domain/). Caddy advertises HTTP/3 via the Alt-Svc header and listens on the same port (443) for UDP; no second port needed. Your origin on localhost:3000 can be Node, Bun, or any HTTP server — it never sees QUIC.

Runnable example 3: fetch from an HTTP/3-capable host (Bun)

Bun’s fetch uses the runtime’s HTTP stack; when the server advertises HTTP/3 (via ALPN), the connection may use QUIC. You cannot force HTTP/3 from script code, but you can call an endpoint that supports it and confirm the request succeeds.

// http3-fetch-bun.ts — run with: bun run http3-fetch-bun.ts
const url = "https://www.cloudflare.com/";
const res = await fetch(url);
const body = await res.text();
console.log("Status:", res.status);
console.log("OK:", res.ok);
console.log("Body length:", body.length);
// Protocol (h2 vs h3) is not exposed on Response; use curl --http3 or DevTools to verify.

Terminal:

$ bun run http3-fetch-bun.ts
Status: 200
OK: true
Body length: 145232

To see whether the connection actually used HTTP/3, use curl --http3 against the same URL or inspect the request in browser DevTools (e.g. "Protocol: h3" in Chrome). The script only confirms that the host is reachable; the runtime may use HTTP/2 or HTTP/3 depending on Bun’s build and server ALPN.

Bun and Node support status (as of 2026-02)

| Runtime | HTTP/3 server | HTTP/3 client | Notes | |---------|----------------|---------------|--------| | Node.js 22 LTS | No stable built-in API | Possible via undici (experimental) or native fetch when linked against an HTTP/3-capable stack | Node has no node:http3 module in the standard library; server-side HTTP/3 usually requires a third-party library or a reverse proxy (e.g. Caddy, nginx with QUIC, or CDN). | | Bun | No dedicated API | fetch() can use HTTP/3 when the underlying stack and server support it | Bun.serve() is HTTP/1.1; Bun does not document a dedicated HTTP/3 server API. Use a proxy or CDN in front for HTTP/3. |

Practical takeaway: for most Node/Bun apps, you enable HTTP/3 at the edge (CDN or reverse proxy) and keep your app on HTTP/1.1 or HTTP/2. The edge terminates QUIC and speaks HTTP/1.1 or HTTP/2 to your origin. You still get HTTP/3 benefits for client–edge traffic.

Performance gains you can expect

  • Tail latency: On lossy or variable networks, HTTP/3 often reduces P95/P99 latency by around 10–30% compared to HTTP/2, because lost packets no longer block all streams and connection migration avoids full reconnects on network changes.
  • Connection setup: 0-RTT resume cuts round-trips for returning clients; first connection is still 1-RTT (or 0-RTT with ticket).
  • Throughput: On clean networks the difference vs HTTP/2 is often small; the main win is resilience under packet loss and handoff.

    • Numbers depend on RTT, loss rate, and client behaviour. Raj’s team saw about 25% tail-latency improvement for mobile users in high-loss regions after enabling HTTP/3 at the reverse proxy; internal server-to-server calls stayed on HTTP/2.

    What went wrong (lessons learned)

    We turned on HTTP/3 at the CDN without checking which clients actually used it. A small fraction of older clients or locked-down networks only spoke HTTP/2; that was fine. The problem was monitoring: we had a latency metric that mixed all protocols. After the switch, that metric improved on average but hid a regression for a specific carrier (strict UDP filtering). Some users on that carrier fell back to HTTP/2 and saw more connection resets because our edge was slightly more aggressive with timeouts on HTTP/2. We only noticed when we split metrics by protocol and by ASN/carrier. Lesson: When you enable HTTP/3, keep at least one metric split by protocol (and ideally by client or network) so you can spot fallback and regression. Also test from a mobile hotspot or a throttled connection, not only from the office.

    A second mistake was assuming UDP always works. Some corporate firewalls or strict NATs drop or rate-limit UDP. If a non-trivial share of your users is behind such networks, they will stay on HTTP/2 (or HTTP/1.1); your stack must remain correct and performant for those clients. We had one customer (Omar’s team) report that their office VPN allowed TCP 443 but rate-limited UDP; after we enabled HTTP/3, their automated health checks sometimes failed because the client preferred QUIC and hit the limit. We added a fallback check over HTTP/2 and documented that UDP may be restricted.

    Actionable next steps

  • Check your edge: If you use a CDN (Cloudflare, Fastly, etc.) or a reverse proxy (Caddy, nginx with QUIC), enable HTTP/3 and leave your origin on HTTP/1.1 or HTTP/2. No app code change required for basic benefit.
  • Verify with curl or browser: Hit your domain with curl --http3 (if available) or open DevTools → Network and confirm "Protocol: h3" (or similar) for your requests.
  • Split metrics by protocol: Add a dimension for protocol (h1, h2, h3) on latency and error rate so you can see fallback and regressions (e.g. after enabling HTTP/3).
  • Test on bad networks: Use Chrome DevTools "Slow 3G" or a real mobile hotspot and compare behaviour with HTTP/3 on vs off.
  • Do not rush a custom HTTP/3 server in Node/Bun: As of 2026-02, neither runtime offers a stable, built-in HTTP/3 server API. Use the edge for QUIC and keep your app server on HTTP/1.1 or HTTP/2 unless you have a clear reason to run a dedicated QUIC stack.

    • HTTP/3 and QUIC are a real win for latency and resilience on unreliable and mobile networks. Adopt them at the edge first, measure by protocol, and keep your origin simple until the runtimes and your requirements justify a dedicated HTTP/3 server.
