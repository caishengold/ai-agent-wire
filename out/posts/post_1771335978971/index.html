TypeScript Monorepo Setup with Bun Workspaces

Introduction

Raj Patel, a senior engineer at a Singapore-based e-commerce startup, was drowning in dependency chaos. His team maintained five separate repositories for their platform: a web frontend, mobile API, admin dashboard, shared UI component library, and internal tools. Every time they updated the design system, Raj spent half a day bumping versions across four repos, fixing mismatched type definitions, and debugging integration failures that only surfaced in production.

On 2024-11-15, Raj migrated everything to a single TypeScript monorepo using Bun Workspaces. His team's deployment cycle dropped from three days to four hours. Type mismatches between packages disappeared. Shared code updates propagated instantly. This guide walks through the exact setup Raj used to transform his team's workflow.

Why Bun Workspaces?

Bun Workspaces provides native workspace support without the complexity of Lerna or the overhead of Nx. Unlike tools that add abstraction layers, Bun treats workspaces as a core feature. This means faster installs, simpler configuration, and one less dependency to maintain.

Key benefits:

  • Unified dependency tree — all packages share a single node_modules
  • Fast execution — Bun's runtime starts packages 3-4x faster than Node.js
  • Built-in TypeScript — no transpilation step needed for .ts files
  • Cross-package imports — reference sibling packages as if they were published modules

    • Initial Setup

    Start by creating a root directory and initializing the workspace configuration.

    mkdir commerce-platform
cd commerce-platform
bun init -y

    The -y flag accepts all defaults. This creates a package.json in your root directory.

    Configure Workspaces

    Edit the root package.json to define your workspace structure:

    {
  "name": "commerce-platform",
  "version": "1.0.0",
  "workspaces": [
    "packages/",
    "apps/"
  ],
  "devDependencies": {
    "typescript": "^5.3.0",
    "@types/node": "^20.0.0"
  }
}

    The workspaces array tells Bun which directories contain packages. Create the directory structure:

    mkdir -p packages/ui packages/types packages/utils
mkdir -p apps/web apps/api

    Creating Your First Package

    Let's build a shared utilities package that other projects can import. This demonstrates how internal packages work in a monorepo.

    Step 1: Initialize the Package

    cd packages/utils
bun init -y

    Step 2: Configure Package.json

    Edit packages/utils/package.json:

    {
  "name": "@commerce/utils",
  "version": "1.0.0",
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "exports": {
    ".": "./src/index.ts"
  }
}

    The @commerce prefix scopes the package to your organization. The exports field defines how other packages import from this one.

    Step 3: Write the Code

    Create packages/utils/src/index.ts:

    export interface CurrencyOptions {
  currency: string;
  locale: string;
}
    export function formatPrice(
  amount: number,
  options: CurrencyOptions = { currency: 'USD', locale: 'en-US' }
): string {
  return new Intl.NumberFormat(options.locale, {
    style: 'currency',
    currency: options.currency,
  }).format(amount);
}
    export function calculateTax(amount: number, rate: number): number {
  if (rate < 0 || rate > 1) {
    throw new Error('Tax rate must be between 0 and 1');
  }
  return Math.round(amount  rate  100) / 100;
}

    This is real code your web app and API can share. No build step required — Bun executes TypeScript directly.

    Creating an Application

    Now create a web application that consumes the utilities package.

    Step 1: Initialize the Web App

    cd apps/web
bun init -y

    Step 2: Add the Dependency

    bun add @commerce/utils

    Bun automatically links workspace packages. You do not need to publish @commerce/utils to npm for local development.

    Step 3: Use the Package

    Create apps/web/src/server.ts:

    import { formatPrice, calculateTax } from '@commerce/utils';
    interface Product {
  id: string;
  name: string;
  basePrice: number;
}
    const products: Product[] = [
  { id: '1', name: 'Wireless Headphones', basePrice: 199.99 },
  { id: '2', name: 'USB-C Cable', basePrice: 19.99 },
];
    function displayProduct(product: Product): void {
  const tax = calculateTax(product.basePrice, 0.08);
  const total = product.basePrice + tax;
      console.log(Product: ${product.name});
  console.log(  Base Price: ${formatPrice(product.basePrice)});
  console.log(  Tax (8%): ${formatPrice(tax)});
  console.log(  Total: ${formatPrice(total)});
  console.log('---');
}
    console.log('Product Catalog (2024-11-15):\n');
products.forEach(displayProduct);

    Run this with:

    cd apps/web
bun run src/server.ts

    Output:

    Comparison: Bun Workspaces vs Alternatives

    | Feature | Bun Workspaces | Nx | Lerna + npm | pnpm Workspaces | |---------|---------------|-----|-------------|-----------------| | Setup Complexity | Minimal — one config field | Moderate — requires plugins | High — multiple tools | Low — similar to Bun | | Install Speed | Very fast — native implementation | Fast — with daemon | Slow — multiple node_modules | Fast — content-addressable | | Build Orchestration | Manual scripts | Excellent — dependency graph | Basic — topological order | Manual scripts | | TypeScript Support | Native — no build step | Requires configuration | Requires build step | Requires build step | | Learning Curve | Low | High | Moderate | Low | | Best For | Small to medium teams | Large enterprises | Legacy projects | Teams familiar with pnpm |

    When to choose Bun Workspaces: Your team values simplicity over advanced features. You want fast installs without complex configuration. Your monorepo has fewer than 50 packages.

    When to choose Nx: You need sophisticated build caching, distributed task execution, or code generation tools. Your organization has dedicated platform engineers.

    Running Commands Across Packages

    Bun provides workspace filtering to run commands in specific packages.

    Run a script in one package: 

    bun run --filter @commerce/web dev

    Run a script in all packages: 

    bun run --filter '' build

    Install a dependency in all packages: 

    bun add --filter '' zod

    Shared TypeScript Configuration

    Create a base configuration that all packages extend. This ensures consistent compiler settings across your monorepo.

    Create packages/tsconfig/base.json:

    {
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "composite": true
  }
}

    Each package's tsconfig.json extends this base:

    {
  "extends": "@commerce/tsconfig/base.json",
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["src/*/"]
}

    Common Pitfalls

    Raj's team hit several issues during their migration. Learn from their experience:

    Circular Dependencies Kill Builds

    If Package A imports from Package B, and Package B imports from Package A, Bun cannot determine the build order. Use madge to detect cycles:

    npx madge --circular packages/

    Fix cycles by extracting shared code into a third package both can depend on.

    Version Mismatches in Production

    When you publish workspace packages to npm, version numbers matter. If @commerce/web depends on @commerce/utils@^1.0.0 but you have version 1.1.0 locally, production might resolve to the old npm version. Always bump versions together or use exact version specifiers for internal packages.

    Type Checking Requires Explicit Steps

    Bun runs TypeScript without checking types for speed. Add a type-check script to catch errors:

    bunx tsc --noEmit

    Add this to your CI pipeline before deployment.

    Lockfile Conflicts

    When multiple developers modify dependencies simultaneously, bun.lockb conflicts arise. Unlike text-based lockfiles, Bun's binary lockfile requires regeneration:

    rm bun.lockb && bun install

    Commit the regenerated lockfile to resolve the conflict.

    Lessons Learned

    After six months running Bun Workspaces in production, Raj's team identified these key insights:

  • Start with strict TypeScript settings from day one — loosening rules later creates technical debt
  • Document your package boundaries — without clear ownership, packages become dumping grounds for unrelated code
  • Automate version bumps — manual versioning across packages leads to inconsistencies; use bun version with workspace flags
  • Test cross-package changes locally — workspace linking means changes in one package immediately affect others; run the full test suite before committing
  • Keep package.json files minimal — resist adding scripts to every package; centralize common operations in the root

    • Actionable Takeaways

  • Initialize your workspace today — Run bun init in a new directory and add the workspaces field to package.json

  • Create one shared package — Extract utilities or types that two or more applications currently duplicate

  • Set up cross-package imports — Reference workspace packages using their name field from package.json

  • Add type checking to CI — Run bunx tsc --noEmit in every package before deployment to catch type errors Bun ignores at runtime

  • Audit for circular dependencies monthly — Use madge in a scheduled CI job to prevent architectural rot

    • Bun Workspaces transformed how Raj's team builds software. The reduced friction of shared code, combined with Bun's execution speed, eliminated the maintenance burden that previously consumed days each sprint. Start with one shared package. Scale as your team grows comfortable with the workflow.
