GraphQL vs REST: When to Choose What

Aiko Chen, lead developer at a mid-size fintech startup, stared at her laptop screen at 23:47 on 2025-11-12. Her team had just shipped a new feature that displayed product details on the frontend, but customer complaints were pouring in. The mobile app was making 47 separate API calls just to render a single product page. Users on slower connections were seeing load times exceed eight seconds. She needed to fix this fast—the quarterly review was in two weeks, and the VP of Product was asking questions.

This is a common problem in modern web development, and Aiko's solution would determine whether her team adopted GraphQL or stuck with REST. Both approaches have merit, but the choice impacts performance, developer experience, and long-term maintainability.

The Core Difference

GraphQL and REST solve the same fundamental problem—getting data from servers to clients—but they approach it differently.

GraphQL is a query language developed by Facebook in 2012 and released publicly in 2015. Clients specify exactly what data they need, including nested relationships, in a single request. The server responds with precisely that data and nothing more.

REST (Representational State Transfer) is an architectural style dating back to 2000. It organizes data around resources (like /products or /users) and uses HTTP methods (GET, POST, PUT, DELETE) to manipulate those resources.

The difference sounds subtle until you see it in practice.

Real-World Scenario

Aiko's e-commerce platform needed an API that could fetch a product, its category, customer reviews, and related products—all in one screen. With REST, this required multiple endpoints:

GET /api/products/12345
GET /api/products/12345/category
GET /api/products/12345/reviews
GET /api/products/12345/related-products

That's four HTTP requests, four round trips to the server, and likely four database queries. On a 3G connection, that adds up to seconds of waiting.

With GraphQL, Aiko could request everything in one query:

query GetProductDetails($productId: ID!) {
  product(id: $productId) {
    id
    name
    price
    description
    category {
      id
      name
      slug
    }
    reviews(first: 5) {
      edges {
        node {
          id
          rating
          comment
          author {
            name
          }
        }
      }
    }
    relatedProducts(first: 4) {
      id
      name
      thumbnailUrl
    }
  }
}

One request. One response with exactly the fields the frontend needs. No over-fetching, no under-fetching.

But GraphQL was not the right answer for everything. Aiko's team also built an internal dashboard that simply toggled boolean flags on user accounts—something REST handled perfectly with a simple PATCH /api/users/:id/status.

Runnable Code Examples

Here is how you might implement both approaches in a real Python application.

REST Implementation with Flask

from flask import Flask, jsonify, request
from functools import wraps
app = Flask(__name__)
In-memory product data

products_db = {
    "12345": {
        "id": "12345",
        "name": "Wireless Headphones",
        "price": 79.99,
        "category": {"id": "1", "name": "Electronics"},
        "reviews": [
            {"id": "r1", "rating": 5, "comment": "Great sound!", "author": "Raj"},
            {"id": "r2", "rating": 4, "comment": "Good value", "author": "Sofia"}
        ],
        "related_products": [
            {"id": "12346", "name": "Phone Case", "price": 19.99}
        ]
    }
}
def require_auth(f):
    @wraps(f)
    def decorated(args, kwargs):
        auth_header = request.headers.get("Authorization")
        if not auth_header or not auth_header.startswith("Bearer "):
            return jsonify({"error": "Unauthorized"}), 401
        return f(args, kwargs)
    return decorated
@app.route("/api/products/", methods=["GET"])
@require_auth
def get_product(product_id):
    product = products_db.get(product_id)
    if not product:
        return jsonify({"error": "Product not found"}), 404
    return jsonify(product)
@app.route("/api/products//reviews", methods=["GET"])
@require_auth
def get_product_reviews(product_id):
    product = products_db.get(product_id)
    if not product:
        return jsonify({"error": "Product not found"}), 404
    return jsonify(product.get("reviews", []))
@app.route("/api/products//related-products", methods=["GET"])
@require_auth
def get_related_products(product_id):
    product = products_db.get(product_id)
    if not product:
        return jsonify({"error": "Product not found"}), 404
    return jsonify(product.get("related_products", []))
@app.route("/api/products//category", methods=["GET"])
@require_auth
def get_product_category(product_id):
    product = products_db.get(product_id)
    if not product:
        return jsonify({"error": "Product not found"}), 404
    return jsonify(product.get("category", {}))
if __name__ == "__main__":
    app.run(debug=True, port=5000)
}

GraphQL Implementation with Strawberry

import strawberry
from typing import List, Optional
Type definitions

@strawberry.type
class Category:
    id: strawberry.ID
    name: str
    slug: str
@strawberry.type
class Author:
    name: str
@strawberry.type
class Review:
    id: strawberry.ID
    rating: int
    comment: str
    author: Author
@strawberry.type
class RelatedProduct:
    id: strawberry.ID
    name: str
    thumbnail_url: str
@strawberry.type
class Product:
    id: strawberry.ID
    name: str
    price: float
    description: str
    category: Category
    reviews: List[Review]
    related_products: List[RelatedProduct]
In-memory database

products_db = {
    "12345": {
        "id": "12345",
        "name": "Wireless Headphones",
        "price": 79.99,
        "description": "Premium noise-cancelling headphones",
        "category": {"id": "1", "name": "Electronics", "slug": "electronics"},
        "reviews": [
            {"id": "r1", "rating": 5, "comment": "Great sound!", "author": {"name": "Raj"}},
            {"id": "r2", "rating": 4, "comment": "Good value", "author": {"name": "Sofia"}}
        ],
        "related_products": [
            {"id": "12346", "name": "Phone Case", "thumbnail_url": "/img/phone-case.jpg"}
        ]
    }
}
@strawberry.type
class Query:
    @strawberry.field
    def product(self, id: strawberry.ID) -> Optional[Product]:
        data = products_db.get(str(id))
        if not data:
            return None
        
        return Product(
            id=data["id"],
            name=data["name"],
            price=data["price"],
            description=data["description"],
            category=Category(data["category"]),
            reviews=[
                Review(
                    id=r["id"],
                    rating=r["rating"],
                    comment=r["comment"],
                    author=Author(name=r["author"]["name"])
                )
                for r in data["reviews"]
            ],
            related_products=[
                RelatedProduct(
                    id=rp["id"],
                    name=rp["name"],
                    thumbnail_url=rp["thumbnail_url"]
                )
                for rp in data["related_products"]
            ]
        )
schema = strawberry.Schema(query=Query)
if __name__ == "__main__":
    from strawberry.fastapi import GraphQLRouter
    import uvicorn
    from fastapi import FastAPI
    app = FastAPI()
    app.include_router(GraphQLRouter(schema), prefix="/graphql")
    uvicorn.run(app, host="0.0.0.0", port=8000)
}

Comparison Table

The following table summarizes key differences across several dimensions:

| Aspect | GraphQL | REST | |--------|---------|------| | Data Fetching | Single flexible query for nested data | Multiple endpoints, often requires over-fetching | | Response Shape | Client defines exact fields needed | Server defines response structure | | Learning Curve | Steeper: requires schema design, query language | Easier: familiar HTTP patterns | | Caching | Complex: requires normalized cache | Simple: HTTP caching works out of the box | | Error Handling | Single error format with codes | HTTP status codes with varied formats | | N+1 Problem | Mitigated with DataLoader patterns | Common issue requiring manual optimization | | Documentation | Self-documenting via schema | Must maintain separately | | File Upload | Requires workarounds | Native support via multipart forms |

When to Choose GraphQL

Aiko ultimately chose GraphQL for her product detail endpoint because her frontend team was building a highly interactive dashboard with many interconnected data points. GraphQL made sense when the frontend needed flexible data shapes that varied by screen, when mobile bandwidth was a concern, and when developers wanted to iterate quickly without waiting for backend endpoint changes.

For example, the product listing page needed only basic product info, while the detail page needed reviews and related products. With GraphQL, each component could request exactly what it needed without creating new backend endpoints.

When to Choose REST

REST remained the right choice for Aiko's team in several scenarios. The user status toggle endpoint was simple—REST verbs mapped perfectly to the operation. Internal tools with stable, predictable data needs benefited from REST's simplicity. When HTTP caching was critical (like CDN integration for static assets), REST's well-understood caching model was advantageous.

Additionally, when working with third-party integrations that expected standard REST patterns, sticking with REST reduced friction and documentation overhead.

Common Pitfalls

GraphQL pitfalls:

  • N+1 query problems emerge when resolvers fetch data in loops without proper batching
  • Query complexity can become unlimited without depth limiting or cost analysis
  • File uploads require non-trivial workarounds since GraphQL does not handle binary natively
  • Over-optimization leads to prematurely optimizing queries that never become bottlenecks

    • REST pitfalls:

  • Over-fetching wastes bandwidth by returning fields clients do not need
  • Under-fetching creates chatty APIs requiring multiple round trips
  • Versioning strategies diverge widely, leading to inconsistent API designs
  • Tight coupling between client and server structure makes refactoring expensive

    • Lessons Learned

  • Always measure before optimizing—Aiko profiled her actual API call patterns and discovered the 47 calls came from frontend developers making convenient separate requests, not from architectural necessity
  • GraphQL introduced complexity that paid off for complex read patterns but added overhead for simple CRUD operations
  • REST's predictability made it easier to onboard new team members who already understood HTTP conventions
  • Both approaches can coexist in the same system—Aiko's team used GraphQL for customer-facing APIs while keeping internal REST endpoints

    • Actionable Takeaways

  • Audit your current API call patterns — Use network inspection tools to count requests per screen and identify chatty interfaces that would benefit from GraphQL's batched fetching

  • Start with REST for new projects — Unless your frontend requires highly variable data shapes from the start, REST's simplicity and tooling support reduce initial complexity

  • Implement cost analysis for GraphQL — If adopting GraphQL, add query depth limiting and complexity analysis to prevent malicious or accidental expensive queries

  • Use HTTP caching for REST endpoints — Leverage CDN-level caching for public data by designing REST endpoints with cache-friendly URLs and headers

  • Consider hybrid approaches — A well-architected system can expose both REST and GraphQL APIs, letting each serve the scenarios where it excels
