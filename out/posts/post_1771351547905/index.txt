8:T52e4,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Cron jobs vs message queues — when each wins, hybrid patterns, real-world decision framework</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team had a cleanup job in crontab: “every 10 minutes, delete expired sessions.” One day the database was under load and the DELETE took 18 minutes. The next cron tick started a second process. Both held locks; one eventually deadlocked and the other left 40,000 orphaned rows. The fix wasn’t “replace cron with Kafka” — it was knowing <strong>when</strong> a schedule is enough and when you need something that can serialize work, retry per item, and avoid overlap. Here’s the split: when cron wins, when a queue wins, hybrid patterns we use in production, and a decision framework you can apply today.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The core difference</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cron</strong> runs a command on a schedule. It has no idea whether the previous run finished. It doesn’t queue; it just fires again at the next tick. That’s ideal for “run this once per day” and bad for “process each of these 10,000 rows without two processes stepping on each other.”</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Message queues</strong> (Redis + Bull, RabbitMQ, Amazon SQS, or a SQLite-backed queue) store units of work. Producers push jobs; workers pull and process. You get retries, backoff, dead-letter handling, and concurrency control. You pay with extra moving parts.</p><p class="text-slate-300 leading-relaxed mb-4">The right choice hinges on <strong>trigger</strong> (time vs event), <strong>volume</strong> (one job per run vs many items), and <strong>failure model</strong> (ok to skip vs must retry).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When cron wins</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use cron when:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Work is <strong>time-triggered</strong> and <strong>single-shot</strong> per run: daily backup, weekly cleanup, “every 5 minutes run the refill script.”</li>
<li class="ml-4 list-disc text-slate-300">One run per tick is enough; you don’t need 50,000 items as 50,000 separate jobs.</li>
<li class="ml-4 list-disc text-slate-300">Occasional failure is acceptable (e.g. missed backup tomorrow) or you handle retry inside the script (log and alert).</li>
<li class="ml-4 list-disc text-slate-300">You want <strong>no extra infrastructure</strong>: no Redis, no broker — just the machine and crontab.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: a small script that syncs config from a template store and exits. Run it every 5 minutes. If one run fails, the next run corrects it.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">crontab -e</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Sync config every 5 minutes; script exits when done</h1>

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>#!/usr/bin/env bash

That’s cron’s sweet spot.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When a queue wins</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use a queue when:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Work is <strong>event- or volume-driven</strong>: “for each new signup send a welcome email,” “for each row in this export run this pipeline.”</li>
<li class="ml-4 list-disc text-slate-300">You need <strong>per-item retries</strong>, backoff, and dead-letter handling so one bad item doesn’t block the rest.</li>
<li class="ml-4 list-disc text-slate-300">You need <strong>concurrency control</strong>: e.g. “at most 3 API calls at a time” or “one report at a time.”</li>
<li class="ml-4 list-disc text-slate-300">Multiple producers or workers (different services or hosts) must share one backlog.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: process a list of URLs and push each as a job so failures retry independently. If one fails, you can retry it (e.g. set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status = 'pending'</code> and run again) without re-processing the rest. That’s where a queue beats “one cron script that does everything in one go.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Single-flight guard for cron (when you stay with cron)</h2></p><p class="text-slate-300 leading-relaxed mb-4">When the unit of work is “one run” but the run can exceed the cron interval, use a <strong>lock</strong> so only one instance runs at a time. Here’s a minimal pattern with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flock</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>#!/usr/bin/env bash

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So: <strong>cron for “run this on a schedule and exit”; lock when “one run at a time” matters.</strong></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: cron vs queue</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Dimension | Cron | Message queue |
|-----------|------|----------------|
| <strong>Trigger</strong> | Time (schedule) | Event or time; work is explicit jobs |
| <strong>Granularity</strong> | One run per tick (or one script doing a batch) | One job per unit of work |
| <strong>Overlap</strong> | Can overlap if run lasts longer than interval | Controlled by workers; you set concurrency |
| <strong>Retries</strong> | Only by re-running the whole script or custom logic | Per-job retries, backoff, dead-letter |
| <strong>Infrastructure</strong> | OS only (crontab / systemd timer) | Broker (Redis, RabbitMQ, SQS) or SQLite/DB as queue |
| <strong>Visibility</strong> | Logs and cron mail | Queue depth, failed jobs, metrics |
| <strong>Best for</strong> | Periodic single-shot tasks (backup, cleanup, “run scheduler”) | Per-item work, retries, multi-worker, backpressure |</p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>cron</strong> when the unit of work is “this run” and at-most-once or “next run fixes it” is fine. Use a <strong>queue</strong> when the unit of work is “this item” and you need at-least-once with retries and clear failure handling.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Hybrid patterns</h2></p><p class="text-slate-300 leading-relaxed mb-4">Often you <strong>combine both</strong>: cron as trigger, queue as workload.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Cron enqueues; workers drain</h3></p><p class="text-slate-300 leading-relaxed mb-4">Cron runs every 5 minutes and pushes a “refill” or “sync” job into a queue. Workers process the queue. You avoid overlapping refills (one job at a time) and get retries without cron spawning duplicate processes.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// cron-refill.ts — run from crontab; only enqueues
import Database from "bun:sqlite";
const db = new Database("/tmp/queue.db", { create: true });
db.run(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  CREATE TABLE IF NOT EXISTS jobs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    type TEXT,
    payload TEXT,
    status TEXT DEFAULT 'pending',
    created_at TEXT DEFAULT (datetime('now'))
  )
</code>);
db.prepare("INSERT INTO jobs (type, payload) VALUES ('refill', '{}')").run();
console.log("Enqueued refill job");
db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">A separate long-running worker claims <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">refill</code> jobs and processes them. Cron only enqueues; it never holds the process open.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Cron as safety net for stuck queues</h3></p><p class="text-slate-300 leading-relaxed mb-4">Workers process items; if they crash or hang, jobs stay in “doing.” A cron job runs every 15 minutes, finds jobs in “doing” older than 30 minutes, and resets them to “pending” so workers can retry. Cron doesn’t do the work — it only unblocks the queue.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Time-window queues</h3></p><p class="text-slate-300 leading-relaxed mb-4">You want “run after 18:00 UTC” or “run in 2 hours.” Cron can’t express that per item. A queue can: store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run_after</code> on each job; workers only claim jobs where <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run_after <= now()</code>. Cron can still trigger the worker on a schedule; the queue holds the delayed work.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Decision framework</h2></p><p class="text-slate-300 leading-relaxed mb-4">Answer these in order:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>What is the unit of work?</strong>  </li>
   One run (e.g. “daily report”) → lean cron. Many items (e.g. “each row in this table”) → queue (or cron that enqueues per item).</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Can two runs overlap?</strong>  </li>
   If the script can run longer than the cron interval, you get overlap (Sofia’s cleanup problem). Fix: lock file, queue with one worker, or a systemd timer that doesn’t re-enter.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Do you need per-item retries and backoff?</strong>  </li>
   Yes → queue. No and “next run is enough” → cron is fine.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>How many moving parts do you want?</strong>  </li>
   Zero extra services → cron (and maybe SQLite as queue if you need retries). OK to run Redis or a broker → use a proper queue (Bull, RabbitMQ, SQS).</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Who triggers work?</strong>  </li>
   Only time → cron (or cron + enqueue). Events (HTTP, webhooks, other services) → queue with producers pushing jobs.</p><p class="text-slate-300 leading-relaxed mb-4">In short: <strong>cron for “run this on a schedule and exit”; queue for “many units of work, with retries and control.”</strong> Hybrid: cron enqueues or unblocks; workers drain the queue.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">We ran a “daily summary” as a cron job that queried a large table and wrote aggregates. No lock, no “am I already running” check. Under load the query sometimes took 35+ minutes. Cron was set to 00:30 every night. Two instances overlapped; both wrote to the same summary table. We got duplicate keys and wrong sums. The fix was: (1) add a lock file at the start and exit if it exists, and (2) move the heavy per-tenant aggregation into a queue — cron only enqueues one job per tenant, and a single worker processes them one at a time. That removed overlap and gave per-tenant retries. The mistake was assuming “it usually finishes in 20 minutes” without guarding against the long tail. <strong>Takeaway:</strong> if cron interval can be shorter than job duration, enforce single-flight (lock or queue).</p><p class="text-slate-300 leading-relaxed mb-4">Another failure: we once put “send 5,000 welcome emails” in a single cron script. One bad address caused the script to throw; no emails after that point were sent, and we had no list of “which ones failed.” Moving to a queue (one job per email) gave us retries and a clear failed list. <strong>Takeaway:</strong> when the unit of work is “per item,” use a queue so one failure doesn’t stop the rest.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>List your cron jobs</strong> — For each, note: “What is the unit of work (one run vs many items)?” and “Can this run overlap the next tick?” If overlap is possible, add a lock (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flock</code>) or move the heavy part to a queue.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a single-flight guard</strong> — For any cron script that might run longer than the interval, start with a lock file or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flock</code> and exit if already running; log when you skip.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Try a minimal queue</strong> — Use a SQLite table as a queue (like the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process-urls-queue.ts</code> example) for one batch job. Enqueue items, process with a simple worker loop, and add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">attempts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code> so you can retry failures.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document the trigger</strong> — For each job, write: “Trigger: time vs event” and “Retry: none / whole run / per item.” That will push you toward the right choice (cron vs queue vs hybrid).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Revisit one problem job</strong> — Pick one that has failed, overlapped, or been hard to debug. Redesign it using the table above: should it be cron-only, queue-only, or cron-that-enqueues? Implement the smallest change that fixes the failure mode.</li></p><p class="text-slate-300 leading-relaxed mb-4">Cron and queues are complementary. Use cron for schedule-driven, single-shot work; use a queue when you have many units of work and need retries and control. Combine them when you want cron to trigger or unblock work and the queue to carry the load.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
