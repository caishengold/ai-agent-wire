8:T3522,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Implementing API Rate Limiting</h1></p><p class="text-slate-300 leading-relaxed mb-4">When your API suddenly receives ten times the normal traffic, something has to give. Without rate limiting, your services either collapse under the load or become unresponsive for everyone. Rate limiting protects your infrastructure while ensuring fair usage across all clients.</p><p class="text-slate-300 leading-relaxed mb-4">This guide covers the two most common algorithms—token bucket and sliding window—then compares Redis-based versus in-memory implementations with working code examples you can run immediately.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Problem Raj Faced</h2></p><p class="text-slate-300 leading-relaxed mb-4">Raj Mehta, platform engineer at a rapidly growing SaaS company, watched his team's API gateway melt down during a product launch. Their public API served 50,000 requests per minute on a normal day. On launch day, a single client was making 40,000 requests per minute alone, leaving 10,000 requests for everyone else.</p><p class="text-slate-300 leading-relaxed mb-4">"We had no way to control usage," Raj explained. "Our database connections maxed out, legitimate users got 503 errors, and we couldn't even identify which client was causing the problem. We needed rate limiting fast."</p><p class="text-slate-300 leading-relaxed mb-4">Raj's team implemented rate limiting over the following week. By the end, they had granular control over usage, could identify abuse patterns, and their API stability improved dramatically.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Token Bucket Algorithm</h2></p><p class="text-slate-300 leading-relaxed mb-4">The token bucket algorithm is the workhorse of rate limiting. Think of a bucket that holds a fixed number of tokens. Every request removes one token. If the bucket is empty, requests get rejected. Tokens refill at a constant rate.</p><p class="text-slate-300 leading-relaxed mb-4">Here's a working implementation in Python:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import time
import threading
from dataclasses import dataclass, field</p><p class="text-slate-300 leading-relaxed mb-4">@dataclass
class TokenBucket:
    capacity: int
    refill_rate: float  # tokens per second
    tokens: float = field(init=False)
    last_refill: float = field(init=False)
    lock: threading.Lock = field(default_factory=threading.Lock)</p><p class="text-slate-300 leading-relaxed mb-4">    def __post_init__(self):
        self.tokens = float(self.capacity)
        self.last_refill = time.monotonic()</p><p class="text-slate-300 leading-relaxed mb-4">    def _refill(self):
        now = time.monotonic()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed <em> self.refill_rate)
        self.last_refill = now</p><p class="text-slate-300 leading-relaxed mb-4">    def allow_request(self, tokens: int = 1) -> bool:
        with self.lock:
            self._refill()
            if self.tokens >= tokens:
                self.tokens -= tokens
                return True
            return False</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Usage example</h1>

    allowed = limiter.allow_request()
    print(f"Request {i+1}: {'allowed' if allowed else 'rejected'}")
    time.sleep(0.05)  # Simulate requests arriving
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This implementation uses a thread lock to handle concurrent requests safely. The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">_refill</code> method calculates how many tokens should be added based on elapsed time since the last check. When you run this, the first 100 requests succeed rapidly, then you see rejections as the bucket empties, followed by gradual recovery as tokens refill.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Sliding Window Algorithm</h2></p><p class="text-slate-300 leading-relaxed mb-4">The sliding window algorithm provides smoother rate limiting by tracking requests within a rolling time window. Instead of the sharp cutoff you see with token bucket, requests gradually become available as time passes.</p><p class="text-slate-300 leading-relaxed mb-4">Here's a sliding window implementation:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import time
import threading
from collections import deque
from dataclasses import dataclass, field</p><p class="text-slate-300 leading-relaxed mb-4">@dataclass
class SlidingWindowRateLimiter:
    max_requests: int
    window_seconds: float
    requests: deque = field(default_factory=deque)
    lock: threading.Lock = field(default_factory=threading.Lock)</p><p class="text-slate-300 leading-relaxed mb-4">    def allow_request(self) -> bool:
        with self.lock:
            now = time.monotonic()
            cutoff = now - self.window_seconds
            
            # Remove expired timestamps
            while self.requests and self.requests[0] < cutoff:
                self.requests.popleft()
            
            if len(self.requests) < self.max_requests:
                self.requests.append(now)
                return True
            return False</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Usage example</h1>
limiter = SlidingWindowRateLimiter(max_requests=10, window_seconds=1.0)</p><p class="text-slate-300 leading-relaxed mb-4">for i in range(25):
    allowed = limiter.allow_request()
    print(f"Request {i+1}: {'allowed' if allowed else 'rejected'}")
    time.sleep(0.05)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The deque stores timestamps of each request. Before allowing a new request, the code removes any timestamps older than the window. If the remaining count is below the limit, the request is allowed.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Redis vs In-Memory Implementation</h2></p><p class="text-slate-300 leading-relaxed mb-4">Your choice between Redis and in-memory storage depends on your architecture. Here's how they compare:</p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | In-Memory | Redis |
|--------|-----------|-------|
| Persistence | Lost on restart | Survives restarts |
| Distributed support | Single instance only | Works across multiple servers |
| Latency | Sub-microsecond | 1-5ms network round-trip |
| Memory | Limited to server RAM | Uses Redis server memory |
| Complexity | No external dependencies | Requires Redis infrastructure |
| Cost | Free | Server and maintenance costs |</p><p class="text-slate-300 leading-relaxed mb-4">For a single API server, in-memory works well. For distributed systems spanning multiple instances, Redis is essential since it provides a shared source of truth.</p><p class="text-slate-300 leading-relaxed mb-4">Here's a Redis-based rate limiter using the token bucket approach:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import redis
import time
import math</p><p class="text-slate-300 leading-relaxed mb-4">class RedisTokenBucket:
    def __init__(self, redis_client: redis.Redis, key: str, capacity: int, refill_rate: float):
        self.redis = redis_client
        self.key = key
        self.capacity = capacity
        self.refill_rate = refill_rate</p><p class="text-slate-300 leading-relaxed mb-4">    def allow_request(self, tokens: int = 1) -> bool:
        now = time.time()
        key = f"ratelimit:{self.key}"
        
        # Lua script for atomic operations
        lua_script = """
        local key = KEYS[1]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])
        local tokens_requested = tonumber(ARGV[3])
        local now = tonumber(ARGV[4])
        
        local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
        local current_tokens = tonumber(bucket[1])
        local last_refill = tonumber(bucket[2])
        
        if not current_tokens then
            current_tokens = capacity
            last_refill = now
        end
        
        local elapsed = now - last_refill
        current_tokens = math.min(capacity, current_tokens + elapsed </em> refill_rate)
        
        local allowed = false
        if current_tokens >= tokens_requested then
            current_tokens = current_tokens - tokens_requested
            allowed = true
        end
        
        redis.call('HMSET', key, 'tokens', current_tokens, 'last_refill', now)
        redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) * 2)
        
        return {allowed and 1 or 0, current_tokens}
        """
        
        result = self.redis.eval(
            lua_script, 1, key,
            self.capacity, self.refill_rate, tokens, now
        )
        return bool(result[0])</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Usage example</h1>

    allowed = limiter.allow_request()
    print(f"Request {i+1}: {'allowed' if allowed else 'rejected'}")
    time.sleep(0.1)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The Lua script runs atomically on the Redis server, preventing race conditions when multiple API instances check the same bucket simultaneously. This is critical for distributed systems where multiple servers handle requests.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Choosing the Right Algorithm</h2></p><p class="text-slate-300 leading-relaxed mb-4">Token bucket handles burst traffic well. If clients need to make occasional rapid requests and then pause, token bucket lets them use accumulated tokens during spikes. The tradeoff is slightly uneven distribution—you might see clusters of rejections followed by clusters of successes.</p><p class="text-slate-300 leading-relaxed mb-4">Sliding window provides more consistent, predictable limiting. Requests are smoothly distributed across the window rather than arriving in bursts. This feels fairer to clients but doesn't accommodate traffic spikes as gracefully.</p><p class="text-slate-300 leading-relaxed mb-4">For most APIs, token bucket is the better starting point. It handles real-world traffic patterns where users make batches of requests (like refreshing a page or processing a form) better than sliding window does.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Raj's team initially chose in-memory for speed but had to migrate to Redis when they added a second API server—the race conditions caused inconsistent rate limiting</li>
<li class="ml-4 list-disc text-slate-300">Setting capacity too low frustrates users; start conservative and adjust based on actual usage patterns</li>
<li class="ml-4 list-disc text-slate-300">Include rate limit headers (X-RateLimit-Limit, X-RateLimit-Remaining) so clients can adjust their behavior</li>
<li class="ml-4 list-disc text-slate-300">Monitor both rejected requests and near-limit situations—you want to catch abuse before it becomes a problem</li>
<li class="ml-4 list-disc text-slate-300">Implement tiered rate limiting (stricter for unauthenticated endpoints, more lenient for authenticated ones) to balance security with user experience</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Start with token bucket in-memory</strong> — Implement the Python class from this article on your API gateway first; you can add Redis later if needed</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add rate limit response headers</strong> — Include X-RateLimit-Limit and X-RateLimit-Remaining in all responses so clients can self-throttle</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Configure per-client limits</strong> — Different clients need different limits based on their tier; implement tiered limiting from day one</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Monitor your limiter</strong> — Track how many requests get rejected and at what rate; this data informs future limit adjustments</li>
