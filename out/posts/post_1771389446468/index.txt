8:T4c98,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">DNS for developers — record types, TTL strategies, debugging with dig, common pitfalls</h1></p><p class="text-slate-300 leading-relaxed mb-4">Aiko’s deployment pipeline updated the A record for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.shop.example.com</code> to a new Kubernetes ingress IP. Staging and her local machine picked it up within a minute. Customers in Berlin and Sydney kept getting connection refused for another 11 hours. The cause: a 43200-second (12-hour) TTL on that record. Their resolvers had cached the old IP. One config change — lowering TTL before the cutover — would have made the switch invisible. DNS is one of those layers that works until it doesn’t; when it breaks, it’s often in a region where you don’t have a terminal open. This post covers the record types you’ll actually use, how to choose TTLs, how to debug with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code>, and the mistakes that bite back.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Developers who own domains, deploy services, or chase “it works here but not there” — and want to verify instead of guess.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Record types you’ll use in practice</h2></p><p class="text-slate-300 leading-relaxed mb-4">The Domain Name System (DNS) maps names to data. Each record type answers a different question. You don’t need every type; these are the ones that show up in app and infra work.</p><p class="text-slate-300 leading-relaxed mb-4">| Type   | Purpose                          | Example use                                      |
|--------|----------------------------------|--------------------------------------------------|
| <strong>A</strong>  | Hostname → IPv4 address          | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">203.0.113.42</code>              |
| <strong>AAAA</strong> | Hostname → IPv6 address        | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">2001:db8::1</code>               |
| <strong>CNAME</strong> | Alias: name → another name    | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code>               |
| <strong>MX</strong> | Mail server for the domain       | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">mail.provider.com</code> (with priority) |
| <strong>TXT</strong> | Arbitrary text (verification, SPF, DKIM) | Domain ownership, email auth              |
| <strong>NS</strong> | Which servers are authoritative  | Delegation to your DNS provider                  |
| <strong>SRV</strong> | Service discovery (host, port, priority) | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">_http._tcp.api.example.com</code> → host + port |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Rule that trips people up:</strong> A CNAME makes a name an alias of exactly one other name. You cannot have both a CNAME and another record type (A, MX, TXT, etc.) for the same label. Either the label is an alias (CNAME only) or it has “real” records. At the zone apex (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> with nothing in front), a bare CNAME is also problematic; many providers offer “ALIAS” or “CNAME flattening” so the apex can point at another hostname without breaking MX or other records.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 1: inspecting records with dig</h2></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> is the standard CLI tool for querying DNS. You give it a name and optionally a record type; it returns the answer, TTLs, and which server replied.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">A record (IPv4) — replace with your own domain to experiment</h1>
dig +short api.github.com A
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>20.248.137.48
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Without <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">+short</code> you get the full response: TTL, flags, and authority info.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dig api.github.com A
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output (abbreviated):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>; <<>> DiG 9.18.24 <<>> api.github.com A
;; QUESTION SECTION:
;api.github.com.			IN	A</p><p class="text-slate-300 leading-relaxed mb-4">;; ANSWER SECTION:
api.github.com.		43	IN	A	20.248.137.48</p><p class="text-slate-300 leading-relaxed mb-4">;; Query time: 8 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">43</code> in the answer is the TTL in seconds — resolvers may cache this for up to 43 seconds. Checking several types:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">A and AAAA for dual-stack</h1>
dig +short api.github.com A
dig +short api.github.com AAAA</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">MX for mail</h1>
dig +short gmail.com MX</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">TXT (e.g. domain verification)</h1>
dig +short github.com TXT
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example MX output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>5 gmail-smtp-in.l.google.com.
10 alt1.gmail-smtp-in.l.google.com.
20 alt2.gmail-smtp-in.l.google.com.
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">TTL strategies: when to use what</h2></p><p class="text-slate-300 leading-relaxed mb-4">TTL (time-to-live) is how long resolvers and clients may cache the answer. No single number fits every case.</p><p class="text-slate-300 leading-relaxed mb-4">| Situation                         | Typical TTL (seconds)   | Why |
|----------------------------------|-------------------------|-----|
| Stable production endpoint       | 300–3600 (5 min–1 h)    | Balance cache hits with ability to change IPs with notice |
| Pre-migration or failover        | 60–300 (1–5 min)       | After you flip the record, most clients see it within minutes |
| CDN or load-balanced pool        | 300–600                 | Some caching; provider may suggest or override |
| Static marketing site            | 3600–86400 (1–24 h)    | Rarely changes; long TTL cuts DNS load and speeds lookups |
| Staging or ephemeral envs        | 60–300                  | IPs change or tear down; low TTL so fixes stick |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cutover drill:</strong> Lower TTL to 60–300 at least one full TTL period <em>before</em> you change the record. If current TTL is 3600, set it to 300, wait an hour so old caches expire, then change the A/AAAA target. That avoids the “half the world still has the old IP” situation Aiko hit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 2: tracing resolution and querying authority</h2></p><p class="text-slate-300 leading-relaxed mb-4">When “my domain doesn’t resolve” or “I updated DNS but nothing changed”, you need: (1) what your machine gets, (2) what the authoritative server says, (3) whether something in between is caching.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">1. What your default resolver returns</h1>
dig +short docs.github.com A</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">2. Get the nameservers for the zone</h1>
dig +short github.com NS
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example NS output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dns1.p08.nsone.net.
dns2.p08.nsone.net.
dns3.p08.nsone.net.
dns4.p08.nsone.net.
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">3. Ask one of those NS directly (bypass local/cache)</h1>
dig @dns1.p08.nsone.net docs.github.com A +short
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If the authority answer matches what you expect but your default resolver does not, the issue is caching (wait for TTL or flush). If the authority answer is wrong, the bug is in your DNS config at the provider.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Check from another view:</strong> Your laptop may use a different resolver than production. Use a public resolver:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dig @8.8.8.8 docs.github.com A +short
dig @1.1.1.1 docs.github.com A +short
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Full resolution path (optional): <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig +trace docs.github.com A</code> walks the chain from root → TLD → authoritative and shows each hop. Useful when delegation or glue records are wrong.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Low TTL vs high TTL: comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| | Low TTL (e.g. 60–300 s) | High TTL (e.g. 3600–86400 s) |
|--|--------------------------|-------------------------------|
| <strong>Pros</strong> | Changes propagate quickly; fewer “stale IP” incidents after migrations | Fewer DNS queries, less load on auth servers, faster repeat lookups from cache |
| <strong>Cons</strong> | More queries to your DNS provider; slightly higher latency on cache miss | After a change, some users keep the old IP until TTL expires |
| <strong>When to use</strong> | Before/after migrations, failover, or when the target IP changes often | Stable endpoints, static assets, when you rarely change the mapping |</p><p class="text-slate-300 leading-relaxed mb-4">We use 300 s for most production APIs and drop to 60 s the day before a planned cutover.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Common pitfalls</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>CNAME at the zone apex.</strong> The apex is the domain itself (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code>). A CNAME at the apex can conflict with MX and other records and is not allowed by the standard. Use A/AAAA or a provider-specific “ALIAS” / “flattened” target that resolves to an IP on the provider’s side.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Not lowering TTL before a change.</strong> You change the A record; part of the world keeps the old IP for hours. Lower TTL first, wait at least one full old TTL, then switch.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Assuming your change is live everywhere.</strong> Browsers, OS, and recursive resolvers all cache. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> from your machine shows what <em>your</em> resolver returned; production may use another resolver or region. Check from another network or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @8.8.8.8</code> / <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @1.1.1.1</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>TXT record formatting.</strong> TXT can have multiple strings; providers may show them concatenated or separate. For SPF/DKIM, a single string is usual; watch for line breaks or extra quotes that break validation.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>CNAME and another record on the same label.</strong> You cannot have both a CNAME and an A record for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www.example.com</code>. Pick one: either CNAME to another hostname or A/AAAA to IP(s).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>SRV and CNAME confusion.</strong> SRV gives host + port; the host in the SRV target must resolve (usually A/AAAA). If that target is a CNAME, the chain must resolve end-to-end; a broken CNAME breaks the SRV lookup.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">On a migration in 2025 we moved an API from one cloud region to another. We updated the A record to the new load balancer IP and ran smoke tests from our office — all green. Within an hour we got reports of timeouts from users in South America and Southeast Asia. Our office resolver had picked up the new IP quickly; resolvers in those regions were still serving the old one (TTL had been 7200). We had to lower TTL to 60, wait 2 hours, then change the record again. Downtime for those users was about 90 minutes. We now keep TTL at 300 for that record and have a runbook: “Before any IP or host change: set TTL to 60, wait 2× previous TTL, then apply change.”</p><p class="text-slate-300 leading-relaxed mb-4">Another incident: Omar added a CNAME for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> pointing at a third-party API gateway. The provider required a TXT record on the same name for verification. As soon as he added the TXT, DNS broke — their provider did not allow CNAME + TXT on the same label (strict RFC behaviour). The fix was to use a subdomain like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">gateway.api.example.com</code> for the CNAME and keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> as an A record, or use the provider’s “CNAME flattening” so the apex-like name wasn’t a real CNAME in the zone. Lesson: check whether your DNS host allows CNAME plus other types; many do not.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit TTLs</strong> for any hostname that might change (APIs, load balancer targets). If they’re above 600, document why; if you have a migration plan, include “lower TTL 1–2× current TTL before cutover”.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> from your machine and from a public resolver</strong> when debugging: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig +short <name> A</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @1.1.1.1 +short <name> A</code>. If they differ, it’s cache or resolver-specific.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Avoid CNAME at the zone apex.</strong> Use A/AAAA or your provider’s ALIAS/flattening for the root domain; use CNAME for subdomains (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api</code>) when you want to point at another hostname.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Before adding a CNAME, check</strong> whether that label already has (or will need) MX, TXT, or A. If it does, use a different subdomain or an A record.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Keep a one-line runbook</strong> for DNS changes: “TTL ≤ 300 for mutable targets; before cutover: set TTL to 60, wait 2× old TTL, then change record; verify with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @8.8.8.8 <name> A</code>.”</li></p><p class="text-slate-300 leading-relaxed mb-4">Once you’re used to reading <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> output and thinking in TTLs, most DNS issues become quick to isolate — and you avoid the 3 AM “why is Asia still hitting the old server?” call.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
