8:T583b,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Building a Multi-LLM Routing System: From GLM-4-Flash to Cursor-Local</h1></p><p class="text-slate-300 leading-relaxed mb-4">When Raj Patel joined Nexus AI as the infrastructure lead in early 2025, he faced a problem that was becoming all too common in companies building AI-powered products. The engineering team had deployed multiple large language models across different use cases — GLM-4-Flash for fast, high-volume tasks; GPT-4 for complex reasoning; Claude for creative writing — but each model was called independently, with no centralized routing logic. Costs were climbing unpredictably, latency varied wildly depending on which model happened to handle a request, and the team had no unified way to enforce policies across their LLM ecosystem.</p><p class="text-slate-300 leading-relaxed mb-4">Raj's solution was to build an intelligent routing layer that could automatically direct requests to the most appropriate model based on task complexity, cost constraints, latency requirements, and output quality needs. Six months later, Nexus AI had reduced their LLM spending by 47% while actually improving average response times by 30%. This post walks through how they built that system.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Problem: Why Single-Model Architectures Break Down</h2></p><p class="text-slate-300 leading-relaxed mb-4">Most teams start with a single LLM and gradually add more as they discover each model's strengths. Nexus AI was no different. By late 2024, they had four models in production:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>GLM-4-Flash</strong> (Zhipu AI) for simple transformations, classifications, and high-volume tasks</li>
<li class="ml-4 list-disc text-slate-300"><strong>GPT-4o</strong> for complex reasoning and multi-step problems</li>
<li class="ml-4 list-disc text-slate-300"><strong>Claude 3.5 Sonnet</strong> for creative writing and nuanced content generation</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cursor-local</strong> (a fine-tuned Llama 3.1 70B deployed on-premises) for privacy-sensitive tasks and cost optimization</li></p><p class="text-slate-300 leading-relaxed mb-4">The issue was that every developer decided which model to call based on intuition. Some requests that could have been handled by the fast, cheap GLM-4-Flash were being sent to GPT-4o, burning budget unnecessarily. Other requests that needed GPT-4o's reasoning capabilities were being routed to smaller models, resulting in poor output quality that required rework.</p><p class="text-slate-300 leading-relaxed mb-4">Raj realized they needed a systematic approach — not just manual routing rules, but an intelligent system that could classify requests and make routing decisions automatically.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Architecture Overview</h2></p><p class="text-slate-300 leading-relaxed mb-4">The routing system sits between the application's API layer and the various LLM providers.     def __init__(self, models: List[ModelInfo], classifier: RequestClassifier):

        self.latency_history: Dict[str, List[float]] = {}
    
    async def route(self, prompt: str, context: Optional[Dict] = None) -> str:
        classification = await self.classifier.classify(prompt)
        
        # Get available candidates that support the required capability
        candidates = [
            model for model in self.models.values()
            if classification.required_capability in model.capabilities
        ]
        
        # Apply business rules first
        if classification.prefer_local:
            local_candidates = [m for m in candidates if "local" in m.name.lower()]
            if local_candidates:
                candidates = local_candidates
        
        # Score each candidate
        scored = []
        for model in candidates:
            cost_score = self._calculate_cost_score(model, classification)
            latency_score = self._calculate_latency_score(model)
            quality_score = self._calculate_quality_score(classification.complexity)
            
            # Weighted scoring (can be tuned per-use-case)
            total_score = (cost_score <em> 0.4 + 
                         latency_score </em> 0.3 + 
                         quality_score <em> 0.3)
            
            scored.append((model, total_score))
        
        # Select best candidate
        scored.sort(key=lambda x: x[1], reverse=True)
        selected_model = scored[0][0]
        
        # Log the decision for analysis
        await self._log_routing_decision(
            prompt[:100], classification, selected_model.name, scored[0][1]

        # Convert to a 0-1 score (lower cost = higher score)
        return 1.0 / (1.0 + estimated_cost * 10)

        # Get recent latency from history if available
        if model.name in self.latency_history and self.latency_history[model.name]:
            recent = self.latency_history[model.name][-10:]
            avg_latency = sum(recent) / len(recent)
        else:
            avg_latency = model.avg_latency_ms

        return 1.0 / (1.0 + avg_latency / 1000)

Here are three challenges the team faced and how they solved them.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Challenge 1: Cold Start for New Prompts</strong></p><p class="text-slate-300 leading-relaxed mb-4">When the classifier encountered prompts significantly different from anything in its training data, accuracy dropped. The solution was to implement a fallback mechanism: if classification confidence fell below 60%, the system would try the simpler model first, then escalate to a more capable model if the output failed validation checks.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Challenge 2: Cost vs. Quality Tradeoffs</strong></p><p class="text-slate-300 leading-relaxed mb-4">Early versions of the router prioritized cost savings too aggressively. Some users complained that outputs for seemingly complex tasks felt "shallow." The team adjusted the weighting — increasing quality_score from 0.2 to 0.3 — and added a manual override option for users who needed guaranteed high-quality output regardless of cost.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Challenge 3: Model Availability</strong></p><p class="text-slate-300 leading-relaxed mb-4">On two occasions, an external API experienced downtime. The router needed to handle these failures gracefully. They added circuit breakers that would temporarily remove unavailable models from the candidate pool, and implemented automatic retry logic with escalation to backup models.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Start with classification, not routing</strong> — Building an accurate classifier is the foundation. Without understanding what kind of request you're handling, routing becomes guesswork.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Track every routing decision</strong> — The log_routing_decision method seems like overhead, but it provided the data needed to tune weights and identify edge cases.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Model pricing changes frequently</strong> — The cost estimator needs to be configurable without code changes. Treat model pricing as external configuration, not hardcoded constants.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Fallback chains matter more than perfect routing</strong> — No classifier is perfect. Building a reliable escalation path from simple to complex models is essential.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Latency prediction is underrated</strong> — Most teams focus on cost optimization, but latency improvements often have bigger impact on user experience.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit your current model usage</strong> — Review logs from the past month to see what percentage of requests could be handled by a cheaper, faster model. You might find that 40-60% of your spend goes to tasks that don't require your most expensive model.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Build a simple heuristic classifier first</strong> — Before training ML models, try rule-based classification using prompt length, keyword detection, and structure analysis. This gets you 80% of the benefit with 10% of the effort.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Implement cost-per-request tracking</strong> — If you don't already track cost at the request level, add instrumentation now. You need this data to validate routing decisions and demonstrate ROI.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Configure circuit breakers for all external models</strong> — Model providers experience outages. Your routing system should handle these gracefully without requiring manual intervention.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Start with cost-based routing, then add sophistication</strong> — The biggest wins come from routing simple tasks to cheap models. Only after achieving that baseline should you invest in latency optimization and quality scoring.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4">Building a multi-LLM routing system isn't just about saving money — it's about building infrastructure that can adapt as the LLM landscape evolves. New models launch monthly, pricing fluctuates, and capabilities shift. A well-designed routing layer gives you the flexibility to take advantage of these changes without rewriting your application logic.</p><p class="text-slate-300 leading-relaxed mb-4">Raj's team continues to refine their system.
