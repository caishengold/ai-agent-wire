Building a Multi-LLM Routing System: From GLM-4-Flash to Cursor-Local

When Raj Patel joined Nexus AI as the infrastructure lead in early 2025, he faced a problem that was becoming all too common in companies building AI-powered products. The engineering team had deployed multiple large language models across different use cases — GLM-4-Flash for fast, high-volume tasks; GPT-4 for complex reasoning; Claude for creative writing — but each model was called independently, with no centralized routing logic. Costs were climbing unpredictably, latency varied wildly depending on which model happened to handle a request, and the team had no unified way to enforce policies across their LLM ecosystem.

Raj's solution was to build an intelligent routing layer that could automatically direct requests to the most appropriate model based on task complexity, cost constraints, latency requirements, and output quality needs. Six months later, Nexus AI had reduced their LLM spending by 47% while actually improving average response times by 30%. This post walks through how they built that system.

The Problem: Why Single-Model Architectures Break Down

Most teams start with a single LLM and gradually add more as they discover each model's strengths. Nexus AI was no different. By late 2024, they had four models in production:

  • GLM-4-Flash (Zhipu AI) for simple transformations, classifications, and high-volume tasks
  • GPT-4o for complex reasoning and multi-step problems
  • Claude 3.5 Sonnet for creative writing and nuanced content generation
  • Cursor-local (a fine-tuned Llama 3.1 70B deployed on-premises) for privacy-sensitive tasks and cost optimization

    • The issue was that every developer decided which model to call based on intuition. Some requests that could have been handled by the fast, cheap GLM-4-Flash were being sent to GPT-4o, burning budget unnecessarily. Other requests that needed GPT-4o's reasoning capabilities were being routed to smaller models, resulting in poor output quality that required rework.

    Raj realized they needed a systematic approach — not just manual routing rules, but an intelligent system that could classify requests and make routing decisions automatically.

    The Request Classifier analyzes incoming prompts to determine complexity, intent, and required capabilities. The Cost Estimator predicts token usage for each available model. The Latency Predictor maintains historical performance data to estimate response times. The Router Core combines these signals with business rules to make the final routing decision.

    The Request Classifier

    The classifier is the brain of the system. It needs to be fast (it's called on every request) and reasonably accurate. Nexus AI trained a lightweight classifier using embeddings from their most capable model, then distilled that into a smaller model they could run locally.

    Here's the core classification logic:

    from dataclasses import dataclass
from enum import Enum
from typing import Optional
import numpy as np
    class TaskComplexity(Enum):
    SIMPLE = "simple"           # Transformations, classifications
    MODERATE = "moderate"       # Multi-step reasoning
    COMPLEX = "complex"         # Deep analysis, creative tasks
    class RequiredCapability(Enum):
    REASONING = "reasoning"
    CREATIVITY = "creativity"
    FACTUAL = "factual"
    TRANSFORMATION = "transformation"
    @dataclass
class RequestClassification:
    complexity: TaskComplexity
    required_capability: RequiredCapability
    estimated_input_tokens: int
    confidence: float
    prefer_local: bool = False  # Privacy-sensitive?
    class RequestClassifier:
    def __init__(self, embedding_model, capability_model):
        self.embedding_model = embedding_model
        self.capability_model = capability_model
        self.complexity_threshold = 0.65
    
    async def classify(self, prompt: str) -> RequestClassification:
        # Get embedding for similarity-based classification
        embedding = await self.embedding_model.embed(prompt)
        
        # Check for privacy-sensitive keywords
        privacy_keywords = ["private", "internal", "confidential", "customer data"]
        prefer_local = any(kw in prompt.lower() for kw in privacy_keywords)
        
        # Classify complexity based on prompt features
        complexity_score = self._calculate_complexity(prompt, embedding)
        
        if complexity_score < 0.3:
            complexity = TaskComplexity.SIMPLE
        elif complexity_score < 0.7:
            complexity = TaskComplexity.MODERATE
        else:
            complexity = TaskComplexity.COMPLEX
        
        # Identify required capability
        capability = self._identify_capability(prompt)
        
        # Estimate tokens
        estimated_tokens = len(prompt) // 4  # Rough estimate
        
        return RequestClassification(
            complexity=complexity,
            required_capability=capability,
            estimated_input_tokens=estimated_tokens,
            confidence=abs(complexity_score - 0.5)  2,
            prefer_local=prefer_local
        )
    
    def _calculate_complexity(self, prompt: str, embedding: np.ndarray) -> float:
        # Multiple signals combined into a score
        length_signal = min(len(prompt) / 2000, 1.0)
        question_mark_density = prompt.count('?') / max(len(prompt) / 100, 1)
        step_keywords = sum(1 for kw in ["analyze", "compare", "evaluate", "explain why"] 
                          if kw in prompt.lower())
        
        # Simple weighted combination
        score = (length_signal  0.3 + 
                min(question_mark_density, 1)  0.3 + 
                min(step_keywords / 3, 1)  0.4)
        
        return min(score, 1.0)
    
    def _identify_capability(self, prompt: str) -> RequiredCapability:
        prompt_lower = prompt.lower()
        
        if any(kw in prompt_lower for kw in ["write", "create", "story", "creative"]):
            return RequiredCapability.CREATIVITY
        elif any(kw in prompt_lower for kw in ["why", "reason", "explain", "analyze"]):
            return RequiredCapability.REASONING
        elif any(kw in prompt_lower for kw in ["fact", "when", "where", "who"]):
            return RequiredCapability.FACTUAL
        else:
            return RequiredCapability.TRANSFORMATION

    This classifier runs in under 50ms and correctly identifies task complexity about 87% of the time. For edge cases where confidence is low, the system defaults to routing to a more capable model rather than risk poor output quality.

    The Routing Engine

    Once a request is classified, the routing engine makes the final decision. It combines the classification with cost and latency signals, plus any business rules the team has configured.

    from dataclasses import dataclass
from typing import List, Dict, Optional
from datetime import datetime, timedelta
import asyncio
    @dataclass
class ModelInfo:
    name: str
    provider: str
    cost_per_1k_input: float
    cost_per_1k_output: float
    avg_latency_ms: float
    capabilities: List[RequiredCapability]
    supports_streaming: bool = True
    class RoutingEngine:
    def __init__(self, models: List[ModelInfo], classifier: RequestClassifier):
        self.models = {m.name: m for m in models}
        self.classifier = classifier
        self.latency_history: Dict[str, List[float]] = {}
    
    async def route(self, prompt: str, context: Optional[Dict] = None) -> str:
        classification = await self.classifier.classify(prompt)
        
        # Get available candidates that support the required capability
        candidates = [
            model for model in self.models.values()
            if classification.required_capability in model.capabilities
        ]
        
        # Apply business rules first
        if classification.prefer_local:
            local_candidates = [m for m in candidates if "local" in m.name.lower()]
            if local_candidates:
                candidates = local_candidates
        
        # Score each candidate
        scored = []
        for model in candidates:
            cost_score = self._calculate_cost_score(model, classification)
            latency_score = self._calculate_latency_score(model)
            quality_score = self._calculate_quality_score(classification.complexity)
            
            # Weighted scoring (can be tuned per-use-case)
            total_score = (cost_score  0.4 + 
                         latency_score  0.3 + 
                         quality_score  0.3)
            
            scored.append((model, total_score))
        
        # Select best candidate
        scored.sort(key=lambda x: x[1], reverse=True)
        selected_model = scored[0][0]
        
        # Log the decision for analysis
        await self._log_routing_decision(
            prompt[:100], classification, selected_model.name, scored[0][1]
        )
        
        return selected_model.name
    
    def _calculate_cost_score(self, model: ModelInfo, classification: RequestClassification) -> float:
        estimated_cost = (model.cost_per_1k_input  classification.estimated_input_tokens / 1000)
        # Convert to a 0-1 score (lower cost = higher score)
        return 1.0 / (1.0 + estimated_cost * 10)
    
    def _calculate_latency_score(self, model: ModelInfo) -> float:
        # Get recent latency from history if available
        if model.name in self.latency_history and self.latency_history[model.name]:
            recent = self.latency_history[model.name][-10:]
            avg_latency = sum(recent) / len(recent)
        else:
            avg_latency = model.avg_latency_ms
        
        # Lower latency = higher score
        return 1.0 / (1.0 + avg_latency / 1000)
    
    def _calculate_quality_score(self, complexity: TaskComplexity) -> float:
        # Map complexity to expected quality requirements
        quality_requirements = {
            TaskComplexity.SIMPLE: 0.5,
            TaskComplexity.MODERATE: 0.75,
            TaskComplexity.COMPLEX: 1.0
        }
        return quality_requirements[complexity]
    
    async def _log_routing_decision(self, prompt_preview: str, 
                                    classification: RequestClassification,
                                    selected: str, score: float):
        # In production, this would write to a metrics system
        print(f"Routed: {classification.complexity.value}/{classification.required_capability.value} "
              f"-> {selected} (score: {score:.2f})")

    Cost Analysis: The Numbers That Matter

    After deploying the routing system, Raj's team tracked metrics for three months. The results validated the investment.

    | Metric | Before Routing | After Routing | Change | |--------|---------------|---------------|--------| | Monthly LLM spend | $24,500 | $12,980 | -47% | | Average response time | 1.8s | 1.26s | -30% | | Simple task routing to GLM-4-Flash | 0% | 78% | +78% | | Complex tasks sent to GPT-4o | 100% | 94% | -6% | | Privacy tasks sent to Cursor-local | 0% | 89% | +89% |

    The biggest win came from automatically routing simple, high-volume tasks to GLM-4-Flash. These tasks — things like text classification, format conversion, and simple summarization — made up about 60% of total requests but were being handled by more expensive models. The routing system identified these patterns and redirected them appropriately.

    The latency improvement came from a less obvious source: the latency predictor. By maintaining historical performance data, the router learned that GPT-4o was actually slower during certain time windows (likely due to server load) and began routing more requests to Claude during those periods, even when GPT-4o would have been equally capable.

    Implementation Challenges

    Building the routing system wasn't without obstacles. Here are three challenges the team faced and how they solved them.

    Challenge 1: Cold Start for New Prompts

    When the classifier encountered prompts significantly different from anything in its training data, accuracy dropped. The solution was to implement a fallback mechanism: if classification confidence fell below 60%, the system would try the simpler model first, then escalate to a more capable model if the output failed validation checks.

    Challenge 2: Cost vs. Quality Tradeoffs

    Early versions of the router prioritized cost savings too aggressively. Some users complained that outputs for seemingly complex tasks felt "shallow." The team adjusted the weighting — increasing quality_score from 0.2 to 0.3 — and added a manual override option for users who needed guaranteed high-quality output regardless of cost.

    Challenge 3: Model Availability

    On two occasions, an external API experienced downtime. The router needed to handle these failures gracefully. They added circuit breakers that would temporarily remove unavailable models from the candidate pool, and implemented automatic retry logic with escalation to backup models.

    Lessons Learned

  • Start with classification, not routing — Building an accurate classifier is the foundation. Without understanding what kind of request you're handling, routing becomes guesswork.

  • Track every routing decision — The log_routing_decision method seems like overhead, but it provided the data needed to tune weights and identify edge cases.

  • Model pricing changes frequently — The cost estimator needs to be configurable without code changes. Treat model pricing as external configuration, not hardcoded constants.

  • Fallback chains matter more than perfect routing — No classifier is perfect. Building a reliable escalation path from simple to complex models is essential.

  • Latency prediction is underrated — Most teams focus on cost optimization, but latency improvements often have bigger impact on user experience.

    • Actionable Takeaways

  • Audit your current model usage — Review logs from the past month to see what percentage of requests could be handled by a cheaper, faster model. You might find that 40-60% of your spend goes to tasks that don't require your most expensive model.

  • Build a simple heuristic classifier first — Before training ML models, try rule-based classification using prompt length, keyword detection, and structure analysis. This gets you 80% of the benefit with 10% of the effort.

  • Implement cost-per-request tracking — If you don't already track cost at the request level, add instrumentation now. You need this data to validate routing decisions and demonstrate ROI.

  • Configure circuit breakers for all external models — Model providers experience outages. Your routing system should handle these gracefully without requiring manual intervention.

  • Start with cost-based routing, then add sophistication — The biggest wins come from routing simple tasks to cheap models. Only after achieving that baseline should you invest in latency optimization and quality scoring.

    • Building a multi-LLM routing system isn't just about saving money — it's about building infrastructure that can adapt as the LLM landscape evolves. New models launch monthly, pricing fluctuates, and capabilities shift. A well-designed routing layer gives you the flexibility to take advantage of these changes without rewriting your application logic.

    Raj's team continues to refine their system. They're now experimenting with per-user routing (some users consistently need higher quality) and real-time cost monitoring that can trigger alerts when monthly spend approaches budget limits. The routing layer has become a platform for experimentation rather than just a cost-saving mechanism.
