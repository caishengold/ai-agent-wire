Error Boundaries Beyond React — Global Error Handling Patterns in Node, Bun, Deno

When Sofia Martinez joined a health-tech startup as their backend lead, she inherited a Node.js service that crashed silently during unhandled promise rejections. The errors would appear in logs with no context, making debugging a nightmare. Her team spent weeks tracking down issues that could have been caught at the application boundary.

Sofia's story is familiar to many developers. While React's error boundaries get plenty of attention, the runtime environments underneath deserve the same care. Each major JavaScript runtime—Node.js, Bun, and Deno—offers distinct approaches to global error handling. Understanding these patterns prevents production incidents and makes debugging significantly easier.

The Problem with Silent Failures

Unhandled promise rejections and uncaught exceptions don't always surface immediately. They might fail silently in production, leaving you with corrupted data and no trace of what went wrong. A database write that fails without notification, an API call that times out without error handling—these small gaps compound into reliability issues.

Every runtime handles these scenarios differently. Let's examine how each one approaches global error management.

Node.js: The Event Emitter Approach

Node.js uses process-level event listeners to capture errors that escape your application code. The process object emits events for uncaught exceptions and unhandled promise rejections.

const http = require('http');
const server = http.createServer((req, res) => {
  if (req.url === '/crash') {
    throw new Error('Simulated crash');
  }
  res.end('OK');
});
process.on('uncaughtException', (error) => {
  console.error([${new Date().toISOString()}] Uncaught Exception:, error.message);
  console.error('Stack trace:', error.stack);
  process.exit(1);
});
process.on('unhandledRejection', (reason, promise) => {
  console.error([${new Date().toISOString()}] Unhandled Rejection at:, promise);
  console.error('Reason:', reason);
});
server.listen(3000, () => {
  console.log('Server running on port 3000');
});

The critical detail here is process.exit(1). After handling an uncaught exception, you must exit explicitly. Node.js enters an unstable state after such errors, and continuing execution risks data corruption.

For production Node.js services, also consider using domains (deprecated but still functional) or the throw handling in async contexts. The key principle: always log with timestamps and stack traces, then decide whether to exit gracefully.

Bun: Native Graceful Shutdown

Bun takes a more modern approach, treating unhandled errors as fatal by default. Unlike Node.js, Bun exits immediately on uncaught exceptions with a detailed error report. This behavior forces you to handle errors properly rather than letting them slip through.

const server = Bun.serve({
  port: 3000,
  fetch(req) {
    if (new URL(req.url).pathname === '/crash') {
      throw new Error('Bun crash');
    }
    return new Response('OK');
  },
});
process.on('uncaughtException', (error) => {
  console.error([${new Date().toISOString()}] Uncaught:, error.message);
  server.stop();
  process.exit(1);
});
process.on('unhandledRejection', (reason) => {
  console.error([${new Date().toISOString()}] Unhandled rejection:, reason);
  server.stop();
  process.exit(1);
});
console.log(Bun server running on port ${server.port});

Bun's built-in HTTP server (Bun.serve) returns a server object with a .stop() method. This enables graceful shutdown—stop accepting new requests, finish processing existing ones, then exit. The approach prevents the race conditions that occur when you call process.exit() immediately.

The trade-off is that Bun's strictness requires more explicit error handling. What some developers see as rigidity, others view as enforcement of better practices.

Deno: Permission-Based Safety

Deno's approach differs fundamentally. Its permission system prevents many errors before they occur, and its global error handlers integrate with the broader runtime safety model.

const server = Deno.serve({
  port: 3000,
  handler: (req) => {
    if (new URL(req.url).pathname === '/crash') {
      throw new Error('Deno crash');
    }
    return new Response('OK');
  },
});
Deno.addSignalListener('SIGINT', async () => {
  console.log('Shutting down gracefully...');
  await server.finished;
  Deno.exit(0);
});
self.onerror = (message, source, lineno, colno, error) => {
  console.error([${new Date().toISOString()}] Global error:, message);
  console.error('Line:', lineno, 'Column:', colno);
  return false;
};
self.onunhandledrejection = (event) => {
  console.error([${new Date().toISOString()}] Unhandled promise rejection:, event.reason);
};
console.log(Deno server running on port ${server.port});

Deno uses self.onerror and self.onunhandledrejection rather than Node's process events. This reflects Deno's web-standard-first approach. The Deno.serve API returns a server with a .finished property—a Promise that resolves when all pending requests complete. This makes graceful shutdown straightforward.

Additionally, Deno's permission flags (--allow-read, --allow-net, etc.) reduce the blast radius of runtime errors. Even if your code crashes, the damage is constrained by what the process was permitted to do.

Comparing the Three Runtimes

Each runtime takes a different philosophy toward global error handling. Here's how they stack up:

| Aspect | Node.js | Bun | Deno | |--------|---------|-----|------| | Uncaught exception behavior | Emits event, continues | Exits immediately with report | Emits event, exits | | Unhandled rejection behavior | Emits warning, continues | Exits immediately | Emits event, continues | | Built-in HTTP server | No (requires Express/Fastify) | Yes (Bun.serve) | Yes (Deno.serve) | | Graceful shutdown support | Manual | server.stop() + promises | server.finished Promise | | Permission system | No | No | Yes | | Web standard API | No | Partial | Yes |

Node.js offers the most flexibility but requires explicit handling at every level. Bun prioritizes simplicity and crash-fast behavior. Deno combines error handling with its security model for defense in depth.

A Real-World Pattern That Works

Raj Patel, a platform engineer at an e-commerce company, implemented a unified error handler across services running on all three runtimes. His team uses a wrapper pattern that normalizes error handling regardless of the underlying runtime.

function createErrorHandler(serviceName, server) {
  const timestamp = () => new Date().toISOString();
  
  const logError = (type, error) => {
    console.error([${timestamp()}] ${serviceName} - ${type}:, {
      message: error?.message || error,
      stack: error?.stack,
      runtime: Deno ? 'deno' : (Bun ? 'bun' : 'node'),
    });
  };
  const shutdown = async (code = 1) => {
    console.log([${timestamp()}] ${serviceName} shutting down...);
    if (server?.stop) await server.stop();
    if (server?.finished) await server.finished;
    process.exit(code);
  };
  if (typeof self !== 'undefined' && self.onerror !== undefined) {
    self.onerror = (msg, src, line, col, err) => {
      logError('uncaughtException', err || new Error(msg));
      shutdown();
    };
    self.onunhandledrejection = (e) => {
      logError('unhandledRejection', e.reason);
    };
  } else if (typeof process !== 'undefined') {
    process.on('uncaughtException', (err) => {
      logError('uncaughtException', err);
      shutdown();
    });
    process.on('unhandledRejection', (reason) => {
      logError('unhandledRejection', reason);
    });
  }
}
export { createErrorHandler };

This pattern captures the essence of what works in production: consistent logging, graceful shutdown, and runtime-agnostic code that works across environments. Raj's team deploys the same service to different runtimes depending on the workload—Bun for high-throughput API gateways, Deno for security-sensitive internal services, Node.js for legacy integrations.

Lessons Learned

  • Always implement graceful shutdown—let in-flight requests complete before exiting, regardless of the runtime
  • Include timestamps in all error logs—helps correlate incidents across distributed systems
  • Log the stack trace explicitly—Node.js error stacks are more detailed than Bun or Deno by default
  • Test your error handlers—manually trigger crashes in staging to verify your handlers work as expected
  • Consider a unified handler if you deploy across runtimes—reduces mental overhead and ensures consistent behavior

    • Actionable Takeaways

  • Add global error handlers to every service — Even simple services can fail in ways that mask root causes without proper logging
  • Implement graceful shutdown — Use the runtime's shutdown primitives (server.stop(), server.finished, or equivalent) before calling process.exit()
  • Standardize error log format — Include timestamp, service name, error type, message, and stack trace in every log entry
  • Test error paths in staging — Manually trigger uncaught exceptions and verify your handlers log appropriately and shut down cleanly
  • Choose your runtime based on error handling philosophy — Bun's crash-fast model suits teams wanting enforcement; Node.js suits those needing maximum control; Deno suits security-sensitive applications

    • The right error handling pattern depends on your team's priorities. Sofia's team eventually migrated their most critical services to Deno for its permission system and web-standard APIs. Raj's team kept Node.js for backward compatibility but added Bun for new high-performance services. The common thread: they stopped letting errors escape silently.
