API Pagination Patterns — Offset, Cursor, and Keyset Comparison with SQLite

When your API returns thousands of records, you cannot dump everything in a single response. Pagination solves this problem, but choosing the wrong pagination strategy creates performance nightmares. Raj Mehta, backend lead at a logistics company in Berlin, learned this the hard way when his team's shipment tracking API started timing out during peak hours.

His team was using offset pagination because it seemed simple. The problem: as the offset grew larger, queries slowed down dramatically. A request for page 10,000 took over 8 seconds. The root cause was that SQLite had to scan and skip nearly 10,000 rows before returning results.

This article compares three pagination approaches — offset, cursor, and keyset — with working SQLite examples so you can choose the right one for your use case.

The Three Pagination Patterns

Offset Pagination

Offset pagination uses LIMIT and OFFSET clauses to skip a specific number of rows. This is the most common approach because it feels intuitive.

import sqlite3
def get_shipments_offset(page: int, page_size: int = 20) -> list[dict]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    offset = (page - 1) * page_size
    
    cursor = conn.execute("""
        SELECT id, tracking_code, status, created_at
        FROM shipments
        ORDER BY created_at DESC
        LIMIT ? OFFSET ?
    """, (page_size, offset))
    
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    return results

This pattern is straightforward. You request page 5, and the database skips the first 80 rows to get to page 5 with 20 items per page.

The problem emerges at scale. SQLite has to evaluate every row up to the offset point. When you request page 500, the database scans 9,980 rows and throws away 9,980 of them. This becomes unsustainable with millions of records.

Cursor Pagination

Cursor pagination uses an opaque marker — typically the last record's primary key or a timestamp — instead of an offset. The client sends back the cursor from the previous response to get the next batch.

def get_shipments_cursor(last_id: int | None, page_size: int = 20) -> tuple[list[dict], int | None]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    if last_id is None:
        cursor = conn.execute("""
            SELECT id, tracking_code, status, created_at
            FROM shipments
            ORDER BY id DESC
            LIMIT ?
        """, (page_size,))
    else:
        cursor = conn.execute("""
            SELECT id, tracking_code, status, created_at
            FROM shipments
            WHERE id < ?
            ORDER BY id DESC
            LIMIT ?
        """, (last_id, page_size))
    
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    next_cursor = results[-1]["id"] if results else None
    
    return results, next_cursor

This pattern is efficient because the database uses an index on the id column. It performs a single index seek and retrieves exactly the number of rows requested.

The trade-off is that you lose random access. You cannot jump directly to page 10. You must iterate sequentially through cursors. This works well for forward-only scrolling but complicates navigation.

Keyset Pagination

Keyset pagination is a variant of cursor pagination that uses specific column values rather than opaque cursors. You filter by the columns used for ordering.

def get_shipments_keyset(
    created_after: str | None,
    last_tracking_code: str | None,
    page_size: int = 20
) -> list[dict]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    query = """
        SELECT id, tracking_code, status, created_at
        FROM shipments
        WHERE 1=1
    """
    params = []
    
    if created_after:
        query += " AND created_at > ?"
        params.append(created_after)
    
    if last_tracking_code:
        query += " AND tracking_code < ?"
        params.append(last_tracking_code)
    
    query += " ORDER BY tracking_code DESC LIMIT ?"
    params.append(page_size)
    
    cursor = conn.execute(query, params)
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    return results

This approach is transparent. The client sees exactly how pagination works and can reconstruct URLs. It also works well with composite indexes when sorting by multiple columns.

Comparing the Three Approaches

| Aspect | Offset | Cursor | Keyset | |--------|--------|--------|--------| | Performance at scale | Degrades with large offsets | Consistent regardless of position | Consistent with proper indexes | | Random access | Yes (page numbers) | No (sequential only) | Limited (only on indexed columns) | | Implementation complexity | Simple | Moderate | Moderate to complex | | URL readability | Clean (/page/5) | Opaque cursor string | Transparent filter params | | Duplicate rows on inserts | Possible if no stable sort | No | No (with proper filter) |

The table shows why cursor and keyset pagination outperform offset for large datasets. Offset provides the most intuitive API for users who need to jump around, but the performance cost makes it unsuitable for deep pagination.

A Real-World Fix

Raj's team migrated from offset to cursor pagination over a weekend. The implementation took about 6 hours, including client updates. The results were immediate: average response time dropped from 1,200ms to 45ms, even for requests that previously took 8 seconds.

The key was adding an index on the created_at column and changing the client to store the last record's ID instead of calculating offsets. Their mobile app now loads shipment lists instantly, even when viewing recent records.

Sofia Park, a senior engineer on Raj's team, noted that the hardest part was explaining to product managers why they could no longer show "page 42 of 1,500" in the UI. They settled on showing "showing 800-820 of 15,432 shipments" with infinite scroll, which users adapted to quickly.

Lessons Learned

  • Offset pagination works fine for small datasets under a few thousand records where users rarely go beyond page 20
  • Always add composite indexes matching your ORDER BY and WHERE clauses for cursor and keyset pagination
  • Cursor pagination requires client-side changes — you cannot just update the backend
  • Duplicate rows can appear with offset pagination when records are inserted or deleted during pagination
  • Monitor slow queries in production; pagination performance issues often surface only at scale

    • Actionable Takeaways

  • Audit your current pagination — Check how deep users actually paginate in your analytics; if 95% stay within the first 10 pages, offset may be acceptable
  • Add composite indexes — For any paginated query with ORDER BY, create an index covering both the sort column and any filter columns
  • Implement cursor pagination — Start with primary key cursors for consistent performance; move to keyset if you need transparent, bookmarkable URLs
  • Test with realistic data — Run queries at your expected maximum dataset size to verify performance before deployment
  • Update client documentation — Make sure API consumers understand how to handle cursors; provide clear examples in your API documentation

    • The right pagination pattern depends on your dataset size, user behavior, and API design constraints. Offset works for small datasets with random access needs. Cursor and keyset pagination scale gracefully and should be your default choice for growing applications.
