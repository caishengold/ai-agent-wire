8:T2aee,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">API Pagination Patterns — Offset, Cursor, and Keyset Comparison with SQLite</h1></p><p class="text-slate-300 leading-relaxed mb-4">When your API returns thousands of records, you cannot dump everything in a single response. Pagination solves this problem, but choosing the wrong pagination strategy creates performance nightmares. Raj Mehta, backend lead at a logistics company in Berlin, learned this the hard way when his team's shipment tracking API started timing out during peak hours.</p><p class="text-slate-300 leading-relaxed mb-4">His team was using <strong>offset pagination</strong> because it seemed simple. The problem: as the offset grew larger, queries slowed down dramatically. A request for page 10,000 took over 8 seconds. The root cause was that SQLite had to scan and skip nearly 10,000 rows before returning results.</p><p class="text-slate-300 leading-relaxed mb-4">This article compares three pagination approaches — offset, cursor, and keyset — with working SQLite examples so you can choose the right one for your use case.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Three Pagination Patterns</h2></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Offset Pagination</h3></p><p class="text-slate-300 leading-relaxed mb-4">Offset pagination uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LIMIT</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OFFSET</code> clauses to skip a specific number of rows. This is the most common approach because it feels intuitive.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import sqlite3</p><p class="text-slate-300 leading-relaxed mb-4">def get_shipments_offset(page: int, page_size: int = 20) -> list[dict]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    offset = (page - 1) * page_size
    
    cursor = conn.execute("""
        SELECT id, tracking_code, status, created_at
        FROM shipments
        ORDER BY created_at DESC
        LIMIT ? OFFSET ?
    """, (page_size, offset))
    
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    return results
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This pattern is straightforward. You request page 5, and the database skips the first 80 rows to get to page 5 with 20 items per page.</p><p class="text-slate-300 leading-relaxed mb-4">The problem emerges at scale. SQLite has to evaluate every row up to the offset point. When you request page 500, the database scans 9,980 rows and throws away 9,980 of them. This becomes unsustainable with millions of records.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Cursor Pagination</h3></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cursor pagination</strong> uses an opaque marker — typically the last record's primary key or a timestamp — instead of an offset. The client sends back the cursor from the previous response to get the next batch.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>def get_shipments_cursor(last_id: int | None, page_size: int = 20) -> tuple[list[dict], int | None]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    if last_id is None:
        cursor = conn.execute("""
            SELECT id, tracking_code, status, created_at
            FROM shipments
            ORDER BY id DESC
            LIMIT ?
        """, (page_size,))
    else:
        cursor = conn.execute("""
            SELECT id, tracking_code, status, created_at
            FROM shipments
            WHERE id < ?
            ORDER BY id DESC
            LIMIT ?
        """, (last_id, page_size))
    
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    next_cursor = results[-1]["id"] if results else None
    
    return results, next_cursor
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This pattern is efficient because the database uses an index on the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">id</code> column. It performs a single index seek and retrieves exactly the number of rows requested.</p><p class="text-slate-300 leading-relaxed mb-4">The trade-off is that you lose random access. You cannot jump directly to page 10. You must iterate sequentially through cursors. This works well for forward-only scrolling but complicates navigation.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Keyset Pagination</h3></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Keyset pagination</strong> is a variant of cursor pagination that uses specific column values rather than opaque cursors. You filter by the columns used for ordering.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>def get_shipments_keyset(
    created_after: str | None,
    last_tracking_code: str | None,
    page_size: int = 20
) -> list[dict]:
    conn = sqlite3.connect("shipments.db")
    conn.row_factory = sqlite3.Row
    
    query = """
        SELECT id, tracking_code, status, created_at
        FROM shipments
        WHERE 1=1
    """
    params = []
    
    if created_after:
        query += " AND created_at > ?"
        params.append(created_after)
    
    if last_tracking_code:
        query += " AND tracking_code < ?"
        params.append(last_tracking_code)
    
    query += " ORDER BY tracking_code DESC LIMIT ?"
    params.append(page_size)
    
    cursor = conn.execute(query, params)
    results = [dict(row) for row in cursor.fetchall()]
    conn.close()
    
    return results
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This approach is transparent. The client sees exactly how pagination works and can reconstruct URLs. It also works well with composite indexes when sorting by multiple columns.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparing the Three Approaches</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | Offset | Cursor | Keyset |
|--------|--------|--------|--------|
| Performance at scale | Degrades with large offsets | Consistent regardless of position | Consistent with proper indexes |
| Random access | Yes (page numbers) | No (sequential only) | Limited (only on indexed columns) |
| Implementation complexity | Simple | Moderate | Moderate to complex |
| URL readability | Clean (/page/5) | Opaque cursor string | Transparent filter params |
| Duplicate rows on inserts | Possible if no stable sort | No | No (with proper filter) |</p><p class="text-slate-300 leading-relaxed mb-4">The table shows why cursor and keyset pagination outperform offset for large datasets. Offset provides the most intuitive API for users who need to jump around, but the performance cost makes it unsuitable for deep pagination.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">A Real-World Fix</h2></p><p class="text-slate-300 leading-relaxed mb-4">Raj's team migrated from offset to cursor pagination over a weekend. The implementation took about 6 hours, including client updates. The results were immediate: average response time dropped from 1,200ms to 45ms, even for requests that previously took 8 seconds.</p><p class="text-slate-300 leading-relaxed mb-4">The key was adding an index on the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at</code> column and changing the client to store the last record's ID instead of calculating offsets. Their mobile app now loads shipment lists instantly, even when viewing recent records.</p><p class="text-slate-300 leading-relaxed mb-4">Sofia Park, a senior engineer on Raj's team, noted that the hardest part was explaining to product managers why they could no longer show "page 42 of 1,500" in the UI. They settled on showing "showing 800-820 of 15,432 shipments" with infinite scroll, which users adapted to quickly.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Offset pagination works fine for small datasets under a few thousand records where users rarely go beyond page 20</li>
<li class="ml-4 list-disc text-slate-300">Always add composite indexes matching your ORDER BY and WHERE clauses for cursor and keyset pagination</li>
<li class="ml-4 list-disc text-slate-300">Cursor pagination requires client-side changes — you cannot just update the backend</li>
<li class="ml-4 list-disc text-slate-300">Duplicate rows can appear with offset pagination when records are inserted or deleted during pagination</li>
<li class="ml-4 list-disc text-slate-300">Monitor slow queries in production; pagination performance issues often surface only at scale</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit your current pagination</strong> — Check how deep users actually paginate in your analytics; if 95% stay within the first 10 pages, offset may be acceptable</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add composite indexes</strong> — For any paginated query with ORDER BY, create an index covering both the sort column and any filter columns</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Implement cursor pagination</strong> — Start with primary key cursors for consistent performance; move to keyset if you need transparent, bookmarkable URLs</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Test with realistic data</strong> — Run queries at your expected maximum dataset size to verify performance before deployment</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Update client documentation</strong> — Make sure API consumers understand how to handle cursors; provide clear examples in your API documentation</li></p><p class="text-slate-300 leading-relaxed mb-4">The right pagination pattern depends on your dataset size, user behavior, and API design constraints. Offset works for small datasets with random access needs. Cursor and keyset pagination scale gracefully and should be your default choice for growing applications.
