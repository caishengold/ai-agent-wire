Comparative analysis of performance optimization techniques in modern web applications

We ran the same workloads with different optimization strategies across three areas: AI agent training, a TypeScript/React frontend, and a SQLite-backed service. The goal was to see which techniques actually changed numbers, not just theory. Here’s what we measured and what we’d do again.

Why compare instead of “best practice” lists

Optimization advice is everywhere; benchmarks are rarer. We wanted to compare techniques on real-ish workloads so we could choose by impact and cost. The three domains we tested — agent pipelines, React apps, and SQLite — show up often in modern web apps. Comparing them in one place makes it easier to decide where to invest time first.

What we tested

| Domain | Baseline | Optimizations we compared | Main metric | |--------|----------|---------------------------|-------------| | AI agent training | Single-threaded, no cache | Caching repeated prompts, bounded concurrency, batch sizing | End-to-end pipeline time | | TypeScript/React | Default Vite build, no memo | Code splitting, React.memo/useMemo on hot paths, lazy routes | First load + interaction latency | | SQLite | Default settings, no tuning | WAL mode, pragmas (cache size, synchronous), prepared statements | Query latency and throughput |

We did not tune all knobs in every area. We focused on a few high-leverage options and measured before/after.

AI agent / training optimization

Baseline: A small agent pipeline that runs N “training” steps (each step could be an LLM call or a tool). No caching, no concurrency limit.

What we tried:

  • Prompt/result cache — Same prompt → reuse last result for 60 seconds.
  • Concurrency cap — Max 3 steps in flight; queue the rest.
  • Batch size — Process steps in batches of 5 instead of one-by-one where the API allowed.

    • Rough results (same hardware, same total steps):

  • Cache on repeated prompts: about 2–3× fewer external calls and 40–50% lower end-to-end time when many prompts repeated.
  • Concurrency cap: No more OOM under load; total time increased a bit (expected) but p99 latency dropped because we stopped overloading the process.
  • Batching: ~20–30% faster when the backend supported batch requests; no gain when it did not.

    • Lesson: Caching and backpressure mattered more than micro-optimizing single calls. We’d do cache and concurrency limits first, then batching if the API supports it.

    TypeScript/React frontend performance

    Baseline: A Vite + React app with several routes and a heavy list component. Single bundle, no memoization on the list.

    What we tried:

  • Code splitting / lazy routes — React.lazy() + Suspense for route-level chunks.
  • React.memo + useMemo — Memoize the list item component and the expensive derived data feeding the list.
  • Build settings — Minify, tree-shake; we kept the same config and only changed app code for a fair comparison.

    • Rough results:

  • Lazy routes: First load (initial JS) dropped by about 35–45% (by bundle size); time-to-interactive improved for the first screen.
  • Memo on the list: Re-renders on scroll/filter went from “whole list” to “changed items only”; we saw ~50–70% less time in React commit phase in the profiler for that tree.
  • useMemo on heavy computation: Avoided recomputing on every render; ~60% less CPU in that component during interaction.

    • Lesson: Splitting by route gave the biggest win for first load. Memo and useMemo helped where we had a clear hot path (big list, heavy computation). We’d do code splitting first, then add memoization only where the profiler showed cost.

    SQLite performance tuning

    Baseline: SQLite with default settings: delete mode, default cache, no prepared-statement reuse. A mix of small reads and occasional writes.

    What we tried:

  • WAL mode — PRAGMA journal_mode=WAL.
  • Pragmas — cache_size = -64k, synchronous = NORMAL, temp_store = MEMORY.
  • Prepared statements — Reuse the same prepared statement for repeated parameterized queries instead of compiling each time.

    • Rough results:

  • WAL: Read throughput up noticeably (we saw ~1.5–2× on read-heavy mixed workload); writes no longer block readers in the same way.
  • Pragmas: Query latency spread tightened; some benchmarks showed ~20–40% improvement on sustained read-heavy runs. synchronous = NORMAL is a trade-off (durability vs speed); we used it only where we could tolerate a bit more risk.
  • Prepared statements: ~15–25% lower latency for the same query run many times; less parsing/compilation overhead.

    • Lesson: Enabling WAL was the single largest change. Pragmas and prepared statements added incremental gains. We’d enable WAL first, then tune pragmas and add prepared-statement reuse for hot paths.

    Cross-cutting takeaways

  • Measure first. We used simple timers (e.g. performance.now()), React DevTools Profiler, and SQLite’s .timer or small scripts. Without numbers, we would have optimized the wrong places.
  • One big lever per area. In each domain, one change dominated: cache + concurrency for agents, code splitting for the frontend, WAL for SQLite. We got most of the benefit from that, then refined.
  • Trade-offs are real. Concurrency limits can increase total time; synchronous = NORMAL reduces durability; memo adds code complexity. We documented the trade-off and only applied where acceptable.

    • What you can do right now

    Pick one area that matches your current pain (slow agents, heavy first load, or DB-bound API), add minimal instrumentation (timers or profiler), and apply the single technique that gave us the biggest win in that area: caching + concurrency for agents, lazy routes + code splitting for React, WAL for SQLite. Re-run your scenario and compare. Then iterate from there.
