8:T2b06,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Comparative analysis of performance optimization techniques in modern web applications</h1></p><p class="text-slate-300 leading-relaxed mb-4">We ran the same workloads with different optimization strategies across three areas: AI agent training, a TypeScript/React frontend, and a SQLite-backed service. The goal was to see which techniques actually changed numbers, not just theory. Here’s what we measured and what we’d do again.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why compare instead of “best practice” lists</h2></p><p class="text-slate-300 leading-relaxed mb-4">Optimization advice is everywhere; benchmarks are rarer. We wanted to compare techniques on real-ish workloads so we could choose by impact and cost. The three domains we tested — agent pipelines, React apps, and SQLite — show up often in modern web apps. Comparing them in one place makes it easier to decide where to invest time first.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we tested</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Domain | Baseline | Optimizations we compared | Main metric |
|--------|----------|---------------------------|-------------|
| <strong>AI agent training</strong> | Single-threaded, no cache | Caching repeated prompts, bounded concurrency, batch sizing | End-to-end pipeline time |
| <strong>TypeScript/React</strong> | Default Vite build, no memo | Code splitting, React.memo/useMemo on hot paths, lazy routes | First load + interaction latency |
| <strong>SQLite</strong> | Default settings, no tuning | WAL mode, pragmas (cache size, synchronous), prepared statements | Query latency and throughput |</p><p class="text-slate-300 leading-relaxed mb-4">We did not tune all knobs in every area. We focused on a few high-leverage options and measured before/after.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">AI agent / training optimization</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Baseline:</strong> A small agent pipeline that runs N “training” steps (each step could be an LLM call or a tool). No caching, no concurrency limit.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>What we tried:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Prompt/result cache</strong> — Same prompt → reuse last result for 60 seconds.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Concurrency cap</strong> — Max 3 steps in flight; queue the rest.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Batch size</strong> — Process steps in batches of 5 instead of one-by-one where the API allowed.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Rough results (same hardware, same total steps):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Cache on repeated prompts: about <strong>2–3× fewer</strong> external calls and <strong>40–50%</strong> lower end-to-end time when many prompts repeated.</li>
<li class="ml-4 list-disc text-slate-300">Concurrency cap: <strong>No more OOM</strong> under load; total time increased a bit (expected) but p99 latency dropped because we stopped overloading the process.</li>
<li class="ml-4 list-disc text-slate-300">Batching: <strong>~20–30%</strong> faster when the backend supported batch requests; no gain when it did not.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Lesson:</strong> Caching and backpressure mattered more than micro-optimizing single calls. We’d do cache and concurrency limits first, then batching if the API supports it.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">TypeScript/React frontend performance</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Baseline:</strong> A Vite + React app with several routes and a heavy list component. Single bundle, no memoization on the list.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>What we tried:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Code splitting / lazy routes</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">React.lazy()</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Suspense</code> for route-level chunks.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>React.memo + useMemo</strong> — Memoize the list item component and the expensive derived data feeding the list.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Build settings</strong> — Minify, tree-shake; we kept the same config and only changed app code for a fair comparison.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Rough results:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Lazy routes: <strong>First load</strong> (initial JS) dropped by about <strong>35–45%</strong> (by bundle size); time-to-interactive improved for the first screen.</li>
<li class="ml-4 list-disc text-slate-300">Memo on the list: <strong>Re-renders</strong> on scroll/filter went from “whole list” to “changed items only”; we saw <strong>~50–70%</strong> less time in React commit phase in the profiler for that tree.</li>
<li class="ml-4 list-disc text-slate-300">useMemo on heavy computation: Avoided recomputing on every render; <strong>~60%</strong> less CPU in that component during interaction.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Lesson:</strong> Splitting by route gave the biggest win for first load. Memo and useMemo helped where we had a clear hot path (big list, heavy computation). We’d do code splitting first, then add memoization only where the profiler showed cost.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">SQLite performance tuning</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Baseline:</strong> SQLite with default settings: delete mode, default cache, no prepared-statement reuse. A mix of small reads and occasional writes.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>What we tried:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>WAL mode</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PRAGMA journal_mode=WAL</code>.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Pragmas</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cache_size = -64k</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">synchronous = NORMAL</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">temp_store = MEMORY</code>.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Prepared statements</strong> — Reuse the same prepared statement for repeated parameterized queries instead of compiling each time.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Rough results:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">WAL: <strong>Read throughput</strong> up noticeably (we saw ~1.5–2× on read-heavy mixed workload); writes no longer block readers in the same way.</li>
<li class="ml-4 list-disc text-slate-300">Pragmas: <strong>Query latency</strong> spread tightened; some benchmarks showed <strong>~20–40%</strong> improvement on sustained read-heavy runs. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">synchronous = NORMAL</code> is a trade-off (durability vs speed); we used it only where we could tolerate a bit more risk.</li>
<li class="ml-4 list-disc text-slate-300">Prepared statements: <strong>~15–25%</strong> lower latency for the same query run many times; less parsing/compilation overhead.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Lesson:</strong> Enabling WAL was the single largest change. Pragmas and prepared statements added incremental gains. We’d enable WAL first, then tune pragmas and add prepared-statement reuse for hot paths.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Cross-cutting takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Measure first.</strong> We used simple timers (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">performance.now()</code>), React DevTools Profiler, and SQLite’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.timer</code> or small scripts. Without numbers, we would have optimized the wrong places.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>One big lever per area.</strong> In each domain, one change dominated: cache + concurrency for agents, code splitting for the frontend, WAL for SQLite. We got most of the benefit from that, then refined.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Trade-offs are real.</strong> Concurrency limits can increase total time; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">synchronous = NORMAL</code> reduces durability; memo adds code complexity. We documented the trade-off and only applied where acceptable.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one area that matches your current pain (slow agents, heavy first load, or DB-bound API), add minimal instrumentation (timers or profiler), and apply the single technique that gave us the biggest win in that area: <strong>caching + concurrency</strong> for agents, <strong>lazy routes + code splitting</strong> for React, <strong>WAL</strong> for SQLite. Re-run your scenario and compare. Then iterate from there.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
