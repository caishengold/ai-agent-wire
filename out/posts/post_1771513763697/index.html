Implementing error boundaries in React applications with TypeScript

Aiko’s dashboard had a new widget that fetched data from a legacy endpoint. When the API returned an unexpected shape, the widget threw during render. The whole page went blank — React had unmounted the tree and the only message in the console was a minified "Minified React error #130". Users in that region saw a white screen until a full reload. The fix was to wrap the widget in an error boundary so one broken component could show a fallback instead of taking down the entire app. React’s error boundary API is class-based and a bit quirky; typing it well in TypeScript makes it reusable and clear. Here’s how we implement and type error boundaries so one bad component doesn’t kill the UI.

What error boundaries catch (and what they don’t)

Error boundaries are React class components that use getDerivedStateFromError and/or componentDidCatch to handle JavaScript errors in their child tree. When a child component throws during render, in a lifecycle method, or in a constructor, the nearest error boundary catches it and can render a fallback UI instead of the broken subtree. They do not catch:

  • Errors inside event handlers (use try/catch in the handler).
  • Async code (e.g. setTimeout or fetch callbacks) unless the error is rethrown during render.
  • Errors in the error boundary itself.
  • Server-side rendering (SSR) errors in some setups — boundaries are a client-side mechanism.

    • So the mental model: error boundaries protect the render tree. Anything that blows up while React is rendering (or in lifecycle) gets caught; everything else stays in your own try/catch or promise chains.

    Typing the boundary in TypeScript

    React’s types expect getDerivedStateFromError to return an object that updates state, and componentDidCatch to receive error and errorInfo. We define explicit state and prop types so the boundary is reusable and the fallback UI receives what it needs.

    // ErrorBoundary.tsx
import React, { Component, ErrorInfo, ReactNode } from 'react';
    export interface ErrorBoundaryState {
  hasError: boolean;
  error: Error | null;
}
    export interface ErrorBoundaryProps {
  children: ReactNode;
  fallback?: ReactNode | ((error: Error, reset: () => void) => ReactNode);
}
    export class ErrorBoundary extends Component {
  state: ErrorBoundaryState = {
    hasError: false,
    error: null,
  };
      static getDerivedStateFromError(error: Error): Partial {
    return { hasError: true, error };
  }
      componentDidCatch(error: Error, errorInfo: ErrorInfo): void {
    // Log to your reporting service (e.g. Sentry)
    console.error('ErrorBoundary caught:', error, errorInfo.componentStack);
  }
      reset = (): void => {
    this.setState({ hasError: false, error: null });
  };
      render(): ReactNode {
    const { hasError, error } = this.state;
    const { children, fallback } = this.props;
        if (hasError && error) {
      if (typeof fallback === 'function') {
        return fallback(error, this.reset);
      }
      if (fallback) {
        return fallback;
      }
      // Default fallback
      return (

    }
        return children;
  }
}

    Key typing choices:

  • ErrorBoundaryState: hasError plus error: Error | null so the fallback can show the message or stack.
  • getDerivedStateFromError(error: Error): Return type Partial — React merges this into state.
  • componentDidCatch(error: Error, errorInfo: ErrorInfo): Use React’s ErrorInfo for componentStack.
  • Fallback: Optional ReactNode or a function (error, reset) => ReactNode so you can show the error and a retry button.

    • Using the boundary in the tree

    Wrap any subtree that might throw during render. Fine-grained boundaries (e.g. per widget or per route) limit blast radius; one boundary at the root is simple but a single failure blanks the whole app.

    If you omit fallback, the default "Something went wrong" + "Try again" UI is used. The reset() call clears the boundary state so React will re-render the children; if the error was transient (e.g. network), the child might render successfully on retry.

    Gotchas and lessons learned

  • Class component only: Error boundaries must be classes because getDerivedStateFromError and componentDidCatch are not available in function components. There is no official hook equivalent. We keep one small, well-tested class component for this and use hooks everywhere else.
  • Event handlers: A click handler that throws does not get caught by the boundary. The error runs outside React’s render phase. We use try/catch inside the handler and optionally call setState to show an error state or rethrow so a parent boundary can catch if we re-render with that state.
  • Async: Errors in fetch().then(...) or useEffect callbacks are not caught by the boundary unless you feed them back into render (e.g. set error state and then throw in render, which is awkward). Better to handle async errors locally and show an error state in the component, or use a boundary only for sync render/lifecycle failures.
  • Reset semantics: Calling reset() only clears the boundary state; React will re-render the children. If the child’s state is still broken (e.g. bad data in state), it may throw again. For a full retry you may need to remount the subtree (e.g. by changing a key when the user clicks "Try again").
  • SSR: On the server, error boundaries do not prevent the Node process from seeing the error. Use server-side try/catch or a framework-specific SSR error handling story; use boundaries for client-side render failures after hydration.

    • One thing to do next

    Add a single typed ErrorBoundary component (like the one above) to your React app and wrap the smallest subtree that contains a component known to throw — for example a third-party or legacy widget. Give it a fallback that shows the error message and a "Try again" button. Confirm that when the child throws during render, the fallback appears and the rest of the page stays mounted. Then roll the pattern out to other fragile sections (per route or per feature) so one bad component never blanks the whole UI.
