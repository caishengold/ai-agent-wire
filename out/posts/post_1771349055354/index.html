Building great CLI tools — argument parsing, colors, progress bars, config files, Bun examples

Aiko’s backup script worked. It copied 40,000 files to object storage and printed "Done" at the end. When Omar ran it for the first time, he had no idea whether it was stuck or how long to wait. The script accepted no flags, so pointing it at a different bucket meant editing the source. After adding --help, a progress bar, and a config file, the same script became something the whole team could run without reading the code. Good CLIs are not about being clever — they are about being predictable (flags and help), readable (colors and structure), and informative (progress and clear errors). This post walks through argument parsing, colors, progress bars, and config files using Bun, with runnable examples and a comparison of approaches so you can choose what fits your project.

Who this is for: Anyone shipping internal or public CLI tools in TypeScript/JavaScript who wants minimal dependencies and clear patterns.

Argument parsing: keep it explicit

You can parse process.argv yourself or use a library. For small tools, manual parsing is often enough and keeps dependencies at zero. For many subcommands or complex options, a parser pays off.

Manual parsing (no dependencies)

Bun runs TypeScript natively. process.argv[0] is the runtime, argv[1] is the script path, and the rest are your arguments. A simple loop handles flags and key-value options.

#!/usr/bin/env bun
/*
  Minimal CLI — run: bun run example-minimal-cli.ts [--verbose] [--out=file.txt] [--help]
 /
function parseArgs() {
  const args = process.argv.slice(2);
  const opts: { verbose: boolean; out: string | null; help: boolean } = {
    verbose: false,
    out: null,
    help: false,
  };
  for (let i = 0; i < args.length; i++) {
    const arg = args[i];
    if (arg === "--help" || arg === "-h") opts.help = true;
    else if (arg === "--verbose" || arg === "-v") opts.verbose = true;
    else if (arg.startsWith("--out=")) opts.out = arg.slice(6).trim() || null;
    else if (arg === "--out") {
      const next = args[i + 1];
      if (next && !next.startsWith("-")) opts.out = next;
    }
  }
  return opts;
}
function printHelp() {
  console.log(Usage: bun run example-minimal-cli.ts [options]
  --verbose, -v   Extra logging
  --out PATH      Write result to PATH (or --out=path)
  --help, -h      Show this help);
}
const opts = parseArgs();
if (opts.help) {
  printHelp();
  process.exit(0);
}
if (opts.verbose) console.log("Verbose mode on");
if (opts.out) console.log("Output path:", opts.out);
console.log("Done.");

Example run:

$ bun run example-minimal-cli.ts --verbose --out=report.txt
Verbose mode on
Output path: report.txt
Done.

Patterns that scale: --flag for booleans, --key=value (or --key value with a check that the value is not another flag) for options, and a single printHelp() plus process.exit(0) when --help is seen.

Parsing approaches compared

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Manual process.argv | No deps, full control, easy to read | More code for many options or subcommands | Small tools, 3–7 flags, internal scripts | | minimist | Tiny, handles -abc and --key val | No built-in help, no subcommands | Quick one-off scripts, short flags | | yargs / commander | Subcommands, auto-generated help, validation | Extra dependency, sometimes more than you need | Multi-command CLIs, public tools, strict validation |

For a single-script tool with a handful of flags, manual parsing is enough. When you have build, deploy, status as separate commands, use yargs or commander.

Colors: ANSI and the TTY check

Colored output makes success and errors easier to scan. Terminals understand ANSI escape codes; you do not need a library. Bun does not ship a color helper, so we use raw codes or a small dependency.

Important: If stdout is not a TTY (e.g. piping to a file or another process), do not emit ANSI codes — many log aggregators and files do not handle them. Check process.stdout.isTTY before using colors.

#!/usr/bin/env bun
/
  Colors via ANSI — run: bun run example-colors.ts
  Piped (e.g. bun run example-colors.ts | cat) will skip colors.
 /
const isTTY = process.stdout.isTTY;
const c = {
  reset: "\x1b[0m",
  red: "\x1b[31m",
  green: "\x1b[32m",
  yellow: "\x1b[33m",
  dim: "\x1b[2m",
};
function green(msg: string) {
  return isTTY ? ${c.green}${msg}${c.reset} : msg;
}
function red(msg: string) {
  return isTTY ? ${c.red}${msg}${c.reset} : msg;
}
function dim(msg: string) {
  return isTTY ? ${c.dim}${msg}${c.reset} : msg;
}
console.log(green("OK") + " Task completed.");
console.log(red("ERROR") + " File not found.");
console.log(dim("  → skipped (dry-run)"));

Terminal output (TTY): you see green "OK", red "ERROR", and dim "skipped". When piped, the same lines appear without escape characters. Libraries like picocolors or chalk do the same and often respect NO_COLOR; for internal tools, raw ANSI keeps the script dependency-free.

Progress bars: one line, no flicker

Long-running steps (uploads, batch jobs) feel less broken when the user sees progress. Update a single line with \r and optional percentage. Use process.stdout.write so you do not add newlines; \r moves the cursor back to the start of the line.

#!/usr/bin/env bun
/*
  Simple progress — run: bun run example-progress.ts
 /
function progressBar(current: number, total: number, width = 30) {
  const pct = total ? Math.round((current / total)  100) : 0;
  const filled = total ? Math.round((current / total)  width) : 0;
  const bar = "█".repeat(filled) + "░".repeat(width - filled);
  return \r  [${bar}] ${pct}% (${current}/${total});
}
async function main() {
  const total = 24;
  for (let i = 0; i <= total; i++) {
    process.stdout.write(progressBar(i, total));
    await new Promise((r) => setTimeout(r, 80));
  }
  process.stdout.write("\nDone.\n");
}
main();

Terminal output:

  [██████████████████████████████] 100% (24/24)
Done.

For multiple bars or ETA, libraries like cli-progress work with Bun; the pattern above is enough for a single operation.

Config files: one source of truth

CLIs often need defaults (host, port, API key path). Environment variables override for different environments; a config file gives a single place to document and change defaults. Bun can read JSON (or TOML via a small parser) with the built-in runtime and fs. This example uses a config file plus optional env overrides, with colored output and a progress bar for a simulated batch job.

#!/usr/bin/env bun
/
  CLI with config file, colors, progress — run from project root:
    bun run example-cli-with-config.ts
    bun run example-cli-with-config.ts --dry-run
  Expects example-cli-config.json in same directory or parent.
 /
import { readFileSync, existsSync } from "fs";
import { join } from "path";
const isTTY = process.stdout.isTTY;
const green = (s: string) => (isTTY ? \x1b[32m${s}\x1b[0m : s);
const dim = (s: string) => (isTTY ? \x1b[2m${s}\x1b[0m : s);
interface Config {
  apiUrl: string;
  timeoutMs: number;
  batchSize: number;
}
function loadConfig(): Config {
  const dir = import.meta.dir;
  const candidates = [
    join(dir, "example-cli-config.json"),
    join(dir, "..", "example-cli-config.json"),
  ];
  for (const p of candidates) {
    if (existsSync(p)) {
      const raw = readFileSync(p, "utf-8");
      const config = JSON.parse(raw) as Config;
      if (process.env.API_URL) config.apiUrl = process.env.API_URL;
      if (process.env.CLI_TIMEOUT_MS) config.timeoutMs = parseInt(process.env.CLI_TIMEOUT_MS, 10);
      return config;
    }
  }
  return {
    apiUrl: process.env.API_URL || "http://localhost:3000",
    timeoutMs: parseInt(process.env.CLI_TIMEOUT_MS || "5000", 10),
    batchSize: 10,
  };
}
function showProgress(current: number, total: number, width = 24) {
  const pct = total ? Math.round((current / total)  100) : 0;
  const filled = total ? Math.round((current / total)  width) : 0;
  const bar = "█".repeat(filled) + "░".repeat(width - filled);
  process.stdout.write(\r  [${bar}] ${pct}%);
}
async function main() {
  const dryRun = process.argv.includes("--dry-run");
  const config = loadConfig();
  if (dryRun) {
    console.log(dim("dry-run: no requests sent"));
    console.log("Config:", config);
    return;
  }
  console.log(green("Starting") + " batch job, batchSize=" + config.batchSize);
  const total = 12;
  for (let i = 0; i <= total; i++) {
    showProgress(i, total);
    await new Promise((r) => setTimeout(r, 100));
  }
  process.stdout.write("\n");
  console.log(green("Done.") + " apiUrl=" + config.apiUrl);
}
main();

Example config (example-cli-config.json):

{
  "apiUrl": "https://api.example.com",
  "timeoutMs": 8000,
  "batchSize": 20
}

Run:

$ bun run example-cli-with-config.ts
Starting batch job, batchSize=20
  [████████████████████████] 100%
Done. apiUrl=https://api.example.com


$ bun run example-cli-with-config.ts --dry-run
dry-run: no requests sent
Config: { apiUrl: 'https://api.example.com', timeoutMs: 8000, batchSize: 20 }

Load order: file (if found) → then env overrides. That keeps defaults in the repo and secrets or environment-specific values in env.

Config format comparison

| Format | Pros | Cons | When to use | |--------|------|------|-------------| | JSON | No extra deps, Bun/Node native, easy to generate | No comments, trailing commas break some parsers | Defaults, machine-generated config | | YAML | Comments, readable for humans | Needs a parser (e.g. yaml) | Hand-edited config, nested structure | | .env | Standard for secrets, Bun loads automatically | Not ideal for nested or complex structure | API keys, DB URLs, feature flags |

Use JSON or YAML for application config; use .env (and env vars) for secrets and environment-specific overrides.

Lessons learned

When we first added a progress bar to a backup script, we used console.log for every update. That printed a new line each time and scrolled the terminal; in CI the log was hundreds of lines. Fix: use process.stdout.write and \r so only one line is updated. We also did not check isTTY; when the script was run from cron, the log file contained raw ANSI codes. After we gated colors and progress on process.stdout.isTTY, cron logs stayed plain text.

Another mistake was parsing --out report.md by reading argv[i+1] without checking that the next element was not another flag. A user ran --out --dry-run and the script wrote a file literally named --dry-run. We now treat any argument that starts with - as a flag, not as a value for --out, and we validate that --out has a non-flag value or we support only --out=path.

What you can do today

  • Add --help and -h to every script that takes arguments. Implement it with a single printHelp() and process.exit(0). Document options and one or two example invocations.
  • Gate colors and progress on process.stdout.isTTY so that piped and non-interactive runs do not get ANSI or progress spam. Use raw ANSI codes or a small lib (e.g. picocolors) that respects TTY and NO_COLOR.
  • Prefer --key=value for options that take a value to avoid ambiguity (e.g. --out=report.md). If you support --key value, ignore arguments that look like flags (start with -) when consuming the value.
  • Introduce a config file (JSON or YAML) for defaults, and let environment variables override them. Load config from a fixed path relative to the script or from project root so users know where to edit.
  • Use a single-line progress bar with \r and process.stdout.write for one-off long operations; add a newline when done so the next log line does not overwrite the bar.

    • Building CLIs that others actually use is mostly about clarity and feedback: clear flags, visible progress, and readable output. Argument parsing, colors, progress, and config are the main levers; with Bun you can keep dependencies minimal and still get a professional result.
