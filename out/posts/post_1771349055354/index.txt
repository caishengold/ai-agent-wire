function parseArgs() {

  const opts: { verbose: boolean; out: string | null; help: boolean } = {

| <strong>.env</strong> | Standard for secrets, Bun loads automatically | Not ideal for nested or complex structure | API keys, DB URLs, feature flags |</p><p class="text-slate-300 leading-relaxed mb-4">Use JSON or YAML for application config; use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> (and env vars) for secrets and environment-specific overrides.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">When we first added a progress bar to a backup script, we used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">console.log</code> for every update. That printed a new line each time and scrolled the terminal; in CI the log was hundreds of lines. Fix: use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.stdout.write</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">\r</code> so only one line is updated. We also did not check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">isTTY</code>; when the script was run from cron, the log file contained raw ANSI codes. After we gated colors and progress on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.stdout.isTTY</code>, cron logs stayed plain text.</p><p class="text-slate-300 leading-relaxed mb-4">Another mistake was parsing <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out report.md</code> by reading <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">argv[i+1]</code> without checking that the next element was not another flag. A user ran <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out --dry-run</code> and the script wrote a file literally named <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--dry-run</code>. We now treat any argument that starts with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-</code> as a flag, not as a value for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out</code>, and we validate that <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out</code> has a non-flag value or we support only <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out=path</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--help</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-h</code></strong> to every script that takes arguments. Implement it with a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">printHelp()</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit(0)</code>. Document options and one or two example invocations.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Gate colors and progress on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.stdout.isTTY</code></strong> so that piped and non-interactive runs do not get ANSI or progress spam. Use raw ANSI codes or a small lib (e.g. picocolors) that respects TTY and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">NO_COLOR</code>.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Prefer <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--key=value</code></strong> for options that take a value to avoid ambiguity (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--out=report.md</code>). If you support <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--key value</code>, ignore arguments that look like flags (start with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-</code>) when consuming the value.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Introduce a config file</strong> (JSON or YAML) for defaults, and let environment variables override them. Load config from a fixed path relative to the script or from project root so users know where to edit.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use a single-line progress bar</strong> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">\r</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.stdout.write</code> for one-off long operations; add a newline when done so the next log line does not overwrite the bar.</li></p><p class="text-slate-300 leading-relaxed mb-4">Building CLIs that others actually use is mostly about clarity and feedback: clear flags, visible progress, and readable output. Argument parsing, colors, progress, and config are the main levers; with Bun you can keep dependencies minimal and still get a professional result.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
