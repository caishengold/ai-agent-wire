Prompt engineering for code generation — system prompts, chain-of-thought, few-shot, temperature tuning

Raj’s team wired an LLM into their task pipeline to generate small TypeScript helpers from natural-language descriptions. The first run used a single user message: "Write a function that fetches a user by ID." Sometimes the model returned fetch-based code, sometimes axios; once it emitted Python. After a few broken runs in their scheduler, they added a system prompt to fix the runtime and style, dropped in few-shot examples of the exact pattern they wanted, and used chain-of-thought so the model reasoned about the API shape before emitting code. Consistency went up; turning temperature down removed the rest of the randomness.

This article walks through those four levers — system prompt, chain-of-thought (CoT), few-shot, and temperature — with runnable examples and what actually bit us when we pushed them too far.

Why prompt shape matters for code

Code generation is not chat. You need the model to stick to one language, follow your conventions, and not invent endpoints or libraries. A single free-form user prompt is rarely enough. The levers that help are:

  • System prompt — Sets role, constraints, and output format before any user input. Most APIs treat it as higher-priority context.
  • Chain-of-thought — Ask the model to reason first (e.g. list steps or types), then generate code. That often improves correctness.
  • Few-shot — One or more example request/response pairs in the prompt so the model mimics structure and style.
  • Temperature — Controls randomness. Low (e.g. 0.2) for deterministic code; higher for exploration or multiple variants.

    • We use an OpenAI-compatible API so you can run the examples with OpenAI, a local model, or a proxy.

    System prompt: lock role and rules

    The system prompt runs first. Put language, runtime, and "do not invent" rules there so they apply to every request.

    Example: TypeScript only, no extra dependencies, single code block.

    // prompt-system-demo.ts — system prompt for code generation
// Run: bun run prompt-system-demo.ts (set OPENAI_API_KEY)
    import OpenAI from "openai";
    const client = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
    const SYSTEM = You are a code generator. Output only valid code and brief comments.

  • Language: TypeScript only. No Python, no other runtimes.
    • 

  • Do not add endpoints, fields, or dependencies not in the user's request.
    • 

  • Output a single code block. No preamble or explanation outside the block.;
    • const resp = await client.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [
    { role: "system", content: SYSTEM },
    { role: "user", content: "Write a function that takes an array of numbers and returns the sum. Export it." },
  ],
  temperature: 0.2,
  max_tokens: 500,
});
    console.log(resp.choices[0]?.message?.content ?? "");

    Putting "TypeScript only" and "do not add endpoints" in the system prompt reduces off-spec output more reliably than repeating it in every user message.

    Chain-of-thought: reason first, then code

    Asking the model to reason before coding (e.g. list endpoints or types) often improves accuracy. Request CoT in the user prompt, then ask for the final code.

    // prompt-cot-demo.ts
const USER_COT = Given this API:

  • GET /users returns { id: number, name: string }[]
    • 

  • GET /users/:id returns { id: number, name: string }
    • First list the endpoints and response types in one short paragraph. Then write a TypeScript client with one async function per endpoint. Export the client.;
    // Same client.create() with messages: [system, { role: "user", content: USER_COT }]

    CoT doesn’t guarantee correctness, but it often reduces hallucinated endpoints because the model thinks through the spec first. Downside: longer output and more tokens. We use CoT only for larger or ambiguous specs; for a single small function we skip it.

    Few-shot: show input/output examples

    Few-shot means including example request/response pairs so the model matches format and style. Keep examples short and similar to the target task.

    const FEWSHOT = Example 1 — request: "function to double a number"
Response:
export function double(n: number): number { return n  2; }
    Example 2 — request: "function to get first element of array or null"
Response:
export function first(arr: T[]): T | null { return arr.length === 0 ? null : arr[0]; }
    Now do this — request: "function that takes a string and returns word count (words separated by spaces)"
Response:;

    Few-shot works best with one to three clear examples. Too many or too long examples eat context and can confuse the model or mix styles.

    Temperature: control randomness

    Temperature controls how random the next token is. For code you usually want low values so the same prompt gives similar output across runs.

    | Temperature | Use case | Effect | |-------------|----------|--------| | 0.0–0.2 | Production code, CI, fixed formats | Mostly deterministic. | | 0.3–0.5 | Several valid styles | Some variety, still coherent. | | 0.6–0.9 | Brainstorming, multiple variants | More creative, less repeatable. | | 1.0+ | Rare for code | High randomness; usually bad for precise output. |

    Same prompt at 0.0 vs 0.7: at 0.0 you get stable, almost identical code; at 0.7 you get different implementations (regex, Date, manual split) for the same request. For any path that needs repeatable code (scheduler, CI, docs), use 0.0–0.2.

    When to use which

    | Approach | Pros | Cons | |----------|------|------| | System prompt only | One place for rules; works with any client. | No examples; model may still drift on style. | | Chain-of-thought | Often improves correctness; model plans before coding. | Longer output, more tokens. | | Few-shot | Aligns style and structure. | Uses context; bad examples mislead. | | Low temperature (0–0.2) | Repeatable, predictable code. | Less diversity. |

    Combine them: system prompt for rules, one or two few-shot examples for format, CoT when the task is complex, and low temperature for the final call.

    What went wrong for us

    We once put five long few-shot examples (each 40+ lines) into a single prompt for a client generator. The model started mixing styles and sometimes produced invalid code. We also used temperature 0.4 "for a bit of variety." In CI, the same spec produced different code on each run, which broke diff-based reviews.

    We cut to two short examples, moved all style rules into the system prompt, and set temperature to 0.2. Generation became stable. The failure mode was too many few-shot examples and a temperature that was too high for deterministic code.

    CoT is useful but expensive. We used "list endpoints then generate" on every request; for a large spec the reasoning block was 2,000+ tokens. We switched to CoT only for specs above a certain size and kept a direct "generate" prompt for small ones. That cut cost without hurting quality on the small cases.

    What you can do next

  • Add a system prompt to your code-generation flow. Put language, "do not invent" rules, and output format there; keep the user message for the concrete task only.
  • Use one or two few-shot examples — keep each under ~15 lines. Match the kind of code you want and run the same prompt a few times to see if style stabilises.
  • Use CoT only when it helps — e.g. "first list the endpoints and types, then write the client." Skip it for trivial single-function requests.
  • Set temperature to 0.0–0.2 for repeatable code (CI, production). Reserve higher values for interactive or exploratory use.
  • Measure — log token usage and success rate (e.g. does the code compile?) before and after changing prompts or temperature.

    • If you change one thing today: add a short system prompt that fixes the language and forbids invented APIs, and set temperature to 0.2. That alone removes a lot of the randomness and off-spec code we saw in Raj’s first version.
