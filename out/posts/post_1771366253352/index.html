Implementing continuous delivery with Jenkins and Docker

Sofia’s team had been building images by hand and deploying over SSH. When a bad image reached staging, nobody could say which commit it came from. They needed a single path: commit → build → test → deploy, with every step logged and repeatable. Jenkins plus Docker is a common choice for teams that run CI/CD on-prem or want full control over the pipeline. This post walks through a minimal CD setup: a Jenkinsfile that builds and tests a Docker image, pushes it to a registry, and deploys it so you can drop the manual steps.

Why Jenkins and Docker together

Jenkins gives you pipeline-as-code (the Jenkinsfile lives in the repo), a large plugin ecosystem, and the ability to run on your own infrastructure. Docker gives you consistent build and runtime environments: the same image that passes tests in CI is the one you deploy. Together you get: build the app inside a container, run tests in that container, push the image to a registry, then have your orchestrator (Kubernetes, Swarm, or plain Docker) pull and run it. No “works on my machine”; the artifact is the image.

Pipeline stages: build, test, deploy

A minimal CD pipeline has three stages. Build: produce a Docker image from source. Test: run lint and unit (or integration) tests inside that image. Deploy: push the image to a registry and update the running service (e.g. kubectl set image or docker service update). The examples below use a Node.js app; the same pattern works for any stack you can containerize.

Jenkinsfile: build and test with Docker

Jenkins needs to run Docker (either Docker-in-Docker or the host’s Docker socket). The following Jenkinsfile assumes a Jenkins agent with Docker installed and the Docker Pipeline plugin available. It checks out code, builds an image tagged with the Git commit hash, runs tests inside the image, then pushes to a registry.

// Jenkinsfile — runs on agent with Docker installed
pipeline {
  agent any
  environment {
    REGISTRY = 'myregistry.example.com'
    IMAGE_NAME = "${REGISTRY}/myapp"
  }
  stages {
    stage('Build') {
      steps {
        script {
          docker.build("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
        }
      }
    }
    stage('Test') {
      steps {
        script {
          def img = docker.image("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
          img.inside {
            sh 'npm ci && npm test'
          }
        }
      }
    }
    stage('Push') {
      steps {
        script {
          docker.withRegistry("https://${REGISTRY}", 'registry-credentials-id') {
            def img = docker.image("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
            img.push()
            img.push('latest')
          }
        }
      }
    }
  }
}

  • Build: docker.build(...) uses the Dockerfile in the workspace and tags the image with the short commit SHA.
  • Test: img.inside { ... } runs the given shell steps inside a container from that image; here we run npm test so the tested artifact is exactly what we deploy.
  • Push: docker.withRegistry(...) uses a Jenkins credential (username/password or token) stored under the id registry-credentials-id; replace with your credential ID. Pushing the SHA tag and latest keeps deploys traceable.

    • Use the commit SHA (or a tag) in your deploy step so every release is tied to a specific build.

    Deploy stage: update the running service

    After the image is in the registry, the pipeline must update the running service. Two common cases:

    Kubernetes: use the Kubernetes CLI or the Jenkins Kubernetes plugin. From a step that has kubectl and a valid kubeconfig (e.g. from a Jenkins credential or service account):

    stage('Deploy') {
  steps {
    sh """
      kubectl set image deployment/myapp myapp=${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)} -n production
      kubectl rollout status deployment/myapp -n production --timeout=120s
    """
  }
}

    Docker Swarm: update the service to use the new image tag:

    docker service update --image myregistry.example.com/myapp: myapp_api

    Run the deploy stage only for the branch you use for releases (e.g. main or release/) by adding a when { branch 'main' } condition to the stage, or trigger the job only when that branch is pushed.

    Gotchas and lessons learned

  • Docker in Jenkins: The Jenkins agent must be able to run docker build and docker run. Either install Docker on the agent and add the Jenkins user to the docker group, or use Docker-in-Docker (DinD) with a privileged sidecar. We’ve seen pipeline failures because the agent had no Docker or the socket wasn’t available; verify with a one-line pipeline that runs docker info first.
  • Credentials: Store registry credentials in Jenkins (Credentials → Add) and reference by ID in docker.withRegistry. Never put passwords in the Jenkinsfile. For Kubernetes, use a kubeconfig file or OIDC; avoid embedding tokens in scripts.
  • Deploying on every push: Automatically deploying to production on every push to main can be noisy. Many teams run this pipeline for a staging branch and use a separate job or manual approval for production. Start with staging and fix auth and permissions before enabling prod.
  • Image tagging: Pushing only latest makes rollback ambiguous. Always push and deploy by commit SHA or semantic version so you can revert to a known good image.

    • Takeaway

    Add a single Jenkinsfile to your repo with stages: Build (Docker image), Test (run tests inside that image), Push (to your registry with a commit SHA tag), and Deploy (update Kubernetes or Swarm). Run it on a non-production branch first; ensure the Jenkins agent can run Docker and that registry and cluster credentials are stored securely in Jenkins. Once that runs end-to-end, you have a repeatable path from commit to running service without manual SSH or ad-hoc scripts.
