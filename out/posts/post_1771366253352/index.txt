8:T277c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Implementing continuous delivery with Jenkins and Docker</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team had been building images by hand and deploying over SSH. When a bad image reached staging, nobody could say which commit it came from. They needed a single path: commit → build → test → deploy, with every step logged and repeatable. Jenkins plus Docker is a common choice for teams that run CI/CD on-prem or want full control over the pipeline. This post walks through a minimal CD setup: a <strong>Jenkinsfile</strong> that builds and tests a Docker image, pushes it to a registry, and deploys it so you can drop the manual steps.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why Jenkins and Docker together</h2></p><p class="text-slate-300 leading-relaxed mb-4">Jenkins gives you pipeline-as-code (the Jenkinsfile lives in the repo), a large plugin ecosystem, and the ability to run on your own infrastructure. Docker gives you consistent build and runtime environments: the same image that passes tests in CI is the one you deploy. Together you get: build the app inside a container, run tests in that container, push the image to a registry, then have your orchestrator (Kubernetes, Swarm, or plain Docker) pull and run it. No “works on my machine”; the artifact is the image.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Pipeline stages: build, test, deploy</h2></p><p class="text-slate-300 leading-relaxed mb-4">A minimal CD pipeline has three stages. <strong>Build:</strong> produce a Docker image from source. <strong>Test:</strong> run lint and unit (or integration) tests inside that image. <strong>Deploy:</strong> push the image to a registry and update the running service (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kubectl set image</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker service update</code>). The examples below use a Node.js app; the same pattern works for any stack you can containerize.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Jenkinsfile: build and test with Docker</h2></p><p class="text-slate-300 leading-relaxed mb-4">Jenkins needs to run Docker (either Docker-in-Docker or the host’s Docker socket). The following Jenkinsfile assumes a Jenkins agent with Docker installed and the <strong>Docker Pipeline</strong> plugin available. It checks out code, builds an image tagged with the Git commit hash, runs tests inside the image, then pushes to a registry.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Jenkinsfile — runs on agent with Docker installed
pipeline {
  agent any
  environment {
    REGISTRY = 'myregistry.example.com'
    IMAGE_NAME = "${REGISTRY}/myapp"
  }
  stages {
    stage('Build') {
      steps {
        script {
          docker.build("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
        }
      }
    }
    stage('Test') {
      steps {
        script {
          def img = docker.image("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
          img.inside {
            sh 'npm ci && npm test'
          }
        }
      }
    }
    stage('Push') {
      steps {
        script {
          docker.withRegistry("https://${REGISTRY}", 'registry-credentials-id') {
            def img = docker.image("${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)}")
            img.push()
            img.push('latest')
          }
        }
      }
    }
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Build:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker.build(...)</code> uses the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Dockerfile</code> in the workspace and tags the image with the short commit SHA.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Test:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">img.inside { ... }</code> runs the given shell steps inside a container from that image; here we run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">npm test</code> so the tested artifact is exactly what we deploy.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Push:</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker.withRegistry(...)</code> uses a Jenkins credential (username/password or token) stored under the id <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">registry-credentials-id</code>; replace with your credential ID. Pushing the SHA tag and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">latest</code> keeps deploys traceable.</li></p><p class="text-slate-300 leading-relaxed mb-4">Use the commit SHA (or a tag) in your deploy step so every release is tied to a specific build.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Deploy stage: update the running service</h2></p><p class="text-slate-300 leading-relaxed mb-4">After the image is in the registry, the pipeline must update the running service. Two common cases:</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Kubernetes:</strong> use the Kubernetes CLI or the Jenkins Kubernetes plugin. From a step that has <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kubectl</code> and a valid kubeconfig (e.g. from a Jenkins credential or service account):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>stage('Deploy') {
  steps {
    sh """
      kubectl set image deployment/myapp myapp=${IMAGE_NAME}:${env.GIT_COMMIT?.take(7)} -n production
      kubectl rollout status deployment/myapp -n production --timeout=120s
    """
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Docker Swarm:</strong> update the service to use the new image tag:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>docker service update --image myregistry.example.com/myapp:<commit-sha> myapp_api
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run the deploy stage only for the branch you use for releases (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">release/<em></code>) by adding a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">when { branch 'main' }</code> condition to the stage, or trigger the job only when that branch is pushed.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Docker in Jenkins:</strong> The Jenkins agent must be able to run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker build</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker run</code>. Either install Docker on the agent and add the Jenkins user to the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker</code> group, or use Docker-in-Docker (DinD) with a privileged sidecar. We’ve seen pipeline failures because the agent had no Docker or the socket wasn’t available; verify with a one-line pipeline that runs <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker info</code> first.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Credentials:</strong> Store registry credentials in Jenkins (Credentials → Add) and reference by ID in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker.withRegistry</code>. Never put passwords in the Jenkinsfile. For Kubernetes, use a kubeconfig file or OIDC; avoid embedding tokens in scripts.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Deploying on every push:</strong> Automatically deploying to production on every push to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> can be noisy. Many teams run this pipeline for a <strong>staging</strong> branch and use a separate job or manual approval for production. Start with staging and fix auth and permissions before enabling prod.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Image tagging:</strong> Pushing only <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">latest</code> makes rollback ambiguous. Always push and deploy by commit SHA or semantic version so you can revert to a known good image.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a single <strong>Jenkinsfile</strong> to your repo with stages: Build (Docker image), Test (run tests inside that image), Push (to your registry with a commit SHA tag), and Deploy (update Kubernetes or Swarm). Run it on a non-production branch first; ensure the Jenkins agent can run Docker and that registry and cluster credentials are stored securely in Jenkins. Once that runs end-to-end, you have a repeatable path from commit to running service without manual SSH or ad-hoc scripts.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
