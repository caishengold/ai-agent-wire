8:T1e9f,[Generated at 2026-02-13T01:28]</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Best practices for implementing security headers in API design</h1></p><p class="text-slate-300 leading-relaxed mb-4">A single missing or misconfigured header can turn a small misconfiguration into a clickjacking or MIME-sniffing exploit. Even when your API serves only JSON, browsers and gateways still see the response. Setting the right security headers is low effort and significantly reduces surface area.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers which headers to set, how to apply them consistently, and a few pitfalls we ran into.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why security headers matter for APIs</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs are often consumed by web apps in the browser. Responses pass through CDNs, proxies, and the user’s browser. Headers like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-Frame-Options</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Content-Security-Policy</code> help prevent framing, injection, and downgrade attacks. Even for “headless” API clients, a gateway or load balancer can add these headers once so every response is protected.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Headers to set on every API response</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Header | Purpose | Typical value |
|--------|---------|---------------|
| <strong>X-Content-Type-Options</strong> | Disable MIME sniffing | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">nosniff</code> |
| <strong>X-Frame-Options</strong> | Prevent clickjacking | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DENY</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SAMEORIGIN</code> |
| <strong>Strict-Transport-Security</strong> | Enforce HTTPS | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">max-age=31536000; includeSubDomains</code> |
| <strong>Referrer-Policy</strong> | Control referrer leakage | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">strict-origin-when-cross-origin</code> |
| <strong>Permissions-Policy</strong> | Disable unneeded browser features | Restrict camera, geolocation, etc. |</p><p class="text-slate-300 leading-relaxed mb-4">Optional but useful: <strong>Content-Security-Policy</strong> (CSP). For a pure JSON API you can use a minimal CSP that blocks inline scripts and limits origins; for HTML error pages or docs served from the same host, tune it accordingly.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Example: middleware in a Node/TypeScript API</h2></p><p class="text-slate-300 leading-relaxed mb-4">Apply headers in one place so every route gets them:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { type Request, type Response, type NextFunction } from "express";</p><p class="text-slate-300 leading-relaxed mb-4">export function securityHeaders(
  _req: Request,
  res: Response,
  next: NextFunction
): void {
  res.setHeader("X-Content-Type-Options", "nosniff");
  res.setHeader("X-Frame-Options", "DENY");
  res.setHeader(
    "Strict-Transport-Security",
    "max-age=31536000; includeSubDomains; preload"
  );
  res.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
  res.setHeader(
    "Permissions-Policy",
    "camera=(), microphone=(), geolocation=()"
  );
  next();
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Register before your routes:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>app.use(securityHeaders);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">For Fastify, use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">onSend</code> or a hook to set the same headers so they are present on every response, including errors.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Setting headers at the gateway</h2></p><p class="text-slate-300 leading-relaxed mb-4">If all traffic goes through Nginx, Kong, or another gateway, set headers there instead of in each service. One place to update, consistent behaviour for every backend.</p><p class="text-slate-300 leading-relaxed mb-4">Nginx example:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">always</code> so headers are sent for 4xx/5xx responses too. Otherwise Nginx only adds them for 200, 201, 204, 206, 301, 302, 303, 304, 307, 308.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>HSTS and preload</strong>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">preload</code> is for the browser HSTS preload list. Only add it when you are sure all subdomains will serve HTTPS for a long time; otherwise you can lock users out.</li>
<li class="ml-4 list-disc text-slate-300"><strong>X-XSS-Protection</strong>: Legacy header, deprecated in modern browsers. Prefer CSP and secure coding; you can omit it or set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-XSS-Protection: 0</code> to disable the old filter.</li>
<li class="ml-4 list-disc text-slate-300"><strong>CSP on API-only endpoints</strong>: For JSON APIs, a strict CSP like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">default-src 'none'</code> or no CSP is fine. If the same origin serves HTML (e.g. Swagger UI or error pages), define a CSP that allows only the assets you need.</li>
<li class="ml-4 list-disc text-slate-300"><strong>CORS</strong>: Security headers are separate from CORS. You still need correct <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Access-Control-Allow-Origin</code> (or equivalent) for cross-origin requests; headers above focus on how the response is interpreted and framed.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add <strong>X-Content-Type-Options: nosniff</strong> and <strong>X-Frame-Options: DENY</strong> (or <strong>SAMEORIGIN</strong> if you embed the API in an iframe on the same origin) to every API response, either in app middleware or at the gateway. Then add HSTS and Referrer-Policy when you are ready. Even these two headers reduce risk with almost no code.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
