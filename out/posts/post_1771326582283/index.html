Best practices for implementing security headers in API design

A single missing or misconfigured header can turn a small misconfiguration into a clickjacking or MIME-sniffing exploit. Even when your API serves only JSON, browsers and gateways still see the response. Setting the right security headers is low effort and significantly reduces surface area.

This post covers which headers to set, how to apply them consistently, and a few pitfalls we ran into.

Why security headers matter for APIs

APIs are often consumed by web apps in the browser. Responses pass through CDNs, proxies, and the user’s browser. Headers like X-Frame-Options and Content-Security-Policy help prevent framing, injection, and downgrade attacks. Even for “headless” API clients, a gateway or load balancer can add these headers once so every response is protected.

Headers to set on every API response

| Header | Purpose | Typical value | |--------|---------|---------------| | X-Content-Type-Options | Disable MIME sniffing | nosniff | | X-Frame-Options | Prevent clickjacking | DENY or SAMEORIGIN | | Strict-Transport-Security | Enforce HTTPS | max-age=31536000; includeSubDomains | | Referrer-Policy | Control referrer leakage | strict-origin-when-cross-origin | | Permissions-Policy | Disable unneeded browser features | Restrict camera, geolocation, etc. |

Optional but useful: Content-Security-Policy (CSP). For a pure JSON API you can use a minimal CSP that blocks inline scripts and limits origins; for HTML error pages or docs served from the same host, tune it accordingly.

Example: middleware in a Node/TypeScript API

Apply headers in one place so every route gets them:

import { type Request, type Response, type NextFunction } from "express";
export function securityHeaders(
  _req: Request,
  res: Response,
  next: NextFunction
): void {
  res.setHeader("X-Content-Type-Options", "nosniff");
  res.setHeader("X-Frame-Options", "DENY");
  res.setHeader(
    "Strict-Transport-Security",
    "max-age=31536000; includeSubDomains; preload"
  );
  res.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
  res.setHeader(
    "Permissions-Policy",
    "camera=(), microphone=(), geolocation=()"
  );
  next();
}

Register before your routes:

app.use(securityHeaders);

For Fastify, use onSend or a hook to set the same headers so they are present on every response, including errors.

Setting headers at the gateway

If all traffic goes through Nginx, Kong, or another gateway, set headers there instead of in each service. One place to update, consistent behaviour for every backend.

Nginx example:

add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

Use always so headers are sent for 4xx/5xx responses too. Otherwise Nginx only adds them for 200, 201, 204, 206, 301, 302, 303, 304, 307, 308.

Gotchas and lessons learned

  • HSTS and preload: preload is for the browser HSTS preload list. Only add it when you are sure all subdomains will serve HTTPS for a long time; otherwise you can lock users out.
  • X-XSS-Protection: Legacy header, deprecated in modern browsers. Prefer CSP and secure coding; you can omit it or set X-XSS-Protection: 0 to disable the old filter.
  • CSP on API-only endpoints: For JSON APIs, a strict CSP like default-src 'none' or no CSP is fine. If the same origin serves HTML (e.g. Swagger UI or error pages), define a CSP that allows only the assets you need.
  • CORS: Security headers are separate from CORS. You still need correct Access-Control-Allow-Origin (or equivalent) for cross-origin requests; headers above focus on how the response is interpreted and framed.

    • One thing to do right now

    Add X-Content-Type-Options: nosniff and X-Frame-Options: DENY (or SAMEORIGIN if you embed the API in an iframe on the same origin) to every API response, either in app middleware or at the gateway. Then add HSTS and Referrer-Policy when you are ready. Even these two headers reduce risk with almost no code.
