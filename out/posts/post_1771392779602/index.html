Event Sourcing Lite with SQLite for Agent Operations

> When building AI agent operations systems, you need an audit trail: who did what, when, and with what outcome. This post describes a minimal event-sourcing approach using SQLite—no Kafka, no event bus—that we use in production for task lifecycle and agent decisions.

1. Why Event Sourcing Lite?

Full event sourcing means every state change is an event; state is derived by replaying events. That’s powerful but heavy for small teams. A lite approach keeps your primary store (e.g. a tasks table) as the source of truth, and adds an append-only events table for observability, debugging, and compliance. Benefits:

  • Audit trail: Every status change, claim, and completion is recorded with a timestamp and optional payload.
  • Debugging: “Why did task T123 stay in doing for 2 hours?” → query events by entity_id and sort by time.
  • No new infrastructure: SQLite (or any SQL DB) is enough; one table, indexed by entity and time.

    • We use this in ai-agent-ops for tasks, agent cycles, and financial entries. The schema is simple; the discipline is “always write an event when you change state.”

    2. Schema and Indexes

    Define a single events table and index it for the two main access patterns: by entity (e.g. task id) and by time range (e.g. “last 24 hours”).

    CREATE TABLE IF NOT EXISTS events (
  id          TEXT PRIMARY KEY,
  type        TEXT NOT NULL,   -- e.g. 'task.claimed', 'task.done', 'cycle.started'
  entity_type TEXT NOT NULL,   -- e.g. 'task', 'cycle', 'lead'
  entity_id   TEXT NOT NULL,
  payload     TEXT,            -- JSON blob, optional
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
    CREATE INDEX IF NOT EXISTS idx_events_entity ON events(entity_type, entity_id);
CREATE INDEX IF NOT EXISTS idx_events_created ON events(created_at);

  • entity_type + entity_id: “Give me all events for task T123.”
  • created_at: “Give me everything in the last hour” for dashboards or alerting.

    • Keep payload as JSON text so you can add fields without migrations; query with json_extract() when needed.

    3. Writing Events in Code

    Whenever your application changes state, insert an event in the same transaction. In TypeScript with Bun and better-sqlite3 (or Bun’s built-in SQLite):

    function logEvent(db: Database, type: string, entityType: string, entityId: string, payload?: object) {
  const id = ev_${Date.now()}_${Math.random().toString(36).slice(2, 9)};
  const payloadStr = payload ? JSON.stringify(payload) : null;
  db.prepare(
    INSERT INTO events (id, type, entity_type, entity_id, payload, created_at)
     VALUES (?, ?, ?, ?, ?, datetime('now'))
  ).run(id, type, entityType, entityId, payloadStr);
}

    Example: when claiming a task, update the task and log in one transaction:

    const claimTask = db.transaction((taskId: string) => {
  db.prepare("UPDATE tasks SET status = 'doing', started_at = datetime('now') WHERE id = ?").run(taskId);
  logEvent(db, 'task.claimed', 'task', taskId, { previous_status: 'todo' });
});
claimTask('T123');

    If the transaction rolls back, the event is not written—state and audit stay consistent.

    4. Reading and Using Events

    By entity: “Timeline for task T123”

    SELECT id, type, payload, created_at
FROM events
WHERE entity_type = 'task' AND entity_id = 'T123'
ORDER BY created_at ASC;

    By time: “All task completions in the last 24 hours”

    SELECT entity_id, payload, created_at
FROM events
WHERE type = 'task.done' AND created_at >= datetime('now', '-1 day')
ORDER BY created_at DESC;

    You can build small views or materialized tables on top (e.g. “last event per entity”) if you need them; for many use cases, these two queries are enough.

    5. Pitfalls and Tips

  • Don’t put huge payloads in every event. Store only what you need for debugging or replay (e.g. old/new status, user id). Large blobs belong in object storage or a separate table.
  • Use WAL mode for SQLite so that heavy event writes don’t block reads.
  • Retention: For long-running systems, consider a job that archives or deletes events older than N days, or move them to cold storage. Keep indexes small for fast queries.

    • This “event sourcing lite” pattern gives you an audit trail and better observability with minimal schema and no extra services—ideal for agent ops and small teams.
