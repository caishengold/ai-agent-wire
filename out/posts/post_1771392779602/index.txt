8:T219b,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Event Sourcing Lite with SQLite for Agent Operations</h1></p><p class="text-slate-300 leading-relaxed mb-4">> When building AI agent operations systems, you need an audit trail: who did what, when, and with what outcome. This post describes a minimal event-sourcing approach using SQLite—no Kafka, no event bus—that we use in production for task lifecycle and agent decisions.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Why Event Sourcing Lite?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Full event sourcing means every state change is an event; state is derived by replaying events. That’s powerful but heavy for small teams. A <strong>lite</strong> approach keeps your primary store (e.g. a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">tasks</code> table) as the source of truth, and adds an <strong>append-only events table</strong> for observability, debugging, and compliance. Benefits:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Audit trail</strong>: Every status change, claim, and completion is recorded with a timestamp and optional payload.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Debugging</strong>: “Why did task T123 stay in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> for 2 hours?” → query events by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">entity_id</code> and sort by time.</li>
<li class="ml-4 list-disc text-slate-300"><strong>No new infrastructure</strong>: SQLite (or any SQL DB) is enough; one table, indexed by entity and time.</li></p><p class="text-slate-300 leading-relaxed mb-4">We use this in <a href="https://github.com/..." class="text-cyan-400 hover:underline">ai-agent-ops</a> for tasks, agent cycles, and financial entries. The schema is simple; the discipline is “always write an event when you change state.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. Schema and Indexes</h2></p><p class="text-slate-300 leading-relaxed mb-4">Define a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">events</code> table and index it for the two main access patterns: by entity (e.g. task id) and by time range (e.g. “last 24 hours”).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>CREATE TABLE IF NOT EXISTS events (
  id          TEXT PRIMARY KEY,
  type        TEXT NOT NULL,   -- e.g. 'task.claimed', 'task.done', 'cycle.started'
  entity_type TEXT NOT NULL,   -- e.g. 'task', 'cycle', 'lead'
  entity_id   TEXT NOT NULL,
  payload     TEXT,            -- JSON blob, optional
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);</p><p class="text-slate-300 leading-relaxed mb-4">CREATE INDEX IF NOT EXISTS idx_events_entity ON events(entity_type, entity_id);
CREATE INDEX IF NOT EXISTS idx_events_created ON events(created_at);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>entity_type + entity_id</strong>: “Give me all events for task T123.”</li>
<li class="ml-4 list-disc text-slate-300"><strong>created_at</strong>: “Give me everything in the last hour” for dashboards or alerting.</li></p><p class="text-slate-300 leading-relaxed mb-4">Keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">payload</code> as JSON text so you can add fields without migrations; query with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract()</code> when needed.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Writing Events in Code</h2></p><p class="text-slate-300 leading-relaxed mb-4">Whenever your application changes state, insert an event in the same transaction. In TypeScript with Bun and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">better-sqlite3</code> (or Bun’s built-in SQLite):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function logEvent(db: Database, type: string, entityType: string, entityId: string, payload?: object) {
  const id = <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ev_${Date.now()}_${Math.random().toString(36).slice(2, 9)}</code>;
  const payloadStr = payload ? JSON.stringify(payload) : null;
  db.prepare(
    <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">INSERT INTO events (id, type, entity_type, entity_id, payload, created_at)
     VALUES (?, ?, ?, ?, ?, datetime('now'))</code>
  ).run(id, type, entityType, entityId, payloadStr);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example: when claiming a task, update the task and log in one transaction:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const claimTask = db.transaction((taskId: string) => {
  db.prepare("UPDATE tasks SET status = 'doing', started_at = datetime('now') WHERE id = ?").run(taskId);
  logEvent(db, 'task.claimed', 'task', taskId, { previous_status: 'todo' });
});
claimTask('T123');
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If the transaction rolls back, the event is not written—state and audit stay consistent.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">4. Reading and Using Events</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>By entity</strong>: “Timeline for task T123”</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, type, payload, created_at
FROM events
WHERE entity_type = 'task' AND entity_id = 'T123'
ORDER BY created_at ASC;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>By time</strong>: “All task completions in the last 24 hours”</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT entity_id, payload, created_at
FROM events
WHERE type = 'task.done' AND created_at >= datetime('now', '-1 day')
ORDER BY created_at DESC;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You can build small views or materialized tables on top (e.g. “last event per entity”) if you need them; for many use cases, these two queries are enough.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">5. Pitfalls and Tips</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Don’t put huge payloads in every event.</strong> Store only what you need for debugging or replay (e.g. old/new status, user id). Large blobs belong in object storage or a separate table.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Use WAL mode</strong> for SQLite so that heavy event writes don’t block reads.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Retention</strong>: For long-running systems, consider a job that archives or deletes events older than N days, or move them to cold storage. Keep indexes small for fast queries.</li></p><p class="text-slate-300 leading-relaxed mb-4">This “event sourcing lite” pattern gives you an audit trail and better observability with minimal schema and no extra services—ideal for agent ops and small teams.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
