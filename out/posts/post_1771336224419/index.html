API Versioning: URL, Header, or Query Parameter?

Raj Patel had a problem. As the lead backend engineer at a logistics company in Singapore, he oversaw an API that tracked shipments for over 200 corporate clients. The API had been running successfully for three years when his product team announced they needed to restructure the entire data model. New fields for customs documentation, multi-stop routing, and temperature-sensitive cargo tracking were coming in version 2.0.

The catch? About 40% of his clients were still on the original version, and several had contracts guaranteeing uptime through the end of the year. He couldn't simply replace v1 with v2 — that would break production systems for half his customers. But maintaining parallel codebases indefinitely wasn't sustainable either.

Raj needed a versioning strategy that would let old clients continue working while new clients accessed enhanced features. He also needed something simple enough that the junior developers on his team could implement without introducing bugs.

This is the exact challenge every API maintainer faces. Whether you're building a public API for external developers or an internal service for other teams, at some point your API will change in ways that break existing consumers. The question isn't whether to version — it's how to version.

Key Concepts

There are three primary approaches to API versioning, each with distinct trade-offs that affect client developers, infrastructure, and long-term maintenance.

URL Versioning

URL versioning places the version identifier directly in the path of your endpoint. This is the most visible approach and the one most developers default to because it requires no special client configuration.

The method works well when you want absolute clarity about which version is being called. Every request explicitly states the version in the URL, making it impossible to accidentally use the wrong one. This visibility also helps during debugging — logs clearly show which version handled each request.

However, URL versioning creates permanent URL pollution. As you support more versions, your API documentation becomes cluttered, and clients must explicitly update their endpoint URLs to receive new features. There's also the philosophical argument that the URL should identify a resource, not a version — the same data shouldn't live at two different addresses.

#### Example: URL Versioning with FastAPI

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
app = FastAPI()
class WeatherResponseV1(BaseModel):
    temperature: str
    description: str
class WeatherResponseV2(BaseModel):
    temperature: str
    description: str
    forecast: str
    humidity: int
@app.get("/api/v1/weather", response_model=WeatherResponseV1)
async def weather_v1():
    return WeatherResponseV1(
        temperature="20°C",
        description="Sunny"
    )
@app.get("/api/v2/weather", response_model=WeatherResponseV2)
async def weather_v2():
    return WeatherResponseV2(
        temperature="20°C",
        description="Sunny",
        forecast="Partly cloudy tomorrow",
        humidity=65
    )
if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)

This example uses FastAPI's type validation to ensure each version returns properly structured data. Running this server and calling curl http://localhost:8000/api/v1/weather returns the v1 response, while curl http://localhost:8000/api/v2/weather returns the enhanced v2 response with forecast and humidity data.

Header Versioning

Header versioning keeps your URLs clean by passing the version information in an HTTP header. The resource URL stays constant — /api/weather works for all versions — while clients specify which version they expect in the request headers.

This approach aligns better with REST principles, where the URL identifies a resource rather than a version. It also makes it easier to implement version detection as middleware, keeping your route handlers clean.

The downside is discoverability. Unlike URL versioning, clients can't simply visit the endpoint to see what version they're using. Documentation becomes more critical, and some HTTP clients make header manipulation less intuitive than query parameters.

#### Example: Header Versioning with Express

const express = require('express');
const app = express();
const weatherV1 = {
    temperature: '20°C',
    description: 'Sunny'
};
const weatherV2 = {
    temperature: '20°C',
    description: 'Sunny',
    forecast: 'Partly cloudy tomorrow',
    humidity: 65
};
app.get('/api/weather', (req, res) => {
    const version = req.headers['api-version'];
    
    if (version === '2') {
        return res.json(weatherV2);
    }
    
    return res.json(weatherV1);
});
app.listen(3000, () => {
    console.log('Server running on port 3000');
});

Testing this requires passing the header: curl -H "API-Version: 2" http://localhost:3000/api/weather returns the v2 response. Without the header, the server defaults to v1, maintaining backward compatibility for existing clients.

Query Parameter Versioning

Query parameter versioning adds the version to the URL as a parameter, like /api/weather?version=2. This gives you flexibility to mix versions without changing the URL structure, and it's easy to test — you can simply type different versions in a browser.

The approach works well for APIs that need gradual rollout, where you might want to let clients opt into newer versions incrementally. It's also the most forgiving approach for clients, since they can append the parameter without changing their core integration.

The main risk is that clients might forget to include the parameter, accidentally receiving the wrong version. Some teams use query parameters for temporary testing while using headers or URLs for production versions.

#### Example: Query Parameter Versioning with Flask

from flask import Flask, request, jsonify
from functools import wraps
app = Flask(__name__)
def require_version(required_version):
    def decorator(f):
        @wraps(f)
        def decorated_function(args, kwargs):
            requested = request.args.get('version', '1')
            if requested != required_version:
                return jsonify({
                    "error": f"Version {required_version} required",
                    "available_versions": ["1", "2"]
                }), 400
            return f(args, kwargs)
        return decorated_function
    return decorator
@app.route('/api/weather')
def weather():
    version = request.args.get('version', '1')
    
    if version == '2':
        return jsonify({
            "temperature": "20°C",
            "description": "Sunny",
            "forecast": "Partly cloudy tomorrow",
            "humidity": 65
        })
    
    return jsonify({
        "temperature": "20°C",
        "description": "Sunny"
    })
if __name__ == '__main__':
    app.run(debug=True, port=5000)

Run this with python app.py and test with curl "http://localhost:5000/api/weather?version=2" for v2 or curl "http://localhost:5000/api/weather" for the default v1 response.

Decision Matrix

The right choice depends on your specific constraints. Here's how the three approaches compare across the factors that matter most for API maintainers.

| Factor | URL Versioning | Header Versioning | Query Parameter | |--------|---------------|-------------------|-----------------| | Client simplicity | High — version visible in URL | Medium — requires header setup | High — just add parameter | | REST purity | Low — URL identifies version | High — URL identifies resource | Medium — resource varies by param | | Debugging ease | Very high — logs show version | Medium — need to check headers | High — visible in URL | | Version deprecation | Difficult — new URLs needed | Easy — stop returning header | Easy — stop accepting param | | Caching compatibility | Excellent — each URL is distinct | Good — use Vary header | Medium — caching varies | | Documentation burden | Higher — multiple endpoints | Lower — single endpoint | Medium — param documentation |

For public APIs where external developers integrate independently, URL versioning often wins because it reduces confusion. For internal services with sophisticated clients, header versioning keeps your API surface cleaner.

Common Pitfalls

Default Version Mismatch

One of the most common mistakes is not explicitly handling what happens when clients don't specify a version. In the query parameter example above, I defaulted to version 1, which maintains backward compatibility. However, some teams default to the latest version, which breaks existing clients when they deploy new versions.

Always default to the oldest supported version, or require explicit version specification. Let clients opt into changes rather than forcing them.

Ignoring Deprecation Timelines

When you deprecate a version, give clients ample notice. I recommend at least six months for major version deprecations and three months for minor changes. Include deprecation headers in responses so clients can track when they're using a version that will soon be removed.

Mixing Versioning Strategies

Some teams start with query parameters for testing, then switch to headers for production, then add URL versioning for new endpoints. This inconsistency creates maintenance nightmares. Pick one strategy and apply it consistently across your entire API.

Insufficient Testing

Version-related bugs often appear only when multiple client versions interact with your system. Test each supported version combination, and run integration tests that verify clients on different versions can coexist without interference.

Lessons Learned

  • URL versioning provides the best visibility and debugging experience, but creates permanent endpoint sprawl that becomes harder to maintain over time
  • Header versioning keeps URLs clean and follows REST principles more closely, but requires more sophisticated client implementations and clearer documentation
  • Query parameter versioning offers flexibility for gradual rollouts, but risks accidental version mismatches when clients omit the parameter
  • Default to the oldest supported version rather than the newest — this prevents breaking changes from appearing silently in production
  • Document your versioning strategy explicitly and include it in your API specification, whether you use OpenAPI, Swagger, or another format

    • Actionable Takeaways

  • Audit your current API endpoints — Identify which ones need versioning support by checking which ones have changed in the past 12 months and which clients depend on the current response structure

  • Choose one strategy and document it — If you're starting fresh, header versioning offers the best long-term maintainability; if you have existing clients, URL versioning reduces migration friction

  • Set deprecation schedules — Define timeline standards for how long each version receives support, and build deprecation warnings into your API responses six months before cutting off any version

  • Test version coexistence — Run integration tests that simulate multiple client versions hitting your API simultaneously to catch race conditions and response conflicts before production

  • Monitor version distribution** — Track which versions your clients actually use; if less than 5% are on an old version, you can confidently deprecate it and reduce maintenance burden
