Circuit Breaker for Agent API Calls

> When an agent or task runner depends on external APIs (LLMs, third-party services, or your own backends), a failing or slow service can cause every request to hang or retry until timeouts. A circuit breaker stops calling the service after repeated failures and fails fast until the service is given a chance to recover.

1. Why Use a Circuit Breaker?

  • Fail fast: If the provider is down or severely degraded, retrying every task wastes time and resources. Failing quickly lets the scheduler move on or report clearly.
  • Give the service time to recover: After opening the circuit, you stop sending traffic for a period. That reduces load on the struggling service and allows it to stabilize.
  • Avoid cascading failures: One bad dependency can tie up all your workers. A circuit breaker isolates the failure so the rest of the system can keep working (e.g. skip that provider or use a fallback).

    • Use a circuit breaker in addition to retries and backoff: retries handle transient blips; the circuit breaker handles sustained outages.

    2. Three States

    A typical implementation has three states:

  • Closed: Requests go through. Failures are counted. If the failure count (or rate) exceeds a threshold within a time window, the circuit opens.
  • Open: Requests do not call the service; they fail immediately (or return a cached/fallback result). After a reset timeout (e.g. 30–60 seconds), the circuit moves to half-open.
  • Half-open: A limited number of requests (e.g. one or a few) are allowed through. If they succeed, the circuit closes; if they fail, the circuit opens again.

    • Thresholds (e.g. 5 failures in 10 seconds) and the reset timeout are configurable.

    3. Example in TypeScript

    type State = 'closed' | 'open' | 'half-open';
    class CircuitBreaker {
  private state: State = 'closed';
  private failures = 0;
  private lastFailureAt = 0;
  private nextAttemptAt = 0;
      constructor(
    private readonly threshold: number,
    private readonly windowMs: number,
    private readonly resetMs: number
  ) {}
      async call(fn: () => Promise): Promise {
    const now = Date.now();
        if (this.state === 'open') {
      if (now < this.nextAttemptAt) throw new Error('Circuit open');
      this.state = 'half-open';
    }
        if (this.state === 'closed' && this.lastFailureAt > 0 && now - this.lastFailureAt > this.windowMs) {
      this.failures = 0;
    }
        try {
      const result = await fn();
      if (this.state === 'half-open') {
        this.state = 'closed';
        this.failures = 0;
      }
      return result;
    } catch (e) {
      this.failures++;
      this.lastFailureAt = now;
      if (this.state === 'half-open' || this.failures >= this.threshold) {
        this.state = 'open';
        this.nextAttemptAt = now + this.resetMs;
      }
      throw e;
    }
  }
}
    // Usage: wrap your API call
const breaker = new CircuitBreaker(5, 10_000, 30_000);
const response = await breaker.call(() => fetch('https://api.example.com/chat', { ... }));

    4. Tuning and Integration

  • Threshold and window: Lower threshold (e.g. 3) opens the circuit sooner; larger window (e.g. 60s) avoids reopening on short spikes. Choose based on how critical the dependency is and how noisy failures are.
  • Reset timeout: Too short and you keep hitting a service that is still recovering; too long and you delay recovery. Start with 30–60 seconds and adjust.
  • Half-open: Allowing a single request in half-open is common. If you have high concurrency, you might allow a small batch and close only if a majority succeed.
  • Observability: Log state transitions (closed → open, open → half-open, half-open → closed) and optionally expose them in metrics or health checks so you can see when and why the circuit opened.

    • Combined with backoff and jitter on retries, a circuit breaker keeps agent API calls resilient without overloading failing services or blocking the rest of your pipeline.
