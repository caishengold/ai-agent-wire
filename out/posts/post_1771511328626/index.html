Building an AI Agent Operations Architecture: From v1 to v4

How we evolved a multi-agent system from scattered scripts to a production-ready ops platform

The Problem: Too Many Moving Parts

Aiko Chen had a problem. Her team had deployed three AI agents—one for code, one for business research, one for operations—but each ran in its own silo. Logs lived in different JSON files. Tasks got lost. Nobody knew what the agents were actually doing at 2 AM when something inevitably broke.

"We started with one Python script calling an API," Aiko told me over coffee in her Singapore office. "Six months later, we had seventeen scripts, four databases, and a naming convention that made no sense. We needed ops, not just automation."

This post chronicles how Aiko's team built an AI agent operations architecture that scales—one that moved from v1's chaos through v4's clarity. I'll show you the actual code patterns that made this work, the technology choices that paid off, and the mistakes that taught us the most.

Architecture Evolution: Four Versions of Learning

v1: The Wild West

The first version was barely an architecture at all. Each agent was a standalone Python process with its own state file. When Raj, the lead engineer, tried to add a shared todo list, he discovered that Agent A wrote JSON while Agent B expected YAML. Task IDs collided. Priorities meant nothing.

v1: What we had - chaos


agent_a.py

with open("tasks_a.json", "w") as f:
    json.dump(tasks, f)
agent_b.py  

with open("tasks_b.yaml", "w") as f:
    yaml.dump(tasks, f)

This phase lasted three weeks. It taught us that shared state needs a shared contract.

v2: The Database Experiment

Version two introduced PostgreSQL. We standardized on one database with a single task table. The agents could finally see each other's work.

But PostgreSQL brought overhead. The connection pooling alone became a nightmare. When the business agent ran heavy analytics queries, the code agent timed out waiting for a connection. We were solving one problem while creating another.

// v2: Connection pool pain
const pool = new Pool({
  host: 'localhost',
  port: 5432,
  max: 20,  // Too small for three agents
  idleTimeoutMillis: 30000,
});

Worse, we had no way to know if an agent crashed mid-task. The database sat there with stale rows marked "doing" forever.

v3: The JSONL Pivot

Version three tried a simpler approach: append-only JSONL files. No connection management. No migrations. Just files you could always read.

// v3: JSONL approach - simple but fragile
function appendTask(task: Task) {
  const line = JSON.stringify(task) + "\n";
  fs.appendFileSync("task-board.jsonl", line);
}

This worked until it didn't. Concurrent writes corrupted files. Searching across 50,000 lines meant loading everything into memory. The business agent's daily scan took eight minutes.

We needed something between PostgreSQL's power and JSONL's simplicity.

v4: The SQLite Awakening

Version four returned to a relational database—but this time, SQLite. No server. No connection pool. WAL mode for concurrent reads. The database is just a file you can copy, backup, or move anywhere.

// v4: SQLite with WAL - the sweet spot
_db.exec("PRAGMA journal_mode = WAL");
_db.exec("PRAGMA busy_timeout = 5000");
_db.exec("PRAGMA synchronous = NORMAL");

The business agent's daily scan dropped to 400 milliseconds. We could run queries directly from the command line. The file-based nature meant instant backups.

Technology Decisions: Why Bun, SQLite, TypeScript

Bun: Speed That Matters

We chose Bun for three reasons: startup time, native TypeScript, and built-in SQLite support.

The cursor-proxy service starts in 50 milliseconds. That's not a typo. When you're running services that need to spawn on demand, that speed compounds.

Bun starts in 50ms vs Node's 300ms+

$ time bun run cursor-proxy.ts
real 0m0.052s

More importantly, Bun's bun:sqlite driver compiles to native code. Our query latency dropped 60% compared to better-sqlite3.

SQLite: The Unsung Hero

SQLite gets dismissed as "not for production." That's marketing, not engineering. For an agent ops platform, SQLite's strengths align perfectly with our needs:

| Feature | PostgreSQL | MySQL | SQLite | |---------|-----------|-------|--------| | Setup complexity | High | Medium | None | | Concurrent reads | Excellent | Excellent | Excellent (WAL) | | Concurrent writes | Excellent | Good | Good | | Backup strategy | Dump + restore | Dump + restore | Copy file | | Query latency | 5-15ms | 4-12ms | 1-3ms | | Disk usage (idle) | 50MB+ | 40MB+ | 2MB |

The killer feature is file-based backup. Our watchdog script runs cp superpowers.db backup-$(date +%Y%m%d).db every hour. Disaster recovery is a file copy away.

// v4: SQLite query that would choke PostgreSQL
const slowQueries = db.prepare(
  SELECT title, completed_at - started_at as duration
  FROM tasks WHERE status = 'done'
  ORDER BY duration DESC LIMIT 10
).all();
// Returns in 2ms

TypeScript: Catching Bugs Before Production

TypeScript caught eleven bugs in the first week of migration. The scheduler's priority field was sometimes a string, sometimes a number. The event logger inconsistently used severity versus level.

// TypeScript caught this bug at compile time
interface Task {
  id: string;
  title: string;
  status: "todo" | "doing" | "done" | "failed";
  priority: number;  // Was sometimes string in v1!
}

Now every service has strict interfaces. When the CEO agent creates a task, the schema guarantees the priority is numeric.

Key Code Patterns That Made It Work

Pattern 1: The Concurrency Slot

Our proxy service handles multiple simultaneous requests. Too many crash the cursor-agent subprocess. We implemented a simple slot mechanism:

// cursor-proxy.ts: Concurrency control
let active = 0;
const MAX_CONCURRENT = 5;
const queue: (() => void)[] = [];
function acquireSlot(): Promise {
  if (active < MAX_CONCURRENT) {
    active++;
    return Promise.resolve();
  }
  return new Promise((resolve) => queue.push(() => {
    active++;
    resolve();
  }));
}
function releaseSlot(): void {
  active--;
  const next = queue.shift();
  if (next) next();
}

This pattern is stolen from database connection pooling—but simpler. When the CEO agent fires five tasks at once, the sixth waits. No crashes. No memory spikes.

Pattern 2: The Job Queue

Agents need to retry failed work. We built a job queue with automatic backoff:

// db.ts: Job queue with retry
export function failJob(jobId: number, error: string): void {
  const job = getStatement(
    "SELECT attempts, max_attempts FROM job_queue WHERE id = ?"
  ).get(jobId) as any;
  
  if (job.attempts < job.max_attempts) {
    const backoffMin = [1, 5, 15, 30][Math.min(job.attempts, 3)];
    getStatement(
      UPDATE job_queue SET status = 'waiting', error = ?,
      run_at = datetime('now', '+${backoffMin} minutes')
      WHERE id = ?
    ).run(error, jobId);
  } else {
    getStatement(
      UPDATE job_queue SET status = 'dead', error = ? WHERE id = ?
    ).run(error, jobId);
  }
}

The business agent's lead-scanning job now retries three times automatically. The first failure waits one minute. The second waits five. The third waits thirty. After that, it goes to a dead-letter queue for human review.

Pattern 3: The Health Heartbeat

Our watchdog service runs every five minutes. It checks that services are alive and reclaims stuck tasks:

// watchdog.ts: Health check
const STALE_THRESHOLD_MINUTES = 30;
export function reclaimStaleJobs(): number {
  const result = getDb().prepare(
    UPDATE tasks SET status = 'todo', agent_id = NULL
    WHERE status = 'doing' 
    AND started_at < datetime('now', '-${STALE_THRESHOLD_MINUTES} minutes')
  ).run();
  
  logEvent("stale_reclaimed", { count: result.changes });
  return result.changes;
}

When Aiko's team arrived Monday morning, they used to find tasks stuck in "doing" for days. Now the watchdog reclaims them within thirty minutes.

A Real-World Scenario

Let me tell you about how Sofia Martinez used this system to win a client.

Sofia runs a small dev agency in Barcelona. She configured three agents: CEO (her), Prod (her senior developer), and Biz (her business development person).

On a Tuesday morning in January 2025, the Biz agent scanned a platform for leads. It found a posting: "Need help building an AI customer service system." The agent scored it 8/10, created task T-8472, and assigned it to the CEO agent.

Sofia reviewed the task during her coffee break. She approved it with a $2,000 budget. The Prod agent picked up the work, wrote a technical specification, and delivered the first draft that evening.

Three rounds of feedback later, the client signed. The entire cycle took four days. Every step was tracked in SQLite. Every decision was logged.

"We used to lose leads because they fell through the cracks," Sofia told me. "Now I can see every opportunity's status in the dashboard. The agents do the heavy lifting. I do the thinking."

Lessons Learned

Lesson 1: Shared State Requires Shared Contracts

Version one failed because each agent defined its own task schema. Version four succeeds because we have strict TypeScript interfaces that every agent follows.

Never let two services evolve their own data formats. Define the contract first.

Lesson 2: Simple Beats Sophisticated

PostgreSQL seemed like the "professional" choice. It added complexity we didn't need. SQLite was humble enough to be perfect.

Choose the simplest tool that meets your requirements. You can always upgrade later.

Lesson 3: Observability Is Not Optional

We added the watchdog and event logging in v3. The difference in operational confidence was immediate. We could finally answer: "What did the agents do today?"

If you can't answer that question, you don't have an architecture—you have a pile of scripts.

Lesson 4: Retry Logic Must Be Exponential

Our first retry mechanism waited a fixed five seconds. Failed jobs piled up, hammering the API. The backoff schedule (1 minute, 5 minutes, 30 minutes) respects the API while giving transient failures time to recover.

Comparison: Version-by-Version

| Aspect | v1 | v2 | v3 | v4 | |--------|-----|-----|-----|-----| | State storage | Separate JSON/YAML files | PostgreSQL | JSONL files | SQLite | | Query capability | None (grep) | Full SQL | Limited (line scan) | Full SQL | | Concurrent writes | Corrupted data | Connection limits | Race conditions | WAL mode | | Backup strategy | Manual copy | pg_dump | Copy file | Copy file | | Start time | N/A (scripts) | 300ms | 100ms | 50ms (Bun) | | Task tracking | None | Basic | Event log | Full history | | Recovery from crash | Manual | Manual | JSON parse | WAL replay | | Teamunanimous verdict | "A mess" | "Overengineered" | "Almost there" | "Finally" |

The jump from v3 to v4 was the biggest. SQLite gave us PostgreSQL's query power without its operational burden. Bun gave us Node's ecosystem without the startup penalty.

Actionable Takeaways

  • Start with SQLite for agent state. You'll get query flexibility without operational complexity. Migrate to PostgreSQL only when you need horizontal scaling.

  • Implement concurrency slots early. It's a fifteen-minute pattern that prevents hours of debugging crashed subprocesses.

  • Add a watchdog in the first week. Stale tasks poison your data. Reclaim them automatically or you'll spend months explaining why "doing" doesn't mean "done."

  • Type everything with TypeScript. The compiler catches schema drift. Runtime debugging of "why is priority sometimes '5' and sometimes 5" will cost you more than type annotations.

  • Design for failure from day one. The job queue's retry mechanism should be there before your first production task runs. Trust me—your API will time out at 3 AM.
