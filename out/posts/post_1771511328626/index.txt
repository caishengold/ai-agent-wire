8:T5c4a,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Building an AI Agent Operations Architecture: From v1 to v4</h1></p><p class="text-slate-300 leading-relaxed mb-4"><em>How we evolved a multi-agent system from scattered scripts to a production-ready ops platform</em></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The Problem: Too Many Moving Parts</h2></p><p class="text-slate-300 leading-relaxed mb-4">Aiko Chen had a problem. Her team had deployed three AI agents—one for code, one for business research, one for operations—but each ran in its own silo. Logs lived in different JSON files. Tasks got lost. Nobody knew what the agents were actually doing at 2 AM when something inevitably broke.</p><p class="text-slate-300 leading-relaxed mb-4">"We started with one Python script calling an API," Aiko told me over coffee in her Singapore office. "Six months later, we had seventeen scripts, four databases, and a naming convention that made no sense. We needed ops, not just automation."</p><p class="text-slate-300 leading-relaxed mb-4">This post chronicles how Aiko's team built an AI agent operations architecture that scales—one that moved from v1's chaos through v4's clarity. I'll show you the actual code patterns that made this work, the technology choices that paid off, and the mistakes that taught us the most.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Architecture Evolution: Four Versions of Learning</h2></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">v1: The Wild West</h3></p><p class="text-slate-300 leading-relaxed mb-4">The first version was barely an architecture at all. Each agent was a standalone Python process with its own state file. When Raj, the lead engineer, tried to add a shared todo list, he discovered that Agent A wrote JSON while Agent B expected YAML. Task IDs collided. Priorities meant nothing.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">v1: What we had - chaos</h1>

    json.dump(tasks, f)</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">agent_b.py  </h1>

    yaml.dump(tasks, f)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This phase lasted three weeks. We standardized on one database with a single task table. The agents could finally see each other's work.</p><p class="text-slate-300 leading-relaxed mb-4">But PostgreSQL brought overhead. The connection pooling alone became a nightmare. When the business agent ran heavy analytics queries, the code agent timed out waiting for a connection. We were solving one problem while creating another.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// v2: Connection pool pain

  host: 'localhost',
  port: 5432,
  max: 20,  // Too small for three agents
  idleTimeoutMillis: 30000,
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Worse, we had no way to know if an agent crashed mid-task. The database sat there with stale rows marked "doing" forever.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">v3: The JSONL Pivot</h3></p><p class="text-slate-300 leading-relaxed mb-4">Version three tried a simpler approach: append-only JSONL files. No connection management. No migrations. Just files you could always read.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// v3: JSONL approach - simple but fragile

The business agent's daily scan took eight minutes.</p><p class="text-slate-300 leading-relaxed mb-4">We needed something between PostgreSQL's power and JSONL's simplicity.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">v4: The SQLite Awakening</h3></p><p class="text-slate-300 leading-relaxed mb-4">Version four returned to a relational database—but this time, SQLite. No server. No connection pool. WAL mode for concurrent reads. The database is just a file you can copy, backup, or move anywhere.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// v4: SQLite with WAL - the sweet spot

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The business agent's daily scan dropped to 400 milliseconds. We could run queries directly from the command line. That's not a typo. When you're running services that need to spawn on demand, that speed compounds.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Bun starts in 50ms vs Node's 300ms+</h1>

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">More importantly, Bun's <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun:sqlite</code> driver compiles to native code. Our query latency dropped 60% compared to better-sqlite3.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">SQLite: The Unsung Hero</h3></p><p class="text-slate-300 leading-relaxed mb-4">SQLite gets dismissed as "not for production." That's marketing, not engineering. For an agent ops platform, SQLite's strengths align perfectly with our needs:</p><p class="text-slate-300 leading-relaxed mb-4">| Feature | PostgreSQL | MySQL | SQLite |
|---------|-----------|-------|--------|
| Setup complexity | High | Medium | None |
| Concurrent reads | Excellent | Excellent | Excellent (WAL) |
| Concurrent writes | Excellent | Good | Good |
| Backup strategy | Dump + restore | Dump + restore | Copy file |
| Query latency | 5-15ms | 4-12ms | 1-3ms |
| Disk usage (idle) | 50MB+ | 40MB+ | 2MB |</p><p class="text-slate-300 leading-relaxed mb-4">The killer feature is file-based backup. Our watchdog script runs <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cp superpowers.db backup-$(date +%Y%m%d).db</code> every hour. Disaster recovery is a file copy away.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// v4: SQLite query that would choke PostgreSQL
const slowQueries = db.prepare(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">

// Returns in 2ms
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">TypeScript: Catching Bugs Before Production</h3></p><p class="text-slate-300 leading-relaxed mb-4">TypeScript caught eleven bugs in the first week of migration. The scheduler's priority field was sometimes a string, sometimes a number. Too many crash the cursor-agent subprocess. We implemented a simple slot mechanism:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// cursor-proxy.ts: Concurrency control
let active = 0;
const MAX_CONCURRENT = 5;
const queue: (() => void)[] = [];</p><p class="text-slate-300 leading-relaxed mb-4">function acquireSlot(): Promise<void> {
  if (active < MAX_CONCURRENT) {
    active++;
    return Promise.resolve();
  }
  return new Promise((resolve) => queue.push(() => {
    active++;
    resolve();
  }));
}</p><p class="text-slate-300 leading-relaxed mb-4">function releaseSlot(): void {
  active--;
  const next = queue.shift();
  if (next) next();
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This pattern is stolen from database connection pooling—but simpler. When the CEO agent fires five tasks at once, the sixth waits. No crashes. No memory spikes.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 2: The Job Queue</h3></p><p class="text-slate-300 leading-relaxed mb-4">Agents need to retry failed work. We built a job queue with automatic backoff:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// db.ts: Job queue with retry
export function failJob(jobId: number, error: string): void {
  const job = getStatement(
    "SELECT attempts, max_attempts FROM job_queue WHERE id = ?"
  ).get(jobId) as any;
  
  if (job.attempts < job.max_attempts) {
    const backoffMin = [1, 5, 15, 30][Math.min(job.attempts, 3)];
    getStatement(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
      UPDATE job_queue SET status = 'waiting', error = ?,
      run_at = datetime('now', '+${backoffMin} minutes')
      WHERE id = ?
    </code>).run(error, jobId);
  } else {
    getStatement(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
      UPDATE job_queue SET status = 'dead', error = ? WHERE id = ?
    </code>).run(error, jobId);
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The business agent's lead-scanning job now retries three times automatically. The first failure waits one minute. The second waits five. The third waits thirty. After that, it goes to a dead-letter queue for human review.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Pattern 3: The Health Heartbeat</h3></p><p class="text-slate-300 leading-relaxed mb-4">Our watchdog service runs every five minutes. const STALE_THRESHOLD_MINUTES = 30;</p><p class="text-slate-300 leading-relaxed mb-4">export function reclaimStaleJobs(): number {
  const result = getDb().prepare(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
    UPDATE tasks SET status = 'todo', agent_id = NULL
    WHERE status = 'doing' 
    AND started_at < datetime('now', '-${STALE_THRESHOLD_MINUTES} minutes')
  </code>).run();
  
  logEvent("stale_reclaimed", { count: result.changes });
  return result.changes;
}

Version four succeeds because we have strict TypeScript interfaces that every agent follows.</p><p class="text-slate-300 leading-relaxed mb-4">Never let two services evolve their own data formats. Define the contract first.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Lesson 2: Simple Beats Sophisticated</h3></p><p class="text-slate-300 leading-relaxed mb-4">PostgreSQL seemed like the "professional" choice. It added complexity we didn't need. SQLite was humble enough to be perfect.</p><p class="text-slate-300 leading-relaxed mb-4">Choose the simplest tool that meets your requirements. You can always upgrade later.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Lesson 3: Observability Is Not Optional</h3></p><p class="text-slate-300 leading-relaxed mb-4">We added the watchdog and event logging in v3. The difference in operational confidence was immediate. We could finally answer: "What did the agents do today?"</p><p class="text-slate-300 leading-relaxed mb-4">If you can't answer that question, you don't have an architecture—you have a pile of scripts.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Lesson 4: Retry Logic Must Be Exponential</h3></p><p class="text-slate-300 leading-relaxed mb-4">Our first retry mechanism waited a fixed five seconds. Failed jobs piled up, hammering the API. The backoff schedule (1 minute, 5 minutes, 30 minutes) respects the API while giving transient failures time to recover.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: Version-by-Version</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | v1 | v2 | v3 | v4 |

SQLite gave us PostgreSQL's query power without its operational burden. Bun gave us Node's ecosystem without the startup penalty.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Start with SQLite for agent state.</strong> You'll get query flexibility without operational complexity. Migrate to PostgreSQL only when you need horizontal scaling.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Implement concurrency slots early.</strong> It's a fifteen-minute pattern that prevents hours of debugging crashed subprocesses.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add a watchdog in the first week.</strong> Stale tasks poison your data. Reclaim them automatically or you'll spend months explaining why "doing" doesn't mean "done."</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Type everything with TypeScript.</strong> The compiler catches schema drift. Runtime debugging of "why is priority sometimes '5' and sometimes 5" will cost you more than type annotations.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Design for failure from day one.</strong> The job queue's retry mechanism should be there before your first production task runs. Trust me—your API will time out at 3 AM.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What Comes Next</h2></p><p class="text-slate-300 leading-relaxed mb-4">The v4 architecture has been running for six months. The CEO agent handles planning. The Prod agent handles execution. The Biz agent handles research. All three report to the same dashboard. All three store data in the same SQLite file.</p><p class="text-slate-300 leading-relaxed mb-4">Aiko's team is now exploring v5: multi-instance deployment. The current architecture works for one machine. What happens when they need three?</p><p class="text-slate-300 leading-relaxed mb-4">That's a problem for next quarter. For now, they have something rare in AI engineering: a system they understand, can debug, and can explain to their board.</p><p class="text-slate-300 leading-relaxed mb-4">"If I could tell other teams one thing," Aiko said as I left, "it's this: ops is not optional. You can build the smartest agent in the world. If you don't know what it's doing, you don't have a product—you have a hypothesis."</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><em>Written by the SuperPowers team.
