Full-Text Search with SQLite FTS5 — setup, indexing, ranking, real-world example

Relational databases handle exact matches well. When users need to find documents containing specific words, phrases, or partial terms, the standard SQL LIKE operator quickly becomes a bottleneck. SQLite addresses this gap with its FTS5 (Full-Text Search version 5) extension — a lightweight, zero-configuration search engine built directly into the database.

This guide walks you through setting up FTS5, understanding how it indexes content, and implementing relevance ranking in a real application.

How FTS5 Works

FTS5 creates an inverted index that maps terms to the documents containing them. Instead of scanning every row like a traditional LIKE '%query%' search, FTS5 locates matching documents in near-constant time.

Consider a simple example: a table with 100,000 articles. A LIKE query searching for "machine learning" scans all 100,000 rows. The same query against an FTS5 virtual table identifies matching documents directly from the index, typically completing in milliseconds regardless of table size.

FTS5 vs Standard LIKE

| Aspect | LIKE '%pattern%' | FTS5 | |--------|-----------------|------| | Query performance | O(n) full table scan | O(1) index lookup | | Wildcard support | Limited (trailing only) | Full prefix, suffix matching | | Ranking | None | BM25 relevance scoring | | Phrase matching | Requires complex queries | Native phrase operators | | Index maintenance | None | Automatic with writes | | Storage overhead | None | 20-50% additional |

The trade-off is straightforward: FTS5 uses more storage and slightly slows write operations, but delivers search performance that scales.

Setting Up FTS5

Creating an FTS5 virtual table follows a familiar pattern. Suppose Raj Patel, a backend engineer at a growing SaaS company, needs to add search to his application's knowledge base. His team stores help articles in a regular table and needs fast, relevant search.

First, the base table holds the source data:

import sqlite3
conn = sqlite3.connect("knowledge_base.db")
cursor = conn.cursor()
cursor.execute("""
    CREATE TABLE IF NOT EXISTS articles (
        id INTEGER PRIMARY KEY,
        title TEXT NOT NULL,
        content TEXT NOT NULL,
        category TEXT,
        created_at TEXT DEFAULT (datetime('now'))
    )
""")

Next, the FTS5 virtual table stores the searchable content:

cursor.execute("""
    CREATE VIRTUAL TABLE IF NOT EXISTS articles_fts USING fts5(
        title,
        content,
        category,
        content='articles',
        content_rowid='id'
    )
""")

The content and content_rowid parameters link the FTS5 table to the base table, enabling synchronized updates.

Synchronizing Data

Keeping the FTS5 index current requires triggers. When rows are inserted, updated, or deleted in the base table, the triggers maintain the search index:

cursor.execute("""
    CREATE TRIGGER IF NOT EXISTS articles_ai AFTER INSERT ON articles BEGIN
        INSERT INTO articles_fts(rowid, title, content, category)
        VALUES (new.id, new.title, new.content, new.category);
    END
""")
cursor.execute("""
    CREATE TRIGGER IF NOT EXISTS articles_ad AFTER DELETE ON articles BEGIN
        INSERT INTO articles_fts(articles_fts, rowid, title, content, category)
        VALUES ('delete', old.id, old.title, old.content, old.category);
    END
""")
cursor.execute("""
    CREATE TRIGGER IF NOT EXISTS articles_au AFTER UPDATE ON articles BEGIN
        INSERT INTO articles_fts(articles_fts, rowid, title, content, category)
        VALUES ('delete', old.id, old.title, old.content, old.category);
        INSERT INTO articles_fts(rowid, title, content, category)
        VALUES (new.id, new.title, new.content, new.category);
    END
""")
conn.commit()

Now the index updates automatically. Raj can insert sample data and test the search:

sample_articles = [
    ("Getting Started with API Integration",

     "api"),

Executing Search Queries

FTS5 supports several query operators. The simplest is a single term:

def search_articles(query: str, limit: int = 10):
    cursor.execute("""
        SELECT a.id, a.title, a.category,
               bm25(articles_fts) as rank
        FROM articles_fts
        JOIN articles a ON articles_fts.rowid = a.id
        WHERE articles_fts MATCH ?
        ORDER BY rank
        LIMIT ?
    """, (query, limit))
    
    return cursor.fetchall()
results = search_articles("machine learning")
for row in results:
    print(f"{row[1]} ({row[2]}) - Score: {row[3]:.2f}")

The bm25() function returns relevance scores using the BM25 ranking algorithm. Lower (more negative) scores indicate better matches.

Query Operators

FTS5 supports powerful query syntax:

AND operator: both terms must appear

results = search_articles("api AND authentication")
OR operator: either term appears

results = search_articles("database OR migration")
Phrase matching: exact phrase

results = search_articles('"machine learning"')
Prefix matching: terms starting with prefix

results = search_articles("data")
NOT operator: exclude term

results = search_articles("api NOT rate")

Building a Search Interface

Aiko Tanaka, the frontend developer on Raj's team, builds a search endpoint. She adds highlighting to show users where matches occur:

def search_with_highlight(query: str, limit: int = 10):
    cursor.execute("""
        SELECT a.id, a.title, a.category,
               snippet(articles_fts, 1, '', '', '...', 32) as snippet,
               bm25(articles_fts) as rank
        FROM articles_fts
        JOIN articles a ON articles_fts.rowid = a.id
        WHERE articles_fts MATCH ?
        ORDER BY rank
        LIMIT ?
    """, (query, limit))
    
    return cursor.fetchall()
results = search_with_highlight("migration")
for row in results:
    print(f"Title: {row[1]}")
    print(f"Category: {row[2]}")
    print(f"Snippet: {row[3]}")
    print(f"Relevance: {row[4]:.2f}\n")

The snippet() function extracts context around matches and wraps matching terms in tags.

Understanding Ranking

BM25, the default ranking algorithm, considers three factors:

  • Term frequency (TF) — How often does the query term appear in the document?
  • Inverse document frequency (IDF) — How rare is the term across the corpus?
  • Document length — Are matches in shorter or longer documents?

    • This combination rewards documents with multiple occurrences of rare terms while penalizing matches in lengthy documents where the term appears infrequently.

    FTS5 exposes ranking through the bm25() function. For custom ranking, you can modify the query:

    cursor.execute("""
    SELECT id, title, bm25(articles_fts, 1.5, 0.0, 1.0) as rank
    FROM articles_fts
    WHERE articles_fts MATCH ?
    ORDER BY rank
""", ("query",))

    The parameters adjust term frequency saturation (default 1.2), document length normalization (default 0.75), and a constant term weight.

    Performance Considerations

    FTS5 performs well out of the box, but a few configurations help:

    Rebuild the index after bulk inserts for optimal performance
    
cursor.execute("INSERT INTO articles_fts(articles_fts) VALUES('rebuild')")
    Analyze index statistics
    
cursor.execute("SELECT      FROM articles_fts WHERE articles_fts='info'")
stats = cursor.fetchone()
print(stats)

    For very large datasets, consider the tokenize option to configure stemming or remove stopwords:

    cursor.execute("""
    CREATE VIRTUAL TABLE IF NOT EXISTS articles_fts2 USING fts5(
        title,
        content,
        tokenize='porter unicode61'
    )
""")

    The porter tokenizer applies stemming (reducing words to root forms), while unicode61 handles international characters properly.

    Lessons Learned

  • Always use triggers to keep the FTS5 index synchronized with your base table; manually maintaining the index introduces bugs
  • Prefix searches have a cost — trailing wildcards (data) work well, but leading wildcards (data) require more processing
  • BM25 scoring is query-dependent — the same document scores differently for different queries, which is the intended behavior
  • Combine FTS5 with regular columns in queries when you need to filter by category, date, or other attributes alongside text search

    • Actionable Takeaways

  • Create your FTS5 table with content linking — Use the content and content_rowid parameters to enable automatic index maintenance via triggers
  • Index content and title separately — Weight title matches higher by including them as a separate column or adjusting BM25 parameters
  • Add category filters in the WHERE clause — FTS5 handles text matching while regular SQL filters narrow results by other attributes
  • Test with realistic query volumes — Small datasets mask performance issues that appear at scale
  • Consider custom tokenizers for non-English content — The porter stemmer and unicode61 tokenizer handle most international text

    • FTS5 provides production-ready full-text search without external services or complex infrastructure. For applications where Elasticsearch or Algolia would be overkill, SQLite FTS5 delivers excellent results with minimal operational overhead.
