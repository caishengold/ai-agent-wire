Health Checks and Readiness Probes for Long-Running Agent Services

> Agent-ops systems often run as long-lived processes: schedulers, publishers, or worker loops. To run them under systemd, Kubernetes, or a process manager, you need clear health and readiness signals. This post describes how to design and expose them so orchestration can restart unhealthy instances and avoid sending traffic to not-yet-ready ones.

1. Liveness vs Readiness

Liveness answers: “Is the process alive and willing to keep running?” If the answer is no, the orchestrator restarts the process. Use it for deadlocks, unrecoverable errors, or “heartbeat failed” conditions.

Readiness answers: “Is this instance ready to accept work or traffic?” If no, the orchestrator stops sending work (e.g. no new tasks, no HTTP requests) but does not restart. Use it for “still starting up,” “dependency temporarily down,” or “maintenance mode.”

For a task runner that only processes a local queue, “liveness” might be “I am looping and have not crashed.” Readiness might be “DB is reachable and I have claimed a task slot.” For an HTTP API in front of the same runner, liveness could be the same; readiness could add “DB + cache connected.”

2. What to Check

Process-level

  • Main loop is running (e.g. a periodic heartbeat timestamp updated by the loop).
  • No “I am stuck” condition: e.g. if “last successful task” is older than a threshold, consider yourself unhealthy.

    • Dependencies

  • Database: open a connection and run a trivial query (SELECT 1 or PRAGMA quick_check for SQLite).
  • External APIs: optional; if you depend on one for every task, a quick HEAD or GET to a status URL can be part of readiness; avoid making it a hard liveness requirement if the API is flaky.

    • Resource limits

  • Optional: check disk space, memory, or queue depth. If the queue is over a limit, you might report “not ready” until backpressure eases.

    • Keep checks fast and cheap. Timeout after 1–2 seconds so the health endpoint does not hang.

    3. Exposing Health Endpoints

    HTTP

  • GET /health/live → 200 if process is alive.
  • GET /health/ready → 200 if ready to accept work, 503 otherwise.

    • Return 200 with an optional JSON body like {"ok":true,"ts":"..."}. No sensitive data. Log failures for debugging.

    File-based (e.g. systemd)

  • Touch a file every N seconds in the main loop; systemd’s WatchdogSec can restart if the file is not updated.
  • Or run a tiny HTTP server only for health; systemd can use curl -f http://localhost:PORT/health/live in ExecStartPost or a watchdog unit.

    • CLI

  • For cron-driven runners, “health” might be a separate script that checks DB and last-run timestamp and exits 0 or 1. A wrapper or monitoring system can run it periodically.

    • 4. Integrating with systemd

  • Use Type=notify or Type=simple and optionally WatchdogSec if you support sd_notify.
  • In the agent, after DB init and first successful loop iteration, call sd_notify("READY=1") so systemd marks the unit as active.
  • For watchdog, send WATCHDOG=1 in the main loop at an interval smaller than WatchdogSec so systemd restarts the process if the loop hangs.

    • This gives you automatic restart on hang and clear “ready” semantics for ordering (e.g. start DB first, then agent).

    5. Safe Defaults

  • If a dependency (DB, API) is down, prefer readiness = no over liveness = no so the orchestrator does not restart the process repeatedly. Once the dependency is back, readiness can flip to yes without a restart.
  • Avoid putting secrets or internal details in health responses. Use a separate admin or debug endpoint behind auth for that.
  • Document what “live” and “ready” mean for your service so operators and SREs know what to expect when probes fail.

    • With clear liveness and readiness signals, long-running agent services fit cleanly into modern orchestration and recover predictably from dependency and transient failures.
