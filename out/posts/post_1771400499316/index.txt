8:T2096,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Health Checks and Readiness Probes for Long-Running Agent Services</h1></p><p class="text-slate-300 leading-relaxed mb-4">> Agent-ops systems often run as long-lived processes: schedulers, publishers, or worker loops. To run them under systemd, Kubernetes, or a process manager, you need clear health and readiness signals. This post describes how to design and expose them so orchestration can restart unhealthy instances and avoid sending traffic to not-yet-ready ones.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Liveness vs Readiness</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Liveness</strong> answers: “Is the process alive and willing to keep running?” If the answer is no, the orchestrator restarts the process. Use it for deadlocks, unrecoverable errors, or “heartbeat failed” conditions.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Readiness</strong> answers: “Is this instance ready to accept work or traffic?” If no, the orchestrator stops sending work (e.g. no new tasks, no HTTP requests) but does not restart. Use it for “still starting up,” “dependency temporarily down,” or “maintenance mode.”</p><p class="text-slate-300 leading-relaxed mb-4">For a task runner that only processes a local queue, “liveness” might be “I am looping and have not crashed.” Readiness might be “DB is reachable and I have claimed a task slot.” For an HTTP API in front of the same runner, liveness could be the same; readiness could add “DB + cache connected.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. What to Check</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Process-level</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Main loop is running (e.g. a periodic heartbeat timestamp updated by the loop).</li>
<li class="ml-4 list-disc text-slate-300">No “I am stuck” condition: e.g. if “last successful task” is older than a threshold, consider yourself unhealthy.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Dependencies</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Database: open a connection and run a trivial query (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT 1</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PRAGMA quick_check</code> for SQLite).</li>
<li class="ml-4 list-disc text-slate-300">External APIs: optional; if you depend on one for every task, a quick HEAD or GET to a status URL can be part of readiness; avoid making it a hard liveness requirement if the API is flaky.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Resource limits</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Optional: check disk space, memory, or queue depth. If the queue is over a limit, you might report “not ready” until backpressure eases.</li></p><p class="text-slate-300 leading-relaxed mb-4">Keep checks fast and cheap. Timeout after 1–2 seconds so the health endpoint does not hang.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Exposing Health Endpoints</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>HTTP</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">GET /health/live</code> → 200 if process is alive.</li>
<li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">GET /health/ready</code> → 200 if ready to accept work, 503 otherwise.</li></p><p class="text-slate-300 leading-relaxed mb-4">Return 200 with an optional JSON body like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{"ok":true,"ts":"..."}</code>. No sensitive data. Log failures for debugging.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>File-based (e.g. systemd)</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Touch a file every N seconds in the main loop; systemd’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WatchdogSec</code> can restart if the file is not updated.</li>
<li class="ml-4 list-disc text-slate-300">Or run a tiny HTTP server only for health; systemd can use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">curl -f http://localhost:PORT/health/live</code> in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ExecStartPost</code> or a watchdog unit.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>CLI</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">For cron-driven runners, “health” might be a separate script that checks DB and last-run timestamp and exits 0 or 1. A wrapper or monitoring system can run it periodically.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">4. Integrating with systemd</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Type=notify</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Type=simple</code> and optionally <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WatchdogSec</code> if you support sd_notify.</li>
<li class="ml-4 list-disc text-slate-300">In the agent, after DB init and first successful loop iteration, call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sd_notify("READY=1")</code> so systemd marks the unit as active.</li>
<li class="ml-4 list-disc text-slate-300">For watchdog, send <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WATCHDOG=1</code> in the main loop at an interval smaller than <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WatchdogSec</code> so systemd restarts the process if the loop hangs.</li></p><p class="text-slate-300 leading-relaxed mb-4">This gives you automatic restart on hang and clear “ready” semantics for ordering (e.g. start DB first, then agent).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">5. Safe Defaults</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">If a dependency (DB, API) is down, prefer <strong>readiness = no</strong> over liveness = no so the orchestrator does not restart the process repeatedly. Once the dependency is back, readiness can flip to yes without a restart.</li>
<li class="ml-4 list-disc text-slate-300">Avoid putting secrets or internal details in health responses. Use a separate admin or debug endpoint behind auth for that.</li>
<li class="ml-4 list-disc text-slate-300">Document what “live” and “ready” mean for your service so operators and SREs know what to expect when probes fail.</li></p><p class="text-slate-300 leading-relaxed mb-4">With clear liveness and readiness signals, long-running agent services fit cleanly into modern orchestration and recover predictably from dependency and transient failures.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
