8:T19a2,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Health Check Endpoints: Design and Implementation in TypeScript</h1></p><p class="text-slate-300 leading-relaxed mb-4">Health checks are a cornerstone of production systems: load balancers, orchestrators (Kubernetes, Docker Swarm), and monitoring tools rely on them to decide whether a process is alive and ready to receive traffic. A well-designed health endpoint keeps operations simple and failures detectable.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Two Common Variants</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Liveness</strong> answers: “Is the process running?” It should be cheap and fast. If it fails, the runtime typically restarts the process. It should not depend on databases, caches, or external APIs—only in-process state.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Readiness</strong> answers: “Can this instance accept traffic?” It may check DB connectivity, cache availability, or that warm-up has finished. Failing readiness usually means “stop sending me traffic for now” rather than “restart me.”</p><p class="text-slate-300 leading-relaxed mb-4">Exposing both (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/live</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health/ready</code>) gives platforms the right knobs: restart when dead, drain when not ready.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Minimal Implementation in TypeScript</h2></p><p class="text-slate-300 leading-relaxed mb-4">Using a simple HTTP server (e.g. with Bun or Node’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">http</code>), you can add a liveness probe that returns 200 and a short JSON body:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import type { ServerRequest } from "bun";</p><p class="text-slate-300 leading-relaxed mb-4">export function handleHealth(req: ServerRequest): Response | null {
  const url = new URL(req.url);
  if (url.pathname === "/health/live") {
    return new Response(
      JSON.stringify({ status: "ok", ts: new Date().toISOString() }),
      { status: 200, headers: { "Content-Type": "application/json" } }
    );
  }
  if (url.pathname === "/health/ready") {
    const ready = checkDb() && checkCache(); // your checks
    return new Response(
      JSON.stringify({
        status: ready ? "ok" : "degraded",
        db: dbOk,
        cache: cacheOk,
      }),
      { status: ready ? 200 : 503, headers: { "Content-Type": "application/json" } }
    );
  }
  return null;
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Liveness stays trivial; readiness encapsulates whatever “ready” means for your service (DB, cache, feature flags, etc.).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What to Check in Readiness</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Database</strong>: Run a no-op or a tiny query (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT 1</code>) with a short timeout. If the DB is down or slow, fail readiness so traffic is shifted away.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Caches</strong>: Ping Redis/Memcached or equivalent. Optional: if the cache is down you might still be “ready” but with degraded behavior; document it and consider a “degraded” state with 200 vs 503.</li>
<li class="ml-4 list-disc text-slate-300"><strong>External APIs</strong>: Use sparingly and with timeouts. If a third-party is down, failing readiness for the whole process may be too aggressive; sometimes a “degraded” flag is better than 503.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Startup</strong>: During bootstrap (migrations, seed data, connection pools), return 503 until initialization is complete so the orchestrator does not send traffic too early.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Security and Performance</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Do not expose sensitive data (connection strings, internal hostnames). Return only status and perhaps component names.</li>
<li class="ml-4 list-disc text-slate-300">Avoid expensive work: no heavy queries or large payloads. Use timeouts (e.g. 2–5 seconds) so a stuck dependency does not hang the probe.</li>
<li class="ml-4 list-disc text-slate-300">If your framework allows, keep health routes out of auth middleware so load balancers do not need credentials. Optionally restrict by IP or network if needed.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Metrics and Logging</h2></p><p class="text-slate-300 leading-relaxed mb-4">Log readiness failures (and optionally liveness hits) with low cardinality so you can alert on “ready” flapping or repeated restarts. Metrics such as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">health_check_duration_seconds</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">health_check_result</code> (0 = ok, 1 = fail) integrate well with Prometheus and Grafana. In TypeScript, you can wrap the handler with a small timer and a counter to record success/failure and latency.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">A clear split between liveness (am I alive?) and readiness (am I ready to serve?) plus lightweight, timeout-bounded checks for DB and cache gives you robust health endpoints. Implement them in TypeScript with simple JSON responses, avoid dependencies in liveness, and keep readiness fast and safe—then plug them into your orchestrator and monitoring stack for reliable production behavior.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
