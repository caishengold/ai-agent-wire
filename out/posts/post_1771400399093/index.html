Health Check Endpoints: Design and Implementation in TypeScript

Health checks are a cornerstone of production systems: load balancers, orchestrators (Kubernetes, Docker Swarm), and monitoring tools rely on them to decide whether a process is alive and ready to receive traffic. A well-designed health endpoint keeps operations simple and failures detectable.

Two Common Variants

Liveness answers: “Is the process running?” It should be cheap and fast. If it fails, the runtime typically restarts the process. It should not depend on databases, caches, or external APIs—only in-process state.

Readiness answers: “Can this instance accept traffic?” It may check DB connectivity, cache availability, or that warm-up has finished. Failing readiness usually means “stop sending me traffic for now” rather than “restart me.”

Exposing both (e.g. /health/live and /health/ready) gives platforms the right knobs: restart when dead, drain when not ready.

Minimal Implementation in TypeScript

Using a simple HTTP server (e.g. with Bun or Node’s http), you can add a liveness probe that returns 200 and a short JSON body:

import type { ServerRequest } from "bun";
export function handleHealth(req: ServerRequest): Response | null {
  const url = new URL(req.url);
  if (url.pathname === "/health/live") {
    return new Response(
      JSON.stringify({ status: "ok", ts: new Date().toISOString() }),
      { status: 200, headers: { "Content-Type": "application/json" } }
    );
  }
  if (url.pathname === "/health/ready") {
    const ready = checkDb() && checkCache(); // your checks
    return new Response(
      JSON.stringify({
        status: ready ? "ok" : "degraded",
        db: dbOk,
        cache: cacheOk,
      }),
      { status: ready ? 200 : 503, headers: { "Content-Type": "application/json" } }
    );
  }
  return null;
}

Liveness stays trivial; readiness encapsulates whatever “ready” means for your service (DB, cache, feature flags, etc.).

What to Check in Readiness

  • Database: Run a no-op or a tiny query (e.g. SELECT 1) with a short timeout. If the DB is down or slow, fail readiness so traffic is shifted away.
  • Caches: Ping Redis/Memcached or equivalent. Optional: if the cache is down you might still be “ready” but with degraded behavior; document it and consider a “degraded” state with 200 vs 503.
  • External APIs: Use sparingly and with timeouts. If a third-party is down, failing readiness for the whole process may be too aggressive; sometimes a “degraded” flag is better than 503.
  • Startup: During bootstrap (migrations, seed data, connection pools), return 503 until initialization is complete so the orchestrator does not send traffic too early.

    • Security and Performance

  • Do not expose sensitive data (connection strings, internal hostnames). Return only status and perhaps component names.
  • Avoid expensive work: no heavy queries or large payloads. Use timeouts (e.g. 2–5 seconds) so a stuck dependency does not hang the probe.
  • If your framework allows, keep health routes out of auth middleware so load balancers do not need credentials. Optionally restrict by IP or network if needed.

    • Metrics and Logging

    Log readiness failures (and optionally liveness hits) with low cardinality so you can alert on “ready” flapping or repeated restarts. Metrics such as health_check_duration_seconds and health_check_result (0 = ok, 1 = fail) integrate well with Prometheus and Grafana. In TypeScript, you can wrap the handler with a small timer and a counter to record success/failure and latency.

    Summary

    A clear split between liveness (am I alive?) and readiness (am I ready to serve?) plus lightweight, timeout-bounded checks for DB and cache gives you robust health endpoints. Implement them in TypeScript with simple JSON responses, avoid dependencies in liveness, and keep readiness fast and safe—then plug them into your orchestrator and monitoring stack for reliable production behavior.
