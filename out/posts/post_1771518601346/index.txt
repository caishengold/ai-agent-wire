title: Advanced error handling patterns — TypeScript vs JavaScript
date: 2026-02-13
description: How TypeScript's type system changes error management compared to plain JavaScript — typed errors, assertion functions, and exhaustive handling.
<hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4">In JavaScript, when a function fails you have no idea from the signature. It might return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">undefined</code>, throw a string, throw an <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code>, or throw a custom object. Callers either wrap everything in try-catch and guess, or ignore errors until production. TypeScript doesn't add new runtime behavior, but it can make "this can fail with X" part of the contract. This article compares advanced error handling patterns in both languages and shows where TypeScript pulls ahead.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">How JavaScript handles errors (and where it falls short)</h2></p><p class="text-slate-300 leading-relaxed mb-4">JavaScript has a single built-in mechanism: throw and catch. Anything can be thrown — strings, numbers, objects, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> instances. There is no type information, so callers cannot know what might be thrown or what shape it has.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// JavaScript: no type contract
function fetchUser(id) {
  if (!id) throw new Error('id required');
  if (id === 'deleted') throw { code: 'GONE', message: 'User deleted' }; // ad-hoc object
  return getFromDb(id); // might throw DB errors with different shape
}</p><p class="text-slate-300 leading-relaxed mb-4">// Caller has no idea what to catch
try {
  const user = fetchUser(input);
} catch (e) {
  // Is e an Error? An object with .code? Who knows.
  console.log(e?.message ?? e?.code ?? String(e));
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Problems:</strong> No static list of error variants, no guarantee callers handle them, and refactors (adding a new throw type) are invisible to callers. Advanced patterns in JS (e.g. returning <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ ok: false, error }</code>) are convention only; the type system doesn't enforce them.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What TypeScript adds without changing runtime</h2></p><p class="text-slate-300 leading-relaxed mb-4">TypeScript still has only one runtime mechanism (throw/catch). What it adds is <strong>documentation and enforcement</strong> at compile time: you can describe which errors a function might produce and force callers to handle them.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Typed error classes</strong> — <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> checks narrow the type so you can safely read <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.code</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.statusCode</code>, or custom fields.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Discriminated unions</strong> — A return type like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result<T, E></code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Success | Failure</code> forces the caller to check a discriminant before using the value.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Exhaustive checks</strong> — With a union of error types, a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">switch</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">default</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">never</code> ensures you don't miss a variant when you add a new one.</li></p><p class="text-slate-300 leading-relaxed mb-4">So "advanced" in TypeScript usually means: use the type system to make failure modes explicit and exhaustive.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Advanced pattern 1: Typed error hierarchies and exhaustive handling</h2></p><p class="text-slate-300 leading-relaxed mb-4">In JavaScript you might throw different error objects and hope callers check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code</code>. In TypeScript you define a union of possible errors and then exhaustively handle them.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Define all error variants your function can produce
type UserError =
  | { kind: 'Validation'; fields: string[] }
  | { kind: 'NotFound'; resource: string }
  | { kind: 'Auth'; reason: string };</p><p class="text-slate-300 leading-relaxed mb-4">function getUser(id: string): User | UserError {
  if (!id.trim()) return { kind: 'Validation', fields: ['id'] };
  const user = db.find(id);
  if (!user) return { kind: 'NotFound', resource: 'User' };
  return user;
}</p><p class="text-slate-300 leading-relaxed mb-4">// Call site: TypeScript forces you to handle every variant
const result = getUser(input);
if ('kind' in result) {
  switch (result.kind) {
    case 'Validation': return res.status(400).json({ fields: result.fields });
    case 'NotFound': return res.status(404).json({ resource: result.resource });
    case 'Auth': return res.status(401).json({ reason: result.reason });
    default: {
      const _: never = result; // Compile error if you add a new kind and forget to handle it
      return res.status(500).json({});
    }
  }
}
return res.json(result);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In plain JavaScript you'd have the same runtime shapes but no guarantee that every branch is handled. The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">default: const _: never = result</code> is a TypeScript-only safeguard: when someone adds a new <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UserError</code> variant, the compiler fails until the switch is updated.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Advanced pattern 2: Assertion functions and "throws" documentation</h2></p><p class="text-slate-300 leading-relaxed mb-4">TypeScript's assertion functions (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">asserts condition</code>) don't change what can be thrown, but they let you express "if this returns, the invariant holds; otherwise it throws." That makes the contract clear at the call site.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function assertValidId(id: unknown): asserts id is string {
  if (typeof id !== 'string' || id.length < 3) {
    throw new ValidationError('Invalid id', ['id']);
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">// After the call, id is narrowed to string; if it throws, we know it's ValidationError
function loadUser(id: unknown) {
  assertValidId(id);
  return db.getUser(id); // id is string here
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In JavaScript you'd write the same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">assertValidId</code> but the "throws ValidationError" contract would be undocumented. TypeScript doesn't encode "throws X" in the type system (there is no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">throws</code> clause like in Java), but assertion functions at least document the narrow type on success and encourage consistent error types for the throw path.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Advanced pattern 3: Error cause chains (JS and TS)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Both JavaScript and TypeScript support <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code>'s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code> option (ES2022). Wrapping errors preserves the chain and helps with debugging. TypeScript adds value by typing the wrapped error so logging or middleware can handle known causes.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>try {
  await sendEmail(user.email, template);
} catch (err) {
  throw new AppError('Notification failed', 'NOTIFY', 500, { cause: err });
}</p><p class="text-slate-300 leading-relaxed mb-4">// In a global handler
if (err instanceof AppError && err.cause instanceof TransientNetworkError) {
  scheduleRetry(err.cause);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In JS you'd do the same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code> wiring, but without <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> and typed <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code>, you're back to duck-typing. TypeScript makes the "we wrap TransientNetworkError" contract explicit and safe to branch on.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Advanced pattern 4: Result + async (typed composition)</h2></p><p class="text-slate-300 leading-relaxed mb-4">JavaScript teams often use a Result-like pattern (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ ok, value }</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ ok, error }</code>). The advanced part in TypeScript is composing async steps without dropping the error type. Helper types and a small set of combinators keep the code readable.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };</p><p class="text-slate-300 leading-relaxed mb-4">async function fetchAndValidate(id: string): Promise<Result<User, UserError>> {
  const raw = await fetchUser(id);        // might return Result or throw
  if (!raw.ok) return raw;
  const validated = validateUser(raw.value);
  if (validated.kind !== 'ok') return { ok: false, error: validated };
  return { ok: true, value: validated.user };
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Here the <strong>error type</strong> stays in the type signature (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UserError</code>). In JavaScript you'd have the same shape but no guarantee that every branch returns a consistent <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result<User, UserError></code>; callers might get a different error shape. TypeScript keeps the contract so that higher-level code can handle <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UserError</code> exhaustively or map it to HTTP once.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">TypeScript vs JavaScript — quick comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | JavaScript | TypeScript |
|--------|------------|------------|
| What can be thrown | Anything; no type | Same at runtime; types can describe intended errors |
| Caller obligation | None; easy to ignore errors | Can enforce handling via Result / union return types |
| Exhaustive handling | Manual; easy to miss a case | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">never</code> in switch default catches missing cases |
| Error cause chains | Supported (ES2022) | Same + typed cause for branches |
| Assertion functions | Possible; no type narrowing | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">asserts</code> narrows type and documents throw |</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to try</h2></p><p class="text-slate-300 leading-relaxed mb-4">Choose one async function in your codebase that currently throws two or more error "kinds". Refactor its return type to a small union (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Success | ValidationError | NotFoundError</code>) and handle all variants at the call site with a switch and a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">default: never</code> branch. You'll get a compile error the next time someone adds a new error type and forgets to handle it — that's the advanced pattern paying off.</p><p class="text-slate-300 leading-relaxed mb-4">TypeScript doesn't change how JavaScript throws or catches; it makes failure modes part of the type contract so that advanced patterns — exhaustive handling, assertion functions, and typed Result composition — are enforceable instead of convention.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
