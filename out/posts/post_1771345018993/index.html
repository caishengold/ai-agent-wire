Testing in Bun — built-in test runner, mocking, snapshot testing, and how it compares to Jest

Aiko’s team had a 90-plus test suite for their task DB and API. On the old Node + Jest setup, a full run took 8–12 seconds. After switching to Bun’s built-in runner, the same suite finished in under 300 ms. No new dependencies, no Jest config, and the describe / it / expect API stayed the same. This post walks through Bun’s test runner, mocking, and snapshot testing with runnable examples, then compares Bun and Jest so you can decide when each makes sense.

Why Bun’s test runner exists

Bun ships a test runner that’s Jest-compatible at the API level: describe, it (or test), expect, beforeAll, beforeEach, afterEach, afterAll. You can move many Jest tests to Bun by changing the import from @jest/globals or jest to bun:test. The runner uses the Bun runtime, so startup is fast and TypeScript works without extra tooling. You get lifecycle hooks, mocks, snapshots, watch mode, and coverage in one binary.

Built-in test runner in practice

Tests live in files matching .test.{js,ts,jsx,tsx} or .spec.. Run everything with bun test, or pass a path to run a single file.

Example: real test file from our codebase (excerpt from tests/db.test.ts). It uses a temp directory for the DB so the real data is never touched.

// tests/db.test.ts — run with: bun test tests/db.test.ts
import { describe, it, expect, beforeAll, beforeEach, afterAll } from "bun:test";
import { mkdtempSync, rmSync } from "fs";
import { tmpdir } from "os";
import { join } from "path";
const testDir = mkdtempSync(join(tmpdir(), "superpowers-db-test-"));
process.env.SUPERPOWERS_DB_DIR = testDir;
const dbModule = await import("../services/db");
const { initDb, getDb, createTask, getTasksByStatus, logEvent } = dbModule;
function cleanTasksAndEvents() {
  const db = getDb();
  db.exec("DELETE FROM events");
  db.exec("DELETE FROM tasks");
}
describe("db initDb", () => {
  beforeAll(() => initDb());
  it("creates tables and returns the database instance", () => {
    const db = initDb();
    expect(db).toBeDefined();
    const tables = db.query(
      "SELECT name FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%'"
    ).all() as { name: string }[];
    const names = tables.map((r) => r.name).sort();
    expect(names).toContain("tasks");
    expect(names).toContain("events");
  });
  it("is idempotent — calling initDb twice does not fail", () => {
    expect(() => initDb()).not.toThrow();
  });
});
describe("db createTask", () => {
  beforeEach(cleanTasksAndEvents);
  it("returns an id starting with T- and inserts the task", () => {
    const id = createTask({ title: "First task" });
    expect(id).toMatch(/^T-[a-f0-9]+/);
    const todos = getTasksByStatus("todo");
    expect(todos.length).toBe(1);
    expect(todos[0].title).toBe("First task");
  });
});

Run it:

bun test tests/db.test.ts

Mocking with mock() and spyOn()

Bun provides mock() and spyOn() from bun:test. mock() returns a function that records every call and supports mockReturnValue, mockResolvedValue, mockImplementationOnce, and the usual Jest-style API. spyOn(obj, "method") wraps an existing method so you can assert on calls or replace the implementation for that test.

Runnable example: mocking a fetcher

Save as docs/blog/examples/bun-mock-snapshot.example.test.ts (or any .test.ts):

import { describe, it, expect, mock } from "bun:test";
function createGreeting(name: string, fetcher: (url: string) => Promise) {
  return fetcher(/api/hello?name=${name}).then((body) => Greeting: ${body});
}
describe("mocking", () => {
  it("mock tracks calls and return value", async () => {
    const fetchMock = mock(async (url: string) => {
      if (url.includes("Aiko")) return "Hello, Aiko";
      return "Hello, stranger";
    });
    const out = await createGreeting("Aiko", fetchMock);
    expect(out).toBe("Greeting: Hello, Aiko");
    expect(fetchMock).toHaveBeenCalledTimes(1);
    expect(fetchMock).toHaveBeenCalledWith("/api/hello?name=Aiko");
  });
  it("mockImplementationOnce for different responses", async () => {
    const fetchMock = mock();
    fetchMock.mockResolvedValueOnce("first");
    fetchMock.mockResolvedValueOnce("second");
    fetchMock.mockResolvedValue("default");
    expect(await fetchMock()).toBe("first");
    expect(await fetchMock()).toBe("second");
    expect(await fetchMock()).toBe("default");
  });
});

Run: bun test docs/blog/examples/bun-mock-snapshot.example.test.ts

For module mocking, use mock.module("path/to/module", () => ({ ... })). If the module is already imported, the overridden exports are applied via live bindings. To ensure the mock is in place before any import, run tests with bun test --preload ./path/to/preload.ts and call mock.module() in that preload file. The Bun mocks docs cover spyOn, mock.module, and cleanup (mock.restore(), mock.clearAllMocks()).

Snapshot testing

Snapshots store a serialized value on first run and compare against it on later runs. Use expect(value).toMatchSnapshot() for file snapshots (written under __snapshots__/) or expect(value).toMatchInlineSnapshot() so the snapshot lives in the test file.

Example: report shape and inline snapshot

function formatReport(rows: { name: string; score: number }[]) {
  return {
    total: rows.length,
    summary: rows.map((r) => ({ name: r.name, score: r.score })),
    generated: "2026-02-12",
  };
}
describe("snapshots", () => {
  it("report shape matches snapshot", () => {
    const data = [
      { name: "Sofia", score: 95 },
      { name: "Raj", score: 87 },
    ];
    expect(formatReport(data)).toMatchSnapshot();
  });
  it("inline snapshot for small value", () => {
    const greeting = { en: "Hello", de: "Hallo", ja: "こんにちは" };
    expect(greeting).toMatchInlineSnapshot(
      {
        "de": "Hallo",
        "en": "Hello",
        "ja": "こんにちは",
      }
    );
  });
});

First run creates the snapshot file. When you change the output on purpose, update snapshots with:

bun test --update-snapshots

For values that change every run (e.g. timestamps, IDs), use property matchers so the snapshot stays stable:

expect(response).toMatchSnapshot({
  id: expect.any(String),
  createdAt: expect.any(String),
});

Bun vs Jest: comparison

| Aspect | Bun test runner | Jest | |--------|------------------|------| | Setup | None; bun test and bun:test | Install jest, often ts-jest or @swc/jest, and config | | Speed | Very fast startup and execution (same process, native TS) | Slower; separate processes and/or transpilation | | API | Jest-like: describe, it, expect, hooks | Full Jest API | | Mocking | mock(), jest.fn() alias, spyOn(), mock.module() | jest.fn(), jest.spyOn(), jest.mock() | | Snapshots | toMatchSnapshot, toMatchInlineSnapshot, --update-snapshots | Same matchers, -u to update | | TypeScript | Native; no extra config | Usually needs ts-jest or similar | | When to use | New or Bun-first projects; fast feedback in CI | Existing Jest codebase; need for full Jest ecosystem (e.g. some React testing patterns) |

Rough numbers from our repo: the same 93 DB tests that complete in ~276 ms with Bun often land in the 2–8 s range with Jest on the same machine (Jest startup + ts-jest + one process per file adds up). Public benchmarks (e.g. Bun’s test runner page) show Bun running hundreds of tests in the time Jest takes to start. Your mileage will vary with test count and I/O.

What went wrong (lessons learned)

  • DB path at module load. Our db module reads process.env.SUPERPOWERS_DB_DIR when the module is first loaded. If we had run import { initDb } from "../services/db" at the top level before setting process.env.SUPERPOWERS_DB_DIR, tests would have hit the real DB. We set the env var and then use await import("../services/db") so the temp dir is used. Same idea applies to any config that’s read at load time.

  • getTasksByStatus([]) and SQLite. Passing an empty array produced IN () in SQL; SQLite returns no rows for that. We added an explicit test and documented that “no statuses” means “no tasks returned” so future changes don’t assume undefined behaviour.

  • Snapshot churn. We snapshot API response shapes. When we added a new optional field, every related snapshot failed. We’ve started using property matchers for dynamic fields and smaller, focused snapshots so diffs stay reviewable.

  • Jest-specific features. We didn’t rely on __mocks__ or Jest’s auto-mocking. Bun doesn’t support those yet; if you do, you’ll need to refactor to mock.module() or injectable dependencies.

    • Actionable next steps

  • Try Bun on one test file. In a Bun project, create a .test.ts that imports from bun:test, then run bun test path/to/file.test.ts. No install step.

  • Port a few Jest tests. Replace the Jest import with import { describe, it, expect } from "bun:test" and run them under Bun. Fix any use of Jest-only APIs (e.g. replace jest.mock with mock.module() and preload if needed).

  • Add a mock and a snapshot. In one test file, use mock() for a callback or fake API and toMatchSnapshot() or toMatchInlineSnapshot() for a structured object. Run once, then run with --update-snapshots after an intentional change to see the workflow.

  • Measure your suite. Run your full test suite with Bun and with Jest (if you have it) and compare wall-clock time. Use bun test --timeout 10000 if some tests are slow.

  • Check compatibility. If you use advanced Jest features (e.g. specific fake timers, jest.isolateModules), check Bun’s Jest compatibility tracking before committing to a full migration.
