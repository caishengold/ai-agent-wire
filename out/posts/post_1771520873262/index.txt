title: A comparative analysis of error handling techniques in TypeScript
date: 2026-02-13
description: When to use try-catch, custom errors, Result types, and async patterns — with code examples and a simple decision guide.
<hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4">Your API returns 500. The logs say "Error". You spend twenty minutes tracing the call stack before you find the real cause: a missing field that could have been a clear validation error. TypeScript gives you several ways to handle failures; picking the right one makes the difference between debuggable code and mystery boxes.</p><p class="text-slate-300 leading-relaxed mb-4">This article compares the main error handling techniques in TypeScript — try-catch, custom error classes, Result-like patterns, and async-specific approaches — with examples and a short guide on when to use each.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we're comparing</h2></p><p class="text-slate-300 leading-relaxed mb-4">We'll look at four approaches:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Try-catch</strong> — built-in, familiar, good for synchronous throws.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Custom error classes</strong> — typed, domain-specific errors you can <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> and pass through layers.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Result / Either style</strong> — explicit success/failure in the type system, no hidden throws.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Async error handling</strong> — combining the above with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">async/await</code> and promise rejection.</li></p><p class="text-slate-300 leading-relaxed mb-4">Each has trade-offs. The goal is to choose by context (sync vs async, API boundary vs internal, strict typing vs simplicity) rather than by habit.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Try-catch: when it fits</h2></p><p class="text-slate-300 leading-relaxed mb-4">Try-catch is the default. You throw, you catch, you log or recover. It works well when the failure is exceptional and you handle it one or two levels up.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>function parseConfig(path: string): Config {
  const raw = fs.readFileSync(path, 'utf-8');
  const data = JSON.parse(raw); // can throw
  return validateConfig(data);  // can throw
}</p><p class="text-slate-300 leading-relaxed mb-4">// Caller decides what to do
try {
  const config = parseConfig('./config.json');
  startServer(config);
} catch (err) {
  console.error('Config load failed:', err instanceof Error ? err.message : err);
  process.exit(1);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> No extra types, easy to read, works with any code that throws. <strong>Cons:</strong> Callers can forget to catch; types don't tell you "this might throw"; stack traces can be noisy if you rethrow without wrapping.</p><p class="text-slate-300 leading-relaxed mb-4">Use try-catch when the failure is rare, the caller is nearby, and you're fine with "might throw" being implicit in the type.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Custom error classes: domain and layers</h2></p><p class="text-slate-300 leading-relaxed mb-4">When you have several failure modes (validation, not found, auth, network), plain <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> forces you to parse messages or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> on ad-hoc types. Custom classes give you stable, typed errors and a clear hierarchy.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, new.target.prototype); // for instanceof
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">class ValidationError extends AppError {
  constructor(message: string, public readonly fields?: string[]) {
    super(message, 'VALIDATION_ERROR', 400);
    this.name = 'ValidationError';
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">class NotFoundError extends AppError {
  constructor(resource: string) {
    super(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${resource} not found</code>, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">// In a route handler
try {
  const user = await getUserById(req.params.id);
  if (!user) throw new NotFoundError('User');
  return res.json(user);
} catch (err) {
  if (err instanceof ValidationError) return res.status(400).json({ error: err.message, fields: err.fields });
  if (err instanceof NotFoundError) return res.status(404).json({ error: err.message });
  throw err; // rethrow unknown errors to a global handler
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Callers can branch on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code>, add middleware that maps error classes to HTTP status, and attach extra fields (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">fields</code> for validation). <strong>Cons:</strong> You must remember to set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">name</code> and fix the prototype chain so <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> works after transpilation.</p><p class="text-slate-300 leading-relaxed mb-4">Use custom errors at API or service boundaries where you need to translate failures into HTTP responses or user-facing messages.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Result-style: errors as values</h2></p><p class="text-slate-300 leading-relaxed mb-4">Some teams prefer to avoid throws and model failure in the type system. A <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result<T, E></code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Either<E, T></code>) makes "this can fail" explicit in the signature.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };</p><p class="text-slate-300 leading-relaxed mb-4">function divide(a: number, b: number): Result<number, string> {
  if (b === 0) return { ok: false, error: 'Division by zero' };
  return { ok: true, value: a / b };
}</p><p class="text-slate-300 leading-relaxed mb-4">function parseUserId(input: string): Result<string, ValidationError> {
  const id = input.trim();
  if (!id || id.length < 3) return { ok: false, error: new ValidationError('Invalid id', ['id']) };
  return { ok: true, value: id };
}</p><p class="text-slate-300 leading-relaxed mb-4">// Call site: no try-catch, compiler forces you to handle both branches
const result = divide(10, 0);
if (result.ok) {
  console.log(result.value);
} else {
  console.error(result.error);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> No hidden control flow; every call site must handle failure. Great for parsers, validators, and pure logic. <strong>Cons:</strong> More boilerplate; composing many async steps can get verbose unless you add helpers (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">flatMap</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">mapErr</code>). Not every function needs this level of explicitness.</p><p class="text-slate-300 leading-relaxed mb-4">Use Result when you want the type system to enforce handling and when the operation is a clear "success or failure" with a single error type.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Async: combining techniques</h2></p><p class="text-slate-300 leading-relaxed mb-4">With async code, the same ideas apply: you can throw (and catch with try-catch), throw custom errors, or return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Promise<Result<T, E>></code>. A common pitfall is forgetting that a rejected promise is like an uncaught throw — it will surface to the global rejection handler if not caught.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>async function fetchUser(id: string): Promise<User> {
  const res = await fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/api/users/${id}</code>);
  if (!res.ok) {
    if (res.status === 404) throw new NotFoundError('User');
    throw new AppError(await res.text(), 'API_ERROR', res.status);
  }
  const data = await res.json();
  return validateUser(data); // sync validation, can throw ValidationError
}</p><p class="text-slate-300 leading-relaxed mb-4">// Caller
try {
  const user = await fetchUser(req.params.id);
  return res.json(user);
} catch (err) {
  if (err instanceof NotFoundError) return res.status(404).json({ error: err.message });
  if (err instanceof ValidationError) return res.status(400).json({ error: err.message });
  return res.status(500).json({ error: 'Internal error' });
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Best practice:</strong> In async functions, prefer throwing typed errors (custom classes) and centralize mapping to HTTP in one place (middleware or a top-level catch). That keeps route handlers short and consistent.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Custom errors and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code>:</strong> If you compile to ES5 or use different bundles, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof Error</code> subclasses can fail. Fix: call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Object.setPrototypeOf(this, new.target.prototype)</code> in the constructor.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Lost stack traces:</strong> Wrapping errors in a new <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error(message)</code> drops the original stack. Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">throw new AppError('Failed', 'CODE', 500, { cause: err });</code> and log <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">error.cause</code> where needed.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Result + async:</strong> Chaining many <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result</code>-returning async steps gets noisy. Either add a small helper library (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">neverthrow</code>) or use try-catch with custom errors for async flows and reserve Result for sync, pure functions.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Context | Prefer |
|--------|--------|
| Sync, rare failure, single caller | try-catch |
| API / service boundary, multiple error kinds | Custom error classes |
| Parsers, validators, pure logic | Result&lt;T, E&gt; |
| Async HTTP / DB calls | Custom errors + try-catch in handlers |
| Library that must not throw | Result or return error codes |</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one boundary in your codebase (e.g. one API route or one service method) and introduce a single custom error class for its main failure mode. Map that class to a status code and a clear message. You'll get better logs and a pattern you can reuse elsewhere.</p><p class="text-slate-300 leading-relaxed mb-4">Error handling in TypeScript doesn't need to be one-size-fits-all. Use try-catch for simplicity, custom errors for boundaries, and Result when you want the type system to remind you to handle failure — and you'll spend less time hunting "Error" in the logs.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
