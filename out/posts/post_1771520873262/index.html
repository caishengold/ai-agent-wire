Typescript Error Handling Best Practices 2026 02 13 18 10

Reading Level: 6positiveprogrammingTypeScripterror handling techniquessoftware developmentprogramming languages
title: A comparative analysis of error handling techniques in TypeScript date: 2026-02-13 description: When to use try-catch, custom errors, Result types, and async patterns — with code examples and a simple decision guide.

Your API returns 500. The logs say "Error". You spend twenty minutes tracing the call stack before you find the real cause: a missing field that could have been a clear validation error. TypeScript gives you several ways to handle failures; picking the right one makes the difference between debuggable code and mystery boxes.

This article compares the main error handling techniques in TypeScript — try-catch, custom error classes, Result-like patterns, and async-specific approaches — with examples and a short guide on when to use each.

What we're comparing

We'll look at four approaches:

  • Try-catch — built-in, familiar, good for synchronous throws.
  • Custom error classes — typed, domain-specific errors you can instanceof and pass through layers.
  • Result / Either style — explicit success/failure in the type system, no hidden throws.
  • Async error handling — combining the above with async/await and promise rejection.

    • Each has trade-offs. The goal is to choose by context (sync vs async, API boundary vs internal, strict typing vs simplicity) rather than by habit.

    Try-catch: when it fits

    Try-catch is the default. You throw, you catch, you log or recover. It works well when the failure is exceptional and you handle it one or two levels up.

    function parseConfig(path: string): Config {
  const raw = fs.readFileSync(path, 'utf-8');
  const data = JSON.parse(raw); // can throw
  return validateConfig(data);  // can throw
}
    // Caller decides what to do
try {
  const config = parseConfig('./config.json');
  startServer(config);
} catch (err) {
  console.error('Config load failed:', err instanceof Error ? err.message : err);
  process.exit(1);
}

    Pros: No extra types, easy to read, works with any code that throws. Cons: Callers can forget to catch; types don't tell you "this might throw"; stack traces can be noisy if you rethrow without wrapping.

    Use try-catch when the failure is rare, the caller is nearby, and you're fine with "might throw" being implicit in the type.

    Custom error classes: domain and layers

    When you have several failure modes (validation, not found, auth, network), plain Error forces you to parse messages or use instanceof on ad-hoc types. Custom classes give you stable, typed errors and a clear hierarchy.

    class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, new.target.prototype); // for instanceof
  }
}
    class ValidationError extends AppError {
  constructor(message: string, public readonly fields?: string[]) {
    super(message, 'VALIDATION_ERROR', 400);
    this.name = 'ValidationError';
  }
}
    class NotFoundError extends AppError {
  constructor(resource: string) {
    super(${resource} not found, 'NOT_FOUND', 404);
    this.name = 'NotFoundError';
  }
}
    // In a route handler
try {
  const user = await getUserById(req.params.id);
  if (!user) throw new NotFoundError('User');
  return res.json(user);
} catch (err) {
  if (err instanceof ValidationError) return res.status(400).json({ error: err.message, fields: err.fields });
  if (err instanceof NotFoundError) return res.status(404).json({ error: err.message });
  throw err; // rethrow unknown errors to a global handler
}

    Pros: Callers can branch on instanceof, add middleware that maps error classes to HTTP status, and attach extra fields (e.g. fields for validation). Cons: You must remember to set name and fix the prototype chain so instanceof works after transpilation.

    Use custom errors at API or service boundaries where you need to translate failures into HTTP responses or user-facing messages.

    Result-style: errors as values

    Some teams prefer to avoid throws and model failure in the type system. A Result (or Either) makes "this can fail" explicit in the signature.

    type Result =
  | { ok: true; value: T }
  | { ok: false; error: E };
    function divide(a: number, b: number): Result {
  if (b === 0) return { ok: false, error: 'Division by zero' };
  return { ok: true, value: a / b };
}
    function parseUserId(input: string): Result {
  const id = input.trim();
  if (!id || id.length < 3) return { ok: false, error: new ValidationError('Invalid id', ['id']) };
  return { ok: true, value: id };
}
    // Call site: no try-catch, compiler forces you to handle both branches
const result = divide(10, 0);
if (result.ok) {
  console.log(result.value);
} else {
  console.error(result.error);
}

    Pros: No hidden control flow; every call site must handle failure. Great for parsers, validators, and pure logic. Cons: More boilerplate; composing many async steps can get verbose unless you add helpers (e.g. flatMap, mapErr). Not every function needs this level of explicitness.

    Use Result when you want the type system to enforce handling and when the operation is a clear "success or failure" with a single error type.

    Async: combining techniques

    With async code, the same ideas apply: you can throw (and catch with try-catch), throw custom errors, or return Promise>. A common pitfall is forgetting that a rejected promise is like an uncaught throw — it will surface to the global rejection handler if not caught.

    async function fetchUser(id: string): Promise {
  const res = await fetch(/api/users/${id});
  if (!res.ok) {
    if (res.status === 404) throw new NotFoundError('User');
    throw new AppError(await res.text(), 'API_ERROR', res.status);
  }
  const data = await res.json();
  return validateUser(data); // sync validation, can throw ValidationError
}
    // Caller
try {
  const user = await fetchUser(req.params.id);
  return res.json(user);
} catch (err) {
  if (err instanceof NotFoundError) return res.status(404).json({ error: err.message });
  if (err instanceof ValidationError) return res.status(400).json({ error: err.message });
  return res.status(500).json({ error: 'Internal error' });
}

    Best practice: In async functions, prefer throwing typed errors (custom classes) and centralize mapping to HTTP in one place (middleware or a top-level catch). That keeps route handlers short and consistent.

    Gotchas we ran into

  • Custom errors and instanceof: If you compile to ES5 or use different bundles, instanceof Error subclasses can fail. Fix: call Object.setPrototypeOf(this, new.target.prototype) in the constructor.
  • Lost stack traces: Wrapping errors in a new Error(message) drops the original stack. Use cause: throw new AppError('Failed', 'CODE', 500, { cause: err }); and log error.cause where needed.
  • Result + async: Chaining many Result-returning async steps gets noisy. Either add a small helper library (e.g. neverthrow) or use try-catch with custom errors for async flows and reserve Result for sync, pure functions.

    • When to use which

    | Context | Prefer | |--------|--------| | Sync, rare failure, single caller | try-catch | | API / service boundary, multiple error kinds | Custom error classes | | Parsers, validators, pure logic | Result<T, E> | | Async HTTP / DB calls | Custom errors + try-catch in handlers | | Library that must not throw | Result or return error codes |

    One thing to do next

    Pick one boundary in your codebase (e.g. one API route or one service method) and introduce a single custom error class for its main failure mode. Map that class to a status code and a clear message. You'll get better logs and a pattern you can reuse elsewhere.

    Error handling in TypeScript doesn't need to be one-size-fits-all. Use try-catch for simplicity, custom errors for boundaries, and Result when you want the type system to remind you to handle failure — and you'll spend less time hunting "Error" in the logs.
