8:T4b67,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">DNS for developers: record types, TTL strategies, debugging with dig, and common pitfalls</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj's new microservice returned 502s for half of his users. The health checks passed in his region; in Frankfurt and Tokyo, the load balancer kept hitting an old IP. Turned out the team had set a 24-hour TTL (time-to-live) on the service's A record. When they migrated to a new cluster, Europe and Asia kept resolving the old address for up to a day. One config change — lowering TTL before the cutover — would have made the switch invisible. DNS is one of those layers that works until it doesn't; when it breaks, it's often at 3 AM and in a region you don't have a terminal open in. This post covers the record types you'll actually use, how to think about TTLs, how to debug with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code>, and the mistakes we've seen (and made).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Developers who deploy services, configure domains, or troubleshoot "it works on my machine but not in production" — and want to stop guessing and start verifying.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Record types you'll use in practice</h2></p><p class="text-slate-300 leading-relaxed mb-4">The Domain Name System (DNS) maps names to data. Each "record type" answers a different question. You don't need to memorise every type; these are the ones that show up in app and infra work.</p><p class="text-slate-300 leading-relaxed mb-4">| Type  | Purpose | Example use |
|-------|---------|-------------|
| <strong>A</strong> | Hostname → IPv4 address | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">203.0.113.42</code> |
| <strong>AAAA</strong> | Hostname → IPv6 address | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">2001:db8::1</code> |
| <strong>CNAME</strong> | Alias: name → another name | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www.example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> |
| <strong>MX</strong> | Mail server for the domain | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> → <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">mail.provider.com</code> (with priority) |
| <strong>TXT</strong> | Arbitrary text (verification, SPF, DKIM) | Domain ownership, email auth |
| <strong>NS</strong> | Which servers are authoritative for the domain | Delegation to your DNS provider |
| <strong>SRV</strong> | Service discovery (host, port, priority) | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">_http._tcp.api.example.com</code> → host + port |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Important rule:</strong> A CNAME makes a name an alias of exactly one other name. So you cannot have both a CNAME and another record type (A, MX, etc.) for the same label. Either the label is an alias (CNAME only) or it has "real" records (A, AAAA, MX, …). Many providers (e.g. Cloudflare, Route53) offer "CNAME flattening" or "ALIAS" so you can point <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> at another hostname without a bare CNAME at the zone apex — because at the apex, CNAME is technically problematic (RFC 1034).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 1: inspecting records with dig</h2></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> is the standard CLI tool for querying DNS. You give it a name and optionally a record type; it shows the response, TTLs, and which server answered.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Query A record for a well-known host (replace with your own domain to experiment)</h1>
dig +short api.github.com A
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>20.248.137.48
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Without <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">+short</code>, you get the full response with TTL and authority info:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dig api.github.com A
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output (trimmed):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>; <<>> DiG 9.18.24 <<>> api.github.com A
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12345
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1</p><p class="text-slate-300 leading-relaxed mb-4">;; QUESTION SECTION:
;api.github.com.			IN	A</p><p class="text-slate-300 leading-relaxed mb-4">;; ANSWER SECTION:
api.github.com.		43	IN	A	20.248.137.48</p><p class="text-slate-300 leading-relaxed mb-4">;; Query time: 12 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
;; WHEN: Wed Feb 12 03:31:00 UTC 2026
;; MSG SIZE  rcvd: 56
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">43</code> in the answer is the TTL in seconds — this record will be cached for 43 seconds by this resolver. Checking multiple types in one go:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">A and AAAA for dual-stack</h1>
dig +short api.github.com A
dig +short api.github.com AAAA</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">MX for mail</h1>
dig +short gmail.com MX</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">TXT (e.g. for domain verification)</h1>
dig +short github.com TXT
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Trace through CNAME chains by querying each name. If <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www.example.com</code> is a CNAME to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cdn.example.com</code>, query both to see the full path.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">TTL strategies: when to use what</h2></p><p class="text-slate-300 leading-relaxed mb-4">TTL is how long resolvers and clients are allowed to cache the answer. No single number fits every case.</p><p class="text-slate-300 leading-relaxed mb-4">| Situation | Typical TTL | Why |
|-----------|-------------|-----|
| Stable production endpoint (e.g. API apex) | 300–3600 (5 min–1 h) | Balance cache hit rate and ability to change IPs with notice |
| Pre-migration or failover | 60–300 (1–5 min) | Short window so after you flip the record, most clients see it within minutes |
| CDN or load-balanced pool | Often 300–600 | Provider may override or suggest; you want some caching but not days |
| Static marketing site | 3600–86400 (1–24 h) | Rarely changes; long TTL reduces load on DNS and speeds lookups |
| Staging or ephemeral envs | 60–300 | You'll change IPs or tear down; keep TTL low so fixes stick quickly |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cutover drill:</strong> Lower TTL to 60–300 at least one full TTL period <em>before</em> you change the record. Example: if current TTL is 3600, set it to 300, wait an hour (so old caches expire), then change the A/AAAA target. That way you avoid the "half the world still has the old IP" problem Raj hit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 2: tracing resolution and checking authority</h2></p><p class="text-slate-300 leading-relaxed mb-4">When "my domain doesn't resolve" or "I updated DNS but nothing changed", you want to see: (1) what your machine is actually getting, (2) what the authoritative server says, (3) whether there's a caching layer in between.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">1. What your default resolver returns (often your ISP or corporate DNS)</h1>
dig +short docs.github.com A</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">2. Query the authoritative nameservers directly (bypass local cache)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">First get the NS for the zone</h1>
dig +short github.com NS
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example NS output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dns1.p08.nsone.net.
dns2.p08.nsone.net.
dns3.p08.nsone.net.
dns4.p08.nsone.net.
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">3. Ask one of those NS directly for the A record</h1>
dig @dns1.p08.nsone.net docs.github.com A +short
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If the direct authority answer matches what you expect but your default resolver doesn't, the problem is caching (wait for TTL or flush local/recursive cache). If the authority answer is wrong, the bug is in your DNS config at the provider.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Probe from elsewhere:</strong> Your laptop might use a different resolver than production. Use a public resolver to simulate another view:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>dig @8.8.8.8 docs.github.com A +short
dig @1.1.1.1 docs.github.com A +short
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: low TTL vs high TTL</h2></p><p class="text-slate-300 leading-relaxed mb-4">| | Low TTL (e.g. 60–300 s) | High TTL (e.g. 3600–86400 s) |
|--|--------------------------|-------------------------------|
| <strong>Pros</strong> | Changes propagate quickly; fewer "stale IP" incidents after migrations | Fewer DNS queries, less load on auth servers, slightly faster repeat lookups from cache |
| <strong>Cons</strong> | More queries to your DNS provider; slightly more latency on cache miss | After a change, some users keep old IP until TTL expires |
| <strong>When to use</strong> | Before/after migrations, failover, or when the target IP changes often | Stable endpoints, static assets, when you rarely change the mapping |</p><p class="text-slate-300 leading-relaxed mb-4">We use 300 s for most production APIs and drop to 60 s the day before a planned cutover.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Common pitfalls</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>CNAME at the zone apex.</strong> The apex is the domain itself (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">example.com</code> with nothing in front). A CNAME at the apex can conflict with MX and other records and is not allowed by the standard. Use an A/AAAA record or a provider-specific "ALIAS" / "flattened" target that resolves to an IP on the provider's side.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Forgetting to lower TTL before a change.</strong> You change the A record; half the world still has the old IP for hours. Lower TTL first, wait at least one full old TTL, then switch.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Assuming your change is live everywhere.</strong> Browsers, OS, and recursive resolvers all cache. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> from your machine shows what <em>your</em> resolver returned; production might use a different resolver or a different region. Check from another network or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @8.8.8.8</code> / <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @1.1.1.1</code> to see another view.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>TXT record formatting.</strong> TXT can have multiple strings; some providers show them concatenated, others as separate strings. For SPF/DKIM, a single string is usual; watch for accidental line breaks or extra quotes that break validation.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>CNAME and "other record" on the same label.</strong> You cannot have both a CNAME and an A record for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www.example.com</code>. Pick one: either CNAME to another hostname or A/AAAA to IP(s).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">On a migration in 2025, we moved an API from one cloud region to another. We updated the A record to the new load balancer IP and ran smoke tests from our office — all green. Within an hour, we got reports of timeouts from users in South America and Southeast Asia. Our office resolver had picked up the new IP quickly; resolvers in those regions were still serving the old one (TTL had been 7200). We had to lower TTL to 60, wait 2 hours, then change the record again. Downtime for those users was about 90 minutes. We now keep TTL at 300 for that record and have a runbook: "Before any IP or host change: set TTL to 60, wait 2× previous TTL, then apply change."</p><p class="text-slate-300 leading-relaxed mb-4">Another incident: Aiko added a CNAME for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> pointing at a third-party API gateway. The provider required a TXT record on the same name for verification. The moment she added the TXT, DNS broke — their provider didn't allow CNAME + TXT on the same label (strict RFC behaviour). Fix was to use a subdomain like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">gateway.api.example.com</code> for the CNAME and keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api.example.com</code> as an A record or use the provider's "CNAME flattening" at the edge so the apex-like name wasn't a real CNAME in the zone. Lesson: check whether your DNS host allows CNAME plus other types; many do not.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit TTLs</strong> for any hostname that might change (APIs, LB targets). If they're above 600, document why; if you have a migration plan, include "lower TTL 1–2× current TTL before cutover".</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> from your machine and from a public resolver</strong> when debugging: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig +short <name> A</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @1.1.1.1 +short <name> A</code>. If they differ, it's cache or resolver-specific.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Avoid CNAME at the zone apex.</strong> Use A/AAAA or your provider's ALIAS/flattening for the root domain; use CNAME for subdomains (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">www</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api</code>) when you want to point at another hostname.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Before adding a CNAME, check</strong> whether that label already has (or will need) MX, TXT, or A. If it does, use a different subdomain or an A record.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Keep a one-line runbook</strong> for DNS changes: "TTL ≤ 300 for mutable targets; before cutover: set TTL to 60, wait 2× old TTL, then change record; verify with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig @8.8.8.8 <name> A</code>."</li></p><p class="text-slate-300 leading-relaxed mb-4">Once you're used to reading <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dig</code> output and thinking in TTLs, most DNS issues become quick to isolate — and you avoid the 3 AM "why is Asia still hitting the old server?" call.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
