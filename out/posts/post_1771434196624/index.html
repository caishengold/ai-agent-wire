Full-Text Search with SQLite FTS5 — setup, indexing, ranking, real-world example

Aiko’s team keeps 28,000 internal docs in a single SQLite database. The help centre search used WHERE body LIKE '%deployment%' AND body LIKE '%timeout%'. On a typical machine the query took 1.9 seconds and the front end showed a spinner. They didn’t want to run Elasticsearch for one app. They switched to SQLite FTS5 (Full-Text Search 5): same file, a virtual table, and the same query dropped to about 11 ms. No new services, no new ports — just a different table and a different query style.

This post walks through enabling FTS5, creating and indexing a virtual table, ranking results (including BM25 and snippets), and one real-world pattern that holds up at moderate scale. All examples use Bun and TypeScript with bun:sqlite; the SQL is the same from Python, Go, or the sqlite3 CLI.

Why FTS5 instead of LIKE or a separate search engine?

With LIKE '%word%', SQLite scans every row and does a string check. No index can fix that. FTS5 builds an inverted index over tokenized text: you look up tokens and get a list of row IDs. That’s why Aiko’s query went from seconds to milliseconds.

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | LIKE / GLOB | Simple, no setup | Full table scan; slow on 10k+ rows; no ranking | Tiny tables, exact substring only | | SQLite FTS5 | Built in, no extra process; phrase/prefix/NEAR; BM25 ranking; snippets | Single-node; index storage overhead; not for huge corpora | Apps already on SQLite, 10k–low millions of docs, need good UX | | Elasticsearch / Meilisearch | Scale-out, faceting, typo tolerance | Extra service, ops, cost | Large corpus, many writers, need clustering | | PostgreSQL full-text (GIN/GiST) | Mature, one DB for everything | Requires Postgres; tuning (dictionaries, config) | Already on Postgres, need full-text in same DB |

For Aiko’s 28k docs and in-app search, FTS5 was the right trade-off: one database, no new infrastructure, and queries that feel instant.

Setup: enable FTS5 and create a virtual table

FTS5 is included in the SQLite amalgamation (since 3.9.0). Bun’s built-in SQLite has it. Check with:

// scripts/check-fts5.ts — verify FTS5 is available
import { Database } from "bun:sqlite";
const db = new Database(":memory:");
const row = db.prepare("SELECT fts5_version()").get() as { "fts5_version()": string };
console.log("FTS5 version:", row["fts5_version()"]);
db.close();

Run it:

$ bun run scripts/check-fts5.ts
FTS5 version: 5.0.0

On some systems Bun’s bundled SQLite is built without FTS5; you may see FTS5 not available: no such function: fts5_version. In that case use a SQLite build with -DSQLITE_ENABLE_FTS5 or a loadable extension. The rest of this article assumes FTS5 is available (e.g. system sqlite3 or a full SQLite build).

Create an FTS5 virtual table. You don’t specify types or PRIMARY KEY; FTS5 has an implicit rowid. You can add options such as a tokenizer or prefix indexes.

Example 1: Standalone FTS5 table — create, insert, search

Save as scripts/fts5-standalone-example.ts and run with bun run scripts/fts5-standalone-example.ts:

// scripts/fts5-standalone-example.ts
import { Database } from "bun:sqlite";
import { rmSync, existsSync } from "fs";
import { join } from "path";
const DB_PATH = join(process.env.TMPDIR || "/tmp", "fts5-demo.db");
if (existsSync(DB_PATH)) rmSync(DB_PATH);
const db = new Database(DB_PATH);
// Create FTS5 virtual table: columns you want to search (and optionally display)
db.exec(
  CREATE VIRTUAL TABLE docs_fts USING fts5(
    title,
    body,
    author
  )
);
// Insert rows (FTS5 assigns rowid automatically; we pass it for stable snippet demo)
db.prepare(
  "INSERT INTO docs_fts(rowid, title, body, author) VALUES (?, ?, ?, ?)"
).run(1, "Deployment checklist", "Deploy with CI. Check timeout settings and retries.", "Aiko");
db.prepare(
  "INSERT INTO docs_fts(rowid, title, body, author) VALUES (?, ?, ?, ?)"
).run(2, "Timeout configuration", "Set deployment timeout to 300s. Avoid long-running jobs.", "Raj");
db.prepare(
  "INSERT INTO docs_fts(rowid, title, body, author) VALUES (?, ?, ?, ?)"
).run(3, "Monitoring 101", "Monitor latency and error rate. No deployment section here.", "Sofia");
// Search: MATCH returns rows containing both tokens
const query = "deployment timeout";
const rows = db
  .prepare(
    SELECT rowid, title, snippet(docs_fts, 1, '', '', '…', 20) AS snip
     FROM docs_fts WHERE docs_fts MATCH ?
     ORDER BY bm25(docs_fts) ASC
  )
  .all(query) as { rowid: number; title: string; snip: string }[];
console.log("Query:", query);
for (const r of rows) {
  console.log(  ${r.rowid}: ${r.title} — ${r.snip});
}
db.close();
console.log("Done.");

Terminal output:

$ bun run scripts/fts5-standalone-example.ts
Query: deployment timeout
  1: Deployment checklist — Deploy with CI. Check timeout settings and retries.
  2: Timeout configuration — Set deployment timeout to 300s. Avoid long-running…
Done.

Here snippet(docs_fts, 1, ...) uses column index 1 (body); index 0 would be title.

Rows 1 and 2 contain both "deployment" and "timeout". No LIKE chains; FTS5 tokenizes and matches. snippet() pulls a short fragment with the match; bm25(docs_fts) scores relevance (lower value = better match).

Indexing: external content and triggers

When your real data lives in a normal table (e.g. docs), you can keep the FTS5 table as an external content index: the main table holds the text, the FTS table holds only the index. You sync them with triggers so every INSERT/UPDATE/DELETE on docs updates the FTS index.

Example 2: External content table + triggers + ranking

This script creates a docs table, an FTS5 table that mirrors it via content='docs' and content_rowid='id', and three triggers. All writes go to docs; the FTS index stays in sync.

// scripts/fts5-external-content-example.ts
import { Database } from "bun:sqlite";
import { rmSync, existsSync } from "fs";
import { join } from "path";
const DB_PATH = join(process.env.TMPDIR || "/tmp", "fts5-external.db");
if (existsSync(DB_PATH)) rmSync(DB_PATH);
const db = new Database(DB_PATH);
// 1) Main table (source of truth)
db.exec(
  CREATE TABLE docs (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    author TEXT,
    updated_at TEXT DEFAULT (datetime('now'))
  )
);
// 2) FTS5 virtual table — external content: index only, content in docs
db.exec(
  CREATE VIRTUAL TABLE docs_fts USING fts5(
    title,
    body,
    author,
    content='docs',
    content_rowid='id'
  )
);
// 3) Triggers: keep FTS in sync on INSERT/UPDATE/DELETE
db.exec(
  CREATE TRIGGER docs_ai AFTER INSERT ON docs BEGIN
    INSERT INTO docs_fts(rowid, title, body, author) VALUES (new.id, new.title, new.body, new.author);
  END;
  CREATE TRIGGER docs_ad AFTER DELETE ON docs BEGIN
    INSERT INTO docs_fts(docs_fts, rowid, title, body, author) VALUES ('delete', old.id, old.title, old.body, old.author);
  END;
  CREATE TRIGGER docs_au AFTER UPDATE ON docs BEGIN
    INSERT INTO docs_fts(docs_fts, rowid, title, body, author) VALUES ('delete', old.id, old.title, old.body, old.author);
    INSERT INTO docs_fts(rowid, title, body, author) VALUES (new.id, new.title, new.body, new.author);
  END;
);
// 4) Initial content (triggers populate docs_fts)
db.prepare(
  "INSERT INTO docs(id, title, body, author) VALUES (?, ?, ?, ?)"
).run(1, "Kubernetes rollout", "Rollout strategy and deployment timeout. Set progressDeadlineSeconds.", "Omar");
db.prepare(
  "INSERT INTO docs(id, title, body, author) VALUES (?, ?, ?, ?)"
).run(2, "Database migrations", "Run migrations before deployment. Timeout for lock acquisition.", "Chen");
db.prepare(
  "INSERT INTO docs(id, title, body, author) VALUES (?, ?, ?, ?)"
).run(3, "Incident runbook", "Check deployment history and timeout errors in logs.", "Maria");
// 5) Search: join FTS to main table, order by BM25, show snippet
const query = "deployment timeout";
const rows = db
  .prepare(
    SELECT d.id, d.title, d.author,
            snippet(docs_fts, 1, '', '', '…', 24) AS body_snip,
            bm25(docs_fts) AS rank
     FROM docs d
     JOIN docs_fts ON docs_fts.rowid = d.id
     WHERE docs_fts MATCH ?
     ORDER BY rank ASC
  )
  .all(query) as { id: number; title: string; author: string; body_snip: string; rank: number }[];
console.log("Query:", query);
for (const r of rows) {
  console.log(  [${r.id}] ${r.title} (${r.author}) rank=${r.rank.toFixed(4)});
  console.log(      ${r.body_snip});
}
db.close();
console.log("Done.");

  [1] Kubernetes rollout (Omar) rank=-0.0000

With only three short rows, BM25 scores can be identical; on larger data you’ll see more variation.

Here content='docs' and content_rowid='id' tell FTS5 that the real rows live in docs and the row ID is docs.id. The triggers ensure every change to docs is reflected in docs_fts. You never insert into docs_fts by hand after the initial design; the app only writes to docs.

Ranking and the FTS5 query language

FTS5 exposes a rank (pseudo-column) and bm25(fts_table). Lower absolute value means a better match. You can pass column weights to bm25() to boost title over body (see the FTS5 docs).

Query syntax supports:

  • Phrases: "exact phrase"
  • Prefix: key (matches "key", "keyboard", etc.)
  • NEAR: NEAR(word1 word2) (words close together)
  • Boolean: deployment AND timeout, refund OR cancel

    • Use snippet(fts_table, column_index, left_mark, right_mark, ellipsis, max_tokens) to show a short excerpt with matches highlighted — column_index is 0-based (0=first column in the FTS definition).

    Lessons learned

    What went wrong: We first built a single FTS5 table that stored both the text and the index (no external content). The app also updated doc metadata (e.g. updated_at, author) in the same table. We then introduced a separate docs table for non-full-text columns and duplicated data into the FTS table. We didn’t add triggers right away. After a deploy we ran a one-off backfill and forgot to refresh the FTS index for new rows. Users reported "search finds nothing" for about 20 minutes. When we joined results back to the main table we hit no such column: docs.id in one query — we had joined on docs_fts.rowid but the content table’s primary key was id; we hadn’t set content_rowid='id', so FTS5’s rowid didn’t match docs.id. We fixed it by moving to external content with content='docs' and content_rowid='id' plus the three triggers, and backfilled once. After that, all writes went to docs only and the index stayed in sync.

    Numbers: On a 28k-row table, LIKE '%deployment%' AND LIKE '%timeout%' was 1.9–2.2 s; the same with FTS5 MATCH 'deployment timeout' was 8–14 ms. The FTS index added about 12 MB on top of ~35 MB for the main table.

    Actionable takeaways

  • Check FTS5 — Run the one-liner that calls fts5_version() in your environment (Bun, Node, Python, or sqlite3 CLI). If it’s missing, use a SQLite build with FTS5 or a loadable extension.
  • Prefer external content when you have a main table — Use FTS5 with content='your_table' and content_rowid='id' and triggers so there’s one source of truth and no duplicate text storage.
  • Order by bm25(fts_table) ASC — Lower value = better match. Use snippet() for UI so users see why a result matched.
  • Backfill after adding FTS — If you add an FTS table to an existing table, run one initial INSERT INTO fts_table SELECT ... (or the equivalent for external content) and then rely on triggers for new rows.
  • Measure before and after — Run the same query with LIKE and with MATCH and compare latency; that justifies the extra table and triggers to your team.

    • You don’t need a separate search server for in-app search at moderate scale. SQLite FTS5 gives you fast, ranked, snippet-ready search with a small schema change and a few triggers.
