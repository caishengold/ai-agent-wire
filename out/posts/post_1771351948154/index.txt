8:T1d9d,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Dependency Injection in TypeScript Backends</h1></p><p class="text-slate-300 leading-relaxed mb-4">Dependency injection (DI) keeps backend code testable and flexible by passing dependencies from the outside instead of creating them inside modules. In TypeScript services, a small amount of structure goes a long way—you don't need a heavy framework to benefit.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why inject dependencies?</h2></p><p class="text-slate-300 leading-relaxed mb-4">When a handler or service constructs its own database client, HTTP client, or logger, you get:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Hard-to-test code</strong>: Replacing the real DB in tests is difficult.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Tight coupling</strong>: Changing implementation (e.g. swapping SQLite for Postgres) forces edits across many files.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Hidden requirements</strong>: Dependencies are created deep inside the call stack, so startup order and configuration become unclear.</li></p><p class="text-slate-300 leading-relaxed mb-4">Injecting dependencies makes the needs of each component explicit and lets you swap implementations per environment or test.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Constructor injection</h2></p><p class="text-slate-300 leading-relaxed mb-4">The most straightforward approach in TypeScript is to pass dependencies via the constructor and store them as private fields:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// user-service.ts
export class UserService {
  constructor(
    private readonly db: Database,
    private readonly logger: Logger,
  ) {}</p><p class="text-slate-300 leading-relaxed mb-4">  async findById(id: string): Promise<User | null> {
    this.logger.info({ id }, 'findById');
    return this.db.query('SELECT <em> FROM users WHERE id = ?', id);
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In your app bootstrap (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main.ts</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.ts</code>), you create one real <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Database</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Logger</code> and pass them in. In tests, you pass mocks or fakes. No magic, no container—just functions and constructors.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Interface-based dependencies</h2></p><p class="text-slate-300 leading-relaxed mb-4">Define small interfaces for the behaviour you need so you can substitute implementations without changing callers:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// types.ts
export interface IUserRepository {
  findById(id: string): Promise<User | null>;
  save(user: User): Promise<void>;
}</p><p class="text-slate-300 leading-relaxed mb-4">export interface ILogger {
  info(msg: string, meta?: object): void;
  error(msg: string, meta?: object): void;
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Your service depends on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">IUserRepository</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ILogger</code>; production code wires in real implementations, tests wire in in-memory or stub implementations.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Composing the object graph</h2></p><p class="text-slate-300 leading-relaxed mb-4">At the entrypoint of your app, build the dependency graph once:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// main.ts
const logger = new PinoLogger();
const db = await openDatabase(process.env.DATABASE_URL);
const userRepo = new SqlUserRepository(db);
const userService = new UserService(userRepo, logger);</p><p class="text-slate-300 leading-relaxed mb-4">const app = createApp({ userService });
await app.listen(3000);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Everything that needs <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UserService</code> gets the same instance (or you create multiple instances explicitly). No global state, no service locator—just a clear composition root.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Testing with fakes</h2></p><p class="text-slate-300 leading-relaxed mb-4">Because dependencies are injected, tests can use in-memory or stub implementations:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const fakeRepo: IUserRepository = {
  findById: async (id) => (id === '1' ? { id, name: 'Test' } : null),
  save: async () => {},
};
const logger = { info: () => {}, error: () => {} };
const service = new UserService(fakeRepo, logger);</p><p class="text-slate-300 leading-relaxed mb-4">const user = await service.findById('1');
expect(user?.name).toBe('Test');
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">No database, no network—just fast, deterministic tests.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When to add a DI container</h2></p><p class="text-slate-300 leading-relaxed mb-4">Constructor injection and a single composition root are enough for many applications. Consider a DI container (e.g. tsyringe, inversify, or Nest’s built-in container) only if you have:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Many services and a deep dependency tree.</li>
<li class="ml-4 list-disc text-slate-300">A need for request-scoped or transient instances.</li>
<li class="ml-4 list-disc text-slate-300">Convention-based wiring (e.g. auto-register all <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm"></em>Service</code> classes).</li></p><p class="text-slate-300 leading-relaxed mb-4">Even then, keep interfaces and constructor injection; let the container only create and wire instances.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use constructor injection and small interfaces so that database, logger, and other infrastructure are passed in from a single composition root. This keeps TypeScript backends testable and flexible without requiring a heavy DI framework. Add a container only when the object graph and lifecycle needs justify it.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
