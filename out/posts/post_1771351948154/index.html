Dependency Injection in TypeScript Backends

Dependency injection (DI) keeps backend code testable and flexible by passing dependencies from the outside instead of creating them inside modules. In TypeScript services, a small amount of structure goes a long way—you don't need a heavy framework to benefit.

Why inject dependencies?

When a handler or service constructs its own database client, HTTP client, or logger, you get:

  • Hard-to-test code: Replacing the real DB in tests is difficult.
  • Tight coupling: Changing implementation (e.g. swapping SQLite for Postgres) forces edits across many files.
  • Hidden requirements: Dependencies are created deep inside the call stack, so startup order and configuration become unclear.

    • Injecting dependencies makes the needs of each component explicit and lets you swap implementations per environment or test.

    Constructor injection

    The most straightforward approach in TypeScript is to pass dependencies via the constructor and store them as private fields:

    // user-service.ts
export class UserService {
  constructor(
    private readonly db: Database,
    private readonly logger: Logger,
  ) {}
      async findById(id: string): Promise {
    this.logger.info({ id }, 'findById');
    return this.db.query('SELECT  FROM users WHERE id = ?', id);
  }
}

    In your app bootstrap (e.g. main.ts or server.ts), you create one real Database and Logger and pass them in. In tests, you pass mocks or fakes. No magic, no container—just functions and constructors.

    Interface-based dependencies

    Define small interfaces for the behaviour you need so you can substitute implementations without changing callers:

    // types.ts
export interface IUserRepository {
  findById(id: string): Promise;
  save(user: User): Promise;
}
    export interface ILogger {
  info(msg: string, meta?: object): void;
  error(msg: string, meta?: object): void;
}

    Your service depends on IUserRepository and ILogger; production code wires in real implementations, tests wire in in-memory or stub implementations.

    Composing the object graph

    At the entrypoint of your app, build the dependency graph once:

    // main.ts
const logger = new PinoLogger();
const db = await openDatabase(process.env.DATABASE_URL);
const userRepo = new SqlUserRepository(db);
const userService = new UserService(userRepo, logger);
    const app = createApp({ userService });
await app.listen(3000);

    Everything that needs UserService gets the same instance (or you create multiple instances explicitly). No global state, no service locator—just a clear composition root.

    Testing with fakes

    Because dependencies are injected, tests can use in-memory or stub implementations:

    const fakeRepo: IUserRepository = {
  findById: async (id) => (id === '1' ? { id, name: 'Test' } : null),
  save: async () => {},
};
const logger = { info: () => {}, error: () => {} };
const service = new UserService(fakeRepo, logger);
    const user = await service.findById('1');
expect(user?.name).toBe('Test');

    No database, no network—just fast, deterministic tests.

    When to add a DI container

    Constructor injection and a single composition root are enough for many applications. Consider a DI container (e.g. tsyringe, inversify, or Nest’s built-in container) only if you have:

  • Many services and a deep dependency tree.
  • A need for request-scoped or transient instances.
  • Convention-based wiring (e.g. auto-register all Service classes).

    • Even then, keep interfaces and constructor injection; let the container only create and wire instances.

    Summary

    Use constructor injection and small interfaces so that database, logger, and other infrastructure are passed in from a single composition root. This keeps TypeScript backends testable and flexible without requiring a heavy DI framework. Add a container only when the object graph and lifecycle needs justify it.
