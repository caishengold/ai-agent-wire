8:T5e96,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Monorepo vs polyrepo: tooling, trade-offs, and a migration guide</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team had 12 repositories: three Next.js apps, a shared UI library, an API gateway, and seven small services. A single feature often touched four repos. Versioning the shared library meant publishing to npm, bumping the dependency in every consumer, and hoping nobody merged in between. One Friday they shipped a “patch” to the UI package; by Monday they’d found that the API gateway was still on the previous minor and type definitions had drifted. They spent two days untangling. This post is about when a monorepo (one repo, many packages) makes sense versus staying with many repos (polyrepo), which tools to use — Turborepo, Nx, Bun workspaces — and how to move without setting the place on fire.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Teams with multiple apps or packages that share code, or anyone weighing “we should put everything in one repo” against “we should split it out.”</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the choice matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Polyrepo means one Git repository per project. Dependencies between projects are versioned and published (e.g. npm packages). You get clear boundaries and independent release cycles, but cross-repo changes are painful: multiple PRs, version skew, and “which commit of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@acme/ui</code> does staging use?”</p><p class="text-slate-300 leading-relaxed mb-4">A monorepo holds multiple packages (or apps) in one tree. Dependencies between them are usually <strong>workspace</strong> references (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"@acme/ui": "workspace:<em>"</code>). You get atomic commits across the whole stack and a single source of truth, but you need tooling to build, test, and deploy the right bits in the right order.</p><p class="text-slate-300 leading-relaxed mb-4">The real decision is rarely “mono forever” or “poly forever.” It’s “what do we need </em>right now<em> for our team size, release cadence, and shared code?” Tooling narrows the pain: good monorepo tooling makes builds and caching predictable; without it, CI and local dev slow down fast.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Tooling overview: Turborepo, Nx, Bun workspaces</h2></p><p class="text-slate-300 leading-relaxed mb-4">Three common options for JavaScript/TypeScript monorepos:</p><p class="text-slate-300 leading-relaxed mb-4">| Tool | What it does | Best for | Cost / complexity |
|------|----------------|----------|--------------------|
| <strong>Turborepo</strong> | Task runner + remote cache. Runs tasks (build, test, lint) in dependency order with incremental builds. | Teams already on npm/pnpm/yarn; want simple config and Vercel-style caching. | Low. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">turbo.json</code> + pipeline. |
| <strong>Nx</strong> | Monorepo orchestration + code generation, dependency graph, affected commands, optional distributed cache. | Larger orgs; need “only run what changed” and plugins (Next, Nest, etc.). | Medium–high. More concepts (projects, targets, plugins). |
| <strong>Bun workspaces</strong> | Built-in workspace resolution in Bun. No separate task runner; you script pipelines or add Turbo/Nx on top. | Bun-first stacks; minimal setup; you bring your own orchestration. | Low for workspaces alone; add Turbo/Nx if you want caching/affected. |</p><p class="text-slate-300 leading-relaxed mb-4">There’s no single “best.” Turborepo is the lightest path to “run tasks in order and cache them.” Nx adds structure and scale. Bun workspaces give you dependency resolution without locking you into a runner.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: monorepo vs polyrepo</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Dimension | Monorepo | Polyrepo |
|-----------|----------|----------|
| <strong>Cross-project changes</strong> | One PR, one commit. Refactors span apps and libs atomically. | Multiple PRs, version bumps, coordination. Risk of version skew. |
| <strong>CI</strong> | One repo to clone; need smart task scheduling (affected, cache). Can get slow if not tuned. | Per-repo CI; simpler but duplicated config; cross-repo pipelines are custom. |
| <strong>Access control</strong> | Coarse (repo-level). Need CODEOWNERS or path rules for finer control. | Fine (repo = boundary). Good for strict ownership. |
| <strong>Onboarding</strong> | Clone once; see everything. Can be overwhelming. | Clone only what you need; may miss how pieces fit. |
| <strong>Tooling</strong> | Turborepo, Nx, Bun workspaces, Lerna, etc. | Standard Git + package publish; no monorepo layer. |
| <strong>When it fits</strong> | Multiple apps/packages with heavy shared code; small–medium team; want atomic refactors. | Independent teams/services; strict ownership; different release cadences. |</p><p class="text-slate-300 leading-relaxed mb-4">Aiko’s team moved to a monorepo when they had two apps and one shared lib; the tipping point was “every UI change required a publish and three PRs.” Omar’s team stayed polyrepo for six microservices owned by different squads; they wanted deploy and ownership boundaries. Your context decides.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 1: Turborepo with pnpm workspaces</h2></p><p class="text-slate-300 leading-relaxed mb-4">A minimal Turborepo setup: one app (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apps/web</code>) and one shared package (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/utils</code>). The app depends on the package; Turbo runs <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">build</code> in dependency order and caches outputs.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. Root <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">package.json</code> (pnpm workspaces + Turbo):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "acme-monorepo",
  "private": true,
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev"
  },
  "devDependencies": {
    "turbo": "^2.3.0"
  },
  "packageManager": "pnpm@9.14.2"
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. Root <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">pnpm-workspace.yaml</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>packages:
  - "apps/</em>"
  - "packages/<em>"
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. Root <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">turbo.json</code> (pipeline: build depends on nothing; tasks run in order):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/<strong>", ".next/</strong>"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>4. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/utils/package.json</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "@acme/utils",
  "version": "0.0.0",
  "main": "./dist/index.js",
  "scripts": {
    "build": "echo 'Building utils' && mkdir -p dist && echo 'export const add = (a, b) => a + b;' > dist/index.js"
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>5. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apps/web/package.json</code> (depends on workspace package):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "web",
  "private": true,
  "scripts": {
    "build": "echo 'Building web (uses @acme/utils)' && mkdir -p dist"
  },
  "dependencies": {
    "@acme/utils": "workspace:</em>"
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">From repo root:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>pnpm install
pnpm build
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example terminal output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ pnpm build
• Packages in scope: web, @acme/utils
• Running build in 2 tasks
@acme/utils:build: cache miss
@acme/utils:build: Building utils
web:build: cache miss
web:build: Building web (uses @acme/utils)
Tasks: 2 successful, 2 total
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Second run: both tasks get cache hits if nothing changed. You get dependency-ordered builds and incremental cache without writing a custom runner.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 2: Bun workspaces (no Turbo)</h2></p><p class="text-slate-300 leading-relaxed mb-4">Bun understands workspaces natively. You don’t need Turborepo for resolution; you only need it if you want cached pipeline tasks. Here’s a Bun-only setup.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. Root <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">package.json</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "acme-bun-workspace",
  "private": true,
  "workspaces": ["apps/<em>", "packages/</em>"]
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/logger/package.json</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "@acme/logger",
  "version": "1.0.0",
  "main": "index.ts"
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/logger/index.ts</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Simple logger used by apps in the workspace
export function log(level: string, msg: string): void {
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[${level}] ${msg}</code>);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>4. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apps/cli/package.json</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "name": "cli",
  "private": true,
  "dependencies": {
    "@acme/logger": "workspace:<em>"
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>5. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apps/cli/run.ts</code>:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { log } from "@acme/logger";
log("INFO", "Running from Bun workspace");
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">From repo root:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>bun install
bun run apps/cli/run.ts
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example terminal output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run apps/cli/run.ts
[INFO] Running from Bun workspace
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Bun resolves <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@acme/logger</code> to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/logger</code> without publishing. For “run only affected” or remote cache, you’d add Turbo (or Nx) on top and keep the same workspace layout.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Migration guide: polyrepo → monorepo</h2></p><p class="text-slate-300 leading-relaxed mb-4">Moving existing repos into one tree is the riskiest part. Doing it in stages reduces breakage.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Phase 1 — Prepare</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Pick the tool (Turborepo, Nx, or Bun workspaces + optional runner).</li>
<li class="ml-4 list-disc text-slate-300">Create a new repo (or choose the “main” one). Layout: e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apps/</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">packages/</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">tools/</code>.</li>
<li class="ml-4 list-disc text-slate-300">Document current build, test, and deploy steps for each project. You’ll replicate them inside the monorepo.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Phase 2 — Move one consumer and one shared package</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Don’t move everything at once. Example: move <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">shared-ui</code> and one app that uses it.</li>
<li class="ml-4 list-disc text-slate-300">Use Git history: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">git subtree add</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">git filter-repo</code> to bring in history, or start fresh and keep old repos read-only for archaeology.</li>
<li class="ml-4 list-disc text-slate-300">Replace published dependency with workspace dependency: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"@acme/ui": "workspace:</em>"</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"workspace:^"</code> if you need semver-like behavior).</li>
<li class="ml-4 list-disc text-slate-300">Wire the tool: add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">turbo.json</code> (or Nx config) so <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">build</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">test</code> run in order. Confirm CI runs the same commands.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Phase 3 — Validate and cut over</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Run full build and test in the monorepo. Fix path and config issues (tsconfig paths, Jest roots, etc.).</li>
<li class="ml-4 list-disc text-slate-300">Switch CI to the monorepo. Point deploys at the right app(s). Often “build from root with Turbo” replaces “build from app dir.”</li>
<li class="ml-4 list-disc text-slate-300">Retire or archive the old repos. Keep them read-only so links and blame still work if needed.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Phase 4 — Migrate the rest</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Move remaining apps and packages one or two at a time. Each time: add to workspace, replace deps with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">workspace:<em></code>, run pipeline, fix breakage.</li>
<li class="ml-4 list-disc text-slate-300">Standardize scripts: e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">turbo run build --filter=./apps/web</code> for app-specific builds.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotchas</strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Path and config:</strong> TypeScript path aliases, Jest <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">moduleNameMapper</code>, and bundler configs often assume a single package. Update them to workspace-relative paths or package names.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Lockfile:</strong> Use one lockfile at root (pnpm/yarn/Bun). Delete nested <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node_modules</code> and lockfiles after moving.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Publishing:</strong> If you still publish some packages to npm, use changesets or similar so version bumps and changelogs stay consistent.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">We’ve seen a few concrete failures and surprises:</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Cache poisoning:</strong> A team had Turborepo’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">outputs</code> set to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">["dist/<strong>"]</code>. A bug in their build script wrote a partial <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dist/</code> and then exited 0. Turbo cached that. Clean builds passed; cached builds failed in CI until they cleared the cache and fixed the script. </strong>Lesson:<strong> Cache only real artifacts; ensure failing builds don’t exit 0.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Nx and “affected” on the wrong base:<strong> Another team ran <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">nx affected:test --base=main</code> in CI. Their main branch was rarely updated; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">main</code> was weeks behind. Almost every PR was “affected,” so they ran the full test suite every time. </strong>Lesson:<strong> Use the actual merge base (e.g. the commit you’re merging into) for affected; or use a recent enough baseline so “affected” is meaningful.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Bun workspaces and hoisting:<strong> In one setup, a nested dependency required a different version than the root. Bun’s default hoisting put one version at root; a package deep in the tree expected another and broke at runtime. </strong>Lesson:<strong> With Bun (or any workspace), if you see “module not found” or wrong version at runtime, check where the dependency is resolved (root vs package) and adjust <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">resolutions</code> or package-specific deps.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Big-bang merge:<strong> A team merged six repos in one weekend with no automated tests per package. Monday: broken builds, unclear ownership. </strong>Lesson:<strong> Migrate incrementally (one or two packages at a time) and keep each step green.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary and what to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"></strong>Monorepo<strong> gives atomic cross-project changes and a single source of truth; </strong>polyrepo<strong> gives clear ownership and independent releases. Your shared-code and team structure should drive the choice.</li>
<li class="ml-4 list-disc text-slate-300"></strong>Turborepo<strong> is the lightest way to get ordered, cached tasks; </strong>Nx<strong> adds structure and “affected” at scale; </strong>Bun workspaces<strong> give workspace resolution with minimal config — add Turbo or Nx if you need caching/affected.</li>
<li class="ml-4 list-disc text-slate-300">Migration works best in small steps: one shared package + one consumer first, then expand.</li></p><p class="text-slate-300 leading-relaxed mb-4"></strong>Concrete next steps you can do today:<strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Map dependencies:<strong> List which repos or packages depend on which. Draw a small dependency graph (even on paper). That tells you the first candidate to move (e.g. the lib everything else uses).</li>
<li class="ml-4 list-decimal text-slate-300"></strong>Try one tool in a branch:<strong> In a throwaway repo, add Turborepo or Bun workspaces with two packages and one app. Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">build</code> and see how it feels. No need to migrate production yet.</li>
<li class="ml-4 list-decimal text-slate-300"></strong>Lock CI and deploy:<strong> Document exactly how each app is built and deployed today. When you move, replicate that in the monorepo so behavior doesn’t change.</li>
<li class="ml-4 list-decimal text-slate-300"></strong>Decide on history:<strong> Choose whether you’ll preserve Git history (subtree/filter-repo) or start fresh. If you start fresh, keep old repos read-only and link from the monorepo README.</li>
<li class="ml-4 list-decimal text-slate-300"></strong>Migrate one pair:</em><em> Move one shared package and one app; switch to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">workspace:</em></code> and get CI green. Use that as the template for the rest.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once that first pair is in and green, the rest is repetition and patience.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
