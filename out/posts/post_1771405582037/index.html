Monorepo vs polyrepo: tooling, trade-offs, and a migration guide

Sofia’s team had 12 repositories: three Next.js apps, a shared UI library, an API gateway, and seven small services. A single feature often touched four repos. Versioning the shared library meant publishing to npm, bumping the dependency in every consumer, and hoping nobody merged in between. One Friday they shipped a “patch” to the UI package; by Monday they’d found that the API gateway was still on the previous minor and type definitions had drifted. They spent two days untangling. This post is about when a monorepo (one repo, many packages) makes sense versus staying with many repos (polyrepo), which tools to use — Turborepo, Nx, Bun workspaces — and how to move without setting the place on fire.

Who this is for: Teams with multiple apps or packages that share code, or anyone weighing “we should put everything in one repo” against “we should split it out.”

Why the choice matters

Polyrepo means one Git repository per project. Dependencies between projects are versioned and published (e.g. npm packages). You get clear boundaries and independent release cycles, but cross-repo changes are painful: multiple PRs, version skew, and “which commit of @acme/ui does staging use?”

A monorepo holds multiple packages (or apps) in one tree. Dependencies between them are usually workspace references (e.g. "@acme/ui": "workspace:"). You get atomic commits across the whole stack and a single source of truth, but you need tooling to build, test, and deploy the right bits in the right order.

The real decision is rarely “mono forever” or “poly forever.” It’s “what do we need right now for our team size, release cadence, and shared code?” Tooling narrows the pain: good monorepo tooling makes builds and caching predictable; without it, CI and local dev slow down fast.

Tooling overview: Turborepo, Nx, Bun workspaces

Three common options for JavaScript/TypeScript monorepos:

| Tool | What it does | Best for | Cost / complexity | |------|----------------|----------|--------------------| | Turborepo | Task runner + remote cache. Runs tasks (build, test, lint) in dependency order with incremental builds. | Teams already on npm/pnpm/yarn; want simple config and Vercel-style caching. | Low. turbo.json + pipeline. | | Nx | Monorepo orchestration + code generation, dependency graph, affected commands, optional distributed cache. | Larger orgs; need “only run what changed” and plugins (Next, Nest, etc.). | Medium–high. More concepts (projects, targets, plugins). | | Bun workspaces | Built-in workspace resolution in Bun. No separate task runner; you script pipelines or add Turbo/Nx on top. | Bun-first stacks; minimal setup; you bring your own orchestration. | Low for workspaces alone; add Turbo/Nx if you want caching/affected. |

There’s no single “best.” Turborepo is the lightest path to “run tasks in order and cache them.” Nx adds structure and scale. Bun workspaces give you dependency resolution without locking you into a runner.

Comparison: monorepo vs polyrepo

| Dimension | Monorepo | Polyrepo | |-----------|----------|----------| | Cross-project changes | One PR, one commit. Refactors span apps and libs atomically. | Multiple PRs, version bumps, coordination. Risk of version skew. | | CI | One repo to clone; need smart task scheduling (affected, cache). Can get slow if not tuned. | Per-repo CI; simpler but duplicated config; cross-repo pipelines are custom. | | Access control | Coarse (repo-level). Need CODEOWNERS or path rules for finer control. | Fine (repo = boundary). Good for strict ownership. | | Onboarding | Clone once; see everything. Can be overwhelming. | Clone only what you need; may miss how pieces fit. | | Tooling | Turborepo, Nx, Bun workspaces, Lerna, etc. | Standard Git + package publish; no monorepo layer. | | When it fits | Multiple apps/packages with heavy shared code; small–medium team; want atomic refactors. | Independent teams/services; strict ownership; different release cadences. |

Aiko’s team moved to a monorepo when they had two apps and one shared lib; the tipping point was “every UI change required a publish and three PRs.” Omar’s team stayed polyrepo for six microservices owned by different squads; they wanted deploy and ownership boundaries. Your context decides.

Runnable example 1: Turborepo with pnpm workspaces

A minimal Turborepo setup: one app (apps/web) and one shared package (packages/utils). The app depends on the package; Turbo runs build in dependency order and caches outputs.

1. Root package.json (pnpm workspaces + Turbo):

{
  "name": "acme-monorepo",
  "private": true,
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev"
  },
  "devDependencies": {
    "turbo": "^2.3.0"
  },
  "packageManager": "pnpm@9.14.2"
}

2. Root pnpm-workspace.yaml:

packages:
  - "apps/"
  - "packages/"

3. Root turbo.json (pipeline: build depends on nothing; tasks run in order):

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/", ".next/"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

4. packages/utils/package.json:

{
  "name": "@acme/utils",
  "version": "0.0.0",
  "main": "./dist/index.js",
  "scripts": {
    "build": "echo 'Building utils' && mkdir -p dist && echo 'export const add = (a, b) => a + b;' > dist/index.js"
  }
}

5. apps/web/package.json (depends on workspace package):

{
  "name": "web",
  "private": true,
  "scripts": {
    "build": "echo 'Building web (uses @acme/utils)' && mkdir -p dist"
  },
  "dependencies": {
    "@acme/utils": "workspace:"
  }
}

From repo root:

pnpm install
pnpm build

Example terminal output:

$ pnpm build
• Packages in scope: web, @acme/utils
• Running build in 2 tasks
@acme/utils:build: cache miss
@acme/utils:build: Building utils
web:build: cache miss
web:build: Building web (uses @acme/utils)
Tasks: 2 successful, 2 total

Second run: both tasks get cache hits if nothing changed. You get dependency-ordered builds and incremental cache without writing a custom runner.

Runnable example 2: Bun workspaces (no Turbo)

Bun understands workspaces natively. You don’t need Turborepo for resolution; you only need it if you want cached pipeline tasks. Here’s a Bun-only setup.

1. Root package.json:

{
  "name": "acme-bun-workspace",
  "private": true,
  "workspaces": ["apps/", "packages/"]
}

2. packages/logger/package.json:

{
  "name": "@acme/logger",
  "version": "1.0.0",
  "main": "index.ts"
}

3. packages/logger/index.ts:

// Simple logger used by apps in the workspace
export function log(level: string, msg: string): void {
  console.log([${level}] ${msg});
}

4. apps/cli/package.json:

{
  "name": "cli",
  "private": true,
  "dependencies": {
    "@acme/logger": "workspace:"
  }
}

5. apps/cli/run.ts:

import { log } from "@acme/logger";
log("INFO", "Running from Bun workspace");

From repo root:

bun install
bun run apps/cli/run.ts

Example terminal output:

$ bun run apps/cli/run.ts
[INFO] Running from Bun workspace

Bun resolves @acme/logger to packages/logger without publishing. For “run only affected” or remote cache, you’d add Turbo (or Nx) on top and keep the same workspace layout.

Migration guide: polyrepo → monorepo

Moving existing repos into one tree is the riskiest part. Doing it in stages reduces breakage.

Phase 1 — Prepare

  • Pick the tool (Turborepo, Nx, or Bun workspaces + optional runner).
  • Create a new repo (or choose the “main” one). Layout: e.g. apps/, packages/, tools/.
  • Document current build, test, and deploy steps for each project. You’ll replicate them inside the monorepo.

    • Phase 2 — Move one consumer and one shared package

  • Don’t move everything at once. Example: move shared-ui and one app that uses it.
  • Use Git history: git subtree add or git filter-repo to bring in history, or start fresh and keep old repos read-only for archaeology.
  • Replace published dependency with workspace dependency: "@acme/ui": "workspace:" (or "workspace:^" if you need semver-like behavior).
  • Wire the tool: add turbo.json (or Nx config) so build and test run in order. Confirm CI runs the same commands.

    • Phase 3 — Validate and cut over

  • Run full build and test in the monorepo. Fix path and config issues (tsconfig paths, Jest roots, etc.).
  • Switch CI to the monorepo. Point deploys at the right app(s). Often “build from root with Turbo” replaces “build from app dir.”
  • Retire or archive the old repos. Keep them read-only so links and blame still work if needed.

    • Phase 4 — Migrate the rest

  • Move remaining apps and packages one or two at a time. Each time: add to workspace, replace deps with workspace:, run pipeline, fix breakage.
  • Standardize scripts: e.g. turbo run build --filter=./apps/web for app-specific builds.

    • Gotchas

  • Path and config: TypeScript path aliases, Jest moduleNameMapper, and bundler configs often assume a single package. Update them to workspace-relative paths or package names.
  • Lockfile: Use one lockfile at root (pnpm/yarn/Bun). Delete nested node_modules and lockfiles after moving.
  • Publishing: If you still publish some packages to npm, use changesets or similar so version bumps and changelogs stay consistent.

    • What went wrong (lessons learned)

    We’ve seen a few concrete failures and surprises:

    Cache poisoning: A team had Turborepo’s outputs set to ["dist/"]. A bug in their build script wrote a partial dist/ and then exited 0. Turbo cached that. Clean builds passed; cached builds failed in CI until they cleared the cache and fixed the script. Lesson: Cache only real artifacts; ensure failing builds don’t exit 0.

    Nx and “affected” on the wrong base: Another team ran nx affected:test --base=main in CI. Their main branch was rarely updated; main was weeks behind. Almost every PR was “affected,” so they ran the full test suite every time. Lesson: Use the actual merge base (e.g. the commit you’re merging into) for affected; or use a recent enough baseline so “affected” is meaningful.

    Bun workspaces and hoisting: In one setup, a nested dependency required a different version than the root. Bun’s default hoisting put one version at root; a package deep in the tree expected another and broke at runtime. Lesson: With Bun (or any workspace), if you see “module not found” or wrong version at runtime, check where the dependency is resolved (root vs package) and adjust resolutions or package-specific deps.

    Big-bang merge: A team merged six repos in one weekend with no automated tests per package. Monday: broken builds, unclear ownership. Lesson: Migrate incrementally (one or two packages at a time) and keep each step green.

    Summary and what to do next

  • Monorepo gives atomic cross-project changes and a single source of truth; polyrepo gives clear ownership and independent releases. Your shared-code and team structure should drive the choice.
  • Turborepo is the lightest way to get ordered, cached tasks; Nx adds structure and “affected” at scale; Bun workspaces give workspace resolution with minimal config — add Turbo or Nx if you need caching/affected.
  • Migration works best in small steps: one shared package + one consumer first, then expand.

    • Concrete next steps you can do today:

  • Map dependencies: List which repos or packages depend on which. Draw a small dependency graph (even on paper). That tells you the first candidate to move (e.g. the lib everything else uses).
  • Try one tool in a branch: In a throwaway repo, add Turborepo or Bun workspaces with two packages and one app. Run build and see how it feels. No need to migrate production yet.
  • Lock CI and deploy: Document exactly how each app is built and deployed today. When you move, replicate that in the monorepo so behavior doesn’t change.
  • Decide on history: Choose whether you’ll preserve Git history (subtree/filter-repo) or start fresh. If you start fresh, keep old repos read-only and link from the monorepo README.
  • Migrate one pair: Move one shared package and one app; switch to workspace: and get CI green. Use that as the template for the rest.

    • Once that first pair is in and green, the rest is repetition and patience.
