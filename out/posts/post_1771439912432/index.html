Stale Task Recovery: Resetting Stuck doing Tasks

> When a worker claims a task (sets status='doing') and then crashes, gets killed, or loses its connection, that task can stay in doing forever. No other worker will pick it up, and the queue appears stuck. This post describes how to detect and recover stale doing tasks using a timeout and a small recovery job.

1. The Problem

In a typical task runner you have:

  • Claim: SELECT ... WHERE status='todo' ... LIMIT 1 then UPDATE ... SET status='doing', started_at=now() WHERE id=?
  • Run the task.
  • Complete: UPDATE ... SET status='done', completed_at=now() WHERE id=?

    • If the process dies after the claim and before the complete step, the row stays in doing with a started_at timestamp. No scheduler will select it (they only select todo), so the task is effectively lost unless you have a way to put it back.

    2. Defining “Stale”

    A task in doing is stale if it has been in that state longer than a chosen threshold, e.g. 10 or 30 minutes. So:

  • stale_threshold_seconds = 600 (10 minutes)
  • Stale condition: status = 'doing' AND (strftime('%s','now') - strftime('%s', started_at)) > stale_threshold_seconds

    • You can store started_at as ISO8601 text or as Unix timestamp; the idea is the same: compare elapsed time since started_at to your threshold.

    3. Recovery Policy

    When you detect a stale task, you have two main options:

    Option A: Reset to todo

  • UPDATE tasks SET status='todo', started_at=NULL WHERE id=? AND status='doing' AND ... (stale condition)
  • The task becomes eligible again; another worker (or the same runner after restart) can claim it.
  • Use this when the task is idempotent or when duplicate execution is acceptable or mitigated (e.g. by idempotency keys).

    • Option B: Mark as failed / dead

  • UPDATE tasks SET status='failed', completed_at=datetime('now'), ... WHERE id=? ...
  • You might add a failure_reason column (e.g. "stale_doing_timeout").
  • Use this when you prefer to not retry automatically and want visibility (dashboards, alerts) instead.

    • Many setups use A for automatic retry and optionally a separate “dead letter” or alert when a task has been reset too many times.

    4. Implementing a Recovery Job

    Run a small periodic job (same process or a separate “janitor” script) that:

  • Selects rows where status='doing' and started_at is older than your threshold.
  • For each such row, either reset to todo or mark as failed (and optionally increment a retry counter).
  • Log each reset/fail so you can correlate with crashes or slow workers.

    • Example (SQLite, reset to todo):

    UPDATE tasks
SET status = 'todo', started_at = NULL
WHERE status = 'doing'
  AND (strftime('%s','now') - strftime('%s', started_at)) > 600;

    Run this every 1–5 minutes so stale tasks don’t sit for long. Use a single DB connection and keep the job quick (no heavy work in the same transaction if you have many rows).

    5. Avoiding False Positives

  • Threshold: Set the stale threshold above your expected maximum task duration. If the longest task usually finishes in 2 minutes, 10 minutes is a safe margin; if you have 30-minute tasks, use 45–60 minutes.
  • Concurrency: If multiple workers run the recovery job, use a conditional update (e.g. UPDATE ... WHERE id=? AND status='doing' AND ...) so only one process actually flips a given row, or run recovery in a single designated process.
  • Observability: Count how many tasks you reset per run; if that number spikes, investigate slow or crashing workers rather than only relying on recovery.

    • With a clear definition of “stale,” a simple recovery job, and a sensible threshold, your queue no longer gets stuck on orphaned doing tasks and can keep making progress after restarts or failures.
