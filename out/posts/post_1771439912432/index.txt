8:T23e3,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Stale Task Recovery: Resetting Stuck <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> Tasks</h1></p><p class="text-slate-300 leading-relaxed mb-4">> When a worker claims a task (sets <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status='doing'</code>) and then crashes, gets killed, or loses its connection, that task can stay in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> forever. No other worker will pick it up, and the queue appears stuck. This post describes how to detect and recover stale <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> tasks using a timeout and a small recovery job.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. The Problem</h2></p><p class="text-slate-300 leading-relaxed mb-4">In a typical task runner you have:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Claim</strong>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT ... WHERE status='todo' ... LIMIT 1</code> then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UPDATE ... SET status='doing', started_at=now() WHERE id=?</code></li>
<li class="ml-4 list-disc text-slate-300"><strong>Run</strong> the task.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Complete</strong>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UPDATE ... SET status='done', completed_at=now() WHERE id=?</code></li></p><p class="text-slate-300 leading-relaxed mb-4">If the process dies after the claim and before the complete step, the row stays in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">started_at</code> timestamp. No scheduler will select it (they only select <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">todo</code>), so the task is effectively lost unless you have a way to put it back.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. Defining “Stale”</h2></p><p class="text-slate-300 leading-relaxed mb-4">A task in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> is <strong>stale</strong> if it has been in that state longer than a chosen threshold, e.g. 10 or 30 minutes. So:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">stale_threshold_seconds = 600</code> (10 minutes)</li>
<li class="ml-4 list-disc text-slate-300"><strong>Stale condition</strong>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status = 'doing' AND (strftime('%s','now') - strftime('%s', started_at)) > stale_threshold_seconds</code></li></p><p class="text-slate-300 leading-relaxed mb-4">You can store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">started_at</code> as ISO8601 text or as Unix timestamp; the idea is the same: compare elapsed time since <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">started_at</code> to your threshold.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Recovery Policy</h2></p><p class="text-slate-300 leading-relaxed mb-4">When you detect a stale task, you have two main options:</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Option A: Reset to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">todo</code></strong>  
<li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UPDATE tasks SET status='todo', started_at=NULL WHERE id=? AND status='doing' AND ... (stale condition)</code>  </li>
<li class="ml-4 list-disc text-slate-300">The task becomes eligible again; another worker (or the same runner after restart) can claim it.  </li>
<li class="ml-4 list-disc text-slate-300">Use this when the task is idempotent or when duplicate execution is acceptable or mitigated (e.g. by idempotency keys).</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Option B: Mark as failed / dead</strong>  
<li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UPDATE tasks SET status='failed', completed_at=datetime('now'), ... WHERE id=? ...</code>  </li>
<li class="ml-4 list-disc text-slate-300">You might add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">failure_reason</code> column (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"stale_doing_timeout"</code>).  </li>
<li class="ml-4 list-disc text-slate-300">Use this when you prefer to not retry automatically and want visibility (dashboards, alerts) instead.</li></p><p class="text-slate-300 leading-relaxed mb-4">Many setups use <strong>A</strong> for automatic retry and optionally a separate “dead letter” or alert when a task has been reset too many times.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">4. Implementing a Recovery Job</h2></p><p class="text-slate-300 leading-relaxed mb-4">Run a small periodic job (same process or a separate “janitor” script) that:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300">Selects rows where <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status='doing'</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">started_at</code> is older than your threshold.</li>
<li class="ml-4 list-decimal text-slate-300">For each such row, either reset to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">todo</code> or mark as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">failed</code> (and optionally increment a retry counter).</li>
<li class="ml-4 list-decimal text-slate-300">Log each reset/fail so you can correlate with crashes or slow workers.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example (SQLite, reset to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">todo</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>UPDATE tasks
SET status = 'todo', started_at = NULL
WHERE status = 'doing'
  AND (strftime('%s','now') - strftime('%s', started_at)) > 600;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run this every 1–5 minutes so stale tasks don’t sit for long. Use a single DB connection and keep the job quick (no heavy work in the same transaction if you have many rows).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">5. Avoiding False Positives</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Threshold</strong>: Set the stale threshold above your expected maximum task duration. If the longest task usually finishes in 2 minutes, 10 minutes is a safe margin; if you have 30-minute tasks, use 45–60 minutes.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Concurrency</strong>: If multiple workers run the recovery job, use a conditional update (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UPDATE ... WHERE id=? AND status='doing' AND ...</code>) so only one process actually flips a given row, or run recovery in a single designated process.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Observability</strong>: Count how many tasks you reset per run; if that number spikes, investigate slow or crashing workers rather than only relying on recovery.</li></p><p class="text-slate-300 leading-relaxed mb-4">With a clear definition of “stale,” a simple recovery job, and a sensible threshold, your queue no longer gets stuck on orphaned <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> tasks and can keep making progress after restarts or failures.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
