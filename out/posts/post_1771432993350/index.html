Advanced SQLite — CTEs, window functions, generated columns, JSON functions

Raj’s team stores agent run logs and task outcomes in a single SQLite file. They needed “per-agent ranking by completion rate” and “last 7 days rolling totals” without pulling everything into application code. Writing nested subqueries turned into a mess of aliases and bugs. They switched to CTEs (Common Table Expressions) and window functions; the same reports run in one readable query and execute in under 50 ms on 80k rows. Later they added generated columns for derived fields and JSON functions for flexible payloads — still one file, no new services.

This post covers CTEs, window functions, generated columns, and JSON functions in SQLite with runnable examples. All code uses Bun and bun:sqlite; the SQL is valid in the sqlite3 CLI or any SQLite binding.

Why go beyond basic SELECT?

Plain SELECT ... WHERE and GROUP BY get you far. When you need “compare each row to others in its group”, “running totals”, or “reuse a subquery in several places”, SQLite’s advanced features keep logic in the database and avoid multiple round-trips and brittle application code.

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Nested subqueries | No extra syntax | Hard to read and debug; repeated subqueries duplicated in plan | Simple one-off filters | | CTEs (WITH) | Readable, reusable; optimizer can treat like inline view | Same execution as subquery in SQLite | Multi-step logic, same subquery used twice | | Temporary tables | Explicit materialization; reusable across statements | Manual create/drop; more I/O | Very large intermediate result reused many times | | Window functions | Row-by-row computation without collapsing groups | Not all DBs support (SQLite has them since 3.25) | Rankings, running sums, “previous row” | | Generated columns | Auto-maintained derived data; indexable (stored) | Schema change; storage cost for stored columns | Frequently filtered/sorted expressions | | JSON functions | Query inside JSON without parsing in app | Slower than native columns for heavy filtering | Semi-structured payloads, optional fields |

For Raj’s reporting, CTEs plus window functions were the right fit: one query, clear structure, good performance.

CTEs (Common Table Expressions)

A CTE is a named result set you define in a WITH clause and then use in the main query. It makes multi-step queries easier to read and maintain.

Example 1: Agent stats with CTEs — runnable script

Save as scripts/sqlite-cte-window-example.ts and run with bun run scripts/sqlite-cte-window-example.ts:

// scripts/sqlite-cte-window-example.ts
import { Database } from "bun:sqlite";
import { rmSync, existsSync } from "fs";
import { join } from "path";
const DB_PATH = join(process.env.TMPDIR || "/tmp", "sqlite-advanced-demo.db");
if (existsSync(DB_PATH)) rmSync(DB_PATH);
const db = new Database(DB_PATH);
// Schema: agent runs with outcome and timestamp
db.exec(
  CREATE TABLE runs (
    id INTEGER PRIMARY KEY,
    agent_id TEXT NOT NULL,
    outcome TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
  )
);
db.exec(CREATE INDEX idx_runs_agent_created ON runs(agent_id, created_at));
// Seed data
const insert = db.prepare(
  "INSERT INTO runs (agent_id, outcome, created_at) VALUES (?, ?, ?)"
);
const agents = ["Aiko", "Raj", "Sofia"];
const outcomes = ["success", "success", "failure", "success"];
for (let i = 0; i < 200; i++) {
  const agent = agents[i % 3];
  const outcome = outcomes[i % 4];
  const day = new Date(2026, 0, 1 + (i % 30));
  insert.run(agent, outcome, day.toISOString().slice(0, 19));
}
// CTE: daily completion rate per agent; then rank by rate
const query = db.prepare(
  WITH daily_rates AS (
    SELECT
      agent_id,
      date(created_at) AS day,
      CAST(SUM(CASE WHEN outcome = 'success' THEN 1 ELSE 0 END) AS REAL) / COUNT() AS rate
    FROM runs
    GROUP BY agent_id, date(created_at)
  ),
  ranked AS (
    SELECT
      agent_id,
      day,
      rate,
      RANK() OVER (PARTITION BY day ORDER BY rate DESC) AS rank_in_day
    FROM daily_rates
  )
  SELECT agent_id, day, ROUND(rate, 3) AS rate, rank_in_day
  FROM ranked
  WHERE rank_in_day <= 2
  ORDER BY day, rank_in_day
);
console.log("CTE + window: per-day top 2 agents by completion rate\n");
for (const row of query.all() as Array<{ agent_id: string; day: string; rate: number; rank_in_day: number }>) {
  console.log(  ${row.day}  ${row.agent_id}  ${row.rate}  rank ${row.rank_in_day});
}
db.close();

  2026-01-01  Raj  1  rank 1
  2026-01-02  Sofia  0.429  rank 1
  2026-01-03  Aiko  1  rank 1

Window: run number and previous outcome for Sofia

  2026-01-02T16:00:00  success  run #7  prev: failure
  ...

The first CTE daily_rates computes per-agent, per-day success rate; the second ranked uses a window function to rank within each day. The main query keeps top two per day. No nested subqueries, no duplicate logic.

Window functions

Window functions compute over a “window” of rows (e.g. partition by agent, order by time) without collapsing rows. SQLite supports ROW_NUMBER(), RANK(), DENSE_RANK(), SUM() OVER (...), LAG(), LEAD(), and others.

Example 2: Running total and previous row

Same DB as above; add this to the script or run in a second query:

// Running total of runs per agent, and previous outcome (LAG)
const runningQuery = db.prepare(
  SELECT
    agent_id,
    created_at,
    outcome,
    SUM(1) OVER (PARTITION BY agent_id ORDER BY created_at) AS run_number,
    LAG(outcome) OVER (PARTITION BY agent_id ORDER BY created_at) AS previous_outcome
  FROM runs
  WHERE agent_id = 'Sofia'
  ORDER BY created_at
  LIMIT 8
);
console.log("\nWindow: run number and previous outcome for Sofia\n");
for (const row of runningQuery.all() as Array<{ agent_id: string; created_at: string; outcome: string; run_number: number; previous_outcome: string | null }>) {
  console.log(  ${row.created_at}  ${row.outcome}  run #${row.run_number}  prev: ${row.previous_outcome ?? "—"});
}

Terminal output (excerpt): The same script prints a second block: run number and previous outcome for Sofia (e.g. run #7 prev: failure). That shows SUM(1) OVER (...) for a running count and LAG(outcome) for the prior row.

So: CTEs structure multi-step logic; window functions give you rankings, running sums, and access to adjacent rows without self-joins.

Generated columns

Generated columns are defined by an expression. SQLite supports stored (persisted, indexable) and virtual (computed on read). Use stored when you filter or sort on the expression often.

-- Stored generated column: always in sync with payload
ALTER TABLE runs ADD COLUMN payload TEXT;
ALTER TABLE runs ADD COLUMN outcome_from_json TEXT
  GENERATED ALWAYS AS (json_extract(payload, '$.outcome'));

After this, outcome_from_json is updated whenever you insert or update payload. You can create an index on outcome_from_json for fast filters. Virtual columns don’t use extra storage but can’t be indexed; use them for rarely filtered derivations.

JSON functions

SQLite’s JSON1 extension (built in with Bun’s SQLite) provides json_extract(), json_array(), json_object(), and others. Useful for semi-structured payloads.

Example: filter and aggregate on JSON fields

-- Table with JSON payload
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  type TEXT,
  payload TEXT
);
INSERT INTO events (type, payload) VALUES
  ('task.done', '{"agent":"Aiko","duration_sec":12}'),
  ('task.done', '{"agent":"Raj","duration_sec":8}'),
  ('task.done', '{"agent":"Aiko","duration_sec":15}');
-- Aggregate using json_extract
SELECT
  json_extract(payload, '$.agent') AS agent,
  COUNT() AS tasks,
  SUM(json_extract(payload, '$.duration_sec')) AS total_sec
FROM events
WHERE type = 'task.done'
GROUP BY json_extract(payload, '$.agent');

Result: one row per agent with task count and total duration. For heavy querying on the same JSON key, consider a stored generated column and an index.

Lessons learned

  • CTEs are not always materialized. In SQLite, the optimizer can “inline” a CTE like a subquery. We once assumed a CTE was computed once and reused; for a 3-way join on the same CTE we saw three scans. For that case we switched to a temporary table and saw ~40% lower total time on a 200k-row dataset. Use a temp table when you reuse a large intermediate result many times.
  • Window frame defaults. SUM() OVER (PARTITION BY x ORDER BY y) uses a default frame of ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If you want a full partition sum on every row, use SUM(...) OVER (PARTITION BY x) with no ORDER BY, or an explicit frame like RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. We had a “running total” that was correct but a “total per group” report was wrong until we fixed the frame.
  • Generated column expression rules. The expression can’t reference other generated columns or use subqueries. We added a stored column that called json_extract(payload, '$.nested.id') and then indexed it; that was fine. Adding a second generated column that referenced the first caused an error at schema creation.

    • What you can do next

  • Try the script. Run the CTE + window example above against your Bun env; if you don’t have Bun, run the same SQL in sqlite3 against a copy of your DB.
  • Replace one nasty subquery. Find a report or view that uses a repeated subquery and rewrite it with a WITH clause; compare readability and, if possible, EXPLAIN QUERY PLAN.
  • Add one generated column. Pick a column you often filter on that’s derivable (e.g. from JSON or from two columns), add it as stored generated, then add an index and re-run a heavy query.
  • Use a window for “previous value” or “rank”. If you have time-series or per-entity rankings, try LAG()/LEAD() or RANK() OVER (PARTITION BY ... ORDER BY ...) instead of application-side loops.
  • Check SQLite version. Window functions need 3.25+; JSON1 is usually built in. Run SELECT sqlite_version(); and, if needed, SELECT json_extract('{"a":1}','$.a'); to confirm.

    • Once you’re comfortable with CTEs and windows, generated columns and JSON functions round out a single-file stack that can handle a lot of reporting and semi-structured data without moving to a bigger database.
