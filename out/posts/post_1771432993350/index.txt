8:T4aa3,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Advanced SQLite — CTEs, window functions, generated columns, JSON functions</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s team stores agent run logs and task outcomes in a single SQLite file. They needed “per-agent ranking by completion rate” and “last 7 days rolling totals” without pulling everything into application code. Writing nested subqueries turned into a mess of aliases and bugs. They switched to <strong>CTEs</strong> (Common Table Expressions) and <strong>window functions</strong>; the same reports run in one readable query and execute in under 50 ms on 80k rows. Later they added <strong>generated columns</strong> for derived fields and <strong>JSON functions</strong> for flexible payloads — still one file, no new services.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers <strong>CTEs</strong>, <strong>window functions</strong>, <strong>generated columns</strong>, and <strong>JSON functions</strong> in SQLite with runnable examples. All code uses Bun and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun:sqlite</code>; the SQL is valid in the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3</code> CLI or any SQLite binding.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why go beyond basic SELECT?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Plain <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT ... WHERE</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">GROUP BY</code> get you far. When you need “compare each row to others in its group”, “running totals”, or “reuse a subquery in several places”, SQLite’s advanced features keep logic in the database and avoid multiple round-trips and brittle application code.</p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Nested subqueries</strong> | No extra syntax | Hard to read and debug; repeated subqueries duplicated in plan | Simple one-off filters |
| <strong>CTEs (WITH)</strong> | Readable, reusable; optimizer can treat like inline view | Same execution as subquery in SQLite | Multi-step logic, same subquery used twice |
| <strong>Temporary tables</strong> | Explicit materialization; reusable across statements | Manual create/drop; more I/O | Very large intermediate result reused many times |
| <strong>Window functions</strong> | Row-by-row computation without collapsing groups | Not all DBs support (SQLite has them since 3.25) | Rankings, running sums, “previous row” |
| <strong>Generated columns</strong> | Auto-maintained derived data; indexable (stored) | Schema change; storage cost for stored columns | Frequently filtered/sorted expressions |
| <strong>JSON functions</strong> | Query inside JSON without parsing in app | Slower than native columns for heavy filtering | Semi-structured payloads, optional fields |</p><p class="text-slate-300 leading-relaxed mb-4">For Raj’s reporting, CTEs plus window functions were the right fit: one query, clear structure, good performance.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">CTEs (Common Table Expressions)</h2></p><p class="text-slate-300 leading-relaxed mb-4">A CTE is a named result set you define in a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WITH</code> clause and then use in the main query. It makes multi-step queries easier to read and maintain.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example 1: Agent stats with CTEs — runnable script</strong></p><p class="text-slate-300 leading-relaxed mb-4">Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scripts/sqlite-cte-window-example.ts</code> and run with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/sqlite-cte-window-example.ts</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/sqlite-cte-window-example.ts
import { Database } from "bun:sqlite";
import { rmSync, existsSync } from "fs";
import { join } from "path";</p><p class="text-slate-300 leading-relaxed mb-4">const DB_PATH = join(process.env.TMPDIR || "/tmp", "sqlite-advanced-demo.db");
if (existsSync(DB_PATH)) rmSync(DB_PATH);
const db = new Database(DB_PATH);</p><p class="text-slate-300 leading-relaxed mb-4">// Schema: agent runs with outcome and timestamp
db.exec(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  CREATE TABLE runs (
    id INTEGER PRIMARY KEY,
    agent_id TEXT NOT NULL,
    outcome TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
  )
</code>);
db.exec(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">CREATE INDEX idx_runs_agent_created ON runs(agent_id, created_at)</code>);</p><p class="text-slate-300 leading-relaxed mb-4">// Seed data
const insert = db.prepare(
  "INSERT INTO runs (agent_id, outcome, created_at) VALUES (?, ?, ?)"
);
const agents = ["Aiko", "Raj", "Sofia"];
const outcomes = ["success", "success", "failure", "success"];
for (let i = 0; i < 200; i++) {
  const agent = agents[i % 3];
  const outcome = outcomes[i % 4];
  const day = new Date(2026, 0, 1 + (i % 30));
  insert.run(agent, outcome, day.toISOString().slice(0, 19));
}</p><p class="text-slate-300 leading-relaxed mb-4">// CTE: daily completion rate per agent; then rank by rate
const query = db.prepare(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  WITH daily_rates AS (
    SELECT
      agent_id,
      date(created_at) AS day,
      CAST(SUM(CASE WHEN outcome = 'success' THEN 1 ELSE 0 END) AS REAL) / COUNT(<em>) AS rate
    FROM runs
    GROUP BY agent_id, date(created_at)
  ),
  ranked AS (
    SELECT
      agent_id,
      day,
      rate,
      RANK() OVER (PARTITION BY day ORDER BY rate DESC) AS rank_in_day
    FROM daily_rates
  )
  SELECT agent_id, day, ROUND(rate, 3) AS rate, rank_in_day
  FROM ranked
  WHERE rank_in_day <= 2
  ORDER BY day, rank_in_day
</code>);</p><p class="text-slate-300 leading-relaxed mb-4">console.log("CTE + window: per-day top 2 agents by completion rate\n");
for (const row of query.all() as Array<{ agent_id: string; day: string; rate: number; rank_in_day: number }>) {
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">  ${row.day}  ${row.agent_id}  ${row.rate}  rank ${row.rank_in_day}</code>);
}
db.close();
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal output (excerpt):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run scripts/sqlite-cte-window-example.ts
CTE + window: per-day top 2 agents by completion rate</p><p class="text-slate-300 leading-relaxed mb-4">  2025-12-31  Aiko  0.571  rank 1
  2026-01-01  Raj  1  rank 1
  2026-01-02  Sofia  0.429  rank 1
  2026-01-03  Aiko  1  rank 1
  ...</p><p class="text-slate-300 leading-relaxed mb-4">Window: run number and previous outcome for Sofia</p><p class="text-slate-300 leading-relaxed mb-4">  2026-01-02T16:00:00  failure  run #7  prev: —
  2026-01-02T16:00:00  success  run #7  prev: failure
  ...
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The first CTE <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">daily_rates</code> computes per-agent, per-day success rate; the second <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ranked</code> uses a window function to rank within each day. The main query keeps top two per day. No nested subqueries, no duplicate logic.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Window functions</h2></p><p class="text-slate-300 leading-relaxed mb-4">Window functions compute over a “window” of rows (e.g. partition by agent, order by time) without collapsing rows. SQLite supports <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ROW_NUMBER()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RANK()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DENSE_RANK()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SUM() OVER (...)</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LAG()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LEAD()</code>, and others.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example 2: Running total and previous row</strong></p><p class="text-slate-300 leading-relaxed mb-4">Same DB as above; add this to the script or run in a second query:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Running total of runs per agent, and previous outcome (LAG)
const runningQuery = db.prepare(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">
  SELECT
    agent_id,
    created_at,
    outcome,
    SUM(1) OVER (PARTITION BY agent_id ORDER BY created_at) AS run_number,
    LAG(outcome) OVER (PARTITION BY agent_id ORDER BY created_at) AS previous_outcome
  FROM runs
  WHERE agent_id = 'Sofia'
  ORDER BY created_at
  LIMIT 8
</code>);
console.log("\nWindow: run number and previous outcome for Sofia\n");
for (const row of runningQuery.all() as Array<{ agent_id: string; created_at: string; outcome: string; run_number: number; previous_outcome: string | null }>) {
  console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">  ${row.created_at}  ${row.outcome}  run #${row.run_number}  prev: ${row.previous_outcome ?? "—"}</code>);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Terminal output (excerpt):</strong> The same script prints a second block: run number and previous outcome for Sofia (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run #7  prev: failure</code>). That shows <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SUM(1) OVER (...)</code> for a running count and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LAG(outcome)</code> for the prior row.</p><p class="text-slate-300 leading-relaxed mb-4">So: <strong>CTEs</strong> structure multi-step logic; <strong>window functions</strong> give you rankings, running sums, and access to adjacent rows without self-joins.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Generated columns</h2></p><p class="text-slate-300 leading-relaxed mb-4">Generated columns are defined by an expression. SQLite supports <strong>stored</strong> (persisted, indexable) and <strong>virtual</strong> (computed on read). Use stored when you filter or sort on the expression often.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- Stored generated column: always in sync with payload
ALTER TABLE runs ADD COLUMN payload TEXT;
ALTER TABLE runs ADD COLUMN outcome_from_json TEXT
  GENERATED ALWAYS AS (json_extract(payload, '$.outcome'));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">After this, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">outcome_from_json</code> is updated whenever you insert or update <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">payload</code>. You can create an index on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">outcome_from_json</code> for fast filters. Virtual columns don’t use extra storage but can’t be indexed; use them for rarely filtered derivations.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">JSON functions</h2></p><p class="text-slate-300 leading-relaxed mb-4">SQLite’s JSON1 extension (built in with Bun’s SQLite) provides <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_array()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_object()</code>, and others. Useful for semi-structured payloads.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: filter and aggregate on JSON fields</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- Table with JSON payload
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  type TEXT,
  payload TEXT
);
INSERT INTO events (type, payload) VALUES
  ('task.done', '{"agent":"Aiko","duration_sec":12}'),
  ('task.done', '{"agent":"Raj","duration_sec":8}'),
  ('task.done', '{"agent":"Aiko","duration_sec":15}');</p><p class="text-slate-300 leading-relaxed mb-4">-- Aggregate using json_extract
SELECT
  json_extract(payload, '$.agent') AS agent,
  COUNT(</em>) AS tasks,
  SUM(json_extract(payload, '$.duration_sec')) AS total_sec
FROM events
WHERE type = 'task.done'
GROUP BY json_extract(payload, '$.agent');
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Result: one row per agent with task count and total duration. For heavy querying on the same JSON key, consider a stored generated column and an index.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>CTEs are not always materialized.</strong> In SQLite, the optimizer can “inline” a CTE like a subquery. We once assumed a CTE was computed once and reused; for a 3-way join on the same CTE we saw three scans. For that case we switched to a temporary table and saw ~40% lower total time on a 200k-row dataset. Use a temp table when you reuse a large intermediate result many times.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Window frame defaults.</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SUM() OVER (PARTITION BY x ORDER BY y)</code> uses a default frame of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW</code>. If you want a full partition sum on every row, use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SUM(...) OVER (PARTITION BY x)</code> with no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ORDER BY</code>, or an explicit frame like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING</code>. We had a “running total” that was correct but a “total per group” report was wrong until we fixed the frame.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Generated column expression rules.</strong> The expression can’t reference other generated columns or use subqueries. We added a stored column that called <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract(payload, '$.nested.id')</code> and then indexed it; that was fine. Adding a second generated column that referenced the first caused an error at schema creation.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do next</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Try the script.</strong> Run the CTE + window example above against your Bun env; if you don’t have Bun, run the same SQL in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3</code> against a copy of your DB.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Replace one nasty subquery.</strong> Find a report or view that uses a repeated subquery and rewrite it with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WITH</code> clause; compare readability and, if possible, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EXPLAIN QUERY PLAN</code>.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add one generated column.</strong> Pick a column you often filter on that’s derivable (e.g. from JSON or from two columns), add it as stored generated, then add an index and re-run a heavy query.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use a window for “previous value” or “rank”.</strong> If you have time-series or per-entity rankings, try <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LAG()</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">LEAD()</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RANK() OVER (PARTITION BY ... ORDER BY ...)</code> instead of application-side loops.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Check SQLite version.</strong> Window functions need 3.25+; JSON1 is usually built in. Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT sqlite_version();</code> and, if needed, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SELECT json_extract('{"a":1}','$.a');</code> to confirm.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once you’re comfortable with CTEs and windows, generated columns and JSON functions round out a single-file stack that can handle a lot of reporting and semi-structured data without moving to a bigger database.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
