8:T4f3c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Authentication patterns for APIs — JWT, session tokens, API keys, OAuth2 PKCE</h1></p><p class="text-slate-300 leading-relaxed mb-4">Omar’s team shipped a partner API protected by API keys. Six months later they found one key in a public GitHub repo, another in a support ticket that had been forwarded to a contractor. They had to rotate every key, break several integrations, and add proper key storage docs. The real issue wasn’t the keys themselves — it was picking the wrong pattern for each use case and not knowing when to switch. This post compares the four patterns we use most: API keys, session tokens, JWTs (JSON Web Tokens), and OAuth2 PKCE (Proof Key for Code Exchange), with runnable examples and a comparison matrix so you can choose and implement them correctly.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the choice matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs need to know <em>who</em> is calling and <em>what</em> they’re allowed to do. The mechanism you use affects security, ops (rotation, revocation), and client types (server, browser, mobile). No single pattern fits every scenario. API keys are simple but easy to leak. Sessions are revocable but need server-side state. JWTs are stateless but hard to revoke before expiry. PKCE solves browser/mobile flows where you can’t keep a client secret. We’ll go through each and then put them in a table.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">API keys</h2></p><p class="text-slate-300 leading-relaxed mb-4">An <strong>API key</strong> is a long secret string the client sends on every request, usually in a header (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-API-Key</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer <key></code>) or query param. The server looks it up in a store (DB, cache) and maps it to an identity and permissions.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Simple to implement and to give to partners. No crypto in the client.  
<strong>Cons:</strong> If leaked, anyone with the key has the same access until you revoke it. Query params get logged; headers can end up in logs or proxies. Rotation forces clients to update.</p><p class="text-slate-300 leading-relaxed mb-4">Use for: server-to-server, scripts, internal tools, partner integrations where you control or document key storage.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Middleware: validate API key and attach identity (concept)
async function requireApiKey(req: Request): Promise<{ userId: string; scope: string[] } | null> {
  const key = req.headers.get("x-api-key") ?? req.query.get("api_key");
  if (!key) return null;
  const record = await db.get("SELECT user_id, scope FROM api_keys WHERE key_hash = ?", [hash(key)]);
  return record ? { userId: record.user_id, scope: record.scope.split(",") } : null;
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Store keys as a hash (e.g. SHA-256), never plaintext. Rate limit and audit by key so you can spot abuse and rotate when needed.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Session tokens</h2></p><p class="text-slate-300 leading-relaxed mb-4">A <strong>session</strong> is created at login: the server stores session data (user id, roles, expiry) in a store (DB, Redis) and returns a <strong>session id</strong> to the client. The client sends that id on each request (cookie or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization</code> header). The server looks up the session and gets the identity.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Revocable instantly (delete or invalidate the session). No sensitive data in the token.  
<strong>Cons:</strong> Every request may hit the store (unless you cache). You need a shared or sticky store for multi-node deployments. Cookie handling (SameSite, Secure, HTTPOnly) matters for browsers.</p><p class="text-slate-300 leading-relaxed mb-4">Use for: web apps with a login page, anything where you need to log users out immediately or invalidate all sessions.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">JWT (JSON Web Token)</h2></p><p class="text-slate-300 leading-relaxed mb-4">A <strong>JWT</strong> is a signed payload (claims like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sub</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">scope</code>) that the server signs with a secret or private key. The client sends the token (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer <jwt></code>). The server verifies the signature and optionally expiry; no DB lookup is required for verification.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Stateless verification; horizontal scaling is easy. Good for microservices (one service issues, others verify with the public key or shared secret).  
<strong>Cons:</strong> Hard to revoke before <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code> unless you add a blocklist or short expiry + refresh flow. Putting too much in the payload bloats the token. Algorithm confusion (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">alg: none</code>) and key leakage are real risks.</p><p class="text-slate-300 leading-relaxed mb-4">Use for: service-to-service, mobile apps with a backend that issues tokens, or when you want stateless auth and accept revocation limits.</p><p class="text-slate-300 leading-relaxed mb-4">Runnable example — sign and verify with HMAC-SHA256 (no external deps):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/auth-jwt-demo.ts — sign and verify JWT with HMAC-SHA256 (no deps)

The client generates a random <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_verifier</code>, computes <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_challenge = base64url(sha256(code_verifier))</code>, and sends the challenge when requesting the authorization code. When exchanging the code for tokens, it sends the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_verifier</code>. The server hashes the verifier and checks it against the stored challenge so a stolen authorization code alone can’t be used.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> No client secret in the browser or app. Mitigates authorization-code interception.  
<strong>Cons:</strong> You need an authorization server (or IdP) that supports PKCE. Flow is more steps than “send API key”.</p><p class="text-slate-300 leading-relaxed mb-4">Use for: browser SPAs (e.g. Raj’s dashboard calling your API after “Login with X”), native mobile apps, and any OAuth2 flow where the client is not fully trusted with a secret.</p><p class="text-slate-300 leading-relaxed mb-4">Runnable example — generate <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_verifier</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_challenge</code> (S256):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/auth-pkce-demo.ts — generate PKCE code_verifier and code_challenge (no deps)

|----------------|--------------------------------|-----------------------------------------|--------------------------------------------------|
| <strong>API key</strong>    | Simple; no crypto in client    | Leaks in logs/URLs; rotation breaks clients | Server-to-server, scripts, partners, internal tools |
| <strong>Session</strong>    | Revocable; no secrets in token | Needs server/store; cookie/state design | Web login; need to invalidate sessions fast      |
| <strong>JWT</strong>        | Stateless; scales horizontally | Revocation before exp is awkward        | Services, mobile backends, stateless APIs        |
| <strong>OAuth2 PKCE</strong>| No client secret; safe for SPAs/mobile | Needs auth server; more flow steps   | Browser/mobile OAuth; public clients            |</p><p class="text-slate-300 leading-relaxed mb-4">Rough mapping:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Human in a browser (your app):</strong> Session or OAuth2 (with PKCE if you’re the client).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Server or script calling your API:</strong> API key (hashed, scoped) or JWT issued by you.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Third-party app (e.g. “Login with X”):</strong> OAuth2 with PKCE for the client side; issuer gives JWTs or opaque tokens.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Service-to-service inside your system:</strong> JWT or short-lived API key, with verification that doesn’t hit a DB every time if you can.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4">We made three mistakes that are worth avoiding.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>API key in query params.</strong> We documented <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">?api_key=xxx</code> for ease. One partner committed it to GitHub; another sent it in a support email. We moved to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization: Bearer</code> only and started hashing keys. After that we found two keys in proxy logs that had logged query strings. We now recommend headers only and never log the key (or even the full <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Authorization</code> header).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>JWT with no expiry.</strong> An early internal service issued JWTs with no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code>. When we needed to revoke access we had no way to do it except changing the signing key and breaking every client. We added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code> (e.g. 15–60 minutes) and refresh tokens for long-lived access, and for high-risk cases we added a small blocklist in Redis keyed by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">jti</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>PKCE with plain code_challenge.</strong> We had a legacy flow that sent <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code_challenge</code> as plain text (method <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">plain</code>) instead of S256. That gives no protection if the code is intercepted. We switched to S256 only and deprecated <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">plain</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit where API keys appear</strong> — Search code and docs for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">api_key</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">apikey</code>, query params. Move to header-only and ensure keys are hashed in storage and never logged.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Run the JWT and PKCE demos</strong> — In this repo: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/auth-jwt-demo.ts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/auth-pkce-demo.ts</code>. Use them as a reference for signing/verifying JWTs and generating PKCE parameters in your stack.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Pick one pattern per use case</strong> — Map “browser user”, “partner API”, “mobile app”, “internal service” to one of the four. Document it and enforce it (e.g. API key only for server clients, PKCE for the SPA).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add expiry to every token</strong> — JWTs and session tokens should have a short <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exp</code>. Use refresh tokens or re-login for longer sessions; keep access tokens under an hour where possible.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Plan rotation</strong> — For API keys, support multiple keys per client and a grace period so you can rotate without downtime. For JWTs, use short expiry and a refresh flow so you can rotate signing keys on a schedule.</li></p><p class="text-slate-300 leading-relaxed mb-4">The scripts in this repo run with Bun and no extra dependencies. Use them as a starting point for middleware or auth helpers; for production, consider a library like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">jose</code> for JWTs and a well-audited OAuth2/PKCE client for the full flow.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
