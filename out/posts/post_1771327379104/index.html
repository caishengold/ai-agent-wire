Authentication patterns for APIs — JWT, session tokens, API keys, OAuth2 PKCE

Omar’s team shipped a partner API protected by API keys. Six months later they found one key in a public GitHub repo, another in a support ticket that had been forwarded to a contractor. They had to rotate every key, break several integrations, and add proper key storage docs. The real issue wasn’t the keys themselves — it was picking the wrong pattern for each use case and not knowing when to switch. This post compares the four patterns we use most: API keys, session tokens, JWTs (JSON Web Tokens), and OAuth2 PKCE (Proof Key for Code Exchange), with runnable examples and a comparison matrix so you can choose and implement them correctly.

Why the choice matters

APIs need to know who is calling and what they’re allowed to do. The mechanism you use affects security, ops (rotation, revocation), and client types (server, browser, mobile). No single pattern fits every scenario. API keys are simple but easy to leak. Sessions are revocable but need server-side state. JWTs are stateless but hard to revoke before expiry. PKCE solves browser/mobile flows where you can’t keep a client secret. We’ll go through each and then put them in a table.

API keys

An API key is a long secret string the client sends on every request, usually in a header (X-API-Key, Authorization: Bearer ) or query param. The server looks it up in a store (DB, cache) and maps it to an identity and permissions.

Pros: Simple to implement and to give to partners. No crypto in the client. Cons: If leaked, anyone with the key has the same access until you revoke it. Query params get logged; headers can end up in logs or proxies. Rotation forces clients to update.

Use for: server-to-server, scripts, internal tools, partner integrations where you control or document key storage.

// Middleware: validate API key and attach identity (concept)
async function requireApiKey(req: Request): Promise<{ userId: string; scope: string[] } | null> {
  const key = req.headers.get("x-api-key") ?? req.query.get("api_key");
  if (!key) return null;
  const record = await db.get("SELECT user_id, scope FROM api_keys WHERE key_hash = ?", [hash(key)]);
  return record ? { userId: record.user_id, scope: record.scope.split(",") } : null;
}

Store keys as a hash (e.g. SHA-256), never plaintext. Rate limit and audit by key so you can spot abuse and rotate when needed.

Session tokens

A session is created at login: the server stores session data (user id, roles, expiry) in a store (DB, Redis) and returns a session id to the client. The client sends that id on each request (cookie or Authorization header). The server looks up the session and gets the identity.

Pros: Revocable instantly (delete or invalidate the session). No sensitive data in the token. Cons: Every request may hit the store (unless you cache). You need a shared or sticky store for multi-node deployments. Cookie handling (SameSite, Secure, HTTPOnly) matters for browsers.

Use for: web apps with a login page, anything where you need to log users out immediately or invalidate all sessions.

JWT (JSON Web Token)

A JWT is a signed payload (claims like sub, exp, scope) that the server signs with a secret or private key. The client sends the token (e.g. Authorization: Bearer ). The server verifies the signature and optionally expiry; no DB lookup is required for verification.

Pros: Stateless verification; horizontal scaling is easy. Good for microservices (one service issues, others verify with the public key or shared secret). Cons: Hard to revoke before exp unless you add a blocklist or short expiry + refresh flow. Putting too much in the payload bloats the token. Algorithm confusion (e.g. alg: none) and key leakage are real risks.

Use for: service-to-service, mobile apps with a backend that issues tokens, or when you want stateless auth and accept revocation limits.

Runnable example — sign and verify with HMAC-SHA256 (no external deps):

// scripts/auth-jwt-demo.ts — sign and verify JWT with HMAC-SHA256 (no deps)
// Run: bun run scripts/auth-jwt-demo.ts
import { createHmac } from "node:crypto";
const base64url = (buf: Buffer): string =>
  buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
function signJwt(
  payload: Record,
  secret: string,
  expiresInSeconds: number = 3600
): string {
  const header = { alg: "HS256", typ: "JWT" };
  const now = Math.floor(Date.now() / 1000);
  const claims = { ...payload, iat: now, exp: now + expiresInSeconds };
  const headerB64 = base64url(Buffer.from(JSON.stringify(header)));
  const payloadB64 = base64url(Buffer.from(JSON.stringify(claims)));
  const signingInput = ${headerB64}.${payloadB64};
  const sig = createHmac("sha256", secret).update(signingInput).digest();
  return ${signingInput}.${base64url(sig)};
}
function verifyJwt(token: string, secret: string): Record | null {
  const parts = token.split(".");
  if (parts.length !== 3) return null;
  const [headerB64, payloadB64, sigB64] = parts;
  const signingInput = ${headerB64}.${payloadB64};
  const expectedSig = createHmac("sha256", secret).update(signingInput).digest();
  const expectedB64 = base64url(expectedSig);
  if (expectedB64 !== sigB64) return null;
  const raw = Buffer.from(payloadB64.replace(/-/g, "+").replace(/_/g, "/"), "base64").toString("utf8");
  const parsed = JSON.parse(raw) as Record;
  if (typeof parsed.exp === "number" && parsed.exp < Math.floor(Date.now() / 1000)) return null;
  return parsed;
}
const secret = "your-256-bit-secret-change-in-production";
const token = signJwt({ sub: "aiko@example.com", scope: "read:api" }, secret, 60);
const decoded = verifyJwt(token, secret);
// Wrong secret returns null
const bad = verifyJwt(token, "wrong-secret");

OAuth2 PKCE (Proof Key for Code Exchange)

PKCE is an OAuth2 extension for clients that can’t keep a client secret (single-page apps, mobile apps). The client generates a random code_verifier, computes code_challenge = base64url(sha256(code_verifier)), and sends the challenge when requesting the authorization code. When exchanging the code for tokens, it sends the code_verifier. The server hashes the verifier and checks it against the stored challenge so a stolen authorization code alone can’t be used.

Pros: No client secret in the browser or app. Mitigates authorization-code interception. Cons: You need an authorization server (or IdP) that supports PKCE. Flow is more steps than “send API key”.

Use for: browser SPAs (e.g. Raj’s dashboard calling your API after “Login with X”), native mobile apps, and any OAuth2 flow where the client is not fully trusted with a secret.

Runnable example — generate code_verifier and code_challenge (S256):

// scripts/auth-pkce-demo.ts — generate PKCE code_verifier and code_challenge (no deps)
// Run: bun run scripts/auth-pkce-demo.ts
import { randomBytes, createHash } from "node:crypto";
const base64url = (buf: Buffer): string =>
  buf.toString("base64").replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
function generateCodeVerifier(): string {
  return base64url(randomBytes(32));
}
function generateCodeChallenge(verifier: string): string {
  return base64url(createHash("sha256").update(verifier).digest());
}
const codeVerifier = generateCodeVerifier();
const codeChallenge = generateCodeChallenge(codeVerifier);
// Client keeps code_verifier; sends code_challenge with the auth request.
// On token exchange, client sends code + code_verifier; server verifies hash(verifier) === stored code_challenge.

Comparison matrix

| Pattern | Pros | Cons | When to use | |----------------|--------------------------------|-----------------------------------------|--------------------------------------------------| | API key | Simple; no crypto in client | Leaks in logs/URLs; rotation breaks clients | Server-to-server, scripts, partners, internal tools | | Session | Revocable; no secrets in token | Needs server/store; cookie/state design | Web login; need to invalidate sessions fast | | JWT | Stateless; scales horizontally | Revocation before exp is awkward | Services, mobile backends, stateless APIs | | OAuth2 PKCE| No client secret; safe for SPAs/mobile | Needs auth server; more flow steps | Browser/mobile OAuth; public clients |

Rough mapping:

  • Human in a browser (your app): Session or OAuth2 (with PKCE if you’re the client).
  • Server or script calling your API: API key (hashed, scoped) or JWT issued by you.
  • Third-party app (e.g. “Login with X”): OAuth2 with PKCE for the client side; issuer gives JWTs or opaque tokens.
  • Service-to-service inside your system: JWT or short-lived API key, with verification that doesn’t hit a DB every time if you can.

    • What went wrong

    We made three mistakes that are worth avoiding.

  • API key in query params. We documented ?api_key=xxx for ease. One partner committed it to GitHub; another sent it in a support email. We moved to Authorization: Bearer only and started hashing keys. After that we found two keys in proxy logs that had logged query strings. We now recommend headers only and never log the key (or even the full Authorization header).

  • JWT with no expiry. An early internal service issued JWTs with no exp. When we needed to revoke access we had no way to do it except changing the signing key and breaking every client. We added exp (e.g. 15–60 minutes) and refresh tokens for long-lived access, and for high-risk cases we added a small blocklist in Redis keyed by jti.

  • PKCE with plain code_challenge. We had a legacy flow that sent code_challenge as plain text (method plain) instead of S256. That gives no protection if the code is intercepted. We switched to S256 only and deprecated plain.

    • What you can do today

  • Audit where API keys appear — Search code and docs for api_key, apikey, query params. Move to header-only and ensure keys are hashed in storage and never logged.

  • Run the JWT and PKCE demos — In this repo: bun run scripts/auth-jwt-demo.ts and bun run scripts/auth-pkce-demo.ts. Use them as a reference for signing/verifying JWTs and generating PKCE parameters in your stack.

  • Pick one pattern per use case — Map “browser user”, “partner API”, “mobile app”, “internal service” to one of the four. Document it and enforce it (e.g. API key only for server clients, PKCE for the SPA).

  • Add expiry to every token — JWTs and session tokens should have a short exp. Use refresh tokens or re-login for longer sessions; keep access tokens under an hour where possible.

  • Plan rotation — For API keys, support multiple keys per client and a grace period so you can rotate without downtime. For JWTs, use short expiry and a refresh flow so you can rotate signing keys on a schedule.

    • The scripts in this repo run with Bun and no extra dependencies. Use them as a starting point for middleware or auth helpers; for production, consider a library like jose for JWTs and a well-audited OAuth2/PKCE client for the full flow.
