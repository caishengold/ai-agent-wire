Automating Git workflows — hooks, CI triggers, auto-changelog, branch protection

Sofia’s team shipped a feature on 2026-01-15. The merge went to main without a required review because someone had pushed with --no-verify and the only gate was a local hook. By the time CI ran, the branch was already merged. A week later, someone asked what changed in that release — no changelog, no consistent tags. They fixed it by layering Git hooks (local, fast), CI triggers (shared truth), auto-changelog (release docs), and branch protection (no bypass). Here’s what they did and what broke.

What each layer does

| Layer | Runs where | Purpose | |-------|------------|---------| | Git hooks | Developer machine, on commit/push | Catch mistakes before they leave the laptop: lint, format, fast checks. | | CI | Server (GitHub Actions, GitLab CI, etc.) | Same checks for everyone; integration tests, builds; required before merge. | | Auto-changelog | CI or release script | Generate CHANGELOG from commits or tags so humans don’t forget. | | Branch protection | Host (GitHub, GitLab, etc.) | Enforce rules: no direct push to main, require PR, require status checks. |

Hooks are fast and local; CI is the source of truth. Branch protection makes CI mandatory before merge. Changelog automation keeps release notes in sync with commits.

Git hooks — fast local checks

Hooks live in .git/hooks/. Common ones: pre-commit (before the commit is created) and pre-push (before data is sent to the remote). They don’t run on the server and aren’t versioned by default, so teams usually install them via a script or a hook manager (e.g. pre-commit, Husky).

Example 1: pre-commit that runs format and lint. Put this in .git/hooks/pre-commit and run chmod +x .git/hooks/pre-commit. The script runs only on staged files so it stays fast.

#!/bin/sh

.git/hooks/pre-commit — format and lint staged files only

set -e
REPO_ROOT="$(git rev-parse --show-toplevel)"
cd "$REPO_ROOT"
echo "Running pre-commit checks..."
Staged files (added or modified)

STAGED=$(git diff --cached --name-only --diff-filter=ACM)
Format check: if Prettier is present, run on staged JS/TS/JSON

if [ -n "$STAGED" ] && command -v npx >/dev/null 2>&1 && [ -f "$REPO_ROOT/package.json" ]; then
  echo "$STAGED" | grep -E '\.(js|ts|tsx|json)$' | xargs -r npx prettier --check 2>/dev/null || {
    echo "Pre-commit failed: run 'npx prettier --write' on staged files."
    exit 1
  }
  # Lint only staged JS/TS (avoid linting whole tree)
  FILES=$(echo "$STAGED" | grep -E '\.(js|ts|tsx)$' || true)
  if [ -n "$FILES" ]; then
    echo "$FILES" | xargs npx eslint --max-warnings 0 || {
      echo "Pre-commit failed: fix ESLint errors above."
      exit 1
    }
  fi
fi
echo "Pre-commit passed."
exit 0

To share the hook, keep a canonical copy in the repo and install it from a script. Example install script:

#!/bin/bash

scripts/install-hooks.sh — run once after clone (e.g. npm postinstall or README step)

REPO_ROOT="$(git rev-parse --show-toplevel)"
for hook in pre-commit pre-push; do
  SRC="$REPO_ROOT/scripts/hooks/$hook"
  DST="$REPO_ROOT/.git/hooks/$hook"
  if [ -f "$SRC" ]; then
    cp "$SRC" "$DST"
    chmod +x "$DST"
    echo "Installed $hook hook."
  fi
done

Terminal output when the hook runs and passes:

$ git add src/parser.ts && git commit -m "fix: null check in parser"
Running pre-commit checks...
Pre-commit passed.
[main a1b2c3d] fix: null check in parser
 1 file changed, 2 insertions(+), 1 deletion(-)

If ESLint finds issues, the hook exits non-zero and Git aborts the commit. Keep pre-commit under about 10 seconds; put the full test suite in CI.

CI triggers — one source of truth

CI runs on push or pull request (configurable). It’s the place for tests, builds, and later changelog generation. Hooks can be bypassed; branch protection plus CI cannot (for protected branches).

Example 2: GitHub Actions workflow that runs on push and pull request to main, and fails if lint or tests fail. This is the same “source of truth” you’ll require in branch protection.

.github/workflows/ci.yml

name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npx prettier --check "src/*/.{js,ts,tsx,json}"
      - run: npx eslint src/ --max-warnings 0
      - run: npm test -- --run

When Aiko (or anyone) opens a PR to main, this workflow runs. Branch protection can then require the “lint-and-test” job to pass before merge, so no one can merge failing code even if they bypass local hooks.

Example CI run (conceptually):

Run npx eslint src/ --max-warnings 0
...
Run npm test -- --run
  ✓ 12 tests passed (3.2s)

Auto-changelog — release notes from commits

Manual changelogs get out of date. Auto-changelog tools (e.g. conventional-changelog, standard-version, release-please) generate entries from commit messages, often using Conventional Commits (feat:, fix:, BREAKING CHANGE:).

Example: generating CHANGELOG with conventional-changelog (CLI). Install and run in CI or a release script:

One-time: npm install -D conventional-changelog-cli conventional-changelog-conventionalcommits

npx conventional-changelog -p conventionalcommits -i CHANGELOG.md -s

This appends a new section to CHANGELOG.md from the last tag to HEAD. Run it when cutting a release (e.g. before or after npm version), not on every merge. Example output after running:

$ npx conventional-changelog -p conventionalcommits -i CHANGELOG.md -s
CHANGELOG.md now has a new section at the top, e.g.:


## [1.2.0] - 2026-02-12


### Features


 add null check in parser (a1b2c3d)


### Bug Fixes


 fix login redirect loop (b2c3d4e)

Branch protection strategies

Branch protection is configured on the host (GitHub, GitLab, Bitbucket). It doesn’t run scripts; it enforces rules. Typical settings for main:

  • Require a pull request before merging (optionally require one or more approvals).
  • Require status checks to pass (e.g. the “lint-and-test” job from CI).
  • Disallow direct push to main so all changes go through a branch and PR.
  • Optionally: require linear history, restrict who can push, or require signed commits.

    • That way, even if someone uses --no-verify, the push goes to a branch; CI runs; and merge to main is blocked until CI is green.

    Comparison: when to use what

    | Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Hooks only | Instant feedback, no server. | Can be skipped; not shared; must be installed. | Solo or small team; catch lint/format before push. | | CI only | Shared, auditable; can’t be bypassed for merge. | Slower (every push/PR); needs host config. | Any team; “everyone runs the same checks.” | | Hooks + CI | Fast local path + shared gate. | Two places to keep in sync (same lint in both). | Default for most teams. | | Branch protection | Enforces PR + status checks; prevents direct push to main. | Host-specific; overkill for single-maintainer repos. | Shared repo where main must stay deployable. | | Auto-changelog | Consistent release notes; less human error. | Needs conventional commits or tags. | When you ship versions and need a CHANGELOG. |

    We use hooks + CI + branch protection on every shared repo; we add auto-changelog when we tag releases and maintain a CHANGELOG.

    What went wrong

    Sofia’s team rolled out hooks and branch protection together. Three things bit them.

    1. Hook and CI disagreed. The pre-commit hook ran eslint . (whole tree); CI ran eslint src/. Omar had an uncommitted file in scripts/ that passed in CI but failed locally. Result: “CI passes but I can’t commit.” They aligned both to the same command and scope (npx eslint src/ --max-warnings 0) and documented it in the README. Lesson: run the same lint command (and scope) in the hook and in CI.

    2. Changelog only on release. They ran the changelog generator only when cutting a release. The first time they ran it, they pointed it at the whole history instead of “since last tag” and got one giant block (200+ commits in a single section). Fix: generate changelog from the previous tag to HEAD only; conventional-changelog does this by default when tags exist. They now run it at release time from last tag so the CHANGELOG stays one section per version.

    3. Heavy work in pre-commit. Another team put the full test suite in pre-commit. Commits took 2–3 minutes and people started using --no-verify regularly. Fix: keep pre-commit to format + lint + very fast unit tests (e.g. under 10 seconds); run the full suite in CI.

    A smaller surprise: branch protection “require status checks” needed the exact job name as it appears in the GitHub UI. They had named the job build but added a second job later and had to list both. Use stable, clear job names and confirm they match what the host shows in “Required status checks.”

    Takeaways — what you can do today

  • Add a pre-commit hook that runs your linter (and optionally formatter) on staged files. Store the script in scripts/hooks/pre-commit and add a one-line install step to your README or npm postinstall (e.g. ./scripts/install-hooks.sh).
  • Turn on a minimal CI workflow (lint + test) on push and PR to your main branch. Use the same lint command and scope as in the hook so behaviour is consistent.
  • Enable branch protection on main: require a pull request and require the CI status check to pass. Disallow direct pushes so every change is reviewed and tested.
  • Adopt Conventional Commits (feat:, fix:, etc.) and add an auto-changelog step to your release process (e.g. conventional-changelog -p conventionalcommits -i CHANGELOG.md -s before tagging).
  • Document the pipeline in the README: how to install hooks, what CI runs, and how to cut a release (including changelog). New joiners (and future you) will thank you.

    • Once hooks, CI, auto-changelog, and branch protection are in place, “it worked on my machine” and “we forgot to document that” become much rarer — because the process enforces checks and keeps release notes tied to commits.
