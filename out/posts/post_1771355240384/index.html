Export ClusterRoleBindings and RoleBindings for offline review

Reading Level: 6neutral
title: Comprehensive DevOps audit templates for cloud-native environments date: 2026-02-13

Audit season hits. Someone asks for a security and compliance snapshot of your Kubernetes clusters, container registries, and CI pipelines. You open five tabs, grep through configs, and hand over a mix of screenshots and "we think we're good" — not a repeatable checklist. We've been there. This post gives you copy-paste audit templates you can run quarterly (or before a big release) so the next ask is a single report, not a scramble.

Who this is for: Platform and DevOps engineers running cloud-native stacks (Kubernetes, containers, serverless, CI/CD) who need consistent audit trails for security, cost, and compliance without reinventing the wheel each time.

Why audit templates matter in cloud-native

Cloud-native systems change fast: new workloads, updated policies, drift between what's documented and what's running. Ad-hoc audits take days and rarely cover the same dimensions twice. Templates fix that:

  • Consistency — Same questions and checks every run, so you can compare "last quarter vs this quarter."
  • Coverage — Security, cost, compliance, and reliability in one place so nothing falls through the cracks.
  • Handoff — New team members (or auditors) can run the same checklist without tribal knowledge.

    • We focus on actionable checklists and minimal runnable commands you can adapt to your environment (AWS EKS, GKE, AKS, or self-hosted K8s).

    Template 1: Cluster and workload security

    Use this when auditing who can do what in the cluster and whether workloads follow baseline hardening.

    Checklist (mark Pass / Fail / N/A)

    | # | Check | How to verify | Notes | |---|--------|----------------|--------| | 1 | RBAC least privilege | kubectl get clusterrolebindings -o wide; review subjects and roles | Prefer namespaced Roles over ClusterRoles where possible | | 2 | No anonymous auth | kubectl get --raw /api/v1 | grep -i anonymous or check API server flags | Disable if not explicitly required | | 3 | Pod security (restricted) | kubectl get ns -o jsonpath='{range .items[]}{.metadata.name}{"\t"}{.metadata.labels}{"\n"}{end}' | Ensure prod namespaces have pod-security.kubernetes.io/enforce=restricted (or equivalent) | | 4 | Non-root containers | Check Dockerfile / image: USER not root; or use PSS | Scan Dockerfiles or image metadata | | 5 | Read-only root filesystem where possible | Deployment spec: securityContext.readOnlyRootFilesystem: true | Some apps need writable dirs; mount emptyDir for those | | 6 | No privileged containers in prod | kubectl get pods -A -o json \| jq '.items[].spec.containers[]? \| select(.securityContext.privileged==true)' | Should return empty | | 7 | Image pull policy and digest pinning | Deployments use imagePullPolicy: Always and digest (@sha256:...) or pinned tag | Avoid latest in prod | | 8 | Network policies present | kubectl get networkpolicies -A \| wc -l | At least default-deny or per-workload policies in critical namespaces |

    Example: quick RBAC dump for review

    Export ClusterRoleBindings and RoleBindings for offline review
    
kubectl get clusterrolebindings -o yaml > crb-audit-$(date +%Y%m%d).yaml
kubectl get rolebindings -A -o yaml > rb-audit-$(date +%Y%m%d).yaml

    Template 2: Container registry and image hygiene

    Focus: what's in the registry, who can pull/push, and whether images are scanned and signed.

    Checklist

    | # | Check | How to verify | Notes | |---|--------|----------------|--------| | 1 | Registry access is IAM/role-based | Review registry IAM policies (ECR, GCR, ACR, etc.) | No long-lived global pull credentials in CI | | 2 | Image scanning in pipeline | CI job runs Trivy, Clair, or vendor scanner on build | Fail build on HIGH/CRITICAL | | 3 | Base images from trusted sources | Inspect Dockerfile FROM; prefer distro LTS or vendor images | Document exceptions | | 4 | No secrets in images | Scan with TruffleHog or similar; no env vars with "secret" in CI | Use secret managers at runtime | | 5 | Image retention / lifecycle | Configure retention (e.g. keep last N tags per repo) | Reduces blast radius and cost | | 6 | Signing (optional but recommended) | Cosign or Notary; verify in admission controller | Enforce "signed only" in prod |

    Example: Trivy in CI (GitHub Actions)

    - name: Run Trivy image scanner
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myregistry/myapp:${{ github.sha }}'
    format: 'sarif'
    output: 'trivy-results.sarif'
    severity: 'CRITICAL,HIGH'
  env:
    TRIVY_EXIT_CODE: '1'

    Template 3: CI/CD and pipeline security

    Audit how code gets built, tested, and deployed — and where secrets and permissions live.

    Checklist

    | # | Check | How to verify | Notes | |---|--------|----------------|--------| | 1 | Pipelines use short-lived credentials | No long-lived API keys in env; use OIDC or workload identity where possible | GitHub OIDC, GitLab ID tokens, etc. | | 2 | Secrets in vault or secret manager | Scan pipeline YAML for literal secrets; use secret store references | e.g. ${{ secrets.DEPLOY_KEY }} not hardcoded | | 3 | Build from committed Dockerfile only | Pipeline builds image from repo, not ad-hoc docker run | Reproducible builds | | 4 | Deploy only from main/protected branch or tag | Branch protection + pipeline rules | No deploy from random forks | | 5 | Approval gate for prod | Manual approval or change-management integration | Document who can approve | | 6 | Pipeline logs and artifacts retention | Configure retention; no secrets in logs | Mask secrets in log output |

    Example: branch rule (GitHub Actions)

    on:
  push:
    branches: [main]
  workflow_dispatch:
jobs:
  deploy:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    # ... deploy steps

    Template 4: Cost and resource efficiency

    Cloud-native sprawl burns budget if nobody looks at requests/limits and idle resources.

    Checklist

    | # | Check | How to verify | Notes | |---|--------|----------------|--------| | 1 | CPU/memory requests and limits set | kubectl get pods -A -o custom-columns=... or use Kubecost / OpenCost | Avoid "no limits" in prod | | 2 | Right-sizing | Compare requests vs actual usage (metrics server or cloud billing) | Downsize over-provisioned workloads | | 3 | HPA/VPA in place for variable load | kubectl get hpa,vpa -A | Scale to zero or min replicas for batch where possible | | 4 | Unused volumes and snapshots | List PVs, PVCs, and cloud snapshots; delete detached | Schedule recurring review | | 5 | Idle or low-utilization nodes | Cluster autoscaler logs; remove single-replica dev namespaces from prod cluster | Consider separate dev cluster |

    Example: list pods without limits

    kubectl get pods -A -o json | jq -r '
  .items[] | select(.spec.containers[]? | .resources.limits == null) |
  "\(.metadata.namespace)/\(.metadata.name)"
'

    Template 5: Observability and incident readiness

    Can you detect and debug issues quickly? This template checks the basics.

    Checklist

    | # | Check | How to verify | Notes | |---|--------|----------------|--------| | 1 | Centralized logging | Logs from pods/clusters flow to one place (e.g. Loki, Elastic, cloud log) | Retention and access controls documented | | 2 | Metrics and dashboards | Prometheus/Grafana or cloud equivalent; key SLOs on dashboard | Latency, error rate, throughput | | 3 | Alerts on SLO breach and critical failures | Alertmanager or PagerDuty/Opsgenie; no alert storms | Run a game day to test | | 4 | Tracing for request flows | Sampling or full trace for critical paths | Trace ID in logs for correlation | | 5 | Runbooks for top alerts | Each alert has a runbook link or embedded steps | Kept in repo or wiki |

    How to run these audits

  • Schedule — Run full audit quarterly; security subset (Templates 1–3) after major infra or tooling changes.
  • Owner — Assign one person per template (or rotate) so someone owns the outcome.
  • Store results — Save checklist results (Pass/Fail/N/A) and command outputs in a dated doc or wiki. Example: audit-2026-02-cluster-security.md.
  • Track remediation — Open tickets for every Fail; close only after verification.

    Gotchas we ran into

  • RBAC dumps are huge. Filter by namespace or use a script to list only bindings that reference human users or broad service accounts; otherwise the YAML is unreadable.
  • Image scanning in CI is slow. Run scan in parallel with tests or use a separate "scan" job that doesn't block merge but must pass before deploy. Cache the scanner DB.
  • Cost tools need permissions. Give a read-only, scoped account to Kubecost/OpenCost (or cloud billing) so you don't grant more than needed.
  • Audit fatigue. If the checklist has 50 items, teams skip. Start with 5–10 must-haves per template and add more as they become habit.

    • Takeaway

    Pick one template (we suggest Template 1: cluster security) and run it this week. Export your RBAC and pod security context for one namespace, and fix one clear gap. Next quarter, run the full set and compare — you'll have a baseline instead of a one-off scramble.

    If you want a single file to share with your team, copy the checklists and runbook snippet above into a repo (e.g. docs/audits/) and version it so improvements stay in one place.
