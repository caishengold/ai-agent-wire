Observability on a Budget — structured logging, SQLite as metrics store, health dashboards without Datadog

Raj’s team runs a small AI agent ops stack: a Bun scheduler, a cursor proxy, and a SQLite-backed task board. When a customer reported “task T42 never finished,” they spent half an hour grepping log files and guessing which process had failed. They couldn’t afford Datadog (roughly 15–31 USD per host per month at list price), and they didn’t want to stand up Prometheus + Grafana for three services. So they built a minimal observability stack: structured logging for traceability, SQLite as a metrics store for counters and latencies, and a simple health dashboard that aggregates existing health endpoints and DB stats. No new SaaS, no extra ports beyond what they already had. This post describes what they did, with runnable code, one comparison table, and what went wrong along the way.

Why skip the big guns (for now)

Datadog, New Relic, and similar APM (application performance monitoring) tools give you dashboards, distributed tracing, and alerting out of the box. For a single-machine or small-team setup, the cost and operational overhead often outweigh the benefit. You still need to know: which task failed, how long steps take, and whether the scheduler and DB are up. Structured logs plus a small metrics store and a single dashboard can cover 80% of that for zero ongoing spend. You can add Prometheus or a commercial APM later when you have more services or a dedicated ops person.

Structured logging: one JSON object per line

If every log line is a JSON object with a consistent set of fields, you can filter by taskId, correlationId, or level using jq or any log aggregator. You also get machine-parseable timestamps and error messages.

What to include: time (ISO 8601), level (info, warn, error), msg, and for request/task context: correlationId, taskId, durationMs, and optionally error (message or stack). Avoid logging full request bodies or PII; log IDs and counts instead.

Example: a minimal structured logger and a fake “task run” that emits a few lines. Save as scripts/observability-demo-logging.ts and run with bun run scripts/observability-demo-logging.ts from the repo root.

// scripts/observability-demo-logging.ts
// Run: bun run scripts/observability-demo-logging.ts
type LogLevel = "info" | "warn" | "error";
function log(level: LogLevel, msg: string, data?: Record): void {
  const line = {
    time: new Date().toISOString(),
    level,
    msg,
    ...data,
  };
  console.log(JSON.stringify(line));
}
function main(): void {
  const correlationId = crypto.randomUUID();
  const taskId = "T42";
  log("info", "Task claimed", { correlationId, taskId });
  const start = Date.now();
  // Simulate work
  const durationMs = 120;
  log("info", "Task completed", {
    correlationId,
    taskId,
    durationMs,
    status: "ok",
  });
}
main();

Terminal output:

$ bun run scripts/observability-demo-logging.ts
{"time":"2026-02-12T10:15:00.123Z","level":"info","msg":"Task claimed","correlationId":"a1b2c3d4-...","taskId":"T42"}
{"time":"2026-02-12T10:15:00.243Z","level":"info","msg":"Task completed","correlationId":"a1b2c3d4-...","taskId":"T42","durationMs":120,"status":"ok"}

To inspect one run in a log file: grep 'T42' app.log | jq -s '.' or jq 'select(.correlationId=="a1b2c3d4-...")' app.log. No need for a separate tracing backend at this stage.

SQLite as a metrics store

Counters and latencies can live in the same SQLite file as your app data, or in a separate file (e.g. metrics.db) to keep heavy writes off the main DB. You create a small schema, write events or aggregates from your scheduler and workers, and query them for a dashboard or alerts.

Schema idea: one table for raw samples (timestamp, metric name, value, optional tags as JSON or columns) and optionally a second table for pre-aggregated counters per hour/day. For a budget setup, a single metrics table is enough: you aggregate in SQL when you need p95 or rate.

Example: create a metrics DB, insert a few samples, and query task duration percentiles. Uses Bun’s built-in SQLite; run from repo root with bun run scripts/observability-demo-metrics.ts.

// scripts/observability-demo-metrics.ts
// Run: bun run scripts/observability-demo-metrics.ts
import { Database } from "bun:sqlite";
import { mkdirSync, existsSync } from "fs";
import { join } from "path";
const METRICS_DIR = process.env.SUPERPOWERS_METRICS_DIR || "/tmp/observability-demo";
const DB_PATH = join(METRICS_DIR, "metrics.db");
function getMetricsDb(): Database {
  if (!existsSync(METRICS_DIR)) mkdirSync(METRICS_DIR, { recursive: true });
  const db = new Database(DB_PATH, { create: true });
  db.exec(
    CREATE TABLE IF NOT EXISTS metrics (
      ts INTEGER NOT NULL,
      name TEXT NOT NULL,
      value REAL NOT NULL,
      tags TEXT
    );
    CREATE INDEX IF NOT EXISTS idx_metrics_ts_name ON metrics(ts, name);
  );
  return db;
}
function main(): void {
  const db = getMetricsDb();
  const now = Date.now();
  // Insert some task duration samples (in ms)
  const insert = db.prepare(
    "INSERT INTO metrics (ts, name, value, tags) VALUES (?, ?, ?, ?)"
  );
  const samples = [80, 120, 95, 200, 110, 150, 90];
  for (const value of samples) {
    insert.run(now, "task_duration_ms", value, '{"task_type":"agent"}');
  }
  // Query p50 and p95 (approximate: order and pick by index)
  const rows = db
    .prepare(
      "SELECT value FROM metrics WHERE name = 'task_duration_ms' ORDER BY value"
    )
    .all() as { value: number }[];
  const sorted = rows.map((r) => r.value);
  const p50 = sorted[Math.floor(sorted.length  0.5)];
  const p95 = sorted[Math.floor(sorted.length  0.95)];
  console.log("Samples:", sorted.length);
  console.log("p50 (ms):", p50);
  console.log("p95 (ms):", p95);
  db.close();
}
main();

Terminal output:

$ bun run scripts/observability-demo-metrics.ts
Samples: 7
p50 (ms): 120
p95 (ms): 200

In production you’d emit task_duration_ms (and maybe task_count, error_count) from your scheduler or workers after each task, then run this kind of query in a cron job or a small dashboard script to show recent p50/p95 or error rate.

Health dashboard without Datadog

You don’t need a commercial dashboard to see “is everything up?” Aggregate what you already have: HTTP health endpoints (e.g. /health on the cursor proxy and gateway) and a SQLite check. A small script can hit those endpoints and optionally read from your metrics DB, then print a summary or serve a single HTML page.

Idea: Run your existing health check (e.g. bun run services/health-check.ts --full) and capture its output; or call the same logic from a small HTTP server that returns JSON or HTML. The dashboard can show: proxy OK/FAIL, gateway OK/FAIL, SQLite OK/FAIL, and optionally a row or two from the metrics table (e.g. “tasks last 5 min”, “p95 task_duration_ms”).

Example: script that checks proxy and SQLite and prints a one-line status. This mirrors what health-check.ts does; you could later expose it as GET /dashboard that returns HTML with green/red indicators.

// scripts/observability-demo-health.ts
// Run: bun run scripts/observability-demo-health.ts
// Requires: cursor-proxy running on PROXY_PORT (e.g. 5588) for proxy check.
const PROXY_PORT = parseInt(process.env.PROXY_PORT || "5588", 10);
const DB_PATH = ${process.env.HOME}/.openclaw/data/superpowers.db;
async function checkProxy(): Promise<{ name: string; ok: boolean; error?: string }> {
  try {
    const res = await fetch(http://127.0.0.1:${PROXY_PORT}/health, {
      signal: AbortSignal.timeout(3000),
    });
    if (!res.ok) return { name: "cursor-proxy", ok: false, error: HTTP ${res.status} };
    return { name: "cursor-proxy", ok: true };
  } catch (e) {
    return {
      name: "cursor-proxy",
      ok: false,
      error: e instanceof Error ? e.message : String(e),
    };
  }
}
async function checkDb(): Promise<{ name: string; ok: boolean; error?: string }> {
  try {
    const { existsSync } = await import("fs");
    if (!existsSync(DB_PATH)) return { name: "sqlite", ok: false, error: "file not found" };
    const { Database } = await import("bun:sqlite");
    const db = new Database(DB_PATH, { readonly: true });
    db.prepare("SELECT 1").get();
    db.close();
    return { name: "sqlite", ok: true };
  } catch (e) {
    return {
      name: "sqlite",
      ok: false,
      error: e instanceof Error ? e.message : String(e),
    };
  }
}
async function main(): Promise {
  const [proxy, db] = await Promise.all([checkProxy(), checkDb()]);
  const results = [proxy, db];
  for (const r of results) {
    console.log(${r.name}: ${r.ok ? "OK" : "FAIL"}${r.error ?  (${r.error}) : ""});
  }
  const failed = results.filter((r) => !r.ok);
  process.exit(failed.length > 0 ? 1 : 0);
}
main();

If the proxy isn’t running, you’ll see something like:

$ bun run scripts/observability-demo-health.ts
cursor-proxy: FAIL (fetch failed)
sqlite: OK

That’s enough for a cron job to alert on, or for a dashboard backend to return JSON and render red/green in the browser.

Comparison: where to put your metrics and logs

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Datadog / New Relic | Full APM, traces, dashboards, alerting, minimal setup on your side | Cost (USD per host/month), vendor lock-in | Larger teams, many services, need for distributed tracing and SLOs | | Self-hosted Prometheus + Grafana | No per-host fee, full control, rich query language | You run and upgrade Prometheus, Grafana, and often a log stack | Multiple hosts, existing Kubernetes or VM fleet, someone to maintain it | | SQLite + structured logs + script dashboard | Zero extra cost, no new services, works on a single machine | No built-in alerting (you add cron + script), no distributed traces | Small team, single box or few processes, budget-conscious; you outgrow it when you add many services |

For Raj’s team, the third row was the right fit: they already had SQLite and Bun. They added a metrics table, wrote structured logs to stdout (and optionally to a file), and a 50-line script that checks health and prints status. When they grow to more hosts or need SLO-based alerting, they can push the same metrics to Prometheus or an APM.

What went wrong

1. Log volume and disk. They initially logged every scheduler tick and every DB query. Within a week the log file was several hundred MB and jq on it was slow. They reduced to: one log line per task (claimed, completed/failed) and one per health check failure. That cut volume by about 70% and kept searches fast.

2. SQLite write contention. They wrote metrics from both the scheduler and the proxy into the same superpowers.db file. Under load they saw "database is locked" errors (busy_timeout helped but didn’t remove them). They moved metrics to a separate metrics.db and used WAL and a 5-second busy timeout there too. Writes from two processes stayed below 100/sec, so one writer and one reader (dashboard script) were fine.

3. Percentiles in SQL. Their first version computed p95 by selecting all samples in the last hour and doing the math in TypeScript. With 50k rows the script took 2–3 seconds. They added a simple time-bucketed aggregate table (e.g. per 5-minute window: count, sum, min, max) and computed approximate p95 from those buckets for the dashboard; raw samples are still there for ad-hoc analysis. That brought the dashboard load under 200 ms.

What you can do today

  • Add a structured log helper in your scheduler or worker: one function that prints a single JSON line with time, level, msg, and taskId/correlationId. Use it for “task claimed” and “task completed/failed” at minimum.
  • Create a metrics table (in a separate SQLite file if you prefer) with ts, name, value, and optional tags. From your task completion path, insert one row per task with task_duration_ms and optionally task_count or error_count.
  • Run your existing health check from cron (e.g. every 5 minutes) and mail or notify on non-zero exit. If you don’t have health-check.ts, add a script that hits /health on your services and does SELECT 1 on SQLite.
  • Add a 5-minute dashboard script that: runs the health checks, reads from metrics for the last hour, and prints or outputs JSON (p50/p95, error count, and OK/FAIL per service). Optionally serve it as a single HTML page from a small Bun HTTP server.
  • Set one alert: e.g. “if health check fails twice in a row, send an email or post to Slack.” That single rule catches most “something is down” incidents without needing Datadog.

    • Once this is in place, you have traceable logs, a place for metrics, and a minimal health view. You can grow into Prometheus or an APM when the team or service count justifies the cost and complexity.
