Comparing load balancing approaches in API gateway design

Your gateway is getting 8,000 requests per second. Three of your backend instances are healthy; one is starting to thrash. Without a clear strategy for spreading traffic, you might send half your users to the slow instance and watch p99 latency spike. The choice of load balancing algorithm is not cosmetic — it shapes reliability and performance for every downstream service.

This post compares the main approaches we see in API gateways (Kong, Envoy, AWS ALB, nginx, etc.) and when each one pays off. We focus on what to pick for typical REST/gRPC backends and what we learned the hard way.

Why the algorithm matters

A gateway sits in front of multiple instances of the same service. Its job is to choose, for each request, which instance handles it. The algorithm affects:

  • Fairness — whether some instances are overloaded while others sit idle
  • Session affinity — whether a user sticks to one instance (needed for in-memory state or connection pooling)
  • Failure handling — how quickly traffic leaves unhealthy or slow nodes
  • Predictability — whether you can reason about where a given request will go (e.g. for debugging or compliance)

    • No single strategy is best for every workload. Picking one is a product of your traffic shape, backend behavior, and ops constraints.

    Round-robin

    Requests are distributed in a fixed order: A → B → C → A → B → C. Implementation is simple and behavior is easy to reason about.

    When it works well: Stateless services, similar instance sizes, roughly equal cost per request. Good default when you have no special requirements.

    Limitation: It ignores current load. If one instance is slow (e.g. GC pause or a heavy query), it still gets the same share of new requests. You need health checks and possibly circuit breaking on top.

    Request 1 → Instance A
Request 2 → Instance B
Request 3 → Instance C
Request 4 → Instance A
...

    Weighted round-robin

    Same idea as round-robin, but you assign weights (e.g. 2 : 1 : 1). Stronger instances get more traffic. Useful when capacity differs (e.g. 4-core vs 2-core nodes) or when you’re draining a smaller pool.

    When it works well: Mixed instance sizes, canary rollouts (e.g. 10% to new version, 90% to current). You need to keep weights in sync with actual capacity; otherwise you under- or over-use nodes.

    Least connections

    The gateway (or proxy) tracks how many active connections (or in-flight requests) each backend has and sends new requests to the one with the fewest. This adapts to real-time load.

    When it works well: Long-lived or variable-cost requests — WebSockets, streaming, or endpoints where some calls take 10 ms and others 2 seconds. Round-robin would overload the instance that happens to be handling the slow ones; least connections naturally balances.

    Gotcha: You need accurate connection or request counts. Some gateways count TCP connections; others count HTTP/2 streams or in-flight requests. For HTTP/1.1, connection count is a decent proxy; for HTTP/2, in-flight request count is better.

    Sticky sessions (session affinity)

    A hash of some key (e.g. cookie, header, or client IP) decides the backend. The same key always maps to the same instance (until it fails or the pool changes).

    When it works well: In-memory sessions, local caches, or connection pooling that benefit from repeated use of the same server. Some compliance or audit requirements also prefer deterministic routing.

    Limitation: Imbalance — a few very active keys can overload one instance. Also, when an instance goes down, all traffic that was bound to it must be re-assigned; rehashing can cause a thundering herd of new connections. Use with timeouts and small sticky windows when possible.

    Hash("session_id_xyz") % 3 → Instance B  (always B for this session)

    Geographic and latency-based routing

    Traffic is steered by region or by measured latency (e.g. health checks that report RTT). Users in Tokyo hit Tokyo backends; users in Frankfurt hit EU backends. Or the gateway probes backends and sends requests to the one with lowest latency.

    When it works well: Multi-region deployments, data residency, or reducing cross-region latency. Essential when backends are far apart.

    Gotcha: Probes can lie (e.g. one region has great probe latency but poor user-path latency). Combine with real-user metrics and failover rules so a bad region doesn’t get all traffic just because probes look good.

    Health checks and failover

    Whatever algorithm you use, it should integrate with health checks. Unhealthy or failing instances should get no new traffic; optionally, existing connections should be drained. Common patterns:

  • Active health checks: Gateway periodically calls a /health (or similar) and marks the instance down after N failures.
  • Passive (reaction to errors): After 5xx or connection errors, temporarily skip the instance. This catches issues that /health might miss (e.g. DB only failing under load).
  • Gradual recovery: When an instance comes back, send it a small fraction of traffic first (e.g. 10%) to avoid overloading it or hiding flakiness.

    • We’ve seen gateways that do round-robin but ignore health — they keep sending traffic to a dead instance. Always wire the load balancer to a clear notion of “healthy” and “unhealthy.”

    What we’d do differently

  • We started with round-robin everywhere. For a few services with long-running requests, switching to least-connections cut p99 latency by a large margin because we stopped piling work onto already-busy instances.
  • We used IP-based stickiness for a stateful service. A few corporate NATs sent huge volume from one “client”; we moved to cookie-based affinity and rebalanced the pool.
  • We once relied only on active health checks; a backend passed /health but returned 5xx under load. Adding passive failure detection (and short circuiting) reduced user-facing errors.

    • Takeaway

    Choose by workload: round-robin for simple stateless APIs, weighted round-robin when capacity is uneven or you’re canarying, least connections when request cost or lifetime varies a lot, and sticky sessions only when you need affinity — and then watch for hot spots. Pair any strategy with health checks and failover so the algorithm runs over a pool you trust. If you’re building or tuning a gateway today, pick one algorithm, measure p50/p99 and error rate per backend, then try the next candidate and compare. A few hours of experiments will beat guessing.
