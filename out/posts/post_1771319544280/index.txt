8:T279f,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Comparing load balancing approaches in API gateway design</h1></p><p class="text-slate-300 leading-relaxed mb-4">Your gateway is getting 8,000 requests per second. Three of your backend instances are healthy; one is starting to thrash. Without a clear strategy for spreading traffic, you might send half your users to the slow instance and watch p99 latency spike. The choice of load balancing algorithm is not cosmetic — it shapes reliability and performance for every downstream service.</p><p class="text-slate-300 leading-relaxed mb-4">This post compares the main approaches we see in API gateways (Kong, Envoy, AWS ALB, nginx, etc.) and when each one pays off. We focus on what to pick for typical REST/gRPC backends and what we learned the hard way.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the algorithm matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">A gateway sits in front of multiple instances of the same service. Its job is to choose, for each request, which instance handles it. The algorithm affects:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Fairness</strong> — whether some instances are overloaded while others sit idle</li>
<li class="ml-4 list-disc text-slate-300"><strong>Session affinity</strong> — whether a user sticks to one instance (needed for in-memory state or connection pooling)</li>
<li class="ml-4 list-disc text-slate-300"><strong>Failure handling</strong> — how quickly traffic leaves unhealthy or slow nodes</li>
<li class="ml-4 list-disc text-slate-300"><strong>Predictability</strong> — whether you can reason about where a given request will go (e.g. for debugging or compliance)</li></p><p class="text-slate-300 leading-relaxed mb-4">No single strategy is best for every workload. Picking one is a product of your traffic shape, backend behavior, and ops constraints.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Round-robin</h2></p><p class="text-slate-300 leading-relaxed mb-4">Requests are distributed in a fixed order: A → B → C → A → B → C. Implementation is simple and behavior is easy to reason about.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it works well:</strong> Stateless services, similar instance sizes, roughly equal cost per request. Good default when you have no special requirements.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Limitation:</strong> It ignores current load. If one instance is slow (e.g. GC pause or a heavy query), it still gets the same share of new requests. You need health checks and possibly circuit breaking on top.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Request 1 → Instance A
Request 2 → Instance B
Request 3 → Instance C
Request 4 → Instance A
...
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Weighted round-robin</h2></p><p class="text-slate-300 leading-relaxed mb-4">Same idea as round-robin, but you assign weights (e.g. 2 : 1 : 1). Stronger instances get more traffic. Useful when capacity differs (e.g. 4-core vs 2-core nodes) or when you’re draining a smaller pool.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it works well:</strong> Mixed instance sizes, canary rollouts (e.g. 10% to new version, 90% to current). You need to keep weights in sync with actual capacity; otherwise you under- or over-use nodes.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Least connections</h2></p><p class="text-slate-300 leading-relaxed mb-4">The gateway (or proxy) tracks how many active connections (or in-flight requests) each backend has and sends new requests to the one with the fewest. This adapts to real-time load.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it works well:</strong> Long-lived or variable-cost requests — WebSockets, streaming, or endpoints where some calls take 10 ms and others 2 seconds. Round-robin would overload the instance that happens to be handling the slow ones; least connections naturally balances.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> You need accurate connection or request counts. Some gateways count TCP connections; others count HTTP/2 streams or in-flight requests. For HTTP/1.1, connection count is a decent proxy; for HTTP/2, in-flight request count is better.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Sticky sessions (session affinity)</h2></p><p class="text-slate-300 leading-relaxed mb-4">A hash of some key (e.g. cookie, header, or client IP) decides the backend. The same key always maps to the same instance (until it fails or the pool changes).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it works well:</strong> In-memory sessions, local caches, or connection pooling that benefit from repeated use of the same server. Some compliance or audit requirements also prefer deterministic routing.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Limitation:</strong> Imbalance — a few very active keys can overload one instance. Also, when an instance goes down, all traffic that was bound to it must be re-assigned; rehashing can cause a thundering herd of new connections. Use with timeouts and small sticky windows when possible.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Hash("session_id_xyz") % 3 → Instance B  (always B for this session)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Geographic and latency-based routing</h2></p><p class="text-slate-300 leading-relaxed mb-4">Traffic is steered by region or by measured latency (e.g. health checks that report RTT). Users in Tokyo hit Tokyo backends; users in Frankfurt hit EU backends. Or the gateway probes backends and sends requests to the one with lowest latency.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When it works well:</strong> Multi-region deployments, data residency, or reducing cross-region latency. Essential when backends are far apart.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> Probes can lie (e.g. one region has great probe latency but poor user-path latency). Combine with real-user metrics and failover rules so a bad region doesn’t get all traffic just because probes look good.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Health checks and failover</h2></p><p class="text-slate-300 leading-relaxed mb-4">Whatever algorithm you use, it should integrate with health checks. Unhealthy or failing instances should get no new traffic; optionally, existing connections should be drained. Common patterns:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Active health checks:</strong> Gateway periodically calls a /health (or similar) and marks the instance down after N failures.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Passive (reaction to errors):</strong> After 5xx or connection errors, temporarily skip the instance. This catches issues that /health might miss (e.g. DB only failing under load).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Gradual recovery:</strong> When an instance comes back, send it a small fraction of traffic first (e.g. 10%) to avoid overloading it or hiding flakiness.</li></p><p class="text-slate-300 leading-relaxed mb-4">We’ve seen gateways that do round-robin but ignore health — they keep sending traffic to a dead instance. Always wire the load balancer to a clear notion of “healthy” and “unhealthy.”</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we’d do differently</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">We started with round-robin everywhere. For a few services with long-running requests, switching to least-connections cut p99 latency by a large margin because we stopped piling work onto already-busy instances.</li>
<li class="ml-4 list-disc text-slate-300">We used IP-based stickiness for a stateful service. A few corporate NATs sent huge volume from one “client”; we moved to cookie-based affinity and rebalanced the pool.</li>
<li class="ml-4 list-disc text-slate-300">We once relied only on active health checks; a backend passed /health but returned 5xx under load. Adding passive failure detection (and short circuiting) reduced user-facing errors.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Choose by workload: <strong>round-robin</strong> for simple stateless APIs, <strong>weighted round-robin</strong> when capacity is uneven or you’re canarying, <strong>least connections</strong> when request cost or lifetime varies a lot, and <strong>sticky sessions</strong> only when you need affinity — and then watch for hot spots. Pair any strategy with <strong>health checks and failover</strong> so the algorithm runs over a pool you trust. If you’re building or tuning a gateway today, pick one algorithm, measure p50/p99 and error rate per backend, then try the next candidate and compare. A few hours of experiments will beat guessing.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
