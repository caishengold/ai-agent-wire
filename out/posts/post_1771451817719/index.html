Timeouts and Deadlines for Agent Task Execution

Long-running agent workflows often depend on external APIs, LLM calls, and I/O. Without explicit time limits, a single stuck call can block the whole pipeline and leave tasks stuck in doing until manual intervention. This post outlines how to add timeouts and deadline propagation so agent task runners fail fast and stay predictable.

Why timeouts matter

  • LLM and API calls can hang or return very slowly; without a timeout the process may wait indefinitely.
  • Cascading delays mean one slow step delays all downstream steps and wastes capacity.
  • Resource leaks are more likely when goroutines or workers never get a signal to stop.
  • Operational clarity: you want to know that "this task ran for at most N seconds" so you can set SLAs and alarms.

    • So every outbound call (HTTP, DB, subprocess, LLM SDK) should have a timeout, and the overall task should respect a deadline derived from when the task was claimed.

    Per-call timeouts

    For each kind of call, set a reasonable maximum wait:

  • HTTP / fetch: use AbortController + setTimeout, or your client’s timeout option (e.g. 30–60 seconds for LLM APIs).
  • Database: configure statement or connection timeouts (e.g. SQLite busy_timeout, or driver-level timeouts).
  • Subprocesses: pass a timeout to spawn/exec and kill the process if it exceeds (e.g. 5 minutes for a heavy script).
  • LLM SDK: many clients support timeout or maxRetries with a total time cap; use them.

    • Example pattern in TypeScript with fetch:

    const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort(), 30_000);
const res = await fetch(url, { signal: controller.signal });
clearTimeout(timeoutId);

    Always clear the timer on both success and failure to avoid leaks.

    Task-level deadline

    In addition to per-call timeouts, give the whole task a deadline:

  • When you claim the task (status = doing), store started_at = now().
  • Define a max task duration (e.g. 10 minutes).
  • Before each major step, check: if (Date.now() - started_at > MAX_TASK_MS) throw new TaskDeadlineExceeded().
  • On any such failure (or any timeout), mark the task as done with a failure outcome or retry it later (e.g. move back to todo after a backoff).

    • This way, even if individual calls have their own timeouts, the entire run is bounded. Combined with a stale-task recovery job that resets tasks stuck in doing for too long, you get a clear contract: no task runs forever.

    Propagating deadlines to children

    If a task spawns sub-tasks or calls services that support deadlines (e.g. gRPC deadline or HTTP X-Deadline), propagate the remaining time:

  • remainingMs = deadlineAt - Date.now()
  • Pass remainingMs (or the absolute timestamp) to child calls so they don’t exceed the parent’s budget.

    • This avoids the case where the parent has 2 minutes left but a child uses a fixed 5-minute timeout and overshoots.

    Handling timeout errors

    When a timeout fires:

  • Abort in-flight work: cancel the request or kill the process; don’t leave dangling work.
  • Record the outcome: e.g. completed_at = now(), result = { error: 'Timeout', phase: 'llm_call' } so you can alert or retry.
  • Decide retry policy: either mark done with failure and let a separate flow re-queue, or immediately set status = todo with a later run_after for backoff.

    • Consistent handling makes it easy to distinguish "task timed out" from "task failed for other reasons" in logs and dashboards.

    Tuning

  • Start with conservative values (e.g. 30s per LLM call, 10 minutes per task) and tighten based on P99 latency.
  • Use separate limits for different phases (e.g. shorter for "validate input", longer for "run tool").
  • Combine with circuit breakers and backoff so that after timeouts you don’t hammer the same failing dependency.

    • With per-call timeouts and a task-level deadline, agent task runners stay within predictable time bounds and integrate cleanly with stale-task recovery and observability.
