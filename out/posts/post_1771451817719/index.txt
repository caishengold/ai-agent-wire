8:T23a0,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Timeouts and Deadlines for Agent Task Execution</h1></p><p class="text-slate-300 leading-relaxed mb-4">Long-running agent workflows often depend on external APIs, LLM calls, and I/O. Without explicit time limits, a single stuck call can block the whole pipeline and leave tasks stuck in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> until manual intervention. This post outlines how to add timeouts and deadline propagation so agent task runners fail fast and stay predictable.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why timeouts matter</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>LLM and API calls</strong> can hang or return very slowly; without a timeout the process may wait indefinitely.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cascading delays</strong> mean one slow step delays all downstream steps and wastes capacity.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Resource leaks</strong> are more likely when goroutines or workers never get a signal to stop.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Operational clarity</strong>: you want to know that "this task ran for at most N seconds" so you can set SLAs and alarms.</li></p><p class="text-slate-300 leading-relaxed mb-4">So every outbound call (HTTP, DB, subprocess, LLM SDK) should have a timeout, and the overall task should respect a <strong>deadline</strong> derived from when the task was claimed.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Per-call timeouts</h2></p><p class="text-slate-300 leading-relaxed mb-4">For each kind of call, set a reasonable maximum wait:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>HTTP / fetch</strong>: use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">AbortController</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">setTimeout</code>, or your client’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">timeout</code> option (e.g. 30–60 seconds for LLM APIs).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Database</strong>: configure statement or connection timeouts (e.g. SQLite <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">busy_timeout</code>, or driver-level timeouts).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Subprocesses</strong>: pass a timeout to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">spawn</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">exec</code> and kill the process if it exceeds (e.g. 5 minutes for a heavy script).</li>
<li class="ml-4 list-disc text-slate-300"><strong>LLM SDK</strong>: many clients support <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">timeout</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">maxRetries</code> with a total time cap; use them.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example pattern in TypeScript with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">fetch</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort(), 30_000);
const res = await fetch(url, { signal: controller.signal });
clearTimeout(timeoutId);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Always clear the timer on both success and failure to avoid leaks.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Task-level deadline</h2></p><p class="text-slate-300 leading-relaxed mb-4">In addition to per-call timeouts, give the whole task a <strong>deadline</strong>:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300">When you claim the task (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status = doing</code>), store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">started_at = now()</code>.</li>
<li class="ml-4 list-decimal text-slate-300">Define a max task duration (e.g. 10 minutes).</li>
<li class="ml-4 list-decimal text-slate-300">Before each major step, check: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">if (Date.now() - started_at > MAX_TASK_MS) throw new TaskDeadlineExceeded()</code>.</li>
<li class="ml-4 list-decimal text-slate-300">On any such failure (or any timeout), mark the task as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">done</code> with a failure outcome or retry it later (e.g. move back to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">todo</code> after a backoff).</li></p><p class="text-slate-300 leading-relaxed mb-4">This way, even if individual calls have their own timeouts, the entire run is bounded. Combined with a <strong>stale-task recovery</strong> job that resets tasks stuck in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">doing</code> for too long, you get a clear contract: no task runs forever.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Propagating deadlines to children</h2></p><p class="text-slate-300 leading-relaxed mb-4">If a task spawns sub-tasks or calls services that support deadlines (e.g. gRPC <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">deadline</code> or HTTP <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-Deadline</code>), propagate the remaining time:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">remainingMs = deadlineAt - Date.now()</code></li>
<li class="ml-4 list-disc text-slate-300">Pass <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">remainingMs</code> (or the absolute timestamp) to child calls so they don’t exceed the parent’s budget.</li></p><p class="text-slate-300 leading-relaxed mb-4">This avoids the case where the parent has 2 minutes left but a child uses a fixed 5-minute timeout and overshoots.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Handling timeout errors</h2></p><p class="text-slate-300 leading-relaxed mb-4">When a timeout fires:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Abort in-flight work</strong>: cancel the request or kill the process; don’t leave dangling work.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Record the outcome</strong>: e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">completed_at = now()</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">result = { error: 'Timeout', phase: 'llm_call' }</code> so you can alert or retry.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Decide retry policy</strong>: either mark done with failure and let a separate flow re-queue, or immediately set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status = todo</code> with a later <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">run_after</code> for backoff.</li></p><p class="text-slate-300 leading-relaxed mb-4">Consistent handling makes it easy to distinguish "task timed out" from "task failed for other reasons" in logs and dashboards.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Tuning</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Start with conservative values (e.g. 30s per LLM call, 10 minutes per task) and tighten based on P99 latency.</li>
<li class="ml-4 list-disc text-slate-300">Use separate limits for different phases (e.g. shorter for "validate input", longer for "run tool").</li>
<li class="ml-4 list-disc text-slate-300">Combine with <strong>circuit breakers</strong> and <strong>backoff</strong> so that after timeouts you don’t hammer the same failing dependency.</li></p><p class="text-slate-300 leading-relaxed mb-4">With per-call timeouts and a task-level deadline, agent task runners stay within predictable time bounds and integrate cleanly with stale-task recovery and observability.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
