Building a Task Scheduler with Scheduler.ts

Aiko Chen, lead developer at Tech Innovators Ltd., faced a recurring problem every Monday morning. Her team spent 45 minutes manually generating sales analytics reports—copying data from three different databases, running calculations, and formatting the output in spreadsheets. The process was error-prone and took away valuable time from actual analysis work.

In early 2024, Aiko decided to automate this workflow. She needed a scheduler that could run tasks at specific times, handle failures gracefully, and maintain a clear record of what had executed and when. After evaluating several approaches, she built a custom task scheduler using Scheduler.ts, a powerful Node.js library that provides exactly this functionality.

This tutorial walks through building that same scheduler. You will learn how to define tasks using templates, track execution state with SQLite, schedule jobs with cron expressions, and handle failures with retry logic.

Task Templates

Task templates form the foundation of any scheduler. They encapsulate everything the scheduler needs to know about a job: what to run, when to run it, and how to handle problems.

Creating a Task Template

The TaskTemplate class accepts a configuration object with several key properties. The name identifies the task for logging and monitoring. The cron expression defines the schedule. The taskFunction contains the actual work to perform.

import { TaskTemplate } from 'scheduler.ts';
interface SalesReportData {
  region: string;
  startDate: string;
  endDate: string;
}
async function generateSalesReport(): Promise {
  console.log('Fetching sales data from databases...');
  
  // Simulate database queries
  await new Promise(resolve => setTimeout(resolve, 1000));
  
  return {
    region: 'North America',
    startDate: '2024-03-11',
    endDate: '2024-03-15'
  };
}
const salesReportTask = new TaskTemplate({
  name: 'Sales Analytics Report',
  cron: '0 10   1,3', // 10:00 AM every Monday and Wednesday
  taskFunction: generateSalesReport,
  retryStrategy: {
    maxRetries: 3,
    interval: 60000, // Wait 1 minute between attempts
  },
});

The retry strategy is particularly important. Network calls fail. Databases timeout. External services become unavailable. Without retries, a single failure would prevent the report from generating until the next scheduled run.

SQLite State Machine

The scheduler needs to know the current state of every task. Is it pending? Running? Completed? Failed? This information lives in the SQLite state machine, which persists across application restarts.

Initializing the State Machine

Initializing the state machine creates the necessary database tables if they do not exist. The SQLite database file is portable and requires no separate server process, making it ideal for single-instance deployments.

import { SQLiteStateMachine } from 'scheduler.ts';
const stateMachine = new SQLiteStateMachine({
  databasePath: './scheduler-state.db',
  enableWAL: true, // Write-Ahead Logging for better concurrency
});
await stateMachine.initialize();
console.log('State machine ready. Current tasks:', 
  await stateMachine.getTaskStatuses()
);

The state machine tracks not just success or failure, but also intermediate states like "retrying" and "scheduled." This visibility becomes critical when debugging why a particular run did not execute.

Querying Task History

You can query the state machine to understand historical execution patterns:

interface TaskExecution {
  taskId: string;
  status: 'pending' | 'running' | 'completed' | 'failed' | 'retrying';
  startTime: Date;
  endTime?: Date;
  error?: string;
  attemptNumber: number;
}
// Get executions from the past week
const recentExecutions = await stateMachine.queryExecutions({
  taskName: 'Sales Analytics Report',
  startDate: new Date('2024-03-11'),
  endDate: new Date('2024-03-18'),
});
console.log(Found ${recentExecutions.length} executions);

This history helps identify patterns. If a task consistently fails at a particular time, you can investigate whether external dependencies are experiencing issues.

Cron Triggers

Cron expressions are the standard way to describe time-based schedules. The format consists of five fields: minute, hour, day of month, month, and day of week.

Setting Up Cron Triggers

import { CronTrigger } from 'scheduler.ts';
const cronTrigger = new CronTrigger({
  cron: '0 10   1,3',
  taskTemplate: salesReportTask,
  stateMachine: stateMachine,
  timezone: 'America/New_York', // Ensure runs happen at local time
});
await cronTrigger.start();
console.log('Scheduler started. Next run:', cronTrigger.getNextRunTime());

The timezone parameter is crucial for distributed teams. A job scheduled for "10 AM" means different absolute times depending on where your servers and users are located.

Common Cron Expressions

| Expression | Schedule | Use Case | |------------|----------|----------| | 0 | Every hour | Hourly data aggregation | | 0 0 | Daily at midnight | Daily backup jobs | | 0 9 1-5 | Weekdays at 9 AM | Morning reports | | 0 /6 | Every 6 hours | Periodic sync jobs | | 0 0 1 | First of month | Monthly billing runs |

Retry Strategy

Transient failures are inevitable in distributed systems. A retry strategy determines how the scheduler responds when a task fails.

Implementing Exponential Backoff

Linear retries (waiting the same amount of time between attempts) often make things worse. If a service is overloaded, all concurrent retry attempts can exacerbate the problem. Exponential backoff spreads retry attempts over increasing time intervals.

import { RetryStrategy } from 'scheduler.ts';
const retryStrategy = new RetryStrategy({
  maxRetries: 3,
  baseInterval: 60000, // Start with 1 minute
  maxInterval: 300000, // Cap at 5 minutes
  backoffMultiplier: 2, // Double the wait each attempt
  retryableErrors: ['ECONNREFUSED', 'ETIMEDOUT', 'ENOTFOUND'],
});
salesReportTask.retryStrategy = retryStrategy;
// When the task fails, the scheduler automatically:
// Attempt 1: Wait 1 minute, then retry
// Attempt 2: Wait 2 minutes, then retry  
// Attempt 3: Wait 4 minutes, then retry (capped at maxInterval)

The retryableErrors array ensures the scheduler only retries on transient issues. Permanent failures (invalid credentials, malformed requests) should fail immediately rather than waste resources retrying.

Putting It All Together

Here is how the complete scheduler initialization looks:

import { Scheduler } from 'scheduler.ts';
async function main() {
  const stateMachine = new SQLiteStateMachine({
    databasePath: './scheduler-state.db',
  });
  
  await stateMachine.initialize();
  
  const salesReportTask = new TaskTemplate({
    name: 'Sales Analytics Report',
    cron: '0 10   1,3',
    taskFunction: generateSalesReport,
    retryStrategy: new RetryStrategy({
      maxRetries: 3,
      baseInterval: 60000,
      backoffMultiplier: 2,
    }),
  });
  
  const scheduler = new Scheduler({
    stateMachine,
    maxConcurrentTasks: 5,
  });
  
  scheduler.registerTask(salesReportTask);
  await scheduler.start();
  
  console.log('Scheduler running. Press Ctrl+C to stop.');
}
main().catch(console.error);

The Scheduler class manages the overall lifecycle. It handles concurrent task limits (preventing resource exhaustion), graceful shutdown (waiting for running tasks to complete), and error logging.

For Aiko's use case—running reports on a single server without additional infrastructure—Scheduler.ts provides the best balance of features and simplicity. If she later needed to scale to multiple workers, she would need to migrate to BullMQ or a similar distributed solution.

Lessons Learned

Building production schedulers reveals patterns that are not obvious during development. Here are the key insights from Aiko's implementation:

Always define retry strategies from the start. Adding retries after a production failure is more stressful than planning ahead. Set reasonable defaults and adjust based on observed failure patterns.

Store execution history, not just current state. When troubleshooting a missing report from two days ago, you will need to know whether it ran, failed, or never triggered. The state machine should persist this information.

Timezone handling matters more than expected. A job scheduled for "10 AM" in New York runs at 3 PM UTC. If your database is in London and your users are in Tokyo, you need to be explicit about which timezone applies.

Test cron expressions before deploying. Use tools like crontab.guru to validate your expressions. A small typo can cause jobs to run at completely wrong times—or not at all.

Graceful shutdown prevents data loss. When the application receives a termination signal, wait for the current task to complete before exiting. Abrupt termination can leave tasks in inconsistent states.

Actionable Takeaways

  • Start with a single task template — Define one task with a simple cron schedule, verify it executes correctly, then add complexity. Incremental testing catches problems early.

  • Configure the SQLite database path — Use an absolute path or ensure the working directory is predictable. Relative paths can cause confusion in production environments.

  • Set up monitoring before running in production — Track task execution times, failure rates, and retry counts. Without metrics, you will not know if something goes wrong until a user reports it.

  • Document the cron expressions — Add comments explaining what each schedule means. Future maintainers (including yourself in three months) will thank you.

  • Plan for failure scenarios — What happens if the task runs for more than 24 hours? If the database becomes read-only? If the disk is full? Test these edge cases before they happen in production.
