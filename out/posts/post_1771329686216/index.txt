8:T4551,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Building a Task Scheduler with Scheduler.ts</h1></p><p class="text-slate-300 leading-relaxed mb-4">Aiko Chen, lead developer at Tech Innovators Ltd., faced a recurring problem every Monday morning. Her team spent 45 minutes manually generating sales analytics reports—copying data from three different databases, running calculations, and formatting the output in spreadsheets. The process was error-prone and took away valuable time from actual analysis work.</p><p class="text-slate-300 leading-relaxed mb-4">In early 2024, Aiko decided to automate this workflow. She needed a scheduler that could run tasks at specific times, handle failures gracefully, and maintain a clear record of what had executed and when. After evaluating several approaches, she built a custom task scheduler using Scheduler.ts, a powerful Node.js library that provides exactly this functionality.</p><p class="text-slate-300 leading-relaxed mb-4">This tutorial walks through building that same scheduler. You will learn how to define tasks using templates, track execution state with SQLite, schedule jobs with cron expressions, and handle failures with retry logic.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Task Templates</h2></p><p class="text-slate-300 leading-relaxed mb-4">Task templates form the foundation of any scheduler. They encapsulate everything the scheduler needs to know about a job: what to run, when to run it, and how to handle problems.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Creating a Task Template</h3></p><p class="text-slate-300 leading-relaxed mb-4">The TaskTemplate class accepts a configuration object with several key properties. The name identifies the task for logging and monitoring. The cron expression defines the schedule. The taskFunction contains the actual work to perform.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { TaskTemplate } from 'scheduler.ts';</p><p class="text-slate-300 leading-relaxed mb-4">interface SalesReportData {
  region: string;
  startDate: string;
  endDate: string;
}</p><p class="text-slate-300 leading-relaxed mb-4">async function generateSalesReport(): Promise<SalesReportData> {
  console.log('Fetching sales data from databases...');
  
  // Simulate database queries
  await new Promise(resolve => setTimeout(resolve, 1000));
  
  return {
    region: 'North America',
    startDate: '2024-03-11',
    endDate: '2024-03-15'
  };
}</p><p class="text-slate-300 leading-relaxed mb-4">const salesReportTask = new TaskTemplate({
  name: 'Sales Analytics Report',
  cron: '0 10 <em> </em> 1,3', // 10:00 AM every Monday and Wednesday
  taskFunction: generateSalesReport,
  retryStrategy: {
    maxRetries: 3,
    interval: 60000, // Wait 1 minute between attempts
  },
});
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The retry strategy is particularly important. Network calls fail. Databases timeout. External services become unavailable. Without retries, a single failure would prevent the report from generating until the next scheduled run.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">SQLite State Machine</h2></p><p class="text-slate-300 leading-relaxed mb-4">The scheduler needs to know the current state of every task. Is it pending? Running? Completed? Failed? This information lives in the SQLite state machine, which persists across application restarts.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Initializing the State Machine</h3></p><p class="text-slate-300 leading-relaxed mb-4">Initializing the state machine creates the necessary database tables if they do not exist. The SQLite database file is portable and requires no separate server process, making it ideal for single-instance deployments.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { SQLiteStateMachine } from 'scheduler.ts';</p><p class="text-slate-300 leading-relaxed mb-4">const stateMachine = new SQLiteStateMachine({
  databasePath: './scheduler-state.db',
  enableWAL: true, // Write-Ahead Logging for better concurrency
});</p><p class="text-slate-300 leading-relaxed mb-4">await stateMachine.initialize();</p><p class="text-slate-300 leading-relaxed mb-4">console.log('State machine ready. Current tasks:', 
  await stateMachine.getTaskStatuses()
);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The state machine tracks not just success or failure, but also intermediate states like "retrying" and "scheduled." This visibility becomes critical when debugging why a particular run did not execute.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Querying Task History</h3></p><p class="text-slate-300 leading-relaxed mb-4">You can query the state machine to understand historical execution patterns:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>interface TaskExecution {
  taskId: string;
  status: 'pending' | 'running' | 'completed' | 'failed' | 'retrying';
  startTime: Date;
  endTime?: Date;
  error?: string;
  attemptNumber: number;
}</p><p class="text-slate-300 leading-relaxed mb-4">// Get executions from the past week
const recentExecutions = await stateMachine.queryExecutions({
  taskName: 'Sales Analytics Report',
  startDate: new Date('2024-03-11'),
  endDate: new Date('2024-03-18'),
});</p><p class="text-slate-300 leading-relaxed mb-4">console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Found ${recentExecutions.length} executions</code>);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This history helps identify patterns. If a task consistently fails at a particular time, you can investigate whether external dependencies are experiencing issues.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Cron Triggers</h2></p><p class="text-slate-300 leading-relaxed mb-4">Cron expressions are the standard way to describe time-based schedules. The format consists of five fields: minute, hour, day of month, month, and day of week.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Setting Up Cron Triggers</h3></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { CronTrigger } from 'scheduler.ts';</p><p class="text-slate-300 leading-relaxed mb-4">const cronTrigger = new CronTrigger({
  cron: '0 10 <em> </em> 1,3',
  taskTemplate: salesReportTask,
  stateMachine: stateMachine,
  timezone: 'America/New_York', // Ensure runs happen at local time
});</p><p class="text-slate-300 leading-relaxed mb-4">await cronTrigger.start();
console.log('Scheduler started. Next run:', cronTrigger.getNextRunTime());
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The timezone parameter is crucial for distributed teams. A job scheduled for "10 AM" means different absolute times depending on where your servers and users are located.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Common Cron Expressions</h3></p><p class="text-slate-300 leading-relaxed mb-4">| Expression | Schedule | Use Case |
|------------|----------|----------|
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0 <em> </em> <em> </em></code> | Every hour | Hourly data aggregation |
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0 0 <em> </em> <em></code> | Daily at midnight | Daily backup jobs |
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0 9 </em> <em> 1-5</code> | Weekdays at 9 AM | Morning reports |
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0 </em>/6 <em> </em> <em></code> | Every 6 hours | Periodic sync jobs |
| <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">0 0 1 </em> <em></code> | First of month | Monthly billing runs |</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Retry Strategy</h2></p><p class="text-slate-300 leading-relaxed mb-4">Transient failures are inevitable in distributed systems. A retry strategy determines how the scheduler responds when a task fails.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Implementing Exponential Backoff</h3></p><p class="text-slate-300 leading-relaxed mb-4">Linear retries (waiting the same amount of time between attempts) often make things worse. If a service is overloaded, all concurrent retry attempts can exacerbate the problem. Exponential backoff spreads retry attempts over increasing time intervals.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { RetryStrategy } from 'scheduler.ts';</p><p class="text-slate-300 leading-relaxed mb-4">const retryStrategy = new RetryStrategy({
  maxRetries: 3,
  baseInterval: 60000, // Start with 1 minute
  maxInterval: 300000, // Cap at 5 minutes
  backoffMultiplier: 2, // Double the wait each attempt
  retryableErrors: ['ECONNREFUSED', 'ETIMEDOUT', 'ENOTFOUND'],
});</p><p class="text-slate-300 leading-relaxed mb-4">salesReportTask.retryStrategy = retryStrategy;</p><p class="text-slate-300 leading-relaxed mb-4">// When the task fails, the scheduler automatically:
// Attempt 1: Wait 1 minute, then retry
// Attempt 2: Wait 2 minutes, then retry  
// Attempt 3: Wait 4 minutes, then retry (capped at maxInterval)
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The retryableErrors array ensures the scheduler only retries on transient issues. Permanent failures (invalid credentials, malformed requests) should fail immediately rather than waste resources retrying.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Putting It All Together</h2></p><p class="text-slate-300 leading-relaxed mb-4">Here is how the complete scheduler initialization looks:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import { Scheduler } from 'scheduler.ts';</p><p class="text-slate-300 leading-relaxed mb-4">async function main() {
  const stateMachine = new SQLiteStateMachine({
    databasePath: './scheduler-state.db',
  });
  
  await stateMachine.initialize();
  
  const salesReportTask = new TaskTemplate({
    name: 'Sales Analytics Report',
    cron: '0 10 </em> <em> 1,3',
    taskFunction: generateSalesReport,
    retryStrategy: new RetryStrategy({
      maxRetries: 3,
      baseInterval: 60000,
      backoffMultiplier: 2,
    }),
  });
  
  const scheduler = new Scheduler({
    stateMachine,
    maxConcurrentTasks: 5,
  });
  
  scheduler.registerTask(salesReportTask);
  await scheduler.start();
  
  console.log('Scheduler running. Press Ctrl+C to stop.');
}</p><p class="text-slate-300 leading-relaxed mb-4">main().catch(console.error);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The Scheduler class manages the overall lifecycle. It handles concurrent task limits (preventing resource exhaustion), graceful shutdown (waiting for running tasks to complete), and error logging.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: Scheduler.ts vs. Alternatives</h2></p><p class="text-slate-300 leading-relaxed mb-4">When building a task scheduler, you have several options. Here is how Scheduler.ts compares to other popular approaches:</p><p class="text-slate-300 leading-relaxed mb-4">| Feature | Scheduler.ts | node-cron | BullMQ | Agenda |
|---------|-------------|-----------|--------|--------|
| State persistence | SQLite built-in | None | Redis required | MongoDB required |
| Retry mechanism | Built-in | Manual | Built-in | Built-in |
| Distributed support | Single instance | Single instance | Yes (Redis) | Yes (MongoDB) |
| TypeScript support | Native | Type definitions | Native | Type definitions |
| Setup complexity | Low | Low | High | Medium |
| Cron expressions | Yes | Yes | Yes | Custom syntax |</p><p class="text-slate-300 leading-relaxed mb-4">For Aiko's use case—running reports on a single server without additional infrastructure—Scheduler.ts provides the best balance of features and simplicity. If she later needed to scale to multiple workers, she would need to migrate to BullMQ or a similar distributed solution.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons Learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">Building production schedulers reveals patterns that are not obvious during development. Here are the key insights from Aiko's implementation:</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Always define retry strategies from the start.</strong> Adding retries after a production failure is more stressful than planning ahead. Set reasonable defaults and adjust based on observed failure patterns.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Store execution history, not just current state.</strong> When troubleshooting a missing report from two days ago, you will need to know whether it ran, failed, or never triggered. The state machine should persist this information.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Timezone handling matters more than expected.</strong> A job scheduled for "10 AM" in New York runs at 3 PM UTC. If your database is in London and your users are in Tokyo, you need to be explicit about which timezone applies.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Test cron expressions before deploying.</strong> Use tools like crontab.guru to validate your expressions. A small typo can cause jobs to run at completely wrong times—or not at all.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Graceful shutdown prevents data loss.</strong> When the application receives a termination signal, wait for the current task to complete before exiting. Abrupt termination can leave tasks in inconsistent states.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Start with a single task template</strong> — Define one task with a simple cron schedule, verify it executes correctly, then add complexity. Incremental testing catches problems early.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Configure the SQLite database path</strong> — Use an absolute path or ensure the working directory is predictable. Relative paths can cause confusion in production environments.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Set up monitoring before running in production</strong> — Track task execution times, failure rates, and retry counts. Without metrics, you will not know if something goes wrong until a user reports it.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Document the cron expressions</strong> — Add comments explaining what each schedule means. Future maintainers (including yourself in three months) will thank you.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Plan for failure scenarios</strong> — What happens if the task runs for more than 24 hours? If the database becomes read-only? If the disk is full? Test these edge cases before they happen in production.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Results</h2></p><p class="text-slate-300 leading-relaxed mb-4">Aiko's scheduler has been running for over a year now. The sales analytics reports generate automatically every Monday and Wednesday at 10 AM Eastern. Her team has saved approximately 200 hours annually—time now spent on actual analysis rather than manual data compilation.</p><p class="text-slate-300 leading-relaxed mb-4">The scheduler has handled several edge cases gracefully: network blips triggered automatic retries, database maintenance windows were accommodated through schedule adjustments, and execution history made debugging occasional issues straightforward. Building the scheduler took a single afternoon; the ROI accumulated from day one.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4">[Last updated: 2026-02-17]</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
