8:T417c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Common system design anti-patterns and how to avoid them</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a new “recommendations” feature in January 2026. On launch, the API that assembled a user’s homepage started calling the new service synchronously. When the recommendations service hit 800 ms latency (a bad deploy), the homepage endpoint waited on it. Within 12 minutes, connection pools were exhausted, and the main app started returning 503s. They rolled back, but 40 minutes of order submissions were lost because the order service had been in the same synchronous chain. The root cause wasn’t one bug — it was a handful of system design choices that are easy to make and expensive to fix later.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers anti-patterns we see repeatedly: synchronous call chains, missing idempotency, single points of failure, and tight coupling. For each we give a concrete alternative and runnable code so you can compare before/after.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why these patterns hurt</h2></p><p class="text-slate-300 leading-relaxed mb-4">Anti-patterns in system design don’t show up in unit tests. They appear under load, partial failure, or retries. The cost is latency spikes, duplicate work, cascading failures, and data inconsistency. Fixing them after launch usually means changing contracts, adding queues or caches, and migrating behavior — all while keeping the system running.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Anti-pattern 1: Synchronous call chains</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What happens:</strong> Service A calls B, B calls C. If B or C is slow or down, A blocks. Threads or connections pile up, and the whole chain fails.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Better:</strong> Call only what you need for the critical path; do the rest asynchronously (queue, event, or fire-and-forget with timeouts). Never let the latency of a non-critical dependency become the latency of your user-facing API.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Bad: blocking chain</h3></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// bad-chain.ts — Don't do this. Without an idempotency key, each retry creates a new order. Picking the wrong one is a common anti-pattern.</p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Synchronous RPC/HTTP chain</strong> | Simple, immediate response | One slow service blocks all; cascades; pool exhaustion | Only for a single, fast, critical dependency |
| <strong>Message queue (e.g. job queue)</strong> | Decouples services; natural backpressure; retries | Eventually consistent; need to design for duplicates | Order processing, notifications, heavy work |
| <strong>Event stream (e.g. Kafka, events)</strong> | Multiple consumers; replay; audit trail | More ops; ordering and partitioning to think about | High throughput, multiple subscribers, analytics |
| <strong>Parallel HTTP with timeouts</strong> | Low latency when deps are fast; no new infra | Still fails if deps are down; need timeouts and fallbacks | Read path, aggregation of a few services |</p><p class="text-slate-300 leading-relaxed mb-4">Use synchronous chains only for the minimal set of calls that must complete for the response; use queues or events for anything that can be eventually consistent or retried in the background.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Anti-pattern 3: Single point of failure and tight coupling</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What happens:</strong> One service or one DB holds all critical state. When it’s down or degraded, the whole product is down. Tight coupling (e.g. services calling each other’s internal URLs, or sharing a single DB) makes deployment and failure domains huge.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Better:</strong>  
<li class="ml-4 list-disc text-slate-300"><strong>Redundancy:</strong> Multiple instances behind a load balancer; DB with replicas; avoid “one box does everything.”  </li>
<li class="ml-4 list-disc text-slate-300"><strong>Loose coupling:</strong> Publish events or use a queue; consumers don’t call back into the producer’s internal API.  </li>
<li class="ml-4 list-disc text-slate-300"><strong>Bounded contexts:</strong> Each service owns its data; others access it via API or events, not direct DB access.</li></p><p class="text-slate-300 leading-relaxed mb-4">Design so that the failure of one component degrades gracefully (e.g. recommendations missing) instead of taking down the entire request path.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4">On a previous system we had three services in a row: <strong>API → Orders → Payments</strong>. Under load, the payment provider started responding in 3–5 seconds. Our payment service didn’t have a circuit breaker or a hard timeout. The order service kept opening new HTTP connections while waiting. Each connection held a DB connection for the transaction. Within about 15 minutes we hit PostgreSQL’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">max_connections</code> (100). Error in logs: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">FATAL: remaining connection slots are reserved for non-replication superuser connections</code>. The API then returned 503 for all orders. We lost roughly 40 minutes of orders before we added timeouts, limited concurrency to the payment service, and introduced a circuit breaker. The numbers: payment p99 went from ~200 ms to ~4.2 s before the incident; after the fix we capped outbound calls at 10 concurrent and 2 s timeout, and we opened the circuit after 5 failures in 10 s. Repeating the same call pattern without those guards would have caused the same failure again.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable next steps</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit your critical paths.</strong> List every outbound HTTP call in the request path. For each one, add a timeout (e.g. 2–5 s) and decide if it must block the response. If not, move it to a queue or background job.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Introduce idempotency keys</strong> for any endpoint that creates or updates important state (orders, payments, signups). Enforce the key on the server and document it for clients. Store key → result with a TTL (e.g. 24 h).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a circuit breaker</strong> around external APIs (LLMs, payment gateways, third-party APIs). Use a small library or the pattern from the circuit-breaker post in this blog. Log when the circuit opens so you can correlate with incidents.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Draw a dependency diagram</strong> (even on a napkin): which service calls which, and whether it’s sync or async. Break any long synchronous chain into at most one or two blocking calls; rest should be parallel or async.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Run a game day:</strong> kill or throttle one dependency (e.g. one service or one DB) and see how the system behaves. Fix the single points of failure and missing timeouts you discover.</li></p><p class="text-slate-300 leading-relaxed mb-4">You don’t have to fix everything at once. Start with the path that handles money or critical user actions: add timeouts, idempotency, and a circuit breaker there first. Then work backward through the chain.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
