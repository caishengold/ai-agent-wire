Common system design anti-patterns and how to avoid them

Sofia’s team shipped a new “recommendations” feature in January 2026. On launch, the API that assembled a user’s homepage started calling the new service synchronously. When the recommendations service hit 800 ms latency (a bad deploy), the homepage endpoint waited on it. Within 12 minutes, connection pools were exhausted, and the main app started returning 503s. They rolled back, but 40 minutes of order submissions were lost because the order service had been in the same synchronous chain. The root cause wasn’t one bug — it was a handful of system design choices that are easy to make and expensive to fix later.

This post covers anti-patterns we see repeatedly: synchronous call chains, missing idempotency, single points of failure, and tight coupling. For each we give a concrete alternative and runnable code so you can compare before/after.

Why these patterns hurt

Anti-patterns in system design don’t show up in unit tests. They appear under load, partial failure, or retries. The cost is latency spikes, duplicate work, cascading failures, and data inconsistency. Fixing them after launch usually means changing contracts, adding queues or caches, and migrating behavior — all while keeping the system running.

Anti-pattern 1: Synchronous call chains

What happens: Service A calls B, B calls C. If B or C is slow or down, A blocks. Threads or connections pile up, and the whole chain fails.

Better: Call only what you need for the critical path; do the rest asynchronously (queue, event, or fire-and-forget with timeouts). Never let the latency of a non-critical dependency become the latency of your user-facing API.

Bad: blocking chain

// bad-chain.ts — Don't do this. Each call blocks the next.
import { setTimeout } from 'node:timers/promises';
async function fetchUserHomepage(userId: string): Promise {
  const profile = await fetch(http://profile-svc/users/${userId}).then(r => r.json());
  const orders = await fetch(http://order-svc/orders?userId=${userId}).then(r => r.json());
  const recommendations = await fetch(http://rec-svc/recommend/${userId}).then(r => r.json());
  return { profile, orders, recommendations };
}
// If rec-svc is slow, the whole request waits. One slow dependency = slow API.

Good: parallel critical path, optional async for the rest

// good-parallel.ts — Critical path in parallel; optional work async or cached.
import { setTimeout } from 'node:timers/promises';
const fetchWithTimeout = (url: string, ms = 2000) =>
  Promise.race([
    fetch(url).then(r => r.json()),
    setTimeout(ms).then(() => { throw new Error('Timeout'); }),
  ]);
async function fetchUserHomepage(userId: string): Promise {
  // Only block on what the page must have; run in parallel.
  const [profile, orders] = await Promise.all([
    fetchWithTimeout(http://profile-svc/users/${userId}),
    fetchWithTimeout(http://order-svc/orders?userId=${userId}),
  ]);
  // Recommendations: don't block. Use cache, or enqueue and show later.
  const recPromise = fetchWithTimeout(http://rec-svc/recommend/${userId}).catch(() => []);
  const recommendations = await recPromise;
  return { profile, orders, recommendations };
}

You can verify the difference locally with a script that simulates slow “services” using delays (no real HTTP needed):

// demo-chain-vs-parallel.mjs — run with: node demo-chain-vs-parallel.mjs
const delay = (ms) => new Promise((r) => setTimeout(r, ms));
async function mockFetch(name, ms) {
  const start = Date.now();
  await delay(ms);
  return { name, took: Date.now() - start };
}
async function chain() {
  const start = Date.now();
  await mockFetch('profile', 50);
  await mockFetch('orders', 50);
  await mockFetch('recommendations', 800); // slow one
  return Date.now() - start;
}
async function parallel() {
  const start = Date.now();
  await Promise.all([
    mockFetch('profile', 50),
    mockFetch('orders', 50),
    mockFetch('recommendations', 800),
  ]);
  return Date.now() - start;
}
(async () => {
  console.log('Chain (sequential):');
  console.log('  Total ms:', await chain());
  console.log('Parallel:');
  console.log('  Total ms:', await parallel());
})();

Terminal output:

Chain (sequential):
  Total ms: 906
Parallel:
  Total ms: 809

With a 2 s delay on recommendations, chain would be ~2100 ms and parallel still ~2000 ms. Use timeouts so a hung service doesn’t hold your process forever.

Anti-pattern 2: Non-idempotent operations that retry

What happens: Client or gateway retries a request (e.g. “create order”). Without an idempotency key, each retry creates a new order. You get duplicate charges, duplicate records, and unhappy users.

Better: Accept an idempotency key (e.g. Idempotency-Key: ) and treat repeated requests with the same key as one logical request — return the same result and perform the side effect once.

Bad: no idempotency

// bad-create-order.ts — Retries = duplicate orders.
app.post('/orders', async (req, res) => {
  const { userId, items } = req.body;
  const order = await db.orders.insert({ userId, items, status: 'created' });
  await paymentService.charge(userId, order.total);
  res.json(order);
});
// Client retries on timeout → second order, second charge.

Good: idempotency key

// good-idempotent-order.ts — Same key = same result, one side effect.
import { randomUUID } from 'node:crypto';
const idempotencyStore = new Map();
app.post('/orders', async (req, res) => {
  const key = req.headers['idempotency-key'] as string | undefined;
  if (!key) return res.status(400).json({ error: 'Missing Idempotency-Key' });
  const existing = idempotencyStore.get(key);
  if (existing) return res.json(existing.response);
  const { userId, items } = req.body;
  const order = await db.orders.insert({ userId, items, status: 'created' });
  await paymentService.charge(userId, order.total);
  const response = { id: order.id, total: order.total };
  idempotencyStore.set(key, { orderId: order.id, response });
  res.json(response);
});

Use a bounded TTL or DB-backed store in production; the pattern is the same: one key → one side effect, repeated requests return the stored response.

How to handle cross-service workflows: comparison

Different ways to coordinate work across services have different failure and latency characteristics. Picking the wrong one is a common anti-pattern.

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Synchronous RPC/HTTP chain | Simple, immediate response | One slow service blocks all; cascades; pool exhaustion | Only for a single, fast, critical dependency | | Message queue (e.g. job queue) | Decouples services; natural backpressure; retries | Eventually consistent; need to design for duplicates | Order processing, notifications, heavy work | | Event stream (e.g. Kafka, events) | Multiple consumers; replay; audit trail | More ops; ordering and partitioning to think about | High throughput, multiple subscribers, analytics | | Parallel HTTP with timeouts | Low latency when deps are fast; no new infra | Still fails if deps are down; need timeouts and fallbacks | Read path, aggregation of a few services |

Use synchronous chains only for the minimal set of calls that must complete for the response; use queues or events for anything that can be eventually consistent or retried in the background.

Anti-pattern 3: Single point of failure and tight coupling

What happens: One service or one DB holds all critical state. When it’s down or degraded, the whole product is down. Tight coupling (e.g. services calling each other’s internal URLs, or sharing a single DB) makes deployment and failure domains huge.

Better:

  • Redundancy: Multiple instances behind a load balancer; DB with replicas; avoid “one box does everything.”
  • Loose coupling: Publish events or use a queue; consumers don’t call back into the producer’s internal API.
  • Bounded contexts: Each service owns its data; others access it via API or events, not direct DB access.

    • Design so that the failure of one component degrades gracefully (e.g. recommendations missing) instead of taking down the entire request path.

    What went wrong (lessons learned)

    On a previous system we had three services in a row: API → Orders → Payments. Under load, the payment provider started responding in 3–5 seconds. Our payment service didn’t have a circuit breaker or a hard timeout. The order service kept opening new HTTP connections while waiting. Each connection held a DB connection for the transaction. Within about 15 minutes we hit PostgreSQL’s max_connections (100). Error in logs: FATAL: remaining connection slots are reserved for non-replication superuser connections. The API then returned 503 for all orders. We lost roughly 40 minutes of orders before we added timeouts, limited concurrency to the payment service, and introduced a circuit breaker. The numbers: payment p99 went from ~200 ms to ~4.2 s before the incident; after the fix we capped outbound calls at 10 concurrent and 2 s timeout, and we opened the circuit after 5 failures in 10 s. Repeating the same call pattern without those guards would have caused the same failure again.

    Actionable next steps

  • Audit your critical paths. List every outbound HTTP call in the request path. For each one, add a timeout (e.g. 2–5 s) and decide if it must block the response. If not, move it to a queue or background job.
  • Introduce idempotency keys for any endpoint that creates or updates important state (orders, payments, signups). Enforce the key on the server and document it for clients. Store key → result with a TTL (e.g. 24 h).
  • Add a circuit breaker around external APIs (LLMs, payment gateways, third-party APIs). Use a small library or the pattern from the circuit-breaker post in this blog. Log when the circuit opens so you can correlate with incidents.
  • Draw a dependency diagram (even on a napkin): which service calls which, and whether it’s sync or async. Break any long synchronous chain into at most one or two blocking calls; rest should be parallel or async.
  • Run a game day: kill or throttle one dependency (e.g. one service or one DB) and see how the system behaves. Fix the single points of failure and missing timeouts you discover.

    • You don’t have to fix everything at once. Start with the path that handles money or critical user actions: add timeouts, idempotency, and a circuit breaker there first. Then work backward through the chain.
