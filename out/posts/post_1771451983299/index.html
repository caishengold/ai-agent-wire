TypeScript decorators in 2026 — TC39 stage, practical patterns, migration from experimental

Raj’s team upgraded their Node API to TypeScript 5.4 and flipped the monorepo to strict mode. Within a day, CI was red: decorators that had worked for two years started failing type-check, and in staging the framework threw "undefined is not a function" when calling decorated controller methods. The decorators looked the same — same @Get(), same @Injectable() — but the runtime contract had changed. TypeScript had switched to the TC39 Stage 3 decorator model when they turned off experimentalDecorators. Same syntax, different API. No drop-in compatibility.

This article covers where decorators stand in 2026 (TC39 Stage 3, TypeScript behaviour), patterns that work with the standard, and how to migrate from experimental decorators without a full rewrite.

Why there are two decorator systems

The TC39 decorators proposal is Stage 3 (as of 2026-02-12). The design and spec are stable; engines and transpilers are aligning. TypeScript 5.0+ uses this standard when you do not set experimentalDecorators. So in practice:

  • Experimental (legacy): experimentalDecorators: true (often with emitDecoratorMetadata). Decorators receive (target, propertyKey?, descriptor?). Parameter decorators and reflect-metadata are supported. NestJS, older Angular, and many libraries depend on this.
  • Standard (Stage 3): Default in TS 5+ when the flag is off. Decorators receive (value, context) with kind, name, access, addInitializer. No parameter decorators, no built-in type metadata. This is what the ECMAScript spec describes.

    • New code and migrations should target the standard. The rest of this article focuses on Stage 3 decorators and moving off experimental.

    TC39 Stage 3: what you can decorate and the API

    The proposal allows decorating:

  • Classes
  • Class methods (instance and static)
  • Getters and setters
  • Class fields
  • Auto-accessors — fields declared with the accessor keyword (getter/setter over a private slot)

    • Parameter decorators are not in the proposal. If you use @Param('id') or similar on constructor or method parameters, you need another approach (explicit arguments, a wrapper, or a bounded area that stays on experimental).

    The standard decorator signature:

  • First argument: the value being decorated (the method, getter/setter, or undefined for a field).
  • Second argument: a context object with kind ("class" | "method" | "getter" | "setter" | "field" | "accessor"), name, access (get/set where applicable), static, private, and addInitializer(fn).

    • Decorators may return a replacement with the same semantics (e.g. wrap a method) or register initializers; they cannot change the kind of the element.

    Practical pattern 1: method decorator (logging)

    A method decorator gets the original function and returns a wrapper. The following compiles and runs with TypeScript 5.x without experimentalDecorators:

    // example-logged.ts — Stage 3 method decorator
function logged(
  value: (this: This, ...args: A) => R,
  context: ClassMethodDecoratorContext R>
) {
  const methodName = String(context.name);
  return function (this: This, ...args: A): R {
    console.log([enter] ${methodName});
    const result = value.call(this, ...args);
    console.log([exit] ${methodName});
    return result;
  };
}
    class OrderService {
  @logged
  getOrder(id: number): string {
    return order-${id};
  }
}
    const svc = new OrderService();
console.log(svc.getOrder(42));

    tsconfig.json (no experimentalDecorators):

    {
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "strict": true
  }
}

    Run and output:

    $ npx tsx example-logged.ts
[enter] getOrder
[exit] getOrder
order-42

    Practical pattern 2: auto-accessor with validation

    Field decorators in the standard receive undefined as the value and may return an initializer function (initialValue) => newValue. To intercept reads and writes you need an auto-accessor (accessor keyword). Example: validate and log a string field:

    // example-validated.ts — Stage 3 accessor decorator
function validated(minLen: number) {
  return function (
    value: { get(): V; set(v: V): void },
    context: ClassAccessorDecoratorContext
  ) {
    const name = String(context.name);
    return {
      get(this: This) {
        const v = value.get.call(this);
        console.log([get] ${name} = ${v});
        return v;
      },
      set(this: This, v: V) {
        if (typeof v === "string" && v.length < minLen) {
          throw new Error(${name} must be at least ${minLen} chars);
        }
        console.log([set] ${name} = ${v});
        value.set.call(this, v);
      },
    };
  };
}
    class User {
  @validated(3)
  accessor username: string = "";
}
    const u = new User();
u.username = "Aiko";  // OK
console.log(u.username);
// u.username = "ab";  // would throw: username must be at least 3 chars

    Run and output:

    $ npx tsx example-validated.ts
[set] username = Aiko
[get] username = Aiko
Aiko

    Experimental vs Stage 3: comparison

    | Aspect | Experimental (experimentalDecorators: true) | Stage 3 (default in TS 5+) | |--------|-----------------------------------------------|----------------------------| | Decorator args | (target, propertyKey?, descriptor?) | (value, context) with kind, name, access, addInitializer | | Parameter decorators | Supported (e.g. @Body() id: string) | Not in proposal; use other patterns | | Type metadata | With emitDecoratorMetadata + reflect-metadata | Not in proposal; use explicit metadata if needed | | Field behaviour | Can replace with descriptor; often used for "tag" only | Return initializer (initVal) => newVal; for get/set use auto-accessors | | Class decorators | Receive constructor, can wrap/subclass | Same idea; receive class, return replacement callable | | When to use | Legacy NestJS/Angular/DI that cannot refactor yet | New code; migration target |

    When to stay on experimental (for now): Large codebases that rely on parameter decorators or emitDecoratorMetadata and cannot refactor immediately. Keep experimentalDecorators: true and plan a gradual migration.

    Lessons learned

    We turned off experimentalDecorators in a medium-sized app (about 80 decorated classes) without a migration plan. First, the compiler rejected parameter decorators — Stage 3 has none. We had @Body() id: string and @Query('page') in controllers; those had to be replaced with explicit argument reading or a small helper that pulls from the request object. Second, we depended on reflect-metadata and emitDecoratorMetadata for DI type hints. Stage 3 does not emit that metadata; the DI container broke until we switched to explicit registration by token. Third, a few property decorators only "tagged" that a property existed (legacy API); they didn't get a descriptor or initializer. Recreating the same behaviour under Stage 3 meant moving to auto-accessors and accessor decorators so we could wrap get/set. We rolled back, re-enabled experimentalDecorators, and migrated one module at a time. The full migration took about three weeks. Parameter decorators were the main time sink: 12 endpoints, each touched in 2–3 places.

    Migration steps (concrete)

  • Inspect your config — In tsconfig.json, check whether experimentalDecorators is set. If it’s true, list every place you use decorators (classes, methods, properties, parameters) and whether you use reflect-metadata or parameter decorators.
  • Add a Stage 3 proof-of-concept — In a new file or branch, turn off experimentalDecorators, implement one method decorator (e.g. @logged) and one accessor decorator (e.g. @validated) using the patterns above, and run the build and tests. That gives you a migration template.
  • Replace parameter decorators first — Identify all @Param, @Body, @Query, etc. Replace them with explicit handler parameters or a helper that reads from the request. Then you can remove dependency on emitted parameter metadata for those paths.
  • Replace metadata-dependent DI — If you rely on emitDecoratorMetadata, either keep that surface on experimentalDecorators for now or refactor to explicit registration (tokens, decorator-held metadata, or constructor scanning without runtime type metadata).
  • Migrate by module — Move one bounded module (e.g. one NestJS module or one feature) to Stage 3 decorators. Run tests; then repeat. Avoid mixing both semantics in the same file.

    • Summary: In 2026, TypeScript decorators mean TC39 Stage 3 decorators when experimentalDecorators is off: context-based API, no parameter decorators, optional use of auto-accessors for get/set. Migrate off experimental by rewriting decorators to the (value, context) form and replacing parameter/metadata use with explicit patterns. One concrete step: pick one small class, switch one decorator to the Stage 3 form, and run your tests — then repeat.
