8:T4db2,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">TypeScript decorators in 2026 — TC39 stage, practical patterns, migration from experimental</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s team upgraded their Node API to TypeScript 5.4 and flipped the monorepo to strict mode. Within a day, CI was red: decorators that had worked for two years started failing type-check, and in staging the framework threw <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"undefined is not a function"</code> when calling decorated controller methods. The decorators looked the same — same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Get()</code>, same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Injectable()</code> — but the runtime contract had changed. TypeScript had switched to the <strong>TC39 Stage 3</strong> decorator model when they turned off <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>. Same syntax, different API. No drop-in compatibility.</p><p class="text-slate-300 leading-relaxed mb-4">This article covers where decorators stand in 2026 (TC39 Stage 3, TypeScript behaviour), patterns that work with the standard, and how to migrate from experimental decorators without a full rewrite.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why there are two decorator systems</h2></p><p class="text-slate-300 leading-relaxed mb-4">The <a href="https://github.com/tc39/proposal-decorators" class="text-cyan-400 hover:underline">TC39 decorators proposal</a> is <strong>Stage 3</strong> (as of 2026-02-12). The design and spec are stable; engines and transpilers are aligning. TypeScript 5.0+ uses this standard when you <strong>do not</strong> set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>. So in practice:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Experimental (legacy):</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators: true</code> (often with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">emitDecoratorMetadata</code>). Decorators receive <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(target, propertyKey?, descriptor?)</code>. Parameter decorators and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">reflect-metadata</code> are supported. NestJS, older Angular, and many libraries depend on this.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Standard (Stage 3):</strong> Default in TS 5+ when the flag is off. Decorators receive <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(value, context)</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kind</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">name</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">access</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">addInitializer</code>. No parameter decorators, no built-in type metadata. This is what the ECMAScript spec describes.</li></p><p class="text-slate-300 leading-relaxed mb-4">New code and migrations should target the standard. The rest of this article focuses on Stage 3 decorators and moving off experimental.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">TC39 Stage 3: what you can decorate and the API</h2></p><p class="text-slate-300 leading-relaxed mb-4">The proposal allows decorating:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Classes</li>
<li class="ml-4 list-disc text-slate-300">Class methods (instance and static)</li>
<li class="ml-4 list-disc text-slate-300">Getters and setters</li>
<li class="ml-4 list-disc text-slate-300">Class fields</li>
<li class="ml-4 list-disc text-slate-300"><strong>Auto-accessors</strong> — fields declared with the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">accessor</code> keyword (getter/setter over a private slot)</li></p><p class="text-slate-300 leading-relaxed mb-4">Parameter decorators are <strong>not</strong> in the proposal. If you use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Param('id')</code> or similar on constructor or method parameters, you need another approach (explicit arguments, a wrapper, or a bounded area that stays on experimental).</p><p class="text-slate-300 leading-relaxed mb-4">The standard decorator signature:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>First argument:</strong> the value being decorated (the method, getter/setter, or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">undefined</code> for a field).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Second argument:</strong> a context object with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kind</code> (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"class"</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"method"</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"getter"</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"setter"</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"field"</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">"accessor"</code>), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">name</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">access</code> (get/set where applicable), <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">static</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">private</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">addInitializer(fn)</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4">Decorators may return a replacement with the same semantics (e.g. wrap a method) or register initializers; they cannot change the kind of the element.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical pattern 1: method decorator (logging)</h2></p><p class="text-slate-300 leading-relaxed mb-4">A method decorator gets the original function and returns a wrapper. The following compiles and runs with TypeScript 5.x <strong>without</strong> <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// example-logged.ts — Stage 3 method decorator
function logged<This, A extends unknown[], R>(
  value: (this: This, ...args: A) => R,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: A) => R>
) {
  const methodName = String(context.name);
  return function (this: This, ...args: A): R {
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[enter] ${methodName}</code>);
    const result = value.call(this, ...args);
    console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[exit] ${methodName}</code>);
    return result;
  };
}</p><p class="text-slate-300 leading-relaxed mb-4">class OrderService {
  @logged
  getOrder(id: number): string {
    return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">order-${id}</code>;
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">const svc = new OrderService();
console.log(svc.getOrder(42));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>tsconfig.json</strong> (no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "strict": true
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run and output:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ npx tsx example-logged.ts
[enter] getOrder
[exit] getOrder
order-42
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical pattern 2: auto-accessor with validation</h2></p><p class="text-slate-300 leading-relaxed mb-4">Field decorators in the standard receive <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">undefined</code> as the value and may return an <strong>initializer</strong> function <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(initialValue) => newValue</code>. To intercept reads and writes you need an <strong>auto-accessor</strong> (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">accessor</code> keyword). Example: validate and log a string field:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// example-validated.ts — Stage 3 accessor decorator
function validated(minLen: number) {
  return function <This, V>(
    value: { get(): V; set(v: V): void },
    context: ClassAccessorDecoratorContext<This, V>
  ) {
    const name = String(context.name);
    return {
      get(this: This) {
        const v = value.get.call(this);
        console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[get] ${name} = ${v}</code>);
        return v;
      },
      set(this: This, v: V) {
        if (typeof v === "string" && v.length < minLen) {
          throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${name} must be at least ${minLen} chars</code>);
        }
        console.log(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[set] ${name} = ${v}</code>);
        value.set.call(this, v);
      },
    };
  };
}</p><p class="text-slate-300 leading-relaxed mb-4">class User {
  @validated(3)
  accessor username: string = "";
}</p><p class="text-slate-300 leading-relaxed mb-4">const u = new User();
u.username = "Aiko";  // OK
console.log(u.username);
// u.username = "ab";  // would throw: username must be at least 3 chars
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run and output:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ npx tsx example-validated.ts
[set] username = Aiko
[get] username = Aiko
Aiko
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Experimental vs Stage 3: comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | Experimental (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators: true</code>) | Stage 3 (default in TS 5+) |
|--------|-----------------------------------------------|----------------------------|
| <strong>Decorator args</strong> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(target, propertyKey?, descriptor?)</code> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(value, context)</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">kind</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">name</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">access</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">addInitializer</code> |
| <strong>Parameter decorators</strong> | Supported (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Body() id: string</code>) | Not in proposal; use other patterns |
| <strong>Type metadata</strong> | With <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">emitDecoratorMetadata</code> + <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">reflect-metadata</code> | Not in proposal; use explicit metadata if needed |
| <strong>Field behaviour</strong> | Can replace with descriptor; often used for "tag" only | Return initializer <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(initVal) => newVal</code>; for get/set use auto-accessors |
| <strong>Class decorators</strong> | Receive constructor, can wrap/subclass | Same idea; receive class, return replacement callable |
| <strong>When to use</strong> | Legacy NestJS/Angular/DI that cannot refactor yet | New code; migration target |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When to stay on experimental (for now):</strong> Large codebases that rely on parameter decorators or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">emitDecoratorMetadata</code> and cannot refactor immediately. Keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators: true</code> and plan a gradual migration.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4">We turned off <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> in a medium-sized app (about 80 decorated classes) without a migration plan. First, the compiler rejected <strong>parameter decorators</strong> — Stage 3 has none. We had <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Body() id: string</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Query('page')</code> in controllers; those had to be replaced with explicit argument reading or a small helper that pulls from the request object. Second, we depended on <strong>reflect-metadata</strong> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">emitDecoratorMetadata</code> for DI type hints. Stage 3 does not emit that metadata; the DI container broke until we switched to explicit registration by token. Third, a few <strong>property decorators</strong> only "tagged" that a property existed (legacy API); they didn't get a descriptor or initializer. Recreating the same behaviour under Stage 3 meant moving to <strong>auto-accessors</strong> and accessor decorators so we could wrap get/set. We rolled back, re-enabled <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>, and migrated one module at a time. The full migration took about three weeks. Parameter decorators were the main time sink: 12 endpoints, each touched in 2–3 places.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Migration steps (concrete)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Inspect your config</strong> — In <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">tsconfig.json</code>, check whether <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> is set. If it’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">true</code>, list every place you use decorators (classes, methods, properties, parameters) and whether you use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">reflect-metadata</code> or parameter decorators.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Add a Stage 3 proof-of-concept</strong> — In a new file or branch, turn off <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code>, implement one method decorator (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@logged</code>) and one accessor decorator (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@validated</code>) using the patterns above, and run the build and tests. That gives you a migration template.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Replace parameter decorators first</strong> — Identify all <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Param</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Body</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">@Query</code>, etc. Replace them with explicit handler parameters or a helper that reads from the request. Then you can remove dependency on emitted parameter metadata for those paths.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Replace metadata-dependent DI</strong> — If you rely on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">emitDecoratorMetadata</code>, either keep that surface on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> for now or refactor to explicit registration (tokens, decorator-held metadata, or constructor scanning without runtime type metadata).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Migrate by module</strong> — Move one bounded module (e.g. one NestJS module or one feature) to Stage 3 decorators. Run tests; then repeat. Avoid mixing both semantics in the same file.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><em>Summary: In 2026, TypeScript decorators mean <strong>TC39 Stage 3 decorators</strong> when <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">experimentalDecorators</code> is off: context-based API, no parameter decorators, optional use of auto-accessors for get/set. Migrate off experimental by rewriting decorators to the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">(value, context)</code> form and replacing parameter/metadata use with explicit patterns.
