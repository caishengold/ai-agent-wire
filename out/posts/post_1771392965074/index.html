Feature flags done right — implementation patterns, gradual rollout, kill switches, open-source tools

Feature flags done right — implementation patterns, gradual rollout, kill switches, open-source tools

Sofia’s team shipped a new payment path at 22:00 UTC. By 02:30, support was flooded: a subset of users in the EU saw failed charges and duplicate pending transactions. The fix was in main in 20 minutes, but the last deployment had already gone to production. Rolling back would have reverted two other features that had shipped the same day. Instead, they flipped a kill switch for the new payment path. Traffic fell back to the old flow in under a minute. No redeploy, no rollback. That’s what feature flags are for — and doing them right is mostly about patterns and tooling, not magic.

This article covers implementation patterns (in-process, remote, hybrid), gradual rollout and percentage-based toggles, kill switches in practice, and open-source options you can run yourself. We’ll use runnable code, a comparison of approaches, and a short “what went wrong” section from real use.

Why feature flags in the first place?

Beyond the obvious “turn things off without redeploying”:

  • Gradual rollout: Enable a new path for 5% of traffic, then 25%, then 100% while watching error rates and latency.
  • Kill switch: One flag to disable a feature when it misbehaves — no code change, no pipeline.
  • Per-tenant or per-segment: Beta for internal users (e.g. by email domain or tenant ID) before opening to everyone.
  • Experimentation: A/B tests by branching on a flag and measuring outcomes (conversions, errors, etc.).

    • Flags are not a substitute for good testing or small deploys. They add a dimension of runtime control on top of that.

    Implementation patterns

    How you store and evaluate flags determines how fast you can change them and what infrastructure you need.

    Pattern 1: In-process (env or config at startup)

    Flags live in environment variables or a config file. The app reads them once at startup.

    // flags/env.ts — runs in any Node/Bun app
const FLAG_DEFS = {
  useNewBilling: { default: false },
  highTrafficMode: { default: false },
  betaSearch: { default: false },
} as const;
    export type FlagName = keyof typeof FLAG_DEFS;
    function envBool(name: string): boolean | undefined {
  const v = process.env[FEATURE_${name}];
  if (v === "true") return true;
  if (v === "false") return false;
  return undefined;
}
    export function getFlag(name: FlagName): boolean {
  const envVal = envBool(name);
  if (envVal !== undefined) return envVal;
  return FLAG_DEFS[name].default;
}
    // Usage at a call site
if (getFlag("useNewBilling")) {
  return await newBillingService.charge(req);
}
return await legacyBilling.charge(req);

    Pros: No extra services, type-safe keys, trivial to test (mock env). Cons: Changing a flag needs a restart or an env change in your platform (e.g. Kubernetes ConfigMap refresh), so not ideal for emergency kill switches unless your deploy is very fast.

    Pattern 2: Remote or DB-backed with TTL cache

    Flags are stored in a database or remote config service. The app caches them for a short TTL so you can turn a feature off without restarting.

    // flags/remote.ts — Node/Bun, assumes a minimal DB or HTTP source
const cache = new Map<
  string,
  { value: boolean; expiresAt: number }
>();
const TTL_MS = 30_000; // 30 seconds
    async function fetchFromSource(name: string): Promise {
  // Example: HTTP to your config service, or DB query
  const res = await fetch(
    https://config.example.com/flags/${name},
    { headers: { "Authorization": Bearer ${process.env.CONFIG_TOKEN} } }
  );
  if (!res.ok) return false;
  const data = await res.json();
  return Boolean(data?.enabled);
}
    export async function getFlagRemote(
  name: string,
  bypassCache = false
): Promise {
  const now = Date.now();
  const entry = cache.get(name);
  if (!bypassCache && entry && entry.expiresAt > now) {
    return entry.value;
  }
  const value = await fetchFromSource(name);
  cache.set(name, { value, expiresAt: now + TTL_MS });
  return value;
}
    // For kill switches: bypass cache so the flip is immediate
export async function isKillSwitchOff(flagName: string): Promise {
  return getFlagRemote(flagName, true);
}

    Pros: Change flags at runtime; kill switches take effect within one request (if you bypass cache) or within TTL. Cons: Depends on a config store or DB; you must define behavior when the source is unreachable (e.g. fall back to env or “off”).

    Pattern 3: Percentage rollout (gradual release)

    You want “enable for 10% of requests” or “enable for tenant IDs in this list”. A common approach is to hash a stable key (user ID, tenant ID, or request ID) and compare to a threshold.

    // flags/rollout.ts
function hashToPercent(s: string): number {
  let h = 0;
  for (let i = 0; i < s.length; i++) {
    h = (h  31 + s.charCodeAt(i)) >>> 0;
  }
  return h % 100;
}
    export function isInRollout(
  flagName: string,
  percent: number,
  contextKey: string
): boolean {
  if (percent <= 0) return false;
  if (percent >= 100) return true;
  return hashToPercent(${flagName}:${contextKey}) < percent;
}
    // Usage: enable new billing for 15% of tenants
const tenantId = req.tenant?.id ?? req.ip;
if (isInRollout("useNewBilling", 15, tenantId) && (await getFlagRemote("useNewBilling"))) {
  return await newBillingService.charge(req);
}
return await legacyBilling.charge(req);

    Runnable check — from the repo run bun run docs/blog/examples/example-rollout.ts (or paste the snippet into a script and run with bun run or ts-node):

    // example-rollout.ts
function hashToPercent(s: string): number {
  let h = 0;
  for (let i = 0; i < s.length; i++) {
    h = (h  31 + s.charCodeAt(i)) >>> 0;
  }
  return h % 100;
}
function isInRollout(flagName: string, percent: number, contextKey: string): boolean {
  if (percent <= 0) return false;
  if (percent >= 100) return true;
  return hashToPercent(${flagName}:${contextKey}) < percent;
}
    const tenantIds = ["tenant-a", "tenant-b", "tenant-c", "tenant-d", "tenant-e"];
console.log("Rollout 40% for flag 'newBilling':");
tenantIds.forEach((id) => {
  console.log(  ${id} -> ${isInRollout("newBilling", 40, id) ? "ON" : "OFF"});
});

    Example output (from bun run example-rollout.ts):

    Rollout 40% for flag 'newBilling':
  tenant-a -> OFF
  tenant-b -> OFF
  tenant-c -> OFF
  tenant-d -> OFF
  tenant-e -> OFF

    With these five keys the hash lands above 40% for all; with a larger set of tenant IDs you’ll see roughly that percentage ON. Same key always gets the same result, so users don’t flicker between old and new behavior.

    Kill switches in practice

    A kill switch is just a feature flag you flip when something is wrong. To make it reliable:

  • Short TTL or no cache for that flag so the change is visible quickly (see getFlagRemote(name, true) above).
  • Fail closed: If the flag service is down, decide policy upfront — e.g. “treat as off” so the risky feature is disabled.
  • Single place to flip: One dashboard or one config key per feature, so on-call (e.g. Raj at 03:00) isn’t hunting through env vars or code.
  • Audit: Log when the flag is evaluated and when it’s changed, so you can see who turned off what and when.

    • We keep our most critical flags (payment path, new auth flow) in a remote store with a 30s TTL and a “kill switch” API that bypasses cache. Flipping the switch propagates in under a minute.

    Open-source tools and when to use them

    You don’t have to build the store and UI yourself. Open-source feature-flag services give you a backend, SDKs, and often a UI for toggles and rollouts.

    | Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Env / config only | No extra infra, type-safe, easy tests | No runtime change without restart/redeploy | Small apps, flags changed rarely | | DB or remote config (custom) | Runtime changes, full control, can do kill switches with short TTL | You build and maintain the store and (optional) UI | You need control and already have a config DB or HTTP service | | Unleash (open-source) | Hosted or self-hosted, UI, SDKs, percentage rollouts, segments | Extra service to run and maintain | Teams that want a ready-made solution and can run another service | | Flagsmith (open-source) | Similar to Unleash, cloud or self-hosted | Same as above | When you want a second option to compare with Unleash | | LaunchDarkly / Split (commercial) | Mature, many integrations, experiments | Cost, vendor lock-in | When budget allows and you want minimal ops |

    Unleash is widely used and runs well in Docker or Kubernetes. Minimal usage with the Node SDK:

    // example-unleash.ts — run with: npx ts-node example-unleash.ts (after npm i unleash-client)
import { initialize, isEnabled } from "unleash-client";
    const client = initialize({
  url: process.env.UNLEASH_URL || "http://localhost:4242/api",
  appName: process.env.UNLEASH_APP_NAME || "my-app",
  customHeaders: { Authorization: process.env.UNLEASH_API_TOKEN || "" },
});
    client.on("ready", () => {
  const enabled = isEnabled("newBilling");
  console.log("Flag 'newBilling':", enabled);
  process.exit(0);
});
    setTimeout(() => {
  console.log("Unleash client timeout (not running Unleash?)");
  process.exit(1);
}, 5000);

    If Unleash is running and the flag exists, you’ll see Flag 'newBilling': true or false. Otherwise the script exits after 5 seconds — which matches the “fail closed” idea: if the flag service is unavailable, your code can treat flags as off or use local defaults.

    What went wrong (lessons learned)

  • Typo in flag key: We had useNewBilling in code and use_new_billing in the config store. The SDK returned “off” for the typo key. We didn’t catch it until we enabled the flag in the UI and saw no traffic change. Fix: Single source of truth for flag names (e.g. a shared const or codegen from the same list the UI uses).
  • Cache too long for kill switches: Initially we cached remote flags for 5 minutes. When we turned off the new payment path, some instances took 5 minutes to see the change. Fix: Short TTL (30–60s) for flags that might be used as kill switches, or a dedicated “bypass cache” path for critical toggles.
  • No fallback when the flag service was down: In one incident the config service was unreachable and our SDK defaulted to “on” for a new feature. We had intended “off” when unavailable. Fix: Explicit default and “fail closed” for dangerous features when the flag backend is unavailable.

    • Actionable next steps

  • Introduce one kill switch for your riskiest recent feature (e.g. new payment or auth path). Implement it with env today; later move it to a remote or DB-backed flag with short TTL so you can flip it without redeploy.
  • Add a percentage rollout for the next big change: use a stable key (tenant ID or user ID) and a hash-based percentage so the same user always sees the same path. Start at 5–10% and increase only when metrics look good.
  • Try Unleash or Flagsmith in Docker locally: create a flag, use the SDK in a small script (like the example above), and flip the flag in the UI to see the behavior. That gives you a concrete baseline if you later want a hosted solution.
  • Document your “when the flag service is down” policy (e.g. “treat all flags as off” or “use env defaults”) and implement that in code so you don’t have to decide during an outage.
  • Audit flag usage once per quarter: remove flags that have been 100% on or 100% off for months and fold the code path into the main branch so you don’t carry dead toggles forever.

    • Feature flags done right are mostly about clear patterns, a safe default when the system is unavailable, and a short path from “something is wrong” to “that thing is off.” Start with one kill switch and one gradual rollout; then grow from there.
