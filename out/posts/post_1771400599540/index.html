HTTP Caching Headers for TypeScript APIs (2026)

Caching reduces load on your backend and improves latency for clients. This post shows how to set standard HTTP caching headers from a TypeScript API so browsers and CDNs can cache responses correctly.

Why Cache Headers Matter

Without cache headers, every request hits your server. With Cache-Control, ETag, and Last-Modified, clients and proxies can reuse responses when appropriate. You control freshness (how long a response is valid) and support conditional requests (304 Not Modified) to save bandwidth.

Cache-Control Basics

Cache-Control is the main header. Common directives:

  • public — Response may be stored by any cache (browser, CDN).
  • private — Only the user's browser may cache (e.g. personalized data).
  • max-age=N — Response is fresh for N seconds.
  • no-store — Do not store the response anywhere.
  • no-cache — Store but revalidate with the server before reuse (often used with ETag).
  • must-revalidate — Once stale, must revalidate; no stale serve without checking.

    • Example for a public, cacheable list that is fresh for 5 minutes:

    res.setHeader("Cache-Control", "public, max-age=300");

    Example for private user data that must revalidate:

    res.setHeader("Cache-Control", "private, no-cache, must-revalidate");

    ETag and Conditional Requests

    ETag is an opaque string that changes when the resource changes. Clients send If-None-Match: . If the current ETag matches, you respond with 304 Not Modified and no body, saving bandwidth.

    Minimal Node/Bun example:

    import { createServer } from "http";
    function getListETag(data: unknown): string {
  const str = JSON.stringify(data);
  let hash = 0;
  for (let i = 0; i < str.length; i++)
    hash = (hash << 5) - hash + str.charCodeAt(i);
  return "${hash >>> 0}";
}
    createServer((req, res) => {
  const list = { items: [1, 2, 3], updated: Date.now() };
  const etag = getListETag(list);
      if (req.headers["if-none-match"] === etag) {
    res.writeHead(304);
    res.end();
    return;
  }
      res.setHeader("Cache-Control", "public, max-age=60");
  res.setHeader("ETag", etag);
  res.setHeader("Content-Type", "application/json");
  res.writeHead(200);
  res.end(JSON.stringify(list));
}).listen(3000);

    For production, use a proper hash (e.g. crypto.createHash("sha256").update(payload).digest("hex")) or a weak ETag with W/ prefix if you prefer.

    Last-Modified and If-Modified-Since

    For resources that have a clear “last modified” time (e.g. a file or a record’s updated_at), you can send Last-Modified and honor If-Modified-Since:

    const lastModified = new Date(record.updated_at).toUTCString();
if (req.headers["if-modified-since"] === lastModified) {
  res.writeHead(304);
  res.end();
  return;
}
res.setHeader("Last-Modified", lastModified);
res.setHeader("Cache-Control", "public, max-age=0, must-revalidate");

    Use max-age=0, must-revalidate when you want clients to always revalidate but still benefit from 304 when unchanged.

    When Not to Cache

  • User-specific or sensitive data — Prefer private or no-store.
  • Real-time or highly dynamic data — Short max-age or no-cache + ETag.
  • Mutable mutations (POST/PUT/DELETE) — Do not cache; use no-store on responses and invalidate related URLs if your design exposes them.

    • Summary

    Set Cache-Control on every response: public/private, plus max-age or no-cache/must-revalidate as appropriate. Add ETag (and optionally Last-Modified) for conditional requests and 304 responses. In TypeScript APIs, a small helper that sets these headers per route will keep caching consistent and your APIs faster and cheaper to run.
