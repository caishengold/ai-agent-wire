8:T3553,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Event-driven architecture in action: real-world case studies</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s team added a “notify on order shipped” feature by calling the notification service directly from the order service. A few months later, marketing wanted “send discount when cart abandoned,” support wanted “create ticket when refund requested,” and analytics wanted “log every state change.” Each new consumer meant changing the order service, redeploying it, and hoping nothing broke. They switched to publishing events and letting each team subscribe. The order service shrank; new features stopped requiring changes to it. This post walks through three real-world patterns: order/cart events, audit and analytics pipelines, and cross-service workflows — with concrete examples and lessons from production.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Context:</strong> Event-driven architecture (EDA) means services communicate by producing and consuming events instead of calling each other directly. You get loose coupling, easier scaling of consumers, and the ability to add new behaviour without touching producers. The trade-off is eventual consistency, debugging across async flows, and the need for a reliable event bus. We focus on patterns that work with Redis Streams, RabbitMQ, or cloud queues (e.g. SQS) and TypeScript/Bun backends.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Case study 1: Order and cart events (e-commerce)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Problem:</strong> One service (orders) was the single point of change. Every new “when X happens, do Y” required code in that service.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Approach:</strong> The order service publishes events when state changes: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OrderCreated</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OrderPaid</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OrderShipped</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OrderRefunded</code>. Notification, marketing, analytics, and support each subscribe to the events they need. The order service never imports those domains.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Event shape (minimal but useful):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// events/order-events.ts — shared types; producers and consumers both use these
export type OrderEvent =
  | { type: "OrderCreated"; orderId: string; userId: string; amountCents: number; at: string }
  | { type: "OrderPaid"; orderId: string; at: string }
  | { type: "OrderShipped"; orderId: string; trackingCode: string; at: string }
  | { type: "OrderRefunded"; orderId: string; reason: string; at: string };</p><p class="text-slate-300 leading-relaxed mb-4">export function orderEventId(ev: OrderEvent): string {
  return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">${ev.type}-${ev.orderId}-${ev.at}</code>;
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Producer (order service):</strong> publish after persisting. Use a single function so all events go through the same bus and format.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// order-service/publish.ts — after DB write, publish one event
import { Redis } from "ioredis";
import type { OrderEvent } from "../events/order-events";</p><p class="text-slate-300 leading-relaxed mb-4">const STREAM = "orders:events";
const redis = new Redis(process.env.REDIS_URL!);</p><p class="text-slate-300 leading-relaxed mb-4">export async function publishOrderEvent(ev: OrderEvent): Promise<void> {
  await redis.xadd(STREAM, "<em>", "payload", JSON.stringify(ev), "type", ev.type);
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Consumer (notification worker):</strong> read from the stream, handle only the events it cares about, and acknowledge. Other consumers can read the same stream (or a separate one if you fan out at publish time).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// notification-worker/order-handler.ts — one of many consumers
import { Redis } from "ioredis";
import type { OrderEvent } from "../events/order-events";</p><p class="text-slate-300 leading-relaxed mb-4">const STREAM = "orders:events";
const GROUP = "notifications";
const redis = new Redis(process.env.REDIS_URL!);</p><p class="text-slate-300 leading-relaxed mb-4">async function handle(ev: OrderEvent): Promise<void> {
  if (ev.type === "OrderShipped") {
    await sendShippingNotification(ev.orderId, ev.trackingCode);
  }
  if (ev.type === "OrderRefunded") {
    await sendRefundConfirmation(ev.orderId);
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">async function run(): Promise<void> {
  while (true) {
    const result = await redis.xreadgroup("GROUP", GROUP, "notif-worker", "COUNT", 10, "BLOCK", 5000, "STREAMS", STREAM, ">");
    if (!result) continue;
    for (const [, messages] of result) {
      for (const [id, fields] of messages) {
        const payload = fields[fields.indexOf("payload") + 1];
        await handle(JSON.parse(payload) as OrderEvent);
        await redis.xack(STREAM, GROUP, id);
      }
    }
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Outcome:</strong> New features (e.g. “create support ticket on refund”) are new consumers. No changes to the order service. Teams can deploy and scale consumers independently.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Case study 2: Audit and analytics pipeline</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Problem:</strong> Compliance required a full audit trail of who did what and when. Analytics wanted the same data in a different shape (aggregated, denormalized). Doing both inside each API would have duplicated logic and slowed requests.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Approach:</strong> Services emit <strong>audit events</strong> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">UserLoggedIn</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DocumentApproved</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ConfigChanged</code>) to a dedicated stream. One consumer writes to an audit store (append-only, immutable). Another consumer feeds an analytics warehouse or real-time dashboards. The API only publishes; it does not wait for audit or analytics.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Event and producer example:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// events/audit-events.ts
export type AuditEvent = {
  type: string;
  actorId: string;
  resource: string;
  action: string;
  meta?: Record<string, unknown>;
  at: string; // ISO 8601
};</p><p class="text-slate-300 leading-relaxed mb-4">// audit.ts — call after any sensitive action
export async function audit(ev: AuditEvent): Promise<void> {
  await redis.xadd("audit:events", "</em>", "payload", JSON.stringify(ev));
  // Fire-and-forget from API’s perspective; don’t await consumers
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Lessons:</strong> Use a single stream (or partition by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">actorId</code>/date if volume is huge) so ordering is preserved. Give each consumer its own consumer group so audit and analytics can process at different speeds. Store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">at</code> in UTC and always specify time zone when you display (e.g. “2026-02-13 00:50 UTC”).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Case study 3: Cross-service workflow (saga-style)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Problem:</strong> “When payment succeeds, reserve inventory, then ship.” If inventory fails, you must refund. Multiple services and failures make “one transaction” impossible; you need a workflow that can compensate.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Approach:</strong> A small <strong>orchestrator</strong> (or workflow engine) subscribes to events from payment, inventory, and shipping. It keeps minimal state (e.g. “waiting for inventory” for this <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">orderId</code>) and emits commands or more events. On failure events (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">InventoryReservationFailed</code>), it triggers compensation (e.g. emit <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RefundRequested</code>). This is a saga: forward steps and compensating steps driven by events.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Sketch:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>PaymentSuccess → Orchestrator → ReserveInventory
InventoryReserved → Orchestrator → CreateShipment
ShipmentCreated → Orchestrator → Done</p><p class="text-slate-300 leading-relaxed mb-4">InventoryReservationFailed → Orchestrator → RefundRequested
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Implementation note:</strong> Store workflow state (e.g. in Redis or SQLite) keyed by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">orderId</code> so you know which step you’re in. Idempotency keys on commands (e.g. “refund for order X”) prevent double refunds when you retry.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Ordering and partitioning:</strong> Redis Streams (and most queues) preserve order per stream or per partition. If you need global order across all events, use one stream or partition by a key (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">orderId</code>) so all events for that key go to the same partition.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Schema evolution:</strong> Add optional fields; avoid removing or renaming. Consumers should ignore unknown fields. Consider a small version or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">eventSchemaVersion</code> in the payload for big changes.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Poison messages:</strong> One bad event can block a consumer. Parse in a try/catch; on failure, move the message to a dead-letter stream (or increment retry count) and ack so the rest of the stream progresses. Alert on DLQ depth.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Debugging:</strong> Correlation IDs help. Put <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">correlationId</code> (and optionally <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">causationId</code>) in every event so you can trace a flow across services in logs and traces.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>We started with “fire and forget” from the API and no consumer groups.</strong> When we added a second consumer, we had to introduce groups and explicit ack so each consumer could progress independently. Doing that from day one would have saved a migration.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Pick one bounded flow (e.g. “order lifecycle” or “user signup”) and replace one direct call with an event: producer publishes after the write, one consumer does the old behaviour. Ship that. Then add a second consumer (e.g. analytics or notifications) without changing the producer. That’s event-driven architecture in action — and you can do it this week with Redis Streams or your existing queue.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
