Environment variable management: dotenv, Vault, 1Password CLI, and Bun's built-in .env

Sofia's staging deploy worked. Production didn't. The app read DATABASE_URL from process.env; in production the process was started by systemd without loading the project's .env file. The service kept falling back to an empty string or a default, and the first user request hit "connection refused". Took 40 minutes to trace it to "env not loaded where we thought it was." Getting env vars into the right place, at the right time, without leaking them into logs or repos, is one of those chores that only gets attention after it breaks. This post compares four practical options: the classic dotenv pattern, HashiCorp Vault, 1Password CLI, and Bun's native .env handling — with runnable examples and a few mistakes we've run into.

Who this is for: Developers and small teams who need to manage API keys, DB URLs, and feature flags across local, CI, and production without turning every deploy into a secret-hunt.

The problem in one sentence

Your code expects process.env.API_KEY (or Bun.env.API_KEY). Something has to populate that before the first line of app logic runs — and that "something" differs by runtime, deployment target, and how much you care about rotation and audit.

Option 1: dotenv (Node and most runtimes)

The dotenv pattern: read a .env file from disk, parse KEY=value lines, and assign them to process.env. Works in Node, Deno (via a port), and any environment where you control the entrypoint and the file is present.

Example: Node with dotenv. Create a small script and a .env file in the same directory:

mkdir -p /tmp/env-demo && cd /tmp/env-demo
npm init -y
npm install dotenv


.env (do not commit; add to .gitignore)

API_KEY=sk-demo-abc123
DATABASE_URL=postgres://localhost:5432/mydb
LOG_LEVEL=debug


// index.mjs — run with: node index.mjs
import "dotenv/config";  // loads .env into process.env by default
console.log("API_KEY set:", !!process.env.API_KEY);
console.log("LOG_LEVEL:", process.env.LOG_LEVEL);
console.log("DATABASE_URL (masked):", process.env.DATABASE_URL?.replace(/:[^:@]+@/, ":*@") ?? "not set");


$ node index.mjs
API_KEY set: true
LOG_LEVEL: debug
DATABASE_URL (masked): postgres://@localhost:5432/mydb

You can also load a specific path: dotenv.config({ path: "/etc/myapp/.env" }). In production, many teams don't ship a .env file; they rely on the process environment (systemd Environment=, Kubernetes secrets, etc.) and use dotenv only for local development. That avoids putting secrets on disk in prod.

Option 2: Bun's built-in .env support

Bun automatically loads .env, .env.local, .env.production, and similar files before your script runs. No import, no extra dependency. Priority order: .env.local overrides .env; env-specific files (e.g. .env.production) are chosen by Bun.env.NODE_ENV or similar.

Example: same .env, no dotenv package.

cd /tmp/env-demo

re-use the same .env from above; no npm install needed



// bun-app.mjs — run with: bun run bun-app.mjs
// No import: Bun has already loaded .env into process.env and Bun.env
console.log("API_KEY set:", !!Bun.env.API_KEY);
console.log("LOG_LEVEL:", Bun.env.LOG_LEVEL);


$ bun run bun-app.mjs
API_KEY set: true
LOG_LEVEL: debug

So for local and script use, Bun removes the "did we load .env?" step. In production, again, you often inject env via the process (systemd, container, etc.); Bun still reads any .env present in the working directory, so be explicit about not shipping .env in the image or deploy artifact if you don't want file-based secrets there.

Option 3: HashiCorp Vault

Vault is a secret store: you put secrets in Vault, and apps (or CI) pull them at runtime via the Vault API or the Vault agent. Suited to teams that need rotation, audit logs, and a single source of truth across many services.

Typical flow: your app (or a sidecar) authenticates to Vault (e.g. with a token or Kubernetes auth), then reads a path like secret/data/myapp/config and maps the response into environment variables or a temp file. No .env in the repo; secrets live in Vault.

Minimal example: fetching one secret and exporting it. This assumes Vault is already running and you have a token (e.g. VAULT_TOKEN or ~/.vault-token).

One-time: start Vault dev server and write a secret (not for production)


vault server -dev


export VAULT_ADDR='http://127.0.0.1:8200'


vault kv put secret/myapp API_KEY=sk-live-xyz DATABASE_URL="postgres://..."
In your app's startup script or systemd ExecStartPre:

export API_KEY=$(vault kv get -field=API_KEY secret/myapp)
export DATABASE_URL=$(vault kv get -field=DATABASE_URL secret/myapp)
exec node index.mjs

So the "env management" is: Vault holds the secrets; a small wrapper or agent injects them into the process environment before your app starts. Your app stays the same (process.env.API_KEY); only the source of that value changes.

Option 4: 1Password CLI

1Password CLI (op) lets you pull secrets from a 1Password vault into env vars or files. Handy if your team already uses 1Password and you want to avoid maintaining a separate secret store.

Example: inject env from a 1Password item into a command.

One-time: sign in (e.g. op signin)


Item in 1Password: "MyApp Env" with fields API_KEY, DATABASE_URL
eval $(op inject -i env-template.env)
node index.mjs

Where env-template.env looks like:

API_KEY=op://VaultName/MyApp Env/API_KEY
DATABASE_URL=op://VaultName/MyApp Env/DATABASE_URL

op inject replaces the op:// references with the actual secret values and prints KEY=value lines; eval puts them in the shell environment. Alternatively, op run --env-file=env-template.env -- node index.mjs runs the process with those vars injected, without eval.

Comparison: when to use which

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | dotenv | Simple, works everywhere (Node, Deno), no runtime lock-in. | You must remember to load it (e.g. at entrypoint); file must exist where the app runs. | Local dev, scripts, any Node/JS app; prod often uses process env only. | | Bun built-in | Zero config for .env; no extra dependency. | Bun-only; behavior is implicit (load order, which file). | Bun projects; local and script-heavy workflows. | | HashiCorp Vault | Central store, rotation, audit, dynamic secrets. | Operational overhead (run Vault, auth, policies). | Multi-service teams, compliance, rotation requirements. | | 1Password CLI | Reuses existing 1Password vault; good DX for devs. | Depends on 1Password and op; less common in headless/CI. | Teams already on 1Password; local and some CI. |

Rough rule of thumb: local and scripts → dotenv or Bun; production → process env from systemd/Kubernetes/CI, optionally fed by Vault or 1Password; strict audit/rotation → Vault (or similar) as the source, then inject into process env.

Lessons learned

What went wrong (more than once):

  • Assumed .env was loaded. A service was started with bun run services/publisher.ts. The scheduler had changed the working directory before spawning; the .env file lived in the project root. Bun loaded .env from the current working directory, which was different. Result: DEVTO_API_KEY was undefined, every publish failed with 401. Fix: set cwd to the project root when spawning, or pass env explicitly (e.g. from a single source of truth).

  • Dotenv loaded twice, second file overwrote the first. We had dotenv.config() in the main entrypoint and again in a shared library. The library used path: join(__dirname, ".env"), which pointed to a different directory and overwrote DATABASE_URL with an empty or wrong value. Took a while to notice because local dev had the "right" .env first. Fix: load dotenv once at the top-level entrypoint; libraries should not load env by default.

  • Vault KV path mismatch. We moved from KV v1 to KV v2 and kept using secret/myapp in code. Vault KV v2 uses secret/data/myapp for read/write. The app got 404s until we updated the path. Error message was clear ("no value found"); the mistake was assuming path layout stayed the same across versions.

  • 1Password op run and CI. In CI we didn't have an interactive 1Password sign-in. We had to switch to a service account token and op run with OP_SERVICE_ACCOUNT_TOKEN; the first few runs failed with "sign-in required" until we read the headless docs. So: 1Password CLI is smooth for local use; for CI, plan for service accounts and token injection.

    • Runnable example 2: Bun loads .env, then we validate

    This script is the kind of thing you might run in CI or after deploy to confirm required vars are present. It uses Bun so .env is loaded automatically from the project root when you run it with bun run from that root.

    // scripts/check-env.mjs — run from repo root: bun run scripts/check-env.mjs
const required = ["API_KEY", "DATABASE_URL"];
const missing = required.filter((k) => !process.env[k] && !Bun.env[k]);
if (missing.length > 0) {
  console.error("Missing env:", missing.join(", "));
  process.exit(1);
}
console.log("All required env vars set.");


    $ cd /tmp/env-demo && bun run scripts/check-env.mjs
All required env vars set.

    If you run it from a directory that has no .env, or with vars commented out, you get:

    Missing env: API_KEY, DATABASE_URL

    So: Bun's built-in loading is convenient, but validation (like this or a small schema lib) catches misconfiguration before the app hits a random "undefined" at runtime.

    Actionable next steps

  • Decide the single source of truth per environment. For local: a .env (or Bun's default) is fine. For production: document whether env comes from systemd, Kubernetes, or a Vault/1Password injector — and make sure the app never assumes a .env file exists there.

  • Load .env once at the entrypoint. If you use dotenv, call dotenv.config() (or import "dotenv/config") only in the main entry file. Avoid loading it again in libraries or workers unless you explicitly want overrides.

  • Add a small env check script. Like the Bun example above: a script that exits non-zero if required keys are missing. Run it in CI and after deploy (or in a health check) so you fail fast instead of at first user request.

  • If you use Vault, pin the KV path and API version. KV v2 paths include /data/; document the exact path and test with vault kv get so app and ops use the same path.

  • Keep .env out of Git and images. Ensure .env is in .gitignore and that production images or deploy artifacts don't bundle it unless you intentionally ship a non-secret defaults file (e.g. .env.example with placeholders only).

    • Once env loading is explicit and consistent, "it works on my machine" and "staging worked but prod didn't" become a lot rarer.
