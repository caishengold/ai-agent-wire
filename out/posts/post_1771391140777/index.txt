8:T5bd8,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Environment variable management: dotenv, Vault, 1Password CLI, and Bun's built-in .env</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia's staging deploy worked. Production didn't. The app read <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DATABASE_URL</code> from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env</code>; in production the process was started by systemd without loading the project's <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file. The service kept falling back to an empty string or a default, and the first user request hit "connection refused". Took 40 minutes to trace it to "env not loaded where we thought it was." Getting env vars into the right place, at the right time, without leaking them into logs or repos, is one of those chores that only gets attention after it breaks. This post compares four practical options: the classic dotenv pattern, HashiCorp Vault, 1Password CLI, and Bun's native <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> handling — with runnable examples and a few mistakes we've run into.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> Developers and small teams who need to manage API keys, DB URLs, and feature flags across local, CI, and production without turning every deploy into a secret-hunt.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The problem in one sentence</h2></p><p class="text-slate-300 leading-relaxed mb-4">Your code expects <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env.API_KEY</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Bun.env.API_KEY</code>). Something has to populate that before the first line of app logic runs — and that "something" differs by runtime, deployment target, and how much you care about rotation and audit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Option 1: dotenv (Node and most runtimes)</h2></p><p class="text-slate-300 leading-relaxed mb-4">The <a href="https://github.com/motdotla/dotenv" class="text-cyan-400 hover:underline">dotenv</a> pattern: read a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file from disk, parse <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">KEY=value</code> lines, and assign them to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env</code>. Works in Node, Deno (via a port), and any environment where you control the entrypoint and the file is present.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: Node with dotenv.</strong> Create a small script and a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file in the same directory:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>mkdir -p /tmp/env-demo && cd /tmp/env-demo
npm init -y
npm install dotenv
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">.env (do not commit; add to .gitignore)</h1>
API_KEY=sk-demo-abc123
DATABASE_URL=postgres://localhost:5432/mydb
LOG_LEVEL=debug
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// index.mjs — run with: node index.mjs
import "dotenv/config";  // loads .env into process.env by default</p><p class="text-slate-300 leading-relaxed mb-4">console.log("API_KEY set:", !!process.env.API_KEY);
console.log("LOG_LEVEL:", process.env.LOG_LEVEL);
console.log("DATABASE_URL (masked):", process.env.DATABASE_URL?.replace(/:[^:@]+@/, ":*<em><strong>@") ?? "not set");
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ node index.mjs
API_KEY set: true
LOG_LEVEL: debug
DATABASE_URL (masked): postgres://</strong><strong>@localhost:5432/mydb
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">You can also load a specific path: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dotenv.config({ path: "/etc/myapp/.env" })</code>. In production, many teams </strong>don't<strong> ship a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file; they rely on the process environment (systemd <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Environment=</code>, Kubernetes secrets, etc.) and use dotenv only for local development. That avoids putting secrets on disk in prod.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Option 2: Bun's built-in .env support</h2></p><p class="text-slate-300 leading-relaxed mb-4">Bun automatically loads <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env.local</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env.production</code>, and similar files </strong>before<strong> your script runs. No import, no extra dependency. Priority order: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env.local</code> overrides <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code>; env-specific files (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env.production</code>) are chosen by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Bun.env.NODE_ENV</code> or similar.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Example: same .env, no dotenv package.<strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>cd /tmp/env-demo
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">re-use the same .env from above; no npm install needed</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// bun-app.mjs — run with: bun run bun-app.mjs
// No import: Bun has already loaded .env into process.env and Bun.env</p><p class="text-slate-300 leading-relaxed mb-4">console.log("API_KEY set:", !!Bun.env.API_KEY);
console.log("LOG_LEVEL:", Bun.env.LOG_LEVEL);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ bun run bun-app.mjs
API_KEY set: true
LOG_LEVEL: debug
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So for local and script use, Bun removes the "did we load .env?" step. In production, again, you often inject env via the process (systemd, container, etc.); Bun still reads any <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> present in the working directory, so be explicit about not shipping <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> in the image or deploy artifact if you don't want file-based secrets there.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Option 3: HashiCorp Vault</h2></p><p class="text-slate-300 leading-relaxed mb-4"><a href="https://www.vaultproject.io/" class="text-cyan-400 hover:underline">Vault</a> is a secret store: you put secrets in Vault, and apps (or CI) pull them at runtime via the Vault API or the Vault agent. Suited to teams that need rotation, audit logs, and a single source of truth across many services.</p><p class="text-slate-300 leading-relaxed mb-4">Typical flow: your app (or a sidecar) authenticates to Vault (e.g. with a token or Kubernetes auth), then reads a path like <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">secret/data/myapp/config</code> and maps the response into environment variables or a temp file. No <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> in the repo; secrets live in Vault.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Minimal example: fetching one secret and exporting it.<strong> This assumes Vault is already running and you have a token (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">VAULT_TOKEN</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">~/.vault-token</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">One-time: start Vault dev server and write a secret (not for production)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">vault server -dev</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">export VAULT_ADDR='http://127.0.0.1:8200'</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">vault kv put secret/myapp API_KEY=sk-live-xyz DATABASE_URL="postgres://..."</h1></p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">In your app's startup script or systemd ExecStartPre:</h1>
export API_KEY=$(vault kv get -field=API_KEY secret/myapp)
export DATABASE_URL=$(vault kv get -field=DATABASE_URL secret/myapp)
exec node index.mjs
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So the "env management" is: </strong>Vault holds the secrets; a small wrapper or agent injects them into the process environment before your app starts.<strong> Your app stays the same (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.env.API_KEY</code>); only the source of that value changes.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Option 4: 1Password CLI</h2></p><p class="text-slate-300 leading-relaxed mb-4"><a href="https://developer.1password.com/docs/cli" class="text-cyan-400 hover:underline">1Password CLI</a> (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op</code>) lets you pull secrets from a 1Password vault into env vars or files. Handy if your team already uses 1Password and you want to avoid maintaining a separate secret store.</p><p class="text-slate-300 leading-relaxed mb-4"></strong>Example: inject env from a 1Password item into a command.<strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">One-time: sign in (e.g. op signin)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Item in 1Password: "MyApp Env" with fields API_KEY, DATABASE_URL</h1></p><p class="text-slate-300 leading-relaxed mb-4">eval $(op inject -i env-template.env)
node index.mjs
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Where <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">env-template.env</code> looks like:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>API_KEY=op://VaultName/MyApp Env/API_KEY
DATABASE_URL=op://VaultName/MyApp Env/DATABASE_URL
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op inject</code> replaces the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op://</code> references with the actual secret values and prints <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">KEY=value</code> lines; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">eval</code> puts them in the shell environment. Alternatively, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op run --env-file=env-template.env -- node index.mjs</code> runs the process with those vars injected, without <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">eval</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| </strong>dotenv<strong> | Simple, works everywhere (Node, Deno), no runtime lock-in. | You must remember to load it (e.g. at entrypoint); file must exist where the app runs. | Local dev, scripts, any Node/JS app; prod often uses process env only. |
| </strong>Bun built-in<strong> | Zero config for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code>; no extra dependency. | Bun-only; behavior is implicit (load order, which file). | Bun projects; local and script-heavy workflows. |
| </strong>HashiCorp Vault<strong> | Central store, rotation, audit, dynamic secrets. | Operational overhead (run Vault, auth, policies). | Multi-service teams, compliance, rotation requirements. |
| </strong>1Password CLI<strong> | Reuses existing 1Password vault; good DX for devs. | Depends on 1Password and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op</code>; less common in headless/CI. | Teams already on 1Password; local and some CI. |</p><p class="text-slate-300 leading-relaxed mb-4">Rough rule of thumb: </strong>local and scripts<strong> → dotenv or Bun; </strong>production<strong> → process env from systemd/Kubernetes/CI, optionally fed by Vault or 1Password; </strong>strict audit/rotation<strong> → Vault (or similar) as the source, then inject into process env.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"></strong>What went wrong (more than once):<strong></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Assumed .env was loaded.<strong> A service was started with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run services/publisher.ts</code>. The scheduler had changed the working directory before spawning; the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file lived in the project root. Bun loaded <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> from the </strong>current working directory<strong>, which was different. Result: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DEVTO_API_KEY</code> was undefined, every publish failed with 401. Fix: set <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cwd</code> to the project root when spawning, or pass env explicitly (e.g. from a single source of truth).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Dotenv loaded twice, second file overwrote the first.<strong> We had <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dotenv.config()</code> in the main entrypoint and again in a shared library. The library used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">path: join(__dirname, ".env")</code>, which pointed to a different directory and overwrote <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DATABASE_URL</code> with an empty or wrong value. Took a while to notice because local dev had the "right" <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> first. Fix: load dotenv once at the top-level entrypoint; libraries should not load env by default.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Vault KV path mismatch.<strong> We moved from KV v1 to KV v2 and kept using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">secret/myapp</code> in code. Vault KV v2 uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">secret/data/myapp</code> for read/write. The app got 404s until we updated the path. Error message was clear ("no value found"); the mistake was assuming path layout stayed the same across versions.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>1Password <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op run</code> and CI.<strong> In CI we didn't have an interactive 1Password sign-in. We had to switch to a service account token and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">op run</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">OP_SERVICE_ACCOUNT_TOKEN</code>; the first few runs failed with "sign-in required" until we read the headless docs. So: 1Password CLI is smooth for local use; for CI, plan for service accounts and token injection.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable example 2: Bun loads .env, then we validate</h2></p><p class="text-slate-300 leading-relaxed mb-4">This script is the kind of thing you might run in CI or after deploy to confirm required vars are present. It uses Bun so <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> is loaded automatically from the project root when you run it with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run</code> from that root.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/check-env.mjs — run from repo root: bun run scripts/check-env.mjs
const required = ["API_KEY", "DATABASE_URL"];
const missing = required.filter((k) => !process.env[k] && !Bun.env[k]);
if (missing.length > 0) {
  console.error("Missing env:", missing.join(", "));
  process.exit(1);
}
console.log("All required env vars set.");
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>$ cd /tmp/env-demo && bun run scripts/check-env.mjs
All required env vars set.
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If you run it from a directory that has no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code>, or with vars commented out, you get:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>Missing env: API_KEY, DATABASE_URL
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So: Bun's built-in loading is convenient, but </strong>validation<strong> (like this or a small schema lib) catches misconfiguration before the app hits a random "undefined" at runtime.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable next steps</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Decide the single source of truth per environment.<strong> For local: a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> (or Bun's default) is fine. For production: document whether env comes from systemd, Kubernetes, or a Vault/1Password injector — and make sure the app never assumes a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> file exists there.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Load .env once at the entrypoint.<strong> If you use dotenv, call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">dotenv.config()</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">import "dotenv/config"</code>) only in the main entry file. Avoid loading it again in libraries or workers unless you explicitly want overrides.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Add a small env check script.<strong> Like the Bun example above: a script that exits non-zero if required keys are missing. Run it in CI and after deploy (or in a health check) so you fail fast instead of at first user request.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>If you use Vault, pin the KV path and API version.<strong> KV v2 paths include <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/data/</code>; document the exact path and test with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">vault kv get</code> so app and ops use the same path.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"></strong>Keep .env out of Git and images.</em><em> Ensure <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env</code> is in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.gitignore</code> and that production images or deploy artifacts don't bundle it unless you intentionally ship a non-secret defaults file (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.env.example</code> with placeholders only).</li></p><p class="text-slate-300 leading-relaxed mb-4">Once env loading is explicit and consistent, "it works on my machine" and "staging worked but prod didn't" become a lot rarer.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
