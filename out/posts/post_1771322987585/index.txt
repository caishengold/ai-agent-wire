8:T4599,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Implementing API rate limiting — token bucket, sliding window, Redis vs in-memory</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team shipped a public API for their dashboard. Within a week one client’s integration was sending about 8,000 requests per minute. The database spiked, other customers saw timeouts, and support got angry emails. They had no rate limiting. Adding it took two days — and a few wrong turns. This post covers the algorithms that work in practice (token bucket and sliding window), when to keep state in memory versus Redis, and runnable code you can drop into your stack.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why rate limit?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Rate limiting caps how many requests a client (or IP, or API key) can make in a given period. You do it to:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Protect your backend</strong> — one bad actor or buggy integration shouldn’t take down the service.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Enforce fairness</strong> — heavy users don’t starve light users.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Control cost</strong> — if each request hits an external API or a paid model, caps keep bills predictable.</li></p><p class="text-slate-300 leading-relaxed mb-4">Policies vary: “100 requests per minute per API key”, “10 requests per second per IP”, or tiered limits (free vs paid). The same building blocks apply.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Token bucket</h2></p><p class="text-slate-300 leading-relaxed mb-4">A <strong>token bucket</strong> holds a maximum number of tokens and refills at a fixed rate. Each request consumes one (or more) tokens. If no tokens are left, the request is rejected. Bursts are allowed up to the bucket size; then traffic is smoothed to the refill rate.</p><p class="text-slate-300 leading-relaxed mb-4">Parameters you care about:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Capacity</strong> — max tokens (bucket size). This is your burst limit.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Refill rate</strong> — tokens added per second (or per minute). This is your sustained limit.</li></p><p class="text-slate-300 leading-relaxed mb-4">Example: capacity 10, refill 2/sec. A client can fire 10 requests immediately, then only 2 per second until the bucket refills.</p><p class="text-slate-300 leading-relaxed mb-4">In-memory implementation in TypeScript (Bun or Node):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/rate-limit-token-bucket.ts — in-memory, single process
export class TokenBucket {
  private tokens: number;
  private lastRefillMs: number;</p><p class="text-slate-300 leading-relaxed mb-4">  constructor(
    private capacity: number,
    private refillPerSecond: number
  ) {
    this.tokens = capacity;
    this.lastRefillMs = Date.now();

    const now = Date.now();
    const elapsed = (now - this.lastRefillMs) / 1000;
    const added = elapsed <em> this.refillPerSecond;
    this.tokens = Math.min(this.capacity, this.tokens + added);
    this.lastRefillMs = now;
  }</p><p class="text-slate-300 leading-relaxed mb-4">  tryConsume(count: number = 1): boolean {
    this.refill();
    if (this.tokens >= count) {
      this.tokens -= count;
      return true;
    }
    return false;
  }

Good for general API throttling (e.g. 60/min with occasional spikes).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Sliding window</h2></p><p class="text-slate-300 leading-relaxed mb-4">A <strong>sliding window</strong> counts requests in a time window that moves with each request. For example: “max 100 requests per minute” means “count requests in the last 60 seconds”. Unlike a fixed window (e.g. “100 per calendar minute”), the boundary isn’t fixed — so you avoid the “reset at :00” burst where a client can send 100 at 00:59 and another 100 at 01:00.</p><p class="text-slate-300 leading-relaxed mb-4">A common implementation is <strong>sliding window log</strong>: store a timestamp for each request; count how many fall in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">[now - window, now]</code>. Accurate but uses more memory (one entry per request). You trim old timestamps each time.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// scripts/rate-limit-sliding-window.ts — in-memory, single process

  private hits: Map<string, number[]> = new Map();</p><p class="text-slate-300 leading-relaxed mb-4">  constructor(
    private maxRequests: number,

  ) {}</p><p class="text-slate-300 leading-relaxed mb-4">  tryAcquire(key: string): boolean {
    const now = Date.now() / 1000;
    const windowStart = now - this.windowSeconds;</p><p class="text-slate-300 leading-relaxed mb-4">    if (!this.hits.has(key)) this.hits.set(key, []);

Better for billing or strict fairness.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Algorithm comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach        | Pros                          | Cons                                    | When to use                                      |
|----------------|-------------------------------|-----------------------------------------|--------------------------------------------------|
| <strong>Token bucket</strong> | Allows bursts; simple; smooth after burst | Slightly more state (tokens + last refill) | General API throttling, webhooks, user actions   |
| <strong>Fixed window</strong> | Easiest to implement (counter per window) | Burst at boundary (2× limit in 2 seconds) | Internal or low-stakes limits only               |
| <strong>Sliding window</strong> | No boundary burst; strict “N in last T” | More state (timestamps or counter math)  | Billing, strict fairness, abuse prevention       |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Redis vs in-memory</h2></p><p class="text-slate-300 leading-relaxed mb-4">Rate limit state (tokens, timestamps, or counters) has to live somewhere. Two common choices:</p><p class="text-slate-300 leading-relaxed mb-4">| | In-memory | Redis |
|--|-----------|--------|
| <strong>Scope</strong> | Single process (one bucket per process) | Shared across all processes and servers |
| <strong>Restart</strong> | State lost; limits “reset” on deploy | State survives restarts |
| <strong>Latency</strong> | Sub-millisecond | Network round-trip (often 1–2 ms) |
| <strong>Setup</strong> | None | Redis instance (or managed service) |
| <strong>Best for</strong> | Single-node apps, sidecars, dev | Multi-node APIs, strict global limits |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Rule of thumb:</strong> If you run one node and don’t need limits to survive restarts, in-memory is enough. If you run several replicas behind a load balancer and you want “100 req/min per key” across the whole API, you need a shared store — typically Redis.</p><p class="text-slate-300 leading-relaxed mb-4">The token bucket and sliding window examples above are in-memory. Each process has its own buckets. With 3 replicas, a client could get 3× the limit by spreading requests across replicas. For a single-node or per-instance limit, that’s fine.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Redis: sliding window with a sorted set</h3></p><p class="text-slate-300 leading-relaxed mb-4">For Redis, a common pattern is a <strong>sorted set</strong>: score = timestamp, value = unique request id. Remove entries with score below (now - window), count, then if under the limit add the current request and set TTL on the key. For production you should run the “count, then add if under limit” in a single Lua script so two concurrent requests can’t both pass. Libraries like <a href="https://github.com/upstash/ratelimit" class="text-cyan-400 hover:underline">@upstash/ratelimit</a> or <a href="https://github.com/animir/node-rate-limiter-flexible" class="text-cyan-400 hover:underline">rate-limiter-flexible</a> do that for you and support both token bucket and sliding window with Redis and in-memory backends.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Redis sliding window (concept — use a Lua script or a library for atomicity)

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4">We made four mistakes that are worth avoiding.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Fixed window first.</strong> We used “max 100 per minute” with a fixed minute boundary. At 00:59 a client sent 100 requests, at 01:00 another 100. That’s 200 in two seconds. We switched to sliding window for that limit.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>In-memory with 4 replicas.</strong> Our “per-key” limit was per process. One API key could hit 4× the limit by spreading requests across replicas. We moved that tier to Redis so the limit is global.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>No expiry on Redis keys.</strong> Rate-limit keys accumulated. We added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PEXPIRE</code> (or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EXPIRE</code>) after each update — e.g. 2× the window — so keys disappear when idle.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Synchronous Redis in the hot path.</strong> We ran a blocking Redis call and saw latency spikes (p99 went from ~50 ms to 400 ms under load). We moved to async and a single Lua script so one round-trip does the whole check.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do today</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Pick one exposed endpoint</strong> — Add a token bucket (in-memory is fine to start) keyed by API key or IP: e.g. 60 tokens, refill 1/sec. Return 429 with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Retry-After</code> header when the bucket is empty. Measure whether runaway clients or latency improve.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Audit existing limits</strong> — If you use a fixed window (“100 per minute”), try switching that limit to sliding window and watch for the boundary burst disappearing.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Identify by more than IP</strong> — In many corporate environments, thousands of users share one exit IP. If you rate-limit by IP only, one person can block the whole office. Use API keys or JWT (JSON Web Token) claims when you can.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>If you have multiple replicas</strong> — Decide whether the limit is per-instance (in-memory OK) or global (use Redis or another shared store). If global, add key expiry so Redis doesn’t grow unbounded.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Use a library if you need Redis</strong> — <a href="https://github.com/upstash/ratelimit" class="text-cyan-400 hover:underline">@upstash/ratelimit</a> and <a href="https://github.com/animir/node-rate-limiter-flexible" class="text-cyan-400 hover:underline">rate-limiter-flexible</a> support token bucket and sliding window with Redis and in-memory backends and handle atomicity for you.</li></p><p class="text-slate-300 leading-relaxed mb-4">The scripts in this repo run with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/rate-limit-token-bucket.ts</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run scripts/rate-limit-sliding-window.ts</code> with no extra dependencies. Use them as a starting point for middleware or a small service; when you need shared state across nodes, plug in Redis (or a library that wraps it).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
