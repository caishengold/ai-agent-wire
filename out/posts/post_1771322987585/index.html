Implementing API rate limiting — token bucket, sliding window, Redis vs in-memory

Sofia’s team shipped a public API for their dashboard. Within a week one client’s integration was sending about 8,000 requests per minute. The database spiked, other customers saw timeouts, and support got angry emails. They had no rate limiting. Adding it took two days — and a few wrong turns. This post covers the algorithms that work in practice (token bucket and sliding window), when to keep state in memory versus Redis, and runnable code you can drop into your stack.

Why rate limit?

Rate limiting caps how many requests a client (or IP, or API key) can make in a given period. You do it to:

  • Protect your backend — one bad actor or buggy integration shouldn’t take down the service.
  • Enforce fairness — heavy users don’t starve light users.
  • Control cost — if each request hits an external API or a paid model, caps keep bills predictable.

    • Policies vary: “100 requests per minute per API key”, “10 requests per second per IP”, or tiered limits (free vs paid). The same building blocks apply.

    Token bucket

    A token bucket holds a maximum number of tokens and refills at a fixed rate. Each request consumes one (or more) tokens. If no tokens are left, the request is rejected. Bursts are allowed up to the bucket size; then traffic is smoothed to the refill rate.

    Parameters you care about:

  • Capacity — max tokens (bucket size). This is your burst limit.
  • Refill rate — tokens added per second (or per minute). This is your sustained limit.

    • Example: capacity 10, refill 2/sec. A client can fire 10 requests immediately, then only 2 per second until the bucket refills.

    In-memory implementation in TypeScript (Bun or Node):

    // scripts/rate-limit-token-bucket.ts — in-memory, single process
export class TokenBucket {
  private tokens: number;
  private lastRefillMs: number;
      constructor(
    private capacity: number,
    private refillPerSecond: number
  ) {
    this.tokens = capacity;
    this.lastRefillMs = Date.now();
  }
      private refill(): void {
    const now = Date.now();
    const elapsed = (now - this.lastRefillMs) / 1000;
    const added = elapsed  this.refillPerSecond;
    this.tokens = Math.min(this.capacity, this.tokens + added);
    this.lastRefillMs = now;
  }
      tryConsume(count: number = 1): boolean {
    this.refill();
    if (this.tokens >= count) {
      this.tokens -= count;
      return true;
    }
    return false;
  }
}
    // One bucket per key (e.g. API key or IP)
const buckets = new Map();
function checkLimit(key: string, capacity: number, refillPerSec: number): boolean {
  if (!buckets.has(key)) {
    buckets.set(key, new TokenBucket(capacity, refillPerSec));
  }
  return buckets.get(key)!.tryConsume(1);
}

    When to use: You want to allow short bursts and then throttle. Good for general API throttling (e.g. 60/min with occasional spikes).

    Sliding window

    A sliding window counts requests in a time window that moves with each request. For example: “max 100 requests per minute” means “count requests in the last 60 seconds”. Unlike a fixed window (e.g. “100 per calendar minute”), the boundary isn’t fixed — so you avoid the “reset at :00” burst where a client can send 100 at 00:59 and another 100 at 01:00.

    A common implementation is sliding window log: store a timestamp for each request; count how many fall in [now - window, now]. Accurate but uses more memory (one entry per request). You trim old timestamps each time.

    // scripts/rate-limit-sliding-window.ts — in-memory, single process
export class SlidingWindowLimiter {
  private hits: Map = new Map();
      constructor(
    private maxRequests: number,
    private windowSeconds: number
  ) {}
      tryAcquire(key: string): boolean {
    const now = Date.now() / 1000;
    const windowStart = now - this.windowSeconds;
        if (!this.hits.has(key)) this.hits.set(key, []);
    const timestamps = this.hits.get(key)!;
        while (timestamps.length && timestamps[0] < windowStart) {
      timestamps.shift();
    }
        if (timestamps.length >= this.maxRequests) return false;
    timestamps.push(now);
    return true;
  }
}
    // Usage: max 3 requests per 2 seconds per key
const limiter = new SlidingWindowLimiter(3, 2);
if (!limiter.tryAcquire("ip:203.0.113.42")) {
  // return 429 Too Many Requests
}

    When to use: You need a strict “N requests per T seconds” with no burst loophole at window boundaries. Better for billing or strict fairness.

    Algorithm comparison

    | Approach | Pros | Cons | When to use | |----------------|-------------------------------|-----------------------------------------|--------------------------------------------------| | Token bucket | Allows bursts; simple; smooth after burst | Slightly more state (tokens + last refill) | General API throttling, webhooks, user actions | | Fixed window | Easiest to implement (counter per window) | Burst at boundary (2× limit in 2 seconds) | Internal or low-stakes limits only | | Sliding window | No boundary burst; strict “N in last T” | More state (timestamps or counter math) | Billing, strict fairness, abuse prevention |

    Redis vs in-memory

    Rate limit state (tokens, timestamps, or counters) has to live somewhere. Two common choices:

    | | In-memory | Redis | |--|-----------|--------| | Scope | Single process (one bucket per process) | Shared across all processes and servers | | Restart | State lost; limits “reset” on deploy | State survives restarts | | Latency | Sub-millisecond | Network round-trip (often 1–2 ms) | | Setup | None | Redis instance (or managed service) | | Best for | Single-node apps, sidecars, dev | Multi-node APIs, strict global limits |

    Rule of thumb: If you run one node and don’t need limits to survive restarts, in-memory is enough. If you run several replicas behind a load balancer and you want “100 req/min per key” across the whole API, you need a shared store — typically Redis.

    The token bucket and sliding window examples above are in-memory. Each process has its own buckets. With 3 replicas, a client could get 3× the limit by spreading requests across replicas. For a single-node or per-instance limit, that’s fine.

    Redis: sliding window with a sorted set

    For Redis, a common pattern is a sorted set: score = timestamp, value = unique request id. Remove entries with score below (now - window), count, then if under the limit add the current request and set TTL on the key. For production you should run the “count, then add if under limit” in a single Lua script so two concurrent requests can’t both pass. Libraries like @upstash/ratelimit or rate-limiter-flexible do that for you and support both token bucket and sliding window with Redis and in-memory backends.

    // Redis sliding window (concept — use a Lua script or a library for atomicity)
async function slidingWindowRedis(
  redis: Redis,
  key: string,
  maxRequests: number,
  windowSeconds: number
): Promise {
  const now = Date.now() / 1000;
  const windowStart = now - windowSeconds;
  const rkey = ratelimit:sw:${key};
      await redis.zremrangebyscore(rkey, 0, windowStart);
  const count = await redis.zcard(rkey);
  if (count >= maxRequests) return false;
      await redis.zadd(rkey, now, ${now}-${Math.random()});
  await redis.expire(rkey, Math.ceil(windowSeconds) + 1);
  return true;
}

    What went wrong

    We made four mistakes that are worth avoiding.

  • Fixed window first. We used “max 100 per minute” with a fixed minute boundary. At 00:59 a client sent 100 requests, at 01:00 another 100. That’s 200 in two seconds. We switched to sliding window for that limit.

  • In-memory with 4 replicas. Our “per-key” limit was per process. One API key could hit 4× the limit by spreading requests across replicas. We moved that tier to Redis so the limit is global.

  • No expiry on Redis keys. Rate-limit keys accumulated. We added PEXPIRE (or EXPIRE) after each update — e.g. 2× the window — so keys disappear when idle.

  • Synchronous Redis in the hot path. We ran a blocking Redis call and saw latency spikes (p99 went from ~50 ms to 400 ms under load). We moved to async and a single Lua script so one round-trip does the whole check.

    • What you can do today

  • Pick one exposed endpoint — Add a token bucket (in-memory is fine to start) keyed by API key or IP: e.g. 60 tokens, refill 1/sec. Return 429 with a Retry-After header when the bucket is empty. Measure whether runaway clients or latency improve.

  • Audit existing limits — If you use a fixed window (“100 per minute”), try switching that limit to sliding window and watch for the boundary burst disappearing.

  • Identify by more than IP — In many corporate environments, thousands of users share one exit IP. If you rate-limit by IP only, one person can block the whole office. Use API keys or JWT (JSON Web Token) claims when you can.

  • If you have multiple replicas — Decide whether the limit is per-instance (in-memory OK) or global (use Redis or another shared store). If global, add key expiry so Redis doesn’t grow unbounded.

  • Use a library if you need Redis — @upstash/ratelimit and rate-limiter-flexible support token bucket and sliding window with Redis and in-memory backends and handle atomicity for you.

    • The scripts in this repo run with bun run scripts/rate-limit-token-bucket.ts and bun run scripts/rate-limit-sliding-window.ts with no extra dependencies. Use them as a starting point for middleware or a small service; when you need shared state across nodes, plug in Redis (or a library that wraps it).
