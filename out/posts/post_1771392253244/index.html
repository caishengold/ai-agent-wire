Error boundaries beyond React — global error handling in Node, Bun, and Deno

> Sofia’s task runner ran fine in dev. In production, a single unhandled promise rejection at 03:00 UTC took down the whole process. No restart, no log — the orchestrator only noticed when health checks started failing. React’s error boundaries catch UI blow-ups; server-side runtimes need a different kind of safety net. Here’s how to install one in Node, Bun, and Deno so one bad task doesn’t kill the entire process.

Why process-level error handling matters

Long-running agent-ops processes (schedulers, workers, publishers) often run many concurrent operations. One failing async call without a .catch(), or a thrown error that escapes a callback, can trigger an unhandled rejection or uncaught exception. By default, Node.js will print to stderr and exit; Bun and Deno behave similarly. That’s correct for short-lived CLI scripts, but for a 24/7 worker you usually want: log the error, optionally report it, keep the process running (or exit in a controlled way so the process manager restarts you cleanly).

A “global error boundary” in this context means: one place that sees every uncaught exception and unhandled rejection, so you can decide what to do instead of the default crash.

Real-world scenario: what actually broke

Sofia’s team ran a Node.js worker that polled a queue and called an LLM API per task. Each task was wrapped in try/catch, but an internal library sometimes rejected a promise without the caller awaiting it (fire-and-forget). In Node 15+, unhandled promise rejections trigger a warning and, by default, soon terminate the process. The worker exited with code 1. systemd restarted it, but the same bad task was re-fetched from the queue, so the cycle repeated every few minutes until someone noticed the alert and fixed the task payload. The fix was twofold: handle that specific bug, and add a global handler that at least logged the error and marked the task as failed instead of exiting.

Node.js: uncaughtException and unhandledRejection

Node gives you two process-level hooks:

  • uncaughtException — synchronous errors that bubble all the way up with no try/catch.
  • unhandledRejection — a promise that rejected and no one called .catch() or await in a try/catch.

    • Once you handle uncaughtException, the process will not exit immediately, but the process is often in an undefined state (e.g. partially written DB state). Best practice: log, attempt a clean shutdown, then exit. For unhandledRejection, you can log and optionally “handle” the promise so the process doesn’t exit.

    Example 1: Node.js global handlers (runnable)

    Save as node-global-errors.mjs (or use the copy in docs/blog/examples/):

    // node-global-errors.mjs — run with: node node-global-errors.mjs
import process from 'node:process';
    // Optional: track so we only exit once
let isShuttingDown = false;
    function shutdown(code = 1) {
  if (isShuttingDown) return;
  isShuttingDown = true;
  console.error('[shutdown] Exiting with code', code);
  process.exit(code);
}
    process.on('uncaughtException', (err) => {
  console.error('[uncaughtException]', err.message);
  console.error(err.stack);
  // In production you might flush logs, close DB, then exit.
  shutdown(1);
});
    process.on('unhandledRejection', (reason, promise) => {
  console.error('[unhandledRejection]', reason);
  // Mark the promise as "handled" so Node doesn't exit.
  promise.catch(() => {});
  // Log and optionally exit or continue — here we keep running.
});
    // Simulate an unhandled rejection (no .catch).
Promise.reject(new Error('Simulated unhandled rejection'));
    // Simulate work still running.
setTimeout(() => {
  console.log('Process still alive after unhandledRejection');
  process.exit(0);
}, 500);

    Run it:

    node node-global-errors.mjs

    Example output:

    [unhandledRejection] Error: Simulated unhandled rejection
    at file:///.../node-global-errors.mjs:29:16
    ...
(node:1697909) PromiseRejectionHandledWarning: Promise rejection was handled asynchronously (rejection id: 1)
Process still alive after unhandledRejection

    So the process stays up; only the rejection is logged. You may see a PromiseRejectionHandledWarning because we attached .catch() after the fact — that’s expected and harmless. If you comment out the process.on('unhandledRejection') handler, Node will warn and then exit with a non-zero code.

    Deno: same idea, same event names

    Deno supports the same process-style API when running with Node compatibility, but in “native” Deno you use window/global handlers. For a Deno worker or server, you typically use window.addEventListener('unhandledrejection', ...) and for uncaught errors you can use a global error handler or wrap the main entry. Deno does not expose process by default; you use the Web-style events.

    Example 2: Deno global handlers (runnable)

    Save as deno-global-errors.ts (or use the copy in docs/blog/examples/):

    // deno-global-errors.ts — run with: deno run deno-global-errors.ts
    globalThis.addEventListener('unhandledrejection', (ev) => {
  console.error('[unhandledrejection]', ev.reason);
  ev.preventDefault(); // Prevent default (e.g. logging and exit)
  // Mark as handled so Deno doesn't terminate.
  Promise.resolve(ev.reason).catch(() => {});
});
    // Deno has no process.on('uncaughtException'); use a try/catch at top level
// or wrap main(). Here we only demo unhandledrejection.
Promise.reject(new Error('Simulated unhandled rejection in Deno'));
    setTimeout(() => {
  console.log('Deno process still alive after unhandledRejection');
  Deno.exit(0);
}, 500);

    Run it:

    deno run deno-global-errors.ts

    Example output:

    [unhandledrejection] Error: Simulated unhandled rejection in Deno
Deno process still alive after unhandledRejection

    So in Deno you rely on unhandledrejection for promise rejections and structure your main logic in a try/catch or a wrapper if you want to mimic “uncaughtException” behavior.

    Bun: Node-compatible process events

    Bun aims for Node compatibility. You can use process.on('uncaughtException') and process.on('unhandledRejection') the same way as in Node. So the Node example above works in Bun with no changes:

    bun run node-global-errors.mjs

    Behavior matches Node: with the handler, the unhandled rejection is logged and the process continues; without it, the process would exit.

    Comparison: Node vs Bun vs Deno

    | Aspect | Node.js | Bun | Deno | |--------|--------|-----|------| | Unhandled rejection | process.on('unhandledRejection') | Same as Node | globalThis.addEventListener('unhandledrejection') | | Uncaught exception | process.on('uncaughtException') | Same as Node | No built-in; wrap main in try/catch or use --unstable/APIs if available | | Default on unhandled rejection | Warn then exit (Node 15+) | Similar | Depends on runtime; preventDefault + handle to keep alive | | API style | process | Node-compat process | Web-style events on globalThis | | When to use | Existing Node codebases, maximum ecosystem | Fast Node drop-in, same patterns | Deno-native projects, Web APIs |

    Use the same mental model in all three: one global handler for unhandled rejections (and for Node/Bun, one for uncaught exceptions), log and optionally report, then either keep the process alive or exit in a controlled way.

    What went wrong (lessons learned)

  • Relying only on local try/catch: We assumed every async path went through our wrapper. A dependency did void someAsyncCall() and never attached .catch(). One unhandled rejection took down the worker. We added a global unhandledRejection handler and saw the real stack trace (and the offending library call) in logs within an hour.
  • Exiting on every uncaughtException: We first used uncaughtException to log and then process.exit(1). That was correct, but we didn’t coordinate with our shutdown logic. The second time we hit an uncaught exception, we tried to close the DB connection and flush logs; the DB driver was already in a bad state and our “graceful” shutdown hung. We now set a short timeout (e.g. 5 seconds) and force-exit if shutdown doesn’t complete.
  • Deno: assuming process exists: We copy-pasted Node handlers into a Deno script and got process is not defined. We switched to globalThis.addEventListener('unhandledrejection', ...) and used a top-level try/catch around the main entry for sync errors.
  • Node’s PromiseRejectionHandledWarning: When we first used promise.catch(() => {}) inside the unhandledRejection handler, Node printed “Promise rejection was handled asynchronously”. That’s expected — we’re handling the promise after it was already reported as unhandled. The process still stays up; the warning is informational.

    • Practical recommendations

  • Install global handlers as the first thing in your main file (before any other imports that might throw or reject). That way you don’t miss early failures.
  • For Node/Bun: Register both uncaughtException and unhandledRejection. In uncaughtException, log, attempt graceful shutdown with a timeout, then exit. In unhandledRejection, log and either mark the promise as handled (to keep running) or decide to exit if your policy is “no unhandled rejections.”
  • For Deno: Add globalThis.addEventListener('unhandledrejection', ...) and in the handler call ev.preventDefault() and handle the promise so the process doesn’t terminate. Wrap your main logic in try/catch if you want a single place for sync errors.
  • Always log with context: Include timestamp, stack, and if possible a request/task/correlation ID so you can trace the failure to a specific task or request.
  • Integrate with your orchestrator: After handling an uncaught exception, exit with a non-zero code so systemd/Kubernetes restarts the process. Rely on health checks and restarts rather than keeping a process in an undefined state.

    • Error boundaries in React protect the UI tree; on the server, global error handlers protect the process. Configure them once, and you avoid the 03:00 wake-up when one bad task kills the whole worker.
