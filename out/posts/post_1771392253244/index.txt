8:T4dae,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Error boundaries beyond React — global error handling in Node, Bun, and Deno</h1></p><p class="text-slate-300 leading-relaxed mb-4">> Sofia’s task runner ran fine in dev. In production, a single unhandled promise rejection at 03:00 UTC took down the whole process. No restart, no log — the orchestrator only noticed when health checks started failing. React’s error boundaries catch UI blow-ups; server-side runtimes need a different kind of safety net. Here’s how to install one in Node, Bun, and Deno so one bad task doesn’t kill the entire process.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why process-level error handling matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Long-running agent-ops processes (schedulers, workers, publishers) often run many concurrent operations. One failing <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">async</code> call without a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code>, or a thrown error that escapes a callback, can trigger an <strong>unhandled rejection</strong> or <strong>uncaught exception</strong>. By default, Node.js will print to stderr and exit; Bun and Deno behave similarly. That’s correct for short-lived CLI scripts, but for a 24/7 worker you usually want: log the error, optionally report it, keep the process running (or exit in a controlled way so the process manager restarts you cleanly).</p><p class="text-slate-300 leading-relaxed mb-4">A “global error boundary” in this context means: <strong>one place that sees every uncaught exception and unhandled rejection</strong>, so you can decide what to do instead of the default crash.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Real-world scenario: what actually broke</h2></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team ran a Node.js worker that polled a queue and called an LLM API per task. Each task was wrapped in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code>, but an internal library sometimes rejected a promise without the caller awaiting it (fire-and-forget). In Node 15+, unhandled promise rejections trigger a warning and, by default, soon terminate the process. The worker exited with code 1. systemd restarted it, but the same bad task was re-fetched from the queue, so the cycle repeated every few minutes until someone noticed the alert and fixed the task payload. The fix was twofold: handle that specific bug, and add a <strong>global handler</strong> that at least logged the error and marked the task as failed instead of exiting.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Node.js: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code></h2></p><p class="text-slate-300 leading-relaxed mb-4">Node gives you two process-level hooks:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code></strong> — synchronous errors that bubble all the way up with no <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code>.</li>
<li class="ml-4 list-disc text-slate-300"><strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code></strong> — a promise that rejected and no one called <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> in a try/catch.</li></p><p class="text-slate-300 leading-relaxed mb-4">Once you handle <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code>, the process will not exit immediately, but the process is often in an undefined state (e.g. partially written DB state). Best practice: log, attempt a clean shutdown, then exit. For <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code>, you can log and optionally “handle” the promise so the process doesn’t exit.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example 1: Node.js global handlers (runnable)</h3></p><p class="text-slate-300 leading-relaxed mb-4">Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node-global-errors.mjs</code> (or use the copy in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docs/blog/examples/</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// node-global-errors.mjs — run with: node node-global-errors.mjs
import process from 'node:process';</p><p class="text-slate-300 leading-relaxed mb-4">// Optional: track so we only exit once
let isShuttingDown = false;</p><p class="text-slate-300 leading-relaxed mb-4">function shutdown(code = 1) {
  if (isShuttingDown) return;
  isShuttingDown = true;
  console.error('[shutdown] Exiting with code', code);
  process.exit(code);
}</p><p class="text-slate-300 leading-relaxed mb-4">process.on('uncaughtException', (err) => {
  console.error('[uncaughtException]', err.message);
  console.error(err.stack);
  // In production you might flush logs, close DB, then exit.
  shutdown(1);
});</p><p class="text-slate-300 leading-relaxed mb-4">process.on('unhandledRejection', (reason, promise) => {
  console.error('[unhandledRejection]', reason);
  // Mark the promise as "handled" so Node doesn't exit.
  promise.catch(() => {});
  // Log and optionally exit or continue — here we keep running.
});</p><p class="text-slate-300 leading-relaxed mb-4">// Simulate an unhandled rejection (no .catch).
Promise.reject(new Error('Simulated unhandled rejection'));</p><p class="text-slate-300 leading-relaxed mb-4">// Simulate work still running.
setTimeout(() => {
  console.log('Process still alive after unhandledRejection');
  process.exit(0);
}, 500);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run it:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>node node-global-errors.mjs
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[unhandledRejection] Error: Simulated unhandled rejection
    at file:///.../node-global-errors.mjs:29:16
    ...
(node:1697909) PromiseRejectionHandledWarning: Promise rejection was handled asynchronously (rejection id: 1)
Process still alive after unhandledRejection
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So the process stays up; only the rejection is logged. You may see a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PromiseRejectionHandledWarning</code> because we attached <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> after the fact — that’s expected and harmless. If you comment out the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on('unhandledRejection')</code> handler, Node will warn and then exit with a non-zero code.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Deno: same idea, same event names</h2></p><p class="text-slate-300 leading-relaxed mb-4">Deno supports the same <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process</code>-style API when running with Node compatibility, but in “native” Deno you use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">window</code>/global handlers. For a Deno worker or server, you typically use <strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">window.addEventListener('unhandledrejection', ...)</code></strong> and for uncaught errors you can use a global error handler or wrap the main entry. Deno does not expose <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process</code> by default; you use the Web-style events.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example 2: Deno global handlers (runnable)</h3></p><p class="text-slate-300 leading-relaxed mb-4">Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">deno-global-errors.ts</code> (or use the copy in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docs/blog/examples/</code>):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// deno-global-errors.ts — run with: deno run deno-global-errors.ts</p><p class="text-slate-300 leading-relaxed mb-4">globalThis.addEventListener('unhandledrejection', (ev) => {
  console.error('[unhandledrejection]', ev.reason);
  ev.preventDefault(); // Prevent default (e.g. logging and exit)
  // Mark as handled so Deno doesn't terminate.
  Promise.resolve(ev.reason).catch(() => {});
});</p><p class="text-slate-300 leading-relaxed mb-4">// Deno has no process.on('uncaughtException'); use a try/catch at top level
// or wrap main(). Here we only demo unhandledrejection.
Promise.reject(new Error('Simulated unhandled rejection in Deno'));</p><p class="text-slate-300 leading-relaxed mb-4">setTimeout(() => {
  console.log('Deno process still alive after unhandledRejection');
  Deno.exit(0);
}, 500);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Run it:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>deno run deno-global-errors.ts
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[unhandledrejection] Error: Simulated unhandled rejection in Deno
Deno process still alive after unhandledRejection
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">So in Deno you rely on <strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledrejection</code></strong> for promise rejections and structure your main logic in a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> or a wrapper if you want to mimic “uncaughtException” behavior.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Bun: Node-compatible process events</h2></p><p class="text-slate-300 leading-relaxed mb-4">Bun aims for Node compatibility. You can use <strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on('uncaughtException')</code></strong> and <strong><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on('unhandledRejection')</code></strong> the same way as in Node. So the Node example above works in Bun with no changes:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>bun run node-global-errors.mjs
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Behavior matches Node: with the handler, the unhandled rejection is logged and the process continues; without it, the process would exit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: Node vs Bun vs Deno</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | Node.js | Bun | Deno |
|--------|--------|-----|------|
| <strong>Unhandled rejection</strong> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on('unhandledRejection')</code> | Same as Node | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">globalThis.addEventListener('unhandledrejection')</code> |
| <strong>Uncaught exception</strong> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.on('uncaughtException')</code> | Same as Node | No built-in; wrap main in try/catch or use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--unstable</code>/APIs if available |
| <strong>Default on unhandled rejection</strong> | Warn then exit (Node 15+) | Similar | Depends on runtime; preventDefault + handle to keep alive |
| <strong>API style</strong> | <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process</code> | Node-compat <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process</code> | Web-style events on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">globalThis</code> |
| <strong>When to use</strong> | Existing Node codebases, maximum ecosystem | Fast Node drop-in, same patterns | Deno-native projects, Web APIs |</p><p class="text-slate-300 leading-relaxed mb-4">Use the same mental model in all three: <strong>one global handler for unhandled rejections</strong> (and for Node/Bun, one for uncaught exceptions), log and optionally report, then either keep the process alive or exit in a controlled way.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Relying only on local try/catch</strong>: We assumed every async path went through our wrapper. A dependency did <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">void someAsyncCall()</code> and never attached <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code>. One unhandled rejection took down the worker. We added a global <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code> handler and saw the real stack trace (and the offending library call) in logs within an hour.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Exiting on every uncaughtException</strong>: We first used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code> to log and then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process.exit(1)</code>. That was correct, but we didn’t coordinate with our shutdown logic. The second time we hit an uncaught exception, we tried to close the DB connection and flush logs; the DB driver was already in a bad state and our “graceful” shutdown hung. We now set a short timeout (e.g. 5 seconds) and force-exit if shutdown doesn’t complete.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Deno: assuming <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process</code> exists</strong>: We copy-pasted Node handlers into a Deno script and got <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">process is not defined</code>. We switched to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">globalThis.addEventListener('unhandledrejection', ...)</code> and used a top-level try/catch around the main entry for sync errors.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Node’s PromiseRejectionHandledWarning</strong>: When we first used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">promise.catch(() => {})</code> inside the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code> handler, Node printed “Promise rejection was handled asynchronously”. That’s expected — we’re handling the promise after it was already reported as unhandled. The process still stays up; the warning is informational.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Practical recommendations</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Install global handlers as the first thing in your main file</strong> (before any other imports that might throw or reject). That way you don’t miss early failures.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>For Node/Bun</strong>: Register both <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code>. In <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">uncaughtException</code>, log, attempt graceful shutdown with a timeout, then exit. In <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unhandledRejection</code>, log and either mark the promise as handled (to keep running) or decide to exit if your policy is “no unhandled rejections.”</li>
<li class="ml-4 list-decimal text-slate-300"><strong>For Deno</strong>: Add <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">globalThis.addEventListener('unhandledrejection', ...)</code> and in the handler call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ev.preventDefault()</code> and handle the promise so the process doesn’t terminate. Wrap your main logic in try/catch if you want a single place for sync errors.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Always log with context</strong>: Include timestamp, stack, and if possible a request/task/correlation ID so you can trace the failure to a specific task or request.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Integrate with your orchestrator</strong>: After handling an uncaught exception, exit with a non-zero code so systemd/Kubernetes restarts the process. Rely on health checks and restarts rather than keeping a process in an undefined state.</li></p><p class="text-slate-300 leading-relaxed mb-4">Error boundaries in React protect the UI tree; on the server, global error handlers protect the process. Configure them once, and you avoid the 03:00 wake-up when one bad task kills the whole worker.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
