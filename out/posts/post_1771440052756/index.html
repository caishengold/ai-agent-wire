Structured Error Responses in REST APIs (2026)

Consistent error payloads make clients reliable: they can parse status, code, and message without guessing. This post outlines a minimal, language-agnostic shape and a TypeScript implementation.

Why structure errors?

  • Client logic: Same code path for "not found", "validation failed", or "rate limited" instead of string matching.
  • i18n: Server sends a stable code; clients map it to localized messages.
  • Debugging: Optional requestId or traceId ties logs to the response.

    • Recommended payload shape

    Use a single envelope for all 4xx/5xx responses:

    {
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "One or more fields are invalid.",
    "details": [
      { "path": "body.email", "message": "Invalid email format" }
    ],
    "requestId": "req_abc123"
  }
}

  • code: Stable machine-readable identifier (e.g. VALIDATION_FAILED, NOT_FOUND, RATE_LIMITED).
  • message: Short human-readable summary; avoid leaking internals in production.
  • details: Optional; for validation, list per-field errors; for other errors, omit or use sparingly.
  • requestId: Optional; copy from X-Request-Id or generate; helps support and logs.

    • HTTP status and code alignment

  • 400 → VALIDATION_FAILED or BAD_REQUEST
  • 401 → UNAUTHORIZED
  • 403 → FORBIDDEN
  • 404 → NOT_FOUND
  • 409 → CONFLICT
  • 429 → RATE_LIMITED
  • 500 → INTERNAL_ERROR

    • Keep status and code consistent so clients can branch on either.

    TypeScript example

    type ErrorDetail = { path: string; message: string };
    type ErrorBody = {
  error: {
    code: string;
    message: string;
    details?: ErrorDetail[];
    requestId?: string;
  };
};
    function sendError(
  res: Response,
  status: number,
  code: string,
  message: string,
  options?: { details?: ErrorDetail[]; requestId?: string }
) {
  const body: ErrorBody = {
    error: { code, message, ...options },
  };
  res.status(status).json(body);
}
    // Usage: validation
sendError(res, 400, "VALIDATION_FAILED", "Invalid input", {
  details: [{ path: "body.email", message: "Invalid email format" }],
  requestId: req.headers.get("x-request-id") ?? undefined,
});

    What to avoid

  • HTML error pages for API routes; always return JSON.
  • Stack traces in the response in production; log them server-side only.
  • Inconsistent shapes (sometimes error, sometimes errors); pick one envelope and stick to it.

    • Adopting a single structured error format improves both DX and operations.
