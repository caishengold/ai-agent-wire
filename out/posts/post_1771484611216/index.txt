8:T31b8,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Comparative analysis of error handling patterns in TypeScript: promise chaining vs async/await (2026)</h1></p><p class="text-slate-300 leading-relaxed mb-4">Omar’s API layer mixed <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then()</code> chains with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">async/await</code>. When a downstream call failed, the stack trace pointed at the wrong line and the team spent an hour tracing which promise actually threw. The same logic rewritten with a consistent style and explicit error boundaries cut that to a few minutes. How you structure async code in TypeScript directly affects how easy it is to find and fix failures.</p><p class="text-slate-300 leading-relaxed mb-4">This post compares <strong>promise chaining</strong> and <strong>async/await</strong> from an error-handling perspective: where errors surface, how to catch them, and when each style pays off in real APIs.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why it matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">In both styles you work with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Promise<T></code>. The difference is syntax and control flow. Chaining uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then()</code> / <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> / <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.finally()</code>; async/await uses <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> inside <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code>. That choice changes where errors land, how you type them, and how readable stack traces are. Picking one approach per layer (e.g. "API handlers use async/await, internal helpers can chain") reduces surprises.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Error handling with promise chaining</h2></p><p class="text-slate-300 leading-relaxed mb-4">With chaining, each <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then()</code> can throw or return a rejected promise. A single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> at the end handles rejections from any step — but you lose the ability to narrow the error by stage unless you rethrow or tag inside the chain.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Chaining: one catch for the whole pipeline
function fetchUserOrdersChain(userId: string): Promise<{ user: string; orders: number[] }> {
  return fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">https://api.example.com/users/${userId}</code>)
    .then((res) => {
      if (!res.ok) throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HTTP ${res.status}</code>);
      return res.json();
    })
    .then((user: { id: string; name: string }) =>
      fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">https://api.example.com/orders?userId=${user.id}</code>)
    )
    .then((res) => {
      if (!res.ok) throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HTTP ${res.status}</code>);
      return res.json();
    })
    .then((orders: { id: number }[]) => ({ user: "unknown", orders: orders.map((o) => o.id) }))
    .catch((e) => {
      // All failures end up here; hard to tell user fetch vs orders fetch
      console.error("Pipeline failed:", e);
      throw e;
    });
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> No <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code>; one place to log or transform. <strong>Cons:</strong> Stack traces often point at the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch</code> or the last <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then</code>; branching on error type or step requires rethrowing with context or using a tagged error inside the chain.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Error handling with async/await</h2></p><p class="text-slate-300 leading-relaxed mb-4">With async/await, you <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> each promise. Any rejection becomes an exception at that <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code>, so you can wrap specific calls in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> and handle (or rethrow) with full context.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// async/await: catch at the call site you care about
async function fetchUserOrdersAsync(userId: string): Promise<{ user: string; orders: number[] }> {
  const userRes = await fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">https://api.example.com/users/${userId}</code>);
  if (!userRes.ok) throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HTTP ${userRes.status}</code>);
  const user: { id: string; name: string } = await userRes.json();</p><p class="text-slate-300 leading-relaxed mb-4">  let ordersRes: Response;
  try {
    ordersRes = await fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">https://api.example.com/orders?userId=${user.id}</code>);
  } catch (e) {
    // Network error for orders only — we know the stage
    throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Orders fetch failed: ${e instanceof Error ? e.message : String(e)}</code>);
  }
  if (!ordersRes.ok) throw new Error(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">HTTP ${ordersRes.status}</code>);
  const orders: { id: number }[] = await ordersRes.json();
  return { user: user.name, orders: orders.map((o) => o.id) };
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Clear stack traces, local <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> per step, easier to type narrow <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">e</code>. <strong>Cons:</strong> More verbose if you want one global handler; you must remember to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> (or handle) so rejections don’t become unhandled.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Side-by-side comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Aspect | Promise chaining | Async/await |
|--------|------------------|-------------|
| <strong>Where errors are caught</strong> | In the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> attached to the chain | At each <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> or in a surrounding <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> |
| <strong>Stack traces</strong> | Often collapse to the chain or runtime | Reflect the actual <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> line |
| <strong>Per-step handling</strong> | Possible but awkward (rethrow or tag in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.then</code>) | Natural: wrap one or more <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code>s in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> |
| <strong>Typing caught errors</strong> | Same as async/await: use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unknown</code> and narrow | Same: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch (e: unknown)</code> then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">instanceof</code> or type guards |
| <strong>Readability in long flows</strong> | Nested or long chains get hard to follow | Linear; reads like sync code |</p><p class="text-slate-300 leading-relaxed mb-4">For API handlers and service code where you want to map failures to status codes or log with context, <strong>async/await usually wins</strong>: you get clearer errors and simpler control flow. Chaining still makes sense for one-off pipelines or when composing with libraries that return promises and you only need a single final <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Unhandled rejections:</strong> In both styles, a rejected promise that never hits a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> or a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> becomes an unhandled rejection. With async/await, forgetting to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">await</code> (e.g. firing off a promise and not awaiting it) is a common cause.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Mixing styles:</strong> Using both in the same function works but can confuse where errors come from. Prefer one style per function or layer.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Returning from catch:</strong> In a chain, returning a value from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> resolves the promise instead of rethrowing; in async/await, returning from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">catch</code> also resolves. If you want the caller to see the failure, rethrow or throw again in both styles.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Centralised handlers:</strong> With async/await, a top-level <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> in the request handler (or middleware) can normalise all errors; with chaining, a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">.catch()</code> at the end of the chain achieves a similar effect. Consistency across the codebase matters more than the choice itself.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>async/await</strong> for request handlers and any flow where you need to pinpoint and handle errors by step; use <strong>promise chaining</strong> when you have a short, linear pipeline and one final error handler is enough. Stick to one style per file or layer so stack traces and mental model stay clear. If you haven’t already, add a small typed error hierarchy and a central handler (see <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">typescript-error-handling-best-practices-2026-02-12-23-50.md</code>) — that pairs well with either pattern.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
