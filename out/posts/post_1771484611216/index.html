Comparative analysis of error handling patterns in TypeScript: promise chaining vs async/await (2026)

Omar’s API layer mixed .then() chains with async/await. When a downstream call failed, the stack trace pointed at the wrong line and the team spent an hour tracing which promise actually threw. The same logic rewritten with a consistent style and explicit error boundaries cut that to a few minutes. How you structure async code in TypeScript directly affects how easy it is to find and fix failures.

This post compares promise chaining and async/await from an error-handling perspective: where errors surface, how to catch them, and when each style pays off in real APIs.

Why it matters

In both styles you work with Promise. The difference is syntax and control flow. Chaining uses .then() / .catch() / .finally(); async/await uses await inside try/catch. That choice changes where errors land, how you type them, and how readable stack traces are. Picking one approach per layer (e.g. "API handlers use async/await, internal helpers can chain") reduces surprises.

Error handling with promise chaining

With chaining, each .then() can throw or return a rejected promise. A single .catch() at the end handles rejections from any step — but you lose the ability to narrow the error by stage unless you rethrow or tag inside the chain.

// Chaining: one catch for the whole pipeline
function fetchUserOrdersChain(userId: string): Promise<{ user: string; orders: number[] }> {
  return fetch(https://api.example.com/users/${userId})
    .then((res) => {
      if (!res.ok) throw new Error(HTTP ${res.status});
      return res.json();
    })
    .then((user: { id: string; name: string }) =>
      fetch(https://api.example.com/orders?userId=${user.id})
    )
    .then((res) => {
      if (!res.ok) throw new Error(HTTP ${res.status});
      return res.json();
    })
    .then((orders: { id: number }[]) => ({ user: "unknown", orders: orders.map((o) => o.id) }))
    .catch((e) => {
      // All failures end up here; hard to tell user fetch vs orders fetch
      console.error("Pipeline failed:", e);
      throw e;
    });
}

Pros: No try/catch; one place to log or transform. Cons: Stack traces often point at the .catch or the last .then; branching on error type or step requires rethrowing with context or using a tagged error inside the chain.

Error handling with async/await

With async/await, you await each promise. Any rejection becomes an exception at that await, so you can wrap specific calls in try/catch and handle (or rethrow) with full context.

// async/await: catch at the call site you care about
async function fetchUserOrdersAsync(userId: string): Promise<{ user: string; orders: number[] }> {
  const userRes = await fetch(https://api.example.com/users/${userId});
  if (!userRes.ok) throw new Error(HTTP ${userRes.status});
  const user: { id: string; name: string } = await userRes.json();
  let ordersRes: Response;
  try {
    ordersRes = await fetch(https://api.example.com/orders?userId=${user.id});
  } catch (e) {
    // Network error for orders only — we know the stage
    throw new Error(Orders fetch failed: ${e instanceof Error ? e.message : String(e)});
  }
  if (!ordersRes.ok) throw new Error(HTTP ${ordersRes.status});
  const orders: { id: number }[] = await ordersRes.json();
  return { user: user.name, orders: orders.map((o) => o.id) };
}

Pros: Clear stack traces, local try/catch per step, easier to type narrow e. Cons: More verbose if you want one global handler; you must remember to await (or handle) so rejections don’t become unhandled.

Side-by-side comparison

| Aspect | Promise chaining | Async/await | |--------|------------------|-------------| | Where errors are caught | In the .catch() attached to the chain | At each await or in a surrounding try/catch | | Stack traces | Often collapse to the chain or runtime | Reflect the actual await line | | Per-step handling | Possible but awkward (rethrow or tag in .then) | Natural: wrap one or more awaits in try/catch | | Typing caught errors | Same as async/await: use unknown and narrow | Same: catch (e: unknown) then instanceof or type guards | | Readability in long flows | Nested or long chains get hard to follow | Linear; reads like sync code |

For API handlers and service code where you want to map failures to status codes or log with context, async/await usually wins: you get clearer errors and simpler control flow. Chaining still makes sense for one-off pipelines or when composing with libraries that return promises and you only need a single final .catch().

Gotchas and lessons learned

  • Unhandled rejections: In both styles, a rejected promise that never hits a .catch() or a try/catch becomes an unhandled rejection. With async/await, forgetting to await (e.g. firing off a promise and not awaiting it) is a common cause.
  • Mixing styles: Using both in the same function works but can confuse where errors come from. Prefer one style per function or layer.
  • Returning from catch: In a chain, returning a value from .catch() resolves the promise instead of rethrowing; in async/await, returning from catch also resolves. If you want the caller to see the failure, rethrow or throw again in both styles.
  • Centralised handlers: With async/await, a top-level try/catch in the request handler (or middleware) can normalise all errors; with chaining, a single .catch() at the end of the chain achieves a similar effect. Consistency across the codebase matters more than the choice itself.

    • Takeaway

    Use async/await for request handlers and any flow where you need to pinpoint and handle errors by step; use promise chaining when you have a short, linear pipeline and one final error handler is enough. Stick to one style per file or layer so stack traces and mental model stay clear.
