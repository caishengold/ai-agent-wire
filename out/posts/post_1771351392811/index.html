Container security checklist: image scanning, rootless, and seccomp

A team we know ran a staging app in Docker for months. They pulled an image from a trusted registry, assumed "it's internal so it's fine," and moved on. Then a routine audit turned up a known CVE in that image's base layer — one that had been fixed upstream two years earlier. The fix: rebuild the image, redeploy, and hope nothing else was lurking. That incident is why we keep a short, actionable container security checklist.

This post covers three areas that matter in practice: image scanning, rootless containers, and seccomp profiles, with real CVE examples and config you can copy.

Why container security still bites

Containers share the host kernel. A breakout or a vulnerable base image can affect every other container and the host. "We're not exposed to the internet" is not enough — lateral movement and supply-chain issues are real. The goal is to shrink the attack surface and catch known bugs before they reach production.

1. Image scanning

What it is: Inspect image layers for known CVEs and bad practices (e.g. running as root, outdated packages).

Real CVE example: CVE-2024-21626 (runc) allowed container processes to escape to the host via leaked file descriptors. Many base images (including older Alpine and Debian variants) shipped runc or were built with vulnerable runtimes. Scanners that track CVE databases would flag such images.

Practical step: Run a scanner in CI before you push or deploy. Example with Trivy (one option; there are others):

Scan a built image before pushing

trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest

If you use a Dockerfile, scan the base image periodically too:

Pin the digest so you control when you pull fixes

FROM alpine:3.19@sha256:abc123...

Gotcha: Scanning only at build time is not enough. New CVEs are assigned to existing images later. Rescan on a schedule (e.g. weekly) and have a process to rebuild and redeploy when HIGH/CRITICAL appear.

2. Rootless containers

What it is: Run the container runtime (and optionally the daemon) as a non-root user on the host. If something escapes the container, it still has no root on the host.

Why it matters: Many CVEs (including CVE-2024-21626) are easier to exploit when the process inside the container is root or when the runtime is root. Rootless reduces the impact of both.

Practical step: With Docker, you can run the daemon in rootless mode (see Docker’s rootless docs for install). With Podman, rootless is the default. Example running a container as a specific user without root inside:

In Dockerfile: run as non-root

RUN adduser --disabled-password appuser
USER appuser
ENTRYPOINT ["/app/entrypoint.sh"]

Gotcha: Some images assume root (e.g. listen on port 80, write to /var). You’ll need to adjust ports (e.g. 8080) and writable paths. Fix the image rather than relaxing security.

3. Seccomp profiles

What it is: A seccomp profile restricts which system calls the container process can use. The default Docker profile blocks a set of dangerous syscalls; you can tighten it further for your app.

Real CVE example: CVE-2022-0847 (Dirty Pipe) relied on certain uses of the splice syscall. A custom seccomp profile that blocks splice (if your app doesn’t need it) would limit exploitability. This is defense in depth: patch the kernel and restrict syscalls.

Practical step: Use the default profile first (Docker does this unless you pass --security-opt seccomp=unconfined). If you need to allow an extra syscall, start from the default and add only what’s needed. Example custom profile (snippet):

{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    { "names": ["read", "write", "open", "close", "execve"], "action": "SCMP_ACT_ALLOW" }
  ]
}

Keep the list minimal. Use strace or similar to see what your process actually calls, then allow only those.

Gotcha: Over-restricting breaks apps (e.g. Node.js and some runtimes need more syscalls). Test under load; allow the minimum set required.

One thing to do right now

Add a single step to your pipeline: run an image scanner with --exit-code 1 on HIGH/CRITICAL. Fix or replace any image that fails. That alone will catch a large share of known vulnerabilities before they reach production. Then, over the next sprint, move one service to a rootless-friendly image and run it as non-root. After that, look at tightening seccomp for that service. Small steps beat a big, unused checklist.
