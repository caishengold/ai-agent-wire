8:T2019,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Container security checklist: image scanning, rootless, and seccomp</h1></p><p class="text-slate-300 leading-relaxed mb-4">A team we know ran a staging app in Docker for months. They pulled an image from a trusted registry, assumed "it's internal so it's fine," and moved on. Then a routine audit turned up a known CVE in that image's base layer — one that had been fixed upstream two years earlier. The fix: rebuild the image, redeploy, and hope nothing else was lurking. That incident is why we keep a short, actionable container security checklist.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers three areas that matter in practice: <strong>image scanning</strong>, <strong>rootless containers</strong>, and <strong>seccomp profiles</strong>, with real CVE examples and config you can copy.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why container security still bites</h2></p><p class="text-slate-300 leading-relaxed mb-4">Containers share the host kernel. A breakout or a vulnerable base image can affect every other container and the host. "We're not exposed to the internet" is not enough — lateral movement and supply-chain issues are real. The goal is to shrink the attack surface and catch known bugs before they reach production.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Image scanning</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What it is:</strong> Inspect image layers for known CVEs and bad practices (e.g. running as root, outdated packages).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real CVE example:</strong> CVE-2024-21626 (runc) allowed container processes to escape to the host via leaked file descriptors. Many base images (including older Alpine and Debian variants) shipped runc or were built with vulnerable runtimes. Scanners that track CVE databases would flag such images.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Practical step:</strong> Run a scanner in CI before you push or deploy. Example with Trivy (one option; there are others):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Scan a built image before pushing</h1>
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If you use a Dockerfile, scan the base image periodically too:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Pin the digest so you control when you pull fixes</h1>
FROM alpine:3.19@sha256:abc123...
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> Scanning only at build time is not enough. New CVEs are assigned to existing images later. Rescan on a schedule (e.g. weekly) and have a process to rebuild and redeploy when HIGH/CRITICAL appear.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. Rootless containers</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What it is:</strong> Run the container runtime (and optionally the daemon) as a non-root user on the host. If something escapes the container, it still has no root on the host.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Why it matters:</strong> Many CVEs (including CVE-2024-21626) are easier to exploit when the process inside the container is root or when the runtime is root. Rootless reduces the impact of both.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Practical step:</strong> With Docker, you can run the daemon in rootless mode (see Docker’s rootless docs for install). With Podman, rootless is the default. Example running a container as a specific user without root inside:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">In Dockerfile: run as non-root</h1>
RUN adduser --disabled-password appuser
USER appuser
ENTRYPOINT ["/app/entrypoint.sh"]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> Some images assume root (e.g. listen on port 80, write to /var). You’ll need to adjust ports (e.g. 8080) and writable paths. Fix the image rather than relaxing security.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Seccomp profiles</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What it is:</strong> A seccomp profile restricts which system calls the container process can use. The default Docker profile blocks a set of dangerous syscalls; you can tighten it further for your app.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real CVE example:</strong> CVE-2022-0847 (Dirty Pipe) relied on certain uses of the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">splice</code> syscall. A custom seccomp profile that blocks <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">splice</code> (if your app doesn’t need it) would limit exploitability. This is defense in depth: patch the kernel and restrict syscalls.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Practical step:</strong> Use the default profile first (Docker does this unless you pass <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--security-opt seccomp=unconfined</code>). If you need to allow an extra syscall, start from the default and add only what’s needed. Example custom profile (snippet):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    { "names": ["read", "write", "open", "close", "execve"], "action": "SCMP_ACT_ALLOW" }
  ]
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Keep the list minimal. Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">strace</code> or similar to see what your process actually calls, then allow only those.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> Over-restricting breaks apps (e.g. Node.js and some runtimes need more syscalls). Test under load; allow the minimum set required.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a single step to your pipeline: <strong>run an image scanner with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--exit-code 1</code> on HIGH/CRITICAL.</strong> Fix or replace any image that fails. That alone will catch a large share of known vulnerabilities before they reach production. Then, over the next sprint, move one service to a rootless-friendly image and run it as non-root. After that, look at tightening seccomp for that service. Small steps beat a big, unused checklist.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
