8:T4db8,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">SSE vs WebSocket vs Long Polling — when to use each (Bun)</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s ops dashboard showed task counts that updated only when you refreshed. His team needed something closer to live: new tasks and status changes without a full reload. They first tried long polling, then weighed Server-Sent Events (SSE) and WebSockets. Each option behaved differently under load and behind their reverse proxy. This post compares the three approaches with runnable Bun examples, scalability notes, and what actually went wrong in practice.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Context:</strong> All three patterns push or pull data over HTTP (or an HTTP upgrade). Long polling keeps a request open until the server has something to send. SSE keeps a single HTTP connection open and streams events one way (server → client). WebSocket upgrades the connection to a full duplex channel so both sides can send at any time. Choice depends on who sends data, how often, and what your infrastructure allows.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Quick comparison</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach       | Direction      | Protocol        | Typical use                          | Pros                                      | Cons                                           |
|----------------|----------------|-----------------|--------------------------------------|-------------------------------------------|------------------------------------------------|
| <strong>Long polling</strong> | Client asks, server answers | HTTP GET (repeated) | Notifications, simple “any updates?” | Works everywhere, no special proxy config  | More requests, higher latency, easy to mis-tune |
| <strong>SSE</strong>        | Server → client only | HTTP, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">text/event-stream</code> | Feeds, logs, dashboards, LLM streaming | Simple API, auto reconnect, one connection | One-way only; some proxies buffer or timeout   |
| <strong>WebSocket</strong>  | Both ways      | HTTP upgrade → WS | Chat, games, collaborative editing   | Low latency, bidirectional, binary        | More complex; proxy/load-balancer support varies |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>When to use which:</strong> Use <strong>long polling</strong> when you need maximum compatibility (old browsers, strict proxies) and can accept a few seconds of delay. Use <strong>SSE</strong> when the server pushes and the client only consumes (streaming logs, live counters, OpenAI-style token streams). Use <strong>WebSocket</strong> when the client must send and receive frequently (chat, real-time forms, binary protocols).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Example 1: SSE server in Bun</h2></p><p class="text-slate-300 leading-relaxed mb-4">SSE is plain HTTP with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Content-Type: text/event-stream</code>. You keep the response open and write lines in the form <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">data: <payload>\n\n</code>. Bun can stream by returning a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Response</code> whose body is a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ReadableStream</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// sse-server.ts — run with: bun run sse-server.ts

  lastEventId++;
  const payload = { id: lastEventId, at: new Date().toISOString() };
  while (pending.length > 0) {
    const { resolve } = pending.shift()!;
    resolve(payload);
  }

On Linux, default per-process open files (and thus sockets) are often in the thousands. Plan for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ulimit</code> and for memory (each connection has a buffer). Long polling uses one request at a time per client, so peak concurrent connections is lower but you get more request/response cycles.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Proxies and timeouts:</strong> Many reverse proxies (e.g. Nginx, Cloudflare) have read/write timeouts (e.g. 60s). SSE and WebSocket need long-lived connections; configure <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">proxy_read_timeout</code> and similar so they are not closed early. Long polling must use a timeout shorter than the proxy’s.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Reconnection:</strong> SSE’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EventSource</code> reconnects automatically and can send <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Last-Event-ID</code>. WebSocket and long polling need your own backoff and reconnection logic.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Bun specifics:</strong> Bun’s WebSocket implementation is efficient (see <a href="https://bun.sh/docs/runtime/http/websockets" class="text-cyan-400 hover:underline">Bun’s WebSocket docs</a>); SSE is just a streaming HTTP response, so scaling is similar to any streaming HTTP server.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>SSE not updating in browser:</strong> We once forgot <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Cache-Control: no-cache</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Connection: keep-alive</code>. Some browsers or proxies cached the response and never showed new events. Fix: always set those headers for SSE.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Long polling timeouts:</strong> We set the server hold to 30s but the reverse proxy timed out at 10s. Clients got 502s. We reduced the long-poll wait to 8s and added a clear <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Timeout</code> header so clients could retry sooner.</li>
<li class="ml-4 list-disc text-slate-300"><strong>WebSocket 101 not reaching the server:</strong> A load balancer was not configured to pass through <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Upgrade</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Connection</code> headers. The upgrade failed with 400/503. We had to enable WebSocket support on the load balancer and, in one case, use a dedicated subdomain that bypassed the same proxy rules.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Memory growth under SSE:</strong> We kept a list of all open SSE response controllers to broadcast. Forgetting to remove closed connections caused a slow leak. We switched to a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Set</code> and removed the controller in the stream’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cancel</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">close</code> path.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Pick by data flow:</strong> Server-only push → SSE. Bidirectional or binary → WebSocket. Need maximum compatibility and can accept delay → long polling.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Run the examples:</strong> Save the three snippets as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sse-server.ts</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws-server.ts</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">long-poll-server.ts</code> in a Bun project. Run each and call them with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">curl</code> or the small client scripts to see behaviour and headers.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Check proxy and timeouts:</strong> For SSE/WebSocket, ensure your reverse proxy allows long-lived connections and increase timeouts if needed. For long polling, keep the server wait below the proxy timeout.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Reuse your existing SSE:</strong> If you already have an OpenAI-compatible streaming endpoint (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">text/event-stream</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">data: {...}\n\n</code>), you can consume it with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EventSource</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">fetch</code> + stream; same pattern as above.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Measure before scaling:</strong> Use Bun’s <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.pendingRequests</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">server.pendingWebSockets</code> (and your own counters for long-poll waiters) to see how many concurrent clients you have before adding more processes or horizontal scaling.</li></p><p class="text-slate-300 leading-relaxed mb-4">Runnable example scripts for this post live in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docs/blog/examples/</code>: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sse-server.ts</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ws-server.ts</code>, and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">long-poll-server.ts</code>. Run them with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun run docs/blog/examples/<script>.ts</code> from the repo root (ensure ports 3000, 3001, 3002 are free).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
