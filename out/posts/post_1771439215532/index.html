SSE vs WebSocket vs Long Polling — when to use each (Bun)

Raj’s ops dashboard showed task counts that updated only when you refreshed. His team needed something closer to live: new tasks and status changes without a full reload. They first tried long polling, then weighed Server-Sent Events (SSE) and WebSockets. Each option behaved differently under load and behind their reverse proxy. This post compares the three approaches with runnable Bun examples, scalability notes, and what actually went wrong in practice.

Context: All three patterns push or pull data over HTTP (or an HTTP upgrade). Long polling keeps a request open until the server has something to send. SSE keeps a single HTTP connection open and streams events one way (server → client). WebSocket upgrades the connection to a full duplex channel so both sides can send at any time. Choice depends on who sends data, how often, and what your infrastructure allows.

Quick comparison

| Approach | Direction | Protocol | Typical use | Pros | Cons | |----------------|----------------|-----------------|--------------------------------------|-------------------------------------------|------------------------------------------------| | Long polling | Client asks, server answers | HTTP GET (repeated) | Notifications, simple “any updates?” | Works everywhere, no special proxy config | More requests, higher latency, easy to mis-tune | | SSE | Server → client only | HTTP, text/event-stream | Feeds, logs, dashboards, LLM streaming | Simple API, auto reconnect, one connection | One-way only; some proxies buffer or timeout | | WebSocket | Both ways | HTTP upgrade → WS | Chat, games, collaborative editing | Low latency, bidirectional, binary | More complex; proxy/load-balancer support varies |

When to use which: Use long polling when you need maximum compatibility (old browsers, strict proxies) and can accept a few seconds of delay. Use SSE when the server pushes and the client only consumes (streaming logs, live counters, OpenAI-style token streams). Use WebSocket when the client must send and receive frequently (chat, real-time forms, binary protocols).

Example 1: SSE server in Bun

SSE is plain HTTP with Content-Type: text/event-stream. You keep the response open and write lines in the form data: \n\n. Bun can stream by returning a Response whose body is a ReadableStream.

// sse-server.ts — run with: bun run sse-server.ts
const server = Bun.serve({
  port: 3000,
  fetch(req) {
    const url = new URL(req.url);
    if (url.pathname !== "/events") return new Response("Not found", { status: 404 });
    const stream = new ReadableStream({
      start(controller) {
        const id = setInterval(() => {
          const payload = JSON.stringify({ time: new Date().toISOString(), tick: Date.now() });
          controller.enqueue(new TextEncoder().encode(data: ${payload}\n\n));
        }, 1000);
        // Stop after 10 events so the example exits cleanly
        setTimeout(() => {
          clearInterval(id);
          controller.close();
        }, 10_000);
      },
    });
    return new Response(stream, {
      headers: {
        "Content-Type": "text/event-stream",
        "Cache-Control": "no-cache",
        Connection: "keep-alive",
      },
    });
  },
});
console.log(SSE server at ${server.url}/events);

Terminal (server):

$ bun run sse-server.ts
SSE server at http://localhost:3000/events

Client (browser or curl):

curl -N http://localhost:3000/events

Example output:

data: {"time":"2026-02-12T03:45:00.123Z","tick":1739328300123}
data: {"time":"2026-02-12T03:45:01.124Z","tick":1739328301124}
...

In the browser you’d use EventSource:

const es = new EventSource("http://localhost:3000/events");
es.onmessage = (e) => console.log(JSON.parse(e.data));

Example 2: WebSocket server in Bun

Bun’s Bun.serve() accepts a websocket handler. You upgrade the request in fetch; after that, the same TCP connection is used for two-way messages.

// ws-server.ts — run with: bun run ws-server.ts
const server = Bun.serve({
  port: 3001,
  fetch(req, server) {
    const url = new URL(req.url);
    if (url.pathname === "/ws" && server.upgrade(req)) return undefined;
    return new Response("Not found", { status: 404 });
  },
  websocket: {
    open(ws) {
      ws.send(JSON.stringify({ type: "welcome", text: "Connected" }));
    },
    message(ws, msg) {
      const text = typeof msg === "string" ? msg : new TextDecoder().decode(msg);
      ws.send(JSON.stringify({ type: "echo", received: text }));
    },
    close(ws) {
      console.log("Client disconnected");
    },
  },
});
console.log(WebSocket server at ws://localhost:3001/ws);

Terminal (server):

$ bun run ws-server.ts
WebSocket server at ws://localhost:3001/ws

Client (Bun script):

// ws-client.ts — run while ws-server.ts is running: bun run ws-client.ts
const ws = new WebSocket("ws://localhost:3001/ws");
ws.addEventListener("open", () => ws.send("Hello from client"));
ws.addEventListener("message", (e) => console.log("Received:", e.data));
ws.addEventListener("close", () => process.exit(0));

Terminal (client):

$ bun run ws-client.ts
Received: {"type":"welcome","text":"Connected"}
Received: {"type":"echo","received":"Hello from client"}

Example 3: Long polling in Bun

The client repeatedly calls GET; the server holds the request until there is new data (or a timeout), then returns. No streaming — one response per poll.

// long-poll-server.ts — run with: bun run long-poll-server.ts
let lastEventId = 0;
const pending: { resolve: (v: unknown) => void }[] = [];
function notifyAll() {
  lastEventId++;
  const payload = { id: lastEventId, at: new Date().toISOString() };
  while (pending.length > 0) {
    const { resolve } = pending.shift()!;
    resolve(payload);
  }
}
// Simulate server-driven updates every 2.5 seconds
setInterval(notifyAll, 2500);
const server = Bun.serve({
  port: 3002,
  fetch(req) {
    const url = new URL(req.url);
    if (url.pathname === "/poll") {
      return new Promise((resolve) => {
        const timeout = setTimeout(() => {
          const idx = pending.findIndex((p) => p.resolve === res);
          if (idx >= 0) pending.splice(idx, 1);
          resolve(Response.json({ id: 0, at: null, timeout: true }));
        }, 5000);
        const res = (payload: unknown) => {
          clearTimeout(timeout);
          resolve(Response.json(payload));
        };
        pending.push({ resolve: res });
      });
    }
    if (url.pathname === "/notify") {
      notifyAll();
      return Response.json({ ok: true });
    }
    return new Response("Not found", { status: 404 });
  },
});
console.log(Long poll: GET ${server.url}poll (wait up to 5s), POST ${server.url}notify to push);

Terminal (server):

$ bun run long-poll-server.ts
Long poll: GET http://localhost:3002/poll (wait up to 5s), POST http://localhost:3002/notify to push

Client (curl):

Blocks until an event or 5s timeout

curl -s http://localhost:3002/poll

Example: {"id":1,"at":"2026-02-12T03:45:00.000Z"}

Scalability

  • Connections per process: Each SSE or WebSocket connection is a long-lived socket. On Linux, default per-process open files (and thus sockets) are often in the thousands. Plan for ulimit and for memory (each connection has a buffer). Long polling uses one request at a time per client, so peak concurrent connections is lower but you get more request/response cycles.
  • Proxies and timeouts: Many reverse proxies (e.g. Nginx, Cloudflare) have read/write timeouts (e.g. 60s). SSE and WebSocket need long-lived connections; configure proxy_read_timeout and similar so they are not closed early. Long polling must use a timeout shorter than the proxy’s.
  • Reconnection: SSE’s EventSource reconnects automatically and can send Last-Event-ID. WebSocket and long polling need your own backoff and reconnection logic.
  • Bun specifics: Bun’s WebSocket implementation is efficient (see Bun’s WebSocket docs); SSE is just a streaming HTTP response, so scaling is similar to any streaming HTTP server.

    • What went wrong

  • SSE not updating in browser: We once forgot Cache-Control: no-cache and Connection: keep-alive. Some browsers or proxies cached the response and never showed new events. Fix: always set those headers for SSE.
  • Long polling timeouts: We set the server hold to 30s but the reverse proxy timed out at 10s. Clients got 502s. We reduced the long-poll wait to 8s and added a clear Timeout header so clients could retry sooner.
  • WebSocket 101 not reaching the server: A load balancer was not configured to pass through Upgrade and Connection headers. The upgrade failed with 400/503. We had to enable WebSocket support on the load balancer and, in one case, use a dedicated subdomain that bypassed the same proxy rules.
  • Memory growth under SSE: We kept a list of all open SSE response controllers to broadcast. Forgetting to remove closed connections caused a slow leak. We switched to a Set and removed the controller in the stream’s cancel/close path.

    • Takeaways

  • Pick by data flow: Server-only push → SSE. Bidirectional or binary → WebSocket. Need maximum compatibility and can accept delay → long polling.
  • Run the examples: Save the three snippets as sse-server.ts, ws-server.ts, and long-poll-server.ts in a Bun project. Run each and call them with curl or the small client scripts to see behaviour and headers.
  • Check proxy and timeouts: For SSE/WebSocket, ensure your reverse proxy allows long-lived connections and increase timeouts if needed. For long polling, keep the server wait below the proxy timeout.
  • Reuse your existing SSE: If you already have an OpenAI-compatible streaming endpoint (e.g. text/event-stream with data: {...}\n\n), you can consume it with EventSource or fetch + stream; same pattern as above.
  • Measure before scaling: Use Bun’s server.pendingRequests and server.pendingWebSockets (and your own counters for long-poll waiters) to see how many concurrent clients you have before adding more processes or horizontal scaling.
