8:T254e,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Advanced error handling patterns in TypeScript: a comparison with JavaScript</h1></p><p class="text-slate-300 leading-relaxed mb-4">Your API returns <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ error: string }</code> sometimes and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ data: T }</code> other times. In plain JavaScript you might check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">if (res.error)</code> and hope nobody sends a 200 with both fields. In TypeScript you can encode that split in the type system so mistakes show up at compile time. Here’s how we think about advanced error handling in TypeScript and how it differs from typical JavaScript approaches.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why error handling gets harder at scale</h2></p><p class="text-slate-300 leading-relaxed mb-4">In small scripts, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">try/catch</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">throw new Error("something broke")</code> are enough. Once you add async flows, third-party APIs, and shared libraries, you need:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">A clear way to represent “this call can fail in known ways”</li>
<li class="ml-4 list-disc text-slate-300">Type-safe handling so callers can’t ignore errors</li>
<li class="ml-4 list-disc text-slate-300">A consistent shape for errors (message, code, cause) so logging and UI stay sane</li></p><p class="text-slate-300 leading-relaxed mb-4">JavaScript gives you flexibility but little structure. TypeScript doesn’t change the runtime, but it lets you model success and failure so that the compiler enforces handling.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Result types: encoding failure in the type</h2></p><p class="text-slate-300 leading-relaxed mb-4">Instead of throwing and hoping someone catches, you can model “either success or error” as a type. That way every caller has to branch.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// Result<T, E = Error> — either Ok(T) or Err(E)
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };</p><p class="text-slate-300 leading-relaxed mb-4">function parseConfig(json: string): Result<Config, ParseError> {
  try {
    const data = JSON.parse(json);
    if (!data.version) return { ok: false, error: { code: 'MISSING_VERSION', message: 'version required' } };
    return { ok: true, value: data as Config };
  } catch (e) {
    return { ok: false, error: { code: 'INVALID_JSON', message: String(e) } };
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">// Call site: compiler nudges you to handle both cases
const result = parseConfig(process.env.CONFIG ?? '{}');
if (!result.ok) {
  console.error(result.error); // TypeScript knows shape here
  process.exit(1);
}
console.log(result.value); // TypeScript knows value exists here
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In JavaScript you’d often return <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">undefined</code> or throw and lose the “what went wrong” structure. With <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result<T, E></code>, the type system forces you to handle the error path and keeps the error object typed (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ParseError</code> with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">message</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Discriminated unions for API responses</h2></p><p class="text-slate-300 leading-relaxed mb-4">APIs often return either a payload or an error object. A discriminated union keeps the two cases separate and type-safe.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>type ApiResponse<T> =
  | { success: true; data: T }
  | { success: false; error: string; code?: number };</p><p class="text-slate-300 leading-relaxed mb-4">async function fetchUser(id: string): Promise<ApiResponse<User>> {
  const res = await fetch(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/api/users/${id}</code>);
  const body = await res.json();
  if (!res.ok) {
    return { success: false, error: body.message ?? 'Unknown error', code: res.status };
  }
  return { success: true, data: body };
}</p><p class="text-slate-300 leading-relaxed mb-4">const out = await fetchUser('123');
if (out.success) {
  console.log(out.data.name); // User
} else {
  console.log(out.error, out.code); // string, number | undefined
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">No more “maybe it’s data, maybe it’s error” guessing. TypeScript narrows the type after the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">success</code> check, so you get autocomplete and fewer runtime surprises compared to ad-hoc checks in JavaScript.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Custom error classes and cause chains</h2></p><p class="text-slate-300 leading-relaxed mb-4">For deeper stacks (e.g. “DB error caused by network error”), subclassing <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Error</code> and using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code> gives you structure that works with both TypeScript and existing JS tooling.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly cause?: unknown
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, AppError.prototype);
  }
}</p><p class="text-slate-300 leading-relaxed mb-4">async function loadUser(id: string): Promise<User> {
  try {
    return await db.users.get(id);
  } catch (e) {
    throw new AppError(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Failed to load user ${id}</code>, 'USER_LOAD', e);
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">The <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code> chain is standard in modern JS and shows up in stack traces. In TypeScript, the <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">code</code> field and optional <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">cause</code> are part of the type, so logging and error boundaries can rely on them without casting.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we’d do differently</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Don’t over-use Result everywhere.</strong> For one-off scripts or when you’re fine with try/catch, throwing is still valid. Reserve Result for boundaries (parsing, API calls, config loading) where you want explicit handling.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Standardize error shapes.</strong> We started with “sometimes message, sometimes code” and had to retrofit. Pick one shape (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">{ code, message, cause? }</code>) early so logging and UI stay consistent.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Use strict null checks.</strong> With <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">strictNullChecks</code>, “forgot to handle null” becomes a compile error. That pairs well with Result and discriminated unions.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to try today</h2></p><p class="text-slate-300 leading-relaxed mb-4">Introduce a small <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Result<T, E></code> (or a single <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ApiResponse<T></code>) for one function that today returns <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">T | null</code> or throws. Refactor call sites to use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">if (!result.ok) { ... }</code> and see how the types guide you. You don’t need a library; a few lines of types are enough to get most of the benefit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
