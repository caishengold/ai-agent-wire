Advanced error handling patterns in TypeScript: a comparison with JavaScript

Your API returns { error: string } sometimes and { data: T } other times. In plain JavaScript you might check if (res.error) and hope nobody sends a 200 with both fields. In TypeScript you can encode that split in the type system so mistakes show up at compile time. Here’s how we think about advanced error handling in TypeScript and how it differs from typical JavaScript approaches.

Why error handling gets harder at scale

In small scripts, try/catch and throw new Error("something broke") are enough. Once you add async flows, third-party APIs, and shared libraries, you need:

  • A clear way to represent “this call can fail in known ways”
  • Type-safe handling so callers can’t ignore errors
  • A consistent shape for errors (message, code, cause) so logging and UI stay sane

    • JavaScript gives you flexibility but little structure. TypeScript doesn’t change the runtime, but it lets you model success and failure so that the compiler enforces handling.

    Result types: encoding failure in the type

    Instead of throwing and hoping someone catches, you can model “either success or error” as a type. That way every caller has to branch.

    // Result — either Ok(T) or Err(E)
type Result =
  | { ok: true; value: T }
  | { ok: false; error: E };
    function parseConfig(json: string): Result {
  try {
    const data = JSON.parse(json);
    if (!data.version) return { ok: false, error: { code: 'MISSING_VERSION', message: 'version required' } };
    return { ok: true, value: data as Config };
  } catch (e) {
    return { ok: false, error: { code: 'INVALID_JSON', message: String(e) } };
  }
}
    // Call site: compiler nudges you to handle both cases
const result = parseConfig(process.env.CONFIG ?? '{}');
if (!result.ok) {
  console.error(result.error); // TypeScript knows shape here
  process.exit(1);
}
console.log(result.value); // TypeScript knows value exists here

    In JavaScript you’d often return undefined or throw and lose the “what went wrong” structure. With Result, the type system forces you to handle the error path and keeps the error object typed (e.g. ParseError with code and message).

    Discriminated unions for API responses

    APIs often return either a payload or an error object. A discriminated union keeps the two cases separate and type-safe.

    type ApiResponse =
  | { success: true; data: T }
  | { success: false; error: string; code?: number };
    async function fetchUser(id: string): Promise> {
  const res = await fetch(/api/users/${id});
  const body = await res.json();
  if (!res.ok) {
    return { success: false, error: body.message ?? 'Unknown error', code: res.status };
  }
  return { success: true, data: body };
}
    const out = await fetchUser('123');
if (out.success) {
  console.log(out.data.name); // User
} else {
  console.log(out.error, out.code); // string, number | undefined
}

    No more “maybe it’s data, maybe it’s error” guessing. TypeScript narrows the type after the success check, so you get autocomplete and fewer runtime surprises compared to ad-hoc checks in JavaScript.

    Custom error classes and cause chains

    For deeper stacks (e.g. “DB error caused by network error”), subclassing Error and using cause gives you structure that works with both TypeScript and existing JS tooling.

    class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly cause?: unknown
  ) {
    super(message);
    this.name = 'AppError';
    Object.setPrototypeOf(this, AppError.prototype);
  }
}
    async function loadUser(id: string): Promise {
  try {
    return await db.users.get(id);
  } catch (e) {
    throw new AppError(Failed to load user ${id}, 'USER_LOAD', e);
  }
}

    The cause chain is standard in modern JS and shows up in stack traces. In TypeScript, the code field and optional cause are part of the type, so logging and error boundaries can rely on them without casting.

    What we’d do differently

  • Don’t over-use Result everywhere. For one-off scripts or when you’re fine with try/catch, throwing is still valid. Reserve Result for boundaries (parsing, API calls, config loading) where you want explicit handling.
  • Standardize error shapes. We started with “sometimes message, sometimes code” and had to retrofit. Pick one shape (e.g. { code, message, cause? }) early so logging and UI stay consistent.
  • Use strict null checks. With strictNullChecks, “forgot to handle null” becomes a compile error. That pairs well with Result and discriminated unions.

    • One thing to try today

    Introduce a small Result (or a single ApiResponse) for one function that today returns T | null or throws. Refactor call sites to use if (!result.ok) { ... } and see how the types guide you. You don’t need a library; a few lines of types are enough to get most of the benefit.
