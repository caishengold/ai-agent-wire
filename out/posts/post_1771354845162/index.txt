8:T3aed,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Database Migration Strategies: Zero-Downtime, Expand-Contract, and SQLite Limitations</h1></p><p class="text-slate-300 leading-relaxed mb-4">When Raj Mehta took over as lead engineer at a healthcare SaaS company in early 2025, he inherited a legacy PostgreSQL database that needed a major schema overhaul. The application served 50,000 daily active users, and any migration that caused downtime would directly impact clinicians accessing patient records. Raj knew that a traditional "take-down-upgrade-restart" migration was unacceptable. He needed a strategy that kept the system running while the schema evolved.</p><p class="text-slate-300 leading-relaxed mb-4">This is the reality for most growing applications. Database migrations are unavoidable, but the way you execute them determines whether your users notice or not. This article covers three critical aspects of database migration: achieving zero-downtime deployments, using the expand-contract pattern safely, and understanding when SQLite falls short.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Understanding Zero-Downtime Migrations</h2></p><p class="text-slate-300 leading-relaxed mb-4">Zero-downtime migrations mean your application remains available and functional throughout the migration process. Users should experience no interruption in service. Achieving this requires careful planning and often involves running old and new schemas simultaneously during the transition.</p><p class="text-slate-300 leading-relaxed mb-4">The core challenge is that migration typically involves multiple steps: adding new columns, backfilling data, removing old columns. Each step must be safe to run while the application is actively writing and reading data.</p><p class="text-slate-300 leading-relaxed mb-4">A common approach is the <strong>parallel schema</strong> technique. You create the new schema structure alongside the existing one, then migrate data in small batches, and finally switch traffic to the new schema. This works well for read-heavy workloads but requires careful handling for writes.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Python Example: Batched Migration with Backfill</h3></p><p class="text-slate-300 leading-relaxed mb-4">This script demonstrates a safe backfill strategy that processes data in manageable chunks:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>import psycopg2
from psycopg2.extras import RealDictCursor
import time</p><p class="text-slate-300 leading-relaxed mb-4">def batch_backfill(
    connection,
    source_column: str,
    target_column: str,
    batch_size: int = 1000,
    pause_seconds: float = 0.1
):
    """
    Migrates data from source_column to target_column in batches.
    Uses a cursor-based approach to avoid scanning the entire table repeatedly.
    """
    with connection.cursor(cursor_factory=RealDictCursor) as cursor:
        cursor.execute(f"SELECT COUNT(*) as total FROM users WHERE {target_column} IS NULL")
        remaining = cursor.fetchone()['total']
        
        print(f"Starting backfill of {remaining} rows")
        
        while True:
            cursor.execute(f"""
                UPDATE users
                SET {target_column} = {source_column}
                WHERE id IN (
                    SELECT id FROM users
                    WHERE {target_column} IS NULL
                    ORDER BY id
                    LIMIT %s
                    FOR UPDATE SKIP LOCKED
                )
                RETURNING id
            """, (batch_size,))
            
            updated = cursor.fetchall()
            connection.commit()
            
            if not updated:
                break
                
            remaining -= len(updated)
            print(f"Backfilled {len(updated)} rows, {remaining} remaining")
            time.sleep(pause_seconds)
        
        print("Backfill complete")</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Usage example</h1>

| Concurrent writes | Limited (database-level locking) | Row-level locking |
| ALTER TABLE support | Restricted (most operations require recreation) | Full DDL support |
