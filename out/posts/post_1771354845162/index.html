Database Migration Strategies: Zero-Downtime, Expand-Contract, and SQLite Limitations

When Raj Mehta took over as lead engineer at a healthcare SaaS company in early 2025, he inherited a legacy PostgreSQL database that needed a major schema overhaul. The application served 50,000 daily active users, and any migration that caused downtime would directly impact clinicians accessing patient records. Raj knew that a traditional "take-down-upgrade-restart" migration was unacceptable. He needed a strategy that kept the system running while the schema evolved.

This is the reality for most growing applications. Database migrations are unavoidable, but the way you execute them determines whether your users notice or not. This article covers three critical aspects of database migration: achieving zero-downtime deployments, using the expand-contract pattern safely, and understanding when SQLite falls short.

Understanding Zero-Downtime Migrations

Zero-downtime migrations mean your application remains available and functional throughout the migration process. Users should experience no interruption in service. Achieving this requires careful planning and often involves running old and new schemas simultaneously during the transition.

The core challenge is that migration typically involves multiple steps: adding new columns, backfilling data, removing old columns. Each step must be safe to run while the application is actively writing and reading data.

A common approach is the parallel schema technique. You create the new schema structure alongside the existing one, then migrate data in small batches, and finally switch traffic to the new schema. This works well for read-heavy workloads but requires careful handling for writes.

Python Example: Batched Migration with Backfill

This script demonstrates a safe backfill strategy that processes data in manageable chunks:

import psycopg2
from psycopg2.extras import RealDictCursor
import time
def batch_backfill(
    connection,
    source_column: str,
    target_column: str,
    batch_size: int = 1000,
    pause_seconds: float = 0.1
):
    """
    Migrates data from source_column to target_column in batches.
    Uses a cursor-based approach to avoid scanning the entire table repeatedly.
    """
    with connection.cursor(cursor_factory=RealDictCursor) as cursor:
        cursor.execute(f"SELECT COUNT(*) as total FROM users WHERE {target_column} IS NULL")
        remaining = cursor.fetchone()['total']
        
        print(f"Starting backfill of {remaining} rows")
        
        while True:
            cursor.execute(f"""
                UPDATE users
                SET {target_column} = {source_column}
                WHERE id IN (
                    SELECT id FROM users
                    WHERE {target_column} IS NULL
                    ORDER BY id
                    LIMIT %s
                    FOR UPDATE SKIP LOCKED
                )
                RETURNING id
            """, (batch_size,))
            
            updated = cursor.fetchall()
            connection.commit()
            
            if not updated:
                break
                
            remaining -= len(updated)
            print(f"Backfilled {len(updated)} rows, {remaining} remaining")
            time.sleep(pause_seconds)
        
        print("Backfill complete")
Usage example

conn = psycopg2.connect(
    host="localhost",
    database="healthcare_app",
    user="migration_user",
    password="secure_password_here"
)
batch_backfill(conn, "email", "contact_email", batch_size=500)

This script uses FOR UPDATE SKIP LOCKED to avoid contention with live application traffic. The batch size and pause between batches let you tune the migration speed based on your system's tolerance for additional load.

The Expand-Contract Pattern

The expand-contract pattern, also known as the migration pipeline, breaks schema changes into three phases: expand (add new structure), migrate (populate data), and contract (remove old structure). Each phase can be executed independently, allowing the application to remain operational.

Phase 1: Expand

Add the new column, table, or constraint without affecting existing functionality. The application continues using the old schema while the new structure exists alongside it.

import psycopg2
def expand_phase(connection):
    """Phase 1: Add new column alongside existing one"""
    with connection.cursor() as cursor:
        cursor.execute("""
            ALTER TABLE patients
            ADD COLUMN IF NOT EXISTS full_name VARCHAR(255)
        """)
        
        cursor.execute("""
            CREATE INDEX IF NOT EXISTS idx_patients_full_name
            ON patients(full_name)
        """)
        
        connection.commit()
        print("Expand phase complete: new column and index created")
def expand_with_default(connection):
    """
    Adding a NOT NULL column requires a default value
    or a multi-step process for existing tables
    """
    with connection.cursor() as cursor:
        cursor.execute("""
            ALTER TABLE appointments
            ADD COLUMN IF NOT EXISTS status VARCHAR(20) DEFAULT 'scheduled'
        """)
        
        cursor.execute("""
            ALTER TABLE appointments
            ALTER COLUMN status DROP DEFAULT
        """)
        
        connection.commit()
        print("Expand with default complete")

Phase 2: Migrate

Backfill data from the old structure to the new one. Use the batched approach shown earlier to avoid locking the table for extended periods.

Phase 3: Contract

Once all data has been migrated and the application has been updated to use the new schema, remove the old structure.

def contract_phase(connection):
    """Phase 3: Remove old column after migration is complete"""
    with connection.cursor() as cursor:
        cursor.execute("""
            ALTER TABLE patients
            DROP COLUMN IF EXISTS first_name
        """)
        
        cursor.execute("""
            ALTER TABLE patients
            DROP COLUMN IF EXISTS last_name
        """)
        
        connection.commit()
        print("Contract phase complete: legacy columns removed")

The expand-contract pattern is straightforward in theory, but each phase requires testing in a staging environment that mirrors production load. Raj's team at the healthcare company spent three weeks validating each phase before executing in production.

SQLite Limitations for Production Migrations

SQLite is excellent for development, testing, and small-scale applications. Its file-based nature and minimal configuration make it approachable. However, production migrations with SQLite present unique challenges that often surprise teams.

Comparison: SQLite vs PostgreSQL for Migration Strategies

| Aspect | SQLite | PostgreSQL | |--------|--------|------------| | Concurrent writes | Limited (database-level locking) | Row-level locking | | ALTER TABLE support | Restricted (most operations require recreation) | Full DDL support | | Online migration tools | Minimal | Extensive (pgloader, custom solutions) | | Hot backups | Requires specific tooling | Point-in-time recovery | | Migration rollback | Difficult (file-level) | Transaction-based |

SQLite's ALTER TABLE support is particularly limiting. You cannot add a column with a NOT NULL constraint to an existing table without providing a default value. Removing columns requires recreating the entire table, which for large datasets means significant downtime.

TypeScript Example: Detecting SQLite Limitations

Before attempting migration, you can check your database type:

interface DatabaseInfo {
  engine: 'sqlite' | 'postgresql' | 'mysql';
  supportsOnlineDDL: boolean;
  maxColumnNameLength: number;
}
function detectDatabaseCapabilities(connection: any): DatabaseInfo {
  try {
    const result = connection.exec("SELECT sqlite_version() as version");
    return {
      engine: 'sqlite',
      supportsOnlineDDL: false,
      maxColumnNameLength: 1024,
    };
  } catch {
    // Not SQLite, likely PostgreSQL or MySQL
    return {
      engine: 'postgresql',
      supportsOnlineDDL: true,
      maxColumnNameLength: 63,
    };
  }
}
function validateMigrationPlan(
  databaseInfo: DatabaseInfo,
  migrationSteps: string[]
): { valid: boolean; warnings: string[] } {
  const warnings: string[] = [];
  
  if (databaseInfo.engine === 'sqlite') {
    warnings.push(
      'SQLite detected: avoid NOT NULL columns without defaults'
    );
    warnings.push(
      'Table recreation required for column removal - plan for downtime'
    );
    warnings.push(
      'Test migration on data volume matching production'
    );
  }
  
  return {
    valid: warnings.length === 0,
    warnings,
  };
}
// Usage
const dbInfo = detectDatabaseCapabilities(connection);
const validation = validateMigrationPlan(dbInfo, [
  'ADD COLUMN status VARCHAR(20)',
  'BACKFILL status FROM old_status',
  'DROP COLUMN old_status'
]);
if (!validation.valid) {
  console.warn('Migration warnings:', validation.warnings);
}

Real-World Application

When Raj's team needed to denormalize their patient records for performance, they chose a four-week migration window with the expand-contract pattern. Week one added the new denormalized columns. Weeks two and three ran backfill jobs during off-peak hours. Week four updated the application code to read from the new columns, validated in staging, then deployed during a planned maintenance window.

The key to their success was extensive staging validation. They replayed production-like traffic against the staging database to catch edge cases that unit tests missed. They also kept the old columns for 30 days after the migration, allowing instant rollback if issues appeared.

Lessons Learned

  • Backfill in small batches with pauses to prevent locking production traffic
  • Always validate migrations in a staging environment with production-scale data
  • Keep legacy schema elements for a grace period after migration to enable rollback
  • SQLite's limitations make it unsuitable for zero-downtime migrations at scale
  • Test rollback procedures before deploying any migration to production

    • Actionable Takeaways

  • Audit your current migration approach — Review whether your team is using expand-contract or attempting big-bang migrations that require downtime
  • Implement batched backfills — Replace any bulk UPDATE statements with batched approaches that use FOR UPDATE SKIP LOCKED for PostgreSQL
  • Document rollback procedures — Before any migration, write down exactly how to revert if something goes wrong
  • Evaluate SQLite usage — If you're using SQLite in production and need zero-downtime migrations, consider migrating to PostgreSQL
  • Test with production-scale data — Staging databases with tiny datasets hide performance issues that appear in production
