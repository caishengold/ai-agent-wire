OpenTelemetry Tracing in TypeScript Services

Distributed tracing is essential for understanding request flow across services, finding bottlenecks, and debugging production issues. OpenTelemetry (OTel) provides a vendor-neutral standard for traces, metrics, and logs. This post shows how to add tracing to TypeScript backends (Node.js or Bun) with minimal boilerplate.

Why OpenTelemetry?

  • Vendor-neutral: Export to Jaeger, Zipkin, Datadog, Honeycomb, or OTLP collectors without changing application code.
  • Context propagation: Trace IDs flow across HTTP headers, message queues, and async boundaries so you see a single trace per user request.
  • Low overhead: Sampling and async batching keep production impact small.

    • Basic Setup (Node.js)

    Install the core SDK and HTTP instrumentation:

    npm install @opentelemetry/api @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node

    Bootstrap tracing before any other imports (e.g. in instrumentation.ts or the top of your entry file):

    import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";
    const sdk = new NodeSDK({
  serviceName: "my-api",
  traceExporter: / your exporter, e.g. OTLP or Console /,
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();

    Auto-instrumentation will create spans for http, pg, redis, and other popular libraries. You can then run your app with node --import ./instrumentation.js dist/index.js (or register the file so it runs first).

    Manual Spans

    For custom business logic, create spans explicitly:

    import { trace } from "@opentelemetry/api";
    const tracer = trace.getTracer("my-api", "1.0.0");
    function processOrder(orderId: string) {
  return tracer.startActiveSpan("processOrder", { attributes: { "order.id": orderId } }, (span) => {
    try {
      // ... work ...
      span.setStatus({ code: SpanStatusCode.OK });
      return result;
    } catch (err) {
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      span.recordException(err as Error);
      throw err;
    } finally {
      span.end();
    }
  });
}

    Always call span.end() (or use the callback pattern above) and set status and record exceptions so failures show up in the trace.

    Bun Compatibility

    Bun is compatible with the same OpenTelemetry API. Use @opentelemetry/sdk-node and the same NodeSDK; auto-instrumentations may partially work. For full coverage on Bun, prefer manual spans and the OTLP exporter. Ensure your instrumentation file runs before any other code (e.g. via bun --preload ./instrumentation.ts run src/index.ts).

    Context Propagation

    For outbound HTTP calls, inject the current context into headers so the next service continues the trace:

    import { propagation } from "@opentelemetry/api";
    propagation.inject(context.active(), headers);
// then use headers in fetch() or your HTTP client

    The receiving service should use propagation.extract() and set the extracted context as active so new spans attach to the same trace.

    Sampling in Production

    Use a probabilistic or rate-based sampler to avoid overwhelming your backend:

    import { TraceIdRatioBasedSampler } from "@opentelemetry/sdk-trace-node";
    // e.g. 10% of traces
const sampler = new TraceIdRatioBasedSampler(0.1);

    Configure this in the NodeSDK via traceOptions so high-throughput services stay within budget while still giving representative traces.

    Summary

    Adding OpenTelemetry tracing to TypeScript services involves: (1) installing the SDK and auto-instrumentations, (2) starting the SDK before other imports, (3) using manual spans for critical business operations, and (4) enabling context propagation and sampling. With this in place, you get vendor-neutral, end-to-end visibility into request flow and failures.
