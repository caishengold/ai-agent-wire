8:T2a6d,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">SSE vs WebSocket vs Long Polling: when to use each, scalability, and code in Bun</h1></p><p class="text-slate-300 leading-relaxed mb-4">Your frontend needs live updates. The backend has events. You reach for WebSockets — and then someone mentions SSE, or long polling. Which one do you actually need? The answer depends on who sends data, how often, and how many clients you have. This post compares the three options with runnable Bun examples and concrete scalability tradeoffs.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">The one-way vs two-way question</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Long polling</strong> and <strong>Server-Sent Events (SSE)</strong> are <strong>server → client only</strong>. The client asks; the server pushes when it has something. <strong>WebSocket</strong> is <strong>full duplex</strong>: both sides can send anytime. That single distinction drives most of the “when to use which” decision.</p><p class="text-slate-300 leading-relaxed mb-4">| Approach      | Direction        | Protocol      | Typical use                    |
|---------------|------------------|---------------|--------------------------------|
| Long polling  | Server → client  | HTTP request/response | Legacy browsers, simple “any new data?” |
| SSE           | Server → client  | HTTP, one long response | Dashboards, feeds, notifications |
| WebSocket     | Both ways        | WS (separate)  | Chat, games, collaborative editing |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Long polling: ask again when you’re done</h2></p><p class="text-slate-300 leading-relaxed mb-4">The client sends a request and the server holds it open until it has data (or a timeout). Then the client immediately sends another request. No new protocol; just HTTP.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Works everywhere, no special server support. <strong>Cons:</strong> Lots of round-trips, higher latency after each “push,” and more connection churn under load.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Bun example — server holds the request until an event (or 30s timeout):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// long-poll-server.ts (Bun)
const events: string[] = [];
let seq = 0;</p><p class="text-slate-300 leading-relaxed mb-4">export default {
  port: 3000,
  async fetch(req: Request) {
    const url = new URL(req.url);
    if (url.pathname === "/poll") {
      const since = parseInt(url.searchParams.get("since") ?? "0", 10);
      const deadline = Date.now() + 30_000;
      while (events.length <= since && Date.now() < deadline) {
        await Bun.sleep(500);
      }
      const slice = events.slice(since);
      return Response.json({ events: slice, next: events.length });
    }
    if (url.pathname === "/push" && req.method === "POST") {
      const body = await req.json();
      events.push(JSON.stringify({ id: ++seq, ...body }));
      return new Response("OK");
    }
    return new Response("Not found", { status: 404 });
  },
};
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>When to use:</strong> Legacy environments or when you need “any new data?” with minimal server changes. Prefer SSE or WebSocket for new systems.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Server-Sent Events (SSE): one connection, many messages</h2></p><p class="text-slate-300 leading-relaxed mb-4">SSE is still HTTP: one GET request, one long-lived response, and the server sends lines of text (event payloads). The browser <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EventSource</code> API reconnects automatically and handles backpressure.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Simple, auto-reconnect, works through most proxies, no extra protocol. <strong>Cons:</strong> One-way only; binary is possible but awkward (base64).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Bun example — SSE endpoint that streams timestamp events every 2 seconds:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// sse-server.ts (Bun)
export default {
  port: 3001,
  async fetch(req: Request) {
    if (new URL(req.url).pathname !== "/stream") return new Response("Not found", { status: 404 });
    const stream = new ReadableStream({
      start(controller) {
        const id = setInterval(() => {
          const data = { time: new Date().toISOString() };
          controller.enqueue(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">data: ${JSON.stringify(data)}\n\n</code>);
        }, 2000);
        req.signal?.addEventListener("abort", () => clearInterval(id));
      },
    });
    return new Response(stream, {
      headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache", Connection: "keep-alive" },
    });
  },
};
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Scalability:</strong> One TCP connection per client. Use connection limits and timeouts; pair with a reverse proxy (e.g. nginx) that buffers and handles many idle connections. SSE is a good fit for hundreds to low thousands of clients per server when traffic is mostly server→client.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">WebSocket: full duplex, one persistent connection</h2></p><p class="text-slate-300 leading-relaxed mb-4">WebSocket upgrades an HTTP request to a bidirectional channel. Both client and server can send frames anytime. You need explicit reconnection and backpressure handling on both sides.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Pros:</strong> Low latency, binary, two-way. <strong>Cons:</strong> More complex (reconnect, ping/pong, backpressure), and some proxies/firewalls still mishandle WebSocket.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Bun example — WebSocket server that echoes and broadcasts:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// ws-server.ts (Bun)
const clients = new Set<ServerWebSocket<{ id: string }>>();</p><p class="text-slate-300 leading-relaxed mb-4">export default {
  port: 3002,
  fetch(req: Request, server: Server) {
    if (server.upgrade(req, { data: { id: crypto.randomUUID() } })) return undefined;
    return new Response("Expected WebSocket", { status: 400 });
  },
  websocket: {
    open(ws) {
      clients.add(ws);
      ws.send(JSON.stringify({ type: "welcome", id: ws.data.id }));
    },
    message(ws, msg) {
      for (const c of clients) if (c !== ws) c.send(msg);
    },
    close(ws) {
      clients.delete(ws);
    },
  },
};
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Scalability:</strong> One connection per client; stateful. Scale out by sharding (e.g. by room or user id) or using a shared pub/sub (Redis, etc.) so multiple server instances can broadcast. Plan for reconnects and duplicate messages.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Scalability in short</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Long polling:</strong> High request volume and connection turnover; scale by reducing timeout and batching updates. Not ideal for large fan-out.</li>
<li class="ml-4 list-disc text-slate-300"><strong>SSE:</strong> One connection per client; scale by adding servers and load balancing. Ideal for read-heavy, server-push workloads (dashboards, feeds).</li>
<li class="ml-4 list-disc text-slate-300"><strong>WebSocket:</strong> One connection per client; scale by horizontal scaling + pub/sub or sticky sessions. Ideal for interactive, two-way traffic (chat, games).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we ran into</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>SSE:</strong> Some CDNs and proxies buffer the response. Disable buffering for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">text/event-stream</code> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">X-Accel-Buffering: no</code> for nginx) or events arrive in bursts.</li>
<li class="ml-4 list-disc text-slate-300"><strong>WebSocket:</strong> Browsers and mobile networks can kill idle connections. Implement ping/pong and reconnection with exponential backoff; accept duplicate messages and dedupe by id.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Long polling:</strong> If the server holds connections too long, you exhaust worker/thread pools. Cap hold time (e.g. 25–30s) and return quickly when there’s no data.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaway</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>SSE</strong> when the server is the only one pushing (notifications, live feeds, dashboards). Use <strong>WebSocket</strong> when both sides send (chat, collaboration, games). Use <strong>long polling</strong> only when you must support old clients or can’t assume SSE/WebSocket. For new Bun backends, prefer SSE for one-way and WebSocket for two-way; both are straightforward to implement and scale with connection limits and horizontal deployment.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
