SSE vs WebSocket vs Long Polling: when to use each, scalability, and code in Bun

Your frontend needs live updates. The backend has events. You reach for WebSockets — and then someone mentions SSE, or long polling. Which one do you actually need? The answer depends on who sends data, how often, and how many clients you have. This post compares the three options with runnable Bun examples and concrete scalability tradeoffs.

The one-way vs two-way question

Long polling and Server-Sent Events (SSE) are server → client only. The client asks; the server pushes when it has something. WebSocket is full duplex: both sides can send anytime. That single distinction drives most of the “when to use which” decision.

| Approach | Direction | Protocol | Typical use | |---------------|------------------|---------------|--------------------------------| | Long polling | Server → client | HTTP request/response | Legacy browsers, simple “any new data?” | | SSE | Server → client | HTTP, one long response | Dashboards, feeds, notifications | | WebSocket | Both ways | WS (separate) | Chat, games, collaborative editing |

Long polling: ask again when you’re done

The client sends a request and the server holds it open until it has data (or a timeout). Then the client immediately sends another request. No new protocol; just HTTP.

Pros: Works everywhere, no special server support. Cons: Lots of round-trips, higher latency after each “push,” and more connection churn under load.

Bun example — server holds the request until an event (or 30s timeout):

// long-poll-server.ts (Bun)
const events: string[] = [];
let seq = 0;
export default {
  port: 3000,
  async fetch(req: Request) {
    const url = new URL(req.url);
    if (url.pathname === "/poll") {
      const since = parseInt(url.searchParams.get("since") ?? "0", 10);
      const deadline = Date.now() + 30_000;
      while (events.length <= since && Date.now() < deadline) {
        await Bun.sleep(500);
      }
      const slice = events.slice(since);
      return Response.json({ events: slice, next: events.length });
    }
    if (url.pathname === "/push" && req.method === "POST") {
      const body = await req.json();
      events.push(JSON.stringify({ id: ++seq, ...body }));
      return new Response("OK");
    }
    return new Response("Not found", { status: 404 });
  },
};

When to use: Legacy environments or when you need “any new data?” with minimal server changes. Prefer SSE or WebSocket for new systems.

Server-Sent Events (SSE): one connection, many messages

SSE is still HTTP: one GET request, one long-lived response, and the server sends lines of text (event payloads). The browser EventSource API reconnects automatically and handles backpressure.

Pros: Simple, auto-reconnect, works through most proxies, no extra protocol. Cons: One-way only; binary is possible but awkward (base64).

Bun example — SSE endpoint that streams timestamp events every 2 seconds:

// sse-server.ts (Bun)
export default {
  port: 3001,
  async fetch(req: Request) {
    if (new URL(req.url).pathname !== "/stream") return new Response("Not found", { status: 404 });
    const stream = new ReadableStream({
      start(controller) {
        const id = setInterval(() => {
          const data = { time: new Date().toISOString() };
          controller.enqueue(data: ${JSON.stringify(data)}\n\n);
        }, 2000);
        req.signal?.addEventListener("abort", () => clearInterval(id));
      },
    });
    return new Response(stream, {
      headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache", Connection: "keep-alive" },
    });
  },
};

Scalability: One TCP connection per client. Use connection limits and timeouts; pair with a reverse proxy (e.g. nginx) that buffers and handles many idle connections. SSE is a good fit for hundreds to low thousands of clients per server when traffic is mostly server→client.

WebSocket: full duplex, one persistent connection

WebSocket upgrades an HTTP request to a bidirectional channel. Both client and server can send frames anytime. You need explicit reconnection and backpressure handling on both sides.

Pros: Low latency, binary, two-way. Cons: More complex (reconnect, ping/pong, backpressure), and some proxies/firewalls still mishandle WebSocket.

Bun example — WebSocket server that echoes and broadcasts:

// ws-server.ts (Bun)
const clients = new Set>();
export default {
  port: 3002,
  fetch(req: Request, server: Server) {
    if (server.upgrade(req, { data: { id: crypto.randomUUID() } })) return undefined;
    return new Response("Expected WebSocket", { status: 400 });
  },
  websocket: {
    open(ws) {
      clients.add(ws);
      ws.send(JSON.stringify({ type: "welcome", id: ws.data.id }));
    },
    message(ws, msg) {
      for (const c of clients) if (c !== ws) c.send(msg);
    },
    close(ws) {
      clients.delete(ws);
    },
  },
};

Scalability: One connection per client; stateful. Scale out by sharding (e.g. by room or user id) or using a shared pub/sub (Redis, etc.) so multiple server instances can broadcast. Plan for reconnects and duplicate messages.

Scalability in short

  • Long polling: High request volume and connection turnover; scale by reducing timeout and batching updates. Not ideal for large fan-out.
  • SSE: One connection per client; scale by adding servers and load balancing. Ideal for read-heavy, server-push workloads (dashboards, feeds).
  • WebSocket: One connection per client; scale by horizontal scaling + pub/sub or sticky sessions. Ideal for interactive, two-way traffic (chat, games).

    • Gotchas we ran into

  • SSE: Some CDNs and proxies buffer the response. Disable buffering for text/event-stream (e.g. X-Accel-Buffering: no for nginx) or events arrive in bursts.
  • WebSocket: Browsers and mobile networks can kill idle connections. Implement ping/pong and reconnection with exponential backoff; accept duplicate messages and dedupe by id.
  • Long polling: If the server holds connections too long, you exhaust worker/thread pools. Cap hold time (e.g. 25–30s) and return quickly when there’s no data.

    • Takeaway

    Use SSE when the server is the only one pushing (notifications, live feeds, dashboards). Use WebSocket when both sides send (chat, collaboration, games). Use long polling only when you must support old clients or can’t assume SSE/WebSocket. For new Bun backends, prefer SSE for one-way and WebSocket for two-way; both are straightforward to implement and scale with connection limits and horizontal deployment.
