Best practices for robust error handling in TypeScript applications

Raj’s team shipped a feature that parsed JSON from an external API. In production, the provider sometimes returned HTML error pages instead of JSON. JSON.parse threw; the catch block logged e and returned null. For weeks, dashboards showed missing data and nobody could tell why — the log was just [object Object]. They fixed it by introducing typed error classes and a small error-boundary layer that normalises failures and logs structure. Debugging time for similar incidents dropped from hours to minutes.

TypeScript gives you types for your happy path. How you model and handle failures decides whether your app degrades gracefully or fails in opaque ways. This post covers practices that work in real backends and frontends: custom error types, centralised handling, and making sure errors are both catchable and debuggable.

Why generic catch is not enough

Catching unknown or any and rethrowing or logging "something went wrong" loses context. You can’t branch on error kind, you can’t attach correlation IDs, and in production you often can’t tell user input errors from system failures. The first step toward robustness is knowing what you caught.

Use typed error classes

Define a small hierarchy of errors so callers and middleware can distinguish cases (e.g. validation vs network vs auth). You don’t need a huge tree — three or four kinds usually cover most apps.

// errors.ts — runnable: save and run with npx ts-node errors.ts (or tsx)
// Custom error base: preserves name and allows instanceof checks
export class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly statusCode: number = 500
  ) {
    super(message);
    this.name = "AppError";
    Object.setPrototypeOf(this, new.target.prototype);
  }
}
export class ValidationError extends AppError {
  constructor(message: string, public readonly fields?: Record) {
    super(message, "VALIDATION_ERROR", 400);
    this.name = "ValidationError";
  }
}
export class NotFoundError extends AppError {
  constructor(resource: string, id?: string) {
    super(id ? ${resource} with id ${id} not found : ${resource} not found, "NOT_FOUND", 404);
    this.name = "NotFoundError";
  }
}
// Example usage: a service that can throw typed errors
function getUserById(id: string): { id: string; name: string } {
  if (!id || id.length < 3) {
    throw new ValidationError("Invalid user id", { userId: "must be at least 3 characters" });
  }
  const db = new Map([
    ["u1", { id: "u1", name: "Aiko" }],
    ["u2", { id: "u2", name: "Sofia" }],
  ]);
  const user = db.get(id);
  if (!user) throw new NotFoundError("User", id);
  return user;
}
// Centralised handler: turn errors into a consistent shape and status code
function handleError(e: unknown): { statusCode: number; code: string; message: string } {
  if (e instanceof ValidationError) {
    return { statusCode: e.statusCode, code: e.code, message: e.message };
  }
  if (e instanceof NotFoundError) {
    return { statusCode: e.statusCode, code: e.code, message: e.message };
  }
  if (e instanceof AppError) {
    return { statusCode: e.statusCode, code: e.code, message: e.message };
  }
  if (e instanceof Error) {
    return { statusCode: 500, code: "INTERNAL_ERROR", message: e.message };
  }
  return { statusCode: 500, code: "UNKNOWN", message: "An unexpected error occurred" };
}
// Demo
try {
  console.log(getUserById("u1"));
  getUserById("x");
} catch (e) {
  const out = handleError(e);
  console.log("Handled:", out);
}
try {
  getUserById("nonexistent");
} catch (e) {
  console.log("Handled:", handleError(e));
}

Example terminal output:

{ id: 'u1', name: 'Aiko' }
Handled: { statusCode: 400, code: 'VALIDATION_ERROR', message: 'Invalid user id' }
Handled: { statusCode: 404, code: 'NOT_FOUND', message: 'User with id nonexistent not found' }

Object.setPrototypeOf(this, new.target.prototype) keeps instanceof working when targeting ES5 or when the code is transpiled; without it, subclass instances can fail instanceof checks.

Normalise and log at the boundary

Let a single layer (e.g. HTTP error middleware or a top-level promise handler) convert thrown errors into responses and logs. That way you don’t scatter console.log(e) everywhere and you can add request IDs or sanitisation in one place.

Example: API route + error middleware

// api-handler.ts — runnable with Bun or Node (e.g. npx tsx api-handler.ts)
import { ValidationError, NotFoundError, AppError } from "./errors";
type Request = { url: string; method: string };
type Response = { statusCode: number; body: string };
function handleError(e: unknown, req: Request): Response {
  const reqId = req-${Date.now()};
  if (e instanceof ValidationError) {
    console.error([${reqId}] ValidationError:, e.message, e.fields);
    return { statusCode: 400, body: JSON.stringify({ code: e.code, message: e.message, fields: e.fields }) };
  }
  if (e instanceof NotFoundError) {
    console.error([${reqId}] NotFoundError:, e.message);
    return { statusCode: 404, body: JSON.stringify({ code: e.code, message: e.message }) };
  }
  if (e instanceof AppError) {
    console.error([${reqId}] AppError:, e.code, e.message);
    return { statusCode: e.statusCode, body: JSON.stringify({ code: e.code, message: e.message }) };
  }
  const err = e instanceof Error ? e : new Error(String(e));
  console.error([${reqId}] Unhandled:, err.message, err.stack);
  return {
    statusCode: 500,
    body: JSON.stringify({ code: "INTERNAL_ERROR", message: "An error occurred" }),
  };
}
async function getUserRoute(req: Request): Promise {
  const id = new URL(req.url).searchParams.get("id") ?? "";
  if (!id) throw new ValidationError("Missing id", { id: "required" });
  const user = getUserById(id);
  return { statusCode: 200, body: JSON.stringify(user) };
}
async function main() {
  const req: Request = { url: "http://localhost/users?id=u1", method: "GET" };
  try {
    const res = await getUserRoute(req);
    console.log("Response:", res);
  } catch (e) {
    const res = handleError(e, req);
    console.log("Error response:", res);
  }
  try {
    await getUserRoute({ url: "http://localhost/users", method: "GET" });
  } catch (e) {
    console.log("Error response:", handleError(e, req));
  }
}
function getUserById(id: string): { id: string; name: string } {
  if (!id) throw new ValidationError("Invalid user id", { userId: "required" });
  const db = new Map([["u1", { id: "u1", name: "Aiko" }]]);
  const user = db.get(id);
  if (!user) throw new NotFoundError("User", id);
  return user;
}
main();

Running it (with getUserById and error classes in scope) gives you consistent status codes and body shape, and logs that include a request id so you can trace failures.

Approach comparison: when to use what

Different layers of the app need different strategies. The table below summarises where each approach fits.

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Typed error classes + throw | Clear semantics, instanceof checks, one place to map to HTTP/logs | Requires discipline: everyone must throw your types | Backends, shared services, APIs | | Result type (e.g. { ok: true, data } \| { ok: false, error }) | Explicit in the type system; no hidden throws | More boilerplate at call sites; easy to forget to handle ok: false | Parsers, pure functions, libraries | | try/catch at boundary only | Simple; errors surface in one layer | Risk of swallowing errors if you catch and don’t rethrow or log properly | Top-level handlers, route middleware, worker entry points | | Promise.catch + global unhandledRejection | Catches async slips | No request context; hard to map to a single user or request | Last line of defence; log and alert, then exit or degrade |

We use typed errors + throw in domain and service code, and try/catch at the boundary (HTTP, queue consumer) to turn them into responses and logs. Result types we reserve for pure, sync steps (e.g. parsing config) where we want the type to force handling.

Parse and validate at the edges

External input (HTTP body, env vars, JSON from another service) is untyped. Parse once at the edge and throw typed errors so the rest of the app works with known shapes. That avoids JSON.parse or invalid data leaking into the middle of the stack.

  • JSON: wrap JSON.parse in a function that catches SyntaxError and throws an AppError or ValidationError with a clear message (and optionally the raw string length, not the full body).
  • Env: validate required env vars at startup; throw with a list of missing keys so the process fails fast and logs are actionable.
  • Request body: use a schema library (e.g. Zod, io-ts) and map validation failures to your ValidationError so the handler can return 400 with field-level messages.

    • Lessons learned

    We had a production incident on 2025-11-14 where an integration started returning HTML (maintenance page) instead of JSON. Our code did:

    const data = JSON.parse(responseBody);

    No try/catch. The process crashed with a SyntaxError; the process manager restarted it, and the same request was retried. We saw a spike in restarts and no clear error in our logs because the crash happened before our logger ran. We fixed it by:

  • Wrapping all external response parsing in try/catch and throwing a custom ParseError with statusCode: 502 and a message like "Upstream returned invalid JSON".
  • Logging the first 200 characters of the response (with PII stripped) so we could see "<!DOCTYPE html>..." in the logs next time.
  • Adding a circuit breaker for that integration so we stopped hammering a failing upstream.

    • The takeaway: parse at the edge, treat parse failures as first-class errors, and log enough context (safely) so you don’t have to guess in production.

    What you can do today

  • Introduce a base AppError (and 2–3 subclasses) in a shared errors.ts. Replace one or two generic throw new Error(...) call sites and route those through your HTTP or worker error handler so status codes and logs are consistent.
  • Audit catch blocks for catch (e) that log e without checking type. Replace with a small handleError(e) that uses instanceof and returns a stable shape; log there with a request or correlation id.
  • Wrap JSON.parse and env access in helpers that throw your own errors and log a safe snippet of the input on failure.
  • Add an unhandledRejection handler that logs and, in production, triggers an alert or graceful shutdown so no async error is silently dropped.
  • Document in your runbook or README which error codes and status codes your API returns, so frontend and support know what to expect and how to debug.

    • Error handling is boring until it isn’t. A small set of typed errors and a single boundary layer will make the next outage a lot easier to diagnose and fix.
