8:T48f3,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Prompt engineering for code generation — system prompts, chain-of-thought, few-shot, temperature tuning</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team integrated an LLM (large language model) to generate API client code from OpenAPI specs. The first version used a single user prompt: "Generate a TypeScript client for this spec." The model sometimes returned valid code, sometimes added nonexistent endpoints, and occasionally wrote Python instead of TypeScript. After a week of inconsistent runs, they introduced a <strong>system prompt</strong> that fixed the language and style, added <strong>few-shot</strong> examples of input/output pairs, and turned on <strong>chain-of-thought</strong> for the model to reason about the spec before generating. Code quality and consistency improved; tuning <strong>temperature</strong> later reduced the remaining randomness on deterministic paths.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers those four levers — system prompts, chain-of-thought (CoT), few-shot examples, and temperature — with runnable examples, a comparison table, and what actually went wrong when we pushed them too far.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why prompt structure matters for code</h2></p><p class="text-slate-300 leading-relaxed mb-4">Code generation is different from chat or summarisation. You need the model to stick to a language, follow your conventions, and not invent APIs or dependencies. A single free-form user prompt is rarely enough. The levers that help are:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>System prompt</strong> — Sets identity, constraints, and output format before any user input. Most APIs treat it as higher-priority context.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Chain-of-thought</strong> — Asks the model to explain its reasoning (e.g. "List the endpoints, then generate the client"). That often improves correctness before the final code.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Few-shot</strong> — One or more example request/response pairs in the prompt. The model mimics structure and style.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Temperature</strong> — Controls randomness. Low (e.g. 0.2) for deterministic, repeatable code; higher for exploration or multiple variants.</li></p><p class="text-slate-300 leading-relaxed mb-4">Below we use the OpenAI-compatible API (works with OpenAI, local models, or proxies) so you can run the examples yourself.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">System prompt: lock in role and rules</h2></p><p class="text-slate-300 leading-relaxed mb-4">The system prompt runs first and sets the "persona" and rules. Put language, framework, and "do not invent" rules here so they apply to every request.</p><p class="text-slate-300 leading-relaxed mb-4">Example: force TypeScript, no extra endpoints, and a clear output shape.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">prompt_demo_system.py — system prompt for code generation</h1>

You can request CoT in the user prompt and then ask for the final code.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">prompt_demo_cot.py — chain-of-thought then code</h1>

Here we use two short examples and then a real request.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">prompt_demo_fewshot.py — few-shot code generation</h1>

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Few-shot works best when the examples are similar to the target task (same language, same kind of function). Too many or too long examples eat context and can confuse the model.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Temperature: control randomness</h2></p><p class="text-slate-300 leading-relaxed mb-4">Temperature controls how random the next token is. For code you usually want low values so the same prompt gives similar output across runs.</p><p class="text-slate-300 leading-relaxed mb-4">| Temperature | Typical use | Effect |
|-------------|-------------|--------|
| 0.0–0.2     | Production code generation, parsers, fixed formats | Mostly deterministic; small variation. |
| 0.3–0.5     | Code with several valid styles | Some variety, still coherent. |
| 0.6–0.9     | Brainstorming, multiple implementations | More creative, less repeatable. |
| 1.0+        | Rare for code | High randomness; often useless for precise output. |</p><p class="text-slate-300 leading-relaxed mb-4">Same prompt, different temperatures — you’ll see more variation at 0.7 than at 0.2:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">prompt_demo_temp.py — same prompt, different temperatures</h1>
import os
from openai import OpenAI</p><p class="text-slate-300 leading-relaxed mb-4">client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))</p><p class="text-slate-300 leading-relaxed mb-4">def generate(temperature: float) -> str:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "You are a code generator. TypeScript only. One short function."},
            {"role": "user", "content": "Function that checks if a string is a valid ISO date (YYYY-MM-DD)."},
        ],
        temperature=temperature,
        max_tokens=200,
    )
    return resp.choices[0].message.content or ""</p><p class="text-slate-300 leading-relaxed mb-4">for temp in [0.0, 0.7]:
    print(f"--- temperature={temp} ---")
    print(generate(temp))
    print()
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">At 0.0 you get stable, almost identical code across runs; at 0.7 you get different implementations (regex, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Date</code>, manual split) for the same request.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>System prompt only</strong> | Simple, one place for rules; works with any client. | No examples; model may still drift on style. | Baseline for every code-gen task; add language and hard constraints. |
| <strong>Chain-of-thought</strong> | Often improves correctness; model "plans" before coding. | Longer output, more tokens, slightly slower. | Complex specs, multi-step code, or when the model keeps missing steps. |
| <strong>Few-shot</strong> | Aligns style and structure; good for templates. | Uses context; bad examples can mislead. | When you have 1–3 clear input/output examples and want consistency. |
| <strong>Low temperature (0–0.2)</strong> | Repeatable, predictable code. | Less diversity; can get stuck in a local pattern. | Production, CI, or any time you need the same prompt → same code. |
| <strong>Higher temperature (0.5+)</strong> | Multiple variants, more creative solutions. | Inconsistent; not suitable for deterministic pipelines. | Exploration, brainstorming, or generating several options for a human to pick. |</p><p class="text-slate-300 leading-relaxed mb-4">Combine them: system prompt for rules, one or two few-shot examples for format, CoT when the task is complex, and low temperature for the final call.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>What went wrong:</strong> We once put five long few-shot examples (each 40+ lines) into a single prompt for a Go client generator. Context length was fine, but the model started mixing styles from different examples and sometimes produced invalid Go (e.g. mixing pointer and value receivers inconsistently). We also used temperature 0.4 "to allow a bit of variety." In CI, the same spec produced different client code on each run, which broke diff-based reviews.</p><p class="text-slate-300 leading-relaxed mb-4">We cut to two short examples (one GET, one POST), moved all style rules into the system prompt, and set temperature to 0.2. Generation became stable and the output passed <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">go build</code> consistently. The failure mode wasn’t the API — it was <strong>too many few-shot examples and a temperature that was too high for deterministic code</strong>.</p><p class="text-slate-300 leading-relaxed mb-4">Another lesson: CoT is useful but expensive. We asked for "list endpoints then generate" on every request; for a 50-endpoint spec the reasoning block was 2,000+ tokens. We switched to CoT only for specs above 10 endpoints and kept a single direct "generate client" prompt for small specs. That cut cost by about 30% without hurting quality on the small ones.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What you can do next</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add a system prompt</strong> to your current code-generation flow. Put language, "do not invent" rules, and output format (e.g. "single code block") there and leave the user message for the concrete task only.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Try one or two few-shot examples</strong> — keep each under ~15 lines. Match the kind of code you want (e.g. one GET handler, one POST handler) and run the same prompt a few times to see if style stabilises.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Use CoT only when it helps</strong> — e.g. "first list the endpoints and types, then write the client." Use it for larger or ambiguous specs; skip it for trivial single-function requests.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Set temperature to 0.0–0.2</strong> for any path that needs repeatable code (CI, production, docs). Reserve higher values for interactive or exploratory use.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Measure</strong> — log token usage and success rate (e.g. "does the code compile?") before and after changing prompts or temperature so you know what actually improved.</li></p><p class="text-slate-300 leading-relaxed mb-4">If you only change one thing today: add a short system prompt that fixes the language and forbids invented APIs, and set temperature to 0.2. That alone will remove a lot of the randomness and off-spec code we saw in Sofia’s first version.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
