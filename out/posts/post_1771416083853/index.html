Prompt engineering for code generation — system prompts, chain-of-thought, few-shot, temperature tuning

Sofia’s team integrated an LLM (large language model) to generate API client code from OpenAPI specs. The first version used a single user prompt: "Generate a TypeScript client for this spec." The model sometimes returned valid code, sometimes added nonexistent endpoints, and occasionally wrote Python instead of TypeScript. After a week of inconsistent runs, they introduced a system prompt that fixed the language and style, added few-shot examples of input/output pairs, and turned on chain-of-thought for the model to reason about the spec before generating. Code quality and consistency improved; tuning temperature later reduced the remaining randomness on deterministic paths.

This post covers those four levers — system prompts, chain-of-thought (CoT), few-shot examples, and temperature — with runnable examples, a comparison table, and what actually went wrong when we pushed them too far.

Why prompt structure matters for code

Code generation is different from chat or summarisation. You need the model to stick to a language, follow your conventions, and not invent APIs or dependencies. A single free-form user prompt is rarely enough. The levers that help are:

  • System prompt — Sets identity, constraints, and output format before any user input. Most APIs treat it as higher-priority context.
  • Chain-of-thought — Asks the model to explain its reasoning (e.g. "List the endpoints, then generate the client"). That often improves correctness before the final code.
  • Few-shot — One or more example request/response pairs in the prompt. The model mimics structure and style.
  • Temperature — Controls randomness. Low (e.g. 0.2) for deterministic, repeatable code; higher for exploration or multiple variants.

    • Below we use the OpenAI-compatible API (works with OpenAI, local models, or proxies) so you can run the examples yourself.

    System prompt: lock in role and rules

    The system prompt runs first and sets the "persona" and rules. Put language, framework, and "do not invent" rules here so they apply to every request.

    Example: force TypeScript, no extra endpoints, and a clear output shape.

    prompt_demo_system.py — system prompt for code generation
    

    Requires: pip install openai
    

    Set OPENAI_API_KEY in the environment.
    import os
from openai import OpenAI
    client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))
    SYSTEM = """You are a code generator. You output only valid code and brief comments.

  • Language: TypeScript only.
    • 

  • Do not add endpoints or fields that are not in the user's spec or request.
    • 

  • Output a single code block. No preamble or explanation outside the block."""
    • resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": "Write a function that takes an array of numbers and returns the sum. Export it."},
    ],
    temperature=0.2,
    max_tokens=500,
)
    print(resp.choices[0].message.content)

    Run it (with your API key set):

    $ export OPENAI_API_KEY=sk-...
$ python prompt_demo_system.py

    Example output (model-dependent):

    export function sum(numbers: number[]): number {
  return numbers.reduce((acc, n) => acc + n, 0);
}

    Putting "TypeScript only" and "do not add endpoints" in the system prompt reduces off-spec output more reliably than repeating the same in every user message.

    Chain-of-thought: reason first, then code

    Asking the model to reason before coding (e.g. list steps or endpoints) often improves accuracy. You can request CoT in the user prompt and then ask for the final code.

    prompt_demo_cot.py — chain-of-thought then code
    
import os
from openai import OpenAI
    client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))
    SYSTEM = "You are a code generator. Output TypeScript only. No invented APIs."
    USER_COT = """Given this OpenAPI-style fragment:

  • GET /users returns { id: number, name: string }[]
    • 

  • GET /users/{id} returns { id: number, name: string }
    • First list the endpoints and response types in one short paragraph. Then write a TypeScript client with one function per endpoint. Export the client class."""
    resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": USER_COT},
    ],
    temperature=0.2,
    max_tokens=800,
)
    print(resp.choices[0].message.content)

    Example output shape (abbreviated):

    Endpoints: GET /users (array of {id, name}), GET /users/{id} (single object).
    // TypeScript client
export class ApiClient {
  async getUsers(): Promise<{ id: number; name: string }[]> { ... }
  async getUser(id: number): Promise<{ id: number; name: string }> { ... }
}

    CoT doesn’t guarantee correctness, but in practice it reduces hallucinated endpoints because the model "thinks through" the spec first.

    Few-shot: show input/output examples

    Few-shot means including one or more example request/response pairs in the prompt so the model matches format and style. Here we use two short examples and then a real request.

    prompt_demo_fewshot.py — few-shot code generation
    
import os
from openai import OpenAI
    client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))
    SYSTEM = "You are a code generator. Output TypeScript only. Follow the style of the examples."
    FEWSHOT = """Example 1 — request: "function to double a number"
Response:
export function double(n: number): number { return n  2; }
    Example 2 — request: "function to get the first element of an array or null"
Response:
export function first(arr: T[]): T | null { return arr.length === 0 ? null : arr[0]; }
    Now do this — request: "function that takes a string and returns the word count (words separated by spaces)"
Response:"""
    resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": FEWSHOT},
    ],
    temperature=0.2,
    max_tokens=300,
)
    print(resp.choices[0].message.content)

    Example output:

    export function wordCount(s: string): number {
  return s.trim() ? s.trim().split(/\s+/).length : 0;
}

    Few-shot works best when the examples are similar to the target task (same language, same kind of function). Too many or too long examples eat context and can confuse the model.

    Temperature: control randomness

    Temperature controls how random the next token is. For code you usually want low values so the same prompt gives similar output across runs.

    | Temperature | Typical use | Effect | |-------------|-------------|--------| | 0.0–0.2 | Production code generation, parsers, fixed formats | Mostly deterministic; small variation. | | 0.3–0.5 | Code with several valid styles | Some variety, still coherent. | | 0.6–0.9 | Brainstorming, multiple implementations | More creative, less repeatable. | | 1.0+ | Rare for code | High randomness; often useless for precise output. |

    Same prompt, different temperatures — you’ll see more variation at 0.7 than at 0.2:

    prompt_demo_temp.py — same prompt, different temperatures
    
import os
from openai import OpenAI
    client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))
    def generate(temperature: float) -> str:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "You are a code generator. TypeScript only. One short function."},
            {"role": "user", "content": "Function that checks if a string is a valid ISO date (YYYY-MM-DD)."},
        ],
        temperature=temperature,
        max_tokens=200,
    )
    return resp.choices[0].message.content or ""
    for temp in [0.0, 0.7]:
    print(f"--- temperature={temp} ---")
    print(generate(temp))
    print()

    At 0.0 you get stable, almost identical code across runs; at 0.7 you get different implementations (regex, Date, manual split) for the same request.

    Comparison: when to use which

    | Approach | Pros | Cons | When to use | |----------|------|------|-------------| | System prompt only | Simple, one place for rules; works with any client. | No examples; model may still drift on style. | Baseline for every code-gen task; add language and hard constraints. | | Chain-of-thought | Often improves correctness; model "plans" before coding. | Longer output, more tokens, slightly slower. | Complex specs, multi-step code, or when the model keeps missing steps. | | Few-shot | Aligns style and structure; good for templates. | Uses context; bad examples can mislead. | When you have 1–3 clear input/output examples and want consistency. | | Low temperature (0–0.2) | Repeatable, predictable code. | Less diversity; can get stuck in a local pattern. | Production, CI, or any time you need the same prompt → same code. | | Higher temperature (0.5+) | Multiple variants, more creative solutions. | Inconsistent; not suitable for deterministic pipelines. | Exploration, brainstorming, or generating several options for a human to pick. |

    Combine them: system prompt for rules, one or two few-shot examples for format, CoT when the task is complex, and low temperature for the final call.

    Lessons learned

    What went wrong: We once put five long few-shot examples (each 40+ lines) into a single prompt for a Go client generator. Context length was fine, but the model started mixing styles from different examples and sometimes produced invalid Go (e.g. mixing pointer and value receivers inconsistently). We also used temperature 0.4 "to allow a bit of variety." In CI, the same spec produced different client code on each run, which broke diff-based reviews.

    We cut to two short examples (one GET, one POST), moved all style rules into the system prompt, and set temperature to 0.2. Generation became stable and the output passed go build consistently. The failure mode wasn’t the API — it was too many few-shot examples and a temperature that was too high for deterministic code.

    Another lesson: CoT is useful but expensive. We asked for "list endpoints then generate" on every request; for a 50-endpoint spec the reasoning block was 2,000+ tokens. We switched to CoT only for specs above 10 endpoints and kept a single direct "generate client" prompt for small specs. That cut cost by about 30% without hurting quality on the small ones.

    What you can do next

  • Add a system prompt to your current code-generation flow. Put language, "do not invent" rules, and output format (e.g. "single code block") there and leave the user message for the concrete task only.
  • Try one or two few-shot examples — keep each under ~15 lines. Match the kind of code you want (e.g. one GET handler, one POST handler) and run the same prompt a few times to see if style stabilises.
  • Use CoT only when it helps — e.g. "first list the endpoints and types, then write the client." Use it for larger or ambiguous specs; skip it for trivial single-function requests.
  • Set temperature to 0.0–0.2 for any path that needs repeatable code (CI, production, docs). Reserve higher values for interactive or exploratory use.
  • Measure — log token usage and success rate (e.g. "does the code compile?") before and after changing prompts or temperature so you know what actually improved.

    • If you only change one thing today: add a short system prompt that fixes the language and forbids invented APIs, and set temperature to 0.2. That alone will remove a lot of the randomness and off-spec code we saw in Sofia’s first version.
