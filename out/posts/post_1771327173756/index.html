API Timeouts and Deadlines: Why Defaults Bite Us

We run services that call LLM APIs, internal microservices, and third-party providers. For a long time we used library defaults for HTTP timeouts—or no timeout at all. That led to hung workers, cascading delays, and one incident where a single stuck call held a process open for hours. Here’s what we changed so timeouts and deadlines behave predictably and failures fail fast.

Why “no timeout” is a problem

If a downstream never responds, a request without a timeout can block a thread, a connection, or an async task indefinitely. With a fixed pool of workers, one stuck call can reduce effective capacity. If many calls hang (e.g. during an upstream outage), the whole service can stop making progress. Timeouts turn “hang forever” into “fail after N seconds” so you can retry, circuit-break, or return an error to the caller.

What we did wrong at first

  • Relying on default timeouts — Some HTTP clients have very long defaults (e.g. 2 minutes) or no timeout. We didn’t set them explicitly, so “slow” meant “slow for a long time.”
  • Same timeout for every call — We used one value (e.g. 30s) for all outbound requests. LLM calls often need 60–120s; health checks should fail in 2–5s. Using one size for all hid real latency and made health checks useless.
  • No deadline propagation — The front request had a 10s timeout, but each downstream call had its own 30s timeout. A chain of three services could still take 90s before the user saw a response.
  • Ignoring connect vs read — We only set a “total” timeout. In bad network conditions, we spent the whole budget on connection and never got to read. Separating connect timeout (short) from read timeout (longer) made failures detectable earlier.

    • We assumed “it usually returns quickly” was enough. It wasn’t.

    What we changed

    1. Explicit timeouts per use case

    We set timeouts in code, not from env defaults we never looked at. Health checks: 3s connect, 5s total. LLM calls: 10s connect, 120s read. Internal APIs: 5s connect, 30s read. We documented each in a small config table so new endpoints get a sane value by default.

    2. Connect vs read (and write)

    We use a client that supports separate connect and read timeouts. Connect is short (5–10s); read is longer and depends on the operation. That way a stuck TCP handshake fails fast and we don’t burn the whole budget before the first byte.

    3. Deadline propagation

    For request chains we pass a single deadline (e.g. “this request must finish by T”). Each service computes its own timeout as “time until T” and uses that for outbound calls. The user’s 10s limit is respected end-to-end instead of each hop getting a full 10s.

    4. Fail fast and log

    When we hit a timeout we log context: URL, attempt, timeout value, and whether it was connect or read. We don’t retry timeouts blindly—we use the same retry/backoff rules as for 5xx so we don’t amplify load on an already slow upstream.

    Observability

    We added metrics for timeout rate per client and per endpoint. That showed which upstreams were slow or flaky and where we needed to raise timeouts (or fix the upstream). Alerts on “timeout rate above X%” caught regressions before users did.

    Lessons learned

  • Never rely on “default” timeouts. Set connect and read (and write if needed) explicitly per use case.
  • Propagate deadlines in request chains so the top-level SLA is enforced end-to-end.
  • Use shorter connect timeouts so connection failures don’t consume the whole timeout budget.
  • Treat timeouts as failures: log them, metric them, and apply the same retry/backoff and circuit-breaking rules you use for other transient errors.
