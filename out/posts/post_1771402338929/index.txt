8:T298c,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Linux performance debugging toolkit: htop, perf, strace, bpftrace</h1></p><p class="text-slate-300 leading-relaxed mb-4">Your API responds in 2 seconds when it used to take 200 ms. Logs show nothing. You need to know <em>where</em> the time goes — kernel, userspace, I/O, or CPU. A small set of tools can get you from "something is slow" to "this syscall is the culprit" in minutes.</p><p class="text-slate-300 leading-relaxed mb-4">This post walks through a practical toolkit: <strong>htop</strong> for a quick picture, <strong>perf</strong> for CPU and call stacks, <strong>strace</strong> for syscall-level visibility, and <strong>bpftrace</strong> for custom probes. We keep it to real diagnosis stories and copy-paste commands.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why these tools?</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>htop</strong> — Process list, CPU/memory per process, tree view. You see <em>who</em> is busy.</li>
<li class="ml-4 list-disc text-slate-300"><strong>perf</strong> — Sampling profiler and event counters. You see <em>which functions</em> burn CPU.</li>
<li class="ml-4 list-disc text-slate-300"><strong>strace</strong> — Traces syscalls of a process. You see <em>what the kernel is doing</em> (files, network, locks).</li>
<li class="ml-4 list-disc text-slate-300"><strong>bpftrace</strong> — Scriptable BPF probes. You see <em>specific events</em> (e.g. slow syscalls, block I/O) without changing code.</li></p><p class="text-slate-300 leading-relaxed mb-4">Use them in that order when you don’t know the cause: htop → perf → strace or bpftrace when you need syscall or kernel detail.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">htop: who is using CPU and memory?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Install (Debian/Ubuntu): <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install htop</code>. Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">htop</code>.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Sort by CPU: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F6</code> → choose <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">PERCENT_CPU</code>.</li>
<li class="ml-4 list-disc text-slate-300">Tree view: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F5</code> — see parent/child processes.</li>
<li class="ml-4 list-disc text-slate-300">Filter: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">F4</code> and type a string (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">python</code>).</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> A Node.js API was slow. htop showed one process at 98% CPU. Tree view showed it was a worker spawned by the main process. That pointed us to that worker’s code path and led to profiling with perf.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">perf: where is CPU time spent?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Install: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install linux-tools-common linux-tools-$(uname -r)</code> (or equivalent). Then:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Record 10 seconds of CPU usage system-wide (needs root)</h1>
sudo perf record -g -a -- sleep 10</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Show report with call graph</h1>
sudo perf report -g 'graph,0.5,caller'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Focus on the "Overhead" column and the call stack. If you see a specific function (e.g. a regex or JSON parser) at the top, you’ve found a hotspot.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>User-space only for one process:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo perf record -g -p $(pgrep -f "node your-app") -- sleep 10
sudo perf report -g 'graph,0.5,caller'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> After htop showed the busy process, perf reported that 60% of samples were in a single function that did heavy string splitting in a loop. We replaced it with a streaming parser; latency dropped by an order of magnitude.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">strace: what syscalls is this process making?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Attach to a running process or launch a command under strace:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Attach to PID (may need -f to follow forks)</h1>
sudo strace -p <PID> -f -tt -T 2>&1 | tee strace.log</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Run a command and trace it</h1>
strace -tt -T -f -o trace.log -- your-command
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-tt</code> prints timestamps, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">-T</code> prints time spent per syscall. Look for syscalls with high time (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">poll</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">futex</code>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> A service was "CPU busy" in htop but perf showed little userspace CPU. strace revealed thousands of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">futex</code> calls per second with high <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">T</code> values — a lock contention issue. We reduced locking granularity and the load dropped.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> strace is slow and can change timing. Use it for short captures or on already-slow operations. For production, prefer perf or bpftrace when possible.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">bpftrace: custom probes and one-liners</h2></p><p class="text-slate-300 leading-relaxed mb-4">bpftrace lets you ask questions like "which syscalls are slow?" or "what is doing disk I/O?" without editing code. Install: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo apt install bpftrace</code> (or build from <a href="https://github.com/iovisor/bpftrace" class="text-cyan-400 hover:underline">bpftrace</a>).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Slow syscalls (e.g. > 10 ms):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo bpftrace -e 'tracepoint:syscalls:sys_enter_<em> { @start[probe] = nsecs; }
  tracepoint:syscalls:sys_exit_</em> /@start[probe]/
  { $d = (nsecs - @start[probe])/1000000; if ($d > 10) { @slow[probe] = hist($d); } }
  END { clear(@start); }'  # Run a few seconds, then Ctrl+C
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Count syscalls by name:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>sudo bpftrace -e 'tracepoint:syscalls:sys_enter_<em> { @[probe] = count(); }'
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Real case:</strong> We suspected a dependency was doing many small reads. A short bpftrace script counted <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">read</code>/<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">readv</code> by process; one auxiliary process had 10x more than others. We replaced that component and I/O dropped.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Gotcha:</strong> bpftrace needs kernel headers and a supported kernel. On minimal or locked-down systems, strace or perf may be the only option.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Takeaways</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300">Start with <strong>htop</strong> to see which process is busy.</li>
<li class="ml-4 list-decimal text-slate-300">Use <strong>perf</strong> to see which functions use CPU; fix or optimize those.</li>
<li class="ml-4 list-decimal text-slate-300">Use <strong>strace</strong> when you need to see syscalls (I/O, locks, network); keep traces short.</li>
<li class="ml-4 list-decimal text-slate-300">Use <strong>bpftrace</strong> for custom, low-overhead probes when your kernel supports it.</li></p><p class="text-slate-300 leading-relaxed mb-4">One concrete step: the next time something is "slow", run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">htop</code>, sort by CPU, then run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sudo perf record -g -p <PID> -- sleep 10</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">perf report</code>. You’ll often get from "slow" to "this function or this syscall" in under five minutes.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
