Linux performance debugging toolkit: htop, perf, strace, bpftrace

Your API responds in 2 seconds when it used to take 200 ms. Logs show nothing. You need to know where the time goes — kernel, userspace, I/O, or CPU. A small set of tools can get you from "something is slow" to "this syscall is the culprit" in minutes.

This post walks through a practical toolkit: htop for a quick picture, perf for CPU and call stacks, strace for syscall-level visibility, and bpftrace for custom probes. We keep it to real diagnosis stories and copy-paste commands.

Why these tools?

  • htop — Process list, CPU/memory per process, tree view. You see who is busy.
  • perf — Sampling profiler and event counters. You see which functions burn CPU.
  • strace — Traces syscalls of a process. You see what the kernel is doing (files, network, locks).
  • bpftrace — Scriptable BPF probes. You see specific events (e.g. slow syscalls, block I/O) without changing code.

    • Use them in that order when you don’t know the cause: htop → perf → strace or bpftrace when you need syscall or kernel detail.

    htop: who is using CPU and memory?

    Install (Debian/Ubuntu): sudo apt install htop. Run htop.

  • Sort by CPU: F6 → choose PERCENT_CPU.
  • Tree view: F5 — see parent/child processes.
  • Filter: F4 and type a string (e.g. node or python).

    • Real case: A Node.js API was slow. htop showed one process at 98% CPU. Tree view showed it was a worker spawned by the main process. That pointed us to that worker’s code path and led to profiling with perf.

    perf: where is CPU time spent?

    Install: sudo apt install linux-tools-common linux-tools-$(uname -r) (or equivalent). Then:

    Record 10 seconds of CPU usage system-wide (needs root)
    
sudo perf record -g -a -- sleep 10
    Show report with call graph
    
sudo perf report -g 'graph,0.5,caller'

    Focus on the "Overhead" column and the call stack. If you see a specific function (e.g. a regex or JSON parser) at the top, you’ve found a hotspot.

    User-space only for one process:

    sudo perf record -g -p $(pgrep -f "node your-app") -- sleep 10
sudo perf report -g 'graph,0.5,caller'

    Real case: After htop showed the busy process, perf reported that 60% of samples were in a single function that did heavy string splitting in a loop. We replaced it with a streaming parser; latency dropped by an order of magnitude.

    strace: what syscalls is this process making?

    Attach to a running process or launch a command under strace:

    Attach to PID (may need -f to follow forks)
    
sudo strace -p  -f -tt -T 2>&1 | tee strace.log
    Run a command and trace it
    
strace -tt -T -f -o trace.log -- your-command

    -tt prints timestamps, -T prints time spent per syscall. Look for syscalls with high time (e.g. read, poll, futex).

    Real case: A service was "CPU busy" in htop but perf showed little userspace CPU. strace revealed thousands of futex calls per second with high T values — a lock contention issue. We reduced locking granularity and the load dropped.

    Gotcha: strace is slow and can change timing. Use it for short captures or on already-slow operations. For production, prefer perf or bpftrace when possible.

    bpftrace: custom probes and one-liners

    bpftrace lets you ask questions like "which syscalls are slow?" or "what is doing disk I/O?" without editing code. Install: sudo apt install bpftrace (or build from bpftrace).

    Slow syscalls (e.g. > 10 ms):

    sudo bpftrace -e 'tracepoint:syscalls:sys_enter_ { @start[probe] = nsecs; }
  tracepoint:syscalls:sys_exit_ /@start[probe]/
  { $d = (nsecs - @start[probe])/1000000; if ($d > 10) { @slow[probe] = hist($d); } }
  END { clear(@start); }'  # Run a few seconds, then Ctrl+C

    Count syscalls by name:

    sudo bpftrace -e 'tracepoint:syscalls:sys_enter_ { @[probe] = count(); }'

    Real case: We suspected a dependency was doing many small reads. A short bpftrace script counted read/readv by process; one auxiliary process had 10x more than others. We replaced that component and I/O dropped.

    Gotcha: bpftrace needs kernel headers and a supported kernel. On minimal or locked-down systems, strace or perf may be the only option.

    Takeaways

  • Start with htop to see which process is busy.
  • Use perf to see which functions use CPU; fix or optimize those.
  • Use strace when you need to see syscalls (I/O, locks, network); keep traces short.
  • Use bpftrace for custom, low-overhead probes when your kernel supports it.

    • One concrete step: the next time something is "slow", run htop, sort by CPU, then run sudo perf record -g -p -- sleep 10 and perf report. You’ll often get from "slow" to "this function or this syscall" in under five minutes.
