System design for caching strategies: a comparative analysis of Redis and Memcached

Chen's team needed a shared cache for session data and API response warming. They had two options on the table: Redis and Memcached. The default answer in many shops is "use Redis," but Memcached still powers large-scale object caches at companies like Facebook and Wikipedia. The right choice depends on what you're caching, how you need to query it, and whether you care about persistence or multi-datatype operations.

This post compares Redis and Memcached from a system-design angle: data model, persistence, clustering, and operational trade-offs. We include small code examples and a decision guide so you can pick (or mix) them with confidence.

Why the choice still matters

Both are in-memory key-value stores with sub-millisecond latency. The difference shows up when you need more than "get/set by key": structures (lists, sets, sorted sets), persistence, replication, or very high key counts with minimal memory overhead. Picking the wrong one leads to workarounds (e.g. serializing JSON into Memcached strings everywhere) or over-provisioning (running Redis when a simple cache would do).

Data model and API surface

Memcached is a pure key-value cache. Keys and values are strings (or blobs). You get get, set, delete, increment/decrement, and a few helpers. No nested structures. No TTL per key in the original design; many implementations support expiration. It's easy to reason about and to implement clients.

Redis offers strings, hashes, lists, sets, sorted sets, bitmaps, and more. You can do range queries, blocking pops, pub/sub, and Lua scripts. TTL is built in. The API is larger and more flexible but also more to learn and to misuse.

For simple "cache this blob under this key" workloads, both work. When you need to cache structured data and query by field or score, Redis wins without a layer of serialization on your side.

Example: caching a user session

Memcached — value is one serialized blob:

// memcached-session.ts — session as a single serialized value
import { Memcached } from "memcached"; // npm: memcached
const client = new Memcached("localhost:11211");
interface UserSession {
  userId: string;
  name: string;
  roles: string[];
  lastActive: number;
}
async function setSession(sessionId: string, session: UserSession, ttlSeconds = 3600) {
  await client.set(sessionId, JSON.stringify(session), ttlSeconds);
}
async function getSession(sessionId: string): Promise {
  const blob = await client.get(sessionId);
  return blob ? JSON.parse(blob) : null;
}

Redis — same idea, or you can use a hash and update single fields:

// redis-session.ts — session as hash: field-level read/write
import Redis from "ioredis";
const redis = new Redis("localhost:6379");
async function setSession(sessionId: string, session: UserSession, ttlSeconds = 3600) {
  const key = session:${sessionId};
  await redis.hset(key, {
    userId: session.userId,
    name: session.name,
    roles: JSON.stringify(session.roles),
    lastActive: String(session.lastActive),
  });
  await redis.expire(key, ttlSeconds);
}
async function getSession(sessionId: string): Promise {
  const key = session:${sessionId};
  const raw = await redis.hgetall(key);
  if (!raw || !raw.userId) return null;
  return {
    userId: raw.userId,
    name: raw.name,
    roles: JSON.parse(raw.roles ?? "[]"),
    lastActive: Number(raw.lastActive),
  };
}
// Update only lastActive without reading the whole session
async function touchSession(sessionId: string) {
  await redis.hset(session:${sessionId}, "lastActive", String(Date.now()));
}

With Redis you can touch a single field; with Memcached you typically read, modify, and write the whole blob (or maintain a separate key for last-active).

Persistence and durability

Memcached is a cache only. Data is not written to disk. Restart or crash means loss. That's by design: it keeps the implementation simple and predictable. Use it when cache loss is acceptable (e.g. recompute or refill from DB).

Redis can run cache-only (no persistence) or with RDB snapshots and/or AOF (append-only file). If you need "warm" restarts or a small amount of durability for cached data, Redis can do it. For true durability you still use a primary database; Redis persistence is a trade-off between performance and recovery time.

Design takeaway: If your system assumes "cache can disappear anytime," Memcached is a natural fit. If you want to reduce refill load after restarts, Redis with RDB or AOF is an option.

Clustering and horizontal scaling

Memcached is typically scaled by adding nodes. Clients (or a proxy like mcrouter) hash keys to nodes. There is no built-in replication; each key lives on one node. Losing that node loses those keys. Scaling out is straightforward: add nodes and let the hashing spread keys.

Redis has several modes:

  • Single instance — one server, optional persistence.
  • Redis Sentinel — high availability with automatic failover of a primary/replica set.
  • Redis Cluster — sharding across many nodes with hash slots; replication per shard.

    • Cluster mode is more complex to operate than a Memcached pool. If you only need a distributed cache with no replication and no persistence, Memcached's model is simpler. If you need replication or a single logical namespace with structures and scripts, Redis Cluster or Sentinel fits better.

    When to choose which

    | Need | Prefer | |------|--------| | Simple key-value cache, loss acceptable | Memcached or Redis (either works) | | Structures (lists, sets, sorted sets), pub/sub, scripts | Redis | | Minimal memory per key, huge key count | Memcached (often lower overhead) | | Warm restart / some durability for cache | Redis with RDB/AOF | | Replication and failover | Redis (Sentinel/Cluster) | | Easiest "add more nodes" scaling, no replication | Memcached | | Atomic increments, simple counters | Both (Redis has more options) |

    Gotchas and lessons learned

  • Treat both as cache. Don't store the only copy of critical data in Redis or Memcached. Design for invalidation and refill from a source of truth (e.g. DB).

  • Key and value size: Memcached has practical limits on key length (e.g. 250 bytes) and value size (often 1 MB default). Redis allows much larger values; large values increase latency and memory fragmentation. Keep values small when possible.

  • Eviction: Both support eviction policies (LRU, etc.). Configure a max memory and an eviction policy so that under pressure the cache degrades gracefully instead of OOM-ing.

  • Redis single-threaded core: Redis uses one thread for command execution. One slow command (e.g. a big KEYS or a heavy Lua script) blocks others. Use SCAN instead of KEYS, and keep scripts short and fast. Memcached is multi-threaded for request handling.

  • Mixing cache and "database" in Redis: Redis is flexible enough to be used as a small DB (e.g. leaderboards, queues). If you do that, plan for persistence, backups, and failover. Don't mix "disposable cache" and "critical state" on the same instance without a clear story.

    • One thing to do next

    Decide whether your workload is "plain key-value cache, refill from DB is fine" or "structures, partial updates, or warm restart matter." For the first, try Memcached (or Redis with persistence turned off) and measure memory and latency. For the second, use Redis and lock down eviction and persistence so behavior under load and after restarts is predictable. If you already have one of them in production, prefer it unless you have a concrete reason to introduce the other — operational simplicity usually beats theoretical fit.
