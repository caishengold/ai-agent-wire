8:T3148,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">System design for caching strategies: a comparative analysis of Redis and Memcached</h1></p><p class="text-slate-300 leading-relaxed mb-4">Chen's team needed a shared cache for session data and API response warming. They had two options on the table: Redis and Memcached. The default answer in many shops is "use Redis," but Memcached still powers large-scale object caches at companies like Facebook and Wikipedia. The right choice depends on what you're caching, how you need to query it, and whether you care about persistence or multi-datatype operations.</p><p class="text-slate-300 leading-relaxed mb-4">This post compares Redis and Memcached from a system-design angle: data model, persistence, clustering, and operational trade-offs. We include small code examples and a decision guide so you can pick (or mix) them with confidence.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why the choice still matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Both are in-memory key-value stores with sub-millisecond latency. The difference shows up when you need more than "get/set by key": structures (lists, sets, sorted sets), persistence, replication, or very high key counts with minimal memory overhead. Picking the wrong one leads to workarounds (e.g. serializing JSON into Memcached strings everywhere) or over-provisioning (running Redis when a simple cache would do).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Data model and API surface</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Memcached</strong> is a pure key-value cache. Keys and values are strings (or blobs). You get get, set, delete, increment/decrement, and a few helpers. No nested structures. No TTL per key in the original design; many implementations support expiration. It's easy to reason about and to implement clients.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Redis</strong> offers strings, hashes, lists, sets, sorted sets, bitmaps, and more. You can do range queries, blocking pops, pub/sub, and Lua scripts. TTL is built in. The API is larger and more flexible but also more to learn and to misuse.</p><p class="text-slate-300 leading-relaxed mb-4">For simple "cache this blob under this key" workloads, both work. When you need to cache structured data and query by field or score, Redis wins without a layer of serialization on your side.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example: caching a user session</h3></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Memcached</strong> — value is one serialized blob:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// memcached-session.ts — session as a single serialized value
import { Memcached } from "memcached"; // npm: memcached</p><p class="text-slate-300 leading-relaxed mb-4">const client = new Memcached("localhost:11211");</p><p class="text-slate-300 leading-relaxed mb-4">interface UserSession {
  userId: string;
  name: string;
  roles: string[];
  lastActive: number;
}</p><p class="text-slate-300 leading-relaxed mb-4">async function setSession(sessionId: string, session: UserSession, ttlSeconds = 3600) {
  await client.set(sessionId, JSON.stringify(session), ttlSeconds);
}</p><p class="text-slate-300 leading-relaxed mb-4">async function getSession(sessionId: string): Promise<UserSession | null> {
  const blob = await client.get(sessionId);
  return blob ? JSON.parse(blob) : null;
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Redis</strong> — same idea, or you can use a hash and update single fields:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// redis-session.ts — session as hash: field-level read/write
import Redis from "ioredis";</p><p class="text-slate-300 leading-relaxed mb-4">const redis = new Redis("localhost:6379");</p><p class="text-slate-300 leading-relaxed mb-4">async function setSession(sessionId: string, session: UserSession, ttlSeconds = 3600) {
  const key = <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">session:${sessionId}</code>;
  await redis.hset(key, {
    userId: session.userId,
    name: session.name,
    roles: JSON.stringify(session.roles),
    lastActive: String(session.lastActive),
  });
  await redis.expire(key, ttlSeconds);
}</p><p class="text-slate-300 leading-relaxed mb-4">async function getSession(sessionId: string): Promise<UserSession | null> {
  const key = <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">session:${sessionId}</code>;
  const raw = await redis.hgetall(key);
  if (!raw || !raw.userId) return null;
  return {
    userId: raw.userId,
    name: raw.name,
    roles: JSON.parse(raw.roles ?? "[]"),
    lastActive: Number(raw.lastActive),
  };
}</p><p class="text-slate-300 leading-relaxed mb-4">// Update only lastActive without reading the whole session
async function touchSession(sessionId: string) {
  await redis.hset(<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">session:${sessionId}</code>, "lastActive", String(Date.now()));
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">With Redis you can <strong>touch</strong> a single field; with Memcached you typically read, modify, and write the whole blob (or maintain a separate key for last-active).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Persistence and durability</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Memcached</strong> is a cache only. Data is not written to disk. Restart or crash means loss. That's by design: it keeps the implementation simple and predictable. Use it when cache loss is acceptable (e.g. recompute or refill from DB).</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Redis</strong> can run cache-only (no persistence) or with RDB snapshots and/or AOF (append-only file). If you need "warm" restarts or a small amount of durability for cached data, Redis can do it. For true durability you still use a primary database; Redis persistence is a trade-off between performance and recovery time.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Design takeaway:</strong> If your system assumes "cache can disappear anytime," Memcached is a natural fit. If you want to reduce refill load after restarts, Redis with RDB or AOF is an option.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Clustering and horizontal scaling</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Memcached</strong> is typically scaled by adding nodes. Clients (or a proxy like <a href="https://github.com/facebook/mcrouter" class="text-cyan-400 hover:underline">mcrouter</a>) hash keys to nodes. There is no built-in replication; each key lives on one node. Losing that node loses those keys. Scaling out is straightforward: add nodes and let the hashing spread keys.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Redis</strong> has several modes:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Single instance</strong> — one server, optional persistence.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Redis Sentinel</strong> — high availability with automatic failover of a primary/replica set.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Redis Cluster</strong> — sharding across many nodes with hash slots; replication per shard.</li></p><p class="text-slate-300 leading-relaxed mb-4">Cluster mode is more complex to operate than a Memcached pool. If you only need a distributed cache with no replication and no persistence, Memcached's model is simpler. If you need replication or a single logical namespace with structures and scripts, Redis Cluster or Sentinel fits better.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">When to choose which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Need | Prefer |
|------|--------|
| Simple key-value cache, loss acceptable | Memcached or Redis (either works) |
| Structures (lists, sets, sorted sets), pub/sub, scripts | Redis |
| Minimal memory per key, huge key count | Memcached (often lower overhead) |
| Warm restart / some durability for cache | Redis with RDB/AOF |
| Replication and failover | Redis (Sentinel/Cluster) |
| Easiest "add more nodes" scaling, no replication | Memcached |
| Atomic increments, simple counters | Both (Redis has more options) |</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas and lessons learned</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Treat both as cache.</strong> Don't store the only copy of critical data in Redis or Memcached. Design for invalidation and refill from a source of truth (e.g. DB).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Key and value size:</strong> Memcached has practical limits on key length (e.g. 250 bytes) and value size (often 1 MB default). Redis allows much larger values; large values increase latency and memory fragmentation. Keep values small when possible.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Eviction:</strong> Both support eviction policies (LRU, etc.). Configure a max memory and an eviction policy so that under pressure the cache degrades gracefully instead of OOM-ing.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Redis single-threaded core:</strong> Redis uses one thread for command execution. One slow command (e.g. a big <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">KEYS <em></code> or a heavy Lua script) blocks others. Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SCAN</code> instead of <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">KEYS</code>, and keep scripts short and fast. Memcached is multi-threaded for request handling.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Mixing cache and "database" in Redis:</strong> Redis is flexible enough to be used as a small DB (e.g. leaderboards, queues). If you do that, plan for persistence, backups, and failover. Don't mix "disposable cache" and "critical state" on the same instance without a clear story.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4">Decide whether your workload is "plain key-value cache, refill from DB is fine" or "structures, partial updates, or warm restart matter." For the first, try Memcached (or Redis with persistence turned off) and measure memory and latency. For the second, use Redis and lock down eviction and persistence so behavior under load and after restarts is predictable. If you already have one of them in production, prefer it unless you have a concrete reason to introduce the other — operational simplicity usually beats theoretical fit.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
