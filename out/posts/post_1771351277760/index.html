Container security checklist — image scanning, rootless, seccomp, and real CVEs

Sofia’s team pushed a new API image to production on 2026-01-15. The image was based on an old Debian slim tag they’d used for months. A week later, a scanner in a different pipeline flagged the same image: it contained a critical vulnerability in libcurl (CVE-2023-38545) that allowed header injection. Nobody had run that scanner on the API service’s build. The fix wasn’t hard — bump the base image and redeploy — but the incident made them tighten image scanning, move to rootless containers where possible, and lock down syscalls with seccomp. Here’s a concrete checklist you can run against your own stack.

Why this checklist exists

Containers share the host kernel. A process that escapes the container can still abuse that kernel if you don’t constrain it. The checklist below focuses on four areas: what’s inside the image (scanning), who runs as root (rootless), which syscalls are allowed (seccomp), and what actually bit people (real CVE examples). We’re not covering network policies or secrets management here; those are separate layers.

1. Image scanning — catch known CVEs before deploy

If you never scan images, you’re relying on luck. Trivy is free, runs in CI and locally, and outputs machine-readable results. Run it against your built image (or Dockerfile) and fail the build on high/critical.

Example: scan a built image with Trivy (CLI)

Install Trivy (Linux example; see https://github.com/aquasecurity/trivy for other OS)

curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b /usr/local/bin
Build an image (use your own Dockerfile in practice)

docker build -t myapp:test -f - . <<'DOCKERFILE'
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends curl ca-certificates && rm -rf /var/lib/apt/lists/
COPY . /app
WORKDIR /app
CMD ["/bin/bash", "-c", "echo ok"]
DOCKERFILE
Scan and exit 1 if any HIGH or CRITICAL vulns (good for CI)

trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:test

Example output (abbreviated):

myapp:test (debian 12.5)
Total: 42 (HIGH: 5, CRITICAL: 0)
...

If you allow CRITICAL only, use --exit-code 1 --severity CRITICAL. In CI, run this after docker build and before push.

Example: scan a Dockerfile without building (faster for base-only checks)

Dockerfile only — checks base image and RUN instructions for known packages

trivy config --exit-code 1 --severity HIGH,CRITICAL .

This uses the Dockerfile in the current directory. It won’t see vulnerabilities introduced by later COPY or custom binaries; for that you need a full image scan.

2. Rootless containers — limit blast radius

Containers running as root (UID 0) inside the namespace can still do a lot of damage if they escape or if the runtime is compromised. Rootless mode runs the entire container engine (and the container’s init process) as a non-root user on the host, so even a breakout has no root on the host.

Docker rootless (install and run a container)

Install rootless Docker (Ubuntu/Debian: rootlesskit + dockerd-rootless)


See https://docs.docker.com/engine/security/rootless/

curl -fsSL https://get.docker.com/rootless | sh
Add to PATH (example; your install may put it under ~/bin)

export PATH=/home/raj/bin:$PATH
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
Run a container — the daemon and the container process are not host root

docker run --rm alpine id

uid=0(root) gid=0(root) — inside the container you're still root,


but the process on the host runs as raj's UID

On the host, ps will show the container process owned by raj, not root. That’s the point: even if something escapes the namespace, it doesn’t have host root.

Podman is rootless by default when you run as a normal user (podman run ...). No extra install step. Use it when you want rootless without a separate rootless Docker setup.

3. Seccomp profiles — restrict syscalls

Containers can call any syscall the kernel allows. A seccomp profile blocks or allows specific syscalls so that, for example, a compromised process can’t call unshare or mount to break out. Docker ships a default profile that blocks a set of dangerous syscalls; you can tighten it further with a custom profile.

Run with Docker’s default seccomp profile (explicit)

Default profile is applied automatically; we're just showing the flag

docker run --rm --security-opt seccomp=default alpine sh -c "echo ok"

ok

Run with a custom profile that blocks a few more syscalls

Save this as profile.json:

{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_AARCH64"],
  "syscalls": [
    { "names": ["read", "write", "openat", "close", "fstat", "mmap", "mprotect", "munmap", "brk", "rt_sigreturn", "ioctl", "pread64", "pwrite64", "readv", "writev", "execve", "arch_prctl", "set_tid_address", "set_robust_list", "prlimit64", "getpid", "gettid", "gettid", "exit_group"], "action": "SCMP_ACT_ALLOW" }
  ]
}

Then:

docker run --rm --security-opt seccomp=profile.json alpine sh -c "echo ok"

ok
Something that needs a blocked syscall will fail

docker run --rm --security-opt seccomp=profile.json alpine uname

(fails with Operation not permitted or similar, depending on syscall)

In production you’d derive the profile from the actual syscalls your app needs (e.g. with strace or libseccomp-based tools) and allow only those. The example above is deliberately minimal to show the mechanic.

4. Real CVE examples — why scanning and hardening matter

| CVE | Component | What it is | Why it matters for containers | |-----|------------|------------|-------------------------------| | CVE-2019-5736 | runc | Container escape via overwriting the host runc binary from inside the container. | If an attacker can execute code in the container and the container runs as root, they can gain root on the host. Patching runc and reducing container privileges (rootless, read-only rootfs) limits impact. | | CVE-2022-0847 (Dirty Pipe) | Linux kernel | Arbitrary file overwrite in the kernel; can overwrite suid binaries. | Affects any process on the host. Mitigations: keep host kernel updated; run containers rootless and with a tight seccomp profile that blocks the involved syscalls where possible. | | CVE-2023-38545 | libcurl | Header injection in the HTTP client. | If your image ships an old curl/libcurl, an attacker can sometimes inject headers. Image scanning catches the vulnerable version; bumping the base image or the package fixes it. | | CVE-2024-21626 | runc | Container escape via leaked file descriptor to the host’s runc. | Process inside the container can access the host runc binary. Again: patch runc; run rootless and with minimal capabilities. |

Takeaway: image scanning finds known CVEs in userspace (e.g. libcurl, OpenSSL). Rootless + seccomp + updated runtime/kernel reduce the impact of runtime and kernel issues (runc, Dirty Pipe).

Comparison: approaches to container hardening

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | Image scanning only | Catches known CVEs in packages, easy to add to CI. | Doesn’t stop runtime escapes or zero-days. | Every build; minimum baseline. | | Rootless containers | No host root for container processes; limits escape impact. | Some features (e.g. certain networking, some storage drivers) may not work. | Default for new workloads where supported. | | Default seccomp | No config; blocks many dangerous syscalls. | May break legacy apps that rely on odd syscalls. | Default for most images. | | Custom seccomp | Smallest syscall surface. | Requires profiling and testing; can break on kernel/runtime updates. | After you’ve validated your app’s syscalls. | | Read-only rootfs + non-root user | No writes to container FS; process isn’t root inside. | App must be written to use writable volumes where needed. | Combine with the above for sensitive services. |

Use scanning + rootless (or at least non-root user in image) + default seccomp as a baseline. Add custom seccomp and read-only rootfs where you need maximum lock-down.

What went wrong (lessons learned)

  • Assuming “we use a slim image” is enough. Omar’s team used node:18-slim for two years without scanning. A dependency in the Node image had a high CVE; they only found out when a customer’s audit required a report. They added Trivy to CI with --exit-code 1 --severity HIGH,CRITICAL and had to fix 3 images the first run. One of them required upgrading the base to node:20-slim and fixing a small API change. Took a day, not a week, but it could have been avoided.
  • Seccomp too strict too soon. We applied a custom seccomp profile to a Go service that had never been profiled. In staging it was fine; in production under load it started failing with “Operation not permitted” in TLS handshakes. The profile was missing a syscall used by the crypto library. We reverted to the default profile, then used strace to capture the real syscall set and rebuilt the profile. Lesson: test custom seccomp under realistic load and have a quick rollback.
  • Rootless Docker on an older host. On a RHEL 8 host, rootless Docker failed with a permission error on a specific cgroup path. The fix was to upgrade the kernel and the rootless toolkit. We now check the rootless Docker docs for the host’s kernel and package requirements before rolling rootless out to production.

    • Actionable next steps

  • Add image scanning to CI today. Run Trivy (or your scanner) on every built image; fail the build on CRITICAL, and optionally on HIGH. Fix or suppress with justification.
  • List images that still run as root. For each, check whether the process inside can be switched to a non-root user (e.g. in the Dockerfile) and whether the daemon can run rootless. Plan one pilot service for rootless.
  • Confirm default seccomp is on. With Docker, don’t use --security-opt seccomp=unconfined in production. If you already use a custom profile, re-test it after base image or runtime upgrades.
  • Pin and review base images. Use digest-pinned base images (e.g. debian@sha256:...) and re-scan when you bump the digest. Schedule a quarterly review of HIGH/CRITICAL for all production images.
  • Document one “security runbook” for your main app. Include: how to run a Trivy scan locally, where the seccomp profile lives (if any), and what to do when a CVE is reported in your base image (who bumps, who deploys, how long you have).

    • Summary: Use image scanning to catch known CVEs, run rootless where you can, keep default seccomp (or a tested custom one), and learn from real CVEs so your checklist matches what actually happens in production.
