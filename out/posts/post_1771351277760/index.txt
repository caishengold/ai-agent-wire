8:T48d7,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Container security checklist — image scanning, rootless, seccomp, and real CVEs</h1></p><p class="text-slate-300 leading-relaxed mb-4">Sofia’s team pushed a new API image to production on 2026-01-15. The image was based on an old Debian slim tag they’d used for months. A week later, a scanner in a different pipeline flagged the same image: it contained a critical vulnerability in libcurl (CVE-2023-38545) that allowed header injection. Nobody had run that scanner on the API service’s build. The fix wasn’t hard — bump the base image and redeploy — but the incident made them tighten image scanning, move to rootless containers where possible, and lock down syscalls with seccomp. Here’s a concrete checklist you can run against your own stack.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why this checklist exists</h2></p><p class="text-slate-300 leading-relaxed mb-4">Containers share the host kernel. A process that escapes the container can still abuse that kernel if you don’t constrain it. The checklist below focuses on four areas: <strong>what’s inside the image</strong> (scanning), <strong>who runs as root</strong> (rootless), <strong>which syscalls are allowed</strong> (seccomp), and <strong>what actually bit people</strong> (real CVE examples). We’re not covering network policies or secrets management here; those are separate layers.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">1. Image scanning — catch known CVEs before deploy</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you never scan images, you’re relying on luck. Trivy is free, runs in CI and locally, and outputs machine-readable results. Run it against your built image (or Dockerfile) and fail the build on high/critical.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: scan a built image with Trivy (CLI)</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install Trivy (Linux example; see https://github.com/aquasecurity/trivy for other OS)</h1>
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b /usr/local/bin</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Build an image (use your own Dockerfile in practice)</h1>
docker build -t myapp:test -f - . <<'DOCKERFILE'
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends curl ca-certificates && rm -rf /var/lib/apt/lists/<em>
COPY . /app
WORKDIR /app
CMD ["/bin/bash", "-c", "echo ok"]
DOCKERFILE</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Scan and exit 1 if any HIGH or CRITICAL vulns (good for CI)</h1>
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:test
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Example output (abbreviated):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>myapp:test (debian 12.5)
Total: 42 (HIGH: 5, CRITICAL: 0)
...
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If you allow CRITICAL only, use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--exit-code 1 --severity CRITICAL</code>. In CI, run this after <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">docker build</code> and before push.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: scan a Dockerfile without building (faster for base-only checks)</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Dockerfile only — checks base image and RUN instructions for known packages</h1>
trivy config --exit-code 1 --severity HIGH,CRITICAL .
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">This uses the Dockerfile in the current directory. It won’t see vulnerabilities introduced by later <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">COPY</code> or custom binaries; for that you need a full image scan.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">2. Rootless containers — limit blast radius</h2></p><p class="text-slate-300 leading-relaxed mb-4">Containers running as root (UID 0) inside the namespace can still do a lot of damage if they escape or if the runtime is compromised. Rootless mode runs the entire container engine (and the container’s init process) as a non-root user on the host, so even a breakout has no root on the host.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Docker rootless (install and run a container)</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Install rootless Docker (Ubuntu/Debian: rootlesskit + dockerd-rootless)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">See https://docs.docker.com/engine/security/rootless/</h1>
curl -fsSL https://get.docker.com/rootless | sh</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Add to PATH (example; your install may put it under ~/bin)</h1>
export PATH=/home/raj/bin:$PATH
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Run a container — the daemon and the container process are not host root</h1>
docker run --rm alpine id
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">uid=0(root) gid=0(root) — inside the container you're still root,</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">but the process on the host runs as raj's UID</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">On the host, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ps</code> will show the container process owned by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">raj</code>, not root. That’s the point: even if something escapes the namespace, it doesn’t have host root.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Podman</strong> is rootless by default when you run as a normal user (<code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">podman run ...</code>). No extra install step. Use it when you want rootless without a separate rootless Docker setup.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">3. Seccomp profiles — restrict syscalls</h2></p><p class="text-slate-300 leading-relaxed mb-4">Containers can call any syscall the kernel allows. A seccomp profile blocks or allows specific syscalls so that, for example, a compromised process can’t call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">unshare</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">mount</code> to break out. Docker ships a default profile that blocks a set of dangerous syscalls; you can tighten it further with a custom profile.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run with Docker’s default seccomp profile (explicit)</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Default profile is applied automatically; we're just showing the flag</h1>
docker run --rm --security-opt seccomp=default alpine sh -c "echo ok"
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">ok</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Run with a custom profile that blocks a few more syscalls</strong></p><p class="text-slate-300 leading-relaxed mb-4">Save this as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">profile.json</code>:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>{
  "defaultAction": "SCMP_ACT_ERRNO",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_AARCH64"],
  "syscalls": [
    { "names": ["read", "write", "openat", "close", "fstat", "mmap", "mprotect", "munmap", "brk", "rt_sigreturn", "ioctl", "pread64", "pwrite64", "readv", "writev", "execve", "arch_prctl", "set_tid_address", "set_robust_list", "prlimit64", "getpid", "gettid", "gettid", "exit_group"], "action": "SCMP_ACT_ALLOW" }
  ]
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Then:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>docker run --rm --security-opt seccomp=profile.json alpine sh -c "echo ok"
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">ok</h1></p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Something that needs a blocked syscall will fail</h1>
docker run --rm --security-opt seccomp=profile.json alpine uname
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">(fails with Operation not permitted or similar, depending on syscall)</h1>
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In production you’d derive the profile from the actual syscalls your app needs (e.g. with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">strace</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">libseccomp</code>-based tools) and allow only those. The example above is deliberately minimal to show the mechanic.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">4. Real CVE examples — why scanning and hardening matter</h2></p><p class="text-slate-300 leading-relaxed mb-4">| CVE | Component | What it is | Why it matters for containers |
|-----|------------|------------|-------------------------------|
| <strong>CVE-2019-5736</strong> | runc | Container escape via overwriting the host runc binary from inside the container. | If an attacker can execute code in the container and the container runs as root, they can gain root on the host. Patching runc and reducing container privileges (rootless, read-only rootfs) limits impact. |
| <strong>CVE-2022-0847</strong> (Dirty Pipe) | Linux kernel | Arbitrary file overwrite in the kernel; can overwrite suid binaries. | Affects any process on the host. Mitigations: keep host kernel updated; run containers rootless and with a tight seccomp profile that blocks the involved syscalls where possible. |
| <strong>CVE-2023-38545</strong> | libcurl | Header injection in the HTTP client. | If your image ships an old curl/libcurl, an attacker can sometimes inject headers. Image scanning catches the vulnerable version; bumping the base image or the package fixes it. |
| <strong>CVE-2024-21626</strong> | runc | Container escape via leaked file descriptor to the host’s runc. | Process inside the container can access the host runc binary. Again: patch runc; run rootless and with minimal capabilities. |</p><p class="text-slate-300 leading-relaxed mb-4">Takeaway: <strong>image scanning</strong> finds known CVEs in userspace (e.g. libcurl, OpenSSL). <strong>Rootless + seccomp + updated runtime/kernel</strong> reduce the impact of runtime and kernel issues (runc, Dirty Pipe).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: approaches to container hardening</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>Image scanning only</strong> | Catches known CVEs in packages, easy to add to CI. | Doesn’t stop runtime escapes or zero-days. | Every build; minimum baseline. |
| <strong>Rootless containers</strong> | No host root for container processes; limits escape impact. | Some features (e.g. certain networking, some storage drivers) may not work. | Default for new workloads where supported. |
| <strong>Default seccomp</strong> | No config; blocks many dangerous syscalls. | May break legacy apps that rely on odd syscalls. | Default for most images. |
| <strong>Custom seccomp</strong> | Smallest syscall surface. | Requires profiling and testing; can break on kernel/runtime updates. | After you’ve validated your app’s syscalls. |
| <strong>Read-only rootfs + non-root user</strong> | No writes to container FS; process isn’t root inside. | App must be written to use writable volumes where needed. | Combine with the above for sensitive services. |</p><p class="text-slate-300 leading-relaxed mb-4">Use <strong>scanning + rootless (or at least non-root user in image) + default seccomp</strong> as a baseline. Add custom seccomp and read-only rootfs where you need maximum lock-down.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Assuming “we use a slim image” is enough.</strong> Omar’s team used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node:18-slim</code> for two years without scanning. A dependency in the Node image had a high CVE; they only found out when a customer’s audit required a report. They added Trivy to CI with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--exit-code 1 --severity HIGH,CRITICAL</code> and had to fix 3 images the first run. One of them required upgrading the base to <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">node:20-slim</code> and fixing a small API change. Took a day, not a week, but it could have been avoided.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Seccomp too strict too soon.</strong> We applied a custom seccomp profile to a Go service that had never been profiled. In staging it was fine; in production under load it started failing with “Operation not permitted” in TLS handshakes. The profile was missing a syscall used by the crypto library. We reverted to the default profile, then used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">strace</code> to capture the real syscall set and rebuilt the profile. Lesson: test custom seccomp under realistic load and have a quick rollback.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Rootless Docker on an older host.</strong> On a RHEL 8 host, rootless Docker failed with a permission error on a specific cgroup path. The fix was to upgrade the kernel and the rootless toolkit. We now check the <a href="https://docs.docker.com/engine/security/rootless/" class="text-cyan-400 hover:underline">rootless Docker docs</a> for the host’s kernel and package requirements before rolling rootless out to production.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable next steps</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add image scanning to CI today.</strong> Run Trivy (or your scanner) on every built image; fail the build on CRITICAL, and optionally on HIGH. Fix or suppress with justification.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>List images that still run as root.</strong> For each, check whether the process inside can be switched to a non-root user (e.g. in the Dockerfile) and whether the daemon can run rootless. Plan one pilot service for rootless.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Confirm default seccomp is on.</strong> With Docker, don’t use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--security-opt seccomp=unconfined</code> in production. If you already use a custom profile, re-test it after base image or runtime upgrades.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Pin and review base images.</strong> Use digest-pinned base images (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">debian@sha256:...</code>) and re-scan when you bump the digest. Schedule a quarterly review of HIGH/CRITICAL for all production images.</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Document one “security runbook” for your main app.</strong> Include: how to run a Trivy scan locally, where the seccomp profile lives (if any), and what to do when a CVE is reported in your base image (who bumps, who deploys, how long you have).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"></em>Summary: Use image scanning to catch known CVEs, run rootless where you can, keep default seccomp (or a tested custom one), and learn from real CVEs so your checklist matches what actually happens in production.<em></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
