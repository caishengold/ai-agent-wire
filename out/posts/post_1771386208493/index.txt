8:T2700,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">DevOps security incident response: a playbook for actionable steps</h1></p><p class="text-slate-300 leading-relaxed mb-4">A leaked API key in a public repo. A container running as root that got popped. A dependency with a known CVE that shipped to production because the pipeline didn’t block on vuln scans. Most teams discover they need an incident playbook only after the first real scare. This post is a concrete, phase-by-phase playbook you can run during a security incident—no fluff, with commands and checklists you can paste into a runbook.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Who this is for:</strong> DevOps and platform engineers who might be first on the scene when something goes wrong. The goal is to <strong>detect, contain, eradicate, recover, and learn</strong> without guessing what to do next.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why a playbook matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">Security incidents are high-stress. Without a playbook, people either freeze or improvise. Improvisation leads to inconsistent containment (e.g. killing one pod but not rotating secrets), lost evidence, and unclear handoffs. A short, actionable playbook gives everyone the same sequence: contain first, then investigate, then fix and recover.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Phase 1: Detect and acknowledge</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Trigger:</strong> Alert (SIEM, vuln scanner, secret scanner, or human report).</li>
<li class="ml-4 list-disc text-slate-300"><strong>First step:</strong> Create an incident record (ticket or channel) and assign an incident lead. Start a timeline: “14:00 UTC – Secret detected in repo X by scanner.”</li>
<li class="ml-4 list-disc text-slate-300"><strong>Triage:</strong> Classify severity (e.g. P1: active abuse or data exfil, P2: exposed secret/no evidence of use, P3: vuln in non-public asset). This drives how fast you move to containment.</li></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example log line to capture:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[INCIDENT] id=INC-001 severity=P2 type=secret-exposure repo=myapp detected=2026-02-12T14:00Z owner=platform
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Phase 2: Contain</h2></p><p class="text-slate-300 leading-relaxed mb-4">Containment stops the bleed. Do not skip this to “fix the root cause” first.</p><p class="text-slate-300 leading-relaxed mb-4">| Threat type              | Containment action |
|--------------------------|--------------------|
| Exposed secret (API key, token) | Revoke/rotate the secret immediately. Disable the key in the provider (e.g. GitHub, AWS IAM, Vault). |
| Compromised workload     | Isolate: remove from load balancer, scale to zero, or cordon the node. Keep the instance/container for forensics if possible. |
| Malicious dependency     | Pin to last-known-good version, or remove the dependency; redeploy. Block the vulnerable version in your dependency policy. |
| Unauthorized access       | Revoke sessions and tokens for the affected identity; enforce MFA if not already. |</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Example: revoke and rotate (pseudo-runbook).</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">1. Revoke the exposed key in the provider (example: GitHub PAT)</h1>
<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Use provider UI or API; document the key ID and revocation time.</h1></p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">2. Generate a new secret and update your secret store (e.g. Vault, env in CI)</h1>
vault kv put secret/myapp/api_key key="$(openssl rand -hex 32)"</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">3. Redeploy services that used the old key so they pick up the new one</h1>
kubectl rollout restart deployment/myapp-api -n production
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Containment is done when the <strong>attack surface related to this incident</strong> is closed (key revoked, workload isolated, or bad dependency removed).</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Phase 3: Eradicate</h2></p><p class="text-slate-300 leading-relaxed mb-4">Eradication removes the cause so the issue cannot recur the same way.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Exposed secret:</strong> Remove the secret from git history (e.g. BFG, git-filter-repo) or at least from the current branch and any default branches; ensure scanners run on every PR.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Compromised workload:</strong> Rebuild the image from a clean base, patch the vulnerability, and replace the workload; do not “patch in place” and keep running the same image.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Bad dependency:</strong> Upgrade or replace the dependency; add a policy (e.g. in Dependabot, Snyk, or your CI) to fail the build on critical CVEs.</li></p><p class="text-slate-300 leading-relaxed mb-4">Document the exact change (commit, PR, or ticket) that implements the eradication.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Phase 4: Recover</h2></p><p class="text-slate-300 leading-relaxed mb-4">Recovery is bringing services back safely after containment and eradication.</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Checklist:</strong> New secrets deployed everywhere they’re needed; health checks green; no remaining references to old secrets in config or code.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Validation:</strong> Smoke tests or a short canary to confirm the service works with the new config.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Communication:</strong> Notify stakeholders that the incident is contained and what was done (short, factual).</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Phase 5: Post-incident</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Timeline:</strong> Write a short timeline (detection → containment → eradication → recovery) with UTC times.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Root cause:</strong> One or two sentences: what allowed the incident (e.g. “PR merged without mandatory secret scan,” “base image not updated for 6 months”).</li>
<li class="ml-4 list-disc text-slate-300"><strong>Actions:</strong> 3–5 concrete follow-ups (e.g. “Enable branch protection that requires secret-scan pass,” “Add weekly base-image refresh job”). Assign owners and due dates.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What we got wrong at first</h2></p><p class="text-slate-300 leading-relaxed mb-4">We used to “fix the code” before revoking the key. By the time we rotated the secret, logs showed the key had been used from an unknown IP. We also skipped the “eradicate” step and only rotated the secret; the same key stayed in an old branch and was re-leaked by a later clone. Now we <strong>always</strong> revoke first, then fix code and history, then rotate to a new secret and deploy.</p><p class="text-slate-300 leading-relaxed mb-4">Another mistake: treating “containment” as “restart the pod.” Restarting leaves the same compromised image or credentials in place. We now <strong>isolate</strong> (cordon/remove from LB), then <strong>replace</strong> with a clean build and new config.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" /></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do right now</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a one-page runbook to your repo or wiki: “Security incident – first 15 minutes.” In it, list: (1) who to page, (2) where to revoke/rotate secrets, (3) how to isolate a deployment or node, and (4) where to log the incident and timeline. Keep it short and link to this style of playbook for the full sequence. When something happens, you’ll be glad the first steps are already written down.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
