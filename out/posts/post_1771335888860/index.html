Modern testing strategies for TypeScript

Reading Level: 6positiveTypeScript TestingTesting FrameworksCI/CD IntegrationDevelopment PracticesBug Management

TypeScript Testing Guide

Aiko Chen joined FinTrack Solutions as a senior developer in 2024-03. Her first assignment: stabilizing a payment processing dashboard that had shipped with zero automated tests. Bugs reached production weekly. The team spent more time firefighting than building features. Aiko needed a testing strategy that would catch regressions before deployment without slowing down development.

This guide covers the testing approach Aiko implemented, from unit tests to CI integration.

Testing Frameworks

TypeScript developers have three primary framework options. Each makes different trade-offs between speed, compatibility, and ecosystem support.

Bun Test

Bun Test ships with the Bun runtime and executes tests without transpilation. It uses a Jest-compatible API but runs significantly faster by avoiding the Node.js bootstrap overhead.

import { describe, it, expect, beforeEach } from 'bun:test';
interface Payment {
  id: string;
  amount: number;
  currency: string;
  status: 'pending' | 'completed' | 'failed';
}
class PaymentProcessor {
  private payments: Map = new Map();
  createPayment(amount: number, currency: string): Payment {
    const payment: Payment = {
      id: crypto.randomUUID(),
      amount,
      currency,
      status: 'pending'
    };
    this.payments.set(payment.id, payment);
    return payment;
  }
  getPayment(id: string): Payment | undefined {
    return this.payments.get(id);
  }
}
describe('PaymentProcessor', () => {
  let processor: PaymentProcessor;
  beforeEach(() => {
    processor = new PaymentProcessor();
  });
  it('should create a payment with pending status', () => {
    const payment = processor.createPayment(100, 'USD');
    expect(payment.status).toBe('pending');
    expect(payment.amount).toBe(100);
  });
  it('should retrieve a payment by id', () => {
    const payment = processor.createPayment(250, 'EUR');
    const retrieved = processor.getPayment(payment.id);
    expect(retrieved).toEqual(payment);
  });
});

The crypto.randomUUID() call works natively in Bun without polyfills. Tests execute in parallel by default, cutting Aiko's test suite runtime from 45 seconds to 8 seconds.

Vitest

Vitest targets Vite-based projects but works with any TypeScript codebase. It offers Hot Module Replacement (HMR) for tests, re-running only affected tests during development.

import { describe, it, expect, vi } from 'vitest';
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { PaymentDashboard } from './PaymentDashboard';
const mockPayments = [
  { id: '1', amount: 100, currency: 'USD', status: 'completed' as const },
  { id: '2', amount: 250, currency: 'EUR', status: 'pending' as const }
];
describe('PaymentDashboard', () => {
  it('should display payment list', async () => {
    const mockFetch = vi.fn().mockResolvedValue({
      json: () => Promise.resolve(mockPayments)
    });
    global.fetch = mockFetch;
    render();
    
    expect(await screen.findByText('USD 100')).toBeInTheDocument();
    expect(screen.getByText('EUR 250')).toBeInTheDocument();
  });
  it('should filter payments by status', async () => {
    const user = userEvent.setup();
    global.fetch = vi.fn().mockResolvedValue({
      json: () => Promise.resolve(mockPayments)
    });
    render();
    await screen.findByText('USD 100');
    
    await user.click(screen.getByRole('button', { name: /pending/i }));
    
    expect(screen.queryByText('USD 100')).not.toBeInTheDocument();
    expect(screen.getByText('EUR 250')).toBeInTheDocument();
  });
});

The vi.fn() utility creates mock functions with built-in spy capabilities. Aiko used this to verify that her components called the correct API endpoints with proper parameters.

Testing Patterns

Unit Testing

Unit tests verify individual functions in isolation. Aiko wrote unit tests for validation logic, calculation functions, and utility modules.

import { describe, it, expect } from 'vitest';
export function validatePaymentAmount(amount: number, currency: string): {
  valid: boolean;
  error?: string;
} {
  if (amount <= 0) {
    return { valid: false, error: 'Amount must be positive' };
  }
  
  if (currency.length !== 3) {
    return { valid: false, error: 'Currency must be 3-letter ISO code' };
  }
  
  const maxAmounts: Record = {
    USD: 10000,
    EUR: 10000,
    GBP: 8000
  };
  
  const max = maxAmounts[currency];
  if (max && amount > max) {
    return { valid: false, error: Amount exceeds ${currency} limit };
  }
  
  return { valid: true };
}
describe('validatePaymentAmount', () => {
  it('should reject negative amounts', () => {
    const result = validatePaymentAmount(-50, 'USD');
    expect(result.valid).toBe(false);
    expect(result.error).toBe('Amount must be positive');
  });
  it('should reject invalid currency codes', () => {
    const result = validatePaymentAmount(100, 'US');
    expect(result.valid).toBe(false);
  });
  it('should enforce currency-specific limits', () => {
    const result = validatePaymentAmount(15000, 'USD');
    expect(result.valid).toBe(false);
    expect(result.error).toContain('USD limit');
  });
  it('should accept valid payments', () => {
    expect(validatePaymentAmount(500, 'EUR')).toEqual({ valid: true });
  });
});

Integration Testing

Integration tests verify that modules work together correctly. Aiko focused these tests on API endpoints and database interactions.

import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import { createServer } from '../server';
describe('Payment API Integration', () => {
  let server: ReturnType;
  beforeAll(async () => {
    server = createServer();
    await server.start(0); // Random available port
  });
  afterAll(async () => {
    await server.stop();
  });
  it('should create and retrieve a payment', async () => {
    const createResponse = await fetch(
      http://localhost:${server.port}/api/payments,
      {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ amount: 200, currency: 'GBP' })
      }
    );
    
    expect(createResponse.status).toBe(201);
    const { id } = await createResponse.json();
    
    const getResponse = await fetch(
      http://localhost:${server.port}/api/payments/${id}
    );
    const payment = await getResponse.json();
    
    expect(payment.amount).toBe(200);
    expect(payment.currency).toBe('GBP');
  });
});

Using port 0 lets the operating system assign an available port, preventing conflicts when tests run in parallel.

End-to-End Testing

E2E tests simulate real user workflows. Aiko used Playwright to test critical paths: login, payment creation, and receipt generation.

import { test, expect } from '@playwright/test';
test('complete payment workflow', async ({ page }) => {
  await page.goto('http://localhost:3000');
  
  await page.fill('[data-testid="amount-input"]', '150');
  await page.selectOption('[data-testid="currency-select"]', 'USD');
  await page.click('[data-testid="submit-payment"]');
  
  await expect(page.locator('[data-testid="success-message"]')).toBeVisible();
  
  const receiptUrl = await page.getAttribute(
    '[data-testid="receipt-link"]',
    'href'
  );
  expect(receiptUrl).toMatch(/\/receipts\/[\w-]+/);
});

Mocking Strategies

Aiko's payment system depended on external banking APIs. Mocking these dependencies prevented test failures when third-party services had outages.

import { describe, it, expect, vi, beforeEach } from 'vitest';
import { BankingService } from './BankingService';
interface BankTransferRequest {
  accountNumber: string;
  amount: number;
  currency: string;
}
class BankingClient {
  async initiateTransfer(request: BankTransferRequest): Promise<{
    transactionId: string;
    status: 'accepted' | 'rejected';
  }> {
    // Real implementation calls external API
    throw new Error('Not implemented');
  }
}
describe('BankingService', () => {
  let service: BankingService;
  let mockClient: BankingClient;
  beforeEach(() => {
    mockClient = new BankingClient();
    service = new BankingService(mockClient);
  });
  it('should retry failed transfers up to 3 times', async () => {
    const mockTransfer = vi
      .spyOn(mockClient, 'initiateTransfer')
      .mockRejectedValueOnce(new Error('Timeout'))
      .mockRejectedValueOnce(new Error('Timeout'))
      .mockResolvedValueOnce({
        transactionId: 'txn-123',
        status: 'accepted'
      });
    const result = await service.processPayment({
      accountNumber: 'GB82WEST12345698765432',
      amount: 500,
      currency: 'GBP'
    });
    expect(mockTransfer).toHaveBeenCalledTimes(3);
    expect(result.transactionId).toBe('txn-123');
  });
});

The mockRejectedValueOnce chain simulates transient failures followed by success. This tested Aiko's retry logic without hitting real banking APIs.

CI Integration

Aiko configured GitHub Actions to run tests on every pull request. The pipeline blocked merges when coverage dropped below 80% or when any test failed.

.github/workflows/test.yml

name: Test Suite
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Run type check
        run: npm run typecheck
      
      - name: Run unit tests
        run: npm run test:unit -- --coverage
      
      - name: Run integration tests
        run: npm run test:integration
        env:
          TEST_DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
      
      - name: Upload coverage
        uses: codecov/codecov-action@v3
        with:
          fail_ci_if_error: true
          verbose: true

Separate jobs for unit and integration tests allowed parallel execution. The fail_ci_if_error: true flag prevented silent coverage failures.

Framework Comparison

| Feature | Bun Test | Vitest | Jest | |---------|----------|--------|------| | Execution speed | Fastest (native TS) | Fast (esbuild) | Moderate (Babel/ts-jest) | | TypeScript support | Native | Native | Requires transformer | | Vite integration | Partial | Native | Via plugin | | Mocking | Basic | Advanced (vi) | Advanced (jest) | | Ecosystem | Growing | Moderate | Mature | | IDE support | Limited | Excellent | Excellent | | Watch mode | Yes | Yes (HMR) | Yes | | Parallel execution | Default | Configurable | Configurable |

Bun Test suits greenfield projects prioritising speed. Vitest works best with Vite-based applications. Jest remains the safest choice for large teams needing extensive third-party integrations.

Lessons Learned

Six months after implementation, Aiko's team shipped with 94% fewer production bugs. The testing strategy revealed several insights:

  • Test behaviour, not implementation. When Aiko refactored the payment processor from class-based to functional, only two tests needed updating because she had tested inputs and outputs rather than internal methods.

  • Integration tests caught API contract drift. Twice, external banking partners changed response formats. Integration tests failed in CI before those changes reached staging.

  • Snapshot tests require discipline. Early on, developers blindly updated snapshots when tests failed. Aiko added a mandatory code review step for snapshot changes, catching three visual regressions in the following month.

  • Coverage thresholds prevent regression. Setting the 80% minimum forced the team to write tests for edge cases they previously ignored, including malformed currency codes and network timeouts.

  • Parallel test execution revealed race conditions. Running tests concurrently exposed a shared state bug in the payment cache that sequential execution had masked.

    • Actionable Takeaways

  • Start with unit tests for validation logic. Functions with clear inputs and outputs provide immediate value and build team confidence in the testing process.

  • Choose Vitest for Vite projects, Bun Test for speed-critical applications. Both offer better TypeScript support than Jest without additional configuration.

  • Implement integration tests for external dependencies. Mock third-party APIs in unit tests, but verify real integration behaviour before deployment.

  • Set coverage thresholds in CI. A minimum threshold prevents untested code from accumulating, though 100% coverage does not guarantee correctness.

  • Review snapshot changes manually. Require human approval for snapshot updates to prevent visual regressions from passing unnoticed.

    • Aiko's testing strategy transformed FinTrack's development velocity. Feature deployment frequency increased from bi-weekly to daily releases. The team spent less time debugging production issues and more time building features that customers requested.
