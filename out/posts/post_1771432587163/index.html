Advanced SQLite: CTEs, window functions, generated columns, JSON

Raj’s task queue ran fine until he needed “top 3 tasks per priority class” and “time since the previous event” for a dashboard. His first attempt: five nested subqueries and a 400-line report script. After a week of debugging, he switched to common table expressions (CTEs) and window functions in SQLite. The report shrank to one query and ran in 12 ms instead of 80 ms. No Postgres, no new services — just features already in the SQLite we were using.

This post covers four areas we use daily: CTEs, window functions, generated columns, and JSON functions. Each section has runnable examples you can paste into sqlite3. We’ll also compare approaches, share what went wrong on our side, and end with concrete steps you can try today.

Why “advanced” SQLite matters

If you only do simple CRUD, you might not need these. Once you need “latest row per id,” running totals, or reusable subquery logic, CTEs and window functions keep SQL readable and fast. Generated columns and JSON functions let you keep more logic in the database instead of duplicating it in application code. Below we use real query patterns from our agent-ops system, not just syntax.

Common table expressions (CTEs)

CTEs give a subquery a name so you can reference it like a table. They make “get the latest row per id” and multi-step reporting easier to read and maintain.

Example: tasks with a status and updated_at. We want the most recent row per task id (e.g. for an audit trail).

-- Schema (simplified)
CREATE TABLE task_events (
  id INTEGER PRIMARY KEY,
  task_id TEXT NOT NULL,
  status TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
-- CTE: rank events per task by time, then keep only the latest
WITH latest_per_task AS (
  SELECT task_id, status, updated_at,
         ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY updated_at DESC) AS rn
  FROM task_events
)
SELECT task_id, status, updated_at
FROM latest_per_task
WHERE rn = 1;

Without a CTE, you’d repeat the window logic or nest subqueries. The CTE makes the intent clear: “latest row per task” is one named step.

Another use: chained transformations. First compute aggregates, then filter or join on them.

WITH daily_counts AS (
  SELECT date(created_at) AS day, status, COUNT() AS cnt
  FROM tasks
  GROUP BY day, status
),
above_five AS (
  SELECT day, status, cnt FROM daily_counts WHERE cnt > 5
)
SELECT  FROM above_five ORDER BY day, status;

Window functions

Window functions compute over a “window” of rows (e.g. per group or ordered range) without collapsing rows. They’re good for rankings, running totals, and “previous/next” values.

ROW_NUMBER, RANK, DENSE_RANK — we already used ROW_NUMBER() above. Difference: RANK gives ties the same rank with a gap after; DENSE_RANK gives ties the same rank with no gap.

SELECT id, priority,
       ROW_NUMBER() OVER (ORDER BY priority ASC) AS row_num,
       RANK()       OVER (ORDER BY priority ASC) AS rk,
       DENSE_RANK() OVER (ORDER BY priority ASC) AS dr
FROM tasks
LIMIT 10;

Running total — sum of priority “so far” by order:

SELECT id, priority,
       SUM(priority) OVER (ORDER BY id ROWS UNBOUNDED PRECEDING) AS running_total
FROM tasks
ORDER BY id
LIMIT 10;

LAG / LEAD — compare to previous or next row (e.g. “time since previous event”):

SELECT task_id, updated_at,
       LAG(updated_at) OVER (PARTITION BY task_id ORDER BY updated_at) AS prev_at
FROM task_events;

Generated columns

Generated columns are computed from other columns in the same row. Stored generated columns are written to disk and can be indexed. They give you one source of truth for derived values and make search and filters consistent.

Example: we store payload as JSON and want to query by a specific key. A generated column keeps the extracted value in sync and indexable.

CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  payload TEXT NOT NULL,
  kind TEXT GENERATED ALWAYS AS (json_extract(payload, '$.kind')) STORED
);
CREATE INDEX idx_events_kind ON events(kind);

Then WHERE kind = 'task_completed' uses the index. No need to remember to call json_extract in every query.

Another use: normalizing or deriving a value once.

ALTER TABLE tasks ADD COLUMN created_date TEXT
  GENERATED ALWAYS AS (date(created_at)) STORED;

Then you can index and filter by created_date without repeating date(created_at) everywhere.

JSON functions

SQLite’s JSON1 extension (built in since 3.38) gives you json_extract, json_object, json_array, and more. We use it for small, structured blobs such as task metadata or config.

Extract and filter:

SELECT id, json_extract(meta, '$.owner') AS owner
FROM tasks
WHERE json_extract(meta, '$.env') = 'production';

Build JSON in a query:

SELECT json_object('id', id, 'title', title, 'status', status) AS task_json
FROM tasks
WHERE status = 'done'
LIMIT 3;

Array length (e.g. list of tags):

SELECT id, json_array_length(json_extract(meta, '$.tags')) AS tag_count
FROM tasks
WHERE json_extract(meta, '$.tags') IS NOT NULL;

Indexing works best when you expose the key path as a generated column and index that, instead of calling json_extract in every WHERE clause.

Runnable examples with terminal output

Here are two full examples you can run locally. Both assume sqlite3 is installed.

Example 1: CTE + window function — latest event per task

Save as sqlite_cte_demo.sql and run: sqlite3 :memory: < sqlite_cte_demo.sql

-- sqlite_cte_demo.sql
.mode column
.headers on
CREATE TABLE task_events (
  id INTEGER PRIMARY KEY,
  task_id TEXT NOT NULL,
  status TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
INSERT INTO task_events (task_id, status, updated_at) VALUES
  ('T1', 'queued',  '2026-02-10 09:00:00'),
  ('T1', 'running', '2026-02-10 10:00:00'),
  ('T1', 'done',    '2026-02-10 11:00:00'),
  ('T2', 'queued',  '2026-02-10 09:30:00'),
  ('T2', 'running', '2026-02-10 10:15:00');
WITH latest_per_task AS (
  SELECT task_id, status, updated_at,
         ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY updated_at DESC) AS rn
  FROM task_events
)
SELECT task_id, status, updated_at
FROM latest_per_task
WHERE rn = 1;

Example 2: Generated column + JSON — filter by JSON key

-- sqlite_json_demo.sql
.mode column
.headers on
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  payload TEXT NOT NULL,
  kind TEXT GENERATED ALWAYS AS (json_extract(payload, '$.kind')) STORED

CREATE INDEX idx_events_kind ON events(kind);

Comparison: when to use which

| Approach | Pros | Cons | When to use | |----------|------|------|-------------| | CTE | Readable, reusable in one query, no temp tables | Single-query scope only | Multi-step logic, “latest per group,” reporting | | Subquery (inline) | No extra name, works everywhere | Hard to read when nested 2–3 levels | Simple one-off filters | | Temporary table | Persists across statements, debuggable | Manual create/drop, more DDL | Batch jobs, scripts, cross-query reuse | | Window function | No self-join, one pass over data | Syntax can be dense | Rankings, running totals, LAG/LEAD | | Generated column | Indexable, one source of truth | Schema change, storage cost | JSON key or derived value queried often |

For “latest row per id” we use a CTE plus ROW_NUMBER(). For “filter by JSON key” we use a generated column and an index. For one-off reports we avoid temp tables; for nightly aggregates we sometimes use them.

One real pattern: “next task to run”

We combine the above: a CTE to rank by priority and time, then take the first row.

WITH ranked AS (
  SELECT id, title, priority,
         ROW_NUMBER() OVER (ORDER BY priority ASC, created_at ASC) AS rn
  FROM tasks
  WHERE status = 'todo'
)
SELECT id, title, priority FROM ranked WHERE rn = 1;

If we add a “priority class” in JSON, we’d expose it via a generated column and order by that first; the pattern stays the same.

What went wrong (lessons learned)

1. Forgetting that json_extract returns JSON types. We compared json_extract(meta, '$.env') to a string in Python and got no matches. In SQLite, json_extract returns a JSON value; for reliable string comparison we had to cast or ensure the literal was quoted. We now use a generated column for any JSON key we filter on, so the type is consistent and the column is indexable.

2. CTE referenced twice, query plan blew up. In one report we referenced the same CTE four times in joins. SQLite (3.35+) can optimize that, but our version at the time materialized the CTE multiple times. We saw ~200 ms for 50k rows. We rewrote to reference the CTE once and join a copy with AS or moved the logic into a single pass with conditional aggregation; that brought it down to ~25 ms. So: if a CTE is used many times in one query, check EXPLAIN QUERY PLAN and consider a temp table or a single-pass expression.

3. Generated column on date(created_at) without time zone. We added created_date TEXT GENERATED ALWAYS AS (date(created_at)) STORED for daily rollups. Our created_at was stored in UTC. For Aiko (Tokyo) the “day” in local time was sometimes the previous or next UTC day. We didn’t change the column; we documented that “day” is UTC and added a separate application-side “local day” for user-facing reports. Lesson: document what “day” means and whether you’re storing UTC or local time.

Actionable next steps

  • Run the two SQL scripts above — Use sqlite3 :memory: < sqlite_cte_demo.sql and sqlite_json_demo.sql to confirm your SQLite version supports CTEs, window functions, and generated columns (3.25+ for window functions, 3.31+ for generated columns).

  • Find one “latest row per id” query — In your codebase or reports, replace a nested subquery or self-join with a CTE using ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) and WHERE rn = 1.

  • Add one generated column — If you have a JSON column and often filter on one key, add a stored generated column and an index on it; then switch one hot query to use that column and compare latency.

  • Check EXPLAIN QUERY PLAN — For any slow query using a CTE or JSON, run EXPLAIN QUERY PLAN and confirm the plan uses indexes and doesn’t scan more than you expect.

  • Document time zone for date-derived columns — If you add a generated column from date(...), write in your schema or README whether that day is UTC or local, so the next person (or you in six months) doesn’t get surprised.
