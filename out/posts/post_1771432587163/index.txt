8:T5296,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Advanced SQLite: CTEs, window functions, generated columns, JSON</h1></p><p class="text-slate-300 leading-relaxed mb-4">Raj’s task queue ran fine until he needed “top 3 tasks per priority class” and “time since the previous event” for a dashboard. His first attempt: five nested subqueries and a 400-line report script. After a week of debugging, he switched to common table expressions (CTEs) and window functions in SQLite. The report shrank to one query and ran in 12 ms instead of 80 ms. No Postgres, no new services — just features already in the SQLite we were using.</p><p class="text-slate-300 leading-relaxed mb-4">This post covers four areas we use daily: <strong>CTEs</strong>, <strong>window functions</strong>, <strong>generated columns</strong>, and <strong>JSON functions</strong>. Each section has runnable examples you can paste into <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3</code>. We’ll also compare approaches, share what went wrong on our side, and end with concrete steps you can try today.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why “advanced” SQLite matters</h2></p><p class="text-slate-300 leading-relaxed mb-4">If you only do simple CRUD, you might not need these. Once you need “latest row per id,” running totals, or reusable subquery logic, CTEs and window functions keep SQL readable and fast. Generated columns and JSON functions let you keep more logic in the database instead of duplicating it in application code. Below we use real query patterns from our agent-ops system, not just syntax.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Common table expressions (CTEs)</h2></p><p class="text-slate-300 leading-relaxed mb-4">CTEs give a subquery a name so you can reference it like a table. They make “get the latest row per id” and multi-step reporting easier to read and maintain.</p><p class="text-slate-300 leading-relaxed mb-4">Example: tasks with a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">status</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">updated_at</code>. We want the <strong>most recent</strong> row per task id (e.g. for an audit trail).</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- Schema (simplified)
CREATE TABLE task_events (
  id INTEGER PRIMARY KEY,
  task_id TEXT NOT NULL,
  status TEXT NOT NULL,
  updated_at TEXT NOT NULL
);</p><p class="text-slate-300 leading-relaxed mb-4">-- CTE: rank events per task by time, then keep only the latest
WITH latest_per_task AS (
  SELECT task_id, status, updated_at,
         ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY updated_at DESC) AS rn
  FROM task_events
)
SELECT task_id, status, updated_at
FROM latest_per_task
WHERE rn = 1;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Without a CTE, you’d repeat the window logic or nest subqueries. The CTE makes the intent clear: “latest row per task” is one named step.</p><p class="text-slate-300 leading-relaxed mb-4">Another use: chained transformations. First compute aggregates, then filter or join on them.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>WITH daily_counts AS (
  SELECT date(created_at) AS day, status, COUNT(<em>) AS cnt
  FROM tasks
  GROUP BY day, status
),
above_five AS (
  SELECT day, status, cnt FROM daily_counts WHERE cnt > 5
)
SELECT </em> FROM above_five ORDER BY day, status;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Window functions</h2></p><p class="text-slate-300 leading-relaxed mb-4">Window functions compute over a “window” of rows (e.g. per group or ordered range) without collapsing rows. They’re good for rankings, running totals, and “previous/next” values.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>ROW_NUMBER, RANK, DENSE_RANK</strong> — we already used <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ROW_NUMBER()</code> above. Difference: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RANK</code> gives ties the same rank with a gap after; <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">DENSE_RANK</code> gives ties the same rank with no gap.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, priority,
       ROW_NUMBER() OVER (ORDER BY priority ASC) AS row_num,
       RANK()       OVER (ORDER BY priority ASC) AS rk,
       DENSE_RANK() OVER (ORDER BY priority ASC) AS dr
FROM tasks
LIMIT 10;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Running total</strong> — sum of priority “so far” by order:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, priority,
       SUM(priority) OVER (ORDER BY id ROWS UNBOUNDED PRECEDING) AS running_total
FROM tasks
ORDER BY id
LIMIT 10;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>LAG / LEAD</strong> — compare to previous or next row (e.g. “time since previous event”):</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT task_id, updated_at,
       LAG(updated_at) OVER (PARTITION BY task_id ORDER BY updated_at) AS prev_at
FROM task_events;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Generated columns</h2></p><p class="text-slate-300 leading-relaxed mb-4">Generated columns are computed from other columns in the same row. Stored generated columns are written to disk and can be indexed. They give you one source of truth for derived values and make search and filters consistent.</p><p class="text-slate-300 leading-relaxed mb-4">Example: we store <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">payload</code> as JSON and want to query by a specific key. A generated column keeps the extracted value in sync and indexable.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  payload TEXT NOT NULL,
  kind TEXT GENERATED ALWAYS AS (json_extract(payload, '$.kind')) STORED
);
CREATE INDEX idx_events_kind ON events(kind);
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Then <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WHERE kind = 'task_completed'</code> uses the index. No need to remember to call <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract</code> in every query.</p><p class="text-slate-300 leading-relaxed mb-4">Another use: normalizing or deriving a value once.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>ALTER TABLE tasks ADD COLUMN created_date TEXT
  GENERATED ALWAYS AS (date(created_at)) STORED;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Then you can index and filter by <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_date</code> without repeating <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">date(created_at)</code> everywhere.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">JSON functions</h2></p><p class="text-slate-300 leading-relaxed mb-4">SQLite’s JSON1 extension (built in since 3.38) gives you <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_object</code>, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_array</code>, and more. We use it for small, structured blobs such as task metadata or config.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>Extract and filter:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, json_extract(meta, '$.owner') AS owner
FROM tasks
WHERE json_extract(meta, '$.env') = 'production';
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Build JSON in a query:</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT json_object('id', id, 'title', title, 'status', status) AS task_json
FROM tasks
WHERE status = 'done'
LIMIT 3;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><strong>Array length (e.g. list of tags):</strong></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>SELECT id, json_array_length(json_extract(meta, '$.tags')) AS tag_count
FROM tasks
WHERE json_extract(meta, '$.tags') IS NOT NULL;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Indexing works best when you expose the key path as a generated column and index that, instead of calling <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract</code> in every <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WHERE</code> clause.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Runnable examples with terminal output</h2></p><p class="text-slate-300 leading-relaxed mb-4">Here are two full examples you can run locally. Both assume <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3</code> is installed.</p><p class="text-slate-300 leading-relaxed mb-4"><h3 class="text-lg font-semibold text-slate-100 mt-6 mb-2">Example 1: CTE + window function — latest event per task</h3></p><p class="text-slate-300 leading-relaxed mb-4">Save as <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite_cte_demo.sql</code> and run: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3 :memory: < sqlite_cte_demo.sql</code></p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>-- sqlite_cte_demo.sql

</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Comparison: when to use which</h2></p><p class="text-slate-300 leading-relaxed mb-4">| Approach | Pros | Cons | When to use |
|----------|------|------|-------------|
| <strong>CTE</strong> | Readable, reusable in one query, no temp tables | Single-query scope only | Multi-step logic, “latest per group,” reporting |
| <strong>Subquery (inline)</strong> | No extra name, works everywhere | Hard to read when nested 2–3 levels | Simple one-off filters |
| <strong>Temporary table</strong> | Persists across statements, debuggable | Manual create/drop, more DDL | Batch jobs, scripts, cross-query reuse |
| <strong>Window function</strong> | No self-join, one pass over data | Syntax can be dense | Rankings, running totals, LAG/LEAD |
| <strong>Generated column</strong> | Indexable, one source of truth | Schema change, storage cost | JSON key or derived value queried often |</p><p class="text-slate-300 leading-relaxed mb-4">For “latest row per id” we use a CTE plus <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ROW_NUMBER()</code>. For “filter by JSON key” we use a generated column and an index. For one-off reports we avoid temp tables; for nightly aggregates we sometimes use them.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One real pattern: “next task to run”</h2></p><p class="text-slate-300 leading-relaxed mb-4">We combine the above: a CTE to rank by priority and time, then take the first row.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>WITH ranked AS (
  SELECT id, title, priority,
         ROW_NUMBER() OVER (ORDER BY priority ASC, created_at ASC) AS rn
  FROM tasks
  WHERE status = 'todo'
)
SELECT id, title, priority FROM ranked WHERE rn = 1;
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">If we add a “priority class” in JSON, we’d expose it via a generated column and order by that first; the pattern stays the same.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What went wrong (lessons learned)</h2></p><p class="text-slate-300 leading-relaxed mb-4"><strong>1. Forgetting that <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract</code> returns JSON types.</strong> We compared <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract(meta, '$.env')</code> to a string in Python and got no matches. In SQLite, <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">json_extract</code> returns a JSON value; for reliable string comparison we had to cast or ensure the literal was quoted. We now use a generated column for any JSON key we filter on, so the type is consistent and the column is indexable.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>2. CTE referenced twice, query plan blew up.</strong> In one report we referenced the same CTE four times in joins. SQLite (3.35+) can optimize that, but our version at the time materialized the CTE multiple times. We saw ~200 ms for 50k rows. We rewrote to reference the CTE once and join a copy with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">AS</code> or moved the logic into a single pass with conditional aggregation; that brought it down to ~25 ms. So: if a CTE is used many times in one query, check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EXPLAIN QUERY PLAN</code> and consider a temp table or a single-pass expression.</p><p class="text-slate-300 leading-relaxed mb-4"><strong>3. Generated column on <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">date(created_at)</code> without time zone.</strong> We added <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_date TEXT GENERATED ALWAYS AS (date(created_at)) STORED</code> for daily rollups. Our <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">created_at</code> was stored in UTC. For Aiko (Tokyo) the “day” in local time was sometimes the previous or next UTC day. We didn’t change the column; we documented that “day” is UTC and added a separate application-side “local day” for user-facing reports. Lesson: document what “day” means and whether you’re storing UTC or local time.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Actionable next steps</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Run the two SQL scripts above</strong> — Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite3 :memory: < sqlite_cte_demo.sql</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">sqlite_json_demo.sql</code> to confirm your SQLite version supports CTEs, window functions, and generated columns (3.25+ for window functions, 3.31+ for generated columns).</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Find one “latest row per id” query</strong> — In your codebase or reports, replace a nested subquery or self-join with a CTE using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC)</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">WHERE rn = 1</code>.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Add one generated column</strong> — If you have a JSON column and often filter on one key, add a stored generated column and an index on it; then switch one hot query to use that column and compare latency.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Check <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EXPLAIN QUERY PLAN</code></strong> — For any slow query using a CTE or JSON, run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">EXPLAIN QUERY PLAN <your_query></code> and confirm the plan uses indexes and doesn’t scan more than you expect.</li></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Document time zone for date-derived columns</strong> — If you add a generated column from <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">date(...)</code>, write in your schema or README whether that day is UTC or local, so the next person (or you in six months) doesn’t get surprised.</li></p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
