Bun Sqlite Best Practice

title: Bun + SQLite: A Real-World Guide to Best Practices date: 2023-04-05 author: John Doe description: Explore the combination of Bun and SQLite in a real-world scenario, learn best practices, and see code examples to optimize your application's performance.

Introduction

Aiko Chen, lead developer at a mid-size fintech startup, faced a familiar problem in early 2024. Her team needed to deploy a lightweight analytics dashboard for internal use, but the infrastructure costs for PostgreSQL seemed excessive for a tool that would only handle a few thousand queries daily. The deployment needed to be simple, the database needed to start instantly without configuration, and the entire stack had to fit in a single Docker container.

After evaluating several options, Aiko chose Bun as her runtime and SQLite as the database. Three months later, the dashboard handles 50,000 daily operations with p99 latencies under 15ms. This article walks through exactly how she built it, the mistakes she made along the way, and the patterns that made the difference between a sluggish prototype and a production-ready system.

Setting Up the Project

Aiko initialized the project using Bun's built-in package manager. The entire setup took less than two minutes.

mkdir analytics-dashboard && cd analytics-dashboard
bun init -y
bun add sqlite better-sqlite3

She chose better-sqlite3 over sqlite3 for synchronous operations, which works better with Bun's event loop. For async-heavy workloads, the sqlite package with the sqlite3 driver remains a solid choice.

The project structure looked like this:

analytics-dashboard/
├── src/
│   ├── db.js          # Database connection and initialization
│   ├── products.js    # Product CRUD operations
│   ├── auth.js        # Authentication functions
│   └── index.js       # Main entry point
└── database.db        # SQLite file (created automatically)

Building the Database Layer

Aiko created a dedicated database module that handles connection management and schema initialization. This pattern prevents connection leaks and ensures the database is ready before any queries execute.

// src/db.js
import Database from 'better-sqlite3';
let db = null;
export function getDb() {
  if (!db) {
    db = new Database('./analytics.db');
    db.pragma('journal_mode = WAL');
    db.pragma('synchronous = NORMAL');
    initializeSchema(db);
  }
  return db;
}
function initializeSchema(database) {
  database.exec(
    CREATE TABLE IF NOT EXISTS products (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      name TEXT NOT NULL,
      price REAL NOT NULL,
      stock INTEGER NOT NULL DEFAULT 0,
      category TEXT,
      created_at DATETIME DEFAULT CURRENT_TIMESTAMP
    )
  );
  database.exec(
    CREATE TABLE IF NOT EXISTS users (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      username TEXT NOT NULL UNIQUE,
      password_hash TEXT NOT NULL,
      role TEXT NOT NULL DEFAULT 'user',
      created_at DATETIME DEFAULT CURRENT_TIMESTAMP
    )
  );
  database.exec(
    CREATE TABLE IF NOT EXISTS events (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      user_id INTEGER,
      event_type TEXT NOT NULL,
      payload TEXT,
      timestamp DATETIME DEFAULT CURRENT_TIMESTAMP,
      FOREIGN KEY (user_id) REFERENCES users(id)
    )
  );
}
export function closeDb() {
  if (db) {
    db.close();
    db = null;
  }
}

This module enables WAL mode (Write-Ahead Logging), which significantly improves concurrent read performance. The synchronous = NORMAL pragma balances durability and speed—acceptable for analytics data where losing the last few milliseconds of writes matters less than raw throughput.

Implementing CRUD Operations

With the database layer in place, Aiko built a products module with full CRUD functionality. She used prepared statements throughout to prevent SQL injection.

// src/products.js
import { getDb } from './db.js';
export function createProduct(name, price, stock, category = 'general') {
  const db = getDb();
  const stmt = db.prepare(
    'INSERT INTO products (name, price, stock, category) VALUES (?, ?, ?, ?)'
  );
  const result = stmt.run(name, price, stock, category);
  return result.lastInsertRowid;
}
export function getProduct(id) {
  const db = getDb();
  const stmt = db.prepare('SELECT  FROM products WHERE id = ?');
  return stmt.get(id);
}
export function getAllProducts(category = null, limit = 100) {
  const db = getDb();
  if (category) {
    const stmt = db.prepare(
      'SELECT  FROM products WHERE category = ? ORDER BY created_at DESC LIMIT ?'
    );
    return stmt.all(category, limit);
  }
  const stmt = db.prepare(
    'SELECT  FROM products ORDER BY created_at DESC LIMIT ?'
  );
  return stmt.all(limit);
}
export function updateProduct(id, updates) {
  const db = getDb();
  const fields = [];
  const values = [];
  if (updates.name !== undefined) {
    fields.push('name = ?');
    values.push(updates.name);
  }
  if (updates.price !== undefined) {
    fields.push('price = ?');
    values.push(updates.price);
  }
  if (updates.stock !== undefined) {
    fields.push('stock = ?');
    values.push(updates.stock);
  }
  if (fields.length === 0) return false;
  values.push(id);
  const stmt = db.prepare(
    UPDATE products SET ${fields.join(', ')} WHERE id = ?
  );
  const result = stmt.run(...values);
  return result.changes > 0;
}
export function deleteProduct(id) {
  const db = getDb();
  const stmt = db.prepare('DELETE FROM products WHERE id = ?');
  const result = stmt.run(id);
  return result.changes > 0;
}
export function getLowStockProducts(threshold = 10) {
  const db = getDb();
  const stmt = db.prepare(
    'SELECT  FROM products WHERE stock < ? ORDER BY stock ASC'
  );
  return stmt.all(threshold);
}

The updateProduct function uses a dynamic query builder pattern. This approach handles partial updates gracefully—if you only want to update the price, you don't need to specify name or stock.

User Authentication

For authentication, Aiko implemented password hashing using bcrypt. Never store plain-text passwords, even in internal tools.

// src/auth.js
import { getDb } from './db.js';
import bcrypt from 'bcryptjs';
const SALT_ROUNDS = 10;
export function createUser(username, password, role = 'user') {
  const db = getDb();
  const passwordHash = bcrypt.hashSync(password, SALT_ROUNDS);
  try {
    const stmt = db.prepare(
      'INSERT INTO users (username, password_hash, role) VALUES (?, ?, ?)'
    );
    const result = stmt.run(username, passwordHash, role);
    return { success: true, userId: result.lastInsertRowid };
  } catch (error) {
    if (error.code === 'SQLITE_CONSTRAINT_UNIQUE') {
      return { success: false, error: 'Username already exists' };
    }
    throw error;
  }
}
export function verifyCredentials(username, password) {
  const db = getDb();
  const stmt = db.prepare('SELECT  FROM users WHERE username = ?');
  const user = stmt.get(username);
  if (!user) {
    return { valid: false, user: null };
  }
  const valid = bcrypt.compareSync(password, user.password_hash);
  return { valid, user: valid ? user : null };
}
export function getUserById(id) {
  const db = getDb();
  const stmt = db.prepare('SELECT id, username, role FROM users WHERE id = ?');
  return stmt.get(id);
}

The authentication module returns structured results rather than throwing exceptions for invalid credentials. This pattern makes it easier to handle different failure modes in the API layer.

Performance Comparisons

Aiko ran benchmarks to understand the impact of indexing on query performance. She tested four common operations against a table with 10,000 products.

| Operation | Without Index (ms) | With Index (ms) | Improvement | |-----------|-------------------|-----------------|-------------| | Insert Product | 0.8 | 0.9 | -12% | | Find by ID | 4.2 | 0.3 | 93% | | Find by Category | 6.1 | 2.8 | 54% | | Delete by ID | 3.8 | 0.4 | 89% |

The results showed that indexing dramatically improves read and delete operations, with a small overhead on inserts. For read-heavy workloads like Aiko's analytics dashboard, the trade-off clearly favors indexing.

She added indexes for the most common query patterns:

// Add these after table creation in db.js
db.exec('CREATE INDEX IF NOT EXISTS idx_products_category ON products(category)');
db.exec('CREATE INDEX IF NOT EXISTS idx_events_user_id ON events(user_id)');
db.exec('CREATE INDEX IF NOT EXISTS idx_events_timestamp ON events(timestamp)');

Transactions and Data Integrity

When Aiko needed to record an event and update user statistics atomically, she discovered the importance of transactions:

// src/events.js
import { getDb } from './db.js';
export function recordEventWithUserUpdate(userId, eventType, payload) {
  const db = getDb();
  
  const transaction = db.transaction(() => {
    const insertStmt = db.prepare(
      'INSERT INTO events (user_id, event_type, payload) VALUES (?, ?, ?)'
    );
    const eventResult = insertStmt.run(userId, eventType, JSON.stringify(payload));
    const updateStmt = db.prepare(
      UPDATE users 
      SET events_count = COALESCE(events_count, 0) + 1 
      WHERE id = ?
    );
    updateStmt.run(userId);
    return eventResult.lastInsertRowid;
  });
  return transaction();
}

Using db.transaction() ensures that either both operations succeed or both fail. Without this wrapper, a failure after the first operation would leave the database in an inconsistent state.

Common Pitfalls

Aiko encountered several issues that cost her debug time. Here's what to avoid:

  • Forgetting to close the database — In long-running Bun processes, unclosed connections accumulate. Always call closeDb() during shutdown.

  • Using async/await with better-sqlite3 — This library is synchronous by design. Wrapping it in async functions adds overhead without benefit.

  • Ignoring WAL checkpointing — The WAL file grows indefinitely without periodic checkpoints. Add db.pragma('wal_checkpoint(TRUNCATE)') during maintenance windows.

  • Storing large objects as JSON strings — Querying within JSON fields is slow. Use separate tables for data you need to filter.

  • Assuming single-file means single-user — SQLite handles concurrent reads well, but write locking is table-level. Design for write patterns accordingly.

    • Lessons Learned

  • WAL mode and proper pragmas improved throughput by 3x compared to default settings
  • Dynamic query building for partial updates saved code duplication and reduced bugs
  • Transactions prevented data inconsistency during multi-step operations
  • Indexing provided 90%+ improvement on read queries with minimal insert overhead
  • Password hashing with bcrypt is non-negotiable, even for internal tools

    • Actionable Takeaways

  • Enable WAL mode immediately — Add db.pragma('journal_mode = WAL') before any other configuration

  • Profile before optimizing — Use EXPLAIN QUERY PLAN to understand SQLite's query strategy before adding indexes

  • Use transactions for multi-statement operations — The transaction() wrapper in better-sqlite3 makes this trivial

  • Implement graceful shutdown — Call database close handlers when your Bun process receives SIGTERM

  • Hash all passwords — Never store plain-text credentials, and use sufficient salt rounds (10+)

    • Aiko's analytics dashboard has been running stably for three months with zero maintenance incidents. The Bun + SQLite combination delivered exactly what she needed: fast startup, minimal infrastructure, and predictable performance.
