8:T180e,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Log Sampling for High-Throughput TypeScript APIs (2026)</h1></p><p class="text-slate-300 leading-relaxed mb-4">In high-throughput services, logging every request can overwhelm disks, I/O, and log aggregators. Log sampling lets you keep observability without the cost of full-volume logs.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why sample?</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Volume</strong>: At 10k req/s, 10 lines per request means 100k log lines per second.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Cost</strong>: Storage and indexing (e.g. Elasticsearch, Datadog) scale with log volume.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Noise</strong>: Most requests are normal; you care about errors, slow paths, and outliers.</li></p><p class="text-slate-300 leading-relaxed mb-4">Sampling gives you a representative slice plus <strong>full logging for non-success</strong> (errors, timeouts, 4xx/5xx) so you don't lose signal.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Strategy: sample success, log everything else</h2></p><p class="text-slate-300 leading-relaxed mb-4">A common approach:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300"><strong>Log all non-2xx</strong> (and optionally slow requests).</li>
<li class="ml-4 list-decimal text-slate-300"><strong>Sample 2xx</strong> at a fixed rate (e.g. 1 in 100) or by a deterministic rule (e.g. trace ID hash).</li></p><p class="text-slate-300 leading-relaxed mb-4">Example in TypeScript with a minimal middleware-style helper:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>const SAMPLE_RATE = 100; // log 1 in 100 successful requests</p><p class="text-slate-300 leading-relaxed mb-4">function shouldLogSuccess(reqId: string): boolean {
  const n = reqId.split('').reduce((acc, c) => (acc + c.charCodeAt(0)) % SAMPLE_RATE, 0);
  return n === 0;
}</p><p class="text-slate-300 leading-relaxed mb-4">function requestLogger(req: Request, res: Response, durationMs: number) {
  const status = res.statusCode;
  const isSuccess = status >= 200 && status < 300 && durationMs < 500;
  if (!isSuccess || shouldLogSuccess(req.headers['x-request-id'] ?? req.url)) {
    console.log(JSON.stringify({
      ts: new Date().toISOString(),
      method: req.method,
      path: req.url,
      status: status,
      durationMs,
      requestId: req.headers['x-request-id'],
    }));
  }
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Adjust the threshold (e.g. 500ms) so that "slow success" is always logged.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Deterministic vs random sampling</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Deterministic (e.g. hash of request ID)</strong>: Same request ID always sampled or not; good for replay and debugging.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Random</strong>: Simple, but the same user or trace may be over- or under-represented.</li></p><p class="text-slate-300 leading-relaxed mb-4">For trace-based systems, sampling by trace ID keeps a whole trace in or out, which avoids half-logged traces.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">What to always log</h2></p><p class="text-slate-300 leading-relaxed mb-4">Do <strong>not</strong> sample:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">All 4xx and 5xx responses.</li>
<li class="ml-4 list-disc text-slate-300">Requests over a latency threshold (e.g. p99).</li>
<li class="ml-4 list-disc text-slate-300">Health and readiness probes if you use them for alerting.</li>
<li class="ml-4 list-disc text-slate-300">Any path that handles payments or security-sensitive actions (audit trail).</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Structured logs and sampling metadata</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a field so aggregators know a log line is sampled:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>console.log(JSON.stringify({
  ...baseFields,
  sampled: true,
  sampleRate: SAMPLE_RATE,
}));
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">That way dashboards can show "approximate RPS" vs "error count" and avoid double-counting.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Tuning the sample rate</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300">Start with 1/100 or 1/1000 for success, 100% for errors.</li>
<li class="ml-4 list-disc text-slate-300">Increase rate if you need more success-path visibility; decrease if storage or ingestion cost is high.</li>
<li class="ml-4 list-disc text-slate-300">In development or staging, use 1/1 (no sampling) or a higher rate to validate behavior.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Summary</h2></p><p class="text-slate-300 leading-relaxed mb-4">Use log sampling to keep throughput and cost under control while still logging every error and optionally every slow request. Sample success deterministically (e.g. by request or trace ID), always log failures and slow responses, and tag sampled lines so metrics stay interpretable.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
