Log Sampling for High-Throughput TypeScript APIs (2026)

In high-throughput services, logging every request can overwhelm disks, I/O, and log aggregators. Log sampling lets you keep observability without the cost of full-volume logs.

Why sample?

  • Volume: At 10k req/s, 10 lines per request means 100k log lines per second.
  • Cost: Storage and indexing (e.g. Elasticsearch, Datadog) scale with log volume.
  • Noise: Most requests are normal; you care about errors, slow paths, and outliers.

    • Sampling gives you a representative slice plus full logging for non-success (errors, timeouts, 4xx/5xx) so you don't lose signal.

    Strategy: sample success, log everything else

    A common approach:

  • Log all non-2xx (and optionally slow requests).
  • Sample 2xx at a fixed rate (e.g. 1 in 100) or by a deterministic rule (e.g. trace ID hash).

    • Example in TypeScript with a minimal middleware-style helper:

    const SAMPLE_RATE = 100; // log 1 in 100 successful requests
    function shouldLogSuccess(reqId: string): boolean {
  const n = reqId.split('').reduce((acc, c) => (acc + c.charCodeAt(0)) % SAMPLE_RATE, 0);
  return n === 0;
}
    function requestLogger(req: Request, res: Response, durationMs: number) {
  const status = res.statusCode;
  const isSuccess = status >= 200 && status < 300 && durationMs < 500;
  if (!isSuccess || shouldLogSuccess(req.headers['x-request-id'] ?? req.url)) {
    console.log(JSON.stringify({
      ts: new Date().toISOString(),
      method: req.method,
      path: req.url,
      status: status,
      durationMs,
      requestId: req.headers['x-request-id'],
    }));
  }
}

    Adjust the threshold (e.g. 500ms) so that "slow success" is always logged.

    Deterministic vs random sampling

  • Deterministic (e.g. hash of request ID): Same request ID always sampled or not; good for replay and debugging.
  • Random: Simple, but the same user or trace may be over- or under-represented.

    • For trace-based systems, sampling by trace ID keeps a whole trace in or out, which avoids half-logged traces.

    What to always log

    Do not sample:

  • All 4xx and 5xx responses.
  • Requests over a latency threshold (e.g. p99).
  • Health and readiness probes if you use them for alerting.
  • Any path that handles payments or security-sensitive actions (audit trail).

    • Structured logs and sampling metadata

    Add a field so aggregators know a log line is sampled:

    console.log(JSON.stringify({
  ...baseFields,
  sampled: true,
  sampleRate: SAMPLE_RATE,
}));

    That way dashboards can show "approximate RPS" vs "error count" and avoid double-counting.

    Tuning the sample rate

  • Start with 1/100 or 1/1000 for success, 100% for errors.
  • Increase rate if you need more success-path visibility; decrease if storage or ingestion cost is high.
  • In development or staging, use 1/1 (no sampling) or a higher rate to validate behavior.

    • Summary

    Use log sampling to keep throughput and cost under control while still logging every error and optionally every slow request. Sample success deterministically (e.g. by request or trace ID), always log failures and slow responses, and tag sampled lines so metrics stay interpretable.
