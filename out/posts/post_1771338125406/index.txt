8:T2445,<h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Deploying Bun Apps in Production: Docker, systemd, and Zero-Downtime Updates</h1></p><p class="text-slate-300 leading-relaxed mb-4">You shipped a Bun app locally and it flies. Then you put it on a server and wonder why it dies at 3 AM or why every deploy feels like a coin flip. Production is where the real work begins: containers, process managers, health checks, and updates without dropping requests.</p><p class="text-slate-300 leading-relaxed mb-4">This post walks through a practical path we use: <strong>Docker for build and run</strong>, <strong>systemd for supervision</strong>, <strong>HTTP health checks</strong>, and <strong>zero-downtime reloads</strong> so you can deploy Bun apps with confidence.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Why Docker and systemd together?</h2></p><p class="text-slate-300 leading-relaxed mb-4">Docker gives you a consistent runtime and easy rollbacks (just point to a previous image). systemd on the host gives you restarts on crash, log rotation, and integration with the rest of the system (timers, network, etc.). We run the app <em>inside</em> a container and let systemd start, stop, and restart that container. That way you get both portability and robust process management.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Dockerfile that works for Bun</h2></p><p class="text-slate-300 leading-relaxed mb-4">Keep the image small and the build cache effective. Use a multi-stage setup so the final image only has the runtime and your built artifacts.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Build stage</h1>
FROM oven/bun:1 AS builder
WORKDIR /app
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build</p><p class="text-slate-300 leading-relaxed mb-4"><h1 class="text-2xl font-bold text-slate-100 mt-8 mb-4">Run stage</h1>
FROM oven/bun:1-slim
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY package.json ./
EXPOSE 3000
USER bun
CMD ["bun", "run", "dist/index.js"]
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Use <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">bun:1-slim</code> in production to shrink image size. Expose the port your app listens on (here 3000) and run as a non-root user.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Health checks inside the container</h2></p><p class="text-slate-300 leading-relaxed mb-4">Your app should expose a <strong>cheap</strong> endpoint that only checks “am I alive and can I do the minimum work?” For example, a GET that returns 200 and maybe checks DB connectivity. No heavy logic.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>// health.ts
export function healthHandler(req: Request): Response {
  // Optional: ping DB or cache here
  return new Response(JSON.stringify({ status: "ok", ts: Date.now() }), {
    headers: { "Content-Type": "application/json" },
    status: 200,
  });
}
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">In the Dockerfile, add a HEALTHCHECK so Docker (and orchestrators) can see when the process is unhealthy:</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=2 \
  CMD wget -q -O - http://localhost:3000/health || exit 1
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4">Adjust the port and path to match your app. Start period gives the app time to bootstrap before failing.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">systemd unit to run the container</h2></p><p class="text-slate-300 leading-relaxed mb-4">Run the container under systemd so it restarts on failure and starts on boot. Replace <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">your-app</code> and image tag with your names.</p><p class="text-slate-300 leading-relaxed mb-4"><pre class="bg-slate-950 border border-slate-700 rounded-lg p-4 my-4 overflow-x-auto text-sm"><code>[Unit]
Description=Bun app in Docker
After=network-online.target docker.service
Requires=docker.service</p><p class="text-slate-300 leading-relaxed mb-4">[Service]
Type=simple
ExecStartPre=-/usr/bin/docker pull your-registry/your-app:latest
ExecStart=/usr/bin/docker run --rm --name bun-app -p 3000:3000 your-registry/your-app:latest
ExecStop=/usr/bin/docker stop -t 10 bun-app
Restart=always
RestartSec=5</p><p class="text-slate-300 leading-relaxed mb-4">[Install]
WantedBy=multi-user.target
</code></pre></p><p class="text-slate-300 leading-relaxed mb-4"><code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=always</code> and <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">RestartSec=5</code> mean systemd will bring the container back after a crash. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ExecStop</code> gives the process 10 seconds to shut down cleanly.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Zero-downtime updates</h2></p><p class="text-slate-300 leading-relaxed mb-4">The goal is to deploy a new image without dropping in-flight requests. A simple approach:</p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-decimal text-slate-300">Build and push the new image with a <strong>tag</strong> (e.g. <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">latest</code> or a version).</li>
<li class="ml-4 list-decimal text-slate-300">Run <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl reload your-service</code> or <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart your-service</code> during a low-traffic window, <strong>or</strong> use a reverse proxy (nginx, Caddy) in front of two instances and swap traffic.</li></p><p class="text-slate-300 leading-relaxed mb-4">For a single-instance setup, a brief restart is often acceptable: <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">systemctl restart your-service</code>. The health check ensures you only send traffic once the new process is up if you put the proxy in front and use health-check for routing.</p><p class="text-slate-300 leading-relaxed mb-4">For true zero-downtime, run two containers (or two nodes), point the proxy at both, and do a rolling update: start the new container, wait for health to pass, then stop the old one. The proxy handles the switch.</p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">Gotchas we hit</h2></p><p class="text-slate-300 leading-relaxed mb-4"><li class="ml-4 list-disc text-slate-300"><strong>Graceful shutdown</strong>: Bun (and Node) need a few seconds to close connections. Always set a stop timeout (e.g. 10s in <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">ExecStop</code>) and in your app listen for <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">SIGTERM</code> and close the HTTP server before exiting.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Port conflicts</strong>: If you restart the container and the old one is still shutting down, you can get “address already in use”. Using <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">--rm</code> and a fixed container name in the unit avoids orphan containers; the stop timeout reduces the chance of overlap.</li>
<li class="ml-4 list-disc text-slate-300"><strong>Health check too heavy</strong>: Keep <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health</code> fast. If it hits the DB every time, a DB hiccup can mark the app unhealthy and trigger unnecessary restarts.</li></p><p class="text-slate-300 leading-relaxed mb-4"><h2 class="text-xl font-bold text-slate-100 mt-8 mb-3">One thing to do next</h2></p><p class="text-slate-300 leading-relaxed mb-4">Add a <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">/health</code> endpoint to your Bun app, wire it in Docker with HEALTHCHECK, and run the container under systemd with <code class="bg-slate-700/50 px-1.5 py-0.5 rounded text-cyan-300 text-sm">Restart=always</code>. Once that’s in place, you can iterate on zero-downtime and rolling updates without worrying about silent failures.</p><p class="text-slate-300 leading-relaxed mb-4"><hr class="border-slate-700 my-6" />
