Deploying Bun Apps in Production: Docker, systemd, and Zero-Downtime Updates

You shipped a Bun app locally and it flies. Then you put it on a server and wonder why it dies at 3 AM or why every deploy feels like a coin flip. Production is where the real work begins: containers, process managers, health checks, and updates without dropping requests.

This post walks through a practical path we use: Docker for build and run, systemd for supervision, HTTP health checks, and zero-downtime reloads so you can deploy Bun apps with confidence.

Why Docker and systemd together?

Docker gives you a consistent runtime and easy rollbacks (just point to a previous image). systemd on the host gives you restarts on crash, log rotation, and integration with the rest of the system (timers, network, etc.). We run the app inside a container and let systemd start, stop, and restart that container. That way you get both portability and robust process management.

Dockerfile that works for Bun

Keep the image small and the build cache effective. Use a multi-stage setup so the final image only has the runtime and your built artifacts.

Build stage

FROM oven/bun:1 AS builder
WORKDIR /app
COPY package.json bun.lockb ./
RUN bun install --frozen-lockfile
COPY . .
RUN bun run build
Run stage

FROM oven/bun:1-slim
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY package.json ./
EXPOSE 3000
USER bun
CMD ["bun", "run", "dist/index.js"]

Use bun:1-slim in production to shrink image size. Expose the port your app listens on (here 3000) and run as a non-root user.

Health checks inside the container

Your app should expose a cheap endpoint that only checks “am I alive and can I do the minimum work?” For example, a GET that returns 200 and maybe checks DB connectivity. No heavy logic.

// health.ts
export function healthHandler(req: Request): Response {
  // Optional: ping DB or cache here
  return new Response(JSON.stringify({ status: "ok", ts: Date.now() }), {
    headers: { "Content-Type": "application/json" },
    status: 200,
  });
}

In the Dockerfile, add a HEALTHCHECK so Docker (and orchestrators) can see when the process is unhealthy:

HEALTHCHECK --interval=15s --timeout=3s --start-period=5s --retries=2 \
  CMD wget -q -O - http://localhost:3000/health || exit 1

Adjust the port and path to match your app. Start period gives the app time to bootstrap before failing.

systemd unit to run the container

Run the container under systemd so it restarts on failure and starts on boot. Replace your-app and image tag with your names.

[Unit]
Description=Bun app in Docker
After=network-online.target docker.service
Requires=docker.service
[Service]
Type=simple
ExecStartPre=-/usr/bin/docker pull your-registry/your-app:latest
ExecStart=/usr/bin/docker run --rm --name bun-app -p 3000:3000 your-registry/your-app:latest
ExecStop=/usr/bin/docker stop -t 10 bun-app
Restart=always
RestartSec=5
[Install]
WantedBy=multi-user.target

Restart=always and RestartSec=5 mean systemd will bring the container back after a crash. ExecStop gives the process 10 seconds to shut down cleanly.

Zero-downtime updates

The goal is to deploy a new image without dropping in-flight requests. A simple approach:

  • Build and push the new image with a tag (e.g. latest or a version).
  • Run systemctl reload your-service or systemctl restart your-service during a low-traffic window, or use a reverse proxy (nginx, Caddy) in front of two instances and swap traffic.

    • For a single-instance setup, a brief restart is often acceptable: systemctl restart your-service. The health check ensures you only send traffic once the new process is up if you put the proxy in front and use health-check for routing.

    For true zero-downtime, run two containers (or two nodes), point the proxy at both, and do a rolling update: start the new container, wait for health to pass, then stop the old one. The proxy handles the switch.

    Gotchas we hit

  • Graceful shutdown: Bun (and Node) need a few seconds to close connections. Always set a stop timeout (e.g. 10s in ExecStop) and in your app listen for SIGTERM and close the HTTP server before exiting.
  • Port conflicts: If you restart the container and the old one is still shutting down, you can get “address already in use”. Using --rm and a fixed container name in the unit avoids orphan containers; the stop timeout reduces the chance of overlap.
  • Health check too heavy: Keep /health fast. If it hits the DB every time, a DB hiccup can mark the app unhealthy and trigger unnecessary restarts.

    • One thing to do next

    Add a /health endpoint to your Bun app, wire it in Docker with HEALTHCHECK, and run the container under systemd with Restart=always. Once that’s in place, you can iterate on zero-downtime and rolling updates without worrying about silent failures.
