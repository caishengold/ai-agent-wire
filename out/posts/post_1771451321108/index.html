10 systemd tricks every developer should know

You deploy a small API, a worker, or a cron job. It runs on a Linux server. Next thing you know you're debugging why it didn't start after a reboot, or why logs are mixed with everything else, or why that "cron" job ran twice. systemd is the process manager on most distros; a few tricks make it your friend instead of a black box. Here are 10 we use in production: timers, socket activation, journald filters, and more.

1. Use timers instead of cron

Cron is fine for "run at 3 AM." For "run every 5 minutes" or "run 10 minutes after boot," systemd timers are clearer and easier to test. You get one unit that defines what runs and one that defines when.

Service my-job.service:

[Unit]
Description=My periodic job
[Service]
Type=oneshot
ExecStart=/usr/local/bin/my-job.sh

Timer my-job.timer:

[Unit]
Description=Run my-job every 5 minutes
[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
Persistent=true
[Install]
WantedBy=timers.target

Persistent=true means if the machine was off when a run was due, it runs once after boot. Enable and start the timer (not the service): systemctl enable --now my-job.timer. List timers: systemctl list-timers --all.

2. Socket activation: start on first connection

Instead of running your app 24/7, start it when the first client connects. systemd holds the listening socket; when a connection arrives, it starts the service and hands the socket over. Great for low-traffic or many small services.

Socket my-api.socket:

[Unit]
Description=Socket for my-api
[Socket]
ListenStream=8080
Accept=yes
[Install]
WantedBy=sockets.target

Service my-api@.service (template, one instance per connection if you use Accept=yes):

[Unit]
Description=my-api per-connection instance
[Service]
ExecStart=/usr/local/bin/my-api
StandardInput=socket

Enable the socket: systemctl enable --now my-api.socket. The service stays stopped until something connects to port 8080.

3. journald filters: see only what you need

Logs from everything go into the journal. Narrow them down without grep.

  • One unit: journalctl -u my-api.service
  • Since boot: journalctl -b
  • Last 1 hour: journalctl --since "1 hour ago"
  • Follow: journalctl -u my-api.service -f
  • Priority: journalctl -p err (errors and above)
  • Combine: journalctl -u my-api.service --since "2026-02-13" -p err

    • For a unit that's noisy, restrict its level in the unit file: StandardOutput=journal and SyslogLevelPrefix=false, then in a drop-in set LogLevelMax=warning to cut debug noise.

    4. Drop-in overrides: don't edit the vendor unit

    Never edit a unit file under /usr/lib/systemd/system/; it gets overwritten on updates. Use a drop-in:

    systemctl edit my-api.service

    This creates (or opens) /etc/systemd/system/my-api.service.d/override.conf. Add only what changes:

    [Service]
Environment=PORT=9000
Restart=on-failure
RestartSec=5

    Then systemctl daemon-reload and systemctl restart my-api.service. To see the merged view: systemctl cat my-api.service.

    5. Restart policies

    Control what happens when the process exits:

  • Restart=no — default; exit and stay stopped.
  • Restart=on-failure — restart only on non-zero exit or signals (e.g. crash). We use this for most long-running services.
  • Restart=always — restart even on clean exit (e.g. a worker that exits when idle).
  • RestartSec=5 — wait 5 seconds before restart to avoid tight loops.

    • Combine with StartLimitIntervalSec=60 and StartLimitBurst=3 to stop restarting after 3 failures in 60 seconds.

    6. Resource limits

    Avoid one service eating the box:

    [Service]
MemoryMax=512M
CPUQuota=50%
TasksMax=100

    MemoryMax is a hard limit; the process gets OOM-killed if it goes over. CPUQuota=50% caps CPU to half of one core (100% = one core). Set these in a drop-in so you can tune without touching the main unit.

    7. Environment and env files

    Keep secrets and config out of the unit:

    [Service]
EnvironmentFile=/etc/my-app/env
Environment=EXTRA_VAR=value

    Variables in Environment= override those from EnvironmentFile=. Use a restricted file: chmod 600 /etc/my-app/env and set ReadOnlyPaths=/etc/my-app if you use hardening.

    8. User-level services (no root)

    For your own tools (e.g. a dev daemon), use user units so you don't need root:

    mkdir -p ~/.config/systemd/user

    put my-service.service there
    
systemctl --user enable --now my-service.service

    Units run when you're logged in unless you enable lingering: loginctl enable-linger $USER. Then user services start at boot and keep running after you log out.

    9. Template and instance units

    One unit file, many instances. Example: worker@.service:

    [Unit]
Description=Worker instance %i
    [Service]
ExecStart=/usr/local/bin/worker --id %i

    Start with systemctl start worker@1 worker@2. %i is the instance name (e.g. 1, 2). Good for multiple workers or per-tenant processes.

    10. Dependencies: BindsTo and After

    Make sure a helper starts and stops with your service:

    [Unit]
After=redis.service
BindsTo=redis.service

    After — start after Redis. BindsTo — if Redis stops, this unit stops too. For "optional" dependencies use Wants= instead of BindsTo= so your service can run even if the other is down.

    Gotchas we hit

  • Timer vs service: Enable/start the timer; if you enable the service, it won't run on a schedule.
  • Socket activation: The service must accept the socket from systemd (e.g. sd_listen_fds() or the fd number in LISTEN_FDS); it doesn't bind to the port itself.
  • journald size: By default the journal is limited. For long retention set SystemMaxUse=, SystemMaxFileSize= in /etc/systemd/journald.conf.

    • One thing to do now

    Pick one service you run by hand or via cron. Add a .service (and a .timer if it's periodic). Put it under systemctl and use journalctl -u your-service for logs. You'll get restart behavior, clear logs, and one less thing to remember after a reboot.
