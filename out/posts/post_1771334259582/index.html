Exploring Modular Architecture Patterns with Bun CLI for Scalable Web Applications

As applications grow, monolithic codebases become difficult to maintain. Developers find themselves wading through thousands of lines of tightly coupled code to make simple changes. Modular architecture provides a solution by breaking applications into independent, replaceable modules.

Bun, the all-in-one JavaScript runtime, ships with a built-in package manager and bundler. These tools make modular development practical without the overhead of traditional toolchains.

The Case for Modular Design

Raj Patel, a senior engineer at a Singapore-based logistics platform, faced this challenge during 2025-Q2. His team was building a multi-tenant API serving 200+ enterprise clients. Each client needed custom integrations with varying data formats, authentication schemes, and notification preferences.

The initial codebase was a single Express application with 15,000 lines. Adding a new integration required touching authentication, database models, and webhook handlers. Deployments became risky. A change in one area could cascade into unrelated features.

Raj's team restructured the application into modules:

  • Authentication module: OAuth2, API keys, and session management
  • Data transformation module: Format converters for client-specific schemas
  • Notification module: Email, SMS, and webhook dispatchers
  • Audit module: Logging and compliance tracking

    • Each module exposed a clean interface. Modules communicated through events, not direct imports. The codebase became testable. Teams could work in parallel without merge conflicts.

    Bun's Built-in Module Management

    Traditional Node.js workflows require separate tools: npm or yarn for package management, webpack or esbuild for bundling, Jest for testing. Bun consolidates these into a single binary.

    | Feature | Traditional Stack | Bun | |---------|------------------|-----| | Package manager | npm/yarn/pnpm | Built-in | | Bundler | webpack/esbuild/rollup | Built-in | | Test runner | Jest/Vitest | Built-in | | TypeScript | ts-node or transpile | Native | | Cold start | 2-5 seconds | <200ms | | Workspace support | Lerna/Rush/pnpm | Native bun workspaces |

    Bun's workspace support simplifies modular monorepos. You define workspaces in a root package.json:

    {
  "name": "logistics-platform",
  "workspaces": [
    "packages/",
    "integrations/"
  ],
  "scripts": {
    "dev": "bun run --filter '' dev",
    "test": "bun test",
    "build": "bun run --filter '' build"
  }
}

    Each module lives as an independent package with its own package.json, dependencies, and build configuration. Bun resolves workspace dependencies automatically.

    Pattern 1: Plugin Architecture

    A plugin architecture loads modules dynamically at runtime. This pattern works well when you have optional features or need third-party extensibility.

    Sofia Kim, building a document processing pipeline for a legal tech startup in 2025-09, needed to support multiple file formats. New formats emerged quarterly. Hardcoding converters would require frequent deployments.

    She implemented a plugin system using Bun's dynamic imports:

    // packages/core/src/plugin-manager.ts
import { readdir } from 'node:fs/promises';
import { join } from 'node:path';
    export interface FileConverter {
  name: string;
  supportedExtensions: string[];
  convert(input: Buffer): Promise;
}
    export class PluginManager {
  private converters = new Map();
      async loadPlugins(pluginsDir: string): Promise {
    const entries = await readdir(pluginsDir, { withFileTypes: true });
    
    for (const entry of entries) {
      if (entry.isDirectory()) {
        const pluginPath = join(pluginsDir, entry.name, 'index.ts');
        
        try {
          const module = await import(pluginPath);
          const converter: FileConverter = module.default;
          
          for (const ext of converter.supportedExtensions) {
            this.converters.set(ext.toLowerCase(), converter);
          }
          
          console.log(Loaded converter: ${converter.name});
        } catch (error) {
          console.error(Failed to load plugin ${entry.name}:, error);
        }
      }
    }
  }
      getConverter(extension: string): FileConverter | undefined {
    return this.converters.get(extension.toLowerCase());
  }
}

    Individual plugins implement the interface:

    // integrations/pdf-converter/index.ts
import type { FileConverter } from '@legaltech/core';
import { pdfToText } from 'pdf-parse';
    const pdfConverter: FileConverter = {
  name: 'PDF Text Extractor',
  supportedExtensions: ['.pdf'],
  
  async convert(input: Buffer): Promise {
    const text = await pdfToText(input);
    return Buffer.from(text, 'utf-8');
  }
};
    export default pdfConverter;

    Adding a new format requires dropping a folder into the integrations directory. No core code changes. No redeployment.

    Pattern 2: Domain-Driven Modules

    Domain-driven design organizes code around business capabilities. Each module owns its data, logic, and interfaces.

    Chen Wang's healthcare data platform on 2026-01-12 served hospitals, insurance providers, and researchers. Each user type accessed patient data differently:

  • Clinical module: Real-time vitals and medication tracking
  • Billing module: Insurance claims and payment processing
  • Research module: Anonymised aggregate datasets

    • Chen structured the codebase with clear boundaries:

    packages/
├── clinical/
│   ├── src/
│   │   ├── domain/
│   │   │   ├── patient.ts
│   │   │   ├── vitals.ts
│   │   │   └── medication.ts
│   │   ├── api/
│   │   │   └── routes.ts
│   │   └── persistence/
│   │       └── repository.ts
│   ├── package.json
│   └── tsconfig.json
├── billing/
│   └── ...
└── research/
    └── ...

    Each module has internal structure invisible to others. The clinical module exports only what external code needs:

    // packages/clinical/src/index.ts
export { Patient } from './domain/patient';
export { VitalsService } from './services/vitals';
export { createClinicalRoutes } from './api/routes';
    // Internal types stay hidden
// export { InternalCache } from './cache';

    Bun's bundler creates optimised builds per module:

    {
  "scripts": {
    "build": "bun build ./src/index.ts --outdir ./dist --target node"
  }
}

    Pattern 3: Event-Driven Communication

    Direct function calls create tight coupling. Events let modules react to changes without knowing the source.

    Priya Sharma's e-commerce platform on 2025-11-03 processed orders through multiple services. When a customer placed an order:

  • Inventory module checked stock
  • Payment module processed the charge
  • Shipping module created a label
  • Notification module sent confirmations

    • Direct API calls between services created a fragile dependency chain. If the shipping service was down, the entire order failed.

    She replaced synchronous calls with an event bus:

    // packages/event-bus/src/index.ts
type EventHandler = (payload: T) => void | Promise;
    export class EventBus {
  private handlers = new Map>>();
      on(event: string, handler: EventHandler): () => void {
    if (!this.handlers.has(event)) {
      this.handlers.set(event, new Set());
    }
    this.handlers.get(event)!.add(handler);
    
    return () => this.handlers.get(event)?.delete(handler);
  }
      async emit(event: string, payload: T): Promise {
    const handlers = this.handlers.get(event);
    if (!handlers) return;
    
    await Promise.all(
      Array.from(handlers).map(handler => 
        Promise.resolve(handler(payload)).catch(err => {
          console.error(Handler error for ${event}:, err);
        })
      )
    );
  }
}
    export const eventBus = new EventBus();

    Modules publish events without knowing subscribers:

    // packages/orders/src/service.ts
import { eventBus } from '@platform/event-bus';
    export async function createOrder(customerId: string, items: LineItem[]) {
  const order = await db.insert('orders', { customerId, items });
  
  await eventBus.emit('order.created', {
    orderId: order.id,
    customerId,
    items,
    timestamp: new Date().toISOString()
  });
  
  return order;
}

    Other modules subscribe independently:

    // packages/shipping/src/index.ts
import { eventBus } from '@platform/event-bus';
    eventBus.on('order.created', async ({ orderId, items }) => {
  const label = await generateShippingLabel(items);
  await saveLabel(orderId, label);
});

    If the shipping module is offline, the event persists in a queue (using Redis or similar) and processes when available.

    Testing Modular Code

    Bun's test runner works across workspaces. You run tests from the root:

    bun test

    Or filter to specific modules:

    bun test packages/clinical
bun test --filter "converter"

    Mock external modules in tests:

    // packages/orders/src/service.test.ts
import { test, expect, mock } from 'bun:test';
import { createOrder } from './service';
    mock.module('@platform/event-bus', () => ({
  eventBus: {
    emit: mock(() => Promise.resolve())
  }
}));
    test('createOrder emits event', async () => {
  const order = await createOrder('cust-123', [{ sku: 'ABC', qty: 2 }]);
  expect(order.id).toBeDefined();
});

    Performance Considerations

    Modular architectures add overhead. Multiple node_modules directories increase disk usage. Dynamic imports add runtime cost.

    Bun mitigates this through:

  • Global module cache: Workspace dependencies are deduplicated
  • Fast startup: Cold starts under 200ms make dynamic loading practical
  • Tree shaking: Dead code is eliminated during bundling

    • Monitor bundle sizes:

    bun build ./src/index.ts --outdir ./dist --analyze

    Lessons Learned

  • Start with 2-3 modules and extract more as patterns emerge — premature modularisation wastes time
  • Define module boundaries around business capabilities, not technical layers
  • Document the public API of each module — other developers depend on these contracts
  • Implement health checks per module — failures should be isolated
  • Use workspace scripts for cross-module operations — bun run --filter '' build runs all builds in dependency order

    • Actionable Takeaways

  • Audit your current architecture — Identify the top 3 business capabilities that would benefit from independent modules
  • Set up a Bun workspace — Move one existing feature into its own package as an experiment
  • Implement an event bus — Replace one direct service call with event-driven communication
  • Measure module coupling — Track which modules import from each other; reduce cross-module dependencies
  • Document module APIs — Create a README in each package folder explaining what it exports and why
