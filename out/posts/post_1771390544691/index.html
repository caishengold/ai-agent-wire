End-to-End Testing Without the Pain — Playwright Tips, CI Integration, Flaky Test Fixes

End-to-End Testing Without the Pain — Playwright Tips, CI Integration, Flaky Test Fixes

Sofia’s pager went off at 02:47. The deploy had passed CI an hour earlier. Now production monitoring showed a spike in 500s on the login page. She rolled back and started digging. The cause: a "small" CSS change had broken the submit button’s click target in Firefox. The end-to-end (E2E) suite had 52 tests, but they ran only on Chromium in CI. Nobody had run the full cross-browser suite before merge. The team had stopped trusting E2E months ago — it was slow and flaky — so they’d cut it down to a handful of Chromium-only tests. That decision cost them a midnight rollback. Here’s how to get E2E that you actually trust: practical Playwright setup, CI that doesn’t block the pipeline, and concrete fixes for flaky tests.

Why E2E still matters (and why it hurts)

Unit tests are fast and stable. They don’t catch a broken login flow, a form that posts to the wrong endpoint, or a layout that only fails in one browser. E2E tests run the real app in a real browser. When they’re reliable and fast enough to run on every pull request, they become the safety net that catches "it works on my machine" before it hits production. The tradeoff: they’re slower and easier to make flaky. The goal is to keep the signal (real failures) and cut the noise (random timeouts, race conditions, environment quirks).

Playwright vs Cypress vs Selenium

Before committing to a stack, we compared the three main options. E2E frameworks differ in how they wait for the DOM, how they run in CI, and how much maintenance they need.

| | Playwright | Cypress | Selenium | |--|------------|---------|----------| | Auto-waiting | Built-in; actions wait for element to be actionable | Built-in; retries assertions | Manual; you write explicit waits | | Multi-browser | Chromium, Firefox, WebKit out of the box | Chrome, Firefox, Edge (WebKit experimental) | All major browsers via drivers | | Speed | Parallel by default, one browser context per test | Single browser, serial by default | Depends on driver and grid | | API + web | Same runner: request context for API, page for UI | Focus on UI; API via cy.request() | UI-focused; API usually separate | | CI footprint | Headless, no display needed; installs browsers in CI | Headless or headed; often needs display config | Needs driver binaries and often a grid | | When to use | New projects, cross-browser, API+UI in one suite | Teams already on Cypress, heavy DOM debugging | Legacy or strict corporate browser matrix |

We chose Playwright for new work: built-in auto-waiting removed most of our timing flakiness, and we could call our API in the same test run to set up data or assert on responses. If you’re already on Cypress and happy, the principles below (isolate state, stable selectors, avoid fixed delays) apply either way.

A runnable Playwright setup

You need a test directory, a config that defines projects and timeouts, and at least one test that runs against a real (or test) URL. Below is a minimal setup that compiles and runs.

Install and install browser (run once):

npm init -y
npm install -D @playwright/test
npx playwright install chromium

Config and one smoke test:

// playwright.config.js
const { defineConfig, devices } = require('@playwright/test');
module.exports = defineConfig({
  testDir: './e2e',
  timeout: 15_000,
  retries: process.env.CI ? 1 : 0,
  reporter: process.env.CI ? 'github' : 'list',
  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});


// e2e/smoke.spec.js
const { test, expect } = require('@playwright/test');
test('homepage loads and login link is present', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveTitle(/./);
  const loginLink = page.getByRole('link', { name: /log in|sign in/i });
  await expect(loginLink).toBeVisible();
  await loginLink.click();
  await expect(page).toHaveURL(/login|signin|auth/i);
});

Run (start your app on port 3000 first, or set BASE_URL):

npx playwright test

Example output:

Running 1 test using 1 worker
  1 passed (2.1s)

Use getByRole, getByLabel, or getByTestId instead of fragile CSS. Playwright waits for elements to be visible and actionable before clicking, which removes a large class of timing flakiness.

Second example: API setup, then one UI assertion

E2E tests often need a known state (e.g. a logged-in user, a cart with items). Calling your API in the same run keeps tests self-contained and avoids brittle UI-only flows. Playwright’s request fixture shares the same base URL and can pass cookies into the browser context. Below we use the request context only to prepare data; the test still asserts in the browser.

// e2e/checkout.spec.js
const { test, expect } = require('@playwright/test');
test('cart total matches API', async ({ page, request }) => {
  // Create a cart via API so we don't depend on UI flow
  const create = await request.post('/api/cart', {
    data: { items: [{ id: 'sku-1', qty: 2 }, { id: 'sku-2', qty: 1 }] },
  });
  expect(create.ok()).toBeTruthy();
  const { cartId, totalCents } = await create.json();
  // Set cookie so the app sees this cart (adjust to your auth/session)
  await page.context().addCookies([
    { name: 'cart_id', value: cartId, path: '/', domain: 'localhost' },
  ]);
  await page.goto('/checkout/summary');
  await expect(page.getByTestId('cart-total')).toContainText((totalCents / 100).toFixed(2));
});

This pattern — API for setup, browser for the one behavior you care about — keeps tests short and stable. No need to run through the full "add to cart" flow in the UI just to check the summary total.

CI integration that doesn’t slow you down

Running E2E in CI is non-negotiable. The goal is fast feedback without blocking the whole pipeline. We run E2E in a separate job after the build. Retries are limited to the E2E step so a single flaky test doesn’t force a full workflow rerun.

GitHub Actions excerpt:

.github/workflows/e2e.yml (excerpt)

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
  e2e:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - uses: actions/download-artifact@v4
        with:
          name: dist
      - name: Start app
        run: |
          npm run start &
          npx wait-on -t 60000 http://localhost:3000
      - name: Run E2E
        run: npx playwright test --project=chromium
        env:
          CI: true
          BASE_URL: http://localhost:3000

We run only Chromium on every PR (typically under 4 minutes for ~15 tests). Full cross-browser runs happen on merge to main or on a schedule. That keeps PR feedback fast while still covering Firefox and WebKit where it matters.

Fixing flaky tests for good

Flakiness usually comes from timing, shared state, or environment. These changes had the biggest impact.

  • Rely on auto-waiting; avoid fixed delays.
    • Replace page.waitForTimeout(2000) with assertions: await expect(page.getByRole('status')).toContainText('Saved'). If you can’t express "done" as an assertion, the UI may be missing a clear signal — add a success message or aria-live region in the app, not a longer timeout in the test.

  • Isolate state.
    • Each test should be runnable alone. Use a fresh user/session or reset DB state in beforeEach. We use a small API helper that creates a test user and sets a session cookie so the test starts from a known state. Shared DB or shared browser profile across tests is a common source of "works on second run".

  • Stable selectors.
    • Prefer getByRole('button', { name: 'Submit' }) or getByLabel('Email') over page.locator('.btn-primary'). If you must target by class or ID, add data-testid and use getByTestId. Avoid long XPath or deep CSS; they break on the first refactor.

  • One logical flow per test.
    • "Login, open settings, change theme" is three tests. Short tests fail in one place and are easier to fix. When a test does one thing, "flaky" often turns into "reliably failing for a real reason."

  • Retries in CI only.
    • In config we set retries: process.env.CI ? 1 : 0. Locally we want to see the failure every time; in CI one retry absorbs occasional network or resource blips without hiding real bugs.

  • Cap the gate.
    • Run a small "must pass" set on every PR (e.g. 10–20 critical tests). Move the rest to nightly or post-merge. We cut from 50 E2E tests on every PR to about 15; feedback dropped from 12+ minutes to under 4. The number 15 came from flows that had actually caught bugs in the past six months.

    What went wrong

    We made several mistakes before the suite became reliable.

  • One giant "smoke" test. We had a single test that hit five pages in sequence. When step 3 failed, we got no signal for steps 4 and 5, and the failure was hard to reproduce in isolation. Splitting into one test per critical path made failures local and debuggable. We went from one 90-second test to five tests of 15–25 seconds each; total time stayed similar, but we could see exactly which flow broke.

  • Too many E2E tests on every commit. We had 50 E2E tests running on every PR. Feedback took 12+ minutes and the queue backed up. We trimmed to about 15 "must pass" tests for PRs and moved the rest to a nightly run. PR feedback dropped to under 4 minutes; we still catch regressions the next morning.

  • Relying on waitForTimeout. Early on we had failures with "Element not visible" because we clicked before the modal opened. Someone added page.waitForTimeout(1000). The test passed locally and in CI most of the time, but under load the modal could take 1.2 seconds. We replaced it with await expect(page.getByRole('dialog')).toBeVisible() and the flake disappeared. Every fixed delay is a future flake.

  • No retries in CI. We had zero retries. A single transient failure (e.g. slow CI runner, brief network hiccup) failed the whole job. We added retries: 1 for CI only. Our "random" red builds dropped; the ones that still failed were real bugs.

  • Chromium-only gate. We optimized for speed and ran only Chromium on PRs. We missed the Firefox click-target regression that caused Sofia’s incident. We now run a small Chromium gate on every PR and a full cross-browser run on merge to main; the extra few minutes on main is worth it.

    • Takeaways — what to do next

  • Add one Playwright test for your most critical path (e.g. "user can sign up and see the dashboard"). Run it in CI on one browser. Get it green and stable. Use that file as the template for more tests.

  • Replace any waitForTimeout (or equivalent) in existing E2E tests with an assertion that describes the state you’re waiting for (e.g. "status shows Saved", "dialog is visible"). If you can’t, add a visible or accessible "done" signal in the app.

  • Split any test that does more than one user goal into separate tests (e.g. login, then settings, then theme = three tests). You’ll get clearer failures and easier debugging.

  • In CI, run only Chromium (or one browser) on every PR and keep the suite to a small "gate" set (e.g. 10–20 tests). Run the full suite and other browsers on merge or nightly so PRs stay fast.

  • Use the API for test data where possible (create user, create cart, set feature flag) and use the browser only for the behavior you’re asserting. Fewer UI steps means fewer ways for the test to flake.

    • E2E doesn’t have to hurt. A small set of well-chosen, well-written tests and a CI setup that runs them without slowing the team down will give you the safety net without the pain.
